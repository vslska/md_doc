## Конкурентность (Concurrency) vs Параллелизм (Parallelism)

Фундаментальное различие между этими понятиями лежит в архитектурной плоскости: **структурирование программы** против **физического исполнения**.


```
                  Архитектура выполнения задач
                               │
  ┌────────────────────────────┼────────────────────────────┐
  ▼                                                         ▼
[ Concurrency (Конкурентность) ]          [ Parallelism (Параллелизм) ]
Логическое перекрытие во времени.          Физическое одновременное исполнение.
Работа с несколькими задачами              Выполнение нескольких вычислений
одновременно (переключение контекста).     на разной аппаратуре (ядра/процессоры).
```

### Сравнительный анализ моделей

|**Параметр**|**Concurrency (Конкурентность)**|**Parallelism (Параллелизм)**|
|---|---|---|
|**Суть**|Способ **структурирования** приложения для обработки нескольких задач в перекрывающиеся интервалы времени.|Способ **одновременного выполнения** нескольких вычислений на разных физических ресурсах.|
|**Ключевая цель**|Эффективное управление простоями при ожидании операций ввода-вывода (I/O-bound).|Линейное ускорение вычислительно сложных задач (CPU-bound).|
|**Аппаратные требования**|Работает даже на single-core процессорах за счет тайм-шеринга (переключения контекста).|Требует multi-core CPU, мультипроцессорных систем или GPU/TPU кластеров.|
|**Типовые инструменты**|Event Loop, `async/await`, кооперативные сопрограммы, горутины, `gevent`.|`multiprocessing`, GPU-кёрнелы (CUDA), SIMD-инструкции, кластерные вычисления.|

> **Формула Пайка (Rob Pike):** _«Concurrency is about dealing with a lot of things at once. Parallelism is about doing a lot of things at once.»_ (Конкурентность — это умение иметь дело со множеством вещей одновременно; параллелизм — это умение делать множество вещей одновременно).

## Модели исполнения и выполнения задач

Выбор модели зависит от узких мест приложения (I/O-bound или CPU-bound) и особенностей среды выполнения.

```
                          Модели исполнения
                                  │
  ┌───────────────────────┬───────┴───────┬───────────────────────┐
  ▼                       ▼               ▼                       ▼
[ Многопроцессность ]  [ Многопоточность ] [ Асинхронность ]    [ Распределенные ]
OS Processes            OS / OS Threads    App Event Loop      Сетевой кластер
```

|**Модель исполнения**|**Уровень изоляции**|**Плюсы**|**Минусы / Ограничения**|**Примеры реализации**|
|---|---|---|---|---|
|**Многопроцессность**|Операционная система (OS)|Полная память и изоляция процессов; обход блокировок типа CPython GIL.|Вычислительные накладные расходы на IPC (Inter-Process Communication) и переключение контекста; высокий расход RAM.|`multiprocessing`, `Gunicorn sync workers`.|
|**Многопоточность**|ОС / Исполняемая среда|Общая память, легкий вес потоков по сравнению с процессами.|Опасность гонки состояний (Race conditions), взаимных блокировок (Deadlocks); в CPython ограничена GIL для CPU-задач.|`threading`, `pthread`, Java Threads.|
|**Асинхронность (Event-driven)**|Приложение / Runtime|Кооперативная многозадачность с минимальным расходом памяти (один поток).|Любая блокирующая синхронная операция останавливает весь Event Loop; сложность отладки stack trace.|`asyncio`, Node.js, `gevent`, `uvloop`.|
|**Распределенные вычисления**|Сетевой слой|Неограниченное горизонтальное масштабирование ресурсов.|Издержки на сериализацию данных, задержки сети (Network latency), необходимость обработки сбоев узлов.|`Celery`, `Apache Spark`, `Ray`.|

## Масштабируемость (Scalability) и фундаментальные законы

**Масштабируемость** — это способность системы наращивать производительность при добавлении аппаратных ресурсов.

```
                        Типы масштабирования
                                 │
  ┌──────────────────────────────┼──────────────────────────────┐
  ▼                              ▼                              ▼
[ Scale-Up (Вертикальное) ]    [ Scale-Out (Горизонтальное) ] [ Шардирование ]
Увеличение CPU/RAM/SSD          Добавление узлов/серверов      Функциональное / 
на одном узле.                  в единый кластер.              По ключу данных.
```

### Стратегии масштабирования

- **Вертикальное масштабирование (Scale-up):** Увеличение вычислительных мощностей одной физической или виртуальной машины (CPU, RAM, NVMe). Имеет аппаратный предел и высокую экспоненциальную стоимость на топовых конфигурациях.

- **Горизонтальное масштабирование (Scale-out):** Добавление новых экземпляров (узлов) в пул и распределение нагрузки через балансировщик (Nginx, HAProxy, NLB).

- **Функциональное шардирование:** Декомпозиция системы на изолированные сервисы по доменной области (Bounded Context в DDD).

- **Шардирование данных (Data Sharding):** Горизонтальное разделение монолитной базы данных на несколько узлов по ключу шардирования (например, `hash(user_id) % N`).


### Теоретические пределы и законы распределенных систем

#### Закон Амдала (Amdahl's Law)

Определяет максимальный прирост производительности системы при параллельной обработке, который ограничен последовательной частью программы:

$$S(N) = \frac{1}{(1 - P) + \frac{P}{N}}$$

_где $P$ — доля параллелизуемого кода, $N$ — количество ядер процессора._

> **Вывод:** Если 10% кода исполняется последовательно ($P = 0.9$), максимальное ускорение системы не сможет превысить **10 раз**, даже при бесконечном количестве ядер.

#### Закон Густавсона-Барсиса (Gustafson's Law)

Показывает, что при увеличении объема входной задачи параллельная часть растет быстрее последовательной, что позволяет достигать практически линейного ускорения на больших объемах данных.

#### CAP-теорема (Brewer's Theorem)

В любой распределенной системе хранения данных при возникновении сетевого расщепления (Partition Tolerance) невозможно одновременно обеспечить более двух из трех свойств:

```
                     C (Consistency)
                      /\
                     /  \
                    /    \
                   /  CP  \
                  /        \
  A (Availability)──────────P (Partition Tolerance)
              AP
```

- **Consistency (Согласованность):** Любое чтение возвращает самую последнюю запись или ошибку.

- **Availability (Доступность):** Каждый несбойный узел возвращает успешный ответ (без гарантии актуальности).

- **Partition tolerance (Устойчивость к расщеплению):** Система продолжает функционировать при потере связи между узлами.


## Практический инженерный регламент

1. **Профилирование перед архитектурными изменениями:**

    Не закладывайте горизонтальное масштабирование до выявления узких мест (Bottlenecks). В 90% случаев проблемы кроются в неоптимальных SQL-запросах, отсутствии индексов или блокировках на уровне СУБД.

2. **Асинхронность не ускоряет CPU-bound вычисления:**

    Асинхронные фреймворки экономируют ресурсы потоков во время ожидания сетевых ответов (I/O), но тяжелые математические вычисления блокируют Event Loop.

3. **Минимизация распределенных межсервисных блокировок:**

    Избегайте распределенных транзакций (2PC / Two-Phase Commit) и распределенных блокировок (`Redlock`) там, где возможно применить модель событийной согласованности (Eventual Consistency / Saga Pattern).

4. **Управление состоянием (Stateless Architecture):**

    Для эффективного Scale-out держите слой приложений `stateless` (без сохранения состояния сессии на локальном диске или в памяти процесса). Переносите состояние в быстрые внешние хранилища (Redis / Memcached).
