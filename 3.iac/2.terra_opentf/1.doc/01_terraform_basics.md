# Основы Terraform и язык HCL

---

## Теория: Ядро Terraform

**Terraform** (и его форк OpenTofu) — это инструмент IaC от HashiCorp. Он позволяет описывать инфраструктуру (ВМ, сети, диски) декларативно, используя язык **HCL** (HashiCorp Configuration Language).

### Компоненты

| Компонент                       | Что это                                                                                | Зачем нужен                                                                                                                                    |
| ------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Configuration Files** (`.tf`) | Файлы с кодом на HCL.                                                                  | Хранят описание ресурсов, переменных и настроек.                                                                                               |
| **Providers** (Провайдеры)      | Плагины-адаптеры (например, `yandex`, `aws`, `docker`).                                | Служат мостом между HCL-кодом и API облачного провайдера.                                                                                      |
| **Resources** (Ресурсы)         | Конкретные объекты инфраструктуры (ВМ, диск, сеть).                                    | То, чем Terraform управляет (создает, меняет, удаляет).                                                                                        |
| **State** (Состояние)           | Файл `terraform.tfstate` (или удаленное хранилище, например S3).                       | База данных Terraform. Хранит сопоставление твоего кода с реальными ID ресурсов в облаке.                                                      |
| **Provisioners** (Провижнеры)   | Скрипты, выполняемые *после* создания ресурса (например, `local-exec`, `remote-exec`). | Для первоначальной настройки (копирование файлов, запуск команд). *Примечание: в современной практике чаще используют cloud-init или Ansible.* |

## Синтаксис HCL (HashiCorp Configuration Language)

HCL — **декларативный** язык. Ты описываешь **желаемое конечное состояние** ("мне нужна ВМ с таким-то образом"), а не пошаговый алгоритм действий ("создай ВМ, потом подожди, потом создай диск").

### Основные элементы синтаксиса

#### 1. Блоки (Blocks)
Базовая единица HCL. Начинается с типа блока, названия и фигурных скобок.
```hcl
# Блок data (получение информации о существующем ресурсе)
data "yandex_compute_image" "ubuntu" {
  family = "ubuntu-2204-lts"
}
```

#### 2. Атрибуты (Attributes)
Пары `ключ = значение` внутри блоков.
```hcl
# Блок resource (создание нового ресурса)
resource "yandex_compute_snapshot" "default" {
  name           = "test-snapshot"
  source_disk_id = "test_disk_id"
}
```

#### 3. Переменные (Variables)
Параметризация кода, чтобы не хардкодить значения.
```hcl
variable "zone" {
  type        = string
  default     = "ru-central1-a"
  description = "Зона доступности Yandex Cloud"
}
```
*Использование:* `zone = var.zone`

#### 4. Выходные значения (Outputs)
Данные, которые Terraform выведет в консоль после `apply`. Полезно для передачи данных в другие скрипты или модули.
```hcl
output "image_id" {
  description = "ID найденного образа"
  value       = data.yandex_compute_image.ubuntu.image_id
}
```

## Критически важные правила (Best Practices)

### 1. Агностицизм имен файлов
Terraform **не зависит от имени `.tf` файла**. При запуске он склеивает **все** `.tf`-файлы в текущей директории в один логический конфигурационный контекст.

**Рекомендуемая структура (для порядка, а не для работы):**
```text
├── main.tf       # Основные ресурсы
├── variables.tf  # Объявление переменных (variable)
├── terraform.tfvars # Значения переменных (не коммитить в git!)
├── outputs.tf    # Выходные данные (output)
└── provider.tf   # Настройка провайдера (terraform { required_providers { ... } })
```

### 2. Визуальная проверка зависимостей (Mental Check)
Перед запуском `terraform apply` всегда мысленно проверяй цепочку зависимостей и **зоны доступности**. Ресурсы должны быть в одной зоне, если это требуется.

> **Чек-лист перед apply:**
> 1. Диск создан в зоне `ru-central1-a`?
> 2. ВМ создана в зоне `ru-central1-a` и ссылается на этот диск?
> 3. Подсеть для ВМ тоже находится в `ru-central1-a`?
> *Если да → OK. Если нет → будет ошибка при планировании.*

## Базовый рабочий процесс (Workflow)

Хотя в этом файле нет команд, важно помнить стандартный цикл, который ты будешь использовать на практике:

1. `terraform init` — инициализация (скачивание провайдеров).
2. `terraform fmt` - форматирование кода (приведение к стандарту).
3. `terraform validate` — проверка синтаксиса.
4. `terraform plan` — просмотр плана изменений (что будет создано/удалено).
5. `terraform apply` — применение изменений.
6. `terraform destroy` — удаление всей инфраструктуры, описанной в коде.

## 💡 Главный вывод

Terraform — это не просто "скрипт для создания серверов". Это **система управления состоянием**. Ты описываешь *что* ты хочешь получить, а Terraform сам вычисляет разницу между тем, что есть в `state`, и тем, что написано в `.tf` файлах, и строит план действий для устранения этой разницы.
