## 📚 Теория: Основной жизненный цикл (The Core Workflow)

Работа с Terraform — это не просто написание и последовательное выполнение скрипта. Это итеративный процесс функционирования **конечного автомата**, цель которого — привести состояние реальной облачной инфраструктуры (_Actual State_) в строгое соответствие с твоим декларативным кодом (_Desired State_).

```
[ Код HCL ] ──(init)──> [ Загрузка плагинов ] ──(plan)──> [ Расчет графа / Дифф ] ──(apply)──> [ API Облака ]
```

---

### 1. Write / Init (Написание и Инициализация)

Ты создаешь конфигурационные `.tf`-файлы или разворачиваешь существующий код из репозитория Git. Любое действие в новой или измененной рабочей директории начинается с инициализации окружения.

bash

```
terraform init
```

Что происходит на низком уровне:

- **Инициализация Backend (Стейта):** Terraform считывает блок `terraform { backend "..." {} }`. Он проверяет доступность хранилища (локальный диск, AWS S3, Yandex Object Storage) и создает структуру для отслеживания ресурсов. Если настроен удаленный бэкенд, инициализируется механизм блокировок (например, через DynamoDB), предотвращающий одновременный запуск кода разными инженерами. 
- **Загрузка провайдеров (Plugins):** Инспектируется блок `required_providers`. Движок обращается к глобальному реестру (Terraform Registry), скачивает бинарные файлы плагинов под текущую ОС/архитектуру и складывает их в локальный кэш `.terraform/providers/`. 
- **Загрузка модулей:** Проводятся парсинг и локализация всех внешних зависимостей, объявленных через блоки `module`. 

> ⚠️ **Техническое правило:** Команда `terraform init` полностью **идемпотентна** (безопасна для многократного вызова). Ее необходимо перезапускать каждый раз, когда ты изменяешь версию провайдера, добавляешь новый плагин или подключаешь новый внешний модуль.

### 2. Plan (Планирование и Сборка графа)

Команда генерации спеки изменений. Это сугубо аналитический шаг без внесения деструктивных изменений в облачную среду.

bash

```
terraform plan
```

Use code with caution.

Что происходит под капотом (Важное дополнение):

1. **Этап Refresh (Актуализация):** Перед расчетом изменений Terraform в режиме реального времени делает пассивные `GET`/`LIST` запросы к API провайдера (например, Yandex Cloud), чтобы обновить информацию в памяти о существующих ресурсах. Если кто-то вручную удалил сервер через веб-консоль, Terraform зафиксирует это расхождение (_Drift_)
2. **Построение DAG (Направленного ациклического графа):** На основе явных зависимостей (`depends_on`) и неявных ссылок (например, `network_id = yandex_vpc_network.default.id`) движок вычисляет строгую математическую последовательность создания, изменения и удаления объектов.
3. **Расчет диффа:** На экран выводится разница между текущим состоянием инфраструктуры с учетом рефреша и тем, что описано в коде.

Маркеры плана:

- `+ create` — ресурс будет создан с нуля.
- `~ update in-place` — изменятся только отдельные параметры (например, размер RAM на ВМ) без уничтожения самого объекта.
- `- destroy` — ресурс будет полностью удален.
- `-/+ replace` — **самый опасный маркер**. Означает, что измененный тобой параметр (например, имя зоны доступности диска или образ ОС) невозможно применить к текущему объекту. Terraform будет вынужден сначала полностью удалить старый ресурс, а затем создать его заново.

---

3. Apply (Применение и Конвергенция)

Трансляция вычисленного графа в реальные императивные запросы к API облачной платформы. 

```
terraform apply
```

Механизм выполнения:

- Выполняется повторный неявный `plan` для защиты от изменений, которые могли произойти в облаке за секунды между твоим ручным планированием и применением.
- Запрашивается интерактивное подтверждение (`yes`).
- **Параллелизация выполнения:** На основе построенного графа ресурсов Terraform начинает отправлять конкурентные запросы к API. Объекты, не зависящие друг от друга (например, две разные изолированные сети), будут создаваться одновременно.
- **Транзакционная запись стейта:** Как только API возвращает успешный статус (код `201 Created`), Terraform незамедлительно фиксирует физические параметры (ID, MAC-адреса, выданные IP) в файл состояния `terraform.tfstate`. Если в процессе упадет сеть или произойдет сбой на середине пути, стейт не повредится — в нем останется ровно то, что API успел успешно подтвердить.

## 🔄 Управление изменениями (Change)

Когда ты меняешь код `.tf` и запускаешь `plan`, Terraform сравнивает желаемое состояние с текущим `state`. Изменения маркируются специальными префиксами:

| Префикс | Значение | Пример |
|---------|----------|--------|
| `+` | **Создание** нового ресурса. | Новая виртуальная машина или диск. |
| `~` | **Изменение на месте (in-place update)**. Ресурс не пересоздается, меняются только его атрибуты. | Изменение имени ВМ или добавление метки (tags). |
| `-` | **Удаление** ресурса. | Ресурс удален из кода `.tf`. |
| `-/+` | **Замена (Replace)**. Ресурс будет сначала уничтожен (`-`), а затем создан заново (`+`). | Изменение неизменяемых параметров (например, типа диска или зоны доступности). |

> ⚠️ **Внимание к `-/+`**: Если ты видишь этот префикс для критичного ресурса (например, базы данных), это означает **потерю данных** (если диск не вынесен в отдельный ресурс). Всегда читай план внимательно!

**Принудительная замена**: Если ресурс «завис» или его нужно пересоздать вручную, можно использовать флаг:
```bash
terraform apply -replace="yandex_compute_instance.vm"
```

## 🗑️ Уничтожение (Destroy)

Terraform управляет жизненным циклом ресурсов. В отличие от облачной консоли, где ВМ можно просто «остановить» (Stop), Terraform оперирует фактом существования ресурса. 

> 💡 **Золотое правило экономии**: Если ресурс не нужен, его нужно **удалить**, а не останавливать. Остановленная ВМ в большинстве облаков (включая Yandex Cloud) продолжает тарифицироваться за выделенные диски и зарезервированные ресурсы.

Команда для удаления всей инфраструктуры, описанной в текущей директории:
```bash
terraform destroy
```
*Также требует подтверждения `yes`. Terraform построит обратный план зависимостей (сначала удалит ВМ, потом диск, потом сеть).*

---

## Best Practices (Золотые правила Workflow)

1. **Никогда не применяй `apply` без `plan`**. В CI/CD это разделяют на два разных шага (или используют `terraform apply -auto-approve` только после успешного и проверенного `plan`).
2. **Храни State безопасно**. Никогда не коммить `terraform.tfstate` в Git. Используй удаленный бэкенд (S3, YC Object Storage) с блокировкой (state locking).
3. **Проверяй зависимости визуально**. Перед `apply` мысленно пройди по цепочке: *Диск → в той же зоне? → ВМ → в той же зоне? → Подсеть → OK*.
4. **Используй систему контроля версий (Git)**. Код Terraform — это такой же код, как и приложение. Он должен проходить code review.

## Профессиональный инструментарий и автоматизация

В реальной практике инженеры автоматизируют рутинные проверки и используют расширенный набор команд для снижения рисков.

Скорая помощь и валидация перед коммитом

- **`terraform fmt` (Форматирование):** Приводит код к единому стандарту HCL (выравнивание, отступы, синтаксический сахар). Обязательно настраивается как Pre-commit hook в Git, чтобы в репозиторий не попадал «кривой» код.
- **`terraform validate` (Статический анализ):** Проверяет синтаксическую корректность, правильность типов данных переменных и наличие обязательных аргументов в блоках ресурсов без обращения к API провайдера и стейту. 

Продвинутые техники безопасного рана

1. **Изоляция планов через артефакты:**  
    В продакшене никогда не запускают просто `terraform apply`. План сначала сохраняют в бинарный файл-слепок, а затем применяют именно его. Это гарантирует, что применится ровно то, что ты отсмотрел глазами:
    
    ```
    terraform plan -out=tfplan.binary
    terraform apply tfplan.binary
    ```
    
    
2. **Борьба с дрейфом параметров (`-refresh-only`):**  
    Если нужно синхронизировать стейт-файл с реальностью (например, кто-то поменял тег руками в панели облака) без изменения самой инфраструктуры, используют специальный режим таргетирования:
    

    
    ```
    terraform plan -refresh-only
    ```

    
3. **Безопасное уничтожение (`terraform destroy`):**  
    Эквивалент удаления всей созданной инфраструктуры. Команда полностью идентична генерации плана, где абсолютно у всех ресурсов стоит маркер `- destroy`. Чтобы случайно не удалить базу данных, всегда прописывай мета-аргумент внутри критических ресурсов:
    
    hcl
    
    ```
    lifecycle {
      prevent_destroy = true
    }
    ```

## Главный вывод

Terraform Workflow — это цикл **предсказуемости**. Команда `plan` дает тебе возможность увидеть будущее, а `apply` делает это будущее реальностью, фиксируя его в `state`. Твоя главная задача как инженера — внимательно читать вывод `plan` и не допускать случайных `-/+` для критичных данных.
