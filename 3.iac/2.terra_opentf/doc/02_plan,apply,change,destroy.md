## 📚 Теория: Архитектура Core Workflow

Жизненный цикл Terraform базируется на концепции **конечного автомата**. Его ключевая задача — обеспечить сходимость (конвергенцию) между тремя средами данных:

1. **Desired State** — целевая топология, объявленная инженером в конфигурационных файлах `*.tf`.
2. **Prior State** — сохраненный слепок метаданных в файле состояния `terraform.tfstate`.
3. **Actual State** — реальное состояние инфраструктуры, запрашиваемое напрямую у REST API облачного провайдера.

```
[ Исходный код HCL ] ──(init)──> [ Загрузка Плагинов ] ──(plan)──> [ Сборка DAG / Расчет Диффа ] ──(apply)──> [ Вызовы REST API ]
```

---

### 1. Write / Init (Инициализация рантайма)

Любая сессия в рабочей директории, содержащей конфигурацию `*.tf`, начинается с фазы инициализации окружения.

```bash
terraform init
```

Use code with caution.

Системные процессы на низком уровне:

- **Инициализация Backend (Стейт-движка):** Разбор блока `terraform { backend "..." {} }`. Движок валидирует доступность персистентного хранилища (Local, AWS S3, Yandex Object Storage). На удаленных бэкендах инициализируется распределенный механизм распределительных блокировок (`State Locking`), предотвращающий конкурентную запись и повреждение JSON-схемы стейта несколькими воркерами пайплайна.
- **Загрузка провайдеров (gRPC Plugins):** Инспектируется манифест зависимостей `required_providers`. Terraform Core обращается к upstream-реестру (Terraform Registry), скачивает скомпилированные бинарные файлы плагинов под текущую архитектуру ОС и кэширует их в директорию `.terraform/providers/`.
- **Локализация модулей:** Производится парсинг, скачивание и линковка локального или удаленного исходного кода, объявленного в блоках `module`.

> ⚠️ **Техническое свойство:** Команда `terraform init` полностью **идемпотентна**. Перезапуск является обязательным триггером при любой модификации версий плагина, смене конфигурации бэкенда или объявлении новых модулей.

---

2. Plan (Сборка DAG-графа и вычисление Диффа)

Сугубо аналитическая транзакция чтения для генерации спеки изменений без деструктивного или созидательного воздействия на облачную среду.

bash

```
terraform plan
```

Use code with caution.

Внутренний пайплайн вычислений:

1. **Этап Пассивного Обновления (`Refresh Phase`):** Перед расчетом дельты изменений Terraform Core инициирует серию конкурентных `GET`/`LIST` запросов через gRPC-провайдер к API облака (например, Yandex Cloud API). Цель — актуализировать `Prior State` до `Actual State` и выявить дрейф конфигурации (`Configuration Drift`), если ресурсы были изменены вручную мимо кода.
2. **Компиляция Направленного Ациклического Графа (DAG):** На основе явных деклараций (`depends_on`) и неявных интерполяций (например, `network_id = yandex_vpc_network.prod.id`) движок строит математическое дерево топологических зависимостей для определения строгого порядка параллельного деплоя.
3. **Расчет Дифференциала (`Diff Engine`):** Матричное сравнение кода и актуального стейта с выводом маркеров изменений в терминал.

---

3. Apply (Конвергенция и исполнение)

Трансляция вычисленного графа в реальные императивные мутирующие запросы к API провайдера.

bash

```
terraform apply
```

Use code with caution.

Механизм выполнения:

- Выполняется повторный неявный `plan` для защиты от изменений, произошедших в облаке в интервале между ручной генерацией плана и вводом аппрува.
- Запрашивается интерактивное подтверждение (строгий ввод строки `yes`).
- **Параллелизация выполнения:** На основе построенного DAG-графа Terraform Core отправляет асинхронные запросы к API провайдера. Независимые ветки графа (например, параллельные изолированные VPC сети) разворачиваются конкурентно в рамках лимита воркеров.
- **Транзакционная запись состояния:** При получении успешного ответа от API (`HTTP 201 Created` / `HTTP 200 OK`) физические ID и вычисленные атрибуты незамедлительно фиксируются в `terraform.tfstate`. Сбой при создании одного ресурса прерывает выполнение текущей ветки графа, но сохраняет состояние всех успешно созданных до этого момента объектов.

🔄 Управление изменениями (Change) и CRUD-матрица

Каждое изменение в HCL-коде при сопоставлении со стейтом размечается четырьмя типами префиксов, которые жестко маппятся на CRUD-операции облачного API:

|Маркер плана|Операция|Системное поведение|Влияние на продакшен-среду|
|---|---|---|---|
|**`+`**|**Create**|Ресурс отсутствует в стейте. Вызов `POST`.|Безопасно. Аллокация новых мощностей.|
|**`~`**|**Update in-place**|Модификация мутабельных параметров. Вызов `PUT` / `PATCH`.|Безопасно. Изменение атрибутов без разрушения объекта и прерывания сервиса.|
|**`-`**|**Destroy**|Объект удален из конфигурации HCL. Вызов `DELETE`.|Деструктивно. Полное удаление ресурса из облака и стейта.|
|**`-/+`**|**Replace**|**Двухфазная деструкция.** Вызывается изменением параметров, помеченных в схеме провайдера как `Forces replacement`.|**Критический риск!** Объект сначала полностью уничтожается (`DELETE`), затем создается заново (`POST`) с новым физическим ID.|

> ⚠️ **Продакшен-риск `Forces replacement` (`-/+`):** Инициирование замены для стейтфул-компонентов (диски `yandex_compute_disk`, базы данных `yandex_ydb_database`) приводит к **безвозвратному удалению томов и потере данных**. В CLI рядом с изменяемой строкой всегда выводится триггер, вызвавший замену: `# forces replacement`.

Принудительное пересоздание через таргетирование (`-replace`)

Если экземпляр ресурса перешел в невалидное состояние (дрейф конфигурации внутри ОС, повреждение рантайма приложения), но на уровне API облака его статус остается `RUNNING`, Terraform считает его валидным. Для принудительного включения ресурса в деструктивную ветку графа без изменения HCL-кода применяется флаг:

bash

```
terraform apply -replace="yandex_compute_instance.apps_cluster"
```

Use code with caution.

_Механизм:_ Движок принудительно выставляет объекту маркер `-/+` на этапе компиляции плана.

🗑 Депровижнинг инфраструктуры (Destroy)

В парадигме Infrastructure as Code (IaC) состояние «приостановки» ресурса (например, API-вызов `StopComputeInstance`) является неполноценным, так как объект продолжает занимать логическое пространство в стейте и потреблять аллоцированные ресурсы облака.

> 💡 **Экономическая оптимизация в Enterprise:** Единственным легитимным способом прекращения тарификации временных сред (Dev/QA/Staging) является их **полное уничтожение**. Остановленная ВМ в Yandex Cloud продолжает тарифицироваться за выделенные сетевые интерфейсы, статические IP, зарезервированные диски (NVMe/HDD) и квоты RAM.

Для полной деструкции управляемой инфраструктуры выполняется:

bash

```
terraform destroy
```

Use code with caution.

Математика выполнения `destroy` (Инверсия DAG):

Terraform Core инспектирует `terraform.tfstate`, считывает граф зависимостей и инвертирует его (разворачивает в обратном направлении). Если при создании порядок был: `VPC -> Subnet -> Instance`, то удаление пойдет по строгому пути: `Instance -> Subnet -> VPC`. Это исключает возникновение ошибок блокировки ресурсов (`ResourceInUse`) на стороне облачного API. Команда требует подтверждения через терминальный ввод `yes`.

🛠 Инженерный инструментарий и автоматизация пайплайнов

При работе на Enterprise-уровне интерактивный `terraform apply` на продакшен-средах исключается, а рутинные операции автоматизируются в CI/CD.

Валидация в CI/CD (Pre-commit / CI Lint)

- **`terraform fmt -check` (Линтинг):** Проверяет соответствие кода каноническому стилю форматирования HCL. Если отступы или выравнивания нарушены, возвращает `exit code != 0`, что позволяет разворачивать пайплайн.
- **`terraform validate` (Статический анализ):** Выполняет синтаксический анализ конфигурации. Проверяет корректность типов данных, наличие обязательных аргументов блоков и сопоставление схем провайдеров. **Не требует** доступа к удаленному стейту и API облака.

Изоляция планов через артефакты (Immutable Plans)

Для исключения _Race Conditions_ (когда между вашим `plan` и `apply` другой инженер успел применить свой код или изменить облако вручную), в CI/CD применяется разделение на атомарные шаги с фиксацией бинарного плана:

bash

```
# Шаг 1: Сборка графа и сохранение неизменяемого артефакта плана
terraform plan -out=prod_deploy.tfplan

# Шаг 2: Применение строго зафиксированного плана (ввод "yes" не требуется)
terraform apply prod_deploy.tfplan
```

Use code with caution.

Расширенное управление дрейфом и безопасностью

1. **Синхронизация без изменений (`-refresh-only`):** Если произошел дрейф инфраструктуры (изменения внесены мимо Terraform руками через консоль облака), и нужно обновить стейт-файл без модификации реальных ресурсов:
    
    bash
    
    ```
    terraform apply -refresh-only
    ```
    
    Use code with caution.
    
2. **Защита критических узлов (`prevent_destroy`):** Для предотвращения случайного удаления баз данных или корневых сетей при запуске общего `destroy` используется мета-аргумент жизненного цикла:
    
    hcl
    
    ```
    resource "yandex_ydb_database_active_directory" "production_db" {
      name = "prod-db"
    
      lifecycle {
        prevent_destroy = true # Вызовет ошибку на этапе планирования, если ресурс попадет под удаление
      }
    }
    ```
    
    Use code with caution.

💎 Главный вывод

**Terraform Workflow — это цикл предсказуемости и идемпотентности.** Инженер верхнего уровня оценивает план изменений не по факту его успешной компиляции, а по характеру воздействия на стейтфул-компоненты. Ключевая задача — минимизировать маркеры `-/+` на продакшен-окружении и обеспечивать атомарность применения через неизменяемые файлы планов.
