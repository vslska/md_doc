# Провайдер Libvirt: Архитектура и Суть

##  Назначение
Провайдер `dmacvicar/libvirt` обеспечивает управление локальной виртуализацией на базе **KVM/QEMU** через унифицированный API `libvirt`. Инструмент трансформирует декларативный HCL-код в XML-конфигурации, которые передаются демону `libvirtd` для создания виртуальных машин, сетей и хранилищ.

> 💡 **Применение:** Идеальное решение для построения локальных **Private Cloud** и **Homelab** инфраструктур. Позволяет тестировать Kubernetes-кластеры (K3s/RKE2), CI/CD пайплайны и Ansible-плейбуки без затрат на публичные облака.

---

## Механика под капотом (Архитектура)

1. **Демон `libvirtd`:** Центральный узел управления. Работает как фоновая служба в Linux. Terraform-провайдер не взаимодействует с QEMU напрямую, а использует XML-RPC или Unix-сокеты для общения с `libvirtd`.
2. **URI подключения:** Блок `provider` требует указания URI, который определяет транспортный протокол и целевой гипервизор:
   - `qemu:///system` — локальное системное подключение (требует прав `root` или членства в группе `libvirt`).
   - `qemu+ssh://user@host/system` — удаленное управление через SSH-туннель.
   - `qemu+tls://host/system` — безопасное подключение через TLS-сертификаты.
3. **XML-генерация:** Каждый HCL-блок (`domain`, `network`, `volume`) конвертируется в нативный XML-документ libvirt (Domain XML, Network XML). Этот XML передается в API `libvirt`.
4. **State и Drift:** Terraform записывает UUID домена, MAC-адреса и пути к дискам в `terraform.tfstate`. При последующих `plan` провайдер опрашивает `libvirtd` через API. Если ВМ была удалена вне Terraform (например, через `virsh`), возникает **Configuration Drift** (расхождение), что приводит к ошибкам или попыткам пересоздания ресурса.

## Основные ресурсы и Data Sources

| Тип | Ресурс HCL | Описание | Аналог в Cloud |
| :--- | :--- | :--- | :--- |
| **Resource** | `libvirt_domain` | Виртуальная машина (vCPU, RAM, загрузочные устройства). | `aws_instance` |
| **Resource** | `libvirt_volume` | Виртуальный диск (qcow2, raw). Поддерживает Copy-on-Write (CoW). | `aws_ebs_volume` |
| **Resource** | `libvirt_network` | Виртуальная сеть (NAT, Bridge, Isolated). | `aws_vpc` |
| **Resource** | `libvirt_pool` | Storage Pool (логический контейнер для дисков). | AWS S3 Bucket / EBS |
| **Resource** | `libvirt_cloudinit` | ISO-образ с `user-data` и `network-config`. | `aws_instance user_data` |
| **Data** | `libvirt_node_device_info` | Информация о PCI-устройствах хоста (для Passthrough). | `aws_instance_type` |

## Storage Pools (Типы хранилищ)

Storage Pool — это абстракция физического хранилища. Terraform управляет только созданием пула, но не физическими дисками.

| Тип (`type`) | Описание | Пример использования |
| :--- | :--- | :--- |
| `dir` | Обычная директория на файловой системе хоста. | Локальные тесты, простые инсталляции. |
| `logical` | LVM Volume Group. Позволяет создавать thin-provisioned тома. | Production-серверы, требующие снапшотов. |
| `netfs` | NFS или GlusterFS шары. | Распределенные кластеры, миграция ВМ (Live Migration). |
| `iscsi` | iSCSI Target (LUN). | Подключение к корпоративным СХД (NetApp, Pure Storage). |

```hcl
# Пример LVM пула
resource "libvirt_pool" "lvm_pool" {
  name = "vg_data"
  type = "logical"
  name = "vg_data" # Имя Volume Group в системе
}
```

## Networking (Режимы виртуальных сетей)

| Режим (`mode`) | Описание | Особенности |
| :--- | :--- | :--- |
| `nat` | Сеть с трансляцией адресов (NAT). ВМ имеют доступ во внешнюю сеть, но недоступны извне. | Встроенный DHCP и DNS от libvirt. Изоляция от локальной сети хоста. |
| `bridge` | Подключение к существующему Linux-бриджу (например, `br0`). | ВМ получают IP из физической сети. Требует предварительной настройки бриджа на хосте. |
| `isolated` | Полностью изолированная сеть. Только ВМ внутри этой сети могут общаться друг с другом. | Идеально для внутренних баз данных и backend-сервисов. |
| `passthrough` (macvtap) | Прямой проброс сетевого интерфейса хоста в ВМ. | Максимальная производительность (близко к bare-metal). |

## Практический пример (HCL)

Конфигурация для развертывания Ubuntu 22.04 с использованием **Copy-on-Write (CoW)** для экономии дискового пространства и **Cloud-Init** для начальной настройки.

```hcl
terraform {
  required_providers {
    libvirt = {
      source  = "dmacvicar/libvirt"
      version = "~> 0.7.6"
    }
  }
}

provider "libvirt" {
  uri = "qemu:///system"
}

# 1. Storage Pool (Директория)
resource "libvirt_pool" "homelab" {
  name = "homelab"
  type = "dir"
  path = "/var/lib/libvirt/images/homelab"
}

# 2. Базовый образ (Read-Only)
# Скачивается один раз. Все последующие ВМ ссылаются на него.
resource "libvirt_volume" "ubuntu_base" {
  name   = "ubuntu-22.04-base.qcow2"
  pool   = libvirt_pool.homelab.name
  source = "https://cloud-images.ubuntu.com/releases/22.04/release/ubuntu-22.04-server-cloudimg-amd64.img"
  format = "qcow2"
}

# 3. Рабочий диск (CoW Clone)
# Занимает на диске только размер измененных данных (дельта).
resource "libvirt_volume" "ubuntu_vm_disk" {
  name           = "ubuntu-vm-01.qcow2"
  pool           = libvirt_pool.homelab.name
  base_volume_id = libvirt_volume.ubuntu_base.id
  size           = 21474836480 # 20GB (максимальный размер)
}

# 4. Сеть (NAT)
resource "libvirt_network" "internal_net" {
  name      = "internal_net"
  mode      = "nat"
  domain    = "lab.local"
  addresses = ["10.20.30.0/24"]
  dhcp { enabled = true }
}

# 5. Cloud-Init
resource "libvirt_cloudinit_disk" "commoninit" {
  name      = "commoninit.iso"
  pool      = libvirt_pool.homelab.name
  user_data = file("user-data.cfg") # YAML конфигурация
}

# 6. Домен (ВМ)
resource "libvirt_domain" "ubuntu_vm" {
  name   = "ubuntu-vm-01"
  memory = "2048"
  vcpu   = 2
  
  # Автоматическое определение IP из DHCP
  qemu_agent = true 

  cloudinit = libvirt_cloudinit_disk.commoninit.id

  network_interface {
    network_id     = libvirt_network.internal_net.id
    wait_for_lease = true
  }

  disk { volume_id = libvirt_volume.ubuntu_vm_disk.id }
}

output "vm_ip" {
  value = libvirt_domain.ubuntu_vm.network_interface[0].addresses[0]
}
```

## Связь с базой Terraform

1. **Providers и State:** Аналогично облачным провайдерам, `terraform init` загружает бинарник плагина. State-файл хранит **UUID домена** и **пути к volume**. При изменении HCL (например, увеличение RAM) Terraform выполняет `virsh destroy` -> `virsh start`, что отражается в логах `libvirtd`.
2. **Workflow (DAG):** Граф зависимостей строится автоматически: `Pool` -> `Volume (Base)` -> `Volume (Clone)` -> `Network` -> `Domain`. Terraform гарантирует, что диск не будет подключен к ВМ до его создания.
3. **Импорт (Import):** Существующие ВМ, созданные вручную через `virt-manager`, могут быть импортированы в State:
   ```bash
   terraform import libvirt_domain.my_vm <UUID_домена>
   ```
   *UUID можно получить командой `virsh domuuid <имя_вм>`.*

## Подводные камни и Troubleshooting

1. **Permission Denied при создании пула:**
   - *Симптом:* Ошибка `cannot open directory '/var/lib/libvirt/images/homelab': Permission denied`.
   - *Причина:* Демон `libvirtd` (от пользователя `qemu` или `root`) не имеет прав на запись в директорию.
   - *Решение:* Использование стандартных путей (`/var/lib/libvirt/images`) или настройка ACL/SELinux/AppArmor.

2. **Пустой Output IP-адреса:**
   - *Симптом:* `terraform output` возвращает пустую строку.
   - *Причина:* ВМ еще не получила IP от DHCP или QEMU Guest Agent не установлен.
   - *Решение:* Добавить `wait_for_lease = true` в `network_interface`. Для сложных сетей (Bridge) использовать `qemu_agent = true` и установить `qemu-guest-agent` внутри ОС.

3. **Сетевой конфликт (NAT):**
   - *Симптом:* Ошибка создания сети `Network is already in use by interface virbr0`.
   - *Причина:* Libvirt по умолчанию создает сеть `default` (192.168.122.0/24).
   - *Решение:* Использовать уникальные подсети в блоке `addresses`.

4. **Изменение Cloud-Init:**
   - Изменение `user_data` не обновит конфигурацию работающей ВМ. Cloud-init срабатывает только при первом загрузке (First Boot). Для применения изменений требуется пересоздание ресурса (`terraform taint` или удаление ВМ).
