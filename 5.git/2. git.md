# Руководство: Работа с Git (от базовых команд до аварийного отката)

> **Сфера применения:** Распределенный контроль версий, базовый и продвинутый рабочий процесс, управление ветками, разрешение конфликтов, безопасный откат коммитов и спасение потерянного кода.

## 1. Ментальная модель состояний файлов в Git

В Git каждый файл находится в одном из трех (четырех) ключевых состояний:

```
               Три области и состояния Git
                            │
  ┌─────────────────────────┼─────────────────────────┐
  ▼                         ▼                         ▼
[ Working Directory ]    [ Staging Area (Index) ]  [ Repository (.git) ]
  Unmodified / Modified    Staged (индексирован)     Committed (в истории)
   (Файлы на диске)         `git add`                 `git commit`
```

## 2. Базовые команды Git

### Инициализация и настройка

- **Инициализация репозитория:** Создает скрытый каталог `.git` в текущей директории.

```Bash
git init
```
 
- **Глобальная настройка дефолтной ветки (`main` вместо `master`):**

```
git config --global init.defaultBranch main
```

### Просмотр состояния и индексация

- **Просмотр состояния репозитория:** Показывает измененные, добавленные и неаудируемые файлы.
 
```
git status
```

- **Добавление файлов в индекс (Staging Area):**

```
git add <file>    # Конкретный файл
git add .         # Все изменения в текущей директории
```

- **Удаление файла из индекса без удаления с диска:**

```
git rm --cached <file_or_dir>
```

### Коммиты и история

- **Создание коммита:** Сохранение текущего индексированного состояния[cite: 6].

```
git commit -m "Описание изменений"
```

- **Просмотр истории коммитов:**
 
```
git log
git log --oneline --graph --all   # Компактный граф веток
```

### Работа с `.gitignore`

Файл `.gitignore` позволяет исключить файлы и каталоги из отслеживания Git (логи, скомпилированные файлы, секреты)[cite: 6].

_Пример `.gitignore`:_

```sh
*.log
*.tmp
*.exe
/build/
.env
```

## 3. Ветвление и работа с удаленными репозиториями

### Управление ветками

* **Создание новой ветки:**

  ```bash
  git branch new-feature
  ```

* **Переключение на ветку:**

  ```bash
  git checkout new-feature 
  # Современный синтаксис: git switch new-feature
  ```

* **Создание и мгновенный переход:**

  ```bash
  git checkout -b new-feature
  ```

* **Переименование текущей ветки (например, из `master` в `main`):**

  ```bash
  git branch -m master main
  ```

* **Слияние ветки в текущую:**

  ```bash
  git checkout main
  git merge new-feature
  ```

* **Удаление ветки:**

  ```bash
  git branch -d new-feature       # Безопасное удаление (если слита)
  git branch -D new-feature       # Принудительное удаление
  ```

### Работа с удаленными репозиториями (GitHub / GitLab)
* **Привязка удаленного репозитория:**
  ```bash
  git remote add origin https://github.com/username/repository.git
  ```[cite: 6]
* **Отправка изменений (Push):**
  ```bash
  git push -u origin main         # Первичная отправка с привязкой
  ```[cite: 6]
* **Привязка локальной ветки к удаленной, если они не связывались:**
  ```bash
  git push --set-upstream origin main
  ```[cite: 6]
* **Получение изменений (Pull):**
  ```bash
  git pull origin main
  ```[cite: 6]

## 4. Откат изменений, отмена коммитов и очистка

```text
                      Стратегии отката
                             │
 ┌───────────────────────────┼───────────────────────────┐
 ▼                           ▼                           ▼
[ git restore / checkout ]  [ git reset ]               [ git revert ]
Отмена локальных несделанных  Перемещение указателя      Безопасная отмена
изменений на диске.          ветки назад.                публичного коммита.
````

### 4.1. Отмена локальных изменений (до коммита)

- **Отменить незакоммиченные изменения в файле (сброс к `HEAD`):**
    
    Bash
    
    ````
    git restore <file>
    # Старый синтаксис: git checkout -- <file>
    ```[cite: 6]
    ````
    
- **Убрать файл из индекса, оставив изменения в файле:**
    
    Bash
    
    ````
    git restore --staged <file>
    # Старый синтаксис: git reset HEAD <file>
    ```[cite: 6]
    ````
    
- **Очистить проект от всех неотслеживаемых (untracked) файлов и папок:**
    
    Bash
    
    ```
    git clean -fd
    ```
    

### 4.2. Откат локальных коммитов (`git reset`)

> ⚠️ **ВНИМАНИЕ:** Применяй `reset` **только для локальных коммитов**, которые ещё не улетели в `origin` (`push`)!

- **`git reset --soft HEAD~1`** — отменяет коммит, изменения остаются **в индексе** (готовы к новому `commit`).
    
- **`git reset --mixed HEAD~1`** _(по умолчанию)_ — отменяет коммит, изменения остаются на диске, но **выпадают из индекса**.
    
- **`git reset --hard HEAD~1`** — **ЖЕСТКИЙ СБРОС.** Безвозвратно стирает последний коммит и все изменения в коде!
    
- **Принудительно сбросить локальную ветку к состоянию удаленной `origin/main`:**
    
    Bash
    
    ```
    git fetch origin
    git reset --hard origin/main
    ```
    

### 4.3. Откат публичных коммитов (`git revert`)

Безопасный способ отменить изменения, которые **уже находятся в удаленном репозитории**. Не переписывает историю, а создает новый компенсирующий коммит.

- **Отменить конкретный коммит:**
    
    Bash
    
    ```
    git revert <commit_hash>
    ```
    
- **Отменить Merge-коммит (возврат ветки до слияния):**
    
    Bash
    
    ```
    git revert -m 1 <merge_commit_hash>
    ```
    

## 5. Выравнивание истории: `git rebase` и аварийное завершение

Rebase переносит цепочку твоих коммитов поверх актуального `main`, создавая чистую и линейную историю.

Plaintext

```
                  Интерактивный Rebase
                             │
 [ feature ] C1 ── C2 ── C3  │  "Перенос поверх main"
                             ▼
 [ main ]    M1 ── M2 ──────► C1' ── C2' ── C3'
```

### 5.1. Стандартный рабочий процесс Rebase

1. Переключиться на свою ветку и запустить rebase поверх свежего `origin/main`:
    
    Bash
    
    ```
    git checkout feature-branch
    git fetch origin
    git rebase origin/main
    ```
    
2. Интерактивная склейка (Squash) последних 3 коммитов в один:
    
    Bash
    
    ```
    git rebase -i HEAD~3
    ```
    
    _В открывшемся редакторе:_ `pick` — оставить, `squash` (или `s`) — вплавить в предыдущий, `drop` (или `d`) — удалить.
    

### 5.2. Что делать, если Rebase завис или возникли конфликты

#### Вариант А: Запутался в конфликтах / процесс завис — ОТМЕНА

Если что-то пошло не так, верни ветку в исходное состояние одной командой:

Bash

```
git rebase --abort
```

_(Аналогично для повисшего merge: `git merge --abort`)_

#### Вариант Б: Разрешить конфликты и продолжить

1. Открой конфликтующие файлы и исправь маркеры (`<<<<<<<`, `=======`, `>>>>>>>`).
    
2. Добавь исправленные файлы в индекс:
    
    Bash
    
    ```
    git add <resolved_file>
    ```
    
3. Продолжи rebase (**НЕ делай `git commit`!**):
    
    Bash
    
    ```
    git rebase --continue
    ```
    
4. Если коммит стал пустым/дублирующим, пропусти его:
    
    Bash
    
    ```
    git rebase --skip
    ```
    

## 6. Зависшие процессы, заначка (Stash) и спасение кода (`Reflog`)

### 6.1. Временное сохранение кода (`git stash`)

Нужно срочно переключиться на другую ветку или подгрузить hotfix, но код не готов к коммиту:

Bash

```
# Спрятать все изменения (включая untracked файлы -u)
git stash -u -m "Временная заначка перед переключением"

# Посмотреть список заначек
git stash list

# Достать последнюю заначку и удалить её из стека
git stash pop

# Применить заначку без удаления из стека
git stash apply stash@{0}
```

### 6.2. `git reflog`: Восстановление случайно удаленных коммитов и веток

`git reflog` ведет учет **всех передвижений указателя `HEAD`** (даже после `git reset --hard` или удаления ветки).

1. Посмотри историю всех действий:
    
    Bash
    
    ```
    git reflog
    ```
    
2. Найди хэш коммита или ссылку `HEAD@{N}`, где код еще был жив.
    
3. Восстанови состояние:
    
    Bash
    
    ```
    # Способ 1: Жестко вернуться к тому моменту
    git reset --hard HEAD@{2}
    
    # Способ 2: Создать новую ветку из "потерянного" коммита
    git checkout -b rescued-branch a1b2c3d
    ```
    

### 6.3. Сброс блокировки `.git/index.lock`

Если процесс Git завершился аварийно (упал терминал, зависла система), появится ошибка:

`Fatal: Unable to create '/.git/index.lock': File exists.`

**Решение:**

Убедись, что нет запущенных процессов Git, и просто удали файл блокировки:

Bash

```
rm -f .git/index.lock
```

## 7. Полный сквозной воркфлоу разработки (Workflow)

1. **Старт задачи:**
    
    Bash
    
    ```
    git checkout main
    git pull origin main
    git checkout -b feature/user-auth
    ```
    
2. **Процесс разработки (частые локальные коммиты):**
    
    Bash
    
    ```
    # Пишем код...
    git add .
    git commit -m "feat: добавлена форма логина"
    ```
    
3. **Синхронизация с основной веткой перед PR/MR:**
    
    Bash
    
    ```
    git fetch origin
    git rebase origin/main
    # При конфликте: правим файлы -> git add . -> git rebase --continue
    # При ошибке: git rebase --abort
    ```
    
4. **Отправка на GitHub/GitLab:**
    
    Bash
    
    ```
    git push -u origin feature/user-auth
    # Если делал rebase уже отправленной ветки:
    git push --force-with-lease origin feature/user-auth
    ```
    
5. **Финализация после Merge Pull Request:**
    
    Bash
    
    ```
    git checkout main
    git pull origin main
    git branch -d feature/user-auth
    ```
