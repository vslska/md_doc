# Сетевой стек Linux: datapath, TCP/IP, очереди, масштабирование и диагностика

> **Предмет:** Linux networking internals, TCP/IP, очереди, NAPI, RSS/RPS, TCP listen/close path, conntrack и диагностика   
> **Важно:** конкретные значения `sysctl`, размеры очередей и доступные offload-механизмы зависят от версии ядра, драйвера, NIC и топологии. Значения ниже — примеры для анализа, а не универсальный production baseline.

---



---
## 1. Область документа

Сетевой путь Linux нельзя корректно описывать одной последовательностью «NIC → interrupt → TCP → socket → application». Реальный datapath состоит из аппаратных очередей, DMA, драйвера, NAPI, `sk_buff`, software/hardware steering, протокольных уровней, Netfilter, маршрутизации и очередей сокета.

Для TCP-сервера необходимо отдельно рассматривать как минимум:

1. путь **RX** — от NIC до `recv()`/`read()`;
2. путь **TX** — от `send()`/`write()` до NIC;
3. очереди и точки возможного `drop`;
4. распределение работы между CPU;
5. TCP connection establishment;
6. `listen()`/`accept()` backlog;
7. жизненный цикл TCP states;
8. socket memory и autotuning;
9. Netfilter/conntrack;
10. аппаратные offload-механизмы;
11. namespace/network virtualization;
12. инструменты наблюдения и корреляцию метрик.

# 2. Ментальная модель Linux networking

Упрощённая модель RX:

```text
                 PCIe / DMA
                     │
                     ▼
              ┌─────────────┐
              │ NIC RX Ring │
              └──────┬──────┘
                     │
                IRQ / NAPI
                     │
                     ▼
              ┌─────────────┐
              │   driver    │
              └──────┬──────┘
                     │
                  napi_poll
                     │
                     ▼
              ┌─────────────┐
              │    skb      │
              └──────┬──────┘
                     │
              L2 / VLAN / bridge
                     │
                     ▼
             IP / routing / hooks
                     │
                     ▼
              TCP / UDP / etc.
                     │
                     ▼
              socket receive queue
                     │
                     ▼
              recv() / read()
                     │
                     ▼
                user space
```

Это не означает, что каждый пакет проходит через одинаковый набор функций. Например:

- XDP может обработать пакет значительно раньше обычного `skb`-пути;
- bridge, VLAN, bonding, tunneling и virtual devices добавляют собственные этапы;
- GRO может объединить несколько входящих сегментов;
- RPS может перенести protocol processing на другой CPU;
- hardware offload может перенести часть работы в NIC;
- Netfilter hooks зависят от topology и namespace;
- для TCP данные проходят TCP receive path, а не просто «складываются в буфер после удаления заголовков».

# 3. Аппаратный RX path

## 3.1. RX descriptor ring

Современная NIC обычно имеет одну или несколько RX queues. Каждая queue связана с кольцом descriptor'ов.

Упрощённо:

```
NIC
 │
 ├── RX queue 0 ── descriptor ring ──► CPU
 ├── RX queue 1 ── descriptor ring ──► CPU
 ├── RX queue 2 ── descriptor ring ──► CPU
 └── ...
```

Descriptor обычно содержит информацию, позволяющую устройству записать принятые данные в память. Конкретная организация зависит от устройства и драйвера.

Важно различать:

- **ring descriptor** — metadata для устройства/драйвера;
- **packet buffer** — память, куда DMA записывает packet data;
- **`struct sk_buff`** — программная структура ядра, которая представляет пакет после передачи в обычный networking stack.

`sk_buff` сам по себе не является обязательным «контейнером физического буфера NIC» и не следует представлять его как простую структуру, содержащую весь packet payload внутри себя. Kernel documentation описывает `struct sk_buff` как metadata structure, связанный с отдельными data buffers и fragments. citeturn0search2turn0search6

---

## 3.2. DMA

NIC может записывать данные непосредственно в RAM через DMA.

Это означает, что CPU не обязан выполнять:

```
NIC → CPU copies every byte → RAM
```

вместо этого типичный путь выглядит концептуально как:

```
NIC ──DMA──► RAM
       │
       └── descriptor/status ──► driver
```

DMA существенно снижает CPU cost передачи данных, но не делает сетевой I/O «бесплатным»:

- необходимо обслужить descriptor;
- необходимо построить/обновить software metadata;
- необходимо выполнить protocol processing;
- могут выполняться memory allocations/refcount operations;
- возможны cache misses;
- может потребоваться checksum/GRO/GSO processing;
- при RPS появляются дополнительные межъядерные взаимодействия.

# 4. IRQ и NAPI

## 4.1. Почему packet-per-interrupt плохо масштабируется

Если генерировать полноценное аппаратное прерывание для каждого пакета:

```
packet 1 → IRQ
packet 2 → IRQ
packet 3 → IRQ
...
packet N → IRQ
```

стоимость interrupt handling может стать доминирующей.

Linux использует NAPI как механизм, позволяющий сочетать interrupt notification с последующим polling/batching.

---

## 4.2. Типичный NAPI flow

Концептуально:

```
NIC receives packets
       │
       ▼
 hardware interrupt
       │
       ▼
 driver schedules NAPI
       │
       ▼
 NAPI poll()
       │
       ├── packet
       ├── packet
       ├── packet
       └── ...
       │
       ▼
 complete / reschedule
```

Современная kernel documentation описывает `napi_schedule()` как механизм планирования NAPI poll, после чего вызывается driver poll method с `budget`. Для RX драйвер должен соблюдать budget; если работа не завершена, poll должен вернуть `budget`, чтобы NAPI был обслужен снова. citeturn1search6

### Важное уточнение

Не следует описывать NAPI как просто:

> «Hard IRQ отключается и включается SoftIRQ».

Это слишком грубая модель.

Точная реализация зависит от driver/NAPI configuration и версии kernel. Правильнее мыслить так:

```
interrupt/event
      │
      ▼
schedule NAPI
      │
      ▼
poll batches of work
      │
      ├── budget exhausted → poll again
      │
      └── work completed → complete NAPI
```

# 5. `sk_buff`

`struct sk_buff` — одна из центральных структур Linux networking.

Она представляет packet metadata и ссылки на packet data.

Упрощённо:

```
struct sk_buff
       │
       ├── metadata
       │    ├── protocol
       │    ├── device
       │    ├── checksum state
       │    ├── timestamps
       │    └── ...
       │
       └── data buffers
            ├── linear data
            └── page fragments
```

Kernel documentation отдельно подчёркивает, что `struct sk_buff` — metadata structure, а данные находятся в связанных buffers/fragments. citeturn0search6

Это важно для понимания zero-copy, GRO/GSO, page fragments и memory accounting.

# 6. RX scaling: RSS, RPS, RFS

## 6.1. RSS

**RSS — Receive Side Scaling** — аппаратный механизм NIC.

NIC вычисляет flow hash и направляет разные flows в разные RX queues.

```
                    NIC
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      RXQ0         RXQ1         RXQ2
        │            │            │
      CPU0         CPU1         CPU2
```

Главная цель — увеличить parallelism без того, чтобы весь RX datapath выполнялся на одном CPU.

Linux kernel documentation описывает RSS именно как распределение flows по нескольким receive queues, которые могут обслуживаться разными CPU. citeturn1search2

### Практическая диагностика

```
ethtool -l eth0
ethtool -x eth0
ethtool -S eth0
cat /proc/interrupts
```

---

## 6.2. RPS

**RPS — Receive Packet Steering** — software механизм, логически похожий на RSS.

Разница:

```
RSS:
NIC выбирает queue/CPU
        ↓
driver/NAPI
        ↓
protocol processing

RPS:
NIC/driver получает пакет
        ↓
kernel выбирает target CPU
        ↓
packet попадает в backlog target CPU
        ↓
protocol processing
```

RPS выполняется позже RSS и может добавлять IPI/cache overhead. С другой стороны, он не требует аппаратной поддержки конкретного NIC и может использоваться с различными устройствами. citeturn1search8

Настройка:

```
cat /sys/class/net/eth0/queues/rx-0/rps_cpus
echo ff > /sys/class/net/eth0/queues/rx-0/rps_cpus
```

`ff` означает CPU mask для первых 8 CPU, если CPU numbering начинается с 0.

**Важно:** маску нельзя копировать бездумно. На NUMA-системе CPU affinity должна учитывать locality.

---

## 6.3. RFS

**RFS — Receive Flow Steering** — следующий уровень.

Идея:

> направить packet processing ближе к CPU, на котором реально выполняется приложение, читающее этот flow.

Это может уменьшить cache misses, но добавляет tracking и steering overhead.

---

# 7. XPS и TX scaling

Для передачи существует аналогичная задача:

**XPS — Transmit Packet Steering.**

Концептуально:

```
application thread
       │
       ▼
socket / TCP
       │
       ▼
XPS / TX queue selection
       │
       ▼
NIC TX queue
       │
       ▼
NIC
```

На multi-queue NIC важно анализировать не только RX, но и TX queues:

```
ethtool -l eth0
ethtool -S eth0
```

и:

```
ls /sys/class/net/eth0/queues/
```

# 8. `/proc/net/softnet_stat`

Для диагностики RX processing полезен:

```
cat /proc/net/softnet_stat
```

Строки соответствуют CPU.

Однако нельзя универсально трактовать колонки только как:

```
1 = processed
2 = dropped because netdev_max_backlog
3 = squeezed because budget
```

Формат и смысл отдельных полей зависят от kernel implementation.

Практический принцип:

- рост drop-related counters требует проверки backlog/CPU pressure;
- рост time/budget-related counters указывает на ограничение обработки;
- показатели нужно сопоставлять с IRQ distribution, NAPI activity и traffic rate.

---

# 9. `netdev_max_backlog`

`net.core.netdev_max_backlog` относится к очереди входящих пакетов, когда обработка не успевает за поступлением.

Проверка:

```
sysctl net.core.netdev_max_backlog
```

Не следует считать увеличение этого значения универсальным лечением.

Увеличение очереди:

```
+ позволяет временно выдержать burst
- увеличивает buffering
- может увеличивать latency
- не увеличивает CPU capacity
```

Если CPU не успевает обработать packets, большая очередь лишь позволяет дольше накапливать работу.

# 10. GRO, GSO и TSO

## 10.1. GRO

**GRO — Generic Receive Offload.**

На RX несколько сегментов могут быть объединены в более крупный logical packet для дальнейшей обработки stack'ом.

Идея:

```
segment 1 ┐
segment 2 ├──► GRO ──► larger logical packet
segment 3 ┘
```

Это уменьшает количество packet processing operations.

---

## 10.2. GSO

**GSO — Generic Segmentation Offload.**

Вместо того чтобы создавать множество маленьких segments на раннем этапе, kernel может работать с большим logical packet и сегментировать его позже.

---

## 10.3. TSO

**TSO — TCP Segmentation Offload** — аппаратная реализация соответствующей части segmentation на NIC.

Упрощённо:

```
large TCP skb
      │
      ▼
NIC
      │
      ├── segment 1
      ├── segment 2
      ├── segment 3
      └── ...
```

Нельзя путать GSO и TSO:

- GSO — kernel/software abstraction;
- TSO — hardware capability.

---

# 11. Checksum offload

NIC может выполнять checksum-related работу вместо CPU.

Linux networking documentation описывает TX checksum offload через metadata в `sk_buff`, после чего драйвер/NIC выполняет соответствующую операцию. При отсутствии подходящей аппаратной возможности kernel может выполнить её software-side. citeturn2search1

Проверка:

```
ethtool -k eth0
```

Пример:

```
tx-checksum-ip-generic: on
tcp-segmentation-offload: on
generic-segmentation-offload: on
generic-receive-offload: on
```

Не следует отключать offload «для тюнинга» без измерения. Offload часто уменьшает CPU cost.

# 12. Netfilter и packet path

Для многих систем datapath выглядит примерно так:

```
NIC
 │
 ▼
driver / NAPI
 │
 ▼
L2 processing
 │
 ▼
Netfilter hooks
 │
 ▼
routing decision
 │
 ├── local delivery ──► socket
 │
 └── forwarding ──────► output path
```

Точные hooks зависят от направления и topology.

Netfilter может выполнять:

- filtering;
- NAT;
- connection tracking;
- policy decisions.

Поэтому containerized Linux host может иметь значительно более сложный datapath, чем обычный physical host.

# 13. Conntrack

Connection tracking хранит состояние flows.

Типичная проблема:

```
traffic burst
    │
    ▼
conntrack entries
    │
    ▼
table full
    │
    ▼
packet drops
```

Диагностика:

```
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
dmesg | grep -i conntrack
```

Сообщение:

```
nf_conntrack: table full, dropping packet
```

является прямым индикатором того, что conntrack table достигла лимита.

**Важно:** увеличение `nf_conntrack_max` — не бесплатное решение. Нужно учитывать memory consumption и фактическую необходимость tracking.

# 14. TCP connection establishment

## 14.1. Three-way handshake

```
Client                          Server

  SYN ------------------------>

      <---------------------- SYN-ACK

  ACK ------------------------>

           ESTABLISHED
```

После `listen()` Linux должен одновременно обслуживать:

1. ещё не завершённые connection attempts;
2. полностью установленные connections, ожидающие `accept()`.

---

# 15. SYN backlog и accept queue

Упрощённая модель:

```
                 SYN
                  │
                  ▼
        [incomplete requests]
                  │
             SYN-ACK
                  │
                  ▼
        final ACK arrives
                  │
                  ▼
        [completed connections]
                  │
              accept()
                  │
                  ▼
             application
```

Для Linux важно не смешивать два разных backlog concepts:

- `tcp_max_syn_backlog` связан с incomplete connection requests;
- `listen(backlog)` задаёт очередь полностью установленных sockets, ожидающих `accept()`;
- `net.core.somaxconn` ограничивает значение `listen()` backlog. citeturn1search3turn1search1

Начиная с Linux 5.4 default `somaxconn` в man-pages указан как 4096; более старые kernels имели другие defaults. Поэтому документация не должна фиксировать одно значение как вечный «Linux default». citeturn1search5

---

# 16. Практический анализ backlog

Проверка:

```
sysctl net.ipv4.tcp_max_syn_backlog
sysctl net.core.somaxconn
```

Проверка listener:

```
ss -lntp
```

Нужно также смотреть приложение:

- реальный `listen(backlog)`;
- скорость `accept()`;
- latency между готовностью connection и `accept()`;
- worker saturation;
- CPU pressure;
- event-loop latency.

Увеличение backlog не заменяет исправление медленного consumer.

---

# 17. SYN cookies

Проверка:

```
sysctl net.ipv4.tcp_syncookies
```

`tcp_syncookies` предназначен прежде всего для защиты от SYN flood при переполнении SYN backlog.

Linux man-pages отдельно подчёркивает, что syncookies не следует рассматривать как обычный performance tuning mechanism для перегруженного или неправильно настроенного сервера. citeturn1search0

Следовательно:

```
SYN flood protection
        ≠
capacity planning
```

Если application не успевает принимать connections, нужно исследовать application backlog, CPU, event loop и downstream dependencies.

---

# 18. `tcp_synack_retries`

Параметр:

```
sysctl net.ipv4.tcp_synack_retries
```

определяет число повторных передач SYN/ACK для passive TCP connection attempts. Точное время ожидания зависит от TCP timers и kernel behavior; нельзя корректно документировать его как одну фиксированную величину для всех версий. citeturn1search0

Изменять:

```
sysctl -w net.ipv4.tcp_synack_retries=2
```

следует только после понимания последствий для клиентов с высокой latency/loss.

---

# 19. `tcp_abort_on_overflow`

Если application не успевает обслуживать completed connection queue, можно исследовать:

```
sysctl net.ipv4.tcp_abort_on_overflow
```

Это не «магическая настройка load balancer».

При значении `1` Linux может сбрасывать connection при overflow accept queue. Такой режим изменяет наблюдаемое поведение для клиентов и должен применяться только с пониманием application/load-balancer semantics.

---

# 20. TCP socket receive/send buffers

TCP использует socket buffers.

Полезные параметры:

```
sysctl net.ipv4.tcp_rmem
sysctl net.ipv4.tcp_wmem
sysctl net.ipv4.tcp_moderate_rcvbuf
```

Современный Linux умеет автоматически адаптировать receive buffer под характеристики потока.

`tcp_moderate_rcvbuf` управляет TCP receive-buffer autotuning; Linux man-pages указывает его default как enabled. citeturn1search0

Поэтому модель:

```
tcp_rmem = "один фиксированный receive buffer на каждый socket"
```

неверна.

Нужно различать:

- min;
- default;
- max;
- фактическое использование;
- protocol overhead;
- application consumption rate.

# 22. TCP states

Ключевые состояния:

```
LISTEN
SYN-SENT
SYN-RECV
ESTABLISHED
FIN-WAIT-1
FIN-WAIT-2
CLOSE-WAIT
CLOSING
LAST-ACK
TIME-WAIT
CLOSED
```

Необходимо различать **протокольное состояние TCP** и **состояние application lifecycle**.

Например:

```
CLOSE_WAIT
```

не означает «ядро зависло».

# 23. CLOSE_WAIT

`CLOSE_WAIT` возникает после того, как локальный TCP получил FIN от peer.

Упрощённо:

```
peer
  │
 FIN
  ▼
Linux TCP
  │
 ACK
  ▼
CLOSE_WAIT
  │
  │ application must close()
  ▼
CLOSED
```

Ключевой факт:

> `CLOSE_WAIT` означает, что peer уже сообщил о закрытии своей стороны, а локальное приложение ещё не закрыло socket.

Поэтому большое и постоянно растущее число `CLOSE_WAIT` обычно требует анализа application lifecycle.

Диагностика:

```
ss -tanp state close-wait
```

---

# 24. TIME_WAIT

`TIME_WAIT` связан прежде всего с active close.

Его назначение — не дать старым сегментам предыдущего connection incarnation конфликтовать с новым соединением и обеспечить корректную обработку повторного FIN/ACK exchange.

Нельзя формулировать:

> «TIME_WAIT всегда ровно 60 секунд».

Фактическое поведение зависит от TCP implementation и timers. Наблюдать конкретные timers можно через:

```
ss -o state time-wait
```

`ss -o` показывает timer information, включая `timewait` timers. citeturn2search0

---

# 25. TIME_WAIT и ephemeral ports

Большое количество TIME_WAIT может быть нормальным следствием высокой скорости active connections.

Например:

```
10 000 connections/s
×
N seconds of TIME_WAIT lifetime
=
много одновременно существующих TIME_WAIT sockets
```

Но это не означает автоматически:

> «TIME_WAIT — ошибка».

Сначала необходимо выяснить:

- кто выполняет active close;
- используется ли connection reuse/keep-alive;
- какой `ip_local_port_range`;
- сколько destination tuples используется;
- возникает ли фактический `EADDRNOTAVAIL`;
- есть ли application-level connection pooling.

---

# 26. `ip_local_port_range`

Проверка:

```
sysctl net.ipv4.ip_local_port_range
```

Диапазон задаёт пространство локальных ephemeral ports для соответствующих outbound allocations.

Расширение диапазона может помочь, но только если именно ephemeral port allocation является ограничением.

Не следует механически задавать:

```
1024 65535
```

на всех системах: low ports имеют семантические и security implications, а реальная потребность зависит от workload.

---

# 27. `tcp_tw_reuse`

Параметр:

```
sysctl net.ipv4.tcp_tw_reuse
```

имеет исторически изменявшуюся семантику, поэтому документация должна привязывать рекомендации к конкретной версии kernel.

Важно:

- не путать его с давно удалённым `tcp_tw_recycle`;
- не считать его универсальным способом «убрать TIME_WAIT»;
- анализировать timestamps и network topology;
- проверять фактическую причину port exhaustion.

---

# 28. `tcp_tw_recycle`: исторический параметр

Старые статьи часто содержат:

```
net.ipv4.tcp_tw_recycle = 1
```

Для современных Linux это не является допустимой рекомендацией: параметр был удалён из kernel.

Следовательно, production documentation не должна предлагать его включение.

# 29. CLOSE_WAIT vs TIME_WAIT

|Состояние|Кто обычно инициировал закрытие|Основная причина|Где искать проблему|
|---|---|---|---|
|`CLOSE_WAIT`|peer|peer прислал FIN|application|
|`TIME_WAIT`|local endpoint|local active close|protocol semantics / connection churn|
|`SYN_RECV`|remote client|handshake ещё не завершён|SYN rate / loss / backlog|
|`ESTABLISHED`|—|нормальная работа|traffic/application|
|`FIN_WAIT_*`|local endpoint|local close в progress|protocol/application|

Ключевой диагностический принцип:

```
CLOSE_WAIT ↑
    → искать application leak / lifecycle issue

TIME_WAIT ↑
    → искать active-close rate / connection churn / port pressure
```

# 30. Socket memory и `ss -m`

Пример:

```
ss -tm
```

может показывать данные вида:

```
skmem:(r..., rb..., t..., tb..., f..., w..., o..., bl..., d...)
```

где отображаются различные компоненты socket memory accounting. Например, `rmem_alloc` относится к памяти, выделенной для receive path, а `rcv_buf` — к объёму receive buffer. citeturn2search2

Нельзя напрямую трактовать `rb` как «сколько данных реально ждёт приложение».

Socket memory включает не только application payload.

---

# 31. Почему «увеличим TCP buffers» может не помочь

Пусть приложение читает:

```
100 MB/s
```

а сеть может доставлять:

```
1 GB/s
```

Если application consumer не масштабируется, увеличение receive buffer:

```
+ позволяет накопить больше данных
- увеличивает memory usage
- увеличивает latency при переполнении
- не увеличивает application throughput
```

Buffer sizing должен быть связан с:

```
bandwidth × desired buffering interval
```

и ограничен доступной памятью и количеством concurrent sockets.

# 32. IRQ affinity

Проверка:

```
cat /proc/interrupts
```

Можно увидеть распределение NIC interrupts по CPU.

Полезно сопоставлять:

```
NIC queue
    │
    ├── IRQ vector
    │
    ├── CPU
    │
    └── NAPI instance
```

Если весь traffic обслуживается одним CPU:

```
CPU0 = 100%
CPU1..CPU31 = mostly idle
```

то проблема может быть в IRQ/RSS configuration, а не в общем CPU capacity.

---

# 33. `irqbalance`

`irqbalance` может распределять interrupts между CPU.

Но на latency-sensitive или NUMA-sensitive системах автоматическое распределение не всегда совпадает с desired topology.

Поэтому диагностика должна начинаться с измерения:

```
cat /proc/interrupts
ethtool -l eth0
ethtool -x eth0
lscpu -e
numactl -H
```

и только затем переходить к affinity tuning.

---

# 34. NUMA

Для multi-socket systems:

```
NIC
 │
PCIe root complex
 │
NUMA node 0
 │
CPU 0..15
```

Если packet memory и application thread находятся на разных NUMA nodes:

```
NIC/Memory Node 0
        │
        │ remote memory access
        ▼
Application CPU Node 1
```

может возрастать latency и memory bandwidth pressure.

Поэтому RSS/RPS/XPS/IRQ tuning должен учитывать NUMA locality.

# 41. High-load troubleshooting runbook

## Симптом A: высокий RX drop

```
RX drops
  │
  ├── ethtool -S
  │
  ├── ethtool -g
  │
  ├── /proc/interrupts
  │
  ├── /proc/softirqs
  │
  └── CPU/NUMA
```

Проверить:

1. hardware/driver counters;
2. RX ring;
3. IRQ distribution;
4. NAPI/CPU saturation;
5. RSS configuration;
6. RPS only if justified.

---

## Симптом B: высокий `SYN_RECV`

Проверить:

```
ss -tan state syn-recv
```

Далее:

```
sysctl net.ipv4.tcp_max_syn_backlog
sysctl net.ipv4.tcp_syncookies
sysctl net.ipv4.tcp_synack_retries
```

Но затем обязательно определить:

- legitimate connection burst или attack;
- packet loss;
- RTT;
- load balancer behavior;
- application accept rate.

---

## Симптом C: высокий `CLOSE_WAIT`

Проверить:

```
ss -tanp state close-wait
```

Затем:

```
lsof -nP -a -iTCP -sTCP:CLOSE_WAIT
```

Идентифицировать PID/process.

Дальше искать:

- missing `close()`;
- leaked file descriptor;
- blocked worker;
- failed error path;
- incorrect connection lifecycle;
- goroutine/thread leak.

Не начинать с kernel TCP tuning.

---

## Симптом D: высокий `TIME_WAIT`

Проверить:

```
ss -s
```

```
ss -tan state time-wait
```

```
sysctl net.ipv4.ip_local_port_range
```

Далее установить:

- кто active closer;
- сколько connections/sec;
- используется ли keep-alive;
- есть ли pooling;
- действительно ли возникает ephemeral-port exhaustion.

---

## Симптом E: `Cannot assign requested address`

Проверить:

```
ss -s
```

```
cat /proc/sys/net/ipv4/ip_local_port_range
```

И количество outbound connections.

Это может быть связано с исчерпанием локальных ephemeral ports, но диагноз должен подтверждаться фактической topology и connection tuple distribution.

---

## Симптом F: `nf_conntrack: table full`

Проверить:

```
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
```

и:

```
dmesg | grep -i conntrack
```

Дальше определить:

- нужен ли conntrack;
- какой traffic его создаёт;
- не происходит ли connection storm;
- достаточно ли лимита;
- не является ли проблема следствием архитектуры NAT/container networking.

# 42. Что означает «High Load»

High Load — не конкретное число packets/sec.

Систему можно считать перегруженной относительно конкретного ресурса:

```
CPU saturation
memory pressure
RX ring exhaustion
NAPI budget pressure
socket buffer pressure
listen queue pressure
ephemeral port exhaustion
conntrack table exhaustion
NIC bandwidth saturation
PCIe bandwidth saturation
application accept/read rate
```

Поэтому утверждение:

> «сервер выдерживает 1M packets/sec»

без указания packet size, CPU, NIC, protocol, topology, offloads и workload почти бессодержательно.

---

# 43. Packet rate vs bandwidth

Два workload:

```
A:
1 000 000 pps × 64 B
```

и:

```
B:
10 000 pps × 9 KB
```

могут иметь существенно разную CPU profile.

Первый создаёт огромное количество per-packet operations.

Второй может быть bandwidth-heavy, но иметь меньше packet processing overhead.

Поэтому performance analysis должен отдельно смотреть:

```
pps
bps
CPU cycles/packet
CPU cycles/byte
```

---

# 44. Latency vs throughput

Большие queues могут повысить throughput при bursty workload:

```
burst
  ↓
queue
  ↓
batch processing
```

но одновременно увеличить latency:

```
queueing delay ↑
```

Это классический trade-off.

Поэтому tuning должен иметь SLO:

```
throughput target
+
p99/p999 latency target
+
loss target
```

# 45. Почему нельзя универсально рекомендовать:

```
net.core.netdev_max_backlog = 10000
net.core.netdev_budget = 600
net.ipv4.tcp_max_syn_backlog = 16384
net.core.somaxconn = 16384
```

Такие значения могут быть полезными экспериментальными точками, но не являются универсальным production baseline.

Причины:

- kernel version;
- NIC driver;
- CPU count;
- NUMA;
- traffic pattern;
- packet size;
- application accept rate;
- network RTT/loss;
- containerization;
- conntrack;
- memory budget.

Тюнинг должен основываться на наблюдаемом bottleneck.

# 47. Корреляция метрик

Пример:

```
pps ↑
   │
   ├── CPU softirq ↑
   │
   ├── RX queue drops ↑
   │
   └── application latency ↑
```

Это сильнее указывает на packet-processing bottleneck, чем просто:

```
load average = 20
```

Другой пример:

```
SYN_RECV ↑
accept queue overflow ↑
application CPU = 100%
```

указывает на проблему capacity/accept path, а не обязательно на NIC.

# 48. Разделение kernel и application responsibility

Очень важно не приписывать ядру то, что происходит в userspace.

### Kernel отвечает за:

- packet reception/transmission;
- TCP state machine;
- socket queues;
- routing;
- Netfilter;
- congestion control;
- retransmissions;
- memory management;
- namespace isolation.

### Application отвечает за:

- `accept()`;
- `recv()/read()`;
- `send()/write()`;
- `close()`;
- connection pooling;
- worker lifecycle;
- event loop;
- backpressure.

Например:

```
CLOSE_WAIT
```

обычно нельзя исправить изменением `tcp_rmem`.

# 50. Частые ошибки в документации

## Ошибка 1

> «NAPI = softirq, который всегда работает на том же CPU».

Нет. Это слишком грубое описание scheduling model.

---

## Ошибка 2

> «netdev_max_backlog — размер RX ring».

Нет.

RX ring — hardware/driver queue.

`netdev_max_backlog` относится к software networking backlog.

---

## Ошибка 3

> «RPS распределяет hardware interrupts».

Нет.

RSS влияет на hardware queue/interrupt distribution; RPS выбирает CPU для дальнейшей software processing. citeturn1search2turn1search8

---

## Ошибка 4

> «CLOSE_WAIT очищается kernel timeout».

Обычный `CLOSE_WAIT` не должен рассматриваться как timer-based cleanup mechanism. Это состояние означает ожидание локального application close.

---

## Ошибка 5

> «TIME_WAIT всегда 60 секунд».

Слишком конкретное утверждение без kernel/version context.

---

## Ошибка 6

> «syncookies — performance tuning».

Нет. Это защитный механизм при SYN backlog pressure. Linux man-pages прямо предостерегает от использования syncookies как обычного tuning mechanism. citeturn1search0

---

## Ошибка 7

> «Большой backlog решает overload».

Нет.

Backlog — buffer, а не дополнительная processing capacity.

# 52. Итоговая модель

Для системного анализа Linux networking полезно держать в голове следующую цепочку:

```
                    HARDWARE
                       │
                  NIC / DMA
                       │
                 RX/TX rings
                       │
                 IRQ / NAPI
                       │
             ┌─────────┴─────────┐
             │                   │
           RSS                  RPS
             │                   │
             └─────────┬─────────┘
                       │
                    skb
                       │
                GRO / protocol
                       │
             VLAN / bridge / L3
                       │
             Netfilter / conntrack
                       │
                    TCP/UDP
                       │
                socket queues
                       │
                  application
```

Для TCP connection lifecycle:

```
SYN
 │
 ▼
SYN_RECV
 │
ACK
 │
 ▼
ESTABLISHED
 │
 │ application traffic
 │
FIN
 │
 ▼
CLOSE_WAIT       ← peer closed, local application must close
 │
close()
 │
 ▼
CLOSED
```

При active close:

```
ESTABLISHED
     │
    FIN
     ▼
 FIN_WAIT_1
     │
     ▼
 FIN_WAIT_2
     │
     ▼
 TIME_WAIT
     │
     ▼
 CLOSED
```

Главный принцип performance engineering:

> **Сначала определить точку ограничения и подтвердить её измерениями; только после этого менять kernel/network parameters.**

# 54. Версионность и точность

Linux networking — moving target. Параметры, defaults, semantics и driver capabilities меняются между kernel releases.

Поэтому для production runbook рекомендуется фиксировать:

```
Kernel:
  uname -a
  uname -r

Distribution:
  /etc/os-release

NIC:
  ethtool -i eth0
  ethtool eth0
  ethtool -k eth0
  ethtool -l eth0
  ethtool -g eth0

CPU/NUMA:
  lscpu
  numactl -H

Networking:
  ip -details link
  ip route
  sysctl -a
```

Любое конкретное значение `sysctl` должно рассматриваться как **version- and workload-specific configuration**, а не как универсальная константа Linux.
