# Механизм OOM Killer (Out of Memory)

> **Out-Of-Memory (OOM) Killer** — подсистема ядра Linux, активируемая в условиях критической нехватки физической памяти и пространства подкачки (Swap). Основная задача OOM Killer — принудительное завершение одного или нескольких процессов (посредством незадерживаемого сигнала `SIGKILL`) для освобождения оперативной памяти и предотвращения состояния полных блокировок системы (Hard Lockup).

## Причины срабатывания и поведение ядра перед OOM

Когда вся доступная физическая RAM и Swap-пространство исчерпаны, а ядро Linux не может выделять физические страницы для вызовов `brk()`, `mmap()` или `fork()`, наступает состояние **Out of Memory**.

```
       Свободная RAM + Swap исчерпаны
                     │
                     ▼
       Direct Reclaim (Прямое вытеснение)
 ┌───────────────────┴───────────────────┐
 │ Агрессивный сброс Page Cache / Dentry │
 └───────────────────┬───────────────────┘
                     │
         Высокий I/O Шторм + D-state
                     │
                     ▼
        Память ВСЁ ЕЩЁ НЕ освобождена?
         ┌───────────┴───────────┐
         │ ДА                    │ НЕТ
         ▼                       ▼
out_of_memory()              Продолжение
(Запуск OOM Killer)          работы
```

### Режим Direct Reclaim и I/O Шторм

Перед вызовом функтора `out_of_memory()` ядро пытается избежать критического завершения задач с помощью **Direct Reclaim (Прямое вытеснение)**:

1. Приостанавливает исполнение пользовательских потоков.
2. Начинает агрессивно вымывать из RAM чистые страницы файлового кэша (`Page Cache`) и метаданных файловой системы (`dentry`, `inode`).

На высоконагруженных системах это провоцирует **I/O шторм**: процессы проваливаются в состояние непрерываемого сна (**`D-state`**), ожидая сброса данных на диск, а отклик системы падает до нуля. Если после полного вымывания `Page Cache` выделение памяти невозможно, ядро запускает OOM Killer.

## Алгоритм выбора процесса-жертвы (`oom_score`)

OOM Killer сканирует список структур `task_struct` (в масштабах всей ОС или конкретной `cgroup`) и рассчитывает для каждого кандидата балл уничтожения — **`oom_score`** (в диапазоне от `0` до `1000`). Процесс с наибольшим значением уничтожается первым.

### Математическая формула расчета (Ядра Linux $\ge$ 2.6.36, включая 5.x / 6.x)

Базовый балл рассчитывается как доля памяти, занимаемая процессом относительно общего доступного объема (RAM + Swap), выраженная в **промилле (долях от 1000)**:

$$\text{Базовый OOM Score} = \left( \frac{\text{RSS} + \text{Swap} + \text{Tmpfs}}{\text{Total RAM} + \text{Total Swap}} \right) \times 1000$$

К полученному базовому баллу линейно прибавляется пользовательский коэффициент смещения (`oom_score_adj`):

$$\text{Итоговый oom\_score} = \text{Базовый OOM Score} + \text{oom\_score\_adj}$$

### Факторы корректировки скоринга

|**Фактор / Параметр**|**Влияние на oom_score**|**Механика ядра**|
|---|---|---|
|**Потребление RAM + Swap**|Прямо пропорционально|Чем больше сумарный объем `RSS + Swap + Tmpfs`, тем выше базовый скор.|
|**`oom_score_adj`**|Модификатор приоритета|Смещение от `-1000` до `+1000`. Прибавляется математически.|
|**Процессы Root (UID 0)**|$-30$ баллов (скидка 3%)|Ядро дает небольшую скидку привилегированным системным процессам.|
|**Капабилити `CAP_SYS_ADMIN`**|$-30$ баллов (скидка 3%)|Защита администрирующих процессов от случайного уничтожения.|
|**Cgroup v2 Memory Limit**|Локальный перерасчет|Внутри контейнера расчёт промилле идет от `memory.max` этой cgroup.|

> **Защитный барьер:** Если для процесса задано значение `oom_score_adj = -1000`, итоговый `oom_score` принудительно устанавливается в `0`. **Такой процесс никогда не будет уничтожен OOM Killer.**

## Управление приоритетами OOM в продакшене

### Прямой доступ через интерфейс `/proc`

Изменение значения `oom_score_adj` для запущенного процесса (на примере PID `7890`):

```Bash
echo -1000 > /proc/7890/oom_score_adj
```

Просмотр текущего итогового значения с учетом скидок и пользовательских настроек:

```Bash
cat /proc/7890/oom_score
```

### Конфигурация через Systemd

Для автоматической установки правил при старте сервиса используется директива `OOMScoreAdjust` в секции `[Service]`:

```Ini, TOML
[Unit]
Description=Critical Database Engine

[Service]
ExecStart=/usr/bin/postgres -D /var/lib/postgresql/data
# Защита master-процесса базы данных от OOM Killer
OOMScoreAdjust=-1000
```

### Сопоставление классов Quality of Service (QoS) в Kubernetes

Kubernetes автоматически транслирует требования к ресурсам контейнеров в значения `oom_score_adj` для рантайма контейнеризации (CRI):

```Plaintext
   QoS Class            Memory Limits / Requests             oom_score_adj
┌─────────────┐   ┌───────────────────────────────────┐   ┌─────────────────┐
│ Guaranteed  │   │ Requests == Limits (CPU & Memory) │   │     -997        │
├─────────────┤   ├───────────────────────────────────┤   ├─────────────────┤
│ Burstable   │   │ Requests < Limits                 │   │ 2 ... 999       │
├─────────────┤   ├───────────────────────────────────┤   ├─────────────────┤
│ BestEffort  │   │ Limits / Requests НЕ указаны      │   │     1000        │
└─────────────┘   └───────────────────────────────────┘   └─────────────────┘
```

- **Guaranteed (`OOMScoreAdjust=-997`):** Максимальная защита. Уничтожаются в последнюю очередь при исчерпании ресурсов узла.
- **Burstable (`OOMScoreAdjust` от `2` до `999`):** Вычисляется динамически по формуле: $1000 - \left( \frac{\text{memory.requests}}{\text{Node Memory}} \times 1000 \right)$. Чем больше памяти официально зарезервировано, тем меньше шанс гибели.
- **BestEffort (`OOMScoreAdjust=1000`):** Не имеют гарантий. Уничтожаются первыми при малейшем дефиците RAM.


## Стратегии поведения: Kernel Panic вместо OOM Kill

В распределенных отказоустойчивых кластерах (например, ClickHouse, Elasticsearch, PostgreSQL Patroni) уничтожение OOM Killer одного из внутренних рабочих процессов может перевести узел в состояние «зомби» (процесс отвалился, но порты или блокировки остались).

В таких архитектурах безопаснее мгновенно переводить узел в **Kernel Panic** для быстрой перезагрузки и отработки Failover на уровне кластерного балансировщика.

Настройка в `/etc/sysctl.d/99-oom-panic.conf`:

```Ini, TOML
# Переводить ядро в Kernel Panic при невозможности выделить память (0 — по умолчанию)
vm.panic_on_oom = 1

# Автоматически перезагружать ОС через 10 секунд после Kernel Panic
kernel.panic = 10
```

Применение изменений:

```sh
sysctl -p /etc/sysctl.d/99-oom-panic.conf
```

## Диагностика и разбор системных дампов

### Поиск фактов срабатывания OOM

Быстрая проверка логов ядра на наличие событий уничтожения процессов:

```sh
# Через системный журнал systemd
journalctl -k --grep="Out of memory"

# Через буфер сообщений ядра
dmesg -T | grep -i -E 'oom[-_]killer|killed process'
```

## Практический чеклист предотвращения OOM

1. **Мониторинг метрик задержки и памяти:** Отслеживать `Memory RSS`, `Swap Usage` и метрики PSI (`Pressure Stall Information`) по памяти (`/proc/pressure/memory`).
2. **Использование Cgroups v2:** Задавать параметры `memory.high` для упреждающего дроттлинга и вытеснения страниц до достижения `memory.max`.
3. **Корректный Swap:** Наличие небольшого Swap-файла (даже на NVMe-накопителях) позволяет ядру выгружать редко используемые анонимные страницы, предотвращая ранние вызовы OOM.
4. **Тюнинг приложения:** Ограничивать размеры Heap (например, `-Xmx` для JVM) с учетом накладных расходов памяти самого процесса (Native Memory, Shared Libraries, Thread Stacks).
