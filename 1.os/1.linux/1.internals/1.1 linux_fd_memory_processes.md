## Файловые дескрипторы и лимиты

### Что такое File Descriptor

В операционных системах семейства Unix/Linux процесс взаимодействует с файлами, сокетами, межпроцессными каналами (pipe), устройствами и другими объектами ядра через **файловые дескрипторы (File Descriptors, FD)**.

FD представляет собой неотрицательное целое число, являющееся индексом в таблице дескрипторов конкретного процесса (`struct files_struct`).

Стандартные дескрипторы процесса:

| **FD** | **Имя**  | **Назначение**           |
| ------ | -------- | ------------------------ |
| `0`    | `stdin`  | Стандартный поток ввода  |
| `1`    | `stdout` | Стандартный поток вывода |
| `2`    | `stderr` | Стандартный поток ошибок |

Необходимо разграничивать числовой идентификатор FD и структуру ядра, на которую он указывает. Связь структур данных ядра Linux описывается следующей цепочкой:

``` 
Пространство пользователя (User Space)
  │
  └── struct task_struct (Процесс)
        │
        └── struct files_struct (Таблица FD процесса)
              │
              └── FD (Индекс, например: 3)
                    │
                    ▼
Пространство ядра (Kernel Space)
  └── struct file (Open File Description: позиция смещения, флаги доступа)
        │
        └── struct inode / socket / pipe (Физический объект VFS)
````

Таким образом, дескриптор является **процессной ссылкой на открытый объект ядра (`struct file`)**, а не самим файлом или структурой `inode`.

### Последствия исчерпания ресурса файловых дескрипторов

При деградации системы или высокой нагрузке процесс может удерживать большое количество ресурсов:

- Файлов журналов (лог-файлов);
- Сетевых сокетов (TCP/UDP, Unix Domain Sockets);
- Пулов соединений к СУБД;
- Межпроцессных каналов (pipe, fifo);
- Открытых библиотек (`.so`) и конфигурационных файлов. 

При достижении установленного ресурсоемкого лимита новые системные вызовы `open()`, `socket()`, `accept()`, `pipe()` и их аналоги завершаются с ошибкой. В высоконагруженных сервисах исчерпание FD приводит к отказу в обслуживании (Denial of Service) поступающих соединений и каскадным сбоям компонента (например, невозможности сформировать запись в журнале).

### Различие ошибок `EMFILE` и `ENFILE`

Ядро Linux разделяет уровни ограничения ресурсов на процессный и системный.

#### `EMFILE` (`Too many open files`)

Ошибка указывает на достижение локального лимита открытых файлов конкретным процессом (`RLIMIT_NOFILE`).

Проверка ограничений текущей оболочки:

```sh
ulimit -Sn
ulimit -Hn
```

где:

- **soft limit** — мягкий лимит, непосредственно применяемый к процессу;

- **hard limit** — жесткий лимит, определяющий верхнюю границу, до которой soft limit может быть повышен процессом без привилегий `CAP_SYS_RESOURCE`.


#### `ENFILE` (`Too many open files in system`)

Ошибка означает исчерпание глобального системного предела на количество одновременно созданных объектов `struct file` (настраивается через `fs.file-max`).

Диагностика уровня исчерпания ресурса:

*Фрагмент кода*

```sh
EMFILE  →  Ограничение на уровне процесса (RLIMIT_NOFILE)
ENFILE  →  Глобальное ограничение ядра (fs.file-max / память ядра)
```

## Уровни ограничения количества открытых файлов

### Глобальный уровень

Параметр:

```sh
cat /proc/sys/fs/file-max
```

Показывает системный максимум для числа одновременно открытых file descriptions.

Текущее состояние проверяется через:

```sh
cat /proc/sys/fs/file-nr
```

На современных ядрах формат и интерпретация полей `file-nr` зависят от версии ядра; поэтому этот файл следует рассматривать как источник низкоуровневой статистики, а не как универсальную формулу вида «первое число = все открытые FD».

Временное изменение параметра:

```sh
sysctl -w fs.file-max=2097152
```

Для постоянной настройки используется файл:

```sh
/etc/sysctl.conf
```

Пример записи:

 *Фрагмент кода*

```sh
fs.file-max = 2097152
```

Применение постоянной конфигурации:

```sh
sysctl -p
```

или через принудительную загрузку конкретного файла конфигурации `sysctl`.

> **Практический принцип:** увеличение глобального лимита не исправляет `EMFILE`, если проблема находится на уровне конкретного процесса.

### Лимиты процесса: `RLIMIT_NOFILE`

Для процесса действует ресурсный лимит `RLIMIT_NOFILE`.

Проверка в shell:

```sh
ulimit -Sn
ulimit -Hn
```

или:

```sh
ulimit -n
```

Проверка запущенного процесса:

```sh
cat /proc/1234/limits | grep "Max open files"
```

Пример вывода:

```sh
Max open files            65536                65536                files
```

Здесь:

- первое значение — soft limit;
- второе — hard limit.

## Где задавать лимиты в production

### Ограничения в PAM-сессиях

Для процессов, создаваемых в рамках PAM-сессий (интерактивный вход пользователя, SSH-сессии, авторизация через `su`/`sudo`), лимиты конфигурируются в файле:

```sh
/etc/security/limits.conf
```

Пример конфигурации:

```sh
nginx     soft    nofile   65536
nginx    hard    nofile   65536
```

**Ограничение применения:** Данный механизм обрабатывается модулем `pam_limits.so` и **не распространяется** на демоны и фоновые службы, запуск которых осуществляется напрямую системным менеджером (например, `systemd`), минуя стек PAM.

### Сервисы под управлением systemd

Для systemd-сервисов лимит задается непосредственно в конфигурации unit-файла.

Например:

```ini, TOML
[Service]
LimitNOFILE=65536
```

Редактирование drop-in-конфигурации выполняется командой:

```sh
systemctl edit имя_сервиса
```

Применение изменений:
 
```sh
systemctl daemon-reload
systemctl restart имя_сервиса
```

Проверка фактического лимита работающего процесса:

```sh
cat /proc/$(pidof имя_сервиса)/limits | grep "Max open files"
```

> **Важно:** `daemon-reload` перечитывает конфигурацию unit-файлов, но запущенный процесс не получает новые resource limits автоматически. Для применения нового лимита требуется перезапуск процесса.

## Диагностика файловых дескрипторов

### Определение количества активных FD процесса

Для получения точного количества открытых дескрипторов процесса с заданным PID рекомендуется команда:

```sh
find /proc/1234/fd -mindepth 1 | wc -l
```

Использование утилиты `find` предпочтительнее `ls -1 /proc/<PID>/fd | wc -l`, так как исключает потенциальные искажения подсчета при форматировании вывода.

Каталог `/proc/<PID>/fd` содержит символические ссылки на объекты VFS, выделенные процессу.

### Определение удержания ресурсов процессом

Утилита `lsof` позволяет определить открытые файлы, сокеты, pipe и другие объекты:

```sh
lsof -p 1234
```

Для сетевых объектов применяются фильтры `lsof` по типам и протоколам, а также специализированные инструменты:

```sh
ss -p
```

### Лимиты работающего процесса

```sh
cat /proc/1234/limits | grep "Max open files"
```

Проверка файла `limits` процесса обеспечивает получение достоверной информации, в отличие от вызова `ulimit` в текущей shell-сессии.

### Динамическое изменение лимитов выполняющегося процесса

Если перезапуск процесса недопустим, изменение лимитов ресурсов (`RLIMIT_NOFILE`) для запущенного процесса выполняется утилитой `prlimit` (использующей системный вызов `prlimit64`):

```sh
prlimit --pid 1234 --nofile=65536:65536
```

Формат аргумента: `--nofile=SOFT:HARD`.

Проверка примененных изменений:

```sh
prlimit --pid 1234 --nofile
```

#### Ограничения применения `prlimit`

1. Изменения применяются исключительно к указанному процессу (`PID`) и не наследуются ранее созданными дочерними процессами, если не применен флаг `--propagate`.

2. Изменения не сохраняются в конфигурационных файлах и сбрасываются при перезапуске службы.

3. Для изменения лимитов сторонних процессов требуются привилегии `root` или наличие `CAP_SYS_RESOURCE`.


`prlimit` является инструментом оперативного реагирования (hot-fix) и не заменяет конфигурацию в `systemd` или `limits.conf`.

## Виртуальная память

### Основная модель

Linux предоставляет каждому процессу собственное **виртуальное адресное пространство**.

Схема трансляции адресов:

```
Процесс
┌────────────────────────────────────────┐
│        Virtual Address Space           │
│                                        │
│  stack                                 │
│  mmap regions (inc. shared libraries)  │
│  heap                                  │
│  code / text                           │
└───────────────────┬────────────────────┘
                    │
                    ▼
        Таблицы страниц (Page Tables)
                    │
                    ▼
         Физическая память (RAM)

```

Процесс работает с виртуальными адресами. Таблицы страниц (`page tables`) отображают их на физические страницы памяти.

### Страницы памяти

Память управляется страницами (**pages**).

Для архитектур x86/x86-64 базовый размер страницы составляет:

```plaintext
4 KiB
```

В зависимости от архитектуры и конфигурации ядра также могут использоваться Huge Pages, например, размером **2 MiB** или **1 GiB**.

## Page Fault

**Page fault** возникает, когда процессор при обращении к виртуальному адресу обнаруживает, что требуемое отображение отсутствует или требует дополнительной обработки ядром.

Page fault является штатным механизмом управления виртуальной памятью.

### Minor Page Fault и выделение памяти

**Minor Page Fault** (малый сбой страницы) обрабатывается ядром без обращения к блочным устройствам ввода-вывода.

Типичные сценарии возникновения:

- Обращение к странице, находящейся в физической памяти (RAM), но не отображенной в таблице страниц (`Page Table`) данного процесса (например, общая библиотека в Page Cache);
- Механизм Copy-On-Write (COW) при изменении дублированной страницы после вызова `fork()`;
- Первичное обращение к анонимной памяти (Zero-Fill-on-Demand): ядро выделяет физическую страницу, заполненную нулями, без чтения с диска.

### Major Page Fault

**Major fault** требует выполнения операций I/O, например чтения страницы из backing storage.

Типичные сценарии:

1. Отсутствие запрашиваемой страницы файла в Page Cache;
2. Запрошенная анонимная страница была вытеснена в Swap и требует обратной загрузки в RAM.

Схема обработки:

```
CPU
 │
 ▼
Page fault
 │
 ├── данные доступны в RAM
 │       └── Minor fault
 │
 └── требуется I/O
         └── Major fault
                │
                └── storage / swap
```

Высокая частота major faults указывает на дефицит физической памяти или низкую локальность данных, что приводит к росту задержек (latency).

## Anonymous Memory и Page Cache

Для анализа состояния памяти операционной системы разграничиваются основные категории страниц.

### Page Cache

Page Cache (файловый кэш) хранит в оперативной памяти (RAM) содержимое файлов, прочитанное с файловой системы. Данный механизм минимизирует количество прямых обращений к дисковым накопителям.

#### Clean pages

Страница памяти, содержимое которой полностью идентично данным в постоянном хранилище (backing storage). При возникновении дефицита RAM clean page освобождается ядром незамедлительно, без выполнения предварительной записи на диск.

#### Dirty pages

Страница памяти, которая была изменена в процессе работы и на текущий момент не синхронизирована с backing storage. Вытеснение dirty page требует обязательной предварительной записи измененных данных на накопитель с помощью фоновых потоков ядра или системных вызовов синхронизации.

### Anonymous Memory

Anonymous memory (анонимная память) представляет собой области ОЗУ, не имеющие файлового backing storage. Данный тип памяти генерируется динамически в процессе выполнения приложений.

Примеры использования:

- Куча процессов (heap);
- Стек потоков (stack);
- Внутренние структуры runtime сред исполнения;
- Области памяти, выделенные через системный вызов `mmap()` с флагом `MAP_ANONYMOUS`.

Вытеснение анонимной памяти из RAM для освобождения физического пространства осуществляется исключительно в пространство Swap.

Схема разделения памяти:

```
             Physical RAM
                  │
       ┌──────────┴──────────┐
       │                     │
       ▼                     ▼
   Page Cache          Anonymous Memory
       │                     │
       │                     ▼
       │                    Swap
       │
       ▼
   Filesystem
```

## Swap и `vm.swappiness`

`vm.swappiness` — параметр политики reclaim, определяющий соотношение вытеснения анонимной памяти и файлового кэша.

Проверка текущего значения:

```sh
cat /proc/sys/vm/swappiness
```

или:

```sh
sysctl vm.swappiness
```

Временное изменение:

```sh
sysctl -w vm.swappiness=10
```

Постоянная конфигурация в `/etc/sysctl.conf`:

 *Фрагмент кода*

```sh
vm.swappiness = 10
```

### Особенности параметра `swappiness = 0`

Значение `0` не означает полное отключение подсистемы Swap.

Алгоритмы reclaim различаются в зависимости от версии ядра Linux.

Основной принцип:

> `swappiness` задает баланс политики reclaim, но не является выключателем Swap.

Значение параметра выбирается на основе тестирования под конкретным типом нагрузки. Особое внимание требуется для:

- СУБД;
- Среды исполнение JVM;
- Узлов Kubernetes;
- Систем с требованиями low latency.

## `vm.vfs_cache_pressure`

Параметр `vm.vfs_cache_pressure` регулирует склонность ядра к освобождению объектов VFS (dentry и inode cache):

```sh
sysctl vm.vfs_cache_pressure
```

Значение по умолчанию: `100`.

Временное изменение:

```sh
sysctl -w vm.vfs_cache_pressure=50
```

Изменение параметра должно обосновываться метриками:

- Memory pressure;
- Latency операций;
- Нагрузка на I/O;
- Cache hit rate.

## Диагностика памяти

### `/proc/meminfo`

Базовый источник статистики:

```
cat /proc/meminfo
```

Выборка ключевых полей:

```sh
grep -E 'MemTotal|MemFree|MemAvailable|Cached|Buffers|SwapTotal|SwapFree|AnonPages|Dirty|Writeback' /proc/meminfo
```

### Page Faults

При наличии пакета `sysstat` статистика собирается командой:

```sh
sar -B 1
```

Ключевые метрики:

- `majflt/s` — количество major page faults в секунду;
- Интенсивность сканирования и освобождения страниц (reclaim).

Метрики анализируются в комплексе с показателями latency, CPU, I/O wait и сброса страниц в Swap.

## Состояния процессов

Инструменты `ps`, `top`, `btop` отображают текущие состояния процессов. В выводе `ps` состояние определяется полем `STAT`.

Основные состояния:

|**STAT**|**Состояние**|**Смысл**|
|---|---|---|
|`R`|Running / Runnable|Процесс исполняется на CPU или находится в очереди готовности к исполнению|
|`S`|Interruptible sleep|Ожидает события (таймер, I/O, сигнал) и может быть разбужен сигналом|
|`D`|Uninterruptible sleep|Непрерываемое ожидание ресурса в ядре (обычно дисковый или сетевой I/O)|
|`Z`|Zombie|Процесс завершен, но родительский процесс не зафиксировал код завершения через `wait()`|

Символы-модификаторы (`T`, `<`, `N`, `s`, `l`, `+`) уточняют приоритет, наличие потоков или сессию процесса.

### Состояние `R`

Состояние `R` указывает, что задача выполняется на CPU или находится в состоянии `runnable`, ожидая выделения процессорного времени планировщиком.

Для оценки утилизации CPU используются команды:

```sh
top
```

или:

```sh
ps -eo pid,ppid,stat,pcpu,comm --sort=-pcpu
```

### Состояние `S`

Состояние `S` (interruptible sleep) является штатным для большинства процессов, находящихся в ожидании событий (сетевые данные, таймеры, блокировки).

Большое количество процессов в состоянии `S` не является признаком аномалии.

### Состояние `D`

Процесс в состоянии `D` (uninterruptible sleep) заблокирован внутри системного вызова в ядре без возможности обработки сигналов.

Причины возникновения:

- Ожидание отклика дисковой подсистемы;
- Сбои в сетевых файловых системах (NFS);
- Блокировка на уровне драйверов или аппаратных средств.

```sh
ps aux | awk 'NR==1 || $8 ~ /^D/'
```

#### Причины неэффективности `SIGKILL` (`kill -9`) в состоянии `D`

Процесс в состоянии `TASK_UNINTERRUPTIBLE` не реагирует на `SIGKILL` по следующим причинам:

1. Флаг наличия сигнала записывается в структуру `pending` сигналов процесса в `task_struct`.
2. Планировщик задач не переводит процесс в состояние `TASK_RUNNING`, пока не завершится операция ядра.
3. Проверка маски сигналов выполняется только при выходе из системного вызова перед возвратом управления в User Space.

Если операция ввода-вывода заблокирована бессрочно, процесс останется в состоянии `D` до восстановления ресурса или перезагрузки ОС.

#### Диагностика точек блокировки (`wchan` и `kernel stack`)

Анализ точки ожидания процесса с PID `5678` в ядре:

```sh
cat /proc/5678/wchan
```

Просмотр стека вызовов ядра:

```sh
cat /proc/5678/stack
```

Доступ к `/proc/<PID>/stack` определяется правами доступа и конфигурацией ядра.

### Состояние `Z`: Zombie

Zombie — завершившийся процесс, ресурсная структура которого освобождена, но запись в таблице процессов сохраняется до считывания кода завершения родительским процессом через `wait()`.

Zombie-процесс не потребляет ресурсы CPU и RAM.

#### Освобождение ресурсов процессов в состоянии Zombie (`Z`)

Отправка сигналов `SIGKILL` непосредственно к Zombie-процессу не приносит результата, так как процесс уже завершен.

Порядок действий для очистки записи:

1. Определение родительского процесса (`PPID`):
 
```sh
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
```

2. Анализ причин отсутствия вызовов `wait()`/`waitpid()` со стороны родительского процесса.
3. Завершение или перезапуск родительского процесса. При завершении родителя дочерние процессы усыновляются процессом `init` (PID 1) или `subreaper` (например, `systemd`), которые автоматически выполняют `wait()`.

## Практический алгоритм диагностики

### Сценарий A: `Too many open files`

1. Определение целевого процесса:

```sh
systemctl status имя_сервиса
```

2. Проверка установленных лимитов процесса:

```sh
cat /proc/<PID>/limits | grep "Max open files"
```

3. Подсчет количества выделенных дескрипторов:

```sh
find /proc/<PID>/fd -mindepth 1 | wc -l
```

4. Анализ открытых объектов:

```sh
lsof -p <PID>
```

5. Проверка системных ограничений:

```sh
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr
```

6. Проверка и изменение конфигурации unit-файла systemd при необходимости:

```sh
systemctl show имя_сервиса -p LimitNOFILE
```

### Сценарий B: высокая memory pressure

1. Анализ общего распределения памяти:

```sh
free -h
cat /proc/meminfo
```

2. Проверка подсистемы Swap:

```sh
swapon --show
```

3. Анализ частоты сбоев страниц:

```sh
sar -B 1
```

4. Ранжирование процессов по потреблению RAM (RSS):

```sh
ps -eo pid,ppid,%mem,rss,comm --sort=-rss | head
```

5. Сопоставление категорий памяти:

```
RAM usage
   │
   ├── Anonymous memory
   │
   ├── Page Cache
   │
   ├── Swap activity
   │
   └── Kernel memory
```

Объем `Cached` не является признаком нехватки памяти, так как Linux использует нераспределенную RAM под файловый кэш.

### Сценарий C: процессы в состоянии `D`

1. Поиск процессов в состоянии непрерываемого ожидания:

```sh
ps -eo pid,ppid,stat,wchan:32,comm | awk '$3 ~ /^D/'
```

2. Анализ стека ядра заблокированного процесса:

```sh
cat /proc/<PID>/wchan
cat /proc/<PID>/stack
```

3. Просмотр системного журнала на предмет ошибок ввода-вывода или драйверов:

```sh
dmesg -T
journalctl -k
```

## Справочник команд

### File Descriptors

```sh
# Лимиты текущей shell-сессии
ulimit -Sn
ulimit -Hn

# Лимит конкретного процесса
cat /proc/<PID>/limits | grep "Max open files"

# Подсчет количества открытых FD
find /proc/<PID>/fd -mindepth 1 | wc -l

# Просмотр открытых объектов процесса
lsof -p <PID>

# Глобальные параметры ядра
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr

# Проверка лимитов в systemd
systemctl show <service> -p LimitNOFILE
```

### Virtual Memory

```sh
# Общая статистика RAM
free -h

# Статистика подсистемы памяти ядра
cat /proc/meminfo

# Состояние Swap
swapon --show

# Просмотр параметров sysctl
sysctl vm.swappiness
sysctl vm.vfs_cache_pressure

# Мониторинг page faults
sar -B 1
```

### Processes

```sh
# Просмотр состояний процессов
ps -eo pid,ppid,stat,comm

# Поиск Zombie-процессов
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'

# Поиск процессов в D-состоянии
ps -eo pid,ppid,stat,wchan:32,comm | awk '$3 ~ /^D/'

# Точка ожидания в ядре
cat /proc/<PID>/wchan
cat /proc/<PID>/stack

# Журналы ядра
dmesg -T
journalctl -k
```

## Ключевые выводы

1. **FD является ссылкой на объект ядра**, а не самим файлом или структурой `inode`.
2. **`EMFILE` указывает на превышение лимита процесса**, а `ENFILE` — на исчерпание глобального ресурса ядра.
3. **Лимиты работающего процесса проверяются через `/proc/<PID>/limits`**, а не через утилиту `ulimit` текущей оболочки.
4. **Конфигурирование лимитов демонов под управлением systemd** выполняется в unit-файлах с помощью директивы `LimitNOFILE`.
5. **Page fault является штатным механизмом** управления виртуальной памятью.
6. **Major page fault влечет за собой операции ввода-вывода**, оказывая прямое влияние на задержки исполнения.
7. **Page Cache используется ядром** для оптимизации файлового ввода-вывода и освобождается при необходимости выделения памяти.
8. **Параметр `vm.swappiness` регулирует баланс вытеснения страниц**, но не является бинарным переключателем активности Swap.
9. **Процессы в состоянии `D` не реагируют на `SIGKILL`**, поскольку заблокированы внутри системных вызовов в ядре.
10. **Zombie-процессы не потребляют ресурсы CPU и RAM**; очистка таблицы процессов осуществляется через обработку вызовов родительским процессом.

## Заключение

Понимание механизмов адресации памяти, управления файловыми дескрипторами и планирования процессов позволяет производить локализацию неисправностей на основе модели работы ядра Linux.

Архитектурная схема взаимодействия подсистем:

```
                    Linux Kernel
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   File Descriptors   Memory           Processes
        │                │                │
        ▼                ▼                ▼
     limits         page cache         scheduler
     sockets        anonymous          sleep
     files          swap               zombie
     pipes          page faults        I/O wait
```

Диагностический подход заключается в последовательном определении лимитирующего ресурса и подтверждении гипотез данными системных интерфейсов `/proc`, `sysctl`, `ps`, `lsof`, `sar` и журналов ядра.
