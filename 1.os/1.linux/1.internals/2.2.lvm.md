# LVM (Logical Volume Manager): архитектура, устройство, управление, snapshots, thin provisioning и аварийное восстановление

> **LVM2** — подсистема управления блочными устройствами в Linux, которая добавляет слой логической адресации между физическими устройствами и файловой системой. Она позволяет объединять несколько физических устройств в пулы, выделять из них логические тома, расширять их, переносить данные между PV, создавать snapshots, thin volumes и использовать RAID/cache-возможности device-mapper.
>
> Важно: **LVM не является файловой системой и не заменяет RAID, backup или мониторинг**. LVM управляет размещением блоков; файловая система управляет файлами и каталогами; device-mapper и ядро обеспечивают отображение блочных устройств.

## 1. Где LVM находится в стеке хранения

Типичный стек выглядит так:

```text
                         [ Userspace ]
                              │
                       ┌──────▼──────┐
                       │ application │
                       └──────┬──────┘
                              │
==============================│=====================================================
                         [ Kernel ]
                              │
                       ┌──────▼──────┐
                       │     VFS     │
                       └──────┬──────┘
                              │
                    filesystem (XFS/ext4)
                              │
                       ┌──────▼──────┐
                       │  /dev/dm-X  │  <-- (Файловая система лежит
                       │  или тома   │       внутри конкретного LV)
                       │ /dev/mapper │
                       └──────┬──────┘
                              │
                    ┌─────────▼─────────┐
                    │   device-mapper   │ <-- Ядерный движок LVM
                    └─────────┬─────────┘
                              │
                             LVM (Logical Volume Management)
                 ┌────────────┼────────────┐
                 │            │            │
                LV           LV           LV  <-- Логические тома
                 │            │            │
                 └────────────┼────────────┘
                              │
                             VG               <-- Группа томов (пул)
                              │
                 ┌────────────┼────────────┐
                 │            │            │
                PV           PV           PV  <-- Физические тома LVM
                 │            │            │
              /dev/sdb    /dev/sdc    /dev/nvme0n1pX
                 │            │            │
                 └────────────┼────────────┘
                              │
                         block layer          <-- Идентификаторы дисков,
                              │                   очереди запросов (I/O schedulers)
                         driver / HBA         <-- Драйверы (ahci, nvme, mpt3sas)
                              │
==============================│====================================================
                        [ Hardware ]
                              │
                        physical media        <-- Сами чипы памяти или блины HDD

````

Главная идея:

```sh
       filesystem          # Файловая система (работает с файлами и inode)
           │
           ▼
 logical block address     # Логический адрес блока (LBA, с точки зрения ФС)
           │
           ▼
           LV              # Logical Volume (логический том LVM)
           │
           ▼
LVM / device-mapper mapping # Маппинг ядра (перевод логических экстентов LE в физические PE)
           │
           ▼
  PV / physical extents    # Physical Volume (конкретные PE-блоки на физическом уровне)
           │
           ▼
   physical block device   # Физическое блочное устройство (куда пишется итоговый сектор)

```

####  1. Гибкость физических объёмов (Physical Volume, PV)

LVM допускает использование различных типов блочных устройств в качестве PV. Инициализация PV возможна на:
- **Неразмеченных блочных устройствах** (например, `/dev/sdb`, `/dev/nvme0n1`).
- **Отдельных разделах диска** (например, `/dev/sdb1`, `/dev/sdc3`).
- **Устройствах составных слоев абстракции Storage Stack** (программный RAID `mdadm` (`/dev/md0`), зашифрованные LUKS-контейнеры (`/dev/mapper/crypt_disk`), устройства DRBD и др.).

#### 2. Структура PV, метаданные и выравнивание данных

Утверждение _«LVM просто нарезает диск на PE, начиная с нулевого сектора»_ — **грубая ошибка**.

Утверждение о том, что LVM распределяет экстенты (Physical Extents, PE), начиная с нулевого сектора блочного устройства, некорректно.

1. **LVM Label и область метаданных:** Команда `pvcreate` записывает метку LVM (LVM disk label) в один из первых четырех секторов блочного устройства (со смещением 512 байт), а также выделяет область для хранения метаданных VG (Volume Group Metadata Area).
2. **Выравнивание данных (Data Alignment):** Первый физический экстент (PE), предназначенный для пользовательских данных, размещается со смещением относительно начала диска. По умолчанию смещение составляет 1 МиБ, что обеспечивает выравнивание границ PE по размеру физических секторов (4K Advanced Format) и блокам стирания SSD (Erase Block).

# 2. Основные сущности LVM

LVM следует понимать через четыре понятия:

```text
PV → VG → LV → filesystem
```

## 2.1. PV — Physical Volume

**Physical Volume** — блочное устройство, подготовленное для использования LVM.

Примеры:

```sh
/dev/sdb
/dev/sdc
/dev/nvme0n1p3
```

Создание:

```
pvcreate /dev/sdb
```

Проверка:

```
pvs
pvdisplay
pvscan
```

PV содержит:

- LVM label;
- метаданные PV;
- идентификатор PV;
- сведения о размере и размещении;
- physical extents.

`pvcreate` может работать как с целым устройством, так и с разделом. Операция потенциально разрушительна: перед инициализацией необходимо убедиться, что устройство действительно предназначено для LVM. citeturn0search0

---

## 2.2. PE — Physical Extent

PV логически разбивается на **Physical Extents (PE)**.

PE — единица размещения LVM.

Размер PE определяется параметрами volume group. В современных конфигурациях часто используется несколько MiB, но **нельзя считать 4 MiB универсальным фиксированным значением**.

Проверить параметры:

```
vgdisplay vg_data
```

или:

```
vgs -o vg_name,vg_size,vg_free,vg_extent_size
```

Важно различать:

```
PE — physical extent
LE — logical extent
```

Для обычного linear LV логические экстенты LV отображаются на физические экстенты PV.

Упрощённо:

```
LV:
LE0 LE1 LE2 LE3 ...

       mapping

PV:
PE42 PE43 PE900 PE901 ...
```

Эти номера не обязаны быть последовательными на одном физическом устройстве.

---

# 3. VG — Volume Group

**Volume Group** — пул хранения, объединяющий один или несколько PV.

Например:

```
/dev/sdb ──┐
           ├── PV ──┐
/dev/sdc ──┘        │
                    ├── VG vg_data
/dev/sdd ── PV ─────┘
```

Создание:

```
vgcreate vg_data /dev/sdb /dev/sdc
```

Добавление PV:

```
vgextend vg_data /dev/sdd
```

Проверка:

```
vgs
vgdisplay vg_data
```

`vgcreate` создаёт новую VG поверх PV; если переданные устройства ещё не были подготовлены как PV, LVM может выполнить их инициализацию в рамках операции.

---

# 4. LV — Logical Volume

**Logical Volume** — логическое блочное устройство, выделенное из VG.

Например:

```
VG vg_data
├── LV lv_root
├── LV lv_db
├── LV lv_backup
└── LV lv_swap
```

Создание:

```
lvcreate -L 50G -n lv_data vg_data
```

или:

```
lvcreate -l 100%FREE -n lv_data vg_data
```

Проверка:

```
lvs
lvdisplay
lvscan
```

После активации LV обычно доступен как:

```
/dev/vg_data/lv_data
```

и через device-mapper:

```
/dev/mapper/vg_data-lv_data
```

`lvcreate` выделяет логические экстенты из свободного пространства VG. В зависимости от типа LV размещение может быть linear, striped, RAID, thin и т. д.

---

# 5. Linear LV

Наиболее простой тип LV:

```
PV1                 PV2
┌───────────────┐   ┌───────────────┐
│ PE PE PE PE   │   │ PE PE PE PE   │
└───────┬───────┘   └───────┬───────┘
        │                    │
        └─────────┬──────────┘
                  ↓
             linear LV
```

LV может занимать экстенты:

```
PV1: PE 0..999
PV2: PE 0..499

LV:
LE 0..999   → PV1
LE 1000..1499 → PV2
```

Это **не означает**, что физические диски автоматически работают как RAID.

Если один PV, содержащий часть linear LV, полностью теряется, соответствующая часть LV становится недоступной.

---

# 6. LVM и RAID — не одно и то же

Наличие нескольких PV в одной VG:

```
vgcreate vg_data /dev/sdb /dev/sdc
```

**не создаёт RAID-1 и не обеспечивает отказоустойчивость**.

Это всего лишь общий пул адресуемого пространства.

Нужно различать:

```
VG из нескольких PV
    ≠
RAID
```

Для отказоустойчивости используются, в зависимости от архитектуры:

- аппаратный RAID;
- Linux md RAID;
- LVM RAID;
- распределённые системы хранения;
- репликация на уровне приложения;
- backup.

LVM также умеет создавать RAID-подобные LV:

```
lvcreate --type raid1 -m 1 -L 100G -n lv_data vg_data
```

Точный набор возможностей зависит от версии LVM/device-mapper и конфигурации.

# 7. Thin provisioning

Обычный LV резервирует физическое пространство при создании:

```
VG: 1 TiB
LV: 500 GiB

500 GiB физически выделены LV.
```

Thin LV работает иначе:

```
VG
│
└── thin pool: 100 GiB physical
       │
       ├── thin LV A: 500 GiB virtual
       ├── thin LV B: 300 GiB virtual
       └── thin LV C: 200 GiB virtual
```

Виртуальный размер может быть больше физического пространства.

Физические блоки выделяются по мере записи. Thin pool состоит из data и metadata компонентов; kernel `dm_thin_pool` отслеживает соответствие виртуальных и физических блоков. citeturn1search2

Создание thin pool:

```
lvcreate -L 100G -n thinpool vg_data
lvcreate -L 2G -n thinpool_meta vg_data

lvconvert \
  --type thin-pool \
  --poolmetadata thinpool_meta \
  vg_data/thinpool
```

Создание thin LV:

```
lvcreate \
  --type thin \
  --thinpool thinpool \
  -V 500G \
  -n vm01 \
  vg_data
```

Проверка:

```
lvs -a
```

Полезные поля:

```
lvs -o lv_name,lv_attr,lv_size,pool_lv,origin,data_percent,metadata_percent
```

## 7.1. Главная опасность thin provisioning

Можно создать:

```
physical pool = 100G
virtual volumes = 500G
```

но при фактической записи физическое пространство закончится.

Поэтому необходимо мониторить минимум:

```
Data%
Meta%
```

Если thin pool заполнится, поведение зависит от настроек и типа исчерпания, но полагаться на «LVM сам всё исправит» нельзя.

Thin provisioning — это **не создание дополнительной физической ёмкости**, а отложенное распределение уже существующего пространства. citeturn1search2

# 8. Snapshots

LVM snapshot — логический снимок состояния LV.

Классическая модель snapshot использует **Copy-on-Write (COW)**.

Упрощённо:

```
До записи:

Origin:
A B C D E

Snapshot:
        ↑
     смотрит
     на origin
```

После изменения блока `C`:

```
Origin:
A B C' D E

Snapshot:
A B C  D E
      ↑
  сохранён старый блок
```

То есть snapshot первоначально не обязан содержать полную копию всех данных.

Создание:

```
lvcreate \
  -L 10G \
  -s \
  -n root_snapshot \
  /dev/vg0/lv_root
```

Проверка:

```
lvs
```

---

# 9. Snapshot — не backup

Это принципиально важное различие:

```
snapshot ≠ backup
```

Snapshot обычно находится в той же системе хранения и часто в той же VG.

Если физически уничтожена VG/PV:

```
origin + snapshot
        ↓
       потеря
```

Snapshot полезен как:

- точка согласованного чтения;
- краткосрочный источник для backup;
- механизм отката;
- основа для тестирования;
- источник для миграции.

Но сам по себе snapshot не является независимой резервной копией.

---

# 10. Переполнение классического COW snapshot

Для классического snapshot пространство выделяется для хранения старых блоков origin.

Если snapshot имеет размер:

```
10 GiB
```

а origin за время жизни snapshot переписал больше данных, чем snapshot способен сохранить, snapshot может стать `Invalid`.

Проверка:

```
lvs
```

Поэтому размер snapshot нужно рассчитывать исходя не из размера origin, а из ожидаемого **объёма изменений** за период существования snapshot.

Например:

```
origin = 2 TiB
ожидаемые изменения за backup window = 80 GiB

snapshot = 100 GiB
```

Это только пример расчёта; запас должен учитывать реальную write rate и worst-case сценарий.

---

# 11. Thin snapshots

Thin provisioning использует другой механизм совместного хранения блоков.

Thin snapshot первоначально разделяет блоки с origin:

```
             ┌── origin
physical ────┤
blocks       └── snapshot
```

При изменении данные начинают расходиться.

Thin snapshots особенно удобны для большого количества снимков: общие блоки могут разделяться между несколькими thin LV и snapshots. citeturn1search2

Проверка:

```
lvs -a -o lv_name,lv_attr,lv_size,pool_lv,origin,data_percent,metadata_percent
```

# 12. XFS и snapshots: UUID

Если snapshot содержит копию файловой системы, файловая система может иметь тот же UUID, что и origin.

Для XFS это особенно важно.

При работе со snapshot XFS может потребоваться:

```
mount -o ro,nouuid /dev/vg0/root_snapshot /mnt/backup_snap
```

Для writable-копии XFS после отдельного монтирования рекомендуется рассмотреть генерацию нового UUID:

```
xfs_admin -U generate /dev/vg0/root_snapshot
```

Нельзя универсально утверждать, что «Linux всегда блокирует второй mount с одинаковым UUID». Поведение зависит от конкретной файловой системы и параметров mount. Для XFS документация LVM отдельно описывает необходимость `nouuid` при монтировании snapshot и дальнейшую возможность смены UUID. citeturn1search2

# 13. Расширение LV

Пусть:

```
VG:
  Size = 200G
  Free = 50G

LV:
  Size = 100G
```

Расширить LV на 20G:

```
lvextend -L +20G /dev/vg_data/lv_data
```

или:

```
lvextend -l +100%FREE /dev/vg_data/lv_data
```

После увеличения LV **файловая система не обязательно увеличится автоматически**.

Есть два слоя:

```
LV      ← увеличили
  ↓
filesystem ← ещё нужно увеличить
```

Поэтому полезен:

```
lvextend -r -L +20G /dev/vg_data/lv_data
```

`-r`/`--resizefs` просит LVM одновременно изменить размер поддерживаемой файловой системы. Но это не отменяет необходимость понимать тип ФС и проверять результат.

---

# 14. Расширение ext4

Типичный вариант:

```
lvextend -L +20G /dev/vg_data/lv_data
resize2fs /dev/vg_data/lv_data
```

или:

```
lvextend -r -L +20G /dev/vg_data/lv_data
```

Проверка:

```
df -h /mountpoint
lvs
```

---

# 15. Расширение XFS

XFS расширяется в смонтированном состоянии.

После увеличения LV:

```
lvextend -L +20G /dev/vg_data/lv_data
```

увеличить XFS:

```
xfs_growfs /mountpoint
```

Важно: `xfs_growfs` получает **точку монтирования**, например:

```
xfs_growfs /var/lib/data
```

а не путь к LV.

---

# 16. Полный сценарий горячего расширения

Допустим:

```
/dev/sdb       → существующий PV
/dev/vg0/root  → LV
/              → XFS
```

Добавлен новый диск:

```
/dev/sdc
```

### Шаг 1. Проверить устройство

```
lsblk
blkid
```

### Шаг 2. Создать PV

```
pvcreate /dev/sdc
```

### Шаг 3. Добавить PV в VG

```
vgextend vg0 /dev/sdc
```

### Шаг 4. Проверить свободное пространство

```
vgs
pvs
```

### Шаг 5. Расширить LV и filesystem

```
lvextend -r -l +100%FREE /dev/vg0/root
```

### Шаг 6. Проверить

```
lvs
df -h /
```

Такой workflow соответствует разделению ответственности:

```
PV      → добавили физическое пространство
VG      → увеличили пул
LV      → увеличили блочное устройство
FS      → увеличили filesystem
```

# 17. Уменьшение LV — намного опаснее увеличения

Увеличение:

```
FS: 100G → 120G
LV: 100G → 120G
```

обычно безопаснее.

Уменьшение требует сначала освободить конец файловой системы:

```
filesystem
    ↓
уменьшение FS
    ↓
уменьшение LV
```

Нельзя делать:

```
lvreduce -L 20G /dev/vg0/data
```

если файловая система всё ещё рассчитана на 100G.

Иначе часть данных файловой системы окажется за пределами LV.

`lvreduce` прямо предупреждает: перед уменьшением LV файловая система должна быть уменьшена так, чтобы удаляемые экстенты больше не использовались. citeturn1search0

---

# 18. XFS нельзя уменьшить in-place

XFS не поддерживает уменьшение существующей файловой системы.

Поэтому для уменьшения XFS используется миграция:

```
старый XFS
   ↓
backup / xfsdump
   ↓
создание меньшего LV
   ↓
создание нового XFS
   ↓
xfsrestore
```

Например:

```
xfsdump -f /backup/data.dump /mnt/data
```

Создать новый LV:

```
lvcreate -L 20G -n data_new vg0
mkfs.xfs /dev/vg0/data_new
```

Восстановить:

```
xfsrestore -f /backup/data.dump /mnt/data_new
```

После проверки данных можно переключить mount point.

---

# 19. Уменьшение ext4

ext4 поддерживает уменьшение, но операция требует строгой последовательности.

Общий принцип:

```
unmount
   ↓
filesystem check
   ↓
уменьшение filesystem
   ↓
уменьшение LV
```

Пример с LVM wrapper:

```
umount /mnt/data
lvreduce --resizefs -L 20G /dev/vg0/data
```

`--resizefs` просит LVM изменить underlying filesystem вместе с LV, но перед production-операцией всё равно необходимо иметь проверенный backup и убедиться в типе файловой системы. citeturn1search0

---

# 20. pvmove — перенос данных между PV

`pvmove` позволяет перемещать экстенты между PV внутри VG.

Например:

```
VG vg_data

PV old:
████████████████

PV new:
░░░░░░░░░░░░░░░░
```

Запускаем:

```
pvmove /dev/sdb /dev/sdd
```

Получаем:

```
PV old:
░░░░░░░░░░░░░░░░

PV new:
████████████████
```

После этого старый PV можно подготовить к удалению:

```
vgreduce vg_data /dev/sdb
```

и затем:

```
pvremove /dev/sdb
```

Но перед удалением нужно убедиться, что на PV действительно не осталось необходимых экстентов:

```
pvs -o pv_name,pv_size,pv_free
```

`pvmove` предназначен именно для перемещения физических экстентов и используется, в частности, для освобождения PV перед его удалением. citeturn1search1

---

# 21. Замена диска в VG

Типичный сценарий:

```
/dev/sdb → старый диск
/dev/sdc → новый диск
```

### 1. Добавить новый PV

```
pvcreate /dev/sdc
vgextend vg_data /dev/sdc
```

### 2. Перенести экстенты

```
pvmove /dev/sdb /dev/sdc
```

### 3. Проверить

```
pvs
lvs
```

### 4. Удалить старый PV из VG

```
vgreduce vg_data /dev/sdb
```

### 5. Удалить LVM metadata с устройства

```
pvremove /dev/sdb
```

После этого уже можно физически извлекать или переиспользовать устройство.

---

# 22. Важное различие: pvmove не является backup

`pvmove` переносит данные **внутри той же системы хранения**.

Если:

```
old PV → new PV
```

это не означает:

```
old PV → независимая backup-копия
```

При ошибке администратора, повреждении VG или отказе инфраструктуры резервной копии может не оказаться.

---

# 23. LVM metadata

LVM хранит metadata, описывающие:

- PV;
- VG;
- LV;
- UUID;
- размеры;
- mapping;
- типы сегментов;
- snapshots;
- RAID/thin structures.

Для VG metadata LVM создаёт архивные копии конфигурации, обычно в:

```
/etc/lvm/archive/
```

и текущие backup-копии в:

```
/etc/lvm/backup/
```

Проверка:

```
ls -lh /etc/lvm/archive/
ls -lh /etc/lvm/backup/
```

Это **не backup пользовательских данных**. Там хранится описание конфигурации LVM, а не содержимое файловой системы.

---

# 24. Восстановление VG metadata

Сначала посмотреть доступные архивы:

```
vgcfgrestore --list vg0
```

Проверить нужный архив.

Затем восстановление структуры:

```
vgcfgrestore -f /etc/lvm/archive/vg0_00002-12345.vg vg0
```

Это операция высокого риска.

Перед `vgcfgrestore` нужно понимать:

```
какое состояние было корректным;
какие PV существуют;
какие UUID принадлежат системе;
какие изменения были сделаны после выбранного архива.
```

**Не следует механически выполнять `vgcfgrestore` при любой ошибке LVM.** Сначала нужно диагностировать, действительно ли повреждены metadata и соответствует ли выбранный архив фактическим PV.

---

# 25. Что делать при `unknown device`

Типичный сценарий:

```
lvs
pvs
vgs
```

показывают отсутствующее устройство.

Сначала определить физическую картину:

```
lsblk -f
blkid
pvs -a -o+devices
vgs
lvs -a -o+devices
```

Нужно установить:

1. действительно ли диск исчез;
2. изменилось ли имя устройства;
3. виден ли контроллер;
4. присутствует ли PV UUID;
5. какие LV используют отсутствующий PV;
6. есть ли backup metadata.

Не следует сразу запускать `vgreduce --removemissing`, особенно если отсутствующий PV содержит живые данные.

# 26. Имена устройств и UUID

Не следует строить критическую автоматизацию только на:

```

```

Имена `/dev/sdX` могут изменяться.

Для диагностики полезны:

```
lsblk -o NAME,KNAME,PATH,SIZE,FSTYPE,UUID,MOUNTPOINTS
```

Для production-автоматизации важнее устойчивые идентификаторы:

- UUID;
- WWID;
- `/dev/disk/by-id/...`;
- LVM UUID.

# 27. Device-mapper

LVM2 использует **device-mapper** ядра Linux.

Упрощённая модель:

```
/dev/vg0/data
       │
       ▼
device-mapper
       │
       ▼
mapping table
       │
       ▼
physical block devices
```

Device-mapper предоставляет механизмы отображения логических блоков на физические.

На нём построены не только LVM:

- linear mappings;
- snapshots;
- thin provisioning;
- cryptsetup/dm-crypt;
- некоторые RAID/cache-механизмы.

Поэтому:

```
LVM ≠ весь device-mapper
```

LVM — один из пользователей device-mapper.

---

# 28. Striped LV

Striping распределяет последовательные блоки между несколькими PV.

Пример:

```
PV1: A1 A3 A5 A7
PV2: A2 A4 A6 A8
PV3: A9 ...
```

Создание:

```
lvcreate \
  --type striped \
  --stripes 3 \
  --stripesize 64K \
  -L 300G \
  -n lv_fast \
  vg_data
```

Striping может увеличить параллелизм I/O, но **не предоставляет отказоустойчивость**.

Если один из PV, участвующих в striped LV, потерян, соответствующий LV может стать недоступным.

Поэтому:

```
striping = производительность / распределение I/O
RAID1/RAID5/RAID6 и т.п. = механизм избыточности
```

---

# 29. LVM RAID

LVM поддерживает типы LV, использующие device-mapper/MD-подобные механизмы для RAID.

Пример RAID1:

```
lvcreate \
  --type raid1 \
  -m 1 \
  -L 100G \
  -n lv_data \
  vg_data
```

Проверка:

```
lvs -a -o lv_name,lv_attr,lv_size,devices
```

В production нужно отдельно контролировать:

- состояние RAID;
- rebuild;
- degraded state;
- скорость восстановления;
- наличие свободного пространства;
- физическую независимость PV.

Два PV на одном физическом RAID-контроллере или одном физическом носителе не дают той отказоустойчивости, которую предполагает топология.

---

# 30. Filesystem и LV — независимые размеры

Очень важный принцип:

```
PV size
    ↓
VG free
    ↓
LV size
    ↓
filesystem size
    ↓
free space inside filesystem
```

Можно получить:

```
VG = 1 TiB
LV = 500 GiB
FS = 500 GiB
```

или:

```
VG = 1 TiB
LV = 500 GiB
FS = 450 GiB
```

или:

```
VG = 1 TiB
LV = 500 GiB
FS = 500 GiB
free inside FS = 50 GiB
```

Поэтому команды:

```
vgs
lvs
df -h
```

показывают **разные уровни** пространства.

---

# 31. `df` и `lvs` могут показывать разные цифры

Например:

```
lvs
```

может показывать:

```
LV      LSize
data    500G
```

а:

```
df -h /data
```

может показывать:

```
Size  Used  Avail
500G  420G   80G
```

`lvs` говорит о размере блочного устройства.

`df` говорит о состоянии файловой системы.

Если это thin LV, дополнительно появляется третий уровень:

```
virtual LV size
physical thin-pool usage
filesystem usage
```

# 33. TRIM / discard

Для SSD/NVMe важна передача discard-команд вниз по стеку.

Цепочка:

```
filesystem
    ↓
block layer
    ↓
device-mapper/LVM
    ↓
driver
    ↓
SSD/NVMe
```

LVM имеет настройки discard, однако их поведение зависит от конфигурации и конкретного устройства.

Проверить конфигурацию:

```
lvmconfig --type full devices
```

или:

```
lvmconfig --type current
```

Для filesystem можно использовать:

```
fstrim -av
```

Перед включением discard в production необходимо проверить:

- поддержку discard устройством;
- производительность;
- поведение RAID;
- поведение thin pool;
- настройки device-mapper;
- требования безопасности.

Для thin provisioning `fstrim` также может освобождать физические блоки thin pool, если discard не подавляется конфигурацией pool. citeturn1search2

# 43. Что делать после сбоя PV

Если PV пропал:

```
pvs
vgs
lvs
```

не следует сразу удалять отсутствующий PV.

Сначала:

```
lsblk
dmesg
journalctl -k
```

Проверить:

- диск виден или нет;
- есть ли I/O errors;
- проблема физического устройства или пути;
- multipath;
- HBA/SAS/SAN;
- изменилось ли имя устройства;
- существует ли PV с тем же UUID.

Только после определения причины выбирать:

```
ремонт/возврат диска
или
восстановление из backup
или
удаление missing PV
```

---

# 44. Почему `vgreduce --removemissing` опасен

Эта операция сообщает LVM:

```
считать отсутствующие PV окончательно потерянными
```

Если LV содержал экстенты на missing PV, соответствующие данные могут быть безвозвратно потеряны.

Поэтому команда не является универсальным способом исправления:

```
"unknown device"
```

Сначала нужно установить, что PV действительно потерян и что последствия понятны.

---

# 45. LVM metadata backup ≠ data backup

Файлы:

```
/etc/lvm/archive/*
/etc/lvm/backup/*
```

могут помочь восстановить:

```
PV/VG/LV metadata
```

но они не восстанавливают:

```
/home/*
/var/lib/postgresql/*
/var/lib/docker/*
```

То есть:

```
LVM metadata backup
    ≠
filesystem backup
```

Для данных нужны отдельные механизмы:

- restic;
- Borg;
- filesystem dump;
- snapshot + backup software;
- replication;
- object storage;
- tape;
- другой независимый storage.

---

# 46. Snapshot + backup

Практическая схема:

```
application
    │
    ▼
filesystem
    │
    ▼
LVM origin
    │
    ├──── snapshot
    │       │
    │       ▼
    │    read-only mount
    │       │
    │       ▼
    │      backup
    │
    └──── production
```

Но snapshot не гарантирует application consistency.

Например, для базы данных нужно учитывать:

- WAL;
- transaction consistency;
- flush;
- fsync;
- application-level backup;
- crash consistency.

Поэтому:

```
filesystem-consistent snapshot
    ≠
application-consistent backup
```

---

# 47. Важный вопрос: «можно ли snapshot запустить без остановки сервиса?»

Часто да, потому что LVM snapshot работает на уровне блокового устройства.

Но это не означает, что полученный снимок гарантированно является логически согласованным состоянием приложения.

Для базы данных предпочтительнее использовать механизм, обеспечивающий согласованность:

```
DB backup API
или
freeze/quiesce
или
правильный WAL-based backup
```

а snapshot использовать как часть инфраструктуры backup.

# 48. `lvconvert` и изменение типа LV

`lvconvert` используется для более сложных операций:

```
lvconvert --type raid1 ...
lvconvert --type thin ...
lvconvert --merge ...
```

Синтаксис и поддерживаемые типы зависят от версии LVM/device-mapper.

Перед изменением типа production LV необходимо:

```
lvs -a -o+devices
vgs
pvs
```

и иметь проверенный backup.

# 49. Atomicity и отказоустойчивость

LVM сам по себе не делает любую операцию атомарной на уровне приложения.

Например:

```
lvextend
```

может успешно изменить размер блочного устройства, но последующая операция filesystem может завершиться ошибкой.

Поэтому после изменения нужно проверять **оба слоя**:

```
lvs
df -hT
```

При автоматизации желательно:

1. сохранить исходное состояние;
2. выполнить операцию;
3. проверить exit code;
4. проверить размер LV;
5. проверить filesystem;
6. проверить mount;
7. записать результат в monitoring/audit.

# 50. Типовые ошибки

## Ошибка 1

```
Создал VG из двух дисков → получил RAID1
```

Нет.

Получен общий storage pool.

---

## Ошибка 2

```
lvextend увеличил LV → filesystem автоматически увеличился
```

Не всегда.

Используйте:

```
lvextend -r ...
```

или увеличьте filesystem отдельно.

---

## Ошибка 3

```
lvreduce уменьшит filesystem
```

Нет.

Уменьшать filesystem нужно до LV либо использовать проверенный `--resizefs`.

---

## Ошибка 4

```
snapshot = backup
```

Нет.

Snapshot находится в том же storage domain и имеет ограниченное время жизни/ёмкость.

---

## Ошибка 5

```
pvmove = backup
```

Нет.

Это миграция экстентов.

---

## Ошибка 6

```
/dev/sdb всегда будет тем же диском
```

Нет.

Используйте UUID/WWID/by-id и проверяйте topology.

---

## Ошибка 7

```
VG свободен → thin LV можно бесконечно расширять
```

Не обязательно.

Thin LV может иметь virtual size больше physical capacity thin pool, но физические блоки всё равно должны откуда-то выделяться.

# 55. Главный принцип диагностики

Не спрашивайте:

> «Почему Linux говорит, что места нет?»

Сначала задайте вопрос:

> **На каком именно уровне закончилась ёмкость?**

Проверяйте сверху вниз:

```
df
 ↓
filesystem
 ↓
LV
 ↓
VG
 ↓
PV
 ↓
physical storage
```

Для thin provisioning добавляется:

```
thin LV virtual size
        ↓
thin pool data
        ↓
thin pool metadata
```

Это позволяет отличать принципиально разные ситуации:

```
Filesystem full
    ≠
LV full
    ≠
VG full
    ≠
thin pool full
    ≠
physical disk full
```

# 56. Главное, что нужно запомнить

1. **PV** — физическое блочное пространство, подготовленное для LVM.
2. **PE** — единица физического размещения внутри PV.
3. **VG** — пул PE от одного или нескольких PV.
4. **LV** — логическое блочное устройство, выделенное из VG.
5. Несколько PV в одной VG **не означают RAID**.
6. `lvextend` увеличивает LV, а filesystem нужно расширять отдельно или через `-r`.
7. Уменьшение опаснее увеличения: сначала filesystem, потом LV.
8. XFS не умеет in-place shrink.
9. `pvmove` позволяет переносить экстенты между PV без обычного размонтирования файловых систем, но не является backup.
10. Snapshot — точка во времени на уровне блока, а не независимая резервная копия.
11. Классический COW snapshot может стать непригодным при исчерпании пространства для изменившихся блоков.
12. Thin provisioning позволяет виртуально выделить больше пространства, чем физически имеется, но создаёт риск переполнения thin pool.
13. LVM metadata backup позволяет восстанавливать структуру LVM, но не пользовательские данные.
14. `df`, `lvs`, `vgs` и `pvs` измеряют разные уровни storage stack.
15. В production нужно мониторить не только filesystem, но и VG, PV, snapshots, thin pool и RAID-состояние.
