
# Logical Volume Manager (LVM2) — архитектура, управление, снимки и восстановление

> **LVM2 (Logical Volume Manager)** — подсистема управления блочными устройствами в Linux, предоставляющая слой виртуализации и логической адресации между физическими дисками и файловой системой. Она позволяет объединять физические устройства в единые пулы хранения, нарезать их на логические тома, динамически изменять их размеры, перемещать данные «на лету», создавать снимки состояний (snapshots), использовать тонкое выделение ресурсов (thin provisioning) и отказоустойчивые конфигурации (RAID/cache) на базе `device-mapper`.
> 
> **Критически важно:** LVM не является файловой системой и не заменяет аппаратный/программный RAID или резервное копирование. LVM управляет отображением блочных адресов; файловая система организует файлы и каталоги; ядро и `device-mapper` транслируют I/O-запросы.

### Трансляция адресов в LVM

Схема адресации данных при выполнении операций чтения/записи:

```
Filesystem (Логический блок ФС / INode)
   │
   ▼
Logical Block Address (LBA логического тома LV)
   │
   ▼
LVM Extent Mapping (Трансляция LE в PE средствами Device-Mapper)
   │
   ▼
Physical Extent (PE на конкретном Physical Volume)
   │
   ▼
Physical Block Device (Адрес физического сектора на диске)
```

## Базовые сущности и архитектура LVM

Иерархия сущностей LVM выражается классической цепочкой:

$$\text{PV} \longrightarrow \text{VG} \longrightarrow \text{LV} \longrightarrow \text{Filesystem}$$

```
Physical Volume (PV)  ──►  Volume Group (VG)  ──►  Logical Volume (LV)
  (Физический диск)           (Общий пул)            (Логический диск)
```

### Physical Volume (PV)

**Physical Volume** — блочное устройство, инициализированное для использования подсистемой LVM. В качестве PV могут выступать:

- Цельные физические накопители (`/dev/sdb`, `/dev/nvme0n1`);
- Отдельные разделы диска (`/dev/sdb1`, `/dev/nvme0n1p3`);
- Составные блочные устройства (программный RAID `mdadm`, зашифрованные LUKS-контейнеры `/dev/mapper/crypt_disk`).

#### Структура PV и выравнивание данных (Data Alignment)

Инициализация устройства через `pvcreate` **не нарезает экстенты от 0-го сектора**. Структура PV включает:

1. **LVM Label:** Записывается в один из первых 4 секторов (со смещением 512 байт). Содержит UUID устройства и указатели на область метаданных.
2. **VG Metadata Area:** Выделенная область для хранения структуры группы томов (по умолчанию хранит до нескольких копий метаданных).
3. **Data Area (Physical Extents):** Первичный физический экстент (PE 0) размещается с техническим смещением (по умолчанию **1 MiB**). Это выравнивание необходимо для оптимальной работы секторов 4KiB (Advanced Format) и блоков стирания SSD (Erase Block Boundaries).
### Physical Extent (PE) и Logical Extent (LE)

- **PE (Physical Extent):** Неделимый минимальный блок адресации физической памяти в LVM. Размер PE задается при создании VG (по умолчанию часто 4 MiB, но может составлять от 1 MiB до нескольких GiB).
- **LE (Logical Extent):** Единица адресации логического тома (LV). В базовых конфигурациях 1 LE соответствует 1 PE.

```
LV (Logical Extents):    [ LE 0 ]  [ LE 1 ]  [ LE 2 ]  [ LE 3 ]
                            │         │         │         │
Device-Mapper Mapping:      ▼         ▼         ▼         ▼
PV (Physical Extents):   [ PE 42 ] [ PE 43 ] [ PE 900 ] [ PE 901 ]
```

## Группа томов (Volume Group, VG)

**Volume Group** — единый виртуальный пул хранения, объединяющий емкость одного или нескольких PV.

```
  /dev/sdb (PV) ──┐
                  ├──► Volume Group (vg_data) ──┬──► lv_root (LV)
  /dev/sdc (PV) ──┘                             ├──► lv_db   (LV)
                                                └──► lv_swap (LV)
```

VG выступает административной границей выделения дискового пространства. Свободное место внутри VG измеряется исключительно в количестве незанятых экстентов (Free PEs).

## Логические тома (Logical Volume, LV)

**Logical Volume** — блочное устройство, нарезаемое из экстентов VG, предоставляемое операционной системе для создания файловых систем или использования в качестве raw-устройств (например, под swap или базы данных).

После активации доступ к LV осуществляется через два символических пути в системе:

- `/dev/vg_name/lv_name` (традиционный симлинк);
- `/dev/mapper/vg_name-lv_name` (прямое имя устройства в `device-mapper`).

## Типы размещений: Linear и Striped LV

### Linear LV (Линейный том)

По умолчанию LVM выделяет экстенты последовательно. При заполнении одного PV создание тома продолжается на следующем.

```
PV 1 (sdb): [ PE 0 ...... PE 999 ] ──┐
                                     ├──► Linear LV (LE 0 ...... LE 1499)
PV 2 (sdc): [ PE 0 .. PE 499 ] ──────┘
```

> **Важно:** Linear LV **не гарантирует** отказоустойчивость. Выход из строя любого PV, на котором расположены экстенты данного LV, приводит к сбою файловой системы и частичной/полной потере данных.

### Striped LV (Том со чередованием)

Данные записываются параллельно на несколько PV фиктивным блоком (stripe size).

```
Stripe Block 1 ──► PV 1 (sdb)
Stripe Block 2 ──► PV 2 (sdc)
Stripe Block 3 ──► PV 3 (sdd)
```

- **Преимущество:** Увеличение пропускной способности I/O на последовательных операциях чтения/записи.
- **Недостаток:** Надежность снижается пропорционально количеству дисков (отказ одного PV разрушает весь Striped LV).

## Разграничение понятий: LVM и RAID

Добавление множества дисков в одну VG **не является аналогом RAID-1 или RAID-5**.

|**Критерий**|**Обычный LVM (Linear)**|**LVM RAID (--type raid1/5/6)**|**Hardware/mdadm RAID**|
|---|---|---|---|
|**Назначение**|Объединение емкости дисков|Отказоустойчивость и избыточность|Избыточность на уровне дисков|
|**Отказ одного PV**|Потеря данных тома|Сохранность данных (при $n-1$)|Сохранность данных|
|**Производительность**|Равна одиночному диску|Зависит от уровня RAID|Высокая (особенно Hardware)|

LVM поддерживает создание избыточных томов через встроенный модуль `dm-raid` (`lvcreate --type raid1 -m 1 ...`), однако требует физического наличия независимых дисков в составе VG.

## Тонкое выделение ресурсов (Thin Provisioning)

Классический LV аллоцирует 100% физических экстентов в момент создания. **Thin Provisioning** разделяет понятия виртуального и физического размера.

```
VG vg_data (100 GiB Physical)
 └── Thin Pool (100 GiB Physical Data + Meta)
      ├── Thin LV A (Virtual: 500 GiB, Allocated: 10 GiB)
      ├── Thin LV B (Virtual: 300 GiB, Allocated: 25 GiB)
      └── Thin LV C (Virtual: 200 GiB, Allocated: 5 GiB)
```

### Архитектура Thin Pool

Thin Pool состоит из двух раздельных томов:

1. **Data LV:** Блоки данных, выделяемые по мере фактической записи приложениями.
2. **Metadata LV:** Таблица адресации, отслеживающая, какие виртуальные блоки принадлежат конкретным томам и снимкам.

> **Критическая опасность (Overcommit):** Если суммарная фактическая запись на Thin тома превысит физическую емкость Thin Pool, тома перейдут в режим `read-only` или начнут отклонять I/O вызовы (в зависимости от настроек `thin_pool_autoextend_threshold`), что может привести к сбою баз данных и повреждению ФС.

## Механизм снимков (Snapshots)

Снимок LVM — это мгновенное логическое сохранение состояния блока данных на определенный момент времени.

### Классический Copy-on-Write (COW) Snapshot

Работает поверх обычных (Linear) томов.

```
[ Исходное состояние ]
Origin LV:    [ Block A ] [ Block B ] [ Block C ]
Snapshot:     (Пуст, ссылается на Origin)

[ Изменение блока C -> C' ]
1. Старый Block C копируется в Snapshot Storage.
2. New Block C' записывается в Origin LV.

Origin LV:    [ Block A ] [ Block B ] [ Block C' ]
Snapshot:     [ Block C ] (Остальные блоки читаются из Origin)
```

> **Предупреждение:** Если объем изменений на Origin переполнит выделенный размер COW-снапшота, snapshot переходит в состояние `Invalid` и становится непригодным для использования.

### Thin Snapshots

В тонких томах (Thin LV) снимки не используют механизм COW для копирования блоков. Вместо этого обновляется структура метаданных: создается новый указатель на существующие блоки данных (Redirect-on-Write). Это позволяет создавать тысячи снимков мгновенно и без просадки производительности I/O.

### Специфика XFS при монтировании Snapshots

Файловая система XFS запрещает монтирование двух томов с одинаковым UUID в одной ОС. Попытка смонтировать snapshot XFS завершится ошибкой.

**Решение:**

1. Монтирование в режиме чтения без проверки UUID:

```sh
mount -o ro,nouuid /dev/vg_data/lv_snap /mnt/snapshot
```

2. Для создания независимой Writable-копии следует сгенерировать новый UUID:

```sh
xfs_admin -U generate /dev/vg_data/lv_snap
```

## Управление размером: расширение и уменьшение томов

Управление памятью требует осознания разделения слоев:

$$\text{Уровень LVM (Block Device)} \quad \neq \quad \text{Уровень ФС (Filesystem)}$$

```
Увеличение:   Увеличить LV  ──►  Увеличить Filesystem
Уменьшение:   Уменьшить Filesystem  ──►  Уменьшить LV
```

### Горячее расширение (Online Expansion)

Расширение томов производится «на лету» без остановки сервисов.

Пример безопасно совмещенного расширения LV и ФС одной командой:

```sh
lvextend -r -L +20G /dev/vg_data/lv_data
```

Флаг `-r` (`--resizefs`) автоматически вызывает соответствующую утилиту расширения (`resize2fs` для ext4 или `xfs_growfs` для XFS).

### Опасности уменьшения (Shrink)

> **Внимание:** Ошибки при сжатии тома приводят к **необратимому разрушению файловой системы**.

1. **Файловая система XFS НЕ поддерживает уменьшение размера (in-place shrink)**. Единственный путь — создание нового меньшего LV, форматирование и миграция данных (`xfsdump`/`xfsrestore` или `rsync`).
2. Для **ext4** сжатие возможно **только после отмонтирования** и выполнения проверки `e2fsck`.

```sh
# Алгоритм сжатия ext4:
umount /dev/vg_data/lv_data
e2fsck -f /dev/vg_data/lv_data
resize2fs /dev/vg_data/lv_data 10G
lvreduce -L 10G /dev/vg_data/lv_data
mount /dev/vg_data/lv_data /mnt/data
```

## Бесшовный перенос данных (`pvmove`) и замена дисков

Команда `pvmove` переносит физические экстенты (PE) с одного PV на другой в режиме реального времени, без размонтирования ФС и остановки приложений.

```
Исходный PV (/dev/sdb): [ PE0 ][ PE1 ][ PE2 ] ──┐
                                                ├──► pvmove
Целевой PV  (/dev/sdc): [ ... Свободно ... ]  ──┘
```

### Сценарий горячей замены диска

```sh
# 1. Подготовка нового диска и добавление в VG
pvcreate /dev/sdc
vgextend vg_data /dev/sdc

# 2. Миграция данных со старого диска на новый
pvmove /dev/sdb /dev/sdc

# 3. Извлечение старого диска из VG
vgreduce vg_data /dev/sdb
pvremove /dev/sdb
```

> **Важно:** `pvmove` — это операция перемещения физических блоков в рамках одного пула хранилища, она **не является резервным копированием**.

## Метаданные LVM и аварийное восстановление

LVM сохраняет полную схему конфигурации (заголовки PV, структуру VG, карты LE-to-PE) в текстовом формате ASCII в зарезервированной области каждого PV, а также дублирует её в файловой системе ОС:

- Текстовые бэкапы: `/etc/lvm/backup/`
- Архивы прошлых изменений: `/etc/lvm/archive/`
### Восстановление структуры при повреждении метаданных

Если заголовки диска были затерты, их можно восстановить из текстового архива:

```sh
# 1. Просмотр доступных точек восстановления
vgcfgrestore --list vg_data

# 2. Восстановление структуры VG из конкретного архива
vgcfgrestore -f /etc/lvm/archive/vg_data_00001-12345.vg vg_data
```

> **Критическое предупреждение:** Команда `vgreduce --removemissing` удаляет из структуры VG информацию обо всех отсутствующих PV. Если на удаленном PV находились данные незащищенного LV, этот том будет окончательно поврежден. **Не применяйте данную команду без глубокой диагностики причин сбоя диска!**

## Взаимодействие с Device-Mapper и SSD (TRIM/Discard)

Подсистема LVM функционирует поверх ядерного драйвера `device-mapper`. Для корректного освобождения неиспользуемых блоков на SSD/NVMe накопителях требуется прохождение команд TRIM вниз по всему стеку.

```
Filesystem (fstrim / mount -o discard)
   │
   ▼
LVM Thin Pool / Device-Mapper (issue_discards = 1 в lvm.conf)
   │
   ▼
Physical NVMe/SSD Driver
```

Проверка и принудительный запуск выравнивания TRIM:

```sh
fstrim -av
```

## Мониторинг, диагностика и автоматизация

### Структурированный вывод для автоматизации (JSON)

Для использования в скриптах автоматизации вместо разбора текстовых полей через `awk`/`sed` следует применять встроенный формат JSON:

```sh
vgs --reportformat json | jq .
lvs --reportformat json | jq .
```

### Метрики для систем мониторинга (Prometheus / Zabbix)

Метрики, подлежащие обязательному контролю:

1. `VG Free Space (%)` — запасы пространства для расширения томов;
2. `Thin Pool Data (%)` — процент заполнения физических блоков Thin-пула;
3. `Thin Pool Metadata (%)` — процент заполнения таблицы метаданных Thin-пула;
4. `COW Snapshot Utilization (%)` — заполнение классических снимков (риск `Invalid`).

## Справочник команд и чек-лист безопасности

### Сводная таблица ключевых команд

|**Уровень**|**Просмотр**|**Создание**|**Расширение / Изменение**|**Удаление**|
|---|---|---|---|---|
|**PV**|`pvs`, `pvdisplay`|`pvcreate /dev/sdX`|`pvresize`, `pvmove`|`pvremove`|
|**VG**|`vgs`, `vgdisplay`|`vgcreate vg_name /dev/sdX`|`vgextend`, `vgreduce`|`vgremove`|
|**LV**|`lvs`, `lvdisplay`|`lvcreate -L 10G -n lv_name vg_name`|`lvextend`, `lvreduce`, `lvconvert`|`lvremove`|

### Чек-лист безопасности перед деструктивными операциями

- [ ] **Резервная копия:** Выполнено ли реальное резервное копирование пользовательских данных (не snapshot и не метаданные LVM)?
- [ ] **Проверка типа ФС:** Поддерживает ли файловая система `online shrink` (помните: XFS **не поддерживает** уменьшение)?
- [ ] **Проверка отмонтирования:** Отмонтирована ли ФС перед выполнением операций сжатия (`umount`)?
- [ ] **Анализ зависимостей:** Убедились ли вы с помощью `lvs -a -o+devices`, на каких именно физических дисках размещены экстенты удаляемого тома?
