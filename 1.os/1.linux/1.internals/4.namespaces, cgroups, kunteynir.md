# Linux Namespaces, cgroups и контейнеризация

> **Статус:** систематизированная техническая документация  
>  
   **Основные темы:** namespaces, cgroups v1/v2, capabilities, container runtime, `nsenter`, resource limits, Kubernetes mapping, диагностика.
>
> **Принцип точности:** конкретные значения defaults, поведение runtime и расположение cgroup paths зависят от kernel, distribution, runtime и конфигурации. Примеры ниже предназначены для понимания механизма и диагностики, а не являются универсальным production baseline.

---

## 1. Что такое контейнер в Linux

Контейнер — это не отдельная виртуальная машина и не отдельный экземпляр ядра.

В классической Linux-контейнерной модели один kernel обслуживает:

```text
                    Linux kernel
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
     process A        process B        process C
        │                │                │
   namespace set    namespace set    namespace set
        │                │                │
     cgroups          cgroups          cgroups
````

Контейнеризация строится не на одном механизме, а на совокупности kernel primitives:

- **namespaces** — виртуализируют/изолируют видимость определённых kernel resources;
- **cgroups** — организуют процессы и управляют распределением/ограничением ресурсов;
- **capabilities** — разделяют традиционные полномочия root на отдельные привилегии;
- **LSM** — например, SELinux/AppArmor, добавляют security policy;
- **filesystem isolation** — mount namespaces, root filesystem, bind mounts, overlay filesystems и т. п.;
- **seccomp** — ограничивает доступные системные вызовы;
- **networking primitives** — `veth`, bridge, routing, nftables и т. д.

Поэтому утверждение:

> «контейнер = namespaces + cgroups»

полезно как первое приближение, но технически неполно.

# 2. Namespaces

Linux namespace создаёт изолированное представление определённого системного ресурса. Процессы внутри namespace видят namespace-specific view, тогда как процессы в другом namespace могут видеть другой view. Именно namespaces являются одним из фундаментальных механизмов реализации контейнеров. citeturn0search2turn0search3

Проверить namespace процесса:

```
ls -l /proc/<PID>/ns/
```

Типичный набор:

```
cgroup
ipc
mnt
net
pid
pid_for_children
time
time_for_children
user
uts
```

Каждая запись указывает на namespace inode, например:

```
net -> net:[4026532001]
```

Два процесса принадлежат одному конкретному namespace, если соответствующие `/proc/<PID>/ns/...` указывают на один namespace object.

---

# 3. Типы Linux namespaces

Современный Linux предоставляет следующие основные типы:

|Namespace|Флаг|Что виртуализирует|
|---|---|---|
|PID|`CLONE_NEWPID`|process ID namespace|
|NET|`CLONE_NEWNET`|network stack/resources|
|MNT|`CLONE_NEWNS`|mount namespace|
|IPC|`CLONE_NEWIPC`|System V IPC, POSIX message queues|
|UTS|`CLONE_NEWUTS`|hostname/domain name|
|USER|`CLONE_NEWUSER`|UID/GID mappings и связанные privilege semantics|
|CGROUP|`CLONE_NEWCGROUP`|cgroup view|
|TIME|`CLONE_NEWTIME`|offsets для monotonic/boottime clocks|

Сводное описание namespace API приведено в `namespaces(7)`. citeturn0search2

# 4. PID namespace

PID namespace виртуализирует process IDs.

Например:

```
                    host PID namespace
                           │
                         PID 42000
                           │
                  ┌────────┴────────┐
                  │ container       │
                  │ PID namespace   │
                  │                  │
                  │ PID 1            │
                  │ PID 2            │
                  │ PID 3            │
                  └──────────────────┘
```

Один и тот же task может иметь разные PID в разных PID namespaces.

```
container view: PID 1
host view:      PID 42000
```

## 4.1. PID 1

Первый процесс нового PID namespace получает PID `1` в этом namespace.

Это имеет особую семантику:

- он является ancestor для процессов своего namespace;
- kernel применяет к нему специальную обработку orphaned processes;
- корректное завершение и обработка сигналов внутри контейнера зависят от поведения этого процесса.

Следовательно:

> контейнерный PID 1 — это не обязательно `systemd`.

Им может быть:

```
nginx
python
java
bash
tini
```

и т. д.

---

# 5. PID namespaces вложены

PID namespaces образуют иерархию.

Процесс в дочернем PID namespace получает PID также в ancestor namespaces.

```
             host namespace
                  │
              PID 42000
                  │
          container namespace
                  │
               PID 1
```

Поэтому host может видеть процесс контейнера, а процесс внутри контейнера не обязан видеть процессы host namespace.

---

# 6. Создание PID namespace

Основные interfaces:

```
clone(CLONE_NEWPID, ...)
unshare(CLONE_NEWPID)
```

и:

```
unshare --pid --fork --mount-proc bash
```

После создания PID namespace важно помнить, что `unshare(CLONE_NEWPID)` влияет на дочерний процесс: вызывающий процесс не «переписывает» собственный PID в новый namespace.

Именно поэтому в практических командах часто используется:

```
unshare --pid --fork ...
```

# 7. Network namespace

Network namespace виртуализирует networking resources, включая:

- network devices;
- IPv4/IPv6 addresses;
- routing tables;
- firewall/netfilter state в соответствующем контексте;
- sockets;
- network-related `/proc` views;
- port namespace.

Простейшая модель:

```
host network namespace
        │
        ├── eth0
        ├── lo
        └── routes

container network namespace
        │
        ├── eth0
        ├── lo
        └── routes
```

Контейнерный `eth0` часто является одним концом `veth` pair.

---

# 8. `veth`

`veth` — виртуальная Ethernet pair:

```
namespace A                    namespace B

    eth0                         eth0
      │                           │
      └──────── veth pair ────────┘
```

Один конец может находиться в container namespace, другой — в host namespace или bridge topology.

Проверка:

```
ip link
```

Для namespace:

```
ip netns list
ip netns exec <name> ip addr
```

---

# 9. Mount namespace

Mount namespace виртуализирует набор mount points, который видит процесс.

Это позволяет двум процессам иметь разные views:

```
host namespace:

/
├── etc
├── var
├── home
└── ...

container namespace:

/
├── etc
├── app
├── proc
└── ...
```

Важно:

> mount namespace не создаёт автоматически отдельную файловую систему.

Он создаёт отдельное представление mount topology. Реальная изоляция root filesystem требует соответствующей подготовки rootfs, mounts, permissions и других механизмов.

---

# 10. `chroot` и mount namespace — не одно и то же

`chroot()` изменяет root directory для процесса и его descendants, но сам по себе не является полноценным контейнерным механизмом.

`chroot`:

```
изменяет filesystem root для lookup
```

Mount namespace:

```
изолирует mount topology
```

Современная контейнеризация обычно использует mount namespaces и специально подготовленный root filesystem.

---

# 11. IPC namespace

IPC namespace изолирует соответствующие IPC resources, например:

- System V shared memory;
- System V semaphores;
- System V message queues;
- POSIX message queues.

Это позволяет двум контейнерам иметь независимые IPC namespaces.

---

# 12. UTS namespace

UTS namespace позволяет изолировать:

```
hostname
domainname
```

Например:

```
hostname container-a
```

может изменить hostname внутри UTS namespace, не изменяя hostname, наблюдаемый процессами другого UTS namespace.

---

# 13. User namespace

User namespace виртуализирует UID/GID mapping и является важной частью rootless/container security model.

Например:

```
inside container:

UID 0
  │
  ▼
UID 100000 on host
```

Это позволяет процессу иметь UID 0 внутри namespace, не являясь UID 0 в host user namespace.

Но важно различать:

```
UID 0
```

и:

```
full host root privileges
```

Это не одно и то же.

Capabilities и доступ к host resources зависят от user namespace, capabilities, LSM, mounts, device access и других механизмов.

---

# 14. UID/GID mapping

Проверка:

```
cat /proc/<PID>/uid_map
cat /proc/<PID>/gid_map
```

Пример концептуального mapping:

```
container UID     host UID
-----------       --------
0                 100000
1                 100001
2                 100002
...
```

В rootless container это один из ключевых механизмов, позволяющих использовать UID 0 внутри контейнера без UID 0 на host.

---

# 15. Cgroup namespace

Cgroup namespace не является механизмом ограничения ресурсов.

Он виртуализирует **view** процесса на cgroup hierarchy, в частности представление `/proc/<pid>/cgroup` и cgroup mounts. Kernel documentation прямо описывает cgroup namespace как механизм виртуализации cgroup view. citeturn0search0turn0search1

Следовательно:

```
cgroup namespace
    =
visibility/isolation of cgroup view

cgroup controllers
    =
resource control/accounting
```

Это разные понятия.

---

# 16. Time namespace

Time namespace позволяет задавать offsets для определённых clocks, прежде всего:

- `CLOCK_MONOTONIC`;
- `CLOCK_BOOTTIME`.

Это позволяет контейнеру видеть другой relative time/uptime view, не изменяя физические часы host.

Не следует интерпретировать time namespace как:

> «полностью независимые часы».

Например, realtime clock semantics не превращаются автоматически в независимые wall-clock hardware clocks.

---

# 17. Namespace API

Основные системные вызовы:

```
clone()
unshare()
setns()
```

### `clone()`

Создаёт child и может одновременно создать namespace:

```
clone(CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWUSER, ...)
```

### `unshare()`

Отделяет calling process от части текущего namespace context:

```
unshare --mount ...
unshare --net ...
unshare --pid --fork ...
```

### `setns()`

Позволяет присоединить calling process/thread к существующему namespace:

```
nsenter ...
```

---

# 18. Как kernel хранит namespace identity

Проверка:

```
readlink /proc/$$/ns/net
```

например:

```
net:[4026532001]
```

Число — inode-like identifier namespace object.

Сравнение:

```
readlink /proc/1234/ns/net
readlink /proc/5678/ns/net
```

Если идентификаторы одинаковы, процессы находятся в одном network namespace.

# 19. `nsenter`

`nsenter` из `util-linux` позволяет выполнить программу в namespace существующего процесса.

Типичный workflow:

```
host
 │
 ├── найти PID container init
 │
 └── nsenter
       │
       ├── mount namespace
       ├── UTS namespace
       ├── network namespace
       ├── PID namespace
       └── ...
```

Проверить PID контейнера:

```
docker inspect --format '{{.State.Pid}}' <container>
```

После этого:

```
nsenter -t <PID> -m -u -n -p -i
```

Опции следует выбирать по задаче.

Не нужно автоматически входить во все namespaces, если для диагностики требуется только network namespace.

---

# 20. Почему `nsenter` полезен для distroless

Контейнер может не содержать:

```
bash
ip
ss
tcpdump
strace
ps
```

Это особенно характерно для минимальных/distroless images.

Но host может иметь эти инструменты.

Тогда:

```
nsenter -t <container-init-pid> -n ip addr
```

позволяет использовать host binary, но network namespace контейнера.

Для процесса:

```
nsenter -t <PID> -p -m ps aux
```

можно получить process/filesystem view, соответствующий целевому namespace.

# 21. Cgroups

cgroup — механизм ядра Linux для иерархической организации процессов и управления/распределения ресурсов через controllers.

В cgroup hierarchy:

```
/
├── system.slice
│   ├── service-a
│   └── service-b
│
└── workload.slice
    ├── container-a
    └── container-b
```

Каждый process/task находится в cgroup hierarchy согласно правилам конкретной версии cgroup API.

Cgroup v2 является современной unified interface; authoritative kernel documentation описывает её hierarchy, controllers и semantics. citeturn1search3

---

# 22. Cgroups v1 vs v2

## v1

В cgroup v1 контроллеры могли использовать отдельные hierarchies.

Концептуально:

```
memory hierarchy
    ├── A
    └── B

cpu hierarchy
    ├── C
    └── D
```

Один task мог одновременно находиться в разных groups разных hierarchies.

## v2

В cgroup v2 используется unified hierarchy:

```
/
├── service-a
├── service-b
└── container-a
```

Controllers включаются в соответствующих subtree.

Kernel documentation подчёркивает unified hierarchy и иерархическое действие controllers. citeturn1search3

# 25. Controllers

Доступные controllers:

```
cat /sys/fs/cgroup/cgroup.controllers
```

Например:

```
cpuset cpu io memory hugetlb pids
```

Но наличие controller в `cgroup.controllers` не означает, что он уже enabled для children.

Для включения controllers используется:

```
echo "+cpu +memory +io +pids" > /sys/fs/cgroup/cgroup.subtree_control
```

Kernel documentation подчёркивает, что controller должен быть доступен родительскому cgroup и включается через `cgroup.subtree_control`. citeturn1search0

---

# 26. CPU: `cpu.weight`

`cpu.weight` задаёт относительный вес CPU distribution.

Диапазон в cgroup v2:

```
1..10000
```

default:

```
100
```

При конкуренции за CPU активные children получают CPU пропорционально весам. Это **не означает**, что `cpu.weight=100` резервирует фиксированную долю CPU независимо от нагрузки.

Kernel documentation описывает weight model как work-conserving distribution: если sibling не использует доступный ресурс, другой может использовать его. citeturn1search3

---

# 27. CPU: `cpu.max`

`cpu.max` имеет формат:

```
MAX PERIOD
```

или:

```
QUOTA PERIOD
```

Например:

```
echo "200000 100000" > cpu.max
```

означает:

```
200 ms CPU time
на 100 ms scheduling period
```

То есть cgroup получает aggregate CPU bandwidth, эквивалентный двум CPU при длительной загрузке.

Важно:

> это quota группы, а не «закрепление двух физических ядер».

---

# 28. CPU throttling

Проверка:

```
cat cpu.stat
```

Типичные поля:

```
usage_usec
user_usec
system_usec
nr_periods
nr_throttled
throttled_usec
```

Особенно важны:

```
nr_throttled
throttled_usec
```

Они позволяют отличать:

```
CPU просто загружен
```

от:

```
cgroup достиг CPU bandwidth limit
```

Нельзя использовать универсальное правило вроде:

> «если throttled > 10%, обязательно увеличить limit».

Это уже workload-specific engineering decision. Сначала нужно сопоставить throttling с latency, throughput и CPU demand.

---

# 29. Почему CPU limit может неожиданно throttling'ить приложение

Предположим:

```
cpu.max = 100000 100000
```

Это примерно один CPU aggregate.

Если многопоточное приложение одновременно использует несколько CPU:

```
thread 1 ──┐
thread 2 ──┤
thread 3 ──┼──► общий cgroup CPU quota
thread 4 ──┘
```

квота расходуется суммарно.

Поэтому:

```
8 threads × 12.5 ms
≈
100 ms CPU
```

могут исчерпать quota очень быстро.

Это может создавать latency spikes даже при умеренном среднем CPU utilization.

# 30. Memory controller

Основные интерфейсы:

```
memory.max
memory.high
memory.low
memory.min
memory.current
memory.events
memory.stat
```

### `memory.max`

Hard limit.

При достижении limit kernel пытается reclaim memory; если использование не удаётся удержать ниже limit, может возникнуть cgroup OOM condition.

### `memory.high`

Throttle/reclaim boundary, а не обычный hard kill limit.

Превышение `memory.high` не означает автоматический OOM kill.

### `memory.min` / `memory.low`

Protection semantics для reclaim.

Это важно: `memory.low` и `memory.min` — не аналоги `memory.max`.

---

# 31. Cgroup OOM

Важно различать:

```
system-wide OOM
```

и:

```
cgroup memory OOM
```

Cgroup memory limit может привести к OOM event внутри ограниченной cgroup без необходимости немедленно завершать произвольные процессы вне этой группы.

Проверка:

```
cat memory.events
```

Полезные counters включают:

```
high
max
oom
oom_kill
oom_group_kill
```

Точное наличие полей зависит от kernel version.

---

# 32. Exit code 137

Часто:

```
exit code 137
```

означает:

```
128 + 9
= SIGKILL
```

Но:

> exit code 137 сам по себе не доказывает, что причиной был cgroup OOM.

Причиной SIGKILL может быть и другой механизм.

Для подтверждения OOM нужно смотреть:

```
memory.events
kernel logs
runtime events
orchestrator events
application logs
```

---

# 33. Page cache и cgroup memory

Memory controller учитывает не только anonymous memory.

В cgroup memory accounting могут участвовать:

- anonymous memory;
- page cache;
- kernel memory structures;
- socket memory;
- другие виды memory usage.

Kernel documentation explicitly lists page cache, anonymous memory, dentries/inodes и TCP socket buffers среди tracked memory usages. citeturn1search4

Поэтому:

```
container memory
```

не следует интерпретировать как:

```
RSS всех процессов
```

```
cat memory.current
```

Для анализа нужно сопоставлять:

```
memory.current

memory.events
memory.stat
process RSS
page cache
```

# 35. `memory.stat`

```
cat memory.stat
```

позволяет разложить memory usage на категории.

Это значительно полезнее, чем смотреть только:

```
free -m
```

на host.

# 36. PIDs controller

`pids.max` ограничивает количество tasks, которые могут существовать в cgroup.

Проверка:

```
cat pids.current
cat pids.max
```

Если достигнут limit, создание новых tasks через `fork()`/`clone()` может завершиться ошибкой.

Это отдельная защита от:

```
fork bomb
thread explosion
```

Kernel documentation указывает, что PID controller считает TIDs/tasks, а не только традиционные process IDs. citeturn1search4

# 37. I/O controller

В cgroup v2 используется `io` controller.

Проверка доступности:

```
cat cgroup.controllers
```

Настройки:

```
io.max
io.weight
```

Это современная модель вместо прямого копирования старых `blkio.*` интерфейсов v1.

Но важно учитывать:

```
filesystem
block layer
device mapper
NVMe/SCSI
queueing
page cache
writeback
```

Поэтому I/O limit не следует воспринимать как простую «сетевую скорость диска».

# 38. PSI — Pressure Stall Information

PSI показывает время, когда tasks испытывают pressure/stall из-за нехватки ресурса.

Проверка:

```
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

Для cgroup:

```
cat /sys/fs/cgroup/<group>/cpu.pressure
cat /sys/fs/cgroup/<group>/memory.pressure
cat /sys/fs/cgroup/<group>/io.pressure
```

PSI отвечает на вопрос не только:

> «сколько ресурса использовано?»

но и:

> «сколько времени workload был вынужден ждать из-за contention/pressure?»

---

# 39. Namespaces + cgroups

Это два разных измерения контейнера:

```
                 CONTAINER
                     │
          ┌──────────┴──────────┐
          │                     │
      namespaces             cgroups
          │                     │
       "что вижу?"          "сколько могу?"
          │                     │
      PID / NET / MNT       CPU / memory /
      IPC / UTS / USER      IO / PIDs ...
```

Но security model шире:

```
namespaces
+
cgroups
+
capabilities
+
seccomp
+
LSM
+
filesystem/mount policy
+
devices policy
```

# 40. Capabilities

Традиционный Unix root historically обладал большим набором privileged operations.

Linux capabilities разделяют привилегии на отдельные capability bits, например:

```
CAP_NET_ADMIN
CAP_NET_RAW
CAP_SYS_ADMIN
CAP_SYS_PTRACE
CAP_CHOWN
...
```

Проверка процесса:

```
grep Cap /proc/<PID>/status
```

или:

```
capsh --pid=<PID> --print
```

---

# 41. Почему `root` внутри контейнера не равен host root

Даже если:

```
id
```

показывает:

```
uid=0(root)
```

нужно проверить:

- user namespace;
- UID mapping;
- effective capabilities;
- bounding set;
- seccomp;
- LSM policy;
- device access;
- mount topology.

Поэтому корректная модель:

```
container root
    =
root identity in a namespace/security context
```

а не:

```
container root = unrestricted host root
```

---

# 42. `/proc` внутри контейнера

`/proc` — это не просто «папка с процессами».

Её view зависит от:

- PID namespace;
- mount namespace;
- mount options;
- procfs configuration.

Поэтому container `/proc` может показывать только процессы, видимые из его PID namespace.

Для корректного контейнерного environment runtime обычно монтирует соответствующий procfs view.

---

# 43. `/sys/fs/cgroup`

В cgroup v2:

```
/sys/fs/cgroup/
```

обычно содержит unified hierarchy.

Например:

```
/sys/fs/cgroup/
├── cgroup.controllers
├── cgroup.procs
├── cgroup.subtree_control
├── cpu.max
├── memory.max
└── ...
```

В systemd-managed systems hierarchy может содержать:

```
system.slice
user.slice
init.scope
```

а container runtime создаёт свои scopes/slices ниже.

Не следует документировать один конкретный path как универсальный для всех distributions.

# 44. Container runtime: кто создаёт namespaces и cgroups

Docker, Podman, containerd и CRI-O — не сами являются kernel isolation mechanism.

Они используют Linux primitives через runtime stack.

Упрощённо:

```
Docker / Kubernetes
        │
        ▼
container manager / runtime
        │
        ▼
OCI runtime
        │
        ▼
Linux kernel
        │
        ├── namespaces
        ├── cgroups
        ├── capabilities
        ├── seccomp
        ├── mounts
        └── networking
```

OCI runtime specification прямо описывает Linux container configuration через namespaces, cgroups, capabilities, LSM и filesystem isolation. citeturn0search3

# 52. Kubernetes: requests и limits

Kubernetes resource requests/limits — это API-level abstraction.

Упрощённо:

```
Pod spec
   │
   ├── requests
   └── limits
          │
          ▼
     kubelet/runtime
          │
          ▼
       cgroups
          │
          ▼
        kernel
```

Но нельзя считать:

```
request = прямой kernel hard reservation
```

для всех ресурсов.

Например:

- CPU request участвует в scheduling и runtime resource management;
- CPU limit может транслироваться в CPU quota;
- memory limit — в memory hard limit;
- memory request влияет на scheduling/QoS semantics и runtime configuration, но его нельзя безоговорочно называть «забронированной RAM».

# 53. Kubernetes memory limit

При:

```
resources:
  limits:
    memory: "512Mi"
```

runtime обычно реализует соответствующее memory constraint через cgroup memory controller на Linux.

Но точный cgroup path и дополнительные настройки зависят от:

- Kubernetes version;
- kubelet;
- CRI runtime;
- systemd integration;
- cgroup v1/v2.

Для cgroup v2 типичный hard limit представлен через:

```
memory.max
```

а события можно анализировать через:

```
memory.events
```

---

# 54. Kubernetes CPU limit

Например:

```
resources:
  limits:
    cpu: "1"
```

может быть реализован через CPU bandwidth control.

Для cgroup v2:

```
cpu.max
```

является одним из ключевых interfaces.

Если CPU limit создаёт throttling, смотреть:

```
cat cpu.stat
```

особенно:

```
nr_throttled
throttled_usec
```

---

# 55. Kubernetes CPU request

Например:

```
resources:
  requests:
    cpu: "500m"
```

не означает:

```
процесс всегда получает ровно 0.5 физического ядра
```

В Kubernetes request — ресурсная заявка, используемая scheduler и runtime semantics.

На уровне cgroup v2 относительное CPU distribution может быть представлено через:

```
cpu.weight
```

Но конкретная трансляция и scheduling semantics зависят от Kubernetes/runtime configuration.

---

# 56. Kubernetes memory request

Нельзя упрощать:

```
request.memory → memory.min = request
```

как универсальное правило.

Современные runtimes могут использовать разные cgroup interfaces в зависимости от QoS class и конфигурации.

Для анализа production pod необходимо смотреть реальные cgroup files на node, а не выводить kernel configuration только из YAML.

---

# 57. Важная граница: namespace ≠ security boundary

Namespaces изолируют видимость, но не гарантируют полную security isolation.

Например:

```
CAP_SYS_ADMIN
privileged container
host mounts
host PID namespace
host network namespace
device access
weak LSM policy
```

могут существенно изменить security boundary.

Поэтому:

> контейнерная изоляция — композиция механизмов, а не свойство одного namespace.

---

# 58. `--privileged`

`--privileged` в container runtimes следует рассматривать как изменение security model, а не просто «дать root».

Оно может существенно расширять:

- capabilities;
- device access;
- security restrictions;
- доступ к kernel interfaces.

Поэтому для production security analysis нужно рассматривать конкретный runtime configuration, а не только UID.

---

# 59. Почему host PID/network namespaces опасны

Если контейнер запускается с host PID namespace:

```
container
   │
   └── видит host processes
```

Если используется host network:

```
container
   │
   └── использует host network namespace
```

Это уменьшает isolation.

Например:

```
--pid=host
--network=host
```

следует считать явным изменением container isolation model.

---

# 60. Контейнер не имеет собственного kernel

Очень важное отличие:

```
VM:
guest userspace
guest kernel
virtual hardware
host kernel
```

против:

```
container:
container userspace
      │
      ▼
host Linux kernel
      │
      ▼
hardware
```

Поэтому container runtime не загружает отдельное ядро для каждого container.

# 72. Основные ошибки и исправления

## Ошибка: «namespace ограничивает ресурсы»

Нет.

Namespace отвечает главным образом за isolation/view.

Ресурсные controls выполняются cgroups и другими kernel mechanisms.

---

## Ошибка: «cgroup namespace ограничивает CPU»

Нет.

Cgroup namespace виртуализирует view cgroup hierarchy.

CPU limitation выполняет CPU controller.

---

## Ошибка: «memory.max — мягкий лимит»

Нет.

`memory.max` — hard memory limit interface.

Для throttling/reclaim boundary используется `memory.high`.

---

## Ошибка: «exit 137 всегда означает OOM»

Нет.

137 = process terminated by signal 9 (`SIGKILL`) в обычной shell exit-code convention.

Причину нужно подтверждать через kernel/runtime telemetry.

---

## Ошибка: «CPU request = половина физического ядра»

Нет.

Kubernetes request — scheduling/resource-management abstraction.

На runtime/kernel level конкретная реализация зависит от configuration.

---

## Ошибка: «container root = host root»

Нет.

Нужно учитывать user namespace, capabilities, LSM, seccomp, mounts и devices.

---

## Ошибка: «большой CPU limit всегда лучше»

Нет.

Слишком высокий limit может убрать полезный throttling/isolation, а слишком низкий — создавать latency spikes. Настройка должна соответствовать workload SLO.

# 74. Академически точная итоговая модель

Контейнеризация Linux — это не отдельная подсистема ядра под названием «containers».

Это композиция уже существующих kernel mechanisms:

```
                         container
                             │
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
       ▼                     ▼                     ▼
  namespaces             cgroups              security
       │                     │                     │
  isolation/view       accounting/control      policy
       │                     │                     │
       └─────────────────────┼─────────────────────┘
                             ▼
                       Linux kernel
                             │
                       scheduler/MM
                       VFS/network
                       block layer
                             │
                             ▼
                         hardware
```

**Namespaces отвечают прежде всего за то, какой системный мир видит процесс.**

**cgroups отвечают за организацию процессов и распределение/ограничение ресурсов.**

**Capabilities, LSM, seccomp, devices и filesystem policy формируют security boundary.**

**Container runtime связывает эти primitives в единый lifecycle, но сами primitives реализуются ядром Linux.**
