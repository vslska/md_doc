## Архитектура контейнеризации в Linux

В классической модели Linux одно ядро обслуживает несколько изолированных контекстов:

```text
                        Linux Kernel
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
    Process A            Process B            Process C
        │                    │                    │
  Namespace Set        Namespace Set        Namespace Set
        │                    │                    │
     cgroups              cgroups              cgroups
````

Изоляция контейнера строится на наборе механизмов ядра:

- **Namespaces:** Изоляция видимости системных ресурсов (PID, сеть, точки монтирования, имена хостов и другие).
- **cgroups:** Организация процессов в иерархии и управление/ограничение ресурсов (CPU, память, I/O, PIDs).
- **Capabilities:** Разделение суперполномочий `root` на атомарные привилегии.
- **LSM (Linux Security Modules):** Мандатное управление доступом (SELinux, AppArmor).
- **Seccomp:** Фильтрация системных вызовов к ядру.
- **OverlayFS / Mounts:** Изоляция файловой системы и слоистые структуры.


```
Формула контейнера = Namespaces + cgroups + Capabilities + Seccomp + Mounts/OverlayFS
```

## Подсистема Linux Namespaces

**Linux Namespace** создает изолированное представление определенного системного ресурса. Процессы внутри namespace видят только ресурсы, привязанные к данному контексту.

Проверить namespaces процесса (на примере PID `1234`):

```sh
ls -l /proc/1234/ns/
```

Каждая запись является символической ссылкой на inode объекта namespace в памяти ядра:

```sh
net -> net:[4026532001]
pid -> pid:[4026532002]
```

Если у двух процессов совпадают номера inode в `/proc/<PID>/ns/...`, они находятся в одном и том же namespace.

### Сводная таблица типов Namespaces

|**Namespace**|**Флаг ядра**|**Изолируемый системный ресурс**|
|---|---|---|
|**PID**|`CLONE_NEWPID`|Пространство идентификаторов процессов (Process IDs)|
|**NET**|`CLONE_NEWNET`|Сетевой стек (интерфейсы, IP-адреса, таблицы маршрутизации, сокеты, netfilter)|
|**MNT**|`CLONE_NEWNS`|Иерархия точек монтирования (Mount topology)|
|**IPC**|`CLONE_NEWIPC`|Средства межпроцессного взаимодействия (System V IPC, POSIX Message Queues)|
|**UTS**|`CLONE_NEWUTS`|Имя хоста и доменное имя (`hostname`, `domainname`)|
|**USER**|`CLONE_NEWUSER`|Таблицы сопоставления UID/GID и связанные права доступа|
|**CGROUP**|`CLONE_NEWCGROUP`|Отображение иерархии `/proc/self/cgroup`|
|**TIME**|`CLONE_NEWTIME`|Смещение часов `CLOCK_MONOTONIC` и `CLOCK_BOOTTIME`|

## Разбор ключевых типов Namespaces

### PID Namespace и семантика PID 1

PID Namespaces образуют древовидную иерархию. Процесс в дочернем PID Namespace получает изолированный PID внутри него, но одновременно имеет родительские PID во всех вышестоящих Ancestor Namespaces.



```
Host PID Namespace (Корневой)
   │
   └── PID 42000 (host view)
          │
          └── Container PID Namespace
                 │
                 └── PID 1 (container view)
```

Первый процесс, созданный внутри PID Namespace, получает **PID 1**. На него накладывается специальная семантика ядра:

1. Он становится родителем (`ancestor`) для всех осиротевших (`orphaned`) процессов внутри этого namespace.
    
2. По умолчанию ядро не применяет к PID 1 стандартные обработчики сигналов завершения (например, `SIGTERM`), если процесс явно их не зарегистрировал.
    
3. При гибели процесса PID 1 ядро отправляет `SIGKILL` всем остальным процессам данного PID Namespace и уничтожает его.
    

### Network Namespace и виртуальные интерфейсы (`veth`)

Network Namespace изолирует сетевой стек. По умолчанию в новом NET Namespace доступен только интерфейс `lo` в состоянии `DOWN`.

Связывание сети контейнера с хостом выполняется через виртуальную пару парных интерфейсов — **`veth` (Virtual Ethernet)**:



```
Host Network Namespace                       Container Network Namespace
┌────────────────────────┐                   ┌──────────────────────────┐
│  veth_host_a           │ ◄── veth pair ──► │  eth0 (veth_container_a) │
│  (подключен к bridge/  │                   │  IP: 10.244.0.5/24       │
│   routing table)       │                   │  Default GW: 10.244.0.1  │
└────────────────────────┘                   └──────────────────────────┘
```

### Mount Namespace и различие с `chroot`

- **`chroot()`** изменяет только корневую директорию (`/`) для процесса и его потомков, но не изолирует точки монтирования, системные вызовы и файловые структуры ядра.
- **Mount Namespace** создаёт независимую копию дерева точек монтирования. Изменения монтирования внутри одного namespace (при флаге приватизации `MS_PRIVATE`) не отражаются на хосте.

### User Namespace и сопоставление UID/GID

User Namespace виртуализирует идентификаторы пользователей и групп. Это позволяет процессу иметь `UID 0` (root) внутри контейнера, отображаясь при этом на обычного непривилегированного пользователя (например, `UID 100000`) на хост-системе.

Конфигурация трансляции задается в `/proc/<PID>/uid_map` и `/proc/<PID>/gid_map`:

```sh
# /proc/<PID>/uid_map
# ID-inside-ns   ID-on-host   Length
       0           100000      65536
```

Контейнерный UID 0 транслируется в UID 100000 на хосте, UID 1 — в 100001 и так далее.

### Cgroup Namespace и Time Namespace

- **Cgroup Namespace:** Изолирует представление файла `/proc/self/cgroup`. Процесс внутри контейнера видит свой путь относительно корня своей cgroup, а не полное дерево системы.
- **Time Namespace:** Позволяет устанавливать виртуальное смещение относительно часов `CLOCK_MONOTONIC` и `CLOCK_BOOTTIME` (полезно для миграции контейнеров и тестирования).

## Namespace API и утилита `nsenter`

Управление namespaces на уровне системных вызовов выполняется через три системных вызова:

1. **`clone(..., flags)`:** Создает новый дочерний процесс в указанных namespaces.
2. **`unshare(flags)`:** Отсоединяет текущий процесс от наследуемых namespaces.
3. **`setns(fd, nstype)`:** Присоединяет вызывающий поток к существующему namespace через файловый дескриптор из `/proc/<PID>/ns/`.

### Диагностическая утилита `nsenter`

`nsenter` подключается к указанным namespaces существующего процесса. Это незаменимо для отладки минималистичных («distroless») контейнеров, где отсутствуют утилиты `bash`, `ip`, `ss`, `tcpdump`.

```sh
# 1. Получение PID основного процесса контейнера
PID=$(docker inspect --format '{{.State.Pid}}' my_container)

# 2. Выполнение сетевой диагностики в NET Namespace контейнера с помощью бинарников хоста:
nsenter -t $PID -n ip addr
nsenter -t $PID -n ss -lntup
nsenter -t $PID -n tcpdump -i any -n
```

## Подсистема Control Groups (cgroups)

**cgroups (Control Groups)** — механизм ядра Linux, обеспечивающий иерархическую группировку процессов и распределение между ними системных ресурсов (CPU, память, диск, PIDs).

## Сравнение Cgroups v1 и Cgroups v2

|**Параметр**|**Cgroups v1**|**Cgroups v2**|
|---|---|---|
|**Иерархия**|Множественная (каждый контроллер имеет своё изолированное дерево).|Единая (Unified Hierarchy). Все контроллеры привязаны к общему дереву.|
|**Принадлежность процесса**|Процесс мог находиться в разных группах для разных ресурсов (например, CPU: `/groupA`, Mem: `/groupB`).|Процесс находится строго в одном узле единого дерева.|
|**Правило No-Internal-Processes**|Процессы могли находиться на любых уровнях иерархии.|Процессы могут находиться только в листовых узлах (`leaf nodes`), если включены контроллеры subtree.|
|**Управление OOM**|Персональный OOM Kill на уровне отдельного контроллера.|Групповой OOM Kill (`memory.oom.group`), согласованная реакция.|
|**Поддержка eBPF & Pressure**|Ограниченная.|Полное интегрирование с PSI (Pressure Stall Information) и eBPF-контроллерами.|

Проверка версии cgroups на хосте:

```sh
stat -fc %T /sys/fs/cgroup
# Результат "cgroup2fs" указывает на использование cgroups v2
```

## Контроллеры cgroups v2 и управление ресурсами

В cgroups v2 поддерево активируется записью контроллеров в файл `cgroup.subtree_control`:

```sh
echo "+cpu +memory +io +pids" > /sys/fs/cgroup/my_workload/cgroup.subtree_control
```

### CPU Controller: `cpu.weight`, `cpu.max` и троттлинг

1. **`cpu.weight` (Относительный вес, 1–10000, по умолчанию 100):** Задает пропорциональное распределение процессорного времени при конкуренции (Work-conserving mode). Не ограничивает CPU, если система простаивает.
2. **`cpu.max` (Жесткий лимит / Bandwidth Limit):** Задает лимит в формате `QUOTA PERIOD` (в микросекундах).

```sh
# Выделение ровно 2 виртуальных ядер (200ms CPU времени за каждые 100ms)
echo "200000 100000" > /sys/fs/cgroup/my_container/cpu.max
```

#### Причина неожиданного троттлинга (CPU Throttling)

Если приложение многопоточное, 8 потоков, одновременно выполняющихся в течение 12.5 миллисекунд, суммарно расходуют $8 \times 12.5 = 100 \text{ ms}$ CPU-квоты. В результате квота исчерпывается в начале окна `PERIOD`, и процесс блокируется (троттлится) до начала следующего периода, вызывая задержки (Latency Spikes).

Анализ троттлинга:

```sh
cat /sys/fs/cgroup/my_container/cpu.stat
# Векторы контроля: nr_throttled и throttled_usec
```

### Memory Controller: `memory.max`, `memory.high` и Cgroup OOM

- **`memory.max` (Hard Limit):** Абсолютный верхний предел физической памяти. При его превышении ядро пытается освободить `Page Cache`; если память освободить не удалось — вызывается **Cgroup OOM Killer**.
- **`memory.high` (Throttle / Reclaim Limit):** Мягкий предел. При его превышении процесс не убивается, а замедляется (дроттлится), пока ядро агрессивно вымывает страницы памяти.
- **`memory.min` / `memory.low`:** Защищенные гарантированные объемы памяти, не подлежащие вытеснению при дефиците ресурсов в системе.

> **Важно:** `memory.current` учитывает не только `RSS` (Heap/Stack), но и `Page Cache`, `Shared Memory` (`tmpfs`) и структуры ядра (`kernel slab`).

Диагностика Cgroup OOM:

```
cat /sys/fs/cgroup/my_container/memory.events
# Поля для анализа: oom, oom_kill, oom_group_kill
```

### PIDs и I/O Controllers

- **`pids.max`:** Ограничивает суммарное количество задач (потоков и процессов) в группе. Защищает систему от `fork-bomb` и неконтролируемого разрастания потоков.
- **`io.max`:** Настройка лимитов чтения/записи на блочные устройства в IOPS или байтах/сек (`rbps`, `wbps`, `riops`, `wiops`).
### Pressure Stall Information (PSI)

PSI отслеживает время задержек, возникающих из-за ожидания ресурсов (CPU, Memory, I/O).

```sh
cat /sys/fs/cgroup/my_container/memory.pressure
# Вывод:
# some avg10=0.00 avg60=0.00 avg300=0.00 total=0
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

- **`some`:** Процент времени, когда хотя бы один поток заблокирован в ожидании ресурса.
- **`full`:** Процент времени, когда **все** потоки в cgroup одновременно заблокированы (система полностью простаивает из-за дефицита).

## Модель безопасности: Capabilities, Seccomp и LSM

Одного лишь разделения Namespaces недостаточно для обеспечения полной безопасности. Контейнерный контекст ограничивается дополнительными барьерами:

```
┌──────────────────────────────────────────────────────────┐
│                   Container Process                      │
└────────────────────────────┬─────────────────────────────┘
                             │
       ┌─────────────────────┼─────────────────────┐
       ▼                     ▼                     ▼
  Capabilities            Seccomp                 LSM
 (Ограничение        (Фильтрация системных    (AppArmor / SELinux
  привилегий root)      вызовов ядра)          мандатные правила)
```

1. **Capabilities:** Отключение опасных возможностей суперпользователя (например, `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`).
2. **Seccomp (Secure Computing Mode):** Блокировка вызовов ядра (например, запрет `reboot()`, `kexec_load()`, манипуляций с модулями ядра).
3. **Флаг `--privileged`:** Снимает ограничения Seccomp, Capabilities и LSM, предоставляя контейнеру прямой доступ к устройствам хоста и восстанавливая фактически полный доступ к системе.
## Экосистема Container Runtime (OCI, containerd, runc)

Архитектура исполнения контейнеров стандартизирована спецификацией **OCI (Open Container Initiative)**:

```
High-Level Orchestrator (Kubernetes / Kubelet)
       │
       ▼
CRI Runtime (containerd / CRI-O)  <-- Управляет образами, сетью, lifecycle
       │
       ▼
OCI Runtime (runc / crun)        <-- Взаимодействует с ядром Linux (sys-calls)
       │
       ▼
Linux Kernel (Namespaces, cgroups, mounts)
```

## Справочник команд и чек-лист диагностики

### Диагностический чек-лист перед анализом

```sh
# 1. Проверка версии cgroups
stat -fc %T /sys/fs/cgroup

# 2. Поиск Cgroup ID конкретного процесса
cat /proc/<PID>/cgroup

# 3. Проверка привилегий и Capabilities процесса
grep '^Cap' /proc/<PID>/status
capsh --decode=$(grep '^CapEff' /proc/<PID>/status | awk '{print $2}')

# 4. Проверка отображения пользователей в User Namespace
cat /proc/<PID>/uid_map
```

### Набор команд проверки ресурсов (cgroups v2)

```sh
# Метрики CPU и троттлинга
```
