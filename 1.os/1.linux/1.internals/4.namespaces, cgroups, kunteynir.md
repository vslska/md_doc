# Namespaces, Cgroups & Анатомия Контейнеризации

>Этот раздел посвящен механизмам изоляции ядра Linux, которые лежат в основе Docker, Podman, LXC и Kubernetes (CRI-O, containerd). Контейнер — это не виртуальная машина: у него нет собственного гипервизора или выделенного ядра. Контейнер — это обычный изолированный процесс в хостовой ОС, ограничения для которого прозрачно накладываются ядром с помощью двух механизмов: **Namespaces** (определяют, что процесс может _видеть_) и **Cgroups** (определяют, сколько ресурсов процесс может _потребить_).

---

## 1. Namespaces под капотом (Пространства имен)

**Namespaces (Пространства имен)** отвечают за ограничение видимости. Они изолируют системные ресурсы, создавая для группы процессов полную иллюзию того, что они запущены в отдельной, независимой операционной системе.

8 ключевых пространств имен в ядре Linux:

1. **PID (Process ID):** Изолирует дерево процессов. Внутри контейнера главный процесс получает виртуальный `PID 1` (аналог `systemd` или `init`). При этом в таблице процессов хостовой ОС этот же процесс имеет свой реальный уникальный пятизначный PID. Процессы из одного PID namespace не видят процессы из другого.
2. **NET (Network):** Изолирует сетевые устройства, таблицы маршрутизации, порты (сокеты) и правила фильтрации Netfilter (`iptables`/`nftables`). Позволяет контейнеру иметь собственный виртуальный интерфейс (обычно `veth`), свой IP-адрес и изолированный стек.
3. **MNT (Mount):** Изолирует точки монтирования файловой системы. Процесс видит только ту иерархию директорий, которая была подменена для него (например, с помощью `pivot_root` или `chroot`), и не имеет доступа к корневой файловой системе хоста.
4. **IPC (Inter-Process Communication):** Изолирует механизмы межпроцессного взаимодействия: разделяемую память (Shared Memory segments), очереди сообщений POSIX и семафоры System V. Процессы из разных контейнеров не могут читать память друг друга.
5. **UTS (UNIX Timesharing System):** Позволяет процессу задавать собственное имя хоста (`hostname`) и доменное имя (NIS domain name), не влияя на настройки хостовой машины.
6. **USER:** Изолирует идентификаторы пользователей и групп (UID/GID). Позволяет процессу обладать правами суперпользователя `root` (UID 0) внутри своего контейнера, но для хостовой системы этот же процесс будет выполняться от лица обычного непривилегированного пользователя (например, с UID 10001).
    - _Важно:_ Docker по умолчанию **не включает** этот namespace автоматически. Для его активации требуется настройка механизма `userns-remap` в `daemon.json`. В Podman и Rootless Docker этот namespace активен по умолчанию.
7. **CGROUP:** Изолирует видимость путей к контрольным группам в файловой системе `/sys/fs/cgroup`. Процесс внутри контейнера не может увидеть лимиты и метаданные соседних контейнеров.
8. **TIME:** (Добавлено в ядре 5.6). Позволяет процессам внутри пространства имен иметь собственное системное время (offset относительно часов хоста) и свой независимый аптайм. Это критично для тестирования временных зон или симуляции изменения дат без сдвига времени на всем сервере.

### Практическая отладка distroless-контейнеров через `nsenter`

Если контейнер работает некорректно (например, рвутся сетевые соединения), но разработчики собрали ультра-минималистичный образ (Distroless / Scratch), внутри которого нет ни `bash`, ни `sh`, ни утилит диагностики вроде `curl` или `ip`, стандартная команда `docker exec -it <id> bash` вернет ошибку.

**Решение:** Использовать утилиту `nsenter`. Она позволяет системному администратору со стороны хоста (где есть все необходимые инструменты: `tcpdump`, `strace`, `iproute2`) принудительно войти в пространства имен целевого контейнера.

#### Пошаговый алгоритм отладки:

1. **Находим реальный PID процесса контейнера в хостовой ОС:**

```bash
docker inspect --format '{{ .State.Pid }}' <имя_или_ID_контейнера>
# Для containerd/crictl: crictl inspect <id> | grep pid
```

2. **Проникаем в пространства имен контейнера:**  
    _Чтобы диагностика работала корректно, необходимо подключать не только сеть (`-n`), но и пространство монтирования (`-m`), чтобы утилиты корректно считывали сетевые файлы конфигурации вроде `/etc/hosts`:_

```bash
nsenter -t <PID_из_шага_1> -m -u -n -p -F
```

- `-t <PID>` — целевой процесс-якорь, чьи пространства имен мы берем.
- `-m`, `-u`, `-n`, `-p` — входим в Mount, UTS, Network и PID namespaces.
- `-F` — заставляет `nsenter` сделать `fork` перед запуском оболочки. Без этого флага при входе в PID namespace команда `ps` и системные вызовы создания процессов могут работать некорректно.

После выполнения этой команды ваша текущая хостовая сессия терминала проваливается внутрь контейнера. Команда `ip a` или `tcpdump` будет показывать трафик сетевого интерфейса контейнера, но при этом вам доступны абсолютно все бинарники и утилиты, установленные на основном хосте.

## 2. Cgroups (Control Groups) v1 vs v2

Если Namespaces отвечают за изоляцию видимости ресурсов, то **Cgroups (Контрольные группы)** — это механизм ядра Linux, который распределяет, квотирует и ограничивает физические ресурсы процессов (**CPU, Оперативная память, Дисковый ввод-вывод blkio, количество PID**). Именно cgroups не позволяют одному «протекшему» контейнеру монополизировать ресурсы всего сервера и уронить соседние сервисы.

Эволюция архитектуры: В чем принципиальная разница?

- **Cgroups v1 (Устаревший стандарт):**  
    В первой версии каждый контроллер ресурсов (подсистема: `cpu`, `memory`, `blkio`, `pids`) существовал в виде отдельной, независимой иерархического дерева в файловой системе. Один и тот же процесс мог находиться в группе `/sys/fs/cgroup/memory/container1` для лимитирования памяти, но при этом в группе `/sys/fs/cgroup/cpu/background` для лимитирования процессора._Главный минус:_ Подсистемы ядра не могли общаться между собой. Например, подсистема `blkio` (ограничение скорости диска) ничего не знала о подсистеме `memory`. Когда процесс агрессивно писал на диск, ядро забивало RAM грязными страницами (Page Cache), но `blkio` не мог затормозить этот процесс, так как сброс кэша выполняли фоновые потоки ядра, не привязанные к этой cgroup. Это приводило к непредсказуемым фризам и дедлокам ядра.
- **Cgroups v2 (Современный унифицированный стандарт):**  
    В современных дистрибутивах Linux используется **единая унифицированная иерархия** (Unified Hierarchy). Все доступные контроллеры ресурсов жестко привязаны к одной и той же группе процессов. Если процесс перемещается в группу контейнера, все его лимиты (CPU, Memory, I/O) рассчитываются и управляются в одном общем контексте. Это позволило ядру корректно реализовать механизмы **сброса грязных страниц с учетом дисковых лимитов конкретного контейнера** (Writeback Cgroup Tracking) и ввести метрику PSI (Pressure Stall Information), отслеживающую реальное голодание процессов по ресурсам.

---
### Анатомия лимитов в cgroups v2

Все управление cgroups v2 происходит через псевдофайловую систему, примонтированную по пути `/sys/fs/cgroup/`. В отличие от v1, здесь нет раздельных папок под ресурсы, а конфигурационные файлы имеют другие имена.

Ограничение памяти и Cgroup OOM-Killer

В cgroups v2 управление лимитами памяти стало более гибким за счет разделения на жесткие и мягкие границы:

- `memory.max` — жесткий лимит (аналог `memory.limit_in_bytes` из v1). Если процессы внутри cgroup достигают этого порога, ядро сначала пытается агрессивно вычистить их файловый кэш (Page Cache). Если это не помогает, активируется локальный **Cgroup OOM-Killer**. Он завершает самый прожорливый процесс _внутри этой конкретной группы_ (контейнер падает с Exit Code 137). При этом вся остальная операционная система и другие контейнеры продолжают работать без сбоев.
- `memory.high` — мягкий дросселирующий лимит. При его превышении ядро не убивает контейнер, а начинает искусственно замедлять (throttling) его процессы, заставляя их тратить кванты времени на очистку собственной памяти.

#### Ограничение CPU (CFS Scheduler)

Вместо двух раздельных файлов с микросекундами из v1, в v2 лимиты CPU задаются в едином файле `cpu.max`:

- Синтаксис файла: `[квота] [период]` (например, `200000 100000`).
- Это означает, что суммарно всем процессам внутри этой cgroup разрешено использовать 200 000 микросекунд процессорного времени за каждый астрономический период в 100 000 микросекунд. Математически это эквивалентно строгому ограничению в **2 ядра CPU**. Если контейнер превышает квоту, планировщик ядра приостанавливает его потоки до начала следующего периода (CPU Throttling).

### Практическая диагностика cgroups на хосте

**1. Как узнать, какая версия cgroups активна прямо сейчас?**

```bash
mount | grep cgroup
```


- Если в выводе присутствует строка с типом `cgroup2` на пути `/sys/fs/cgroup`, у вас активна **v2**.
- Если вы видите множество отдельных точек монтирования вроде `/sys/fs/cgroup/cpu,cpuacct`, `/sys/fs/cgroup/memory`, то система работает на устаревшей версии **v1**.

**2. Как посмотреть реальные лимиты контейнера со стороны хоста (в cgroups v2)?**  
Зная PID главного процесса контейнера (например, `1234`), можно мгновенно найти его конфигурационную папку в ядре:

```bash
# Узнаем путь к cgroup для конкретного PID
cat /proc/1234/cgroup
# Вывод покажет что-то вроде: 0::/system.slice/docker-<ID>.scope

# Переходим в эту директорию в /sys/fs/cgroup/ и читаем лимиты:
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/cpu.max
```

## 3. Прямая связь Cgroups с лимитами в Kubernetes

В манифестах Kubernetes инженеры всегда описывают ресурсы подов: `requests` (гарантированный минимум для планирования) и `limits` (максимальный потолок). На уровне ядра Linux хостовой ноды рантайм-контейнеризации (containerd / CRI-O) транслирует эти абстракции в совершенно разные конфигурационные файлы и механизмы cgroups v2.

---
### Лимиты памяти (Memory) -> Жесткий потолок и защита

Память является **несжимаемым ресурсом** (Non-compressible resource) — ядро не может временно "замедлить" выделение байт или попросить приложение подождать.

#### 1. `limits.memory: "512Mi"` (Жесткий предел)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../memory.max`

- **Механика работы:** Если процессы внутри пода суммарно перешагивают отметку в 512 МиБ, ядро сначала пытается экстренно высвободить память за счет агрессивного вымывания чистого файлового кэша (Page Cache) этого пода. Если это не помогает опустить утилизацию ниже лимита, ядро мгновенно активирует локальный **Cgroup OOM-Killer**. Самый прожорливый процесс внутри пода завершается с системным кодом **Exit Code 137** (`SIGKILL`). Сам хост при этом не страдает.

#### 2. `requests.memory: "256Mi"` (Гарантия и QoS)

Превращается в файлы: `/sys/fs/cgroup/kubepods.slice/.../memory.min` или `memory.low`

- **Механика работы:** Этот параметр сообщает планировщику памяти ядра (Memory Reclaim Mechanism), что 256 МиБ памяти этого пода являются неприкосновенными. Если на хост-ноде начнется жесткий дефицит RAM (Memory Pressure) и ядро начнет вытеснять кэш и неактивные страницы процессов, чтобы спасти систему от OOM, оно будет обходить этот под стороной, пока его утилизация находится в пределах `requests`.

---

### Лимиты процессора (CPU) -> Троттлинг и веса планировщика

Процессорное время является **сжимаемым ресурсом** (Compressible resource) — ядро может гибко квантовать и распределять его циклы.

#### 1. `limits.cpu: "1"` (Ограничение сверху)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.max`

- **Механика работы:** Настройка конфигурирует планировщик задач ядра **CFS (Completely Fair Scheduler)**. Время CPU делится на жесткие астрономические периоды, которые по умолчанию в Kubernetes составляют **100 мс**.В cgroups v2 в файл `cpu.max` записывается строка вида: `100000 100000` (где первое число — доступная квота в микросекундах, второе — длительность самого периода). Это означает, что суммарно все потоки вашего пода могут вычислять задачи на процессорах хоста не более 100 мс в рамках каждого стомиллисекундного окна.
- **Что происходит при превышении:** За превышение лимита CPU ядро **никогда не убивает** процесс. Оно временно приостанавливает (замораживает) его потоки, убирая их из runqueue планировщика до начала следующего периода в 100 мс. Это называется **CPU Throttling**. Контейнер не падает, но его внутренний Response Time (Latency) моментально улетает вверх, генерируя аномальные задержки на графиках.

##### Архитектурная ловушка многопоточности (Эффект микро-челки)

Частая проблема в Highload: вы задали приложению `limits.cpu: "1"`, графики мониторинга показывают среднюю загрузку CPU контейнера всего в 20-30%, но при этом приложение дико троттлится. Почему?

- Планировщик CFS считает квоту суммарно по всем ядрам. Если ваше приложение (например, на Go или Java) многопоточное и в начале 100-миллисекундного окна одновременно запустило вычисления в **10 потоках**, каждый из которых отработал всего по **10 мс**, то суммарная квота пода в 100 мс будет полностью исчерпана **за первые 10 миллисекунд** текущего периода!
- Оставшиеся 90 миллисекунд периода все потоки приложения будут намертво заморожены ядром, ожидая сброса таймера. Именно поэтому в современных микросервисных архитектурах Senior-инженеры часто либо полностью отключают CPU Limits (оставляя только Requests), либо используют CPU Manager со `static` политикой для пингования ядер.

#### 2. `requests.cpu: "500m"` (Пропорциональное разделение)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.weight`

- **Механика работы:** В cgroups v2 этот параметр задает относительный "вес" (приоритет) процесса на CPU по шкале от 1 до 10000. Значение `500m` (половина ядра) конвертируется рантаймом в числовой вес. Пока хост-нода не нагружена на 100%, ваш под может свободно утилизировать хоть все доступные ядра процессора хоста (если нет CPU лимитов).Но как только на хосте начинается борьба за ресурсы (CPU Distress), планировщик CFS начинает делить свободные такты процессора строго пропорционально весам `cpu.weight` всех запущенных подов. Под с большим request-ом гарантированно вытеснит под с меньшим.

## Практическая диагностика CPU Throttling внутри контейнера

Чтобы понять, страдает ли контейнер от заморозок ядра, не обязательно настраивать сложные экспортеры в Prometheus. Достаточно прочитать системную метрику прямо изнутри cgroup контейнера:

```bash
cat /sys/fs/cgroup/cpu.stat
```

**Ключевые метрики для анализа:**

- `usage_usec` — суммарное время в микросекундах, которое процесс реально вычислял задачи на CPU.
- `nr_periods` — общее количество периодов планировщика, прошедших с момента старта контейнера.
- `nr_throttled` — сколько раз за эти периоды контейнер полностью исчерпывал свою квоту и принудительно ставился ядром на паузу.
- `throttled_usec` — суммарное чистое время в микросекундах, которое приложение провело в замороженном состоянии.

_Метрика здоровья:_ Разделите `nr_throttled` на `nr_periods`. Если полученное значение превышает **0.1-0.15 (более 10-15% периодов уходят в троттлинг)** — лимиты CPU для этого пода зажаты слишком сильно, их необходимо срочно увеличивать либо пересматривать пул потоков приложения.
