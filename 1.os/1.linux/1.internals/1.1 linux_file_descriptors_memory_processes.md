# 1. Файловые дескрипторы и лимиты

## 1.1. Что такое File Descriptor

В Unix/Linux процесс работает с файлами, сокетами, pipe, устройствами и рядом других объектов ядра через **файловые дескрипторы (File Descriptors, FD)**.

FD — это небольшое неотрицательное целое число, являющееся индексом в таблице дескрипторов конкретного процесса.

Стандартные дескрипторы:

| FD | Имя | Назначение |
|---:|---|---|
| `0` | `stdin` | стандартный ввод |
| `1` | `stdout` | стандартный вывод |
| `2` | `stderr` | стандартный поток ошибок |

Важно различать сам числовой FD и объект ядра, на который он указывает. В упрощённой модели цепочка выглядит так:

```text
процесс
  │
  └── таблица FD
        │
        ├── 0 ──────► объект открытого файла
        ├── 1 ──────► объект открытого файла
        └── 2 ──────► объект открытого файла
                         │
                         └── inode / socket / pipe / device ...
```

В Linux дескриптор является **процессным идентификатором ссылки на открытый объект**, а не самим файлом и не inode.

---

## 1.2. Почему исчерпание FD ломает сервис

Сервис может одновременно удерживать большое количество:

- файлов журналов;
- TCP/UDP-сокетов;
- соединений с базой данных;
- pipe;
- Unix domain sockets;
- файлов конфигурации;
- библиотек и других открытых объектов.

При достижении ограничения новые операции `open()`, `socket()`, `accept()` и связанные с ними действия могут завершаться ошибкой.

Для высоконагруженных сервисов это особенно важно: исчерпание FD способно привести к отказу новых соединений и вторичным ошибкам, например невозможности открыть лог-файл.

---

## 1.3. `EMFILE` и `ENFILE`

Linux различает два принципиально разных уровня исчерпания ресурсов.

### `EMFILE`

```text
Too many open files
```

Обычно означает, что процесс достиг своего лимита открытых файлов.

Проверка:

```bash
ulimit -Sn
ulimit -Hn
```

где:

- **soft limit** — текущий применяемый предел;
- **hard limit** — максимальное значение, до которого soft limit может быть повышен процессом в пределах разрешённых прав.

### `ENFILE`

Означает исчерпание глобального ограничения на открытые file descriptions / файловую таблицу ядра.

Таким образом:

```text
EMFILE → ограничение процесса
ENFILE → глобальное ограничение ядра
```

Это принципиально разные проблемы и диагностируются на разных уровнях.

# 2. Уровни ограничения количества открытых файлов

## 2.1. Глобальный уровень

Параметр:

```bash
cat /proc/sys/fs/file-max
```

Показывает системный максимум для числа одновременно открытых file descriptions.

Текущее состояние можно посмотреть через:

```bash
cat /proc/sys/fs/file-nr
```

На современных ядрах формат и интерпретация полей `file-nr` зависят от версии ядра; поэтому этот файл следует рассматривать как источник низкоуровневой статистики, а не как универсальную формулу вида «первое число = все открытые FD».

Временное изменение параметра:

```bash
sysctl -w fs.file-max=2097152
```

Для постоянной настройки:

```text
/etc/sysctl.conf
```

например:

```conf
fs.file-max = 2097152
```

После изменения постоянной конфигурации:

```bash
sysctl -p
```

или применить конкретный файл конфигурации через соответствующий механизм `sysctl`.

> **Практический принцип:** увеличение глобального лимита не исправляет `EMFILE`, если проблема находится на уровне конкретного процесса.

---

## 2.2. Лимиты процесса: `RLIMIT_NOFILE`

Для процесса действует ресурсный лимит `RLIMIT_NOFILE`.

Проверка в shell:

```bash
ulimit -Sn
ulimit -Hn
```

или:

```bash
ulimit -n
```

Проверка уже запущенного процесса:

```bash
cat /proc/1234/limits | grep "Max open files"
```

Пример:

```text
Max open files            65536                65536                files
```

Здесь:

- первое значение — soft limit;
- второе — hard limit.

---

# 3. Где задавать лимиты в production

## 3.1. Пользовательские сессии

Для PAM-сессий лимиты могут задаваться через:

```text
/etc/security/limits.conf
```

Например:

```conf
nginx    soft    nofile   65536
nginx    hard    nofile   65536
```

Однако это **не универсальный способ настройки лимитов для всех типов процессов**.

Особенно важно учитывать, как именно процесс запускается: через интерактивную shell-сессию, PAM, `systemd`, контейнерный runtime и т. д.

---

## 3.2. Сервисы под управлением systemd

Для systemd-сервисов рекомендуется задавать лимит непосредственно в unit configuration.

Например:

```ini
[Service]
LimitNOFILE=65536
```

Редактировать drop-in-конфигурацию удобно через:

```bash
systemctl edit имя_сервиса
```

После изменения:

```bash
systemctl daemon-reload
systemctl restart имя_сервиса
```

Проверить фактический лимит уже работающего процесса:

```bash
cat /proc/$(pidof имя_сервиса)/limits | grep "Max open files"
```

> **Важно:** `daemon-reload` перечитывает конфигурацию unit-файлов, но уже запущенный процесс не получает новые resource limits автоматически. Для применения нового лимита к процессу обычно требуется его перезапуск.

# 4. Диагностика файловых дескрипторов

## 4.1. Сколько FD использует процесс

Для PID `1234`:

```bash
ls -1 /proc/1234/fd | wc -l
```

Более прямой вариант:

```bash
find /proc/1234/fd -maxdepth 1 -type l | wc -l
```

Каталог `/proc/<PID>/fd` содержит символические ссылки на объекты, доступные процессу через FD.

---

## 4.2. Что именно удерживает процесс

Утилита `lsof` позволяет увидеть открытые файлы, сокеты, pipe и другие объекты:

```bash
lsof -p 1234
```

Для сетевых объектов особенно полезны фильтры `lsof` по типам и протоколам, а также специализированные инструменты вроде:

```bash
ss -p
```

---

## 4.3. Лимиты работающего процесса

```bash
cat /proc/1234/limits | grep "Max open files"
```

Это надёжнее, чем смотреть `ulimit` в своей текущей shell-сессии: shell и уже работающий сервис могут иметь разные ограничения.

---

# 5. Изменение лимита живого процесса

Иногда процесс нельзя немедленно перезапустить. В Linux для изменения resource limits существующего процесса может использоваться `prlimit`.

Например:

```bash
prlimit --pid 1234 --nofile=65536:65536
```

Формат:

```text
--nofile=SOFT:HARD
```

Проверка:

```bash
prlimit --pid 1234 --nofile
```

### Важное ограничение

Изменение лимита существующего процесса:

- применяется к этому процессу;
- не изменяет конфигурацию будущих процессов;
- после завершения процесса теряет смысл;
- может требовать соответствующих прав.

Поэтому `prlimit` — инструмент оперативного вмешательства, а не замена постоянной конфигурации systemd/PAM/runtime.

# 6. Виртуальная память

## 6.1. Основная модель

Linux предоставляет каждому процессу собственное **виртуальное адресное пространство**.

Упрощённо:

```text
Процесс
┌─────────────────────────────┐
│ Virtual Address Space       │
│                             │
│ code / text                 │
│ shared libraries            │
│ heap                        │
│ mmap regions                │
│ stack                       │
└──────────────┬──────────────┘
               │
               ▼
        Page Tables
               │
               ▼
       Physical Memory
           (RAM)
```

Процесс работает с виртуальными адресами. Таблицы страниц (`page tables`) отображают их на физические страницы памяти.

---

## 6.2. Страницы памяти

Память управляется страницами (**pages**).

Для распространённых конфигураций x86/x86-64 базовый размер страницы составляет:

```text
4 KiB
```

Но это не универсальное правило для всех архитектур и всех режимов: существуют, например, huge pages.

---

# 7. Page Fault

**Page fault** возникает, когда процессор при обращении к виртуальному адресу обнаруживает, что требуемое отображение отсутствует или требует дополнительной обработки ядром.

Page fault не означает автоматически «ошибка приложения».

Он является нормальным механизмом виртуальной памяти.

---

## 7.1. Minor page fault

**Minor fault** обычно обрабатывается без чтения требуемой страницы с дискового устройства.

Типичные ситуации:

- создание отображения уже существующей страницы;
- использование страницы, уже присутствующей в RAM;
- некоторые сценарии copy-on-write;
- первоначальное обращение к лениво выделенной памяти, когда ядро может предоставить физическую страницу без дискового I/O.

---

## 7.2. Major page fault

**Major fault** требует дорогостоящего внешнего I/O, например чтения страницы с backing storage.

Типичные сценарии:

1. нужная страница файла отсутствует в Page Cache;
2. анонимная страница была вытеснена в Swap и теперь должна быть возвращена в RAM.

Упрощённая цепочка:

```text
CPU
 │
 ▼
Page fault
 │
 ├── данные доступны в RAM
 │       └── Minor fault
 │
 └── требуется I/O
         └── Major fault
                │
                └── storage / swap
```

Высокое число major faults может указывать на сильное давление на память или недостаточную локальность доступа и приводить к росту latency.

---

# 8. Anonymous Memory и Page Cache

Для анализа memory pressure важно различать как минимум два класса страниц.

## 8.1. Page Cache

Page Cache хранит в RAM содержимое файлов, прочитанное с файловой системы.

### Clean pages

Страница не содержит изменений относительно backing storage.

Если ядру срочно требуется RAM, clean cache page может быть освобождена без предварительной записи на диск.

При следующем обращении данные придётся получить снова.

### Dirty pages

Страница была изменена в памяти и ещё не синхронизирована с backing storage.

Такую страницу нельзя просто выбросить: её содержимое должно быть записано в соответствующее хранилище.

---

## 8.2. Anonymous Memory

Anonymous memory не имеет обычного файлового backing.

Типичные примеры:

- heap;
- stack;
- runtime-структуры;
- часть памяти, выделенной приложением через anonymous `mmap()`.

Если такая память должна быть вытеснена из RAM, одним из механизмов является Swap.

Упрощённо:

```text
             Physical RAM
                  │
       ┌──────────┴──────────┐
       │                     │
       ▼                     ▼
   Page Cache          Anonymous Memory
       │                     │
       │                     ▼
       │                    Swap
       │
       ▼
   Filesystem
```

---

# 9. Swap и `vm.swappiness`

`vm.swappiness` — параметр политики reclaim, влияющий на относительную склонность ядра к вытеснению анонимной памяти и файлового кэша.

Проверить:

```bash
cat /proc/sys/vm/swappiness
```

или:

```bash
sysctl vm.swappiness
```

Временно изменить:

```bash
sysctl -w vm.swappiness=10
```

Постоянно:

```conf
vm.swappiness = 10
```

---

## 9.1. Почему `swappiness = 0` не следует считать «магической оптимизацией»

Значение `0` не означает простое правило «Swap полностью выключен».

Семантика reclaim менялась между версиями ядер, поэтому интерпретировать параметр следует с учётом конкретной версии Linux.

Главный принцип:

> `swappiness` — параметр политики reclaim, а не переключатель «Swap on/off».

Для production-систем нельзя выбирать значение только по универсальной рекомендации вроде «всегда 1», «всегда 10» или «всегда 0». Значение следует проверять на реальной нагрузке и учитывать характер приложения.

Особенно осторожно следует подходить к:

- базам данных;
- JVM;
- Kubernetes-нодам;
- системам с жёсткими требованиями к latency;
- memory-intensive приложениям.

---

# 10. `vm.vfs_cache_pressure`

Параметр:

```bash
sysctl vm.vfs_cache_pressure
```

влияет на относительную склонность ядра освобождать cache объектов VFS — прежде всего dentry и inode cache.

Типичное значение по умолчанию:

```text
100
```

Изменение:

```bash
sysctl -w vm.vfs_cache_pressure=50
```

Однако уменьшение этого параметра также не следует считать универсальной production-рекомендацией.

Изменение reclaim-политики должно подтверждаться наблюдением за:

- memory pressure;
- latency;
- I/O;
- cache hit rate;
- поведением конкретного приложения.

# 11. Диагностика памяти

## 11.1. `/proc/meminfo`

Базовый источник статистики:

```bash
cat /proc/meminfo
```

Для быстрой выборки:

```bash
grep -E 'Cached|AnonPages|Buffers' /proc/meminfo
```

Полезно также смотреть связанные поля:

```bash
grep -E 'MemTotal|MemFree|MemAvailable|Cached|Buffers|SwapTotal|SwapFree|AnonPages|Dirty|Writeback' /proc/meminfo
```

---

## 11.2. Page faults

Если установлен `sysstat`:

```bash
sar -B 1
```

Особое внимание можно уделять:

- `majflt/s` — major page faults;
- показателям reclaim/scanning;
- общей динамике памяти и I/O.

При диагностике важно смотреть не отдельное число, а его корреляцию с:

```text
latency
CPU
I/O wait
swap activity
memory pressure
```

# 12. Состояния процессов

Команды:

```bash
ps
top
btop
```

показывают состояние процесса.

Для `ps` полезно поле `STAT`.

Основные состояния:

| `STAT` | Состояние | Смысл |
|---|---|---|
| `R` | Running / Runnable | выполняется или готов к выполнению |
| `S` | Interruptible sleep | ожидает событие и может быть разбужен сигналом |
| `D` | Uninterruptible sleep | ожидает завершения операции в ядре; обычно связан с I/O или другой не прерываемой частью kernel wait |
| `Z` | Zombie | процесс завершился, но родитель ещё не забрал его exit status |

Дополнительные символы `STAT`, например `T`, `<`, `N`, `s`, `l`, `+`, являются модификаторами и должны интерпретироваться отдельно от основного состояния.

---

# 13. Состояние `R`

`R` означает, что задача:

- выполняется на CPU прямо сейчас; или
- находится runnable и ожидает назначения CPU планировщиком.

Поэтому `R` не означает буквально «процесс уже исполняется в эту наносекунду».

Для оценки CPU saturation необходимо смотреть:

```bash
top
```

или:

```bash
ps -eo pid,ppid,stat,pcpu,comm --sort=-pcpu
```

---

# 14. Состояние `S`

`S` — interruptible sleep.

Процесс временно не исполняется и ожидает событие:

- таймер;
- ввод;
- сетевые данные;
- условие синхронизации;
- другое событие ядра.

Это нормальное состояние для большого количества процессов.

Сам факт наличия множества `S`-процессов не является признаком проблемы.

---

# 15. Состояние `D`

`D` — uninterruptible sleep.

Процесс ожидает завершения операции внутри ядра, часто связанной с I/O.

Типичные причины:

- дисковый I/O;
- проблемное сетевое хранилище;
- NFS;
- некоторые kernel locks;
- зависшие устройства или драйверы.

---

## 15.1. Почему `kill -9` может не помочь

`SIGKILL` нельзя обработать пользовательским обработчиком, однако это не означает, что любой процесс немедленно исчезает из списка задач.

Если задача находится в состоянии, в котором выполнение блокировано внутри ядра и не достигает точки, где ядро может завершить её, сигнал может оставаться ожидающим до выхода из соответствующего ожидания.

Поэтому:

```bash
kill -9 1234
```

не всегда мгновенно удаляет процесс из `ps`.

В таком случае следует искать первопричину:

```bash
dmesg
journalctl -k
```

а также исследовать подсистему, на которой заблокирован процесс.

---

## 15.2. `wchan` и kernel stack

Для PID `5678`:

```bash
cat /proc/5678/wchan
```

Можно посмотреть kernel stack:

```bash
cat /proc/5678/stack
```

Доступность и детализация `/proc/<PID>/stack` зависят от прав доступа и конфигурации ядра.

Эти данные помогают понять, где именно задача ожидает внутри kernel.

---

# 16. Состояние `Z`: Zombie

Zombie — это уже завершившийся процесс, для которого родительский процесс ещё не выполнил необходимый `wait()`/`waitpid()` и не забрал exit status.

Важно:

> Zombie не исполняется и не использует своё прежнее адресное пространство.

Однако ядро сохраняет минимальную информацию, необходимую родителю для получения статуса завершения.

---

## 16.1. Как возникает zombie

Упрощённая схема:

```text
Child
  │
  ├── exit()
  │
  ▼
Zombie
  │
  │ ждёт wait()/waitpid()
  ▼
Parent забирает exit status
  │
  ▼
Запись о процессе освобождается
```

Если родитель систематически не делает `wait()`, zombies могут накапливаться.

---

## 16.2. Как найти zombie

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
```

Удобно сразу смотреть PID и PPID:

```bash
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/ {print}'
```

---

## 16.3. Как убрать zombie

Нельзя «убить» zombie обычным `kill`, потому что процесс уже завершён.

Необходимо воздействовать на **родителя**:

1. выяснить `PPID`;
2. проверить, почему родитель не делает `wait()`;
3. корректно завершить/перезапустить родителя, если это необходимо;
4. убедиться, что дочерние процессы корректно reap-ятся.

При смене родителя процесс может быть усыновлён другим процессом, который выполняет соответствующую обработку дочерних процессов.

> **Практический вывод:** наличие одного zombie обычно менее важно, чем систематическое появление большого количества zombie. В последнем случае необходимо искать ошибку управления дочерними процессами.

# 17. Практический алгоритм диагностики

## Сценарий A: `Too many open files`

### Шаг 1. Найти процесс

```bash
ps aux
```

или:

```bash
systemctl status имя_сервиса
```

### Шаг 2. Посмотреть его лимит

```bash
cat /proc/<PID>/limits | grep "Max open files"
```

### Шаг 3. Посчитать FD

```bash
ls -1 /proc/<PID>/fd | wc -l
```

### Шаг 4. Посмотреть содержимое

```bash
lsof -p <PID>
```

### Шаг 5. Проверить глобальный лимит

```bash
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr
```

### Шаг 6. Проверить конфигурацию запуска

Для systemd:

```bash
systemctl cat имя_сервиса
```

И при необходимости:

```bash
systemctl show имя_сервиса -p LimitNOFILE
```

# 18. Сценарий B: высокая memory pressure

Проверить общую картину:

```bash
free -h
```

Затем:

```bash
cat /proc/meminfo
```

Проверить Swap:

```bash
swapon --show
```

Проверить faults:

```bash
sar -B 1
```

Посмотреть процессы, потребляющие память:

```bash
ps -eo pid,ppid,%mem,rss,comm --sort=-rss | head
```

Затем сопоставить:

```text
RAM usage
   │
   ├── Anonymous memory
   │
   ├── Page Cache
   │
   ├── Swap activity
   │
   └── Kernel memory
```

Не следует делать вывод «много Cached = мало памяти». Linux намеренно использует свободную RAM для cache.

# 19. Сценарий C: процессы зависают в `D`

Проверить:

```bash
ps -eo pid,ppid,stat,wchan:32,comm | awk '$3 ~ /^D/'
```

Для конкретного PID:

```bash
cat /proc/<PID>/wchan
cat /proc/<PID>/stack
```

Проверить kernel logs:

```bash
dmesg -T
```

или:

```bash
journalctl -k
```

Далее исследовать соответствующую подсистему:

```text
D-state
   │
   ├── local disk / NVMe
   ├── filesystem
   ├── NFS / network filesystem
   ├── device / driver
   └── kernel synchronization
```

Цель диагностики — не «убить D-процесс», а устранить ресурс или подсистему, на которой он заблокирован.

# 20. Краткая памятка команд

## File Descriptors

```bash
# Лимиты текущей shell-сессии
ulimit -Sn
ulimit -Hn

# Лимит конкретного процесса
cat /proc/<PID>/limits | grep "Max open files"

# Количество FD
ls -1 /proc/<PID>/fd | wc -l

# Открытые объекты
lsof -p <PID>

# Глобальные параметры
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr

# Лимит systemd
systemctl show <service> -p LimitNOFILE
```

## Virtual Memory

```bash
# Общая статистика
free -h

# Полная статистика ядра
cat /proc/meminfo

# Swap
swapon --show

# Swappiness
sysctl vm.swappiness

# VFS cache pressure
sysctl vm.vfs_cache_pressure

# Page faults
sar -B 1
```

## Processes

```bash
# Состояния процессов
ps -eo pid,ppid,stat,comm

# Zombie
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'

# D-state
ps -eo pid,ppid,stat,wchan:32,comm | awk '$3 ~ /^D/'

# Kernel wait point
cat /proc/<PID>/wchan

# Kernel stack
cat /proc/<PID>/stack

# Kernel log
dmesg -T
journalctl -k
```

# 21. Ключевые идеи

### 1. FD — это не файл

File Descriptor — это процессная ссылка на открытый объект ядра.

### 2. `EMFILE` и `ENFILE` — разные уровни проблемы

```text
EMFILE → лимит процесса
ENFILE → глобальный ресурс ядра
```

### 3. `ulimit` текущей shell-сессии не обязательно описывает сервис

Для живого процесса проверяйте:

```bash
/proc/<PID>/limits
```

### 4. systemd требует отдельного внимания

Для systemd-сервисов используйте:

```ini
LimitNOFILE=...
```

### 5. Page fault не равен ошибке

Это нормальный механизм виртуальной памяти.

### 6. Major fault связан с дорогим I/O

Особенно важен при анализе latency и memory pressure.

### 7. Page Cache — не «потерянная» RAM

Linux использует доступную память для ускорения файлового I/O.

### 8. Swap — не просто переключатель

`vm.swappiness` задаёт параметры политики reclaim и должен рассматриваться в контексте нагрузки.

### 9. `D` — повод искать первопричину

Если `kill -9` не устраняет проблему, исследуйте kernel wait, I/O, filesystem, storage и драйверы.

### 10. Zombie нельзя убить

Zombie уже завершён. Исправлять необходимо поведение его родительского процесса.

## Заключение

Понимание файловых дескрипторов, виртуальной памяти и состояний процессов позволяет диагностировать значительную часть проблем Linux не методом проб и ошибок, а по модели работы ядра.

Удобно мыслить на трёх уровнях:

```text
                    Linux Kernel
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   File Descriptors   Memory           Processes
        │                │                │
        ▼                ▼                ▼
     limits         page cache         scheduler
     sockets        anonymous          sleep
     files          swap               zombie
     pipes          page faults        I/O wait
```

Практическая диагностика строится вокруг одного принципа:

> **Сначала определить, какой ресурс или механизм ограничивает процесс, затем подтвердить это наблюдаемыми данными `/proc`, `sysctl`, `systemd`, `ps`, `lsof`, `sar` и kernel logs, и только после этого менять конфигурацию.**
