## Область документа

Сетевой путь (datapath) ядра Linux представляет собой многокомпонентную систему и не может быть корректно описан упрощённой линейной последовательностью вида `NIC → interrupt → TCP → socket → application`. Реальный datapath включает в себя аппаратные очереди, DMA, драйвер, подсистему NAPI, структуры `sk_buff`, программно-аппаратный маршутизатор пакетов (steering), протокольные уровни, подсистему Netfilter, маршрутизацию и очереди сокетов.

Для проектирования и диагностики высоконагруженных серверов необходимо отдельно рассматривать следующие компоненты:

1. Путь приёма (RX datapath) — от NIC до системных вызовов `recv()` / `read()`.
2. Путь передачи (TX datapath) — от системных вызовов `send()` / `write()` до NIC.
3. Очереди и точки возможной потери пакетов (drop points).
4. Механизмы распределения нагрузки между ядрами CPU.
5. Установление TCP-соединений (TCP connection establishment).
6. Очереди вызовов `listen()` / `accept()` (SYN backlog и accept queue).
7. Жизненный цикл состояний TCP (TCP state machine).
8. Управление памятью сокетов и автонастройка (socket memory & autotuning).
9. Фильтрация и отслеживание состояний (Netfilter / conntrack).
10. Аппаратные механизмы разгрузки (hardware offloads).
11. Сетевая виртуализация и изолированные пространства имён (network namespaces).
12. Инструменты наблюдения и методология корреляции метрик.

## Ментальная модель сетевого стека Linux

Концептуальная схема движения пакета при приёме (RX path):

```text
                 PCIe / DMA
                     │
                     ▼
              ┌─────────────┐
              │ NIC RX Ring │
              └──────┬──────┘
                     │
                IRQ / NAPI
                     │
                     ▼
              ┌─────────────┐
              │   Driver    │
              └──────┬──────┘
                     │
                 napi_poll
                     │
                     ▼
              ┌─────────────┐
              │   sk_buff   │
              └──────┬──────┘
                     │
              L2 / VLAN / Bridge
                     │
                     ▼
             IP / Routing / Hooks
                     │
                     ▼
              TCP / UDP / etc.
                     │
                     ▼
            Socket Receive Queue
                     │
                     ▼
              recv() / read()
                     │
                     ▼
                User Space
````

Траектория обработки пакета варьируется в зависимости от архитектуры и настроек системы:

- **XDP (eXpress Data Path):** позволяет обрабатывать или отбрасывать пакеты на уровне драйвера NIC до выделения структуры `sk_buff`.
- **Виртуальные устройства:** Bridge, VLAN, Bonding и туннельные интерфейсы добавляют дополнительные программные этапы обработки.
- **GRO (Generic Receive Offload):** объединяет входящие сегменты на ранних этапах обработки.
- **RPS (Receive Packet Steering):** переносит протокольную обработку на другой CPU.
- **Hardware Offloads:** переносят часть вычислений (контрольные суммы, сегментацию) непосредственно на сетевую карту.
- **Netfilter Hooks:** срабатывают в зависимости от топологии сети, правил фильтрации и контекста namespace.


## Аппаратный уровень приёма (RX Path)

### Кольцевой буфер описателей (RX Descriptor Ring)

Современные сетевые адаптеры используют одну или несколько аппаратных RX-очередей. Каждая очередь ассоциирована с кольцевым буфером описателей (descriptor ring).


```
NIC
 │
 ├── RX Queue 0 ── Descriptor Ring ──► CPU 0
 ├── RX Queue 1 ── Descriptor Ring ──► CPU 1
 ├── RX Queue 2 ── Descriptor Ring ──► CPU 2
 └── ...
```

В сетевом стеке следует четко разграничивать три сущности:

1. **Ring Descriptor** — метаданные, используемые аппаратурой и драйвером для управления передачей.
2. **Packet Buffer** — область оперативной памяти (RAM), куда контроллер NIC записывает данные пакета через DMA.
3. **`struct sk_buff` (skb)** — структура данных ядра Linux, представляющая пакет внутри сетевого стека.


Структура `sk_buff` является метаконтейнером: она хранит управляющие данные и ссылки на выделенные буферы памяти и фрагменты страниц (`skb_shared_info`), а не содержит весь полезный груз (payload) непосредственно внутри своего управляющего блока.

### Прямой доступ к памяти (DMA)

Сетевой адаптер передаёт данные входящих пакетов непосредственно в RAM с помощью Direct Memory Access (DMA), минимизируя участие CPU в процессе копирования данных:


```
NIC ──DMA──► RAM
       │
       └── Descriptor Status Interrupt ──► Driver
```

DMA снижает нагрузку на процессор, однако передача пакета сохраняет накладные расходы на:

- обработку дескрипторов и обновление программных метаданных;
- выполнение протокольного анализа и работу с подсистемой управления памятью (alloc/free, refcounting);
- промахи кэша (cache misses);
- выполнение проверок контрольных сумм и работу механизмов GRO/GSO;
- межъядерное взаимодействие при использовании RPS.


## Прерывания и подсистема NAPI

### Проблема обработки каждого пакета через IRQ

Генерация аппаратного прерывания (Hard IRQ) на каждый поступивший пакет при высокой интенсивности трафика приводит к перегрузке процессора контекстными переключениями (перегрузка прерываниями / interrupt storm).

### Механизм NAPI (New API)

NAPI сочетает первичные аппаратные прерывания с последующей пакетированной обработкой пакетов через опрос (polling):

```
NIC receives packets
       │
       ▼
Hardware Interrupt
       │
       ▼
Driver schedules NAPI (napi_schedule)
       │
       ▼
NAPI poll()
       ├── Process Packet Batch (up to budget)
       └── ...
       │
       ├── Budget exhausted  ──► Reschedule / Continue Poll
       └── Work completed    ──► Re-enable IRQ / Complete NAPI
```

При поступлении пакета генерируется аппаратное прерывание, драйвер регистрирует экземпляр NAPI и планирует вызов `softirq` (в частности `NET_RX_SOFTIRQ`). Затем ядро вызывает функцию опроса драйвера `poll()` с определенным лимитом обработанных пакетов (`budget`). Если драйвер осваивает весь выделенный бюджет, опрос продолжается в следующем цикле `softirq` без повторного включения аппаратных прерываний.

## Структура `sk_buff`

Структура `sk_buff` — ключевой элемент управления пакетами в ядре Linux.

```
struct sk_buff
       │
       ├── Metadata
       │    ├── Protocol
       │    ├── Network Device
       │    ├── Checksum State
       │    ├── Timestamps
       │    └── Socket Reference (sk)
       │
       └── Data Pointers
            ├── Linear Buffer (head, data, tail, end)
            └── Shared Info (skb_shared_info -> page fragments)
```

Разделение метаданных и буферов данных позволяет выполнять операции без лишнего копирования памяти (zero-copy routing, GRO/GSO, сплиттинг заголовков).

## Масштабирование приёма (RX Scaling: RSS, RPS, RFS)

### RSS (Receive Side Scaling)

**RSS** — аппаратный механизм сетевого адаптера. NIC вычисляет хэш-функцию от кортежа заголовков (например, IP/Port 4-tuple) и распределяет входящие потоки по независимым аппаратным RX-очередям, за которыми закреплены отдельные векторы прерываний CPU.

```
                    NIC
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
      RXQ0         RXQ1         RXQ2
        │            │            │
      CPU0         CPU1         CPU2
```

Диагностика RSS:

```
ethtool -l eth0    # Просмотр поддерживаемого и активного количества очередей
ethtool -x eth0    # Просмотр таблицы индирекции RSS
ethtool -S eth0    # Статистика по конкретным RX/TX очередям
cat /proc/interrupts
```

### RPS (Receive Packet Steering)

**RPS** — программный аналог RSS, реализованный на уровне ядра Linux. RPS позволяет распределить обработку протокольного стека между ядрами CPU, если сетевая карта имеет только одну аппаратную очередь или количество очередей меньше числа ядер CPU.

```
NIC / Driver (1 RX Queue)
        │
Kernel computes Flow Hash
        │
Target CPU Inter-Processor Interrupt (IPI)
        │
Target CPU Backlog Processing (NET_RX_SOFTIRQ)
```

Настройка битовой маски процессоров для очереди `rx-0`:

```sh
cat /sys/class/net/eth0/queues/rx-0/rps_cpus
echo "ff" > /sys/class/net/eth0/queues/rx-0/rps_cpus  # Активация на первых 8 ядрах (CPU0-CPU7)
```

_Примечание:_ Маска CPU должна настраиваться с учётом топологии NUMA-узлов.

### RFS (Receive Flow Steering)

**RFS** расширяет RPS, направляя обработку пакетов на ядро CPU, на котором выполняется пользовательский поток приложения, читающий данный сокет. Это повышает локальность данных в L1/L2-кэшах процессора.

## Масштабирование передачи (XPS и TX Scaling)

**XPS (Transmit Packet Steering)** — механизм выборки аппаратной TX-очереди при отправке данных.

```
Application Thread
       │
   Socket / TCP
       │
XPS Mapping Logic ──► Selects TX Queue
       │
  NIC TX Ring
       │
  Physical Wire
```

Настройка XPS позволяет закрепить отправку данных с определённых CPU за конкретными TX-очередями, минимизируя блокировки (lock contention) в драйвере.

## Статистика подсистемы: `/proc/net/softnet_stat`

Служебный файл `/proc/net/softnet_stat` содержит информацию об обработке сетевых прерываний в разрезе каждого CPU (каждая строка соответствует ядру процессора).

Основные поля (слева направо):

1. **Processed:** Количество обработанных пакетов.

2. **Dropped:** Количество пакетов, сброшенных из-за переполнения входной очереди `netdev_max_backlog`.

3. **Squeezed:** Количество раз, когда обработка NAPI завершилась по исчерпанию бюджета (`netdev_budget` или time limit) при наличии оставшихся пакетов.

## Параметр `netdev_max_backlog`

Параметр `net.core.netdev_max_backlog` определяет максимальный размер входной очереди пакетов для ядра CPU, когда драйвер передаёт пакеты в стек ядра (в частности при работе RPS).

```sh
sysctl net.core.netdev_max_backlog
```

Увеличение этого значения позволяет сглаживать кратковременные всплески трафика (bursts), но приводит к увеличению задержек (latency) и расходу оперативной памяти. Увеличение очереди не решает проблему недостатка вычислительной мощности CPU.

## Механизмы оптимизации: GRO, GSO и TSO

### GRO (Generic Receive Offload)

Программная оптимизация приёма: ядро объединяет несколько последовательных входящих TCP/IP-сегментов одного потока в один крупный составной пакет до передачи его в протокольный стек, снижая накладные расходы на обработку заголовков.

### GSO (Generic Segmentation Offload)

Программная оптимизация передачи: ядро формирует пакет большого размера (вплоть до 64 КБ) и спускает его через стек до самого последнего момента пред-драйверной обработки, где производит сегментацию на мелкие MTU-пакеты, если сетевой адаптер не поддерживает TSO.

### TSO (TCP Segmentation Offload)

Аппаратная разгрузка сегментации: ядро передает крупный стек данных сокетного буфера непосредственно в сетевую карту, а NIC самостоятельно разбивает его на отдельный набор кадров Ethernet/TCP с генерацией нужных заголовков.

## Разгрузка вычисления контрольных сумм (Checksum Offload)

При включенном Checksum Offload вычисление контрольных сумм IP/TCP/UDP переносится на аппаратный процессор NIC. Ядро помечает метаданные пакета в `sk_buff` флагами (например, `CHECKSUM_PARTIAL`), избавляя ЦПУ от необходимости последовательного чтения всех байт кадра.

Проверка состояния offload-механизмов:

```sh
ethtool -k eth0
```

## Взаимодействие с подсистемой Netfilter

Подсистема Netfilter предоставляет точки перехвата (hooks) на разных этапах прохождения пакета:

```
       [Ingress / PREROUTING]
                 │
                 ▼
          Routing Decision
          /              \
         ▼                ▼
  [INPUT Hook]      [FORWARD Hook]
         │                │
   Local Socket           │
         │                ▼
  [OUTPUT Hook]    [POSTROUTING Hook]
         \                /
          ▼              ▼
           [Egress / NIC]
```

Netfilter выполняет функции государственного файрвола (tables filter), трансляции адресов (NAT) и отслеживания соединений (conntrack), что добавляет задержки на обработку каждого кадра.

## Подсистема Conntrack (Connection Tracking)

Conntrack фиксирует состояния сетевых сессий. При превышении лимита отслеживаемых соединений ядро начинает отбрасывать входящие пакеты.

Проверка текущего состояния и лимитов:

```sh
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
```

Индикатор переполнения таблицы в системном журнале:

```sh
nf_conntrack: table full, dropping packet
```

## Установление TCP-соединения (Three-Way Handshake)

```
Client                                  Server
  │                                       │
  │ ────────────── SYN ─────────────────► │  (Попадает в SYN Backlog)
  │                                       │
  │ ◄─────────── SYN-ACK ──────────────── │
  │                                       │
  │ ────────────── ACK ─────────────────► │  (Переносится в Accept Queue)
  │                                       │
ESTABLISHED                             ESTABLISHED (Ожидает accept())
```

## Структура очередей подключения: SYN Backlog и Accept Queue

В ядре Linux логически разделены две очереди устанавливаемых соединений:

1. **SYN Backlog (Incomplete Connection Queue):** Содержит соединения, находящиеся в процессе handshake (состояние `SYN_RECV`). Размер регулируется параметром `net.ipv4.tcp_max_syn_backlog`.
2. **Accept Queue (Completed Connection Queue):** Содержит полностью установленные соединения (состояние `ESTABLISHED`), ожидающие вызова `accept()` со стороны приложения.

Ограничение размера Accept Queue определяется как:

$$\text{Effective Accept Queue Limit} = \min(\text{backlog}_{\text{listen()}}, \text{net.core.somaxconn})$$

_Примечание:_ Начиная с ядра Linux 5.4, значение `net.core.somaxconn` по умолчанию составляет `4096` (в более старых версиях ядра применялось значение `128`).

## Анализ переполнения очередей подключения

Проверка системных ограничений:

```sh
sysctl net.ipv4.tcp_max_syn_backlog
sysctl net.core.somaxconn
```

Проверка состояния сокетов слушающего процесса с помощью `ss`:

```sh
ss -lntp
```

В выводе команды `ss -lnt` для слушающих (LISTEN) сокетов:

- `Send-Q` показывает максимальный размер Accept Queue (`backlog`).
- `Recv-Q` показывает текущее количество соединений, ожидающих вызова `accept()`.

Если `Recv-Q > Send-Q`, происходят переполнения очереди приёма и отброс пакетов (или отправка RST в зависимости от настроек).

## Защитный механизм SYN Cookies

Параметр `net.ipv4.tcp_syncookies` активирует механизм генерации криптографических последовательностей `seq` в ответе `SYN-ACK`, что позволяет не расходовать память на хранение состояния в SYN Backlog при атаках типа SYN Flood.

```sh
sysctl net.ipv4.tcp_syncookies
```

_Важное замечание:_ SYN Cookies — защитный механизм от досаждающих атак (DoS), а не средство оптимизации производительности штатной системы. При включении SYN Cookies теряется возможность использования ряда расширенных опций TCP (например, больших окон SACK, если они не запечены в MSS-значения).

## Повторные попытки `tcp_synack_retries`

Параметр `net.ipv4.tcp_synack_retries` задает количество повторных отправок пакета `SYN-ACK` для пассивных TCP-соединений при отсутствии финального `ACK` от клиента.

```sh
sysctl net.ipv4.tcp_synack_retries
```

Снижение данного параметра помогает быстрее освобождать ресурсы при сбоях в сети или нелегитимных подключениях.

## Поведение при переполнении очереди: `tcp_abort_on_overflow`

Параметр `net.ipv4.tcp_abort_on_overflow`:

- `0` (по умолчанию): При переполнении Accept Queue ядро игнорирует входящий финальный `ACK` от клиента, рассчитывая на его повторную передачу после освобождения места в очереди.
- `1`: Ядро немедленно отправляет клиенту флаг `RST`, сбрасывая соединение.

## Управление буферами сокета (Socket Memory & Autotuning)

Размеры буферов чтения и записи задаются векторами из трех значений: `[min, default, max]`.

```sh
sysctl net.ipv4.tcp_rmem
sysctl net.ipv4.tcp_wmem
```

Параметр `net.ipv4.tcp_moderate_rcvbuf` включает автонастройку (autotuning) буфера приёма TCP: ядро автоматически увеличивает или уменьшает выделяемую сокету память в зависимости от доступных ресурсов и пропускной способности канала (RTT / BDP).

## Диагностика сокетов с помощью `ss`

Команда `ss` (Socket Statistics) является современным средством инспекции состояния сокетов, заменившим утилиту `netstat`.

Ключевые команды:

```sh
ss -s                        # Сводная статистика по типам сокетов
ss -lntp                     # Список слушающих TCP-сокетов с фиксацией PID
ss -tan state established     # Активные установленные соединения
ss -tan state time-wait      # Соединения в состоянии TIME_WAIT
ss -tan state close-wait     # Соединения в состоянии CLOSE_WAIT
ss -tm                       # Подробные данные по расходу памяти сокетами (skmem)
```

Вывод `ss -tm` детализирует распределение памяти сокета: `rmem_alloc`, `rcv_buf`, `wmem_alloc`, `snd_buf`, `fwd_alloc`.

## Состояния TCP (TCP Finite State Machine)

Состояния протокола TCP:

- `LISTEN` — ожидание запросов на подключение.
- `SYN-SENT` — отправлен первичный запрос `SYN`.
- `SYN-RECV` — получен `SYN`, отправлен `SYN-ACK`, ожидание `ACK`.
- `ESTABLISHED` — соединение установлено, идет передача данных.
- `FIN-WAIT-1` — инициативно отправлен `FIN`, ожидание `ACK` или `FIN`.
- `FIN-WAIT-2` — получен `ACK` на свой `FIN`, ожидание `FIN` от удаленной стороны.
- `CLOSE-WAIT` — получен `FIN` от удаленной стороны, локальное приложение еще не закрыло сокет.
- `CLOSING` — обе стороны одновременно инициировали закрытие.
- `LAST-ACK` — получен `FIN`, отправлен финальный `ACK`, ожидание подтверждения.
- `TIME-WAIT` — активное закрытие завершено, ожидание истечения таймера (2MSL) для защиты от блуждающих пакетов.
- `CLOSED` — сокет полностью освобожден.

## Причины накопления `CLOSE_WAIT`

Состояние `CLOSE_WAIT` возникает при пассивном закрытии:

```
Peer                       Local System / Application
 │                                     │
 ├────────────── FIN ────────────────► │
 │                                     │ (Ядро ответит ACK автоматически)
 ◄────────────── ACK ─────────────────┤
 │                                     │
 │                                 CLOSE_WAIT
 │                                     │
 │                                     │  Приложение должно вызвать close()!
 │                                     ▼
 ◄────────────── FIN ───────────────── ┤ (После close())
```

**Причина застревания сокетов в `CLOSE_WAIT`:** Ошибка в логике приложения. Приложение получило сигнал о закрытии сокета от клиента (вызов `read()` вернул `0` или EOF), но не выполнило вызов `close()` со своей стороны, либо соответствующий поток/горутина заблокировалась. Настройки ядра Linux не могут принудительно очистить сокеты в состоянии `CLOSE_WAIT`.

## Назначение и особенности `TIME_WAIT`

Состояние `TIME_WAIT` возникает на стороне, которая инициировала закрытие соединения (**Active Close**).

Назначение:

1. Гарантия надежной доставки последнего `ACK` удаленной стороне.
2. Предотвращение наложения старых дублированных пакетов (stray packets) из предыдущего соединения на новое соединение с тем же кортежем адресов (5-tuple).

Просмотр таймеров `TIME_WAIT`:

```sh
ss -o state time-wait
```

## Истощение локальных портов (Ephemeral Ports)

При большом числе кратковременных соединений (High Connection Churn) активное закрытие приводит к накоплению сокетов в состоянии `TIME_WAIT`, что может вызвать исчерпание диапазона локальных портов для исходящих подключений.

Симптом: Появление системной ошибки `EADDRNOTAVAIL` (`Cannot assign requested address`).

## Параметр `ip_local_port_range`

Диапазон локальных эфемерных портов, используемых для исходящих подключений:

```sh
sysctl net.ipv4.ip_local_port_range
```

Расширение диапазона:

```sh
sysctl -w net.ipv4.ip_local_port_range="10240 65535"
```

## Параметр `tcp_tw_reuse`

Параметр `net.ipv4.tcp_tw_reuse` разрешает повторное использование сокетов в состоянии `TIME_WAIT` для новых исходящих подключений, если это безопасно с точки зрения меток времени TCP (TCP Timestamps / RFC 1323).

```sh
sysctl net.ipv4.tcp_tw_reuse
```

## Устаревший параметр `tcp_tw_recycle`

Параметр `net.ipv4.tcp_tw_recycle` **полностью удален из ядра Linux** (начиная с версии 4.12), так как ломал соединения для клиентов, находящихся за общим NAT (из-за несовпадения меток времени от разных хостов). Включение этого параметра в современных системах невозможно, а упоминания в документации являются устаревшими.

## Сравнительный анализ `CLOSE_WAIT` и `TIME_WAIT`

|**Характеристика**|**CLOSE_WAIT**|**TIME_WAIT**|
|---|---|---|
|**Инициатор закрытия**|Удалённая сторона (Passive Close)|Локальная сторона (Active Close)|
|**Причина возникновения**|Приложение не вызвало `close()` сокет|Нормальное завершение протокола TCP|
|**Локализация проблемы**|Ошибка в коде приложения / deadlock|Высокая частота создания коротких сессий|
|**Влияние таймеров ядра**|Таймер отсутствует (висит бессрочно)|Управляется таймером ядра (2MSL)|
|**Решение**|Исправление утечек сокетов в коде|Использование Keep-Alive, Connection Pools, `tcp_tw_reuse`|

## Расход памяти сокетами: Детализация `ss -m`

Пример структуры вывода параметров памяти:

```
skmem:(r<rmem_alloc>,rb<rcv_buf>,t<wmem_alloc>,tb<snd_buf>,f<fwd_alloc>,w<wmem_queued>,o<optmem>,bl<backlog>,d<drops>)
```

- `rmem_alloc` — объём памяти, фактически выделенный под байты данных приёма и метаданные.

- `rcv_buf` — жесткий лимит выделения памяти под буфер приёма сокета.

- `fwd_alloc` — память, зарезервированная под сокет «наперед» (pre-allocated) в рамках аллокатора страниц.

## Ограничения линейного масштабирования буферов

Бесконтрольное увеличение `tcp_rmem` и `tcp_wmem` без анализа скорости обработки данных приложением приводит к:

1. Повышенному расходу RAM (возможен вызов OOM Killer).

2. Явлению Bufferbloat — сглаживанию потерь ценой кратного роста задержек (RTT) и ухудшению работы алгоритмов управления перегрузкой (Congestion Control).


## Распределение аппаратных прерываний (IRQ Affinity)

Назначение векторов прерываний конкретным ядрам CPU настраивается через подсистему `procfs`:

```sh
cat /proc/interrupts
cat /proc/irq/<IRQ_NUM>/smp_affinity_list
```

Принудительная привязка вектора IRQ к ядру №0:

```sh
echo 0 > /proc/irq/<IRQ_NUM>/smp_affinity_list
```

## Служба `irqbalance`

Демон `irqbalance` автоматически распределяет прерывания по ядрам CPU для балансировки нагрузки. В высоконагруженных системах с высокими требованиями к задержкам (Low-Latency Worker) службу `irqbalance` часто отключают, а прерывания сетевых карт и процессы приложения вручную привязывают к изолированным ядрам процессора (CPU Pinning).

## Влияние архитектуры NUMA

В многопроцессорных системах (NUMA) сетевой адаптер PCIe физически подключен к конкретному NUMA-узлу (CPU socket).

```
  [NIC PCIe Controller]
           │
     (PCIe Interconnect)
           │
    [NUMA Node 0 RAM]  ◄─── Minimal Latency ───►  [CPU Node 0]
           ▲
           │ (UPI / Inter-Socket Link — High Latency)
           ▼
    [NUMA Node 1 RAM]  ◄─────────────────────────►  [CPU Node 1]
```

Для достижения максимальной производительности необходимо организовывать обработку прерываний, выделение памяти и выполнение процессов приложения в пределах одного NUMA-узла.

## Сетевые пространства имён (Network Namespaces)

Network Namespace (`netns`) изолирует сетевой стек ядра Linux, предоставляя обособленные экземпляры:

- сетевых интерфейсов;
- таблиц маршрутизации (IPv4/IPv6);
- правил Netfilter / iptables;
- сокетных таблиц и параметров `sysctl`.

Управление простанствами имён:

```sh
ip netns list
ip netns exec <ns_name> ip addr
```

## Виртуальные интерфейсы `veth`

Пара виртуальных интерфейсов (`veth pair`) выступает в роли программного пачкорда, соединяющего два изолированных пространства имён или подключающего namespace к виртуальному мосту (Bridge).

```
[ Network Namespace A ]                   [ Network Namespace B ]
    veth-a-eth0  ◄════════ Virtual Cable ════════►  veth-b-eth0
```

## Точки сброса пакетов (Drop Points)

Пакет может быть отброшен на различных этапах прохождения:

```
1. NIC Hardware Drop   ──► Нехватка аппаратных буферов / CRC Errors
2. RX Ring Overflow    ──► Нехватка RX descriptors
3. Driver / NAPI       ──► Переполнение ring-buffer
4. SoftIRQ Backlog     ──► Переполнение netdev_max_backlog
5. Netfilter / Firewall──► Правила DROP / REJECT / Conntrack table full
6. Routing Layer       ──► No route to host / Unreachable
7. TCP Protocol Layer  ──► PAWS Failures, Checksum Mismatch, Invalid State
8. Socket Buffer       ──► Overflown Receive Buffer
9. Application Level   ──► Overflowed Application Listen Backlog
```

## Недопустимость слепой настройки параметров `sysctl`

Изменение параметров конфигурации ядра Linux без проведения измерений категорически не рекомендуется.

Некорректная последовательность:

```
Проблема ──► Слепое увеличение буферов ──► Отключение offload ──► Ожидание успеха
```

Корректная методология:


## Типовые сценарии устранения неполадок (Runbook)

### Сценарий A: Высокий уровень потерь на приёме (RX Drops)

1. Проверить `ethtool -S eth0` на наличие `rx_missed_errors` или `rx_discards_phy`.
2. Проверить `/proc/net/softnet_stat` (поля 2 и 3).
3. Проверить распределение прерываний по ядрам CPU (`/proc/interrupts`).
4. При необходимости увеличить размеры RX ring-буфера (`ethtool -G`) или скорректировать распределение RSS/RPS.

### Сценарий B: Накопление сокетов в состоянии `SYN_RECV`

1. Проверить размер SYN Backlog (`net.ipv4.tcp_max_syn_backlog`).
2. Проверить статус активации `net.ipv4.tcp_syncookies`.
3. Оценить задержку сети (RTT) и процент потерь пакетов от клиентов.

### Сценарий C: Рост сокетов в состоянии `CLOSE_WAIT`

1. Определить процесс-владелец: `ss -tanp state close-wait` или `lsof -iTCP -sTCP:CLOSE_WAIT`.
2. Выполнить отладку кода приложения в части корректного вызова `close()` сокета при получении `EOF`/`0` байт.

### Сценарий D: Ошибка `Cannot assign requested address`

1. Проверить лимиты эфемерных портов (`net.ipv4.ip_local_port_range`).
2. Включить `net.ipv4.tcp_tw_reuse`.
3. Перевести взаимодействия приложения на пулы постоянных соединений (HTTP Keep-Alive, DB Connection Pools).

## Понятие высокой нагрузки (High Load)

Нагрузка не описывается исключительно абсолютным значением числа пакетов в секунду (PPS) или полосой пропускания (BPS). Высокая нагрузка представляет собой состояние исчерпания конкретного лимитирующего ресурса системы:

- Вычислительная мощность CPU (SoftIRQ / User CPU saturation).
- Пропускная способность системной шины или памяти (PCIe / Memory Bandwidth).
- Дескрипторы очередей (RX/TX Ring descriptors).
- Память сокетов и системных буферов.
- Лимит отслеживаемых соединений Conntrack.
- Количество свободного пространства в эфемерных портах.
- Скорость обработки запросов приложением (Application Read/Accept Rate).

## Сравнение интенсивности пакетов (PPS) и объема данных (BPS)

Различные типы профилей нагрузки оказывают разное воздействие на компоненты системы:

```
Профиль A: High PPS / Low BPS (например, 1 000 000 pps × 64 bytes)
  ──► Высокие накладные расходы на каждый пакет (SoftIRQ, обработка skb, прерывания).
  ──► Ограничением является вычислительная мощность процессора.

Профиль B: Low PPS / High BPS (например, 10 000 pps × 9000 bytes Jumbo Frames)
  ──► Низкая нагрузка на процессор при высокой утилизации шины данных и памяти.
  ──► Ограничением является пропускная способность интерфейсов и RAM.
```

## Соотношение задержки (Latency) и пропускной способности (Throughput)

Увеличение размеров очередей повышает общую пропускную способность системы при импульсной нагрузке, однако приводит к росту задержек на буферизацию (Queueing Delay). Формирование профиля настроек системы требует соблюдения баланса в рамках целевых параметров SLO (Service Level Objectives).

## Недопустимость применения фиксированных наборов системных параметров

Шаблоны оптимизаций вида:

```Ini, TOML
net.core.netdev_max_backlog = 10000
net.core.netdev_budget = 600
net.ipv4.tcp_max_syn_backlog = 16384
net.core.somaxconn = 16384
```

не должны применяться без предварительного проведения нагрузочного тестирования и учета условий конкретной среды (версия ядра, модель NIC, объём RAM, количество ядер CPU, топология NUMA, профиль приложения).

## Минимальный набор метрик наблюдаемости (Observability Set)

Продуктивный хост под управлением Linux должен передавать в мониторинг следующий набор метрик:

1. **NIC Metrics:** `rx/tx_packets`, `rx/tx_bytes`, `rx/tx_errors`, `rx/tx_dropped`, `rx_missed_errors`.
2. **CPU Metrics:** `%softirq`, `%user`, `%system`, `%steal`, распределение прерываний по ядрам.
3. **TCP State Counters:** Состояние сокетов (`ESTABLISHED`, `SYN_RECV`, `TIME_WAIT`, `CLOSE_WAIT`), количество повторных отправок (`tcp_retrans_segs`).
4. **Socket Memory Metrics:** Объем выделенной сокетам памяти.
5. **Conntrack Metrics:** `nf_conntrack_count`, `nf_conntrack_max`.
6. **Application Metrics:** Rate вызовов `accept()`, длительность цикла обработки (Event Loop Latency), количество открытых файловых дескрипторов (FDs).

## Принципы корреляции метрик

Связывание симптомов помогает точно локализовать узкие места системы:

```
Рост PPS ──► Рост CPU %softirq ──► Рост rx_dropped ──► Задержка приложения
  Вывод: Бутлнек на уровне программной обработки пакетов процессором (SoftIRQ / NAPI).

Рост SYN_RECV ──► Переполнение Accept Queue (Listen Overflow) ──► 100% User CPU
  Вывод: Проблема в производительности приложения, которое не успевает выполнять accept().
```

## Распространённые ошибочные суждения

1. **«Обработка NAPI всегда происходит на том же ядре CPU, которое приняло аппаратное прерывание»** — Неверно. Механизмы RPS переносят выполнение `NET_RX_SOFTIRQ` на другие ядра.
2. **«Параметр `netdev_max_backlog` задает размер кольцевого буфера NIC»** — Неверно. Ring buffer настраивается через драйвер (и утилиту `ethtool`), а `netdev_max_backlog` определяет размер входной программной очереди ЦПУ.
3. **«Состояние `CLOSE_WAIT` автоматически сбрасывается ядром по тайм-ауту»** — Неверно. Переход сокета из состояния `CLOSE_WAIT` возможен только после явного вызова `close()` со стороны приложения.
4. **«Параметр `tcp_syncookies` предназначен для оптимизации производительности при высоких нагрузках»** — Неверно. Это защитный механизм fallback-режима при атаках.

## Сводная справочная таблица механизмов

|**Механизм**|**Уровень**|**Назначение**|
|---|---|---|
|**RX Ring**|Hardware / Driver|Кольцевой буфер дескрипторов для DMA-передачи кадра|
|**DMA**|Hardware|Прямая запись данных из сетевой карты в RAM|
|**NAPI**|Driver / Kernel|Опрос сетевой карты батчами с отключением IRQ|
|**`sk_buff`**|Kernel|Основная структура метаданных пакета в ядре|
|**RSS**|NIC Hardware|Распределение входящих потоков по аппаратным очередям|
|**RPS**|Kernel Software|Программная балансировка пакетов по ядрам CPU|
|**RFS**|Kernel Software|Направление пакетов на ядро CPU, где запущен сокет|
|**XPS**|Kernel / Driver|Выбор TX-очереди при отправке пакета|
|**GRO**|Kernel Software|Объединение входящих TCP-сегментов|
|**TSO**|NIC Hardware|Аппаратное разбиение крупных TCP-блоков при отправке|
|**Netfilter**|Kernel|Модуль фильтрации, трансляции адресов (NAT) и сбора состояний|
|**Conntrack**|Kernel / Netfilter|Таблица отслеживания состояний сетевых соединений|
|**SYN Backlog**|TCP Subsystem|Очередь недоустановленных соединений (`SYN_RECV`)|
|**Accept Queue**|Socket / TCP|Очередь готовых соединений (`ESTABLISHED`), ожидающих `accept()`|
|**`ss`**|Userspace|Инструмент инспекции статистики сокетов|
