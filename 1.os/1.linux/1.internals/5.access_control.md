# Linux Access Control: DAC, ACL, capabilities, MAC, LSM и практическая диагностика

> **Статус:** систематизированная техническая документация  
> **Предмет:** Unix permissions, VFS permission checks, special bits, POSIX ACL, capabilities, file capabilities, setuid/setgid, sticky bit, umask, ownership, LSM, SELinux/AppArmor, seccomp и диагностика.
>
> **Точность:** конкретное решение о доступе зависит не только от `rwx`. В Linux результат может определяться DAC, ACL, capabilities, LSM, mount options, filesystem semantics, namespace context и другими проверками.

---

## 1. Общая модель

Классическая модель Unix основана на **DAC — Discretionary Access Control**: владелец объекта и связанные с ним ACL/permissions определяют базовый доступ.

Но современный Linux security path шире:

```text
process credentials
       │
       ▼
  DAC permissions
       │
       ├── mode bits
       └── POSIX ACL
       │
       ▼
 capabilities
       │
       ▼
 LSM security hooks
       │
       ├── SELinux
       ├── AppArmor
       ├── Smack
       └── other LSMs
       │
       ▼
 filesystem / namespace / mount semantics
       │
       ▼
     allow / deny
````

Это концептуальная схема: точный порядок и набор hooks зависят от операции и подсистемы.

Linux capabilities разделяют традиционные root privileges на отдельные привилегии, а LSM добавляет дополнительные security checks. citeturn0search0

# 2. Unix mode bits

У файла есть:

```
owner
group
mode
```

Например:

```
-rwxr-x---
```

разбивается на:

```
owner  = rwx
group  = r-x
other  = ---
```

Числовая запись:

```
0750
```

где:

```
7 = rwx
5 = r-x
0 = ---
```

---

# 3. Значение `r`, `w`, `x`

## 3.1. Обычный файл

|Право|Значение|
|---|---|
|`r`|читать содержимое|
|`w`|изменять содержимое|
|`x`|выполнять файл как программу|

`x` не означает «можно открыть файл».

---

## 3.2. Директория

Для директории значения принципиально другие:

|Право|Значение|
|---|---|
|`r`|читать список directory entries|
|`w`|создавать/удалять/переименовывать entries при наличии необходимых условий|
|`x`|проходить через directory / выполнять lookup/search|

Поэтому:

```
r + x
```

для директории обычно означает:

> можно перечислять содержимое и обращаться к объектам внутри, если остальные компоненты path также разрешают traversal.

---

# 4. Path traversal

Для:

```
/a/b/c/file
```

процесс должен иметь возможность пройти необходимые directory components.

Например:

```
/a        x
/a/b      x
/a/b/c    x
file      соответствующее право
```

Недостаточно иметь `r` на конечном файле, если процесс не может пройти directory path.

Это одна из наиболее частых причин:

```
Permission denied
```

при apparently correct permissions самого файла.

---

# 5. Как выбирается класс permissions

Упрощённо для обычного DAC mode check:

```
effective UID == file UID?
        │
       yes ──► owner bits
        │
       no
        │
effective/supplementary groups match file group?
        │
       yes ──► group class
        │
       no ──► other class
```

Важно:

> group bits и other bits не «складываются» одновременно.

Если процесс классифицирован как owner, используются owner permissions.

---

# 6. Supplementary groups

Процесс имеет:

```
real UID
effective UID
saved set-user-ID
filesystem UID
real/effective/supplementary groups
```

Для практической диагностики чаще всего полезно:

```
id
```

Например:

```
uid=1000(user)
gid=1000(user)
groups=1000(user),10(wheel),998(docker)
```

Наличие supplementary group может изменить результат DAC group check.

# 7. `stat`: основной инструмент

```
stat file
```

или компактно:

```
stat -c '%A %a %U %G %n' file
```

Например:

```
-rw-r----- 640 alice developers config
```

Полезные поля:

```
%A  symbolic mode
%a  octal mode
%U  owner name
%G  group name
%n  path
```

# 8. Octal representation

Базовые bits:

```
r = 4
w = 2
x = 1
```

Например:

```
rwx = 4 + 2 + 1 = 7
rw- = 4 + 2     = 6
r-x = 4 +     1 = 5
r-- = 4         = 4
-w- =     2     = 2
--x =         1 = 1
--- = 0
```

Поэтому:

```
0754
```

означает:

```
owner: rwx
group: r-x
other: r--
```

---

# 9. Special mode bits

Полная octal запись может включать:

```
special bits + owner + group + other
```

Основные special bits:

```
04000 SUID
02000 SGID
01000 sticky
```

Например:

```
4755
2755
1777
```

---

# 10. SUID

SUID (`04000`) на executable file влияет на credentials процесса при `execve()`.

Классический пример:

```
ls -l /usr/bin/passwd
```

может показывать:

```
-rwsr-xr-x
```

Буква:

```
s
```

в owner execute position означает установленный SUID при наличии execute bit.

Важно:

> SUID не означает «процесс становится root вообще во всех смыслах».

Effective credentials и capabilities формируются по правилам `execve()`, file ownership, file capabilities, securebits и других механизмов.

---

# 11. Почему SUID опасен

SUID executable получает особые credentials при запуске.

Если privileged SUID binary содержит exploitable vulnerability, ошибка может привести к privilege escalation.

Поэтому полезно искать:

```
find / -xdev -perm -4000 -type f -ls 2>/dev/null
```

Но список SUID binaries сам по себе не означает наличие уязвимости.

Нужно анализировать:

```
что делает binary
какие capabilities/credentials получает
какие inputs контролирует пользователь
какие security boundaries существуют
```

---

# 12. SGID на файле

SGID (`02000`) на executable file исторически связан с effective group semantics.

Однако поведение зависит от filesystem/kernel security semantics и не должно описываться как простое универсальное правило:

> «процесс всегда получает group файла».

Для современных Linux security explanations важно отдельно рассматривать SGID executable и SGID directory.

---

# 13. SGID на директории

Это один из наиболее практически полезных special bits.

Если directory имеет:

```
drwxrws---
```

новые entries обычно наследуют group directory согласно filesystem semantics.

Пример:

```
mkdir /srv/team
chgrp developers /srv/team
chmod 2770 /srv/team
```

Получаем:

```
/srv/team
    │
    ├── file-a  developers
    ├── file-b  developers
    └── subdir  developers
```

Это удобно для shared project directories.

---

# 14. Sticky bit

Sticky bit (`01000`) на directory ограничивает удаление/rename entries.

Классический пример:

```
drwxrwxrwt /tmp
```

При наличии sticky bit пользователь обычно не может удалить или переименовать чужой entry только на основании write permission directory.

Проверка:

```
ls -ld /tmp
```

---

# 15. Удаление файла определяется directory permissions

Очень важная VFS-ловушка:

```
chmod 000 file
```

не означает:

```
никто не может удалить file
```

Удаление directory entry связано прежде всего с permissions родительской directory и дополнительными checks.

Поэтому:

```
directory = 0777
file      = 0000
```

не запрещает владельцу/процессу с соответствующими directory permissions удалить entry, если отсутствует другое ограничение.

---

# 16. `chmod`

Символьный режим:

```
chmod u+r file
chmod g-w file
chmod o-x file
```

Абсолютный:

```
chmod 0640 file
```

Комбинированный:

```
chmod u=rw,g=r,o= file
```

---

# 17. `chmod -R`: осторожно

Опасный пример:

```
chmod -R +x /srv/app
```

Он может добавить execute permission обычным files.

Часто нужен:

```
chmod -R +X /srv/app
```

`X` имеет специальную семантику: execute добавляется directory и files, которые уже имеют execute permission (согласно `chmod` semantics).

Но даже `+X` не следует применять рекурсивно без понимания исходных permissions.

---

# 18. `umask`

`umask` задаёт bits, которые не должны присутствовать в default permissions при создании объектов.

Проверка:

```
umask
```

Например:

```
0022
```

Важно:

> `umask` не является простым `mode = requested_mode - umask` во всех деталях.

Корректнее рассматривать его как mask, clearing соответствующие permission bits из requested creation mode.

---

# 19. Пример `umask`

Если приложение создаёт файл с requested mode:

```
0666
```

и:

```
umask = 0022
```

получаем:

```
0644
```

Для directory requested mode обычно:

```
0777
```

и при `0022`:

```
0755
```

---

# 20. POSIX ACL

POSIX ACL расширяют классическую модель:

```
owner
group
other
```

дополнительными entries для отдельных users/groups.

Например:

```
user::rwx
user:alice:rwx
group::r-x
group:developers:rwx
mask::rwx
other::---
```

ACL позволяют выражать правила, которые невозможно представить только тремя mode classes. citeturn0search2

---

# 21. Access ACL и Default ACL

У directory могут существовать:

### Access ACL

Определяет permissions самой directory.

### Default ACL

Используется как наследуемая ACL policy для новых filesystem objects, создаваемых в directory. citeturn0search2

Проверка:

```
getfacl /srv/team
```

---

# 22. ACL mask

Очень важная часть POSIX ACL:

```
mask
```

Mask ограничивает effective permissions для:

```
named users
named groups
owning group
```

но не для owner и other entries.

Например:

```
user:alice:rwx
mask::r-x
```

effective permission для Alice будет:

```
r-x
```

а не `rwx`.

`getfacl` показывает effective permissions, что помогает не ошибиться при диагностике. citeturn0search2

---

# 23. Почему `ls -l` недостаточно для ACL

Если:

```
ls -l file
```

показывает:

```
-rw-r-----+
```

символ:

```
+
```

означает наличие extended ACL.

Тогда необходимо:

```
getfacl file
```

Иначе можно ошибочно считать, что mode bits полностью описывают access policy.

---

# 24. `setfacl` / `getfacl`

Добавить user ACL:

```
setfacl -m u:alice:rw file
```

Удалить:

```
setfacl -x u:alice file
```

Посмотреть:

```
getfacl file
```

Для directory default ACL:

```
setfacl -m d:g:developers:rwx /srv/team
```

Конкретная поддержка ACL зависит от filesystem и mount/configuration.

---

# 25. POSIX ACL и mode bits связаны

ACL не является полностью независимым механизмом.

Для POSIX ACL существует соответствие между:

```
ACL entries
```

и отображаемыми:

```
mode bits
```

Особенно важна:

```
ACL_MASK
```

Поэтому изменение:

```
chmod g-w file
```

может изменить mask ACL и тем самым effective permissions named users/groups.

Это одна из причин всегда проверять ACL после `chmod` на ACL-managed filesystem objects.

# 26. Capabilities

Linux capabilities разделяют традиционные root privileges на отдельные units. Capabilities являются per-thread attributes. citeturn0search0

Примеры:

```
CAP_NET_ADMIN
CAP_NET_RAW
CAP_SYS_ADMIN
CAP_SYS_PTRACE
CAP_DAC_OVERRIDE
CAP_DAC_READ_SEARCH
CAP_CHOWN
CAP_KILL
CAP_SETUID
CAP_SETGID
```

Полный список зависит от kernel version.

---

# 27. Effective / Permitted / Inheritable / Bounding / Ambient

Для thread могут существовать несколько capability sets:

```
Permitted
Effective
Inheritable
Bounding
Ambient
```

Основные идеи:

### Effective

Capabilities, которые непосредственно используются для permission checks.

### Permitted

Верхняя граница capabilities, которые thread может иметь в effective set.

### Inheritable

Участвует в capability transformation при `execve()`.

### Bounding

Ограничивает capabilities, которые могут быть получены через `execve()`.

### Ambient

Позволяет определённым capabilities сохраняться через `execve()` для non-privileged executables при выполнении условий kernel model. citeturn0search0

---

# 28. Диагностика capabilities

```
grep '^Cap' /proc/$$/status
```

Для процесса:

```
grep '^Cap' /proc/<PID>/status
```

Удобный инструмент:

```
capsh --print
```

Для binary:

```
getcap /path/to/binary
```

---

# 29. File capabilities

Linux может хранить capabilities непосредственно в extended attribute executable:

```
security.capability
```

Это позволяет предоставить binary определённые capabilities без полного SUID root model. citeturn0search0

Пример:

```
setcap cap_net_raw+ep /path/to/program
```

Проверка:

```
getcap /path/to/program
```

Смысл `+ep` должен рассматриваться через capability transformation rules, а не как произвольный текстовый флаг.

---

# 30. `CAP_DAC_OVERRIDE` и `CAP_DAC_READ_SEARCH`

Эти capabilities особенно важны при анализе файлового доступа.

`CAP_DAC_OVERRIDE` позволяет обходить многие обычные DAC read/write/execute checks.

`CAP_DAC_READ_SEARCH` связан с обходом file read и directory read/search checks и рядом специальных filesystem operations. citeturn0search0

Поэтому:

```
chmod 000 file
```

не является абсолютной security boundary против privileged process с подходящими capabilities.

---

# 31. `CAP_FOWNER`

`CAP_FOWNER` влияет на операции, которые требуют совпадения filesystem UID процесса с UID объекта, и связан с рядом специальных operations, включая управление ACL в соответствующих случаях. citeturn0search0

Это хороший пример того, почему:

```
UID/GID
+
mode bits
```

недостаточно для полного понимания Linux authorization.

---

# 32. `CAP_SYS_ADMIN`

`CAP_SYS_ADMIN` исторически является очень широкой capability.

Её наличие может разрешать большое количество privileged operations.

Поэтому:

> `CAP_SYS_ADMIN` внутри контейнера не следует рассматривать как безобидную «административную» capability.

При container hardening её обычно стараются не выдавать без конкретной необходимости.

---

# 33. DAC ≠ MAC

### DAC

Решение зависит от credentials/ownership/ACL и обычно управляется владельцем объекта или администраторами.

### MAC

Mandatory Access Control накладывает дополнительную policy, которую обычный владелец объекта не может произвольно отменить.

Типичные Linux LSM implementations:

```
SELinux
AppArmor
Smack
TOMOYO
```

Linux Security Module infrastructure предоставляет hooks, через которые security modules участвуют в authorization decisions.

---

# 34. SELinux

SELinux использует label-based security model.

Объект может иметь security context:

```
ls -Z file
```

Например концептуально:

```
user_u:object_r:httpd_sys_content_t:s0
```

Процесс также имеет context.

Проверка доступа зависит не только от Unix permissions:

```
DAC
+
SELinux policy
```

---

# 35. AppArmor

AppArmor в основном использует profile-based policy, связанный с executable/process identity.

Проверка:

```
aa-status
```

В отличие от SELinux, AppArmor обычно мыслится через profiles и path-oriented rules, хотя точные semantics шире этого упрощения.

---

# 36. Почему `chmod 777` не всегда решает `Permission denied`

Если:

```
chmod 777 file
```

но операция всё ещё запрещена, возможны:

```
SELinux denial
AppArmor denial
ACL
mount option
read-only filesystem
capability/security policy
namespace context
filesystem-specific restrictions
```

Поэтому универсальная диагностика:

```
ls -l
getfacl
ls -Z
aa-status
mount/findmnt
capabilities
logs/audit
```

---

# 37. `noexec`, `nosuid`, `nodev`

Mount options также меняют security semantics.

### `noexec`

Ограничивает execution файлов с соответствующего filesystem mount.

### `nosuid`

Отключает/ограничивает применение SUID/SGID semantics и file capabilities на соответствующем mount в соответствии с kernel semantics.

### `nodev`

Не разрешает использовать device special files на этом mount обычным образом.

Проверка:

```
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
```

---

# 38. `noexec` не означает «нельзя прочитать бинарник»

Например:

```
mount /opt -o noexec
```

не означает, что:

```
cat /opt/program
```

невозможен.

Ограничение относится к execution semantics.

Также способы запуска кода через interpreter требуют отдельного анализа:

```
python /opt/script.py
```

может иметь другую security path, чем прямой:

```
/opt/script.py
```

---

# 39. Seccomp

Seccomp ограничивает доступные системные вызовы.

В современном Linux основной механизм — seccomp BPF filters.

Упрощённо:

```
application
    │
    ▼
syscall()
    │
    ▼
seccomp filter
    │
 ┌──┴──────────────┐
 ▼                 ▼
ALLOW             DENY
 │                 │
 ▼                 ▼
kernel          errno / trap /
                kill / user notification
```

`seccomp(2)` описывает strict mode и filter mode; filter может определять результат для системных вызовов. citeturn0search3

---

# 40. Seccomp ≠ capabilities

Capabilities отвечают на вопрос:

```
имеет ли процесс определённую privileged capability?
```

Seccomp:

```
может ли процесс выполнить конкретный syscall
и какой результат должен получить kernel при его вызове?
```

Это разные security layers.

---

# 41. Seccomp в контейнерах

Container runtime может применять seccomp profile, ограничивающий syscall surface.

Например, application может работать с:

```
read
write
openat
mmap
futex
epoll
...
```

но не нуждаться в:

```
mount
reboot
kexec_load
...
```

Точный список зависит от runtime/profile.

---

# 42. `no_new_privs`

`no_new_privs` — важный process attribute для security hardening.

Проверка:

```
grep NoNewPrivs /proc/<PID>/status
```

При установленном `no_new_privs` процесс и его descendants не должны получать новые privileges через mechanisms вроде setuid/setgid executables или file capabilities при `execve()` в случаях, определённых kernel semantics.

Он также важен для некоторых seccomp workflows.

---

# 43. `sudo` и `su` — userspace mechanisms

Не следует смешивать:

```
sudo
su
setuid
capabilities
```

`sudo` — userspace authorization/execution program.

`su` — userspace mechanism смены identity.

SUID — kernel/file execution semantics.

Capabilities — kernel privilege decomposition.

Они могут использоваться вместе, но являются разными уровнями.

---

# 44. ACL vs capabilities

ACL отвечают:

```
может ли этот user/group получить доступ к этому filesystem object?
```

Capabilities:

```
может ли privileged process обойти/выполнить определённые kernel operations?
```

Поэтому:

```
ACL = object-centric authorization
capability = process privilege
```

Это упрощённая, но полезная модель.

---

# 45. Security decision для файла

Упрощённо:

```
              open("/path/file")
                       │
                       ▼
                 path lookup
                       │
                       ▼
                 DAC / ACL
                       │
                       ▼
             capability effects
                       │
                       ▼
                  LSM hooks
                       │
                       ▼
                mount/filesystem
                       │
                       ▼
                   allow/deny
```

Реальный kernel path сложнее и зависит от конкретной операции (`open`, `unlink`, `rename`, `execve`, `ioctl` и т. д.).

# 46. Диагностика `Permission denied`

## Шаг 1 — identity

```
id
```

Для процесса:

```
grep -E '^(Uid|Gid|Groups):' /proc/<PID>/status
```

---

## Шаг 2 — path permissions

```
namei -l /path/to/file
```

`namei` особенно полезен для обнаружения отсутствующего `x` на промежуточной directory.

# 52. `strace` как последний слой диагностики

Для процесса:

```
strace -f -e trace=%file ./program
```

или:

```
strace -f -e openat,access,statx,execve ./program
```

Можно увидеть:

```
openat(...) = -1 EACCES
```

или:

```
execve(...) = -1 EPERM
```

Это помогает связать пользовательский симптом с конкретным syscall.

Но `strace` показывает результат syscall, а не обязательно объясняет, какой security layer отказал.

---

# 53. `EACCES` vs `EPERM`

Грубо:

```
EACCES
```

часто означает отсутствие необходимого access permission.

```
EPERM
```

обычно означает, что операция не разрешена процессу, часто из-за privilege/security restrictions.

Но нельзя использовать:

```
errno == EACCES → точно chmod
errno == EPERM → точно capability
```

как универсальное правило.

Нужно анализировать конкретный syscall и context.

---

# 54. Shared directory: рекомендуемая модель

Для:

```
/srv/project
```

где работают несколько users:

```
groupadd developers
chgrp developers /srv/project
chmod 2770 /srv/project
```

Дополнительно при необходимости:

```
setfacl -m g:developers:rwx /srv/project
```

Для сложной inheritance policy лучше явно использовать default ACL:

```
setfacl -m d:g:developers:rwx /srv/project
```

---

# 55. Secrets

Для secret file обычно нужен принцип least privilege:

```
0600
```

или:

```
0640
```

если доступ требуется отдельной group.

Но permissions файла — только один слой защиты.

Также необходимо учитывать:

```
backup
logs
core dumps
process memory
environment variables
containers
filesystem encryption
secret managers
```

---

# 56. Почему `chmod 777` — плохой универсальный fix

`777` разрешает:

```
owner: rwx
group: rwx
other: rwx
```

Но это не исправляет:

```
ACL mask
SELinux
AppArmor
noexec
read-only mount
namespace
capability
application bug
```

и одновременно расширяет DAC access.

Правильный debugging:

```
find exact denial
→ change only required permission
```

---

# 57. Least privilege

Хорошая security policy начинается не с:

```
chmod 777
```

а с вопроса:

```
Кто должен выполнить какую операцию над каким объектом?
```

После этого выбирается минимальный механизм:

```
owner/group mode
→ ACL
→ capability
→ LSM policy
→ seccomp
```

в зависимости от задачи.

---

# 58. Сравнение механизмов

|Механизм|Что контролирует|Тип|
|---|---|---|
|mode bits|file/directory access|DAC|
|POSIX ACL|более детальный file access|DAC|
|SUID/SGID|execution credentials/group inheritance|privilege semantics|
|sticky bit|directory deletion/rename constraints|DAC semantics|
|capabilities|отдельные privileged operations|privilege|
|SELinux|label/policy-based access|MAC/LSM|
|AppArmor|profile-based restrictions|MAC/LSM|
|seccomp|syscall interface|syscall filtering|
|`noexec`|executable mappings/exec semantics on mount|filesystem/mount|
|`nosuid`|SUID/SGID/file-capability semantics on mount|filesystem/mount|
|user namespace|UID/GID isolation|namespace|

# 60. Итоговая модель Linux access control

```
                       PROCESS
                          │
                    credentials
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
       UID/GID        capabilities      namespaces
          │               │                │
          ▼               │                │
       DAC/ACL            │                │
          │               │                │
          └───────┬───────┘                │
                  ▼                        │
             LSM policy                    │
                  │                        │
                  └──────────┬─────────────┘
                             ▼
                     mount/filesystem
                             │
                             ▼
                       ALLOW / DENY
```

Главный принцип:

> **Linux access control — это не `chmod` и не только UID/GID. Это композиция DAC, ACL, capabilities, LSM, syscall restrictions, mount/filesystem semantics и namespace context.**

# 61. Практический алгоритм

При любой ошибке:

```
Permission denied
       │
       ▼
     who?
       │
       ▼
UID/GID/groups
       │
       ▼
     what?
       │
       ▼
path + object
       │
       ▼
mode bits
       │
       ▼
ACL
       │
       ▼
capabilities
       │
       ▼
mount options
       │
       ▼
SELinux/AppArmor
       │
       ▼
seccomp / namespace / syscall context
       │
       ▼
       root cause
```

Не следует начинать расследование с изменения permissions. Сначала необходимо установить **какая именно проверка отказала**.

# 63. Version-specific note

Linux security semantics эволюционируют.

При production analysis фиксируйте:

```
uname -r
cat /etc/os-release
findmnt
getcap -r /usr/bin /usr/sbin 2>/dev/null
```

а для конкретного процесса:

```
cat /proc/<PID>/status
cat /proc/<PID>/uid_map
cat /proc/<PID>/gid_map
cat /proc/<PID>/attr/current
```

Конкретные capabilities, LSM modules, seccomp behavior и mount semantics зависят от kernel version и configuration.

## Краткая формула

```
DAC:
    UID/GID + mode bits + POSIX ACL

Privilege:
    capabilities + SUID/SGID

MAC:
    SELinux / AppArmor / other LSM

Syscall surface:
    seccomp

Filesystem boundary:
    mount namespace + mount options + filesystem semantics

Identity boundary:
    user namespace

Политика доступа =
    композиция всех применимых security checks
```
