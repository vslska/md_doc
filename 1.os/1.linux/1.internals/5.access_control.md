## Архитектура контроля доступа в Linux

Классическая модель безопасности Unix основана на **DAC (Discretionary Access Control)**: владелец объекта (пользователь) и группы определяют базовые права доступа.

В современном ядре Linux цепочка проверки прав (Security Path) состоит из множества независимых слоев:

```text
                  Вызов операции процесса (например, open, execve)
                                         │
                                         ▼
                             Process Credentials (UID/GID)
                                         │
                                         ▼
                                  DAC Permissions
                                  ├── Mode Bits (rwx)
                                  └── POSIX ACL
                                         │
                                         ▼
                                Linux Capabilities
                         (CAP_DAC_OVERRIDE, CAP_SYS_ADMIN)
                                         │
                                         ▼
                             LSM Hooks (MAC Policy)
                                  ├── SELinux
                                  ├── AppArmor
                                  └── Smack / TOMOYO
                                         │
                                         ▼
                             Syscall Filter (Seccomp)
                                         │
                                         ▼
                   Filesystem / Mount Semantics / Namespaces
                          (ro, noexec, nosuid, user_ns)
                                         │
                                         ▼
                                   [ ALLOW / DENY ]
````

> **Важно:** Успешный проход слоя DAC не гарантирует выполнения операции. Решение может быть заблокировано на уровне Capabilities, LSM-модулей, Seccomp-фильтров или опций монтирования файловой системы.

## Битовые маски Unix (Mode Bits)

Каждый объект VFS (файл, директория, сокет) содержит флаги владения и атрибуты доступа:

- **Owner (UID):** Идентификатор владельца.
- **Group (GID):** Идентификатор группы владения.
- **Mode:** Битовая маска прав доступа.

Символическое представление:



```
-rwxr-x---
││  │  └── Other (нет прав)
││  └───── Group (r-x: чтение, исполнение)
│└──────── Owner (rwx: чтение, запись, исполнение)
└───────── Тип объекта (- = обычный файл, d = директория)
```

## Семантика прав r, w, x

### Обычные файлы

|**Право**|**Символ**|**Семантическое значение**|
|---|---|---|
|**Read**|`r`|Разрешает чтение содержимого файла (операции `read()`).|
|**Write**|`w`|Разрешает модификацию и перезапись содержимого файла (операции `write()`, `truncate()`).|
|**Execute**|`x`|Разрешает загрузку и выполнение файла в качестве бинарного процесса или скрипта (вызов `execve()`).|

> Наличие права `x` на исполнение не дает автоматического права на чтение (`r`). Для запуска интерпретируемых скриптов (Bash, Python) требуются оба флага: `r` и `x`.

### Директории

Для директорий флаги `rwx` имеют совершенно иную смысловую нагрузку:

|**Право**|**Символ**|**Семантическое значение для директории**|
|---|---|---|
|**Read**|`r`|Разрешает чтение списка имён файлов внутри директории (вызовы `readdir()`, `getdents()`).|
|**Write**|`w`|Разрешает создание, удаление и переименование записей (entries) внутри директории.|
|**Execute**|`x`|Разрешает проходить через директорию (traversal/lookup) и обращаться к inode внутри неё.|

> Комбинация `r + x` для директории позволяет просматривать её содержимое и обращаться к находящимся внутри объектам (при наличии соответствующих прав на сами объекты).

## Разрешение путей VFS (Path Traversal)

При обращении к абсолютному пути `/a/b/c/file` ядро последовательно выполняет процедуру `path_resolution(7)`. Процесс обязан иметь флаг **`x` (Execute)** на **всех** промежуточных директориях иерархии:

```
 /         [ x ] -> Разрешено
 ├── a/    [ x ] -> Разрешено
 │   └── b/ [ x ] -> Разрешено
 │       └── c/ [ x ] -> Разрешено
 │           └── file [ r ] -> Успешный доступ на чтение
```

Если хотя бы на одном промежуточном каталоге (например, `/a/b`) отсутствует флаг `x`, ядро немедленно возвращает ошибку `EACCES` (**Permission denied**), даже если права на конечный файл установлены в `0777`.

## Алгоритм выбора класса прав DAC

При проверке стандартных DAC mode bits ядро выбирает **ровно один** класс прав (Owner, Group или Other) по первому совпадению:

```
              Effective UID процесса == UID владельца файла?
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
               ДА                              НЕТ
                 │                                 │
                 ▼                                 ▼
      Применяются права OWNER        Effective / Supplementary GIDs
    (Права Group/Other игнорируются)    процесса совпадают с GID файла?
                                                   │
                                   ┌───────────────┴───────────────┐
                                   ▼                               ▼
                                 ДА                            НЕТ
                                   │                               │
                                   ▼                               ▼
                        Применяются права GROUP        Применяются права OTHER
                      (Права Other игнорируются)
```

> **Важно:** Права не суммируются. Если пользователь является владельцем файла с правами `---rwxrwx` (`0077`), он **не сможет** прочитать файл, так как к нему применятся блокирующие права блока `Owner` (`---`).

## Идентификаторы процесса и Supplementary Groups

Контекст безопасности процесса в Linux определяется набором учетных данных (Credentials):

- **Real UID/GID (`RUID`/`RGID`):** Идентификатор пользователя/группы, запустившего процесс.
- **Effective UID/GID (`EUID`/`EGID`):** Идентификаторы, используемые ядром для большинства проверок прав доступа.
- **Saved Set-User-ID / Saved Set-Group-ID:** Сохраненные идентификаторы для временного сброса/восстановления привилегий.
- **FileSystem UID/GID (`FSUID`/`FSGID`):** Специальные идентификаторы Linux, используемые непосредственно при проверках VFS (обычно совпадают с `EUID`/`EGID`).
- **Supplementary Groups:** Список дополнительных групп, в которых состоит пользователь.
Просмотр учетных данных текущего процесса:

```sh
id
# Вывод: uid=1000(user) gid=1000(user) groups=1000(user),10(wheel),998(docker)
```

## Анализ метаданных файлов с помощью `stat`

Для получения подробных сведений о правах доступа используется утилита `stat`:

```sh
stat -c '%A %a %U(%u) %G(%g) %n' /etc/shadow
# Вывод: -rw-r----- 640 root(0) shadow(42) /etc/shadow
```

Формат вывода:

- `%A`: Символьный режим прав.
- `%a`: Восьмеричный режим прав.
- `%U` / `%u`: Имя и UID владельца.
- `%G` / `%g`: Имя и GID группы.

## Восьмеричное представление прав (Octal Notation)

Каждая группа прав конструируется суммированием битовых значений:

- `r` (Read) = **4**
- `w` (Write) = **2**
- `x` (Execute) = **1**

```
Символьный вид:  r w x  |  r - x  |  r - -
Битовый вид:     4+2+1  |  4+0+1  |  4+0+0
Восьмеричный:      7    |    5    |    4     ==>  0754
```

## Специальные биты режимов (Special Mode Bits)

Полная восьмеричная маска прав включает 4 цифры: `0<Special><Owner><Group><Other>`.

|**Бит**|**Маска**|**Символ**|**Область применения**|**Функция**|
|---|---|---|---|---|
|**SUID** (Set-User-ID)|`04000`|`s` (у owner)|Исполняемые файлы|При запуске процесса `EUID` устанавливается равным UID владельца файла.|
|**SGID** (Set-Group-ID)|`02000`|`s` (у group)|Директории / Файлы|Для директорий: новые объекты наследуют GID директории, а не группы создателя.|
|**Sticky Bit**|`01000`|`t` (у other)|Директории|Удаление/переименование файлов разрешено только владельцу файла, владельцу директории или `root`.|

## Семантика SUID и связанные риски

Классическим примером применения SUID является бинарный файл `/usr/bin/passwd`:

```sh
ls -l /usr/bin/passwd
# Вывод: -rwsr-xr-x 1 root root 68208 Jan 16 18:00 /usr/bin/passwd
```

Буква `s` в позиции исполняемого файла владельца означает, что обычный пользователь при запуске `passwd` получает эффективные права `EUID = 0` (root), что необходимо для записи нового хэша пароля в `/etc/shadow`.

> **Предупреждение:** Любой SUID-бинарник является потенциальным вектором повышения привилегий (Privilege Escalation).
> 
> Поиск всех SUID-файлов в системе:
> 
> ```bash
> find / -xdev -perm -4000 -type f -ls 2>/dev/null
> ```

## Семантика SGID (Файлы vs Директории)

1. **SGID на исполняемом файле (`02000`):** При вызове `execve()` устанавливает `EGID` процесса равным GID файла.
2. **SGID на директории:** Автоматизирует совместную работу в групповых каталогах.

```sh
mkdir /srv/workspace
chgrp developers /srv/workspace
chmod 2770 /srv/workspace # Установка SGID + rwxrwx---
```

Все файлы и поддиректории, создаваемые внутри `/srv/workspace`, автоматически получат GID `developers`, независимо от основной группы пользователя.

## Sticky Bit и удаление объектов

Важнейшее правило VFS Linux: Право на удаление или переименование файла определяется правами РОДИТЕЛЬСКОЙ ДИРЕКТОРИИ (наличием флага `w`), а не самого файла.

Если директория доступна на запись всем (`0777`), любой пользователь может удалить файл `chmod 0000 file.txt`.

Для предотвращения этого используется **Sticky Bit** (`1777`), установленный, например, на `/tmp`:

```sh
ls -ld /tmp
# Вывод: drwxrwxrwt 15 root root 4096 Sep 25 10:00 /tmp
```

Наличие символа `t` гарантирует, что удалить файл из `/tmp` может только его фактический владелец или суперпользователь.

## Практическое применение `chmod` и `umask`

### Символьный и цифровой `chmod`

```sh
# Символьный режим
chmod u+rw,g+r,o-rwx file.txt
chmod -R g+s /srv/shared_dir

# Использование флага +X (заглавная X):
# Добавляет 'x' только к директориям и файлам, у которых уже есть право 'x' хотя бы для кого-то
chmod -R a+rX /srv/app
```

### Маска маскирования `umask`

`umask` вычитает (маскирует) установленные биты из базовых прав, запрашиваемых приложением при создании объекта (`0666` для файлов и `0777` для директорий).

```sh
Запрошено создателем (файл):       0666  (rw-rw-rw-)
Значение umask:                    0022  (---w--w--)
Фактические права файла:           0644  (rw-r--r--)

Запрошено создателем (директория):  0777  (rwxrwxrwx)
Значение umask:                    0022  (---w--w--)
Фактические права директории:      0755  (rwxr-xr-x)
```

## POSIX ACL (Extended Access Control Lists)

Стандартные mode bits ограничены назначением прав ровно одному владельцу, одной группе и всем остальным. **POSIX ACL** позволяют задавать гранулярные права для произвольного числа пользователей и групп.

Наличие у файла расширенных прав ACL обозначается знаком **`+`** в конце строки прав `ls -l`:

```sh
-rw-r-----+ 1 alice developers 1024 Sep 25 10:00 secret.txt
```

### Access ACL vs Default ACL

- **Access ACL:** Задает правила доступа к конкретному файлу или директории.
- **Default ACL:** Определяется **только для директорий** и служит шаблоном наследования прав для всех вновь создаваемых внутри объектов.

```sh
# Чтение ACL
getfacl /srv/project

# Назначение прав пользователю bob и группе qa
setfacl -m u:bob:rw- /srv/project/file.txt
setfacl -m g:qa:rwx /srv/project/file.txt

# Настройка наследования Default ACL на директорию
setfacl -m d:g:developers:rwx /srv/project
```

### Роль ACL Mask и связка с Mode Bits

Запись `mask::` определяет **максимально допустимые эффективные права** для всех названных пользователей (`named users`), названных групп (`named groups`) и основной группы файла.

```
user:bob:rwx           [ Запрошенные права ]
mask::r-x              [ Ограничивающая маска ]
----------------------------------------------
Effective: r-x         [ Фактически предоставленные права ]
```

> **Важно:** Выполнение стандартной команды `chmod g-w file` на файле с ACL меняет значение **`ACL Mask`**, а не права основной группы, что мгновенно урезает эффективные права всех именованных пользователей и групп.

## Подсистема Linux Capabilities

Linux Capabilities разделяют монолитные привилегии пользователя `root` (UID 0) на атомарные единицы управления.

### Множества capabilities процесса (Sets)

Для каждого потока ядро поддерживает 5 наборов capabilities:

```
┌──────────────────────────────────────────────────────────┐
│                   Capability Sets                        │
├──────────────┬───────────────────────────────────────────┤
│ Permitted    │ Абсолютный верхний предел прав потока.    │
│ Effective    │ Права, проверяемые ядром в данный момент. │
│ Inheritable  │ Права, сохраняемые при вызове execve().   │
│ Bounding     │ Ограничительное множество (Bounding Set). │
│ Ambient      │ Права, сохраняемые non-root при execve(). │
└──────────────┴───────────────────────────────────────────┘
```

Просмотр capabilities процесса (в шестнадцатеричном формате):

```sh
grep '^Cap' /proc/<PID>/status
# Декодирование с помощью capsh:
capsh --decode=$(grep '^CapEff' /proc/1/status | awk '{print $2}')
```

### File Capabilities и атрибут `security.capability`

Вместо утилизации небезопасных SUID-бинарников бинарному файлу можно назначить точечные Capabilities с помощью расширенных атрибутов файловой системы (`xattr`):

```sh
# Разрешить утилите ping создавать сырые сокеты без SUID root:
setcap cap_net_raw+ep /usr/bin/ping

# Чтение установленных capabilities:
getcap /usr/bin/ping
# Вывод: /usr/bin/ping cap_net_raw=ep
```

Флаги:

- `e` (Effective): Активирует capability при запуске.
- `p` (Permitted): Добавляет в разрешенное множество.

### Анализ ключевых capabilities (`CAP_DAC_OVERRIDE`, `CAP_SYS_ADMIN` и др.)

- **`CAP_DAC_OVERRIDE`:** Полностью игнорирует любые DAC-проверки прав чтения, записи и исполнения (`rwx`).
- **`CAP_DAC_READ_SEARCH`:** Игнорирует проверки чтения файлов и прохода по директориям (`x`).
- **`CAP_NET_ADMIN`:** Разрешает конфигурирование сетевых интерфейсов, таблиц маршрутизации и правил iptables/nftables.
- **`CAP_SYS_ADMIN`:** Избыточно широкая capability («новый root»). Разрешает монтирование ФС, настройку namespaces, вызовы `quotactl`, `swapon` и сотни других системных операций.

## Мандатное управление доступом (MAC) и LSM

**LSM (Linux Security Modules)** — фреймворк ядра, предоставляющий хуки (hooks) для проверки политик безопасности перед выполнением системных вызовов.

```sh
DAC Check Passed  ──►  LSM Hook (SELinux / AppArmor)  ──► Access Granted / Denied
```

В отличие от DAC, правила MAC накладываются поверх стандартных прав и не могут быть отменены владельцем объекта.

### SELinux (Label-based Security)

SELinux присваивает каждому процессу и объекту ФС метку безопасности (Security Context).

Формат метки: `user:role:type:sensitivity`

```sh
# Просмотр контекстов файлов
ls -Z /var/www/html/index.html
# Вывод: system_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html

# Поиск отказов SELinux (AVC Denials) в журналах
ausearch -m AVC -ts recent
```

Если веб-сервер `httpd` (с типом `httpd_t`) попытается прочитать файл с типом `user_home_t`, SELinux заблокирует доступ, даже если `chmod` установлен в `0777`.

### AppArmor (Path/Profile-based Security)

AppArmor привязывает правила безопасности к абсолютным путям исполняемых файлов с помощью профилей.

```sh
# Проверка статуса AppArmor
aa-status

# Профили находятся в режиме enforce (блокировка) или complain (логирование)
```

## Ограничения монтирования (`noexec`, `nosuid`, `nodev`)

Флаги монтирования файловых систем определяют глобальные ограничения безопасности на уровне VFS:

```sh
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
```

- **`noexec`:** Запрещает прямое исполнение бинарных файлов с данного монтирования (вызов `execve()` вернет `EACCES`).
    > _Примечание:_ `noexec` не предотвращает запуск скриптов через интерпретатор (например, `python /mnt/noexec_fs/script.py`).
- **`nosuid`:** Игнорирует действия битов SUID/SGID и File Capabilities на данной ФС.
- **`nodev`:** Запрещает обращение к символьным и блочным устройствам (`/dev/sdb`, `/dev/mem`).

## Фильтрация системных вызовов (Seccomp & `no_new_privs`)

### Seccomp (Secure Computing Mode)

Seccomp BPF позволяет фильтровать системные вызовы, доступные процессу. Если приложение выполняет запрещенный syscall, ядро незамедлительно завершает его по `SIGSYS` или возвращает ошибку `EPERM`.

### Флаг `no_new_privs`

Атрибут процесса, гарантирующий, что данный процесс и его потомки никогда не смогут получить новые привилегии через вызовы `execve()` (SUID-биты и File Capabilities игнорируются).

Проверка статуса:

```sh
grep NoNewPrivs /proc/<PID>/status
# NoNewPrivs: 1
```

## Пошаговый алгоритм диагностики `Permission denied`

Если приложение возвращает ошибку отказа в доступе, выполните диагностику по шагам:

```
                  [ Ошибка: Permission denied ]
                                │
                                ▼
         Шаг 1. Проверить Identity процесса (UID, GID, Groups)
                 cat /proc/<PID>/status | grep -E 'Uid|Gid|Groups'
                                │
                                ▼
         Шаг 2. Проверить Path Traversal (права 'x' на каталогах)
                 namei -l /path/to/target/file
                                │
                                ▼
         Шаг 3. Проверить конечные Mode Bits и ACL объекта
                 stat /path/to/file
                 getfacl /path/to/file
                                │
                                ▼
         Шаг 4. Проверить параметры монтирования ФС (ro, noexec, nosuid)
                 findmnt -T /path/to/file
                                │
                                ▼
         Шаг 5. Проверить контексты безопасности LSM (SELinux / AppArmor)
                 ls -Z /path/to/file
                 ausearch -m AVC -ts recent
                                │
                                ▼
         Шаг 6. Трассировка системных вызовов (при необходимости)
                 strace -f -e trace=%file -p <PID>
```

## Рекомендуемые паттерны настройки разделяемых ресурсов

Для организации общей директории разработки с несколькими участниками группы `developers`:

```sh
# 1. Создание каталога и назначение владения
mkdir -p /srv/project
chown root:developers /srv/project

# 2. Установка SGID и прав DAC (только для владельца и группы)
chmod 2770 /srv/project

# 3. Настройка Default ACL для автоматического наследования прав
setfacl -m d:g:developers:rwx /srv/project
setfacl -m d:o::--- /srv/project
```
