# Дисковая подсистема Linux: I/O, VFS, inode и LVM

> Цель документа — дать системное, технически точное представление о том, как путь от имени файла до физического I/O проходит через VFS, page cache, файловую систему, блочный слой Linux и, при использовании LVM, device-mapper.
>
> **Версия и область применимости:** Linux 6.x и современные реализации ext4/XFS/LVM2. Конкретное поведение может зависеть от версии ядра, файловой системы, драйвера блочного устройства и конфигурации LVM.

## 1. Модель слоёв

Удобно рассматривать файловый I/O как последовательность уровней:

```text
Приложение
    │
    │ open()/read()/write()/fsync()
    ▼
VFS
    │
    ├── dentry cache
    ├── inode cache
    ├── file object / file descriptor
    └── address_space / page cache
    │
    ▼
Файловая система
    │
    │ ext4 / XFS / ...
    ▼
Block layer
    │
    │ bio / request
    ▼
Device mapper (если используется)
    │
    │ LVM LV / thin-pool / ...
    ▼
Драйвер блочного устройства
    │
    ▼
NVMe / SSD / HDD / виртуальный диск
```

Важно различать три понятия:

- **файл** — объект, предоставляемый файловой системой;
- **inode** — структура файловой системы, содержащая метаданные объекта;
- **имя файла** — имя в каталоге, связанное с inode посредством directory entry.

VFS предоставляет единый интерфейс для разных файловых систем и скрывает их внутренние форматы от пользовательских процессов. Dentry, inode, file и superblock — разные объекты VFS и не должны рассматриваться как синонимы. citeturn0search0

# 2. Inode

## 2.1. Что такое inode

**Inode** — структура файловой системы, идентифицирующая файловый объект и хранящая его метаданные.

Для обычного файла inode, в зависимости от файловой системы, содержит или логически описывает:

- тип объекта;
- права доступа;
- UID/GID;
- размер;
- количество hard links;
- временные метки;
- атрибуты;
- информацию о размещении данных;
- filesystem-specific metadata.

**Имя файла в inode не хранится.**

Имя находится в каталоге. Directory entry связывает имя с номером inode. Поэтому один inode может иметь несколько имён — это механизм hard links. В VFS несколько dentry могут ссылаться на один inode. citeturn0search0turn0search1

Упрощённая модель:

```text
directory
┌─────────────────────────────┐
│ "report.txt" ───────────────┼──► inode #12345
│ "report.old" ───────────────┼──► inode #12345
└─────────────────────────────┘
                                      │
                                      ├── metadata
                                      └── file data
```

Следовательно:

> **Имя файла ≠ inode.**  
> **Hard link ≠ копия файла.**  
> Два имени могут ссылаться на один и тот же inode и, следовательно, на одни и те же данные.

---

## 2.2. Inode в ядре и inode на диске

Не следует смешивать:

1. **on-disk inode** — представление inode в конкретной файловой системе;
2. **VFS `struct inode`** — универсальное представление inode в ядре Linux.

Для block-based файловой системы inode с диска при необходимости представляется в памяти ядра. VFS использует `struct inode` как общий интерфейс, а конкретная файловая система расширяет или дополняет его собственными данными. citeturn0search0

Это принципиально важно:

```text
on-disk filesystem inode
        │
        ▼
filesystem-specific representation
        │
        ▼
VFS struct inode
```

## 2.3. Почему заканчиваются inode

Файловая система может иметь свободное место в байтах, но не иметь свободных inode.

Проверка:

```bash
df -h
df -i
```

Пример:

```text
$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1       100G   40G   60G  40% /var

$ df -i /var
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1       6553600 6553600       0  100% /var
```

В таком состоянии создание нового файлового объекта может завершаться:

```text
No space left on device
```

даже при наличии свободных блоков данных.

### ext4

В ext4 число inode определяется структурой файловой системы и её параметрами размещения inode tables. Поэтому при проектировании файловой системы важно учитывать не только ёмкость, но и предполагаемое количество файлов.

Проверка параметров:

```bash
tune2fs -l /dev/sda1 | grep -E 'Inode count|Free inodes|Inode size'
```

### XFS

XFS использует динамическое выделение inode chunks. Поэтому inode не задаются простой фиксированной таблицей на момент `mkfs` так же, как в классической модели ext4.

При этом XFS ограничивает пространство, которое может быть занято inode, параметром `maxpct`:

```bash
xfs_info /mountpoint
```

Это ограничение связано с распределением пространства файловой системы, а не является отдельным «счётчиком inode», аналогичным `df -i` ext4.

---

## 2.4. Поиск каталогов с большим количеством файлов

Простой вариант:

```bash
find /var -xdev -type f -printf '%h
' 2>/dev/null   | sort | uniq -c | sort -rn | head -20
```

Более информативно — сначала найти каталоги с большим количеством entries, а затем исследовать конкретное приложение.

Для больших файловых деревьев следует помнить, что полный `find /` сам по себе может создавать заметную нагрузку на metadata I/O.

# 3. Удаление открытого файла

## 3.1. Почему `rm` не всегда освобождает место

Рассмотрим:

```bash
rm /var/log/application.log
```

Если процесс продолжает держать файл открытым, место может не освободиться.

Упрощённо:

```text
directory entry ─────► inode ◄──── open file description ◄──── process
      │
      X  rm
```

`rm` удаляет directory entry. Это уменьшает количество hard links (`i_nlink`).

Но открытый файл продолжает существовать, пока существуют необходимые ссылки ядра на соответствующий объект файла/inode. После удаления последней directory entry процесс всё ещё может читать и писать через уже открытый file descriptor.

Когда inode больше не имеет directory links и больше не удерживается открытыми ссылками, файловая система может освободить его данные и метаданные.

Это объясняет классическую ситуацию:

```text
df -h       → filesystem почти заполнена
ls          → большого файла уже нет
lsof        → процесс всё ещё держит deleted file
```

---

## 3.2. Диагностика

```bash
lsof -nP +L1
```

или:

```bash
lsof -nP | grep '(deleted)'
```

Более узкий поиск:

```bash
lsof -nP | grep '/var/log'
```

Также можно проверить `/proc`:

```bash
ls -l /proc/<PID>/fd
```

Пример:

```text
/proc/1234/fd/7 -> /var/log/application.log (deleted)
```

Здесь:

- `1234` — PID;
- `7` — file descriptor процесса;
- `(deleted)` — directory entry уже удалён.

---

## 3.3. Освобождение места без остановки процесса

Если файл является логом и приложение допускает изменение его текущего файла, можно использовать:

```bash
: > /proc/<PID>/fd/<FD>
```

Например:

```bash
: > /proc/1234/fd/7
```

Это **не универсальная операция для произвольного приложения**. Она изменяет размер файла, связанного с открытым descriptor'ом, и может нарушить ожидания приложения относительно file offset, append semantics, логирования или собственной ротации.

Перед применением необходимо понимать:

- какой процесс держит descriptor;
- что это действительно лог;
- как приложение открывает файл;
- используется ли `O_APPEND`;
- не реализована ли собственная система ротации;
- нет ли требований к атомарности/структуре файла.

Для обычной ротации логов предпочтительнее штатный механизм приложения или `logrotate`, если он поддерживается приложением.

---

## 3.4. Почему `copytruncate` не всегда является лучшим решением

`copytruncate` позволяет продолжить запись в тот же inode, одновременно уменьшая его размер после копирования.

Однако между копированием и truncation приложение может продолжать писать в файл, поэтому часть данных может оказаться потеряна.

По этой причине для приложений, поддерживающих reopen/USR1/SIGHUP или собственный механизм rotation, обычно предпочтительнее:

```text
rename old log
    │
    └── application opens a new log
```

а не постоянная запись в тот же inode через `copytruncate`.

# 4. VFS

## 4.1. Назначение VFS

**VFS (Virtual File System)** — абстракционный слой ядра Linux, предоставляющий единый интерфейс различным файловым системам.

Приложение работает с системными вызовами:

```c
open()
read()
write()
close()
fsync()
fdatasync()
```

и не обязано знать внутренний формат ext4, XFS или другой файловой системы.

Упрощённо:

```text
POSIX/Linux system calls
          │
          ▼
         VFS
          │
   ┌──────┼────────┐
   ▼      ▼        ▼
 ext4    XFS      NFS
```

VFS содержит общие объекты, включая:

- `struct super_block`;
- `struct inode`;
- `struct dentry`;
- `struct file`.

# 5. Dentry, inode и file descriptor

Эти понятия часто смешивают.

## 5.1. Dentry

**Dentry** (`struct dentry`) представляет компонент пути в VFS и связывает имя в pathname lookup с inode.

Dentry активно используется для кеширования результатов разрешения путей. Dentry cache находится в RAM и не является файловым объектом, который просто «сохраняется на диске». citeturn0search1

---

## 5.2. Inode

Inode представляет файловый объект на уровне VFS:

```text
inode
├── metadata
├── permissions
├── timestamps
├── link count
└── filesystem-specific data
```

---

## 5.3. File object

`struct file` представляет открытый экземпляр файла в ядре.

У одного inode могут существовать несколько открытых file objects:

```text
inode
  │
  ├── struct file ──► fd 3 ── process A
  │
  └── struct file ──► fd 7 ── process B
```

File descriptor (`fd`) — это уже пользовательское целое число, являющееся индексом в таблице дескрипторов процесса.

Следовательно:

```text
fd
 ↓
struct file
 ↓
inode
```

Это одна из ключевых связей для понимания открытых и удалённых файлов.

# 6. Page Cache и запись

## 6.1. Общая модель

При buffered I/O запись обычно проходит через page cache:

```text
application
     │
     │ write()
     ▼
kernel
     │
     ▼
page cache
     │
     │ dirty pages
     ▼
writeback
     │
     ▼
filesystem
     │
     ▼
block layer
     │
     ▼
storage
```

Это не означает, что `write()` всегда просто «записал данные в RAM и сразу вернул управление».

Поведение зависит от:

- типа I/O;
- наличия page cache;
- размера и характера записи;
- давления памяти;
- dirty limits;
- filesystem semantics;
- `O_DIRECT`;
- `fsync()`/`fdatasync()`;
- состояния блочного устройства.

Поэтому утверждение «`write()` всегда завершается за наносекунды» некорректно.

---

# 7. Dirty pages и writeback

Когда изменённые страницы page cache должны быть записаны обратно в backing storage, они становятся кандидатами на **writeback**.

Основные механизмы writeback реализованы ядром и файловой системой. Историческая формулировка про отдельные универсальные `flusher threads` и процессы `[writeback]` недостаточно точна для современных ядер: реализация writeback изменилась, и её не следует описывать как один фиксированный пользовательский процесс.

---

## 7.1. Основные sysctl

Проверка текущих значений:

```bash
sysctl vm.dirty_background_ratio
sysctl vm.dirty_ratio
sysctl vm.dirty_background_bytes
sysctl vm.dirty_bytes
sysctl vm.dirty_expire_centisecs
sysctl vm.dirty_writeback_centisecs
```

Современная документация ядра определяет:

### `vm.dirty_background_ratio`

Процент от **доступной для dirtying памяти**, при достижении которого начинается background writeback.

Это не просто процент от физического `RAM`.

### `vm.dirty_ratio`

Порог dirty memory, при котором процесс, генерирующий запись, сам начинает выполнять writeback.

Важно:

> Нельзя корректно описывать `dirty_ratio` как правило «ядро блокирует все `write()` всех процессов».

Современная семантика связана с балансированием dirty memory и writeback pressure; конкретное поведение зависит от kernel version и writeback path. citeturn3search0

### `vm.dirty_background_bytes`

Абсолютный размер dirty memory, после которого запускается background writeback.

### `vm.dirty_bytes`

Абсолютный порог dirty memory, аналогичный `dirty_ratio`.

`*_bytes` и соответствующие `*_ratio` являются альтернативными настройками: при записи одного варианта другой устанавливается в `0`. citeturn3search0

---

## 7.2. Временные параметры

### `vm.dirty_expire_centisecs`

Время, после которого dirty data считается достаточно старой для writeout.

Единица измерения — сотые доли секунды.

Например:

```text
3000 = 30 секунд
```

### `vm.dirty_writeback_centisecs`

Период пробуждения механизма периодического writeback.

Например:

```text
500 = 5 секунд
```

Это не означает, что каждая dirty page гарантированно будет записана ровно через 5 секунд.

Оба параметра должны рассматриваться как элементы политики writeback, а не как жёсткие гарантии задержки. citeturn3search0

# 8. Почему опасно бездумно менять dirty limits

Плохая модель:

```text
256 GB RAM
10% dirty
20% dirty
=
25 GB / 50 GB
→ ядро обязательно будет писать 50 GB одним большим burst
```

Так интерпретировать параметры нельзя.

Во-первых, ratio рассчитывается относительно соответствующего понятия available memory, а не просто total RAM. Во-вторых, writeback выполняется постепенно и конкурентно.

Тем не менее чрезмерно большие dirty limits действительно могут увеличить объём данных, находящихся в памяти до writeback, и тем самым увеличить потенциальную задержку при интенсивном I/O.

Поэтому изменение:

```ini
vm.dirty_background_bytes
vm.dirty_bytes
```

должно основываться на измерениях workload, latency и пропускной способности storage, а не на универсальной формуле «1% RAM = правильное значение».

Официальная документация ядра описывает `dirty_background_bytes` как порог запуска background writeback, а `dirty_bytes` — как порог, при котором записывающий процесс начинает writeback. citeturn3search0

# 9. Наблюдение за dirty memory

Быстрая диагностика:

```bash
grep -E '^(Dirty|Writeback|WritebackTmp):' /proc/meminfo
```

Типичный вывод:

```text
Dirty:            123456 kB
Writeback:         12345 kB
WritebackTmp:          0 kB
```

Упрощённо:

- `Dirty` — dirty memory, ожидающая writeback;
- `Writeback` — память, находящаяся в процессе writeback;
- `WritebackTmp` — отдельная категория, используемая некоторыми файловыми системами/механизмами.

Для анализа реального I/O одной `/proc/meminfo` недостаточно. Полезны также:

```bash
iostat -xz 1
vmstat 1
pidstat -d 1
```

# 10. `fsync()`, `fdatasync()` и иллюзия «запись завершена»

Успешный возврат из `write()` не следует автоматически интерпретировать как:

> «данные гарантированно находятся на энергонезависимом носителе».

`write()` сообщает об успешной передаче данных в соответствующий kernel I/O path, но вопрос устойчивости данных после сбоя питания зависит от дальнейшего writeback и storage semantics.

Для явной синхронизации используются:

```c
fsync(fd);
fdatasync(fd);
```

Упрощённо:

- `fsync()` синхронизирует данные и необходимые metadata;
- `fdatasync()` ориентирован прежде всего на данные и metadata, необходимые для последующего корректного чтения файла.

Точная семантика зависит от системного вызова, файловой системы и устройства.

Для приложений, которым важна crash consistency, необходимо анализировать не только `write()`, но и:

```text
write()
  ↓
fsync()/fdatasync()
  ↓
filesystem journal / metadata
  ↓
block layer
  ↓
device cache
  ↓
persistent media
```

# 11. LVM

## 11.1. Что такое LVM

**LVM (Logical Volume Manager)** — слой управления блочными устройствами, обычно реализованный в Linux поверх device-mapper.

Классическая модель:

```text
Physical storage
      │
      ▼
     PV
      │
      ▼
     VG
      │
      ▼
     LV
      │
      ▼
Filesystem
```

---

# 12. PV — Physical Volume

PV — устройство или раздел, подготовленный для использования LVM:

```bash
pvcreate /dev/sdb
```

Проверка:

```bash
pvs
pvdisplay
```

PV разбит на **physical extents (PE)**.

Размер extent задаётся конфигурацией volume group и не следует считать универсально фиксированным «обычно 4 MiB». Значение необходимо проверять:

```bash
vgdisplay
```

или:

```bash
vgs -o vg_name,vg_extent_size
```

---

# 13. VG — Volume Group

VG объединяет один или несколько PV в пул свободных extents:

```bash
vgcreate vg_data /dev/sdb /dev/sdc
```

Проверка:

```bash
vgs
vgdisplay
```

Упрощённо:

```text
PV1 ─┐
     ├──► VG ───► free extents
PV2 ─┘
```

VG не является файловой системой. Это пул, из которого создаются logical volumes.

---

# 14. LV — Logical Volume

LV представляет виртуальное блочное устройство:

```bash
lvcreate -L 50G -n lv_data vg_data
```

Проверка:

```bash
lvs
lsblk
```

Обычно устройство доступно через:

```text
/dev/vg_data/lv_data
```

и/или:

```text
/dev/mapper/vg_data-lv_data
```

После создания LV можно разместить файловую систему:

```bash
mkfs.ext4 /dev/vg_data/lv_data
```

или:

```bash
mkfs.xfs /dev/vg_data/lv_data
```

# 15. Расширение диска виртуальной машины

Рассмотрим типичный сценарий:

```text
VM disk: 50 GiB → 100 GiB
```

При этом необходимо пройти несколько независимых уровней:

```text
Hypervisor
   │
   ▼
Virtual block device
   │
   ▼
Partition (если есть)
   │
   ▼
PV
   │
   ▼
VG
   │
   ▼
LV
   │
   ▼
Filesystem
```

**Важно:** увеличение виртуального диска автоматически не увеличивает файловую систему.

---

## 15.1. Шаг 1 — убедиться, что ядро видит новый размер

Для конкретного устройства способ зависит от типа шины и окружения.

Для SCSI:

```bash
echo 1 > /sys/class/block/sda/device/rescan
```

Проверка:

```bash
lsblk
cat /sys/class/block/sda/size
```

На NVMe подход другой; нельзя механически применять SCSI rescan ко всем устройствам.

# 16. Если PV находится на разделе

Например:

```text
/dev/sda3
    │
    ▼
   PV
    │
    ▼
   VG
```

После увеличения `/dev/sda` необходимо сначала увеличить сам раздел.

Для cloud/VM сценариев часто используется:

```bash
growpart /dev/sda 3
```

Затем проверить:

```bash
lsblk
```

и только после этого:

```bash
pvresize /dev/sda3
```

`partx -u /dev/sda` может использоваться для обновления представления таблицы разделов ядром, если это необходимо в конкретной конфигурации.

**Нельзя** без проверки применять `pvresize /dev/sda`, если PV фактически находится на `/dev/sda3`.

# 17. Если PV находится непосредственно на диске

В схеме:

```text
/dev/sda
   │
   ▼
  PV
   │
   ▼
  VG
```

после увеличения устройства:

```bash
pvresize /dev/sda
```

Проверка:

```bash
pvs
vgs
```

# 18. Расширение LV

Добавить всё свободное пространство VG:

```bash
lvextend -l +100%FREE /dev/vg_system/lv_root
```

Или, если требуется одновременно изменить файловую систему:

```bash
lvextend -r -l +100%FREE /dev/vg_system/lv_root
```

Опция `-r` просит LVM также изменить размер файловой системы. Однако автоматический resize следует всё равно проверять после операции. citeturn3search6

# 19. Расширение файловой системы

## 19.1. ext4

Для ext4:

```bash
resize2fs /dev/vg_system/lv_root
```

Обычно ext4 можно расширять online, если filesystem смонтирована и конкретная конфигурация поддерживает операцию.

Проверка:

```bash
df -h /
lsblk
```

---

## 19.2. XFS

XFS расширяется через точку монтирования:

```bash
xfs_growfs /
```

или:

```bash
xfs_growfs /data
```

Важно:

```text
resize2fs  → device
xfs_growfs → mountpoint
```

В исходной версии документа была опечатка:

```text
/mountpoin
```

правильно:

```text
/mountpoint
```

# 20. Полный пример расширения LVM + ext4

Исходное состояние:

```text
/dev/sda = 50G
/dev/sda3 = PV
VG = vg_system
LV = lv_root
filesystem = ext4
```

После увеличения виртуального диска до 100G:

```bash
# 1. Проверить размер устройства
lsblk

# 2. Переразмерить раздел
growpart /dev/sda 3

# 3. Проверить
lsblk

# 4. Увеличить PV
pvresize /dev/sda3

# 5. Проверить свободное место VG
vgs

# 6. Увеличить LV
lvextend -l +100%FREE /dev/vg_system/lv_root

# 7. Увеличить ext4
resize2fs /dev/vg_system/lv_root

# 8. Проверить результат
df -h /
lvs
pvs
vgs
```

Альтернативно шаги 6–7 можно объединить:

```bash
lvextend -r -l +100%FREE /dev/vg_system/lv_root
```

# 21. LVM Thin Provisioning

## 21.1. Идея

Thin provisioning позволяет создать logical volume с виртуальным размером, превышающим физически выделенное пространство thin pool.

Например:

```text
Physical thin pool: 100G

thin LV #1: 40G
thin LV #2: 40G
thin LV #3: 40G

Virtual capacity: 120G
Physical capacity: 100G
```

Это возможно, потому что физические блоки выделяются по мере записи.

---

## 21.2. Архитектура thin pool

Упрощённо:

```text
VG
│
└── thin-pool
      ├── _tdata
      │     └── physical data blocks
      │
      └── _tmeta
            └── thin metadata
                  │
                  ├── thin LV 1
                  ├── thin LV 2
                  └── thin LV 3
```

Thin pool использует два внутренних компонента:

- data LV — физические блоки данных;
- metadata LV — metadata, необходимые `dm_thin_pool`.

citeturn3search4

---

# 22. Почему `df -h` недостаточно для thin pool

Рассмотрим:

```text
Thin LV virtual size: 100G
Thin pool physical size: 10G
```

Файловая система внутри thin LV может показывать:

```text
Filesystem      Size  Used Avail
/dev/mapper/...  99G   1G   98G
```

Но это не означает, что физический thin pool имеет ещё 98G.

Физическое использование проверяется на уровне LVM:

```bash
lvs -o lv_name,lv_size,pool_lv,data_percent,metadata_percent
```

или:

```bash
lvs -o+data_percent,metadata_percent
```

`Data%` показывает использование пространства данных thin pool, а `Meta%` — использование metadata LV. Оба значения необходимо мониторить. citeturn3search1turn3search4

---

# 23. Что происходит при исчерпании thin pool

Это критический сценарий.

Когда physical data space thin pool исчерпан, дальнейшие записи в thin LVs могут возвращать I/O errors. Документация LVM предупреждает, что исчерпание data или metadata space может привести к ошибкам I/O и, в зависимости от обстоятельств, к повреждению файловой системы. citeturn3search4

Поэтому нельзя описывать ситуацию просто как:

> «ядро переводит весь thin pool в Read-Only».

Точное поведение зависит от состояния thin-pool target, политики LVM/device-mapper, типа ошибки и filesystem.

Практическое правило:

> **Thin pool необходимо расширять до исчерпания data или metadata space, а не после.**

Проверка:

```bash
lvs -o lv_name,lv_size,attr,pool_lv,data_percent,metadata_percent
```

---

# 24. Автоматическое расширение thin pool

LVM2 может использовать `dmeventd` для мониторинга thin pool и автоматического расширения при достижении заданного порога.

Соответствующие настройки:

```text
activation/thin_pool_autoextend_threshold
activation/thin_pool_autoextend_percent
```

Проверка конфигурации:

```bash
lvmconfig --type full activation/thin_pool_autoextend_threshold
lvmconfig --type full activation/thin_pool_autoextend_percent
```

При автоматическом расширении необходимо иметь свободные extents в VG.

Официальная документация LVM рекомендует расширять thin pool до исчерпания и описывает автоматическое расширение через `dmeventd`. citeturn3search1

# 25. Data% и Meta%

Пример:

```text
LV       LSize   Pool   Data%  Meta%
pool0    100G           72.10   18.20
vm01      40G    pool0   8.50
vm02      40G    pool0  63.60
```

Интерпретация:

- `pool0 Data% = 72.10` — физическое data space thin pool заполнено примерно на 72%;
- `pool0 Meta% = 18.20` — metadata space используется примерно на 18%;
- `vm01 Data%` — usage, связанный с конкретным thin LV, а не свободное место файловой системы.

Нельзя напрямую сопоставлять:

```text
df -h
```

и:

```text
lvs Data%
```

как одинаковые метрики. Они измеряют разные уровни системы.

---

# 26. TRIM/Discard и thin provisioning

Для thin provisioning важна ещё одна связь:

```text
filesystem
    │
    │ discard / TRIM
    ▼
device mapper
    │
    ▼
thin pool
```

Удаление файла внутри файловой системы не обязательно означает немедленное освобождение соответствующего физического блока thin pool.

Если filesystem передаёт discard и соответствующие настройки разрешают его обработку, физическое пространство может быть возвращено thin pool.

Проверка поддержки:

```bash
lsblk --discard
```

Ручной TRIM:

```bash
fstrim -av
```

Это особенно важно для виртуализированных storage stacks и thin provisioning.

```text
    │
    ▼

    │
    ▼

    │
    ▼
```

# 30. Ключевые различия, которые необходимо помнить

## 30.1. inode ≠ filename

```text
filename
   │
   ▼
directory entry
   │
   ▼
inode
```

---

## 30.2. inode ≠ file descriptor

```text
file descriptor
      │
      ▼
 struct file
      │
      ▼
    inode
```

---

## 30.3. `df -h` ≠ `df -i`

```text
df -h  → blocks / capacity
df -i  → inodes
```

---

## 30.4. `df -h` ≠ LVM `Data%`

```text
df -h
  └── filesystem-level logical allocation

lvs Data%
  └── physical data consumption inside thin pool
```

---

## 30.5. `write()` ≠ persistent storage

```text
write()
  ↓
kernel I/O path
  ↓
writeback
  ↓
storage
```

Для требований к durability необходимо учитывать `fsync()`/`fdatasync()` и semantics конкретной файловой системы и storage stack.

---

## 30.6. Увеличение диска ≠ увеличение filesystem

Полная цепочка:

```text
virtual disk
    ↓
partition
    ↓
PV
    ↓
VG
    ↓
LV
    ↓
filesystem
```

На каждом уровне необходимо убедиться, что свободное пространство действительно передано следующему уровню.

# 31. Практический runbook

## Если `df -h` показывает 100%

```bash
df -h
df -i
lsof -nP +L1
du -xhd1 / 2>/dev/null | sort -h
```

Проверить:

1. закончились ли filesystem blocks;
2. закончились ли inode;
3. есть ли deleted-open files;
4. нет ли отдельного mountpoint внутри дерева.

---

## Если `df -i` показывает 100%

```bash
df -i
```

Затем найти каталоги с большим количеством файлов:

```bash
find /var -xdev -type f -printf '%h
' 2>/dev/null   | sort | uniq -c | sort -rn | head -20
```

После этого исследовать приложение, которое создаёт большое количество мелких файлов.

---

## Если filesystem медленная

Начать с:

```bash
iostat -xz 1
vmstat 1
pidstat -d 1
```

Затем проверить:

```bash
grep -E '^(Dirty|Writeback|WritebackTmp):' /proc/meminfo
```

и состояние файловой системы/LVM:

```bash
df -h
df -i
pvs
vgs
lvs
```

---

## Если thin pool приближается к заполнению

```bash
lvs -a -o lv_name,lv_size,attr,pool_lv,data_percent,metadata_percent
vgs
```

Проверить:

- `Data%`;
- `Meta%`;
- наличие свободных extents в VG;
- работу `dmeventd`;
- настройки automatic extension.

Thin pool следует расширить **до** исчерпания data или metadata space. citeturn3search1turn3search4

Основная модель:

```text

│ Application                                         │
│                                                     │
│ open/read/write/fsync                              │
└───────────────────────┬─────────────────────────────┘
                        │
                        ▼
                       VFS
          ┌─────────────┼──────────────┐
          │             │              │
       dentry          inode          file
          │             │              │
          └─────────────┼──────────────┘
                        │
                        ▼
                   Page Cache
                        │
                   dirty pages
                        │
                        ▼
                    Writeback
                        │
                        ▼
                   Filesystem
                        │
                        ▼
                    Block Layer
                        │
                        ▼
                 Device Mapper
                        │
                 ┌──────┴──────┐
                 │             │

                 │
```

```text

        ↓

        ↓

        ↓

        ↓
```
