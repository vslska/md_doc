# Дисковая подсистема Linux: I/O, VFS, inode и LVM

> Системное, технически точное описание сквозного пути ввода-вывода (I/O) в ОС Linux — от пользовательского вызова системной функции до физического блочного устройства через VFS, Page Cache, файловые системы, блочный слой (Block Layer) и Device-Mapper (LVM).

## Модель архитектурных слоёв I/O

Подсистема ввода-вывода ядра Linux представляет собой многоуровневую структуру абстракций, разделяющих пользовательское пространство (User Space) и аппаратуру хранения данных.

```text
Пространство пользователя (User Space)
    │
    │ open() / read() / write() / fsync()
    ▼
Виртуальная файловая система (VFS)
    │
    ├── Dentry Cache (Иерархия путей)
    ├── Inode Cache (Метаданные объектов)
    ├── File Table (Открытые дескрипторы)
    └── Page Cache / address_space (Буферизация страниц)
    │
    ▼
Конкретная файловая система (ext4 / XFS / Btrfs)
    │
    ▼
Блочный слой (Block Layer / I/O Scheduler)
    │ (Формирование структур bio и request)
    ▼
Device Mapper (LVM / thin-pool / dm-crypt)
    │
    ▼
Драйвер блочного устройства (NVMe, AHCI, virtio-blk)
    │
    ▼
Физический накопитель (NVMe SSD / SATA SSD / HDD)
````

### Ключевые сущности VFS

- **Файл (File Object):** Динамическая структура данных ядра, отражающая открытый процессом экземпляр файла.
- **Inode (Index Node):** Статическая структура метаданных, однозначно описывающая физический объект на диске.
- **Dentry (Directory Entry):** Связующее звено в памяти, ассоциирующее символьное имя элемента пути с конкретным номером `inode`.

VFS изолирует пользовательские приложения от специфики реализации конкретных файловых систем, предоставляя единую семантику системных вызовов POSIX.

## Структура и метаданные: Inode

### Концепция Inode и разграничение с именами файлов

**Inode** — структура данных файловой системы, хранящая системные атрибуты объекта и указатели на его блоки данных.

#### Атрибуты, содержащиеся в Inode:

- Тип объекта (обычный файл, каталог, символьная ссылка, socket, FIFO, блочное/символьное устройство);
- Права доступа (POSIX mode) и списки контроля доступа (ACL);
- Идентификаторы владельца и группы (UID / GID);
- Точный размер объекта в байтах и количество выделенных секторов;
- Счетчик жестких ссылок (`i_nlink`);
- Временные метки (`atime`, `mtime`, `ctime`, `crtime`);
- Флаги и расширенные атрибуты (xattrs);
- Карты адресации экстентов (Extents Tree) или экстентных блоков.

> **Важно:** Имя файла **никогда** не хранится в самом Inode.

Имена файлов содержатся в блоках данных каталогов. Структура данных каталога сопоставляет строковое имя файла с соответствующим номером Inode.

```
Каталог (Directory Block Data)
┌──────────────────────────────┐
│ "application.log" ───────────┼──► Inode #1048576
│ "application.log.old" ───────┼──► Inode #1048576 (Hard link)
└──────────────────────────────┘
                                       │
                                       ├── Метаданные объекта
                                       └── Дерево экстентов (Данные)
```

Из этого следуют следующие фундаментальные выводы:

1. Имя файла является лишь меткой в структуре каталога, указывающей на Inode.
2. Жёсткая ссылка (Hard Link) — это дополнительная запись в каталоге, указывающая на уже существующий Inode. Создание жесткой ссылки не дублирует данные файла.

### On-disk inode и VFS struct inode

Следует разграничивать представления структур Inode:

1. **On-disk Inode:** Физическая структура фиксированного размера (например, 256 байт в ext4), записанная в специализированной области накопителя (Inode Table).
2. **VFS `struct inode`:** Структура данных в RAM ядра, создаваемая динамически при обращении к файлу для универсального управления объектом в памяти.

```
On-Disk Inode (Таблица на диске)
        │
        ▼ (Чтение при открытии / обращении)
Specific Filesystem Inode (Память драйвера ext4/xfs)
        │
        ▼
VFS struct inode (Универсальный объект ядра)
```

### Причины и диагностика исчерпания емкости inode

Файловая система может исчерпать свободные структуры Inode при наличии значительного объема свободного дискового пространства в байтах.

```sh
df -h /var
df -i /var
```

#### Сравнительный пример состояния:

```sh
$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1       100G   40G   60G  40% /var

$ df -i /var
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1       6553600 6553600       0  100% /var
```

При `IFree = 0` любые попытки создания новых файлов, каталогов или сокетов приводят к ошибке `No space left on device` (код ошибки `ENOSPC`), несмотря на наличие 60 Гб свободного места для блоков данных.

#### Архитектурные различия файловых систем:

- **ext4:** Статическая таблица Inode. Количество Inode задается строго в момент форматирования (`mkfs.ext4`) на основе соотношения `bytes-per-inode`. Изменение числа Inode на существующей ФС невозможно без пересоздания.

```sh
tune2fs -l /dev/sda1 | grep -E 'Inode count|Free inodes|Inode size'
```

- **XFS:** Динамическое выделение пространств под Inode (Inode Chunks). Ограничение задается параметром `maxpct` (максимальный процент пространства ФС, который разрешено занять под структуры Inode).

```sh
xfs_info /mountpoint
```

### Методика поиска директорий с высоким количеством мелких файлов

Для локализации каталогов с аномальным количеством созданных объектов используется следующий конвейер (с исключением внешних точек монтирования):

```sh
find /var -xdev -type f -printf '%h\n' 2>/dev/null | sort | uniq -c | sort -rn | head -20
```

> **Примечание:** На масштабных файловых массивах выполнение системных вызовов `readdir()`/`stat()` утилитой `find` создает высокую нагрузку на I/O метаданных. При возможности рекомендуется локализовать поиск по предполагаемым путям (например, `/var/spool/`, `/var/tmp/`, директории сессий).

## Управление открытыми и удалёнными файлами

### Механика сохранения пространства при удалении открытых файлов (`rm`)

Системный вызов `unlink()` (вызываемый утилитой `rm`) удаляет запись из структуры каталога и уменьшает счетчик ссылок `i_nlink` в Inode на единицу.

```
Каталог (Directory Entry) ─────X (rm / unlink)
                               │
Inode ◄────────────────────────┴── Open File Description ◄── Process FD
  │
  ├── i_nlink = 0
  └── i_count > 0 (Данные удерживаются в памяти и на диске)
```

Освобождение блоков данных файловой системой происходит только при соблюдении **обоих условий**:

1. Счетчик жестких ссылок равен нулю (`i_nlink == 0`).
2. Счетчик открытых файловых дескрипторов в ядре равен нулю (`i_count == 0`).

Если процесс удерживает файловый дескриптор открытым, он сохраняет возможность выполнения операций `read()` и `write()`, а выделенные блоки диска не возвращаются в пул свободных блоков ФС.

### Диагностика открытых удалённых дескрипторов

Для поиска процессов, удерживающих удаленные файлы, используются инструменты `lsof` или анализ виртуальной ФС `/proc`:

```sh
lsof -nP +L1
# или
lsof -nP | grep '(deleted)'
```

Прямой анализ через подсистему `/proc`:

```sh
ls -l /proc/<PID>/fd
```

Пример вывода:

```sh
lrwx------ 1 app app 64 Sep 25 10:00 7 -> /var/log/application.log (deleted)
```

### Освобождение пространства через `/proc` без останова процесса

В ситуациях, когда остановка процесса недопустима, освободить занятые блоки данных удерживаемого файла лога можно путем принудительного усечения размера файла через дескриптор в `/proc`:

```sh
: > /proc/<PID>/fd/<FD>
```

Данная операция выполняет системный вызов `ftruncate()`, сбрасывая размер файла до 0 байт и освобождая экстенты на диске.

> **Внимание:** Метод применим исключительно к текстовым логам и потоковым файлам. Если процесс выполняет запись без флага `O_APPEND` и отслеживает смещение (file offset) внутри файла самостоятельно, сброс размера может привести к созданию разреженного файла (sparse file) с позиционированием в прежний offset и фактическому невозврату дискового пространства.

### Проблематика и риски использования `copytruncate`

При применении утилиты `logrotate` с директивой `copytruncate` выполняются два последовательных шага:

1. Копирование текущего содержимого лог-файла в резервный файл.
2. Усечение исходного файла до нулевого размера через `ftruncate()`.   

#### Проблема состояния гонки (Race Condition):

```
Процесс ротации:  [=== Чтение и копирование ===] ──────────────► [ftruncate(0)]
Записывающий сервис:  ─────────────────────────► [Запись логов] ───^
                                                     │
                                                     ▼
                                            Потерянные данные
```

Данные, записанные приложением в интервале между завершением копирования и моментом вызова `ftruncate()`, уничтожаются.

**Рекомендованный паттерн ротации:** Использование атомарной операции переименования (`rename()`) файла с последующей отправкой процессу сигнала переоткрытия файловых дескрипторов (`SIGHUP` / `SIGUSR1`).

## Виртуальная файловая система (VFS)

VFS предоставляет абстрактный объектно-ориентированный слой, обеспечивающий работу системных вызовов над разрозненными структурами физических и сетевых файловых систем.


```
               POSIX System Calls (read, write, open)
                                │
                                ▼
                   VFS (Virtual File System)
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
Local FS (ext4 / XFS)   Network FS (NFS / SMB)   Pseudo FS (procfs / sysfs)
```

---
## Объекты VFS: Dentry, Inode и File Descriptor

### Dentry (Directory Entry)

Структура `struct dentry` связывает иерархический элемент пути (filename) с соответствующим `struct inode`. Dentry кэшируются в оперативной памяти (Dentry Cache / dcache), исключая необходимость постоянного считывания блоков каталогов с диска при разрешении путей.

### Inode

Структура `struct inode` на уровне VFS содержит все метаданные объекта и табличные указатели на функции конкретной файловой системы (`i_op`, `i_fop`).

### File Object и File Descriptor

- **`struct file`:** Создается ядром при каждом вызове `open()`. Содержит текущую позицию указателя записи/чтения (file offset), флаги открытия (`O_RDWR`, `O_APPEND`) и ссылку на соответствующий `struct dentry`.
- **File Descriptor (FD):** Интегральный индекс в таблице открытых файлов конкретного процесса, указывающий на `struct file`.


```
Process File Table (FD) ──► struct file (Offset, Flags) ──► struct dentry ──► struct inode
```

---
## Модели ввода-вывода (Page Cache и Direct I/O)

### Разграничение Buffered I/O и Direct I/O (`O_DIRECT`)

При использовании буферизованного ввода-вывода (Buffered I/O) данные передаются через виртуальную память ядра (Page Cache).

```
User Space Buffer
        │
        │ write()
        ▼
Page Cache (Kernel Space)
        │
        ├──► [Dirty Page] ──► Writeback (wb_workfn) ──► Block Layer ──► Device
        │
        └──► Direct I/O (O_DIRECT) ─────────────────────► Block Layer ──► Device
```

#### Характеристики механизмов:

1. **Buffered I/O:** Вызов `write()` завершается после копирования данных из пользовательского буфера в страницы Page Cache ядра. Страница маркируется флажком `dirty`. Запись на физический диск откладывается.
2. **Direct I/O (`O_DIRECT`):** Минует Page Cache. Драйвер выполняет прямое копирование страниц памяти пользователя (DMA) в контроллер накопителя. Требует строгого выравнивания размера буфера и смещения по размеру физического сектора диска.
3. **Synchronous I/O (`O_SYNC` / `O_DSYNC`):** Запись транслируется через Page Cache, но системный вызов блокирует поток до полного завершения записи блоков накопителем.

### Задержки вызова `write()`

Утверждение о том, что вызов `write()` при буферизованном I/O завершается мгновенно, является ошибочным. Задержки (latency spikes) возникают в следующих случаях:

- Превышение порогов загрязнения памяти (`vm.dirty_ratio`), приводящее к принудительному переключению процесса в режим синхронного сброса страниц (Throttling).
- Выделение новых блоков на физическом диске при заполнении файла (`alloc-on-fault`).
- Конкуренция за блокировки (locks) на уровне метаданных VFS/Inode.

---
## Механизмы сброса изменённых страниц (Writeback)

### Потоки ядра `wb_workfn` и расчет Dirtyable Memory

Перенос грязных страниц из Page Cache на физические блочные устройства выполняется рабочими потоками ядра `wb_workfn` (сменившими механизмы `pdflush` и `flusher threads`).

Расчет порогов `sysctl` осуществляется ядром от объема **памяти, доступной для загрязнения (Dirtyable Memory)**, а не от всей установленной физической RAM:

$$\text{Dirtyable Memory} = \text{Free Pages} + \text{Reclaimable Page Cache} - \text{Reserved Memory}$$

### Параметры `sysctl` управления Writeback

#### Конфигурация пороговых значений:

- **`vm.dirty_background_ratio` / `vm.dirty_background_bytes`:** Порог изменённой памяти, при достижении которого ядро фоново задействует потоки `wb_workfn` для асинхронного сброса данных. Процессы пользователя при этом не блокируются.
- **`vm.dirty_ratio` / `vm.dirty_bytes`:** Критический порог изменённой памяти. При его достижении ядро переводит записывающие процессы в режим принудительной синхронной записи (Process Throttling). Процесс начинает сбрасывать грязные страницы в контексте собственного системного вызова `write()`.
- **`vm.dirty_expire_centisecs`:** Время жизни грязной страницы (в сотых долях секунды). По истечении этого времени страница помечается как устаревшая и принудительно скидывается при следующем проходе `wb_workfn`.
- **`vm.dirty_writeback_centisecs`:** Периодичность пробуждения потоков `wb_workfn` для проверки наличия устаревших страниц.

> Установка абсолютных значений в байтах (`*_bytes`) автоматически обнуляет соответствующие процентные параметры (`*_ratio`), и наоборот.

---
## Влияние параметров Dirty Limits на стабильность системы

На высоконагруженных серверах с большим объемом RAM (например, 256 ГБ) стандартное значение `dirty_ratio = 20%` может привести к накоплению до 50 ГБ незаписанных данных в RAM.

При последующей интенсивной синхронизации это вызывает эффект «I/O Stalls» — резкий рост latency дисковой подсистемы и заморозку вызовов `write()`.

### Рекомендованный подход к настройке:

Для систем с высокой интенсивностью записи рекомендуется переходить от процентных значений к абсолютным ограничениям в байтах:

```Ini, TOML
vm.dirty_background_bytes = 268435456   # 256 MiB
vm.dirty_bytes = 1073741824              # 1 GiB
```

--- 
## Мониторинг состояния Dirty Memory

Для оперативного контроля объёма грязной памяти в системе используется `/proc/meminfo`:

```sh
grep -E '^(Dirty|Writeback|WritebackTmp):' /proc/meminfo
```

Пример вывода:

```
Dirty:            134852 kB  # Объем страниц, ожидающих записи
Writeback:          4120 kB  # Объем страниц, записываемых на диск в данный момент
WritebackTmp:          0 kB  # Временный буфер (используется FUSE и ZFS)
```

---
## Гарантированная синхронизация: `fsync()` и `fdatasync()`

### Разграничение семантики вызовов

Синхронизация данных Page Cache с физическим носителем обеспечивается специализированными системными вызовами:

1. **`fsync(int fd)`:** Выполняет сброс изменённых страниц данных файла **и всех метаданных** `inode` (размер файла, метки `mtime`/`ctime`, атрибуты, дерево блоков). Требует фиксации транзакции в журнале файловой системы (Journal Commit).
2. **`fdatasync(int fd)`:** Сбрасывает на диск данные файла и **только метаданные, необходимые для корректного считывания этих данных** (например, изменение размера файла `i_size`). Обновление атрибутов вроде `st_atime` или `st_mtime` на диск принудительно не сбрасывается, что существенно снижает количество I/O операций с журналом ФС.

```sh
fsync():     [Данные файла] ──► [Все метаданные Inode] ──► [Журнал ФС (Journal)]
fdatasync():  [Данные файла] ──► [Критичные метаданные (i_size)]
```

### Энергонезависимость и аппаратный кэш накопителя

Возврат управления из вызовов `fsync()`/`fdatasync()` гарантирует, что данные покинули RAM ядра.

Однако если на самом физическом диске включен энергозависимый кэш записи (Volatile Write Cache), ядро транслирует вызовы в аппаратные команды очистки кэша накопителя (`FLUSH CACHE` для SATA/SAS или `Flush command` для NVMe).

## Логические тома LVM (Logical Volume Manager)

LVM2 предоставляет слой виртуализации блочных устройств поверх физических дисков с использованием модуля ядра Device-Mapper.

```
Физические диски (NVMe / SATA / VirtIO)
                 │
                 ▼
     Physical Volumes (PV)
                 │
                 ▼
      Volume Groups (VG)
                 │
                 ▼
     Logical Volumes (LV)
                 │
                 ▼
Файловая система (ext4 / XFS)
```

---
## Physical Volume (PV)

**Physical Volume (PV)** — блочное устройство (весь диск или отдельный раздел), размеченное для использования подсистемой LVM.

Инициализация PV:

```sh
pvcreate /dev/sdbh
```

При инициализации пространство PV разбивается на сетку блоков фиксированного размера — **Physical Extents (PE)**. По умолчанию размер PE составляет 4 MiB, но может быть изменен при создании VG.

---
## Volume Group (VG)

**Volume Group (VG)** — объединение одного или нескольких PV в единый пул экстентов (Storage Pool).

Создание VG:

```
vgcreate vg_data /dev/sdb /dev/sdc
```

VG не содержит логики файловой системы, а представляет собой конструктор дискового пространства.

## Logical Volume (LV)

**Logical Volume (LV)** — логическое блочное устройство, создаваемое из доступных PE в Volume Group.

Создание тома:

```sh
lvcreate -L 50G -n lv_data vg_data
```

Логические тома регистрируются в системе как блочные устройства по путям:

- `/dev/vg_data/lv_data`
    
- `/dev/mapper/vg_data-lv_data`
 

## Процедура расширения дискового пространства VM

Увеличение дискового пространства логического тома в виртуальной среде требует последовательного изменения настроек на всех уровнях стека:



```
1. Hypervisor Disk ──► 2. SCSI/NVMe Bus ──► 3. Partition Table ──► 4. PV ──► 5. VG ──► 6. LV ──► 7. Filesystem
```

### Сканирование изменений на уровне шины устройства

После изменения размера диска на гипервизоре необходимо дать команду ядру пересканировать размер блочного устройства.

Для устройств SCSI/SATA:



```
echo 1 > /sys/class/block/sda/device/rescan
```

Для устройств NVMe сканирование шины выполняется автоматически или с помощью утилиты `nvme-cli`.

## Расширение PV, размещённого на разделе диска

Если структура PV размещена поверх раздела (например, `/dev/sda3`):

1. **Увеличить размер физического раздела:**
    
    
    
    ```
    growpart /dev/sda 3
    ```
    
2. **Считать изменения таблицы разделов:**
    
    
    
    ```
    partx -u /dev/sda3
    ```
    
3. **Выполнить ресайз структуры LVM PV:**
    
    
    
    ```
    pvresize /dev/sda3
    ```
## Расширение PV, размещённого на цельном устройстве

Если PV создан непосредственно на дисковом устройстве без таблицы разделов (`/dev/sdb`):

```
pvresize /dev/sdb
```

---
## Изменение размера Logical Volume (LV)

Выделение всего доступного нераспределенного пространства VG для тома `lv_root`:

```sh
lvextend -l +100%FREE /dev/vg_system/lv_root
```

Использование флага `-r` (`--resizefs`) заставляет LVM автоматически вызвать утилиту изменения размера файловой системы после успешного расширения тома:

```sh
lvextend -r -l +100%FREE /dev/vg_system/lv_root
```

---
## Изменение размера файловых систем

### Расширение ext4

Файловая система ext4 поддерживает онлайн-расширение без отмонтирования. В качестве аргумента передается путь к блочному устройству:

```sh
resize2fs /dev/vg_system/lv_root
```
### Расширение XFS

Файловая система XFS поддерживает расширение **только в смонтированном состоянии**. В качестве аргумента утилите передается **точка монтирования**:

```sh
xfs_growfs /
```

---
## Сквозной регламент расширения LVM + ext4

Исходная задача: Увеличение системного диска `/dev/sda` с 50 ГБ до 100 ГБ на виртуальной машине с ФС ext4 на корневом томе.

```sh
# 1. Проверить текущую конфигурацию
lsblk

# 2. Инициировать повторное сканирование шины диска
echo 1 > /sys/class/block/sda/device/rescan

# 3. Увеличить размер 3-го раздела
growpart /dev/sda 3

# 4. Обновить физический объем LVM
pvresize /dev/sda3

# 5. Увеличить LV и автоматически запустить изменение размера ФС
lvextend -r -l +100%FREE /dev/vg_system/lv_root

# 6. Проверить полученный объем
df -h /
```

## Архитектура LVM Thin Provisioning

### Концепция избыточного выделения (Overprovisioning)

Механизм Thin Provisioning разрешает выделять логическим томам (Thin LVs) виртуальные объемы, превышающие реальную физическую емкость хранилища.

```
Физический Thin Pool: 100 ГБ
 ├── Thin LV1 (Virtual: 50 ГБ, Real Used: 10 ГБ)
 ├── Thin LV2 (Virtual: 50 ГБ, Real Used: 20 ГБ)
 └── Thin LV3 (Virtual: 50 ГБ, Real Used: 15 ГБ)
Итого виртуальный объем: 150 ГБ (Физически занято: 45 ГБ)
```

Физические блоки выделяются томам динамически («по требованию», Allocation on Demand) в момент совершения реальных операций записи.

### Структура Thin Pool (`_tdata` и `_tmeta`)

Thin Pool является составным объектом Device-Mapper, включающим два внутренних тома:

1. **`_tdata` (Data LV):** Хранилище реальных блоков данных пользователей.
2. **`_tmeta` (Metadata LV):** Хранилище метаданных адресации, снимков (snapshots) и деревьев виртуальных пространств `dm-thin`. 
---
## Специфика мониторинга ресурсов в Thin Pool

Поскольку файловая система внутри Thin LV видит только свой виртуальный размер, вывод утилиты `df -h` не показывает реальное остаточное место в физическом пуле.

Для мониторинга используется команда анализа томов LVM:

```sh
lvs -o lv_name,lv_size,pool_lv,data_percent,metadata_percent
```

Пример вывода:

```sh
LV       LSize   Pool   Data%  Meta%
pool0    100G           78.50  24.10
thin_lv1  50G    pool0  12.00
```

---
## Поведение Device-Mapper при исчерпании емкости Thin Pool

При 100% заполнении физического пространства данных (`Data%`) или метаданных (`Meta%`) подсистема `dm-thin-pool` переходит в состояние обработки ошибок, определяемое настройками ядра.

#### Варианты реакций системы:

1. **`error_if_no_space` (По умолчанию):** Запросы на запись, требующие выделения новых экстентов в Thin Pool, мгновенно завершаются с ошибкой ввода-вывода (`EIO`). Файловая система переходит в режим `read-only`, приложения завершаются с ошибкой.
2. **`queue_if_no_space`:** Запросы на запись задерживаются и встают в очередь в ожидании расширения пула. Если свободное пространство не выделяется до истечения таймаутов, операции падают по `EIO`.

> Переполнение метаданных (`Meta%`) приводит к блокированию операций со снимками и повреждению метаданных пула.

## Автоматическое расширение Thin Pool (`dmeventd`)

Демон мониторинга `dmeventd` позволяет автоматически увеличивать размер Thin Pool при достижении заданных порогов заполнения.

Конфигурация в `/etc/lvm/lvm.conf`:

```Ini, TOML
activation {
    thin_pool_autoextend_threshold = 80   # Порог срабатывания в %
    thin_pool_autoextend_percent = 20     # Процент добавления емкости
}
```

Для работы авторасширения в составе Volume Group должны присутствовать свободные нераспределенные экстенты (Unallocated Physical Extents).

---
## Интерпретация метрик Data% и Meta%

|**Метрика**|**Объект контроля**|**Риски при переполнении**|**Рекомендуемые действия**|
|---|---|---|---|
|**`Data%`**|Заполнение физических блоков данных|Переход ФС в Read-Only, ошибки записи `EIO`|Расширить Thin Pool через `lvextend`, выполнить TRIM|
|**`Meta%`**|Пространство адресации и снимков LVM|Полная блокировка пула, невозможность работы снимков|Увеличить размер `_tmeta` через `lvextend --poolmetadatasize`|

---
## Освобождение неиспользуемого пространства (TRIM/Discard)

При удалении файлов внутри файловой системы блоки на Thin LV не освобождаются в физическом Thin Pool автоматически.

Для возврата блоков в пул требуется передача команд Discard/TRIM от файловой системы к `dm-thin-pool`.

#### Инструменты освобождения:

- **Периодический сброс по расписанию (Рекомендуется):**

```sh
 fstrim -av
```

- **Динамический сброс (Опция монтирования):** Монтирование ФС с опцией `discard` (создает дополнительные задержки I/O при частых удалениях мелких файлов).

## Сквозная трассировка операции `write()`

Детализированная схема обработки операции записи в файл:

```
1. User Space: Вызов write(fd, buf, count)
   │
2. VFS: Проверка прав, позиционирование offset, получение struct file и struct inode
   │
3. Page Cache: Выделение/поиск страниц (pages), копирование данных из пространства пользователя, пометка страниц как 'dirty'
   │
4. Kernel Writeback: Поток wb_workfn просыпается по таймеру или порогу dirty_ratio
   │
5. Filesystem Driver (ext4/XFS): Трансляция логического смещения в файле в блоки диска (Extent Allocation)
   │
6. Block Layer: Формирование структур 'bio', объединение запросов в очереди (I/O Scheduler)
   │
7. Device Mapper: Трансляция секторов логического тома в физические сектора PV
   │
8. Device Driver (NVMe/AHCI): Формирование DMA-команд, передача контроллеру диска
   │
9. Hardware: Запись данных во внутренний кэш/NAND-ячейки диска
```

## Классификация метрик производительности I/O

Для локализации узких мест подсистемы I/O следует ориентироваться на следующие показатели утилиты `iostat -xz 1`:

- **`r/s`, `w/s`:** Количество операций чтения/записи в секунду (IOPS).
- **`rkB/s`, `wkB/s`:** Объем считываемых/записываемых данных в секунду (Пропускная способность / Throughput).
- **`await` (`r_await`, `w_await`):** Среднее время обработки запроса устройством, включая время нахождения в очереди (Latency, в миллисекундах). Норма для NVMe: < 1ms, для SSD: < 5ms, для HDD: < 15-20ms.
- **`aqu-sz`:** Средняя длина очереди запросов к устройству.
- **`%util`:** Процент времени, в течение которого диск был загружен работой. На современных SSD метрика может достигать 100% из-за параллелизма каналов, не являясь единственным показателем насыщения.

## Свод фундаментальных технических различий

### Inode vs Filename

`Inode` — объект ФС с атрибутами файла на диске. `Filename` — строка в блоке данных каталога, указывающая на номер `Inode`.

### Inode vs File Descriptor

`Inode` отражает файл на диске. `File Descriptor` — целое число процесса, указывающее на `struct file` в RAM ядра, хранящую контекст работы с этим файлом (offset, флаги).

### `df -h` vs `df -i`

`df -h` оценивает объем занимаемых блоков данных на диске (в байтах). `df -i` оценивает количество занятых и свободных метаструктур `Inode`.

### `df -h` vs LVM Thin `Data%`

`df -h` показывает виртуальный объем с точки зрения файловой системы. `Data%` показывает процент физически задействованного пространства внутри Thin Pool.

### `write()` vs Энергонезависимость

Успешный возврат `write()` означает попадание данных в Page Cache. Энергонезависимая гарантия сохранности на носителе достигается только после вызовов `fsync()` / `fdatasync()`.

## Практические регламенты ликвидации аварийных ситуаций

### Регламент 1: Переполнение ФС (`df -h` = 100%)

1. Проверить наличие удаленных файлов, удерживаемых процессами: `lsof -nP +L1`.
2. В случае нахождения сбросить размер логов без перезапуска демона: `: > /proc/<PID>/fd/<FD>`.
3. Локализовать самые крупные директории: `du -xhd1 / | sort -h`.  

### Регламент 2: Исчерпание Inode (`df -i` = 100%)

1. Выполнить локализацию каталога с большим количеством мелких файлов с помощью сценария на базе `find`.
2. Очистить директории временных файлов или сессий (`rm` или `find -delete`).

### Регламент 3: Деградация I/O Latency (Высокий `await`)

1. Проверить объем грязной памяти в `/proc/meminfo`.
2. Проверить, не активирован ли процесс принудительной синхронизации из-за превышения `vm.dirty_ratio`.
3. Определить процесс-источник аномальной нагрузки через `pidstat -d 1`.

## Терминологический словарь

- **Page Cache:** Кэш страниц памяти ядра, используемый для буферизации I/O операций с файлами.
- **Dirty Page:** Страница в Page Cache, модифицированная в RAM, но еще не записанная на дисковый накопитель.
- **Writeback:** Фоновый процесс синхронизации измененных страниц памяти на энергонезависимое устройство.
- **Dentry:** Структура VFS, связывающая имя файла с метаданными Inode и кеширующая иерархию путей.
- **Physical Extent (PE):** Минимальный непрерывный блок дискового пространства в LVM.
- **Thin Provisioning:** Технология виртуализации хранилища, обеспечивающая динамическое выделение блоков физической памяти при записи.
- **TRIM / Discard:** Команда интерфейса накопителей, оповещающая контроллер диска или подсистему thin-pool об освобождении блоков на уровне ФС.
