# Справочник расширенных способов запуска команд в Linux: Очереди, подстановки, фоновые пулы и замещение процессов

Оболочка Linux предоставляет 11 фундаментальных механизмов ветвления, перенаправления и параллелизации выполнения команд на уровне системных вызовов ядра.

---

## 1. Условные списки на базе кодов возврата (`&&` и `||`)

Каждая утилита после завершения возвращает ядру числовой код (`exit code`), записываемый в системную переменную `$?`. Код `0` означает абсолютный успех, любой код `≥ 1` — ошибку.

### Оператор И (`&&`) — Выполнение при успехе

Следующая команда запустится строго в том случае, если предыдущая вернула `0`.

```bash
# Сборка и деплой запустятся только если тесты прошли успешно
go test ./... && go build -o app && ./deploy.sh
```

### Оператор ИЛИ (`||`) — Выполнение при сбое

Следующая команда запустится строго в том случае, если предыдущая вернула ошибку (`≥ 1`).

```bash
# Аварийный выход из скрипта с фиксацией кода ошибки, если директория недоступна
cd /var/log/audit || { echo "Критично: Нет доступа к аудиту" >&2; exit 1; }
```

### ⚠️ Смертоносная ловушка мнимого тернарного оператора

Многие используют конструкцию `Команда_А && Команда_Б || Команда_В` как аналог `if/then/else`.

- **Где сокрыта авария:** Если `Команда_А` завершилась успешно (`0`), шелл послушно запускает `Команду_Б`. Но если `Команда_Б` в процессе своей работы **внезапно споткнулась и вернула ошибку (не `0`)**, шелл воспринимает всю левую цепочку как сбойную и **начнет выполнять `Команду_В`**.
- **Решение (Безопасная группировка в подоболочку):**

```bash
# Гарантирует, что команда очистки запустится ТОЛЬКО если cd упал
(cd /tmp/pool && rm -f *.tmp) || echo "Ошибка: Директория пула не найдена"
```

## 2. Безусловные списки (`;`)

Команды выполняются строго последовательно друг за другом независимо от результатов выполнения предыдущих шагов.

```bash
# Итоговый код возврата ($?) будет равен коду ПОСЛЕДНЕЙ команды (mv c d)
mv a b; mv b c; mv c d; echo $?
```

_Инженерный нюанс:_ Промежуточные коды ошибок полностью теряются. Если `mv a b` упадет из-за отсутствия файла, шелл все равно попытается выполнить последующие команды, что может привести к непредсказуемому состоянию ФС.

## 3. Подстановка команд (`$()`)

Шелл выполняет команду внутри скобок, перехватывает её `stdout` и подставляет этот текст прямо в текущую строку.

```bash
# Запись вывода в переменную (Кавычки обязательны для сохранения форматирования и пробелов)
active_workers=$(pgrep -f "worker_app")
echo "$active_workers"
```

### ⚠️ Ловушка переполнения буфера `ARG_MAX`

Никогда не используйте подстановку типа `rm $(find . -name "*.log")` в каталогах с миллионами файлов. Вывод развернется в гигантскую строку аргументов, и ядро заблокирует вызов с ошибкой `Argument list too long`. Для массовой обработки используйте потоковый `xargs` (см. Способ 8).

## 4. Подстановка процесса (Process Substitution: `<()`)

Киллер-фича ядер Linux, позволяющая **использовать вывод команды как физический файл** там, где утилита не умеет работать со стандартным потоком `stdin`.

```bash
# Синтаксис: <(команда)
echo <(whoami) # Выведет виртуальный путь ядра: /dev/fd/63
```


_Физика процесса:_ Шелл создает анонимный именованный пайп (FIFO) на уровне VFS и связывает его с дескриптором в `/dev/fd/N`. Принимающая программа думает, что читает обычный файл с диска, но данные стримятся напрямую из RAM без дискового ввода-вывода.

### Боевые примеры для инженера:

```
# 1. Аудит живых служб против эталонного текстового списка
diff <(systemctl list-units --type=service --state=active --no-legend | awk '{print $1}') \
     <(sort /etc/allowed-services.txt)

# 2. Сравнение установленных пакетов на локальном и удаленном серверах по SSH на лету
diff <(dpkg --get-selections | sort) \
     <(ssh root@backup-server "dpkg --get-selections | sort")
```

## 5. Динамическое выполнение строк через `bash -c`

Запускает изолированную **дочернюю оболочку**, которая выполняет переданную текстовую строку как исполняемый код.

Решение проблемы `sudo` с перенаправлением потоков

- **❌ Ошибка:** `sudo echo "data" > /etc/protected.conf` (Permission denied, так как само перенаправление `>` выполняется шеллом текущего бесправного пользователя _до_ активации `sudo`).
- **✅ Решение:** Передать всю строку внутрь рутового шелла (используйте строго одинарные кавычки для защиты строки от преждевременного раскрытия родителем):

```bash
sudo bash -c 'echo "data" > /etc/protected.conf'
```

## 6. Потоковое выполнение через стандартный ввод (`| bash`)

Позволяет генерировать код команд программно (через `sed`/`awk`/`echo`) и пакетно скармливать его на вход интерпретатору.

```bash
# Шаблон: Генерируем -> Проверяем глазами -> Выполняем через | bash
ls ??* | sed 's/^\(.\)\(.*\)$/mv "\1\2" \1/' | bash
```

## 7. Удаленное беспроцессное выполнение через `ssh`

Запуск одиночной команды на удаленном хосте без аллокации полноценного интерактивного псевдотерминала (`pseudo-TTY`).

```bash
# Флаг -T отключает TTY, предотвращая засорение логов приветственными баннерами (motd)
echo "uptime" | ssh -T root@remote-node-1 bash
```

_⚠️ Ловушка локации перенаправления:_

- `ssh server "ls > file.txt"` — файл `file.txt` создастся **на удаленном сервере**.
- `ssh server ls > file.txt` — файл `file.txt` создастся **на локальном хосте**.

## 8. Массовая подстановка аргументов через `xargs`

Принимает список строк из `stdin` и пачками нарезает их в качестве аргументов для целевой утилиты.

### ⚠️ Продакшен-стандарт безопасной обработки имен файлов

Обычный конвейер `ls | xargs rm` намертво сломается или удалит не те данные, если в именах файлов встретятся пробелы или переводы строк. Единственный безопасный способ — разделение путей **нулевым байтом (`\0`)**:

```bash
# Находим логи и безопасно сжимаем их через xargs в параллельном режиме
find /var/log/app -name "*.log" -print0 | xargs -0 gzip
```

- `-print0` — заставляет `find` разделять пути строго символом `\0`.
- `-0` — указывает `xargs` парсить входящий поток строго по разделителю `\0`.

### Топ полезных флагов `xargs` под нагрузкой:

- `-n [N]` — ограничить количество аргументов, передаваемых в один системный вызов (напр., `-n 2`).
- `-I {}` — инлайн-подстановка. Позволяет вставить аргумент в произвольное место команды:

```bash
find . -name "*.conf" -print0 | xargs -0 -I {} cp {} {}.bak
```
 
- `-P [N]` — **Параллелизация ввода-вывода.** Запускает до `N` процессов одновременно. Идеально для параллельного скачивания файлов или бэкапов:

```
cat urls.txt | xargs -n 1 -P 8 wget
```

## 9. Управление фоновыми заданиями (Jobs & `&`)

Добавление символа `&` в конец команды отправляет всю синтаксическую цепочку (задание) в фоновый режим выполнения, мгновенно возвращая управление шеллу.

### Помните: Задание (Job) — это не Процесс (PID)

Задание — это внутренняя абстракция конкретного экземпляра Shell. Одно задание может включать в себя конвейер из десятка параллельных процессов.

### Чит-шит команд управления задачами

|Команда|Действие на уровне Shell|
|---|---|
|`jobs -l`|Показать список всех фоновых задач текущей сессии с их реальными PID|
|`fg %1`|Перевести фоновую задачу №1 на передний план (Foreground)|
|`bg %1`|Возобновить выполнение приостановленной задачи в фоне|
|`kill %1`|Послать сигнал `SIGTERM` задаче по её внутреннему номеру (не PID)|
|`Ctrl + Z`|Приостановить (поставить на паузу) текущий процесс на переднем плане (`Stopped`)|

### ⚠️ Ловушка SIGHUP при уничтожении TTY

При закрытии терминала или обрыве SSH-сессии фоновые процессы по умолчанию получают от родительского шелла сигнал **`SIGHUP (1)` (Hangup)** и аварийно завершаются.

**Профессиональный алгоритм запуска долгих фоновых задач:**

```bash
# 1. Запускаем тяжелый процесс с обязательным глушением вывода в лог (иначе stdout засорит TTY)
rsync -av /data/ /backup/ > /var/log/backup.log 2>&1 &

# 2. Полностью отвязываем последнюю фоновую задачу от таблицы заданий текущего Shell
disown %1
```

_После выполнения `disown` процесс вычёркивается из списка задач шелла. При закрытии терминала сигнал `SIGHUP` ему не прилетит, и он гарантированно продолжит работу как системный демон._

## 10. Замена процесса через `exec`

Утилита `exec` совершает системный вызов `execve()`, **намертво затирая текущий Shell кодом новой программы в памяти**. Без предварительного выделения нового PID (`fork`). После завершения вызванной программы терминал мгновенно закрывается.

Главные применения в DevOps-практике:

### 1. Оптимизация Docker-контейнеров (Entrypoint-скрипты)

Если ваш стартовый bash-скрипт в контейнере подготавливает окружение, а в конце запускает бинарник приложения, используйте строго `exec`. Иначе процесс `bash` останется висеть в памяти с `PID 1`, и контейнер перестанет реагировать на сигналы остановки оркестратора (`docker stop` / Kubernetes), превращаясь в зомби.

```bash
#!/bin/bash
# ... инициализация конфигураций ...
exec python3 main.py # Заместит bash, получит PID 1, будет корректно ловить сигналы
```

### 2. Глобальное перенаправление логов всего скрипта

Конструкция избавляет от необходимости дописывать `>> log.txt` в конце каждой строчки скрипта:

```bash
#!/bin/bash
# Направить вообще весь stdout и stderr скрипта в файл лога на уровне дескрипторов процесса
exec > /var/log/operation.log 2>&1

echo "Этот текст уйдет в лог автоматичеки"
ls /nonexistent_folder # Ошибка тоже запишется в лог
```
