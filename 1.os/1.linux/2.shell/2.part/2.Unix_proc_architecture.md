# Архитектура процессов Unix: Изоляция VFS, иерархия памяти, подсистемы окружения и подоболочки

В основе стабильности и безопасности операционных систем семейства Linux лежит принцип жесткой изоляции адресного пространства процессов. Каждый процесс выполняется в собственной изолированной виртуальной памяти и не может напрямую модифицировать состояние родителя или соседних задач.

---

## Иерархия процессов: Родственные связи в ядре

Каждый процесс в системе имеет строго **один прямой родительский процесс** (Parent Process, идентифицируемый по `PPID`), но может порождать неограниченное количество **дочерних процессов** (Child Processes, идентифицируемых по `PID`).

Вектор влияния в иерархии:

- **Снизу вверх (Блокировка):** Дочерний процесс никогда не может изменить окружение родителя. Если внутри скрипта выполнить `cd /etc` или `set TARGET=1`, эти изменения мгновенно уничтожатся вместе с завершением процесса скрипта. Родительский Shell останется в исходном состоянии.
- **Сверху вниз (Наследование):** Дочерний процесс получает слепок (копию) окружения родителя строго **в момент своего зарождения**. Любые изменения в родителе _после_ вызова `fork()` никак не затронут уже работающих потомков.

## Физика запуска команд: Как работает Конвейер (Pipes)

Конвейер (`command1 | command2`) не выполняет команды последовательно в одном процессе. Ядро Linux порождает **отдельный независимый дочерний процесс под каждую утилиту** внутри конвейера одновременно.

Например, данный конвейер порождает в системе сразу **6 параллельных процессов-потомков**:

```bash
cut -f1 grades | sort | uniq -c | sort -nr | head -n1 | cut -c9
```

_Как это устроено:_ Родительский Shell делает 6 вызовов `fork()`, связывает их файловые дескрипторы через системный вызов `pipe()` и запускает их параллельно. Они одновременно борются за кванты процессорного времени на CPU, передавая данные через кольцевые буферы в RAM.

## Подсистема окружения: Локальные переменные против Экспорта

В Linux переменные жестко разделены на два типа по области их видимости:

### 1. Локальные переменные сессии

Существуют строго внутри контекста текущего экземпляра оболочки. Они не заносятся в системные таблицы окружения и полностью невидимы для любых запускаемых программ и дочерних скриптов.

```bash
# Объявление локальной переменной (пробелы вокруг "=" запрещены!)
app_worker="active"

# Запуск дочерней оболочки Bash
bash

# Попытка прочитать переменную вернет пустоту — дочерний процесс её не унаследовал
echo $app_worker

# Выход из дочерней оболочки обратно к родителю
exit
```

### 2. Переменные окружения (Environment Variables)

Становятся доступными текущей оболочке и **всем её последующим дочерним процессам** вниз по дереву иерархии за счет механизма наследования.

```bash
# Переводим переменную в класс экспортируемых
export app_worker="active"

# Запуск дочернего процесса
bash

# Переменная успешно унаследована и выведется на экран: active
echo $app_worker
exit
```


#### ⚠️ Архитектурный нюанс: Как `export` работает под капотом ядра

Команда `export` не делает переменную глобальной для всей ОС (глобальных переменных в памяти Linux не существует). Она лишь помечает переменную специальным флагом внутри текущего Shell.

Когда Shell вызывает `execve()` для запуска утилиты, ядро считывает все помеченные переменные, формирует из них плоский текстовый массив `char *envp[]` и копирует его в выделенный стек памяти нового дочернего процесса.

#### Трюк: Временный экспорт (Single-command env)

Если переменная нужна строго для одного запуска и вы не хотите засорять окружение текущего терминала, задавайте её непосредственно перед вызовом утилиты:

```bash
# Переменная EDITOR уйдет в окружение только для этого конкретного вызова git
EDITOR=nano git commit
```

## Справочник критически важных переменных окружения

|Переменная|Назначение в системе|Инженерный нюанс применения|
|---|---|---|
|`$HOME`|Путь к домашнему каталогу пользователя|На основе этой переменной утилиты вроде `ssh` ищет ключи в `~/.ssh`|
|`$PWD`|Текущая рабочая директория процесса|Динамически обновляется ядром при каждом успешном вызове `chdir()`|
|`$USER`|Имя текущего залогиненного пользователя|Берется из системных таблиц PAM при аутентификации сессии|
|`$SHELL`|Путь к дефолтной командной оболочке|Используется терминалами для определения, что запускать (напр. `/bin/bash`)|
|`$EDITOR`|Предпочитаемый текстовый редактор системы|Критична для автоматизаций (изменяйте на `export EDITOR=vim`)|
|`$LANG`|Языковая локаль и кодировка символов|Неверная локаль (не UTF-8) ломает парсинг логов с кириллицей|

## Изоляция процессов: Дочерние оболочки против Подоболочек

Администраторы часто путают запуск дочернего шелла с созданием подоболочки. На уровне ядра Linux это принципиально разные сущности по объёму наследования контекста и состояний памяти.

### 1. Дочерняя оболочка (Child Shell)

Запускается явным вызовом `bash`, `zsh` или при старте любого внешнего скрипта.

- **Механика:** Создаётся абсолютно новый, независимый процесс. Он получает копию **строго экспортированных переменных окружения (`export`)**. Локальные переменные, функции и интерактивные псевдонимы (`alias`) родительской сессии в него **не наследуются**.

### 2. Подоболочка (Subshell)

Инициируется синтаксической конструкцией в круглых скобках **`( команды )`**.

- **Механика:** **⚠️ Архитектурная ловушка!** Вопреки мифам, подоболочка — это не работа «внутри одного процесса». Ядро физически делает полноценный системный вызов `fork()`, выделяя новый `PID`. Однако, в отличие от дочернего шелла, создаваемый процесс делает **точный слепок (клон) всей структуры памяти родителя** на момент запуска. Ему становятся доступны все локальные переменные, функции, опции шелла и даже алиасы.
- **Диагностика:** Используйте встроенную переменную `$BASH_SUBSHELL`. В основном процессе и в дочерней оболочке её значение равно `0`. Внутри подоболочки оно становится `>= 1` (в зависимости от уровня вложенности скобок).

### Лабораторный пример: Наследование контекста памяти

Чтобы наглядно увидеть разницу в изоляции, объявим в текущем терминале одну локальную переменную (без `export`) и один интерактивный алиас:

```bash
# Объявляем локальную переменную
local_token="secret_999"

# Создаем алиас
alias ll="ls -lAh"
```


#### Сценарий А: Тестирование Дочерней оболочки (Child Shell)

Новый процесс полностью отрезан от локального контекста родителя:

```bash
# 1. Запускаем дочерний процесс Bash
bash

# 2. Проверяем переменную — вернет пустоту (Переменная не была экспортирована)
echo $local_token 

# 3. Проверяем алиас — вернет ошибку (Алиасы не наследуются дочерними процессами)
ll
# Вывод: bash: ll: command not found

# 4. Проверяем уровень вложенности подоболочек
echo $BASH_SUBSHELL
# Вывод: 0 (Это самостоятельный базовый процесс, а не подоболочка)

# Выходим обратно к родителю
exit
```

#### Сценарий Б: Тестирование Подоболочки (Subshell)

Процесс клонирует память родителя и видит все его локальные структуры:

```bash
# Запускаем команды внутри подоболочки с помощью круглых скобок
(
  # 1. Переменная УСПЕШНО прочитается, хоть она и локальная
  echo "Токен внутри subshell: $local_token"
  
  # 2. Алиас УСПЕШНО отработает
  ll /etc/hosts
  
  # 3. Проверяем уровень вложенности подоболочки
  echo "Уровень subshell: $BASH_SUBSHELL"
)

# Вывод терминала:
# Токен внутри subshell: secret_999
# -rw-r--r-- 1 root root 158 Jan 12 10:00 /etc/hosts
# Уровень subshell: 1
```

### Боевой DevOps-пример: Безопасный чендждир (Change Directory)

Самый частый сценарий применения подоболочек в автоматизации — когда внутри тяжелого скрипта необходимо временно перейти в другую директорию, выполнить там сборку или архивацию, но при этом гарантировать, что основной скрипт не «потеряет» свой исходный рабочий каталог.

##### ❌ Деструктивный подход (Классический Bash-скрипт):

Администраторы часто пишут переходы туда-обратно руками через `cd`. Если команда сборки упадет посередине, скрипт прервется по ошибке, останется в чужой папке и на следующем шаге автоматизации (например, при очистке `rm -rf *`) затрет данные не в той директории.

```bash
cd /opt/app/src
make build
cd -  # Возврат назад. Если make build упадет, до этой строки выполнение не дойдет!
```

##### ✅ Профессиональный подход через Подоболочку:

Изолируем всю логику сборки в круглые скобки. Процесс подоболочки перейдет в нужную папку и сделает операцию. Как только скобка закроется, процесс подоболочки уничтожится, а родительский скрипт гарантированно останется в своей исходной директории, даже если сборка завершилась критическим сбоем.

```bash
# Исходный каталог
pwd # Вывод: /home/user/projects

# Изолированная операция в подоболочке
(cd /var/www/html/assets && tar -czf backup.tar.gz *.png)

# Мы гарантированно остались в исходной папке без лишних проверок и переходов
pwd # Вывод: /home/user/projects
```
