## Еще 4 способов запуска команды

До сих пор использовали два основных способа:
1. Простая команда: `grep Nutshell animals.txt`
2. Конвейер: `cut -f1 grades | sort | uniq -c`

Но оболочка предлагает гораздо больше гибкости. Ниже — 4 первые  из одиннадцати способов.

---

### Способ #1. Условные списки (`&&` и `||`)

Команды могут зависеть от результата предыдущих. Это управляется через **коды возврата**:
- `0` → успех  
- `≠0` → ошибка

##### Оператор `&&` — «выполни следующее, если всё хорошо»
```bash
cd dir && touch new.txt
```
> → `touch` запустится **только если** `cd` завершился успешно.

Практические примеры:
```bash
# Резервное копирование + редактирование + удаление бэкапа
cp file.txt file.safe && nano file.txt && rm file.safe

# Git workflow в одной строке
git add . && git commit -m "fix" && git push
```
##### Оператор `||` — «выполни, если что-то пошло не так»
```bash
cd dir || mkdir dir
```
>→ Если `cd` не удалось — создаём каталог.

Часто используется для аварийного выхода:
```bash
cd important_dir || exit 1
# Комбинирование
cd dir || mkdir dir && cd dir || echo "Не удалось войти или создать dir"
```

>Совет: группируйте сложные цепочки скобками, если нужно контролировать порядок:

```bash
(cd dir || mkdir dir) && cd dir
```

### Способ #2. Безусловные списки (`;`)

Команды выполняются **последовательно**, независимо от результата:

```bash
sleep 300; echo "Пора гулять с собакой!" | mail -s "Напоминание" $USER
```

Особенность:

- Код возврата всего списка — это код **последней** команды.
- Все промежуточные коды теряются.

Пример:
```bash
mv a b; mv b c; mv c d
echo $?  # покажет результат только последнего `mv`
```

>Используйте `;`, когда команды логически связаны, но не зависят друг от друга.

### Способ #3. Подстановка команд `$()`

Оболочка **выполняет команду и подставляет её вывод** прямо в строку.

Синтаксис:
```bash
команда $(другая_команда)
```

Аналог с обратными кавычками (устаревший, но рабочий):
```bash
mv `grep -l "Artist: Kansas" *.txt` kansas
```

Предпочтителен `$()` — он лучше читается и поддерживает **вложенность**:
```bash
echo Today is $(echo $(date +%A) | tr a-z A-Z)!
```

##### Сохранение результата в переменную
```bash
files=$(grep -l "Artist: Kansas" *.txt)
echo "$files"   # обязательно в кавычках!
```

>**Важно**: если имена файлов содержат пробелы, `$()` без дополнительной обработки **сломается**.  
В таких случаях лучше использовать `while read` или массивы .

##### Практический пример: открыть последний PDF
```bash
okular $(ls eStmt_*.pdf | tail -n1)
```

### Коды возврата: как проверить успех?

После любой команды проверьте `$?`:
```bash
ls existing.txt
echo $?   # 0 — успех

ls nonexistent.txt
echo $?   # 1 (или другое ≠0) — ошибка
```

Это то, на чём строятся `&&` и `||`.

### Способ #4. Подстановка процесса (`<()`)

Подстановка процесса — это мощный механизм, позволяющий **использовать вывод команды как файл**, не создавая временных файлов на диске. Это особенно ценно в задачах системного администрирования, где часто нужно сравнивать, фильтровать или синхронизировать данные между разными источниками.

Синтаксис:
```bash
<(команда)
```

Оболочка запускает `команда` в подоболочке и предоставляет её вывод через виртуальный файл в `/dev/fd/...`, который можно передать любой утилите, ожидающей путь к файлу.
#### Пример 1: Сравнить список запущенных служб с эталонным

Допустим, у вас есть эталонный список служб, которые **должны быть активны** на сервере (например, `nginx`, `sshd`, `cron`). Вы хотите проверить, не отключилась ли какая-то из них.

Эталонный список хранится в файле:
```bash
cat /etc/allowed-services.txt
# nginx
# ssh
# cron
```

Теперь сравните его с реально запущенными службами:
```bash
diff <(systemctl list-units --type=service --state=active --no-legend | awk '{print $1}' | sed 's/\.service$//') \
     <(sort /etc/allowed-services.txt)
```

Если вывод пуст — всё в порядке. Если есть расхождения — вы сразу видите, что лишнее запущено или что-то пропало.
#### Пример 2: Найти пользователей, у которых нет домашнего каталога

Сравним список пользователей из `/etc/passwd` с реальными каталогами в `/home`:
```bash
diff <(cut -d: -f1,6 /etc/passwd | grep '^.*:/home' | cut -d: -f1 | sort) \
     <(ls /home | sort)
```

- Левая часть: пользователи, у которых домашний каталог указан как `/home/...`
- Правая часть: реальные каталоги в `/home`

Результат покажет:
- `>` — каталог есть, но пользователя нет («мёртвый» домашний каталог)
- `<` — пользователь есть, но каталога нет (возможно, ошибка при создании)

#### Пример 3: Сравнить списки установленных пакетов на двух серверах

Хотите убедиться, что два сервера имеют одинаковый набор пакетов?

На первом сервере сохраните список:
```bash
dpkg --get-selections > /tmp/packages-server1.txt
```
На втором — сравните напрямую без временного файла:
```bash
diff /tmp/packages-server1.txt <(ssh user@server2 "dpkg --get-selections")
```
Или, если оба списка генерируются локально (например, из разных chroot-окружений):
```bash
diff <(chroot /mnt/server1 dpkg --get-selections) \
     <(chroot /mnt/server2 dpkg --get-selections)
```
#### Как это работает под капотом?

Когда вы пишете `<(...)`, ядро Linux создаёт **анонимный pipe** и связывает его с файловым дескриптором в `/dev/fd/N`. Для внешней программы (например, `diff`) это выглядит как обычный файл:
```bash
echo <(whoami)
# → /dev/fd/63
```
>Это позволяет использовать потоковые данные там, где требуется файл — без записи на диск, без риска коллизий имён, без необходимости очистки.


---

#### Ограничения

- Работает только в **Bash** и **Zsh** (не в POSIX-совместимом `/bin/sh`)
- Некоторые утилиты требуют **seekable** файлы (например, `sort -m`), и тогда `<()` не подойдёт — потребуется временный файл
- Не поддерживает запись (для этого есть `>(...)`, но он редко нужен)

### Команда как строка

Всё, что вы вводите в оболочку, — это **текстовая строка**, которую интерпретатор разбирает и выполняет. Но иногда бывает полезно **собрать команду динамически** — как строку — и затем передать её на выполнение. Это открывает мощные возможности для автоматизации, но требует особой осторожности: **выполняемая строка — это исполняемый код**, и ошибка может привести к непредсказуемым последствиям (вплоть до удаления важных данных).

>**Правило безопасности**:  
   Никогда не выполняйте сгенерированную строку вслепую. Всегда сначала **выведите её на экран**, убедитесь, что она корректна, и только потом запускайте.

Рассмотрим четыре основных способа выполнения команды, представленной в виде строки.

---
#### Cпособ #5. Передача команды в `bash -c`

Команда `bash -c "строка"` запускает новую **дочернюю оболочку**, которая выполняет указанную строку как команду, а затем завершается.

Это особенно полезно в двух случаях:

1. **Изоляция изменений**  
Любые изменения (каталог, переменные, функции) остаются внутри дочерней оболочки:
```bash
$ pwd
/home/user
$ bash -c "cd /tmp && touch temp_file"
$ pwd
/home/user  # текущий каталог не изменился
```

2. **Правильное использование `sudo` с перенаправлением**  
Проблема:
```bash
sudo echo "log" > /var/log/app.log  # ❌ ОШИБКА!
```
Почему? Потому что перенаправление (`>`) обрабатывается **локальной оболочкой от имени обычного пользователя**, ещё до запуска `sudo`. Поэтому вы получаете `Permission denied`.

Решение — передать **всю команду целиком** в оболочку, запущенную под `sudo`:
```bash
sudo bash -c 'echo "log" > /var/log/app.log'  # ✅ РАБОТАЕТ
```

>1. Обратите внимание: внутри `bash -c` используется **одинарная кавычка**, чтобы предотвратить преждевременное раскрытие переменных или спецсимволов в текущей оболочке.
   
---
#### Способ #6. Передача команды через стандартный ввод (`| bash`)

Оболочка может читать команды не только с клавиатуры, но и из **стандартного ввода**. Это позволяет генерировать команды программно и выполнять их пакетно.

Пример: автоматическая сортировка файлов по первой букве имени:
```bash
# Создаём подкаталоги a–z
mkdir {a..z}

# Генерируем команды mv
ls ??* | sed 's/^\(.\)\(.*\)$/mv "\1\2" \1/'

# Проверяем результат (обязательно!)
ls ??* | sed 's/^\(.\)\(.*\)$/mv "\1\2" \1/' | less

# Выполняем
ls ??* | sed 's/^\(.\)\(.*\)$/mv "\1\2" \1/' | bash
```

>Этот подход следует шаблону:  
**1. Сгенерировать → 2. Проверить → 3. Выполнить**

Он особенно мощен при работе с большими наборами данных, где ручной ввод невозможен.

---
#### Способ #7. Удалённое выполнение через `ssh`

Команда `ssh` позволяет не только войти на удалённый хост, но и **выполнить одну команду** без интерактивной сессии:
```bash
ssh user@server "df -h"
```
Это критически важно для скриптов мониторинга, развёртывания и резервного копирования.
##### Важные нюансы:
- **Перенаправление выполняется на том хосте, где интерпретируется команда**:
```bash
ssh server "ls > remote.txt"   # файл создаётся на сервере
ssh server ls > local.txt      # файл создаётся локально
```

- **Подавление лишнего вывода** (например, banner'ов):
```bash
  echo "uptime" | ssh -T server bash
```
- Флаг `-T` отключает выделение псевдотерминала, а явный вызов `bash` часто подавляет приветственные сообщения.
- **Безопасность**: используйте SSH-ключи, чтобы избежать запросов пароля в скриптах.
---
#### Способ #8. Массовое выполнение через `xargs`

Команда `xargs` принимает список строк (обычно из stdin) и **подставляет их как аргументы** в заданную команду.
##### Базовый пример:
```bash
ls *.txt | xargs wc -l
```

>→ эквивалентно `wc -l file1.txt file2.txt ...`

Но у этого подхода есть **фатальный недостаток**: он ломается при именах файлов с пробелами, переводами строк и другими спецсимволами.
##### Безопасное использование: `find -print0 | xargs -0`
```bash
find . -name "*.log" -print0 | xargs -0 gzip
```

- `-print0` в `find` разделяет пути **нулевым байтом** (`\0`)
- `-0` в `xargs` говорит: «используй `\0` как разделитель»

Это **единственный надёжный способ** обрабатывать произвольные имена файлов.

##### Полезные опции `xargs`:

- `-n N` — выполнять команду с **не более чем N аргументами** за раз
```bash
seq 1 6 | xargs -n 2 echo  # → echo 1 2; echo 3 4; echo 5 6
```

- `-I {}` — вставить каждый аргумент в **произвольное место** команды
```bash
find . -name "*.conf" -print0 | xargs -0 -I {} cp {} {}.bak
```

- Обход ограничения «Argument list too long»:  
При попытке `rm *.txt` в каталоге с миллионом файлов вы получите ошибку.  
Решение:
```bash
find . -maxdepth 1 -name "*.txt" -print0 | xargs -0 rm
```

> Альтернатива: `find -exec command {} +` — делает то же самое, что и `xargs`, но встроен в `find`. Однако `xargs` даёт больше контроля (например, через `-I`)

### Способ #9. Фоновое выполнение команды

По умолчанию команды запускаются в **foreground** (переднем плане) — вы ждёте их завершения. Но можно запустить команду в **background** (фоне), чтобы сразу вернуть управление оболочке.

#### Как запустить в фоне?
Добавьте `&` в конец команды:
```bash
$ sleep 60 &
[1] 12345
$
```

- `[1]` — номер задания (job ID)
- `12345` — PID процесса

Команда выполняется в фоне, а вы можете продолжать работать.

>  **Job ≠ Process**:  
> Задание (job) — это концепция оболочки. Оно может включать несколько процессов (например, весь конвейер `cmd1 | cmd2 | cmd3` — одно задание).

#### Управление заданиями: ключевые команды
| Команда   | Действие                                             |
| --------- | ---------------------------------------------------- |
| `jobs`    | Показать все задания в текущей оболочке              |
| `fg [%n]` | Перевести задание на передний план                   |
| `bg [%n]` | Возобновить приостановленное задание в фоне          |
| `kill %n` | Завершить задание по номеру                          |
| `Ctrl-Z`  | Приостановить текущее задание (foreground → stopped) |
Примеры:
```bash
# Запустить в фоне
$ sleep 100 &

# Посмотреть задания
$ jobs
[1]+ Running   sleep 100 &

# Перевести на передний план
$ fg %1

# Или приостановить (Ctrl-Z), потом отправить в фон:
^Z
[1]+ Stopped   sleep 100
$ bg %1
```

> **Важно**:
> - `%n` — номер задания (не PID!)
> - Без `%` — действует на **текущее** задание (`fg`, `bg`, `kill`)

#### Ввод/вывод в фоне

- **stdout/stderr** фоновой команды всё ещё выводятся в терминал — это может "засорить" экран.
- **stdin** недоступен: если команда попытается прочитать ввод — она **автоматически приостанавливается**.
##### Решение:
Перенаправляйте ввод/вывод явно:
```bash
# Безопасный фон с логированием
tar -czf backup.tar.gz /home/user > /tmp/backup.log 2>&1 &

# Или подавите вывод полностью
long_task > /dev/null 2>&1 &
```
---
#### Практические сценарии для администратора

1. **Длительные задачи без блокировки терминала**
```bash
rsync -av /data/ user@remote:/backup/ > /var/log/rsync.log 2>&1 &
```

2. **Параллельный запуск нескольких задач**
```bash
task1 & task2 & task3 &
wait  # дождаться завершения всех фоновых заданий
```
3.  **Работа с редактором без перезапуска**
    
    - Открыли файл в `vim`
    - Нужно проверить что-то в терминале? Нажмите `Ctrl-Z`
    - Выполните команды
    - Вернитесь в редактор: `fg`
    
    → Экономит время и сохраняет контекст.

4. **Условные цепочки в фоне**
```bash
make && make install && systemctl restart myapp &
```

> Если `make` упадёт — остальные команды не выполнятся.

#### Советы и лайфхаки

- **`wait`** — дождаться завершения всех фоновых заданий в скрипте.
- **`disown`** — отвязать задание от оболочки, чтобы оно не завершилось при выходе:
```bash
long_task &
disown %1
exit  # задание продолжит работать
```

> - **Избегайте интерактивных команд в фоне** (`nano`, `less`, `read` и т.д.) — они зависнут.
#### Итог

Фоновое выполнение — не просто «удобство», а **инструмент эффективной работы**:

- Не ждите завершения долгих операций.
- Управляйте несколькими задачами в одной сессии.
- Сохраняйте контекст (редактор, каталог, переменные).

Но помните:
> **Фон — не демон.**  
> При закрытии терминала (без `disown` или `nohup`) фоновые задания получат сигнал `SIGHUP` и завершатся.

Для truly долгих задач используйте `nohup`, `screen` или `tmux`.


### Способ #10. Явные подоболочки `(...)`

Круглые скобки `(команда)` запускают **подоболочку** — временную копию текущей оболочки, которая:

- наследует **всё**: переменные, псевдонимы, функции, текущий каталог;
- изолирована: любые изменения **не влияют на родительскую оболочку**;
- завершается сразу после выполнения.

#### Зачем это нужно?

##### 1. **Временная смена каталога без `cd ..`**
```bash
$ pwd
/home/user
$ (cd /tmp && ls)
file1.txt  file2.log
$ pwd
/home/user  # остались на месте
```

##### 2. **Извлечение архива в другой каталог**
```bash
tar xzf archive.tar.gz -C /target/dir
# или, если `-C` недоступен:
cat archive.tar.gz | (mkdir -p /target && cd /target && tar xzf -)
```

##### 3. **Копирование через `tar` + подоболочка**

```bash
# Локально
tar czf - dir/ | (cd /dest && tar xzf -)

# Удалённо через SSH
tar czf - dir/ | ssh user@host '(cd /dest && tar xzf -)'
```

> → Это **надёжнее**, чем `scp -r`, особенно при сложных правах или символических ссылках.

##### 4. **Изоляция переменных**
```bash
$ VAR=original
$ (VAR=modified; echo "Inside: $VAR")
Inside: modified
$ echo "Outside: $VAR"
Outside: original
```

>Подоболочки — **не процессы**, а лёгкие клонированные контексты.  
   Проверить можно через `$BASH_SUBSHELL`:
```bash
echo $BASH_SUBSHELL        # 0
(echo $BASH_SUBSHELL)      # 1
```

### Способ #11. Замена процесса: `exec`

Команда `exec` **заменяет текущую оболочку** новым процессом. После завершения — **оболочка не возвращается**.

#### Основные применения

##### 1. **Оптимизация скриптов**

Если последняя команда в скрипте — внешняя программа, используйте `exec`, чтобы избежать лишнего процесса:
```bash
#!/bin/bash
# ... подготовка ...
exec python3 app.py  # заменяет bash на python
```

> Экономия памяти и PID при массовом запуске (например, в CI/CD или контейнерах).

##### 2. **Перенаправление всего вывода скрипта**
```bash
#!/bin/bash
exec > /var/log/myscript.log 2>&1
echo "Это попадёт в лог"
ls /nonexistent  # ошибка тоже в лог
```

> Не нужно писать `>> logfile` после каждой команды.

##### 3. **Перенаправление в файловые дескрипторы (продвинуто)**
```bash
exec 3> debug.log
echo "Отладка" >&3
exec 3>&-  # закрыть дескриптор
```
#### Осторожно!
```bash
exec ls
```

>  — после этого **терминал закроется**, потому что оболочка заменена на `ls`, а когда `ls` завершится — родительского процесса нет.

> Используйте `exec` только в скриптах или временных сессиях. Никогда — в интерактивной оболочке, если не хотите вылететь из терминала.

---
### Быстрый справочник: когда что использовать?
| Задача                                           | Рещение                                 |
| ------------------------------------------------ | --------------------------------------- |
| Временно сменить каталог                         | `(cd dir && command)`                   |
| Выполнить команду с изоляцией                    | `(VAR=value; cmd)`                      |
| Перенаправить весь вывод скрипта                 | `exec > log.txt 2>&1`                   |
| Запустить последнюю команду без лишнего процесса | `exec program`                          |
| Копировать дерево каталогов надёжно              | `tar cf - src \| (cd dest && tar xf -)` |

---
### Итог

- **Подоболочки `(...)`** — ваш инструмент для **временной изоляции** без побочных эффектов.
- **`exec`** — мощный, но опасный способ **заменить оболочку** или **перенаправить всё** в скрипте.
