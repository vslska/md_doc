# Интерактивный Bash: Потоки, кавычки, окружение и магия истории команд

## Потоки ввода-вывода и механика перенаправления

Каждому процессу ядро Linux выделяет три стандартных файловых дескриптора: `stdin (0)`, `stdout (1)` и `stderr (2)`. Операторы перенаправления (`>` и `>>`) по умолчанию работают только со `stdout (1)`. Ошибки (`stderr`) продолжают сыпаться в терминал, минуя обычные пайпы.

## ⚠️ Архитектурная ловушка порядка обработки потоков

Шелл парсит операторы перенаправления внутри командной строки **строго слева направо**. На этом этапе часто совершается критическая ошибка, когда пытаются залогировать вывод и ошибки тяжелого скрипта.

- **❌ Ошибочный вариант:**
``` bash
./deploy.sh 2>&1 > /var/log/deploy.log
```

>_Физика процесса:_ Шелл видит `2>&1` и направляет `stderr (2)` туда, куда _в данный момент_ указывает `stdout (1)` (то есть на экран терминала). И только после этого он видит `> /var/log/deploy.log` и перенаправляет поток `stdout (1)` в файл.  
 _Итог:_ Чистый лог ушел в файл, а все ошибки развёртывания (вывод `stderr`) вопреки логике администратора продолжают лететь на экран.


- **✅ Корректный вариант:**
```bash
./deploy.sh > /var/log/deploy.log 2>&1
```
 
 >_Физика процесса:_ Сначала дескриптор `stdout (1)` перенаправляется в целевой файл лога. Затем оператор `2>&1` направляет `stderr (2)` туда, куда _сейчас_ указывает дескриптор `stdout` — то есть в тот же самый файл лога.  
 _Итог:_ Оба потока корректно сливаются в один лог-файл.

## Справочник операторов перенаправления

| Синтаксис  | Назначение и действие                                                 | Реальный пример из практики                                              |
| ---------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `> file`   | Запись `stdout` в файл с предварительным обнулением (перезапись)      | `echo "v1.2.0" > /app/version` — перезаписать версию артефакта           |
| `>> file`  | Направление `stdout` в файл в режиме дописывания (append)             | `echo "$(date): Success" >> /var/log/cron.log` — логирование             |
| `2> file`  | Перенаправление строго потока ошибок `stderr` в файл                  | `tar -czf backup.tar.gz /data 2> tar_errors.log` — сбор ошибок архивации |
| `2>> file` | Перенаправление `stderr` в файл в режиме дописывания                  | `systemctl restart nginx 2>> /var/log/nginx_restart_failures.log`        |
| `&> file`  | Одновременное перенаправление `stdout` и `stderr` в один файл         | `ansible-playbook site.yml &> playbook.log` — полный дамп прогона        |
| `>&2`      | Направление `stdout` внутрь потока `stderr` (вывод ошибок в скриптах) | `echo "Критическая ошибка: База недоступна!" >&2` (уйдет в поток ошибок) |
| `\|&`      | Пайп со слиянием потоков: передает и `stdout`, и `stderr` дальше      | `make build \|& grep -i "error"` — найти любые ошибки сборки С-проекта   |

### Подавление ошибок (`/dev/null`)

Когда ты автоматизируешь проверки в кроне, ошибки утилит часто забивают вывод логов. Виртуальная заглушка `/dev/null` спасает от лишнего шума:

```bash
# Проверяем, запущен ли процесс, игнорируя сообщения grep о несуществующих файлах
grep -q "worker" /var/run/*.pid 2>/dev/null
```

## Отключение интерпретации: Кавычки и экранирование

Пробел в Linux является разделителем аргументов. Если у тебя есть файл с пробелами в имени (например, `Efficient Linux Tips.txt`), шелл передаст утилите три разных аргумента, если вовремя не отключить интерпретацию.

### 1. Одинарные кавычки (`'...'`) — Жесткое экранирование

Полностью отключают интерпретацию всех специальных символов. Текст внутри них воспринимается ядром и шеллом абсолютно буквально.

```bash
# Переменная не будет раскрыта, на экран выведется сырой текст: Переменная $HOME
echo 'Переменная $HOME'

# Идеально для передачи регулярных выражений в awk, чтобы шелл не трогал знак доллара:
awk -F: '{print $1}' /etc/passwd
```

### 2. Двойные кавычки (`"..."`) — Мягкое экранирование

Сохраняют пробелы и защищают от глоббинга, но **разрешают** раскрытие переменных (`$VAR`), подстановку команд через `$()` или обратные кавычки ` `` `, а также работу экранирующего слэша `\`.

```bash
# Переменная расширится до пути, но пробелы внутри пути сохранятся как один аргумент
echo "Путь к домашней папке пользователя $USER: $HOME"

# Подстановка кавычек внутри кавычек через экранирование
echo "Этот сервис называется \"Nginx\""
```

### 3. Обратный слэш (`\`) — Посимвольное экранирование

Указывает шеллу воспринимать следующий за ним символ буквально.

```bash
# Символ доллара потеряет магическую силу, выведется текст: Текущая стоимость $100
echo "Текущая стоимость \$100"

# Перенос длинной строки конвейера для читаемости в Obsidian за счет экранирования символа новой строки:
cat /var/log/nginx/access.log \
  | awk '{print $7}' \
  | sort \
  | uniq -c \
  | sort -nr \
  | head -n 10
```
#### Трюк: Отмена алиасов через `\`

Если у тебя на сервере прописан безопасный псевдоним `alias rm='rm -i'`, который при каждом удалении требует подтверждения `y/n`, ты можешь временно обойти это затенение, поставив обратный слэш перед командой:

```bash
# Запустит чистый бинарник /usr/bin/rm напрямую, минуя интерактивный алиас
\rm /tmp/*.tmp
```

## Переменные, окружение и файлы инициализации

### Локальные переменные vs Окружение (`export`)

Обычное присвоение создает переменную, которая живет **строго внутри текущего процесса оболочки**. Она физически недоступна дочерним процессам (скриптам или запускаемым утилитам).

```bash
# Задаем локальную переменную
TARGET_ENV="production"

# Запускаем питоновский скрипт — он выведет None, так как не видит переменную
python3 -c "import os; print(os.getenv('TARGET_ENV'))"

# Экспортируем переменную в глобальное окружение (Environment)
export TARGET_ENV="production"

# Теперь дочерний процесс Python успешно прочитает значение: production
python3 -c "import os; print(os.getenv('TARGET_ENV'))"
```

_Правило продакшена:_ При объявлении переменных в Bash **нельзя** ставить пробелы вокруг знака равенства (`VAR = value` вернет ошибку `command not found`).

Поиск бинарников и кэширование путей (`$PATH`)

Когда ты пишешь `nginx`, шелл последовательно сканирует каталоги, перечисленные в переменной `$PATH` через двоеточие.

```bash
# Посмотреть структуру путей, заменив двоеточия на переводы строк:
echo $PATH | tr : "\n"
```

### Диагностика путей: `which` vs `type`

Утилита `which` ищет только файлы на диске. Встроенная команда `type` гораздо мощнее, так как она видит псевдонимы, функции и внутренние команды Bash:

```bash
type cp
# Вывод: cp is hashed (/usr/bin/cp) -> шелл говорит, что путь взят из кэша
```


#### ⚠️ Ловушка кэширования путей (`hash -r`)

Bash кэширует (хэширует) пути к программам, чтобы не сканировать диски при каждом вызове. Если ты перенес бинарник утилиты из `/usr/bin/custom-tool` в `/usr/local/bin/custom-tool`, Bash выдаст ошибку `No such file or directory`, так как будет пытаться дергать старый путь из памяти.

- **Решение:** Сбросить кэш путей текущей сессии командой:  
```
hash -r
```

### Автоматизация сессии: `.bashrc` и команда `source`

Конфигурационный файл `$HOME/.bashrc` выполняется автоматически при запуске интерактивного терминала. Если ты добавил туда новый алиас или переменную:

```bash
echo "alias k=kubectl" >> $HOME/.bashrc
```

В текущей открытой сессии этот алиас работать не начнет, так как файл читается один раз при старте. Чтобы применить изменения на лету **без перезапуска терминала**, нужно перечитать конфиг в контексте текущего процесса оболочки:

```bash
source $HOME/.bashrc
# Или через короткий синоним-точку:
. $HOME/.bashrc
```

_Архитектурный нюанс:_ Запуск сценария как `./script.sh` порождает дочерний процесс (`fork`), поэтому переменные внутри него умирают вместе с ним. Команда `source` выполняет код **внутри текущего процесса**, изменяя его окружение.

## Профессиональная работа с историей команд (History)

История интерактивных команд хранится в оперативной памяти текущей сессии Bash и при закрытии терминала сбрасывается в файл, указанный в переменной `$HISTFILE` (по умолчанию это `~/.bash_history`).

### Системный тюнинг истории в `.bashrc`

Чтобы история не затиралась и в ней не копились тысячи одинаковых команд:
```ini
# Максимальное количество строк истории в RAM и в файле на диске
HISTSIZE=50000
HISTFILESIZE=50000

# Игнорировать дубликаты, если они идут подряд, и команды, начатые с пробела (удобно для скрытия паролей)
HISTCONTROL=ignoreboth
```


### Расширение истории (Bang-выражения)

Bang-выражения (`!`) — это не команды, это строковые макросы, которые шелл подставляет **и мгновенно выполняет**.

⚠️ Смертоносная ловушка моментального выполнения

Если ты напишешь `!docker`, шелл найдет последнюю команду, начинающуюся с этого слова, и **тут же запустит её**, даже если это был деструктивный прогон удаления контейнеров.

- **Решение (Безопасный модификатор `:p`):** Добавляй в конец модификатор `print`. Команда не выполнится, а просто распечатается в терминале, позволяя проверить её глазами:
```bash
!docker:p
# Выведет на экран: docker compose down -v (фух, хорошо, что не выполнили сразу!)
```
 
#### Топ самых эффективных Bang-сочетаний в работе:

- `sudo !!` — выполнить предыдущую команду под `sudo` (классика, если забыл root-права).
- `!grep` — найти и выполнить последнюю команду, начинающуюся с `grep`.
- `!?config?` — найти и выполнить последнюю команду, в теле которой встречалось слово `config`.
- `!142` — запустить команду под строгим номером 142 из вывода `history`.
- `!-2` — выполнить команду, которая была 2 шага назад.
- `!-2:p` — безопасно распечатать команду, которая была 2 шага назад.

### Безопасное удаление файлов с помощью аргумента `!$`

Выражение `!$` подставляет **последний аргумент предыдущей команды**. Это лучшая страховка от случайного удаления не тех файлов.

```bash
# Шаг 1: Проверяем глазами, что маска выбрала именно то, что нужно
ls /var/log/nginx/*_old.log
# Вывод: /var/log/nginx/api_old.log  /var/log/nginx/web_old.log

# Шаг 2: Удаляем, подставляя аргумент прошлой команды через !$
rm -f !$
# Шелл сам развернет это в: rm -f /var/log/nginx/*_old.log
```

Аналогично работает макрос `!*` — он подставляет **вообще все аргументы** прошлой команды (не только последний):

```bash
ls file1.txt file2.txt file3.txt
rm -f !*
# Выполнит: rm -f file1.txt file2.txt file3.txt
```

### Инкрементальный поиск по истории (`Ctrl+R`)

Самый быстрый способ достать команду, которую ты запускал три недели назад:

1. Нажми **`Ctrl+R`** в терминале.
2. Начни вводить любую часть команды (например, имя сложного контейнера или флаг `rsync`).
3. Шелл будет на лету подставлять совпадения. Нажимай **`Ctrl+R` повторно**, чтобы листать совпадения дальше вглубь истории.
4. Нажми **`Arrow Left / Arrow Right`** или **`Escape`**, чтобы остановить поиск и отредактировать найденную строку.
5. Нажми **`Ctrl+G`** или **`Ctrl+C`**, чтобы полностью выйти из поиска и очистить строку.

## Редактирование командной строки: Стиль Emacs

По умолчанию командная строка Bash работает в режиме привязок клавиш Emacs. Освоение этих сочетаний экономит часы времени при правке длинных конвейеров.

Инструмент быстрой замены ошибок через знак вставки (`^`)

Если ты опечатался в длинном конвейере, не нужно листать стрелками назад. Используй конструкцию `^старое^новое`:

```bash
# Допустили опечатку в расширении (.jg вместо .jpg)
md5sum *.jg | cut -c1-32 | sort | uniq -c

# Применяем быструю замену
^jg^jpg

# Шелл сам исправит строку и тут же выполнит её:
# md5sum *.jpg | cut -c1-32 | sort | uniq -c
```

_Нюанс:_ Этот метод меняет только **первое** вхождение подстроки слева направо. Если нужно заменить все вхождения по всей строке, используй синтаксис `sed`-замены над историей: `!!:gs/jg/jpg/`.

Шпаргалка по горячим клавишам редактирования в Obsidian

В режиме **Emacs** (по умолчанию) для ускорения работы с длинными командами используй следующие сочетания:

- **Навигация:** `Ctrl+A` (начало строки), `Ctrl+E` (конец), `Alt+B/F` (на слово назад/вперед).
- **Редактирование:** `Ctrl+W` (удалить слово слева), `Alt+D` (слово справа), `Ctrl+K/U` (вырезать до конца/начала), `Ctrl+Y` (вставить/yank).
- **Топ-фича — `Ctrl+X` затем `Ctrl+E`**: Открывает текущую команду в `$EDITOR` (Vim/Nano) для редактирования.
- **`Alt + .`**: Подставляет последний аргумент предыдущей команды (удобно вместо мыши).
- **`Ctrl+L`**: Очищает экран.
- 
```bash
# Пример использования Alt + . (нажать после ввода vim)
tail -n 50 /var/log/app.log
vim [Alt + .] # Автоматически подставит путь к логу
```
