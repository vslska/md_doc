# Архитектура Shell: Процессы, фазы парсинга, типы команд и ловушки ядра

Командная оболочка (Shell) — это не просто интерпретатор, а полноценная среда управления операционной системой, выступающая промежуточным слоем между системными вызовами ядра Linux (Kernel Space) и пользовательскими приложениями (User Space).

---

## 1. Жизненный цикл процесса: Как Shell запускает команды

Когда вы вводите команду (например, `ls -l`) и нажимаете `Enter`, Shell выполняет классическую Unix-цепочку системных вызовов для управления процессами: **`fork() → execve() → wait()`**.

```
[Родительский Shell (PID 100)] ─── fork() ───► [Дочерний Shell (PID 101)]
              │                                             │
           wait()                                        execve("/bin/ls")
              │                                             │
              ▼                                             ▼
[Блокировка до завершения]                      [Процесс ls (PID 101)]
              │                                             │
  ◄─── Сигнал SIGCHLD (exit 0) ─────────────────────────────┘
```

1. **`fork()` (Порождение):** Родительский процесс оболочки дублирует сам себя в памяти. Создается точная копия — дочерний процесс, который наследует все открытые файловые дескрипторы (включая сокеты терминала, `stdout`, `stderr`).
2. **Перенаправление потоков (I/O Redirection):** Внутри дочернего процесса _до_ запуска целевой программы выполняются системные вызовы `dup2()`. Они подменяют дескрипторы (например, вместо экрана `1` направляют поток в файл лога).
3. **`execve()` (Замещение):** Дочерний процесс вызывает `execve()`, передавая ему путь к бинарнику (например, `/bin/ls`) и массив аргументов. Ядро Linux полностью очищает адресное пространство дочернего процесса, заменяет его код кодом утилиты `ls` и передает ей управление. PID процесса при этом _не меняется_.
4. **`wait()` / `waitpid()` (Ожидание):** Родительский Shell засыпает и ждет, пока ядро не пришлет ему сигнал `SIGCHLD`, сообщающий, что дочерний процесс завершился. После этого Shell считывает код возврата (`exit code`, доступный в переменной `$?`) и разблокирует строку ввода.

### ⚠️ Исключение: Оператор `exec`

Если запустить команду через `exec` (например, `exec htop`), Shell выполнит `execve()` **без предварительного `fork()`**. Бинарник `htop` намертво затрет сам процесс оболочки. После закрытия `htop` терминал мгновенно закроется (или оборвется SSH-сессия), так как возвращаться процессу ядра больше некуда.

## 2. Четыре типа команд (Что именно вы запускаете?)

Когда вы вводите слово, Shell проверяет его тип строго в следующем порядке. Нарушение этого приоритета — частая причина того, почему ваши кастомные скрипты работают не так, как ожидалось.

Узнать реальный тип любой команды на проде можно строго через встроенную утилиту: `type -a <команда>`.

### Приоритет №1: Алиасы (Aliases / Псевдонимы)

- **Что это:** Простые строковые подмены, живущие только в интерактивной сессии.
- **Ловушка продакшена:** Алиасы **физически не работают внутри неинтерактивных Bash-скриптов**. Написание `alias k=kubectl` внутри файла `script.sh` вызовет ошибку `command not found`.

### Приоритет №2: Ключевые слова (Keywords)

- **Что это:** Синтаксические конструкции самого языка программирования Shell (`if`, `for`, `while`, `function`). Они обрабатываются парсером оболочки на самом верхнем уровне.

### Приоритет №3: Встроенные команды (Builtins)

- **Что это:** Команды, код которых скомпилирован прямо внутрь бинарника самой оболочки (например, `cd`, `pwd`, `echo`, `set`, `exit`, `kill`).
- **Физика процесса:** Для запуска встроенных команд Shell **не делает системный вызов `fork()`**. Они выполняются мгновенно в контексте памяти текущего процесса. Именно поэтому команда `cd` обязана быть встроенной — если бы она была внешней утилитой, она бы меняла директорию внутри дочернего процесса `fork()`, и после её завершения родительский Shell оставался бы в исходной папке.

### Приоритет №4: Внешние утилиты (External Commands)

- **Что это:** Изолированные бинарные файлы или независимые скрипты, лежащие на диске (например, `/bin/ls`, `/usr/bin/grep`). Для их запуска всегда требуется проход по каталогам переменной `$PATH` и полная цепочка `fork() → execve()`.

## 3. Фазы парсинга строки: 12 шагов обработки данных

Перед тем как отправить команду в ядро, Shell разбивает и модифицирует строку ввода. Понимание этих фаз объясняет, почему кавычки защищают от масок, и как работает экранирование.

Парсинг идет строго последовательно:

```
Строка ввода ──► [1. Чтение] ──► [2. Разбиение на токены] ──► [3. Развертывание алиасов] ──►
 ──► [4. Brace Expansion {}] ──► [5. Подстановка переменных $VAR] ──► [6. Подстановка команд $()] ──►
 ──► [7. Арифметика $(())] ──► [8. Разделение на слова] ──► [9. Глоббинг (Маски *, ?)] ──►
 ──► [10. Поиск путей (Builtin/PATH)] ──► [11. Тюнинг дескрипторов] ──► [12. EXEC() в ядро]
```

- **Критичный Senior-нюанс (Разделение на слова против Глоббинга):** Подстановка переменных (`$VAR`) происходит **раньше**, чем раскрытие масок файлов (Глоббинг). Если в переменной `$FILE` лежит значение `*.txt`, то при вызове `ls $FILE` шелл сначала заменит переменную на текст `*.txt`, а уже на следующем шаге просканирует диск и найдет файлы.
- **Защита кавычками:** Двойные кавычки `"..."` полностью отключают шаги **8 (Разделение на слова)** и **9 (Глоббинг)**, но сохраняют шаги **5 и 6**. Одинарные кавычки `'...'` вырезают вообще все фазы подстановок, отправляя строку в ядро в первозданном виде.

## 4. Классификация оболочек: Interactive, Login, Non-Login

Поведение Shell и файлы конфигурации, которые он считывает при старте, полностью зависят от флагов его запуска.

### Login Shell (Оболочка входа)

- **Когда запускается:** Первая оболочка, которую вы получаете при аутентификации в системе: ввод логина/пароля в TTY-консоли, подключение по SSH (`ssh user@host`), или принудительный вызов через `bash --login`.
- **Порядок чтения конфигов:**
    1. `/etc/profile` (глобальные настройки для всех).
    2. Ищет в домашней папке пользователя **первый попавшийся** файл из списка: `~/.bash_profile` -> `~/.bash_login` -> `~/.profile`. Как только находит один, остальные игнорирует.

### Non-Login Shell (Оболочка сессии)

- **Когда запускается:** Оболочка, запущенная _внутри_ уже созданной сессии: открытие нового окна эмулятора терминала в графической среде (GNOME Terminal, Alacritty) или простой запуск команды `bash`.
- **Порядок чтения конфигов:** Полностью игнорирует файлы профилей. Читает **строго один файл**: `~/.bashrc`.

### Non-Interactive Shell (Неинтерактивная оболочка)

- **Когда запускается:** Автоматический запуск скриптов системой: планировщик `cron`, работа CI/CD пайплайнов (GitLab Runner, GitHub Actions) или выполнение удаленной команды через SSH без выделения терминала (`ssh user@host "uptime"`).
- **Порядок чтения конфигов:** **Игнорирует вообще все файлы конфигов** (`.bashrc`, `.profile` не читаются). Переменные окружения берутся только из файла, указанного в системной переменной `$BASH_ENV` (если она задана).

#### ⚠️ Главная ловушка автоматизации (Почему cron не видит утилиты)

Когда крон или CI/CD запускает ваш скрипт, он работает в режиме _Non-Interactive + Non-Login_. Переменная `$PATH` внутри него сбрасывается к минимальному системному дефолту (обычно только `/bin:/usr/bin`). Все ваши кастомные пути к бинарникам (например, из `/usr/local/bin` или `/opt/kube/`) шелл просто не знает.

- **Инженерное правило:** Внутри скриптов автоматизации всегда либо прописывайте явный экспорт путей в первой строке:

```bash
export PATH="/usr/local/bin:/usr/bin:/bin:/opt/bin:$PATH"
```

Либо вызывайте критические утилиты строго по их полным абсолютным путям (например, `/usr/local/bin/kubectl` вместо простого `kubectl`).
