# Сетевой стек и Тюнинг TCP/IP под High Load

>Этот раздел посвящен внутренней кухне обработки сетевого трафика ядром Linux, жизненному циклу TCP-соединений и системным параметрам оптимизации сетевой подсистемы.

## Прохождение пакета через ядро (Linux Network Stack)

Когда сетевой пакет прилетает на сетевую карту (NIC), он проходит многоступенчатый путь через аппаратные и программные очереди, прежде чем приложение прочитает его из сокета.

### Алгоритм обработки (Низкий уровень)

1. **Ring Buffer & DMA:** Пакет поступает на физический порт сетевой карты. Карта с помощью контроллера **DMA** мгновенно записывает сырые байты пакета напрямую в системную память (RAM) — в области, на которые указывают дескрипторы кольцевого буфера приема (**RX Ring Buffer**). После успешной записи карта генерирует аппаратное прерывание (**Hard IRQ**).
2. **Hard IRQ & Включение NAPI:** CPU приостанавливает текущие задачи. Чтобы поток входящих пакетов на высокой скорости не заспамил CPU миллионами прерываний (эффект IRQ Storm), драйвер использует механизм **NAPI (New API)**: он **отключает аппаратные прерывания** от этой сетевой карты и генерирует мягкое прерывание (**SoftIRQ** подтипа `NET_RX_SOFTIRQ`).
3. **SoftIRQ & Поллинг (NAPI Polling):** Драйвер в цикле (polling) забирает пакеты из RAM. На этом этапе ядро аллоцирует метаструктуру **`sk_buff` (Socket Buffer)**, которая "оборачивает" данные пакета для дальнейшего путешествия по стеку. Дескрипторы RX Ring Buffer очищаются и возвращаются сетевой карте. По окончании пачки аппаратные прерывания карты включаются снова.
4. **Входная очередь ядра (`netdev_max_backlog`):** Из NAPI пакеты передаются подсистеме Vlan/Bonding, а затем попадают во входную очередь сетевой подсистемы ядра. Если стек протоколов загружен, пакеты временно буферизируются здесь.
5. **Стек протоколов и Netfilter:** Функция `netif_receive_skb()` передает пакет вверх. Происходит последовательный разбор заголовков: L2 (Ethernet) -> L3 (IP) -> L4 (TCP/UDP). На этапе L3/L4 пакет прогоняется через хуки **Netfilter** (`iptables`/`nftables`). Здесь отрабатывают правила фильтрации, NAT и conntrack. Если пакет успешно прошел фильтры, выполняется маршрутизация.
6. **Буфер сокета (Receive Buffer):** Данные (payload) очищаются от сетевых заголовков и складываются в очередь чтения (`receive queue`) конкретного сокета приложения. Приложение, заблокированное на системном вызове `epoll_wait()`, `read()` или `recv()`, получает уведомление от ядра, просыпается, выполняет переключение контекста в Kernel Space и копирует данные из буфера сокета в свое пользовательское пространство (User Space).

5.2. Ошибки переполнения очередей (Диагностика и Траблшутинг)

Этап 1: Переполнение на уровне железа (RX Ring Buffer)

Если сетевой чип заполнил все дескрипторы кольцевого буфера в RAM, новые пакеты отбрасываются самой картой.

- **Диагностика:**
    
    bash
    
    ```
    ethtool -S eth0 | grep -E "drop|fifo|miss|discard"
    ```
    
    Use code with caution.
    
    _Если счетчики типа `rx_fifo_errors`, `rx_missed_errors` или `rx_discards` растут — кольцевой буфер переполнен._
- **Тюнинг:** Посмотреть текущий и максимальный размер буфера можно через `ethtool -g eth0`. Увеличить размер буфера до максимума:
    
    bash
    
    ```
    ethtool -G eth0 rx 4096 tx 4096
    ```
    
    Use code with caution.
    

Этап 2: Переполнение на стыке драйвера и стека ядра (`netdev_max_backlog`)

Если драйвер успешно вычитал пакеты из Ring Buffer, но стек протоколов ядра не успевает их обрабатывать, пакеты дропаются на входе в стек.

- **Диагностика:**
    
    bash
    
    ```
    cat /proc/net/softnet_stat
    ```
    
    Use code with caution.
    
    _Каждая строка файла соответствует одному ядру CPU. Нас интересует вторая колонка: это число пакетов, сброшенных из-за переполнения очереди `netdev_max_backlog`. Если оно растет — очередь слишком мала._
- **Тюнинг:** Увеличить размер входной очереди и бюджет обработки пакетов для одного цикла SoftIRQ в `/etc/sysctl.conf`:
    
    ini
    
    ```
    # Увеличиваем размер входной очереди пакетов (дефолт обычно 1000)
    net.core.netdev_max_backlog = 10000
    # Увеличиваем количество пакетов, обрабатываемых за один проход NAPI (дефолт 300)
    net.core.netdev_budget = 600
    ```
    
    Use code with caution.
    

Этап 3: Параллелизация обработки (RSS и RPS)

Чтобы SoftIRQ не утилизировал только одно ядро CPU (обычно `CPU0`), трафик необходимо размазывать по ядрам:

- **RSS (Receive Side Scaling):** Аппаратный механизм сетевой карты. Карта считает хэш от IP/портов пакета и раскладывает пакеты в разные RX-очереди, каждая из которых генерирует свой Hard IRQ на свое ядро CPU.
- **RPS (Receive Packet Steering):** Программный аналог RSS в ядре Linux. Позволяет драйверу пересылать `sk_buff` на обработку стека протоколов другим ядрам CPU через Inter-Processor Interrupts (IPI).
    - _Включить RPS для интерфейса eth0 (размазать обработку первой очереди на первые 8 ядер CPU, маска `ff`):_
        
        bash
        
        ```
        echo "ff" > /sys/class/net/eth0/queues/rx-0/rps_cpus
        ```
        
        Use code with caution.
        

5.3. Тюнинг TCP/IP: Борьба с очередями и SYN Flood

Механизм Handshake и двухуровневая система очередей

Процесс установления TCP-соединения (Three-way Handshake) на стороне ядра Linux жестко разделен на два этапа:

1. **Полуоткрытые соединения (SYN Backlog):** Клиент инициирует соединение и присылает пакет `SYN`. Драйвер ядра выделяет под это соединение структуру в памяти, переводит его в статус `SYN_RECV`, помещает в очередь **SYN backlog** и отправляет клиенту ответный `SYN-ACK`.
2. **Полностью установленные соединения (Listen Backlog):** Клиент отвечает пакетом `ACK`. Соединение переходит в статус `ESTABLISHED`. Ядро извлекает его из SYN-backlog и перемещает во вторую очередь — **Listen backlog** (очередь готовых сокетов). Соединение находится здесь до тех пор, пока приложение не заберет его из пространства ядра с помощью системного вызова `accept()`.

Системный тюнинг очередей (sysctl)

При высокой плотности запросов базовые размеры этих очередей переполняются мгновенно.

- **`net.ipv4.tcp_max_syn_backlog`** (дефолт ~512/1024): Максимальный размер очереди полуоткрытых соединений. Для High Load его увеличивают:
    
    ini
    
    ```
    net.ipv4.tcp_max_syn_backlog = 16384
    ```
    
    Use code with caution.
    
- **`net.core.somaxconn`** (дефолт ~128/4096): Жесткий системный лимит для очереди `Listen backlog`.
    
    - **⚠️ Критическая зависимость:** Значение, указанное в конфигурационных файлах веб-серверов (например, в Nginx: `listen 80 backlog=65536`), **не может быть выше**, чем системный параметр `somaxconn`. Если вы поднимете лимит в Nginx, но оставите дефолт в ядре, Linux урежет очередь приложения до своего системного максимума.
    
    ini
    
    ```
    net.core.somaxconn = 16384
    ```
    
    Use code with caution.
    

Защита от SYN Flood и оптимизация таймаутов

Механизм TCP Syncookies

ini

```
net.ipv4.tcp_syncookies = 1
```

Use code with caution.

Когда очередь `SYN backlog` заполняется на 100%, ядро активирует механизм криптографических куки. Оно перестает выделять дескрипторы памяти под новые `SYN`-запросы. Вместо этого параметры соединения хэшируются и зашифровываются прямо в поле `Sequence Number` исходящего ответа `SYN-ACK`. Если клиент легитимен, он возвращает этот номер в финальном пакете `ACK`. Ядро на лету расшифровывает номер и мгновенно создает готовое соединение в `Listen backlog`.

- **Важный нюанс:** Использование `syncookies` заставляет ядро отбрасывать расширенные TCP-опции (такие как `SACK` или `Window Scaling`). Чтобы этого не происходило, **обязательно** должен быть включен сбор таймстампов — тогда ядро спрячет TCP-опции в неиспользуемые биты временных меток:
    
    ini
    
    ```
    net.ipv4.tcp_timestamps = 1
    ```
    
    Use code with caution.
    

Борьба со "спящими" полуоткрытыми сессиями

По умолчанию ядро делает повторные `SYN-ACK` пакеты 5 раз (`tcp_synack_retries`), удерживая мертвую сессию около 180 секунд. Для высоконагруженных систем этот таймаут сокращают:

ini

```
net.ipv4.tcp_synack_retries = 2
net.ipv4.tcp_syn_retries = 2
```

Use code with caution.

Поведение при переполнении приложения (`tcp_abort_on_overflow`)

Если ваше приложение не успевает вызывать `accept()`, очередь `Listen backlog` заполняется. По умолчанию Linux просто игнорирует входящие `ACK` от клиентов. Клиент уверен, что соединение открыто, начинает слать данные, но сервер их молча дропает.

- Если сервер стоит за балансировщиком нагрузки (HAProxy, Envoy), этот параметр рекомендуется выставить в `1`:
    
    ini
    
    ```
    net.ipv4.tcp_abort_on_overflow = 1
    ```
    
    Use code with caution.
    
    _При переполнении очереди готовых сокетов ядро будет мгновенно отвечать балансировщику пакетом `RST` (Сброс соединения). Балансировщик сразу поймет, что эта нода перегружена, и перенаправит запрос на другой здоровый бэкенд._

5.4. Разбор состояний TIME_WAIT и CLOSE_WAIT

⏳ Состояние TIME_WAIT (Активное закрытие)

Состояние возникает на стороне того узла, **кто первый инициировал закрытие соединения** (вызвал системный вызов `close()`). Обычно активным инициатором выступает сервер (Nginx, отдавший файл без `Keep-Alive`).

- **Зачем это нужно ядру:** Сокет блокируется в этом статусе ровно на **2 * MSL**, что в ядре Linux составляет **60 секунд** (изменить этот таймаут через `sysctl` нельзя). Это необходимо, чтобы дать время долететь "заблудившимся" в сети пакетам старой сессии и гарантировать, что удаленный хост получил финальный пакет `ACK`.
- **В чем проблема под High Load:** Если сервер закрывает 10 000 соединений в секунду, в системе одновременно будут висеть 600 000 сокетов в статусе `TIME_WAIT`. Они стремительно исчерпывают пул свободных локальных (эфемерных) портов, и сервер физически не может открыть ни одного нового исходящего соединения (например, к СУБД), выдавая ошибку `Cannot assign requested address`.

Тюнинг под High Load (Борьба с TIME_WAIT)

1. **Расширение пула эфемерных портов:**
    
    ini
    
    ```
    net.ipv4.ip_local_port_range = 1024 65535
    ```
    
    Use code with caution.
    
2. **Повторное использование сокетов:** Разрешаем ядру безопасно переиспользовать сокеты в состоянии `TIME_WAIT` для новых исходящих соединений к тому же целевому IP/порту:
    
    ini
    
    ```
    net.ipv4.tcp_tw_reuse = 1
    ```
    
    Use code with caution.
    
    - **⚠️ Критическая зависимость:** Параметр `tcp_tw_reuse` **физически не работает**, если отключен сбор сетевых таймстампов (`net.ipv4.tcp_timestamps = 1`).
    - _Важно:_ Забудьте про старый параметр `tcp_tw_recycle` — он полностью удален из ядра Linux начиная с версии 4.12, так как он ломал соединения от клиентов за общим NAT.

🛑 Состояние CLOSE_WAIT (Пассивное закрытие)

Состояние возникает на стороне того узла, **кому прилетел входящий запрос на закрытие** (пакет `FIN`) от соседа.

- **Как это происходит под капотом:** Клиент присылает `FIN`. Ядро Linux автоматически отвечает пакетом `ACK` и переводит сокет в статус `CLOSE_WAIT`. На этом зона ответственности ядра заканчивается. Оно ждет, пока _ваше приложение_ обработает это событие и вызовет `close()` для этого дескриптора сокета.
- **В чем проблема:** Сокеты в состоянии `CLOSE_WAIT` **не имеют таймаутов автоочистки**. Они могут висеть неделями, удерживая File Descriptor процесса. Если их накопится много — процесс упрется в лимит `Max open files` (`EMFILE`), и сервер перестанет принимать новые запросы.
- **Как лечить:** **Тюнинг системных параметров ядра здесь абсолютно бессилен.** Если сервер забит сокетами в `CLOSE_WAIT`, это **100% архитектурный баг в коде приложения** (разработчики забыли обработать конец потока `EOF` и не закрыли дескриптор сокета) либо поток приложения намертво заблокирован (`Deadlock`). Лечится только перезапуском сервиса или исправлением кода.

🛡️ Важный сопутствующий лимит: Netfilter Conntrack

Все сетевые сессии (включая сотни тысяч в состоянии `TIME_WAIT`) заносятся в системную таблицу отслеживания соединений **Conntrack**. При резком наплыве трафика эта таблица переполняется. При этом в логах появляется запись `nf_conntrack: table full, dropping packet`, и ядро начинает намертво отбрасывать любые пакеты.

- **Тюнинг Conntrack под High Load:**
    
    ini
    
    ```
    # Увеличиваем максимальный размер таблицы соранений
    net.netfilter.nf_conntrack_max = 1048576
    
    # Ускоряем очистку закрытых сессий в состоянии TIME_WAIT из таблицы conntrack (дефолт 120 сек)
    net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
    ```
    
    Use code with caution.
    

Шпаргалка по оперативной диагностике сокетов

Для анализа сетевого состояния используйте утилиту `ss`:

**1. Быстрая сводка по всем сокетам в системе:**

bash

```
ss -s
```

Use code with caution.

**2. Поиск процессов, удерживающих сокеты в `CLOSE_WAIT`:**

bash

```
ss -tpna | grep CLOSE_WAIT
```

Use code with caution.

_Вывод четко покажет имя бинарника и PID процесса, внутри которого зависла логика закрытия дескрипторов._
