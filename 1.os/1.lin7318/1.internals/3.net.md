# Сетевой стек и Тюнинг TCP/IP под High Load

Этот раздел посвящен внутренней кухне обработки сетевого трафика ядром Linux, жизненному циклу TCP-соединений и системным параметрам оптимизации сетевой подсистемы.

---

## 1. Прохождение пакета через ядро (Linux Network Stack)

Когда сетевой пакет прилетает на сетевую карту (NIC), он проходит многоступенчатый путь через аппаратные и программные очереди, прежде чем приложение (например, Nginx или Go-воркер) прочитает его из сокета.

### Алгоритм обработки (Низкий уровень)

1. **Ring Buffer & DMA:** Пакет поступает на физический порт сетевой карты. Карта с помощью контроллера **DMA (Direct Memory Access)** мгновенно записывает сырые байты пакета напрямую в системную память (RAM) — в области памяти, на которые указывают дескрипторы кольцевого буфера приема (**RX Ring Buffer**). После успешной записи карта генерирует аппаратное прерывание (**Hard IRQ**).
2. **Hard IRQ & Включение NAPI:** CPU приостанавливает текущие задачи и выполняет верхнюю половину (Top Half) обработчика прерываний драйвера. Чтобы поток входящих пакетов на высокой скорости не заспамил CPU миллионами аппаратных прерываний (эффект IRQ Storm), драйвер использует механизм **NAPI (New API)**: он **отключает аппаратные прерывания** от этой сетевой карты и генерирует мягкое прерывание (**SoftIRQ** подтипа `NET_RX_SOFTIRQ`).
3. **SoftIRQ & Поллинг (NAPI Polling):** Ядро выполняет нижнюю половину (Bottom Half) обработчика. В штатном режиме это происходит сразу после выхода из Hard IRQ на том же ядре CPU (при экстремальной нагрузке задача делегируется потоку `ksoftirqd`). Драйвер переходит в режим опроса (polling) и в цикле пачками (в рамках заданного кванта времени/пакетов) выгребает данные из RAM. На этом этапе ядро аллоцирует метаструктуру **`sk_buff` (Socket Buffer)**, которая "орачивает" данные пакета для дальнейшего путешествия по стеку. Дескрипторы RX Ring Buffer очищаются и возвращаются сетевой карте. По окончании пачки аппаратные прерывания карты включаются снова.
4. **Входная очередь ядра (`netdev_max_backlog`):** Из NAPI пакеты передаются подсистеме Vlan/Bonding, а затем попадают во входную очередь сетевой подсистемы ядра. Если стек протоколов загружен, пакеты временно буферизируются здесь.
5. **Стек протоколов и Netfilter:** Функция `netif_receive_skb()` передает пакет вверх. Происходит последовательный разбор заголовков: L2 (Ethernet) -> L3 (IP) -> L4 (TCP/UDP). На этапе L3/L4 пакет прогоняется через хуки **Netfilter** (`iptables`/`nftables`). Здесь отрабатывают правила фильтрации, NAT и conntrack. Если пакет успешно прошел фильтры, выполняется маршрутизация.
6. **Буфер сокета (Receive Buffer):** Данные (payload) очищаются от сетевых заголовков и складываются в очередь чтения (`receive queue`) конкретного сокета приложения. Приложение, заблокированное на системном вызове `epoll_wait()`, `read()` или `recv()`, получает уведомление от ядра, просыпается, выполняет переключение контекста в Kernel Space и копирует данные из буфера сокета в свое пользовательское пространство (User Space).

## 2. Ошибки переполнения очередей (Диагностика и Траблшутинг)

Если система не успевает обрабатывать пакеты на каком-то из этапов, ядро начинает молча дропать (`drop`) трафик. Локализация места дропа — ключ к правильному тюнингу.

### Этап 1: Переполнение на уровне железа (RX Ring Buffer)

Если сетевой чип заполнил все дескрипторы кольцевого буфера в RAM, а драйвер/CPU не успели их вычитать (например, CPU был занят другой тяжелой задачей), новые пакеты отбрасываются самой картой.

- **Диагностика (с замененными флагами для исключения сетевого резолва):**
```bash
 ethtool -S eth0 | grep -E "drop|fifo|miss|discard"
```

_Если счетчики типа `rx_fifo_errors`, `rx_missed_errors` или `rx_discards` растут — кольцевой буфер переполнен._

- **Тюнинг:** Посмотреть текущий и максимальный размер буфера можно через `ethtool -g eth0`. Увеличить размер буфера до максимума (например, до 4096 дескрипторов):

```
ethtool -G eth0 rx 4096 tx 4096
```

### Этап 2: Переполнение на стыке драйвера и стека ядра (`netdev_max_backlog`)

Если драйвер успешно вычитал пакеты из Ring Buffer, но стек протоколов ядра не успевает их обрабатывать, пакеты дропаются на входе в стек.

- **Диагностика:**

```bash
cat /proc/net/softnet_stat
```

_Каждая строка файла соответствует одному ядру CPU. Нас интересуют первые три колонки (в шестнадцатеричном формате):_
1. `Колонка 1` (Processed): Общее число обработанных пакетов.
2. `Колонка 2` (Dropped): **Критично!** Число пакетов, сброшенных из-за переполнения очереди `netdev_max_backlog`. Если оно растет — очередь слишком мала.
3. `Колонка 3` (Squeezed): Число раз, когда SoftIRQ исчерпал свой временной квант (бюджет пакетов) и досрочно отдал CPU другим задачам, не успев обработать весь сетевой хвост.
- **Тюнинг:** Увеличить размер входной очереди и бюджет обработки пакетов для одного цикла SoftIRQ в `/etc/sysctl.conf`:

```ini
# Увеличиваем размер входной очереди пакетов (дефолт обычно 1000)
net.core.netdev_max_backlog = 10000
# Увеличиваем количество пакетов, обрабатываемых за один проход NAPI (дефолт 300)
net.core.netdev_budget = 600
```

## Этап 3: Параллелизация обработки (RSS и RPS)

Чтобы SoftIRQ не утилизировал только одно ядро CPU (обычно `CPU0`), превращая его в бутылочное горлышко, трафик необходимо размазывать по ядрам:

- **RSS (Receive Side Scaling):** Аппаратный механизм сетевой карты. Карта считает хэш от IP/портов пакета и раскладывает пакеты в разные RX-очереди, каждая из которых генерирует свой Hard IRQ на свое ядро CPU.
- **RPS (Receive Packet Steering):** Программный аналог RSS в ядре Linux. Если сетевая карта дешевая и имеет всего одну RX-очередь, RPS позволяет драйверу пересылать `sk_buff` на обработку стека протоколов другим ядрам CPU через Inter-Processor Interrupts (IPI).
- _Включить RPS для интерфейса eth0 (размазать обработку первой очереди на первые 8 ядер CPU, маска `ff`):_

```bash
echo "ff" > /sys/class/net/eth0/queues/rx-0/rps_cpus
```

## 2. Тюнинг TCP/IP: Борьба с очередями и SYN Flood

Когда на сервер обрушивается огромный поток новых соединений (легитимный наплыв трафика или распределенная атака), стандартные консервативные настройки сетевого стека ядра превращают операционную систему в «тыкву». Падают даже самые производительные сервера на базе Nginx или Go.

### Механизм Handshake и двухуровневая система очередей

Процесс установления TCP-соединения (Three-way Handshake) на стороне ядра Linux жестко разделен на два этапа, каждый из которых имеет собственный буфер ограничения:

```
[Клиент] ─────── SYN ───────> [ SYN Backlog ] ──> (Состояние: SYN_RECV)
[Клиент] <───── SYN-ACK ───── [Ядро Linux]
[Клиент] ─────── ACK ───────> [ Listen Backlog ] ──> (Состояние: ESTABLISHED)
                                      │
                                  accept()
                                      ▼
                               [ Приложение ]
```

1. **Полуоткрытые соединения (SYN Backlog):** Клиент инициирует соединение и присылает пакет `SYN`. Драйвер ядра выделяет под это соединение структуру в памяти, переводит его в статус `SYN_RECV`, помещает в очередь **SYN backlog** и отправляет клиенту ответный `SYN-ACK`.
2. **Полностью установленные соединения (Listen Backlog):** Клиент отвечает пакетом `ACK`. Соединение переходит в статус `ESTABLISHED` (установлено). Ядро извлекает его из SYN-backlog и перемещает во вторую очередь — **Listen backlog** (очередь готовых сокетов). Соединение находится здесь до тех пор, пока приложение не заберет его из пространства ядра в пространство пользователя с помощью системного вызова `accept()`.

### Системный тюнинг очередей (sysctl)

При высокой плотности запросов базовые размеры этих очередей переполняются мгновенно, из-за чего сервер начинает молча игнорировать новые подключения.

- **`net.ipv4.tcp_max_syn_backlog`** (дефолт ~512/1024): Максимальный размер очереди полуоткрытых соединений. При наплыве клиентов или SYN-атаке этот буфер забивается за миллисекунды. Для High Load его увеличивают в десятки раз:
 
```ini
net.ipv4.tcp_max_syn_backlog = 16384
```

- **`net.core.somaxconn`** (дефолт ~128/4096): Жесткий системный лимит для очереди `Listen backlog`.
    
    - **⚠️ Критическая зависимость:** Значение, указанное в конфигурационных файлах веб-серверов (например, в Nginx: `listen 80 backlog=65536`), **не может быть выше**, чем системный параметр `somaxconn`. Если вы поднимете лимит в Nginx, но оставите дефолт в ядре, Linux молча урежет очередь приложения до своего системного максимума.

```ini
net.core.somaxconn = 16384
```


### Защита от SYN Flood и оптимизация таймаутов

#### Механизм TCP Syncookies

```ini
net.ipv4.tcp_syncookies = 1
```

- **Как это работает на самом деле:** Когда очередь `SYN backlog` заполняется на 100%, ядро активирует механизм криптографических куки. Оно перестает выделять дескрипторы памяти под новые `SYN`-запросы (защищая RAM от исчерпания). Вместо этого параметры соединения (IP, порты, параметры заголовков) хэшируются и зашифровываются прямо в поле `Sequence Number` исходящего ответа `SYN-ACK`. Если клиент легитимен, он возвращает этот номер в финальном пакете `ACK`. Ядро на лету расшифровывает номер, проверяет валидность и мгновенно создает готовое соединение в `Listen backlog`, полностью минуя первую очередь.
- **Важный нюанс (Senior-уровень):** Использование `syncookies` заставляет ядро отбрасывать расширенные TCP-опции (такие как `SACK` — выборочное подтверждение пакетов, или `Window Scaling` — масштабирование окна), что сильно бьет по скорости передачи данных для клиентов с плохим качеством связи. Чтобы этого не происходило, **обязательно** должен быть включен сбор таймстампов — тогда ядро спрячет TCP-опции в неиспользуемые биты временных меток:

```ini
net.ipv4.tcp_timestamps = 1
```

### Борьба со "спящими" полуоткрытыми сессиями

Если атакующий или оборвавший связь клиент не присылает финальный `ACK`, ядро по умолчанию будет удерживать полуоткрытое соединение в памяти, отправляя повторные `SYN-ACK` пакеты 5 раз (`tcp_synack_retries`), делая экспоненциальную паузу (общий таймаут ожидания — около 180 секунд).

Для высоконагруженных систем этот таймаут сокращают, уменьшая количество попыток до двух. Очередь будет очищаться в разы быстрее:

```ini
net.ipv4.tcp_synack_retries = 2
net.ipv4.tcp_syn_retries = 2
```

### Поведение при переполнении приложения (`tcp_abort_on_overflow`)

Если ваше приложение (например, залипший под GC Java-процесс или перегруженный PHP-FPM) не успевает вызывать `accept()`, очередь `Listen backlog` заполняется. По умолчанию Linux ведет себя скрытно: он просто игнорирует входящие `ACK` от клиентов. Клиент уверен, что соединение открыто, начинает слать данные (payload), но сервер их молча дропает. Клиент висит по таймауту ожидания ответа.

- Если ваш сервер работает напрямую с клиентами, дефолтное поведение (`0`) оправдано — оно дает приложению шанс "разгрести" очередь, пока клиенты пытаются повторить отправку пакетов.
- Если сервер стоит за балансировщиком нагрузки (HAProxy, Envoy, Cloudflare), этот параметр рекомендуется выставить в `1`:

```ini
net.ipv4.tcp_abort_on_overflow = 1
```

>_При переполнении очереди готовых сокетов ядро будет мгновенно отвечать клиенту (балансировщику) пакетом `RST` (Сброс соединения). Балансировщик сразу поймет, что эта нода перегружена, и перенаправит запрос на другой здоровый бэкенд, не заставляя пользователя ждать._

## 3.Разбор состояний TIME_WAIT и CLOSE_WAIT

Фазы закрытия TCP-сессии. Ошибки в этих состояниях приводят к лавинообразному отказу сетевой подсистемы бэкенда.

```
[Инициатор (Сервер)] ──── FIN ────> [Получатель (Клиент)]
[Инициатор (Сервер)] <─── ACK ───── [Получатель (Клиент)] (Переход в CLOSE_WAIT)
                                           │
                                    Приложение тупит
                                           │
[Инициатор (Сервер)] <─── FIN ───── [Получатель (Клиент)] (Вызов close() в коде)
[Инициатор (Сервер)] ──── ACK ────> [Получатель (Клиент)]
(Переход в TIME_WAIT: 60 сек)
```

### Состояние TIME_WAIT (Активное закрытие)

Состояние возникает на стороне того узла, **кто первый инициировал закрытие соединения** (вызвал системный вызов `close()`). В веб-инфраструктуре активным инициатором обычно выступает сервер (например, Nginx, отдавший статический файл клиенту без заголовка `Keep-Alive`).

- **Зачем это нужно ядру:** Сокет блокируется в этом статусе ровно на **2 * MSL (Maximum Segment Lifetime)**, что в ядре Linux жестко зашито и составляет **60 секунд** (изменить этот таймаут через `sysctl` невозможно, только пересборкой ядра). Это необходимо для двух целей:
    1. Дать время долететь и затухнуть "заблудившимся" в сети пакетам старой сессии, чтобы они случайно не вклинились в новое соединение, если оно откроется на тех же IP и портах.
    2. Гарантировать, что удаленный хост получил финальный пакет `ACK`. Если этот `ACK` потерялся, удаленная сторона пришлет `FIN` повторно, и сервер в состоянии `TIME_WAIT` сможет переотправить `ACK`.
- **В чем проблема под High Load:** Если сервер закрывает 10 000 соединений в секунду, то с учетом 60-секундного ожидания в системе одновременно будут висеть 600 000 сокетов в статусе `TIME_WAIT`. Они стремительно исчерпывают пул свободных локальных (эфемерных) портов. Как результат — сервер физически не может открыть ни одного нового исходящего соединения (например, сделать запрос к базе данных PostgreSQL, Redis или к соседнему микросервису), выдавая ошибку `Cannot assign requested address`.

### Тюнинг под High Load (Борьба с TIME_WAIT)

1. **Расширение пула эфемерных портов:** По умолчанию диапазон портов для исходящих соединений урезан. Расширяем его до максимума в `/etc/sysctl.conf`:

```ini
net.ipv4.ip_local_port_range = 1024 65535
```

2. **Повторное использование сокетов:** Разрешаем ядру безопасно переиспользовать сокеты, находящиеся в состоянии `TIME_WAIT`, для новых исходящих соединений к тому же целевому IP/порту:

```
net.ipv4.tcp_tw_reuse = 1
```

  - **⚠️ Критическая зависимость (Senior-нюанс):** Параметр `tcp_tw_reuse` **физически не работает**, если отключен сбор сетевых таймстампов. Чтобы механизм работал, они обязаны быть включены парой:
 
>```
>net.ipv4.tcp_timestamps = 1
>```

 - **Исторический миф (`tcp_tw_recycle`):** В старых статьях советовали включать `net.ipv4.tcp_tw_recycle`. **Забудьте про него.** Этот параметр агрессивно ломал входящие соединения от легитимных пользователей, сидящих за общим корпоративным или мобильным NAT. Из-за массовых проблем этот параметр был **полностью удален** из ядра Linux начиная с версии 4.12.

### Состояние CLOSE_WAIT (Пассивное закрытие)

Состояние возникает на стороне того узла, **кому прилетел входящий запрос на закрытие** (пакет `FIN`) от соседа.

- **Как это происходит под капотом:** Удаленный клиент закрыл вкладку или оборвал сессию. Его `FIN` прилетает на сервер. Ядро Linux на сетевом уровне обрабатывает пакет, автоматически отвечает клиенту пакетом `ACK` и переводит сокет в статус `CLOSE_WAIT`. На этом зона ответственности ядра заканчивается. Ядро встает в режим ожидания: оно ждет, пока _ваше приложение_ (код воркера) обработает это событие на уровне пользователя и вызовет `close()` для этого дескриптора сокета.
- **В чем проблема:** Сокеты в состоянии `CLOSE_WAIT` **не имеют таймаутов автоочистки**. Они могут висеть часами, днями и неделями, удерживая File Descriptor процесса. Если их накопится много — процесс упрется в лимит `Max open files` (`EMFILE`), и сервер перестанет принимать новые запросы.
- **Как лечить:** **Тюнинг системных параметров ядра здесь абсолютно бессилен.** Если сервер забит сокетами в `CLOSE_WAIT`, это **100% архитектурный баг в коде приложения** (разработчики забыли обработать конец потока `EOF` / нулевой размер при чтении из сокета и не закрыли дескриптор) либо поток приложения намертво заблокирован (`Deadlock`).
    - _Оперативное решение на проде:_ Только перезапуск сервиса (`systemctl restart`).
    - _Стратегическое решение:_ Отладка кода приложения, ревизия конструкций `try-with-resources` / `defer socket.Close()`.

### Важный сопутствующий лимит: Netfilter Conntrack

Если ваш сервер использует `iptables`/`nftables` или Docker (который строит на них сеть), все сетевые сессии (включая сотни тысяч в состоянии `TIME_WAIT`) заносятся в системную таблицу отслеживания соединений **Conntrack**.

При резком наплыве трафика эта таблица переполняется за секунды. При этом в логах `dmesg` появляется запись `nf_conntrack: table full, dropping packet`, и ядро начинает намертво отбрасывать любые пакеты, обрывая доступ к серверу.

- **Тюнинг Conntrack под High Load:**

```ini
 # Увеличиваем максимальный размер таблицы соранений (дефолт обычно 65k)
net.netfilter.nf_conntrack_max = 1048576

# Ускоряем очистку закрытых сессий в состоянии TIME_WAIT из таблицы conntrack (дефолт 120 сек)
net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
```

Шпаргалка по оперативной диагностике сокетов

Для анализа сетевого состояния используйте утилиту `ss` (она работает напрямую с `tcp_diag` ядра и работает в разы быстрее устаревшего `netstat`).

**1. Быстрая сводка по всем сокетам в системе (Оценка масштаба проблемы):**

```bash
ss -s
```

>_Смотрим на строку `TCP:` и количество сокетов в блоках `timewait` и `closed`._

**2. Точечный поиск виновника (Поиск процессов, удерживающих сокеты в `CLOSE_WAIT`):**  
Используем флаги `-t` (tcp), `-p` (показать PID/процесс), `-n` (числовые порты без резолва), `-a` (все сокеты):

```bash
ss -tpna | grep CLOSE_WAIT
```

>_Вывод четко покажет имя бинарника и PID процесса, внутри которого зависла логика закрытия дескрипторов._
