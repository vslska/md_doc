# OOM Killer (Out of Memory)

## Что такое OOM Killer и зачем он нужен?

Когда **вся доступная физическая память и пространство Swap исчерпаны**, а ядро Linux не может выделить физическую страницу памяти для выполнения системных вызовов (`brk`, `mmap`, `fork`), наступает критическое состояние — **Out of Memory (OOM)**.

## Что происходит в системе перед вызовом OOM Killer?

Ядро до последнего пытается избежать убийства процессов. Оно переходит в режим **Direct Reclaim (Прямое вытеснение)**: приостанавливает работу приложений и пытается агрессивно вымывать из RAM чистые страницы файлового кэша (Page Cache) и метаданных.

На Highload-серверах это приводит к лавинообразному росту нагрузки на диски (I/O Шторм). Процессы массово проваливаются в состояние жесткого сна (**`D-state`**), ожидая освобождения памяти. Система перестает отвечать на внешние запросы (происходит hard lockup).

Если даже полное уничтожение Page Cache не освободило нужный объем памяти, активируется механизм `out_of_memory()`. Ядро запускает алгоритм поиска процесса-«жертвы», принудительно завершает его самым жестким системным сигналом **`SIGKILL (-9)`**, который невозможно перехватить или проигнорировать, и мгновенно возвращает всю его память обратно в пул ОС, спасая сервер от полной аппаратной заморозки.

> Это **последняя линия обороны**. Лучше один условный `firefox` или `java-worker` погибнет, чем весь сервер уйдёт в hard lock.

## Как OOM Killer выбирает жертву?

Алгоритм ядра сканирует все запущенные процессы в системе (или внутри конкретной cgroup) и вычисляет для каждого числовой рейтинг — **`oom_score`** (значение от 0 до 1000). Процесс с **наивысшим баллом** уничтожается первым.

### Современная формула расчета (Ядра Linux ≥ 2.6.36, включая 5.x / 6.x)

Базовый балл рассчитывается как доля памяти, которую процесс занимает относительно общего объема доступной системе памяти (RAM + Swap), выраженная в **промилле (долях от 1000)**:

```
Базовый OOM Score = ((RSS + Swap + Tmpfs процесса) / (Общий объем RAM + Общий объем Swap)) * 1000
```

К полученному базовому баллу ядро математически прибавляет пользовательский коэффициент смещения:

```
Итоговый oom_score = Базовый OOM Score + oom_score_adj
```

### Факторы влияния на `oom_score`

|Фактор|Влияние на `oom_score`|Механика ядра|
|---|---|---|
|**Потребление памяти**|Прямо пропорционально|Чем больше RSS + swap + tmpfs, тем выше базовый скор (в промилле от RAM + Swap)|
|**Приоритет (`oom_score_adj`)**|Пользовательский штраф/бонус|Смещение от `-1000` до `+1000`. Прибавляется линейно к базовому скору|
|**root-процессы (UID 0)**|Слегка понижаются|Ядро принудительно отнимает 30 баллов (3% памяти) от базового скора|
|**Процессы с `CAP_SYS_ADMIN`**|Слегка понижаются|Относятся к системным административным задачам, получают ту же скидку в 30 баллов|
|**Процессы с `memcg`-лимитами**|Учёт ведётся **внутри cgroup**|Если лимит превышен внутри контейнера, расчет промилле идет от `memory.max` этой cgroup|

> При `oom_score_adj = -1000` итоговый `oom_score` принудительно сбрасывается в `0`. **Такой процесс ядро не убьет никогда.**

## Управление OOM-приоритетами в продакшене

### 1. Ручное управление через `/proc`

Защитить критически важный процесс (например, master-процесс СУБД с PID `7890`) от OOM Killer можно прямой записью в виртуальную ФС:

```bash
echo -1000 > /proc/7890/oom_score_adj
```

_Проверить текущий реальный балл любого живого процесса:_

```bash
cat /proc/7890/oom_score
```

### 2. Защита процессов в Systemd

Так как после перезапуска сервиса PID изменится, ручная запись через `/proc` не подходит. В systemd-юнитах для этого используется специальная директива в секции `[Service]`:

```ini
[Service]
# Аналог oom_score_adj = -1000 (Полная защита от OOM)
OOMScoreAdjust=-1000
```

### 3. Классы QoS в Kubernetes (Связь с oom_score_adj)

Kubernetes управляет OOM-приоритетами подов автоматически на основе их конфигурации ресурсов (`requests` и `limits`), разделяя их на 3 класса качества обслуживания:

- **Guaranteed:** `requests` строго равны `limits` для CPU и Memory. На уровне ядра рантайм выставляет им `OOMScoreAdjust=-997`. Их ядро убьет в самую последнюю очередь.
- **Burstable:** `requests` меньше чем `limits`. Вычисляется кастомный `oom_score_adj` в диапазоне от `2` до `999` на основе формулы отношения запрошенной памяти к объему ноды. Чем больше памяти запросил под, тем ниже его штраф.
- **BestEffort:** В манифесте вообще не указаны ни `requests`, ни `limits`. Ядро выставляет им жесткий штраф `OOMScoreAdjust=1000`. При малейшей нехватке памяти на ноде эти поды уничтожаются первыми.

## Альтернативное поведение: Тюнинг `panic_on_ooms`

В распределенных Highload-кластерах (например, Elasticsearch, ClickHouse, Галерея баз данных) дефолтное поведение OOM-Killer может быть опасным. Если ядро убьет один из внутренних тяжелых процессов СУБД, база перейдет в состояние «зомби» (процесс мертв, но сетевой порт сокета может остаться открытым), нарушая консистентность данных в кластере.

В таких архитектурах выгоднее настроить **Kernel Panic (Панику ядра)**, чтобы сервер мгновенно уходил в перезагрузку, позволяя балансировщикам и оркестраторам переключить трафик на резервную ноду (Failover).

Настройка в `/etc/sysctl.conf`:

```ini
# Переводить ядро в панику при наступлении OOM (0 — дефолт, убивать процессы; 1 — паника всей ОС)
vm.panic_on_oom = 1

# Автоматически перезагружать сервер через 10 секунд после ухода в Kernel Panic
kernel.panic = 10
```

## Диагностика и разбор логов OOM

Когда процесс падает по OOM, он не успевает записать это в свои логи приложения. Единственный след остается в кольцевом буфере ядра.

### 1. Быстрый поиск факта срабатывания OOM

```bash
journalctl -k --grep="Out of memory"
# Или через dmesg:
dmesg -T | grep -i -E 'oom[-_]killer|killed'
```

### 2. Анатомия лога ядра (Что искать в дампе)

При срабатывании OOM ядро выплескивает в системный лог огромную таблицу метаданных. При анализе дампов важно обращать внимание на следующие маркеры:

```text
[12345.678900] Task in /user.slice/user-1000.slice killed as a result of limit of /user.slice/user-1000.slice
[12345.678910] Memory cgroup out of memory: Killed process 9999 (java) total-vm:4123456kB, anon-rss:2048576kB, file-rss:0kB, shmem-rss:0kB
```

- **`Killed process 9999 (java)`** — указывает точный PID и имя бинарника, который был уничтожен.
- **`anon-rss`** — реальный объем анонимной памяти (куча, стек), который занимал процесс на момент гибели (в килобайтах).
- **`limit of /...`** — если в строке присутствует упоминание путей к cgroup, это означает, что сработал **локальный Cgroup OOM-Killer** (лимит контейнера), а не глобальный дефицит памяти на физическом сервере.
