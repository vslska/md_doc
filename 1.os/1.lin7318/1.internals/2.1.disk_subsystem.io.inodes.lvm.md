# Дисковая подсистема (I/O, Inodes & LVM)

>*Этот раздел посвящен глубокому пониманию работы ядра с накопителями, виртуальной файловой системой (VFS), механизмами кэширования I/O и управлению логическими томами (LVM).*

## 1. Индексы файловой системы (Inodes)

В Linux имя файла — это всего лишь жесткая ссылка (hardlink), связывающая человекочитаемый путь со строкой в таблице директории. Все метаданные файла (размер, владелец, права доступа, метки времени, указатели на физические блоки данных на диске) хранятся в изолированной структуре — **Inode (Index Node)**. Имя файла внутри самой структуры inode **не хранится**.

### Сценарий: «Место на диске есть, но записать файл нельзя»

При попытке создать файл или директорию система выдает ошибку `No space left on device`, хотя утилита `df -h` показывает, что свободно еще более 50% физического объема.

- **Причина:** На файловой системе закончились свободные дескрипторы inode.
    - _В Ext4_ общее количество inode жестко задается один раз при форматировании. Если на диске создается миллион файлов по 1 байту, гигабайты диска будут свободны, но лимит inode исчерпается.
    - _В XFS_ инноды выделяются динамически, но их суммарный объем ограничен процентом от емкости диска (параметр `maxpct`). При забивании диска мелкими файлами XFS тоже может упереться в этот лимит.
- **Диагностика:**
```
df -i
```

 _Смотрим колонку `IUse%`. Если там 100% — новые файлы создать невозможно._
- **Как лечить:** Найти директорию с аномальным количеством мелких файлов (кэш сессий приложений, очереди почты, `/var/lib/php/sessions/`) и очистить её.**Скрипт быстрого поиска топ-10 папок по количеству файлов:**

```bash
find / -xdev -type f | awk -F/ 'NF>1{OFS="/"; NF--; print $0}' | sort | uniq -c | sort -rn | head -10
```

### Сценарий: «Удалили гигантский лог, но место на диске не освободилось»

Администратор выполнил `rm /var/log/heavy_app.log`, файл исчез из видимости, но `df -h` по-прежнему показывает 100% утилизации диска.

- **Причина:** Команда `rm` лишь удаляет жесткую ссылку из дерева директорий и уменьшает счетчик ссылок (link count) в inode файла на единицу. Однако, если запущенный процесс приложения все еще держит этот файл открытым через свой **File Descriptor**, ядро увеличивает счетчик открытых дескрипторов (open refs).Ядро Linux **физически не освободит блоки данных на диске**, пока суммарный счетчик ссылок (`link count` + `open refs`) для данного inode не станет равным нулю.
- **Диагностика (поиск удаленных, но удерживаемых процессов файлами):**  
    Используем `lsof` с флагами `-n` и `-P`, чтобы отключить долгий сетевой резолв на нагруженном сервере:

```
lsof -nP | grep deleted
```

>_Вывод покажет PID процесса, имя приложения и номер дескриптора (FD), который держит файл._

- **Как лечить БЕЗ перезапуска сервиса:**  
    Если сервис критически важный (например, Production СУБД) и его нельзя перезапускать, можно принудительно очистить блоки данных, обнулив файл через виртуальную файловую систему `/proc`. На примере PID `5678` и дескриптора `4`:

```
: > /proc/5678/fd/4
```

>Место на диске освободится **мгновенно**, а приложение продолжит работать.

- **⚠️ Критическое предупреждение:**  
    Этот трюк безопасен для обычных потоковых логов. Но если приложение использует сложную систему логирования, которая кеширует текущую позицию указателя в файле (`file offset`) или использует системный вызов `lseek()`, то следующая запись после обнуления запишется не в начало файла, а **в ту же позицию (смещение), где запись прервалась**. В результате ядро создаст **разреженный файл (Sparse File)**. На диске он будет занимать 0 байт, но его логический размер (в выводе `ls -lh`) останется огромным. Любая попытка прочитать его целиком или сделать бэкап заставит систему забивать нулями реальное пространство диска. Правильный превентивный метод борьбы — настройка `copytruncate` в `logrotate` или использование `truncate -s 0`.

## 2. VFS (Virtual File System) и кэширование записи

**Virtual File System (VFS)** — это абстрактный слой ядра Linux, который предоставляет приложениям единый POSIX-интерфейс (`open`, `read`, `write`, `close`) для работы с любыми типами файловых систем (локальными Ext4/XFS, сетевыми NFS/CephFS, виртуальными `procfs`/`sysfs`).

### Механизм Dirty Pages (Грязные страницы)

Когда приложение выполняет системный вызов `write()`, ядро из соображений производительности не производит синхронную запись на физический накопитель. Вместо этого данные пишутся в оперативную память (Page Cache), а измененные страницы памяти помечаются флагом **`PG_dirty` (Грязные страницы)**.

Для приложения операция завершается за наносекунды. Сбросом этих страниц из RAM на физический диск занимаются специализированные фоновые потоки ядра — **`flusher threads`** (в списке процессов отображаются как `[writeback]`), которые работают асинхронно.

### Тюнинг параметров сброса (sysctl)

Поведение `flusher threads` регулируется через параметры ядра в `/etc/sysctl.conf`.

- **`vm.dirty_background_ratio`** (дефолт ~10%): Процент от общей доступной памяти (Dirtyable Memory). При достижении этого порога ядро активирует фоновые потоки `writeback`. Они начинают сбрасывать данные на диск на заднем плане, **не блокируя** работу приложения.
- **`vm.dirty_ratio`** (дефолт ~20%): Жесткий блокирующий потолок. Если приложение генерирует данные быстрее, чем дисковая подсистема успевает их утилизировать, и объем грязных страниц достигает этого значения, ядро **полностью блокирует все новые системные вызовы `write()`** для всех процессов. Приложение принудительно переводится в состояние жесткого сна (`D-state`) и ждет, пока `flusher threads` не опустят объем грязных страниц ниже лимита. На Highload-системах это проявляется как внезапные дикие фризы (I/O Spikes / Latency spikes).

### Оптимизация для High Load (СУБД, ClickHouse, Kafka, тяжелый I/O)

На серверах с большим объемом RAM (например, 256 ГБ) дефолтные 10% и 20% — это 25 ГБ и 50 ГБ грязных данных соответственно. Попытка сбросить 50 ГБ данных за раз гарантированно "поставит на колени" любой дисковый массив.

Чтобы сброс шел непрерывно, мелкими порциями, параметры переводят из процентов в **абсолютные байты**:

```ini
# Активировать фоновый сброс при накоплении 64 МБ грязных страниц
vm.dirty_background_bytes = 67108864

# Намертво блокировать запись при накоплении 128 МБ грязных страниц
vm.dirty_bytes = 134217728
```

_Важно: При установке параметров с суффиксом `_bytes`, аналогичные параметры с суффиксом `_ratio` ядром автоматически сбрасываются в `0`._

Регулировка по времени (Таймауты)

- **`vm.dirty_expire_centisecs`** (дефолт `3000` = 30 секунд): Определяет "возраст" грязной страницы. Если страница остается грязной дольше этого времени, при следующем цикле бодрствования потоки `writeback` заберут её на диск.
- **`vm.dirty_writeback_centisecs`** (дефолт `500` = 5 секунд): Интервал времени, с которым фоновые потоки `writeback` "просыпаются" и проверяют систему.

Для систем с высокими требованиями к сохранности данных (и быстрыми NVMe) эти параметры часто снижают:

```ini
vm.dirty_expire_centisecs = 1000   # 10 секунд
vm.dirty_writeback_centisecs = 200 # 2 секунды
```

Диагностика кэша записи в реальном времени

```bash
cat /proc/meminfo | grep -E "Dirty|Writeback"
```


- `Dirty` — данные, которые изменены, но еще сидят в RAM.
- `Writeback` — данные, которые прямо в эту секунду контроллер диска физически сбрасывает на накопитель.

## 3. Устройство LVM (Logical Volume Manager)

**LVM** — это слой абстракции между физическими накопителями и файловой системой. Он позволяет объединять разнородные диски в единые пулы памяти, динамически нарезать виртуальные разделы и менять их размеры «на лету» без остановки сервисов.

Трехуровневая архитектура LVM

1. **PV (Physical Volume / Физический том):** Инициализированный для работы с LVM физический диск, NVMe-накопитель или раздел (например, `/dev/sdb`). При инициализации (`pvcreate`) диск разбивается на мелкие блоки — **Физические экстенты (PE — Physical Extents)**, обычно по 4 МБ.
2. **VG (Volume Group / Группа томов):** Виртуальный пул, объединяющий один или несколько PV в единое пространство (аналог программного JBOD). Создается через `vgcreate`.
3. **LV (Logical Volume / Логический том):** «Виртуальный раздел», который нарезается из пула VG (`lvcreate`) путем выделения определенного количества экстентов. Для операционной системы LV выглядит как обычное блочное устройство в `/dev/mapper/`.

Инструкция: Расширение диска внутри виртуалки на лету (Без перезагрузки)

Задача: в панели гипервизора (VMware, Proxmox) размер диска запущенной ВМ увеличили с 50 ГБ до 100 ГБ. Отдаем пространство ОС без остановки продакшена.

### Шаг 1: Сканирование шины SCSI

Заставляем ядро пересканировать SCSI-шину, чтобы актуализировать размер блочного устройства (например, `/dev/sda`):

```bash
echo 1 > /sys/class/block/sda/device/rescan
```

#### ⚠️ Важное ветвление: Диск целиком vs Таблица разделов

- **Сценарий А (Best Practice):** LVM развернут прямо на "сыром" диске (`/dev/sda` является физическим томом PV). В этом случае переходите сразу к **Шагу 2**.
- **Сценарий Б (Legacy):** При установке ОС диск был размечен через MBR/GPT (например, PV — это раздел `/dev/sda3`). Тогда LVM не увидит место, пока не изменится геометрия таблицы разделов. Решается утилитой `growpart` (пакет `cloud-utils`):

```
growpart /dev/sda 3   # Расширяет 3-й раздел на диске /dev/sda
partx -u /dev/sda     # Заставляет ядро обновить таблицу разделов в памяти
```

### Шаг 2: Расширение Physical Volume (PV)

```bash
pvresize /dev/sda
```

### Шаг 3: Расширение Logical Volume (LV)

Добавляем все 100% освободившегося в VG пространства к нашему логическому тому (например, к корню системы):

```bash
lvextend -l +100%FREE /dev/vg_system/lv_root
```

### Шаг 4: Расширение файловой системы под размер тома

**Для Ext4:**

```bash
resize2fs /dev/vg_system/lv_root
```
 
**Для XFS:**  
_В отличие от Ext4, утилите `xfs_growfs` в качестве аргумента передается **точка монтирования** целевой файловой системы:
 
```
xfs_growfs
```

### Архитектурный нюанс: Опасность Overcommit в LVM Thin Provisioning

В современных инфраструктурах часто используют **Thin Pools (Тонкие пулы)**. Они позволяют создавать "виртуальные" LV, суммарный логический размер которых превышает реальный физический размер группы томов (механизм Overcommit). Например, в физический пул размером 100 ГБ можно нарезать пять тонких LV по 40 ГБ каждый.

- **Где сокрыта авария:** Если все приложения начнут одновременно писать реальные данные и суммарный физический объем пула достигнет 100%, произойдет **полный отказ дисковой подсистемы**.
- **Поведение ядра:** В отличие от обычного заполнения диска (когда ФС просто возвращает ошибку `No space left on device` конкретному приложению), при переполнении Thin Pool ядро Linux переводит весь пул в режим **I/O Error** или **Read-Only**. Процессы (особенно базы данных) моментально падают в аварийный останов (Crash).
- **Диагностика тонких томов:** Обычный `df -h` не показывает реальную утилизацию тонкого пула. Используйте команду:

```
lvs -o+data_percent,metadata_percent
```
 
>_Критически важно следить за колонкой `Data%`. Если она приближается к 80-90%, пул необходимо срочно расширять._
