# LVM (Logical Volume Manager): Архитектура, углубленный тюнинг и аварийное восстановление

**LVM** — это слой абстракции между физическими накопителями и файловой системой. Он позволяет объединять физические диски в единые пулы памяти, динамически распределять пространство и управлять томами «на лету» без остановки сервисов.

---

## Подробная трехуровневая архитектура LVM

```text
  [ /dev/sdb1 ]        [ /dev/sdc1 ]  <- Physical Volumes (PV)
        │                    │
        └──────────┬─────────┘
                   ▼
             [  vg_data  ]            <- Volume Group (VG)
        ┌──────────┼──────────┐
        ▼          ▼          ▼
  [ lv_root ] [ lv_db ]  [ lv_swap ]  <- Logical Volumes (LV)
```


1. **PV (Physical Volume):** Инициализированный блочный девайс. При создании (`pvcreate`) ядро нарезает его на **PE (Physical Extents)** — неделимые блоки памяти (по умолчанию **4 MiB**).
2. **VG (Volume Group):** Пул хранилища, объединяющий PE от разных физических дисков в одну виртуальную емкость.
3. **LV (Logical Volume):** Логический раздел, нарезаемый из свободных PE внутри группы томов. ОС видит его как стандартное блочное устройство в `/dev/mapper/vg_name-lv_name`.

## Справочник продвинутых команд управления

|Операция|Команда|Инженерный нюанс|
|---|---|---|
|**Инициализация PV**|`pvcreate /dev/nvme0n1`|Начисто стирает заголовки существующих ФС.|
|**Создание VG**|`vgcreate vg_prod /dev/sdb /dev/sdc`|Объединяет физические диски в пул.|
|**Создание LV**|`lvcreate -l 100%FREE -n lv_data vg_prod`|Нарезка в экстентах (`-l`) точнее, чем в гигабайтах (`-L`).|
|**Создание Striped LV**|`lvcreate -i 3 -I 64k -l 100%FREE -n lv_fast vg_prod`|**Тюнинг Highload:** Распараллеливает запись на 3 диска (RAID-0) блоками по 64 КБ.|
|**Расширение LV**|`lvextend -l +100%FREE /dev/vg_prod/lv_data`|Добавляет все свободные PE из группы томов.|
|**Перенос данных на лету**|`pvmove /dev/sdb /dev/sdd`|**Live-миграция:** Прозрачно перемещает экстенты со старого диска на новый без размонтирования ФС.|
|**Активация VG**|`vgchange -ay vg_prod`|Принудительная активация томов (при загрузке с LiveCD).|

## Практический сценарий: Горячее расширение корня (`/`)

Условие: Корень развернут на `/dev/vg0/lv_root`. В систему на горячую добавлен диск `/dev/sdb` на 50 ГБ.

### Шаг 1. Расширение пула VG

```bash
# Инициализируем диск для LVM
pvcreate /dev/sdb

# Расширяем группу томов vg0, добавляя в неё новый диск
vgextend vg0 /dev/sdb
```

_Убедиться, что показатель `Free PE / Size` увеличился, можно командой `vgs` или `vgdisplay`._

### Шаг 2. Растягивание тома и ФС одной командой

Вместо последовательного выполнения `lvextend` и утилит файловой системы, используйте безопасный универсальный флаг `-r` (`--resizefs`). Он сам определит тип ФС и расширит её:

```bash
lvextend -l +100%FREE -r /dev/vg0/lv_root
```

**Если требуется выполнить операции раздельно:**

```bash
# 1. Расширяем блочное устройство тома
lvextend -l +100%FREE /dev/vg0/lv_root

# 2. Если у вас Ext4:
resize2fs /dev/vg0/lv_root

# 2. Если у вас XFS (В качестве аргумента передается точка монтирования, а не путь к сокету):
xfs_growfs /
```

## Углубленная работа со снапшотами (Snapshots)

Снапшот в LVM работает по принципу **COW (Copy-on-Write)**. Он не копирует данные изначально. При создании снапшота ядро просто фиксирует карту экстентов. Когда процесс пытается _изменить_ блок на оригинальном томе, старый оригинальный блок сначала копируется в пространство снапшота, и только потом перезаписывается.

### ⚠️ Смертоносная ловушка переполнения снапшота

Если объем измененных данных превысит выделенный под снапшот размер (например, выделили 5 ГБ, а база данных перезаписала 6 ГБ), снапшот мгновенно переходит в статус **`Invalid` (Ломается)**. Данные бэкапа внутри него полностью превращаются в кашу. Используйте снапшоты строго как краткосрочный инструмент на время снятия бэкапа.

### ⚠️ Ловушка одинаковых UUID на XFS при монтировании

Снапшот является посекторной копией тома и наследует его уникальный идентификатор `UUID`. Ядро Linux блокирует монтирование двух ФС с одинаковым UUID на одном хосте. Попытка выполнить стандартный `mount` намертво зависнет или выбросит ошибку.

**Правильный алгоритм снятия бэкапа со снапшота:**

```bash
# 1. Создаем снапшот размером 10 ГБ для корня
lvcreate -L 10G -s -n root_snapshot /dev/vg0/lv_root

# 2. Монтируем на XFS с обязательным отключением проверки UUID (флаг nouuid)
mkdir -p /mnt/backup_snap
mount -o ro,nouuid /dev/vg0/root_snapshot /mnt/backup_snap

# 3. После снятия бэкапа — размонтируем и уничтожаем снапшот, чтобы не деградировал I/O
umount /mnt/backup_snap
lvremove -f /dev/vg0/root_snapshot
```

## Безопасное сжатие разделов (lvreduce)

Сжатие — деструктивная операция. Ошибка в расчетах геометрии на 1 мегабайт уничтожит суперблок ФС.

- **Для файловых систем XFS:** Сжатие **невозможно в принципе** на уровне архитектуры ФС. Единственный путь уменьшить XFS том — сделать полный дамп через `xfsdump`, удалить LV, создать LV меньшего размера, форматировать и залить данные обратно через `xfsrestore`.
- **Для файловых систем Ext4:** Никогда не выполняйте `lvreduce` и `resize2fs` раздельными командами вручную. Используйте встроенную безопасную обертку, которая сама выполнит жесткие проверки размеров:

```bash
# Размонтирование обязательно! Сжатие на горячую запрещено
umount /mnt/data

# Безопасное уменьшение тома и ФС Ext4 до строгого размера в 20 ГБ
lvreduce --resizefs -L 20G /dev/vg0/lv_data
```

## Диагностика, автоматизация и аварийное восстановление

### Восстановление разрушенной таблицы метаданных LVM

Если на физическом диске повредились первые сектора и LVM перестал видеть группу томов (ошибка `unknown device`), конфигурацию можно восстановить из автоматических бэкапов ядра.

Ядро Linux сохраняет текстовый дамп метаданных LVM при каждом изменении (создании, расширении, удалении томов) в каталоге `/etc/lvm/archive/`.

```bash
# 1. Смотрим список доступных архивных копий для нашей VG (например, vg0)
vgcfgrestore --list vg0

# 2. Восстанавливаем структуру VG из конкретного файла бэкапа
vgcfgrestore -f /etc/lvm/archive/vg0_00002-12345.vg vg0
```

### Автоматизация: Экспорт состояния в JSON для скриптов мониторинга

Для написания bash-скриптов или кастомных Zabbix/Prometheus экспортеров парсить стандартный вывод утилит через `awk` хрупко. Используйте встроенный JSON-репортер:

```bash
# Вывести список всех VG с объемом свободного места в формате JSON
vgs --reportformat json
```

Пример интеграции с парсером `jq` (найти все VG, где свободное место упало критически низко):

```bash
vgs --reportformat json | jq '.report[0].vg[] | select(.vg_free_size < "5.00g")'
```


### Тюнинг SSD: TRIM / Discards через LVM

По умолчанию LVM блокирует прохождение команд очистки ячеек `TRIM` от файловой системы к физическому SSD-накопителю через свои слои абстракции. Это приводит к деградации скорости записи на SSD со временем.

- **Решение:** Откройте конфигурационный файл `/etc/lvm/lvm.conf`, найдите параметр `issue_discards` и переведите его в режим активации:

```bash
devices {
    issue_discards = 1
}

```

>_После этого команды сброса неиспользуемых блоков данных будут прозрачно долетать от ФС до контроллера SSD._
