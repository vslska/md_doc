# CPU, RAM & Process Architecture  
  
Этот раздел посвящен глубокому пониманию работы ядра с процессами, виртуальной памятью и системными ограничениями. Здесь собрана внутрянка, необходимая для диагностики High Load систем

---

## 1. Анатомия дескрипторов файлов (File Descriptors) и лимитов

В Linux концепция **«всё есть файл»** является фундаментальной. Когда процесс открывает файл на диске, сетевой сокет, пайп (pipe) или устройство, ядро не работает с ними напрямую. Оно выделяет процессу **File Descriptor (FD)** — целое неотрицательное число (0, 1, 2 и т.д.), которое служит индексом в локальной таблице файлов процесса.

Этот индекс ссылается на глобальную таблицу открытых файлов ядра (`struct file`), которая, в свою очередь, указывает на конкретный системный `inode`.

### 1.1. Анатомия сбоя: Ошибки EMFILE и ENFILE

Когда лимиты дескрипторов исчерпаны, приложение теряет стабильность. Сетевые сервисы (Nginx, HAProxy) перестают вызывать `accept()` и сбрасывают новые сетевые соединения, базы данных не могут сбросить логи на диск, а сам процесс теряет возможность логировать происходящее.

Ядро возвращает две разные ошибки в зависимости от уровня, на котором произошел сбой:

- **`EMFILE (Too many open files)`** — достигнут лимит конкретного процесса. Лечится тюнингом лимитов процесса.
- **`ENFILE (File table overflow)`** — глобальный лимит всей операционной системы исчерпан. В этот момент ОС больше не может открыть ни одного файла вообще (критическая ситуация).

### 1.2. Уровни ограничений (Лимиты)

#### Системный уровень (Global Limit)

Ограничивает максимальное количество открытых файлов для всего ядра ОС суммарно по всем процессам.

- **Проверить текущий лимит:** `cat /proc/sys/fs/file-max`
- **Проверить, сколько открыто прямо сейчас:** `cat /proc/sys/fs/file-nr`  
    _(Выведет 3 числа: открытые_FD, выделенные_но_неиспользуемые, системный_максимум)._
- **Временное изменение (до ребута):** `sysctl -w fs.file-max=2097152`
- **Перманентная настройка:** Прописать `fs.file-max = 2097152` в файл `/etc/sysctl.conf`.

#### Процессный уровень (Per-Process Limits / Ulimit)

Ограничивает количество FD, которое может открыть **один конкретный процесс**, порожденный в рамках сессии shell.

- **Soft Limit (Мягкий):** Текущее ограничение. Процесс имеет право сам поднять его во время работы (через системный вызов `setrlimit()`), но не выше значения Hard Limit. Проверить: `ulimit -Sn`
- **Hard Limit (Жесткий):** Потолок для Soft Limit. Обычный пользователь (не root) не может увеличить это значение. Проверить: `ulimit -Hn`

### 1.3. Где настраивать лимиты процессов в продакшене?

#### Для пользователей и SSH-сессий

Настройки задаются в конфигурационном файле `/etc/security/limits.conf`:
```
# Пользователь nginx (мягкий и жесткий лимиты)
nginx    soft    nofile   65536
nginx    hard    nofile   65536
```

#### Для системных демонов (Systemd)

**Важно:** Сервисы под управлением `systemd` полностью игнорируют файл `limits.conf`. Для них лимиты настраиваются напрямую в юните службы (рекомендуется использовать `systemctl edit имя_сервиса`):
```bash
[Service]
LimitNOFILE=65536
```

### 1.4. Диагностика и траблшутинг

#### Подсчет открытых FD процессом

Чтобы быстро узнать, сколько дескрипторов сейчас занял процесс (на примере PID `1234`):

```bash
ls -1 /proc/1234/fd | wc -l
```

_(Флаг `-1` гарантирует вывод строго в один столбец для корректного подсчета через `wc -l`)_.

#### Аудит удерживаемых ресурсов

Чтобы детально разобраться, что именно держит процесс — конкретные лог-файлы, системные библиотеки, сетевые соединения (IP и порты) или пайпы:
```bash
lsof -p 1234
```

#### Проверка лимитов живого процесса

Если процесс уже запущен, параметры `ulimit` для него можно подсмотреть в виртуальной файловой системе `/proc`:

```bash
cat /proc/1234/limits | grep "Max open files"
```

#### Изменение лимитов: Постоянное vs «На лету»

**Вариант А: Постоянное (через Systemd с перезапуском)** 

После добавления `LimitNOFILE=65536` в `[Service]`-секцию юнита, необходимо применить изменения и **перезапустить** сервис. Простого перечитывания конфигурации (`daemon-reload`) для живого процесса недостаточно:

```bash
systemctl daemon-reload
systemctl restart имя_сервиса
```   
 
**Вариант Б: На лету БЕЗ перезапуска (через `prlimit`)**  

Если сервис находится под высокой нагрузкой (например, production-база данных) и его нельзя перезапускать прямо сейчас, можно изменить лимиты для живого PID `1234` с помощью утилиты `prlimit`:

```bash
# Установить Soft и Hard лимиты в 65536 для PID 1234
prlimit --pid 1234 --nofile=65536:65536
```

> _Изменение применится мгновенно в памяти ядра, но сбросится после перезапуска самого процесса._

## 2. Управление памятью: Virtual Memory & Swap

Linux использует **Виртуальную память**. Процессы никогда не работают с физической RAM напрямую. Ядро выделяет каждому процессу изолированное виртуальное адресное пространство, разделенное на **Страницы (Pages)** (на архитектуре x86/x86_64 размер страницы по умолчанию составляет **4 КБ**).

Физическая память выделяется лениво (lazy allocation) — только в момент фактического обращения к адресу.

### 2.1. Механизм маппинга (Page Faults)

Когда процесс запрашивает память (например, через `brk()` или `mmap()`), ядро выделяет ему _виртуальный_ адрес, но физическую RAM под него не резервирует. При первой попытке записи или чтения по этому адресу процессор генерирует исключение — **Page Fault**, заставляя ядро выделить физическую память.

- **Minor Page Fault (Мягкий сбой):** Происходит в контексте RAM, без обращения к диску.
    - _Сценарий 1:_ Процесс впервые пишет в выделенную память, и ядро выделяет ему чистую физическую страницу из пула свободных.
    - _Сценарий 2:_ Процесс открывает файл или общую библиотеку (`.so`), которая **уже загружена** в системный Page Cache другим процессом. Ядро просто связывает виртуальный адрес процесса с уже существующей страницей в RAM.
    - *Сценарий 3:* База данных делает тяжелый `SELECT` второй раз подряд. Данные уже осели в Page Cache Linux после первого раза. Происходит Minor Fault, и данные отдаются мгновенно.
    
- **Major Page Fault (Жесткий сбой):** Происходит, когда нужных данных нет в оперативной памяти. Ядро вынуждено приостановить поток процесса и выполнить **тяжелую операцию ввода-вывода (I/O) с диска**:
    - _Сценарий 1:_ Чтение куска файла, которого еще нет в Page Cache.
    - _Сценарий 2:_ Чтение страницы анонимной памяти, которая ранее была вытеснена в Swap.
    - **Влияние на Highload:** Высокий показатель Major Page Faults переводит нагрузку из CPU-bound в I/O-bound, драматически увеличивает latency приложения и может полностью парализовать систему.

#### 2.2. Разница между Anonymous Memory и Page Cache

Ядро Linux разделяет физическую память на две основные категории ( при управлении страницами (Page Frame Reclamation)), которые по-разному вытесняются при нехватке RAM (Memory Pressure):

- **Page Cache (Файловый кэш):** Копия данных файлов с диска в RAM.
    - _Чистые страницы (Clean):_ Полностью совпадают с данными на диске. Если системе нужна память, ядро мгновенно и бесшумно уничтожает их. При следующем обращении к ним произойдет Major Page Fault, и они перечитаются с диска.
    - _Грязные страницы (Dirty):_ Изменены процессом, но еще не записаны на диск. Их нельзя просто выбросить — сначала фоновые потоки ядра (`flusher threads`) должны сбросить их на диск.
- **Anonymous Memory (Анонимная память):** Память, созданная процессами и не связанная с файлами (стек, куча/heap, runtime-данные приложения). Её нельзя просто уничтожить. Единственный способ освободить RAM от анонимной памяти без убийства процесса — сбросить её в **Swap**.

#### 2.3. Тюнинг `vm.swappiness`

Параметр `vm.swappiness` (значение от 0 до 100, дефолт в большинства дистрибутивов — 60) определяет соотношение между вытеснением Page Cache и сбросом Anonymous Memory в Swap при нехватке памяти.
```
Ratio = Готовность сбрасывать Page Cache / Готовность сбрасывать в Swap
```

- **Миф:** `swappiness = 0` — это лучшая настройка, которая полностью отключает Swap для скорости.
- **Реальность (для ядер Linux 3.5+):** При `swappiness = 0` ядро **категорически запрещает** свопить анонимную память, пока это физически возможно. Ядро будет агрессивно вымывать Page Cache (уничтожая скорость работы с диском и файлами) и кэш метаданных. Если память все равно закончится, система вызовет **OOM-Killer** и убьет ваше приложение, даже если раздел Swap заполнен всего на 1%.
- **Рекомендации для Production (Базы данных, K8s-ноды, Java/Go highload):**  
    Устанавливайте значение `1` или `10`. Это заставляет ядро максимально сохранять Page Cache, но оставляет ему легальную возможность использовать Swap в экстренных ситуациях вместо моментального вызова OOM-Killer.
    - Изменить на лету: `sysctl -w vm.swappiness=10`
    - Закрепить перманентно в `/etc/sysctl.conf`: `vm.swappiness = 10`

#### 2.4. Важный компаньон: `vm.vfs_cache_pressure`

При тюнинге swappiness часто забывают про кэш метаданных файловой системы (директории и структуры файлов — `directory/inode entries`).

- По умолчанию параметр равен `100`.
- Если вы снизили `swappiness`, ядро начнет сильнее давить на файловые кэши. Чтобы ядро слишком агрессивно не выбивало из памяти метаданные файлов (что заставит систему заново перечитывать дерево каталогов с диска), этот параметр рекомендуется снизить до `50`:
    
    bash
    
    ```
    sysctl -w vm.vfs_cache_pressure=50
    ```
    
    Use code with caution.
    

2.5. Полезные команды для диагностики памяти

- **Мониторинг Page Faults в реальном времени:**
    
    bash
    
    ```
    sar -B 1
    ```
    
    Use code with caution.
    
    _(Смотрим на колонки `majflt/s` (Major faults, должно быть около 0) и `pgscank/s` / `pgscand/s` (работа ядра по поиску страниц для очистки))._
- **Посмотреть объем Page Cache и Anonymous памяти прямо сейчас:**
    
    bash
    
    ```
    cat /proc/meminfo | grep -E "Cached|AnonPages|Buffers"
    ```
    
    Use code with caution.

Глава 3. Виды состояний процессов (Process States)

В выводе команд `top`, `ps` или `btop` каждый процесс имеет статус (колонку `STAT`). На низком уровне ядро управляет процессами через планировщик (Scheduler), переводя их между очередями выполнения и ожидания.

|Статус в `ps`|Состояние ядра|Описание|Можно ли убить через `kill -9`?|
|---|---|---|---|
|**R**|`TASK_RUNNING`|Выполняется на CPU прямо сейчас или находится в очереди (runqueue) на исполнение.|Да|
|**S**|`TASK_INTERRUPTIBLE`|Мягкий сон. Ждет события (сетевого пакета, таймера, ввода пользователя). Легко просыпается от сигналов.|Да|
|**D** / **K**|`TASK_UNINTERRUPTIBLE` / `TASK_KILLABLE`|Жесткий сон. Ждет ответа от железа (I/O диска, блокировки в ядре, сетевая ФС). Игнорирует стандартные сигналы.|**Обычно НЕТ** (Зависит от подтипа)|
|**Z**|`EXIT_ZOMBIE`|Процесс завершился, но родитель еще не прочитал его код возврата. Ресурсы освобождены, осталась только запись в таблице.|**НЕТ** (Он уже мертв)|

3.1. Глубокий разбор статуса D (Uninterruptible Sleep)

Процесс заблокирован внутри системного вызова на уровне ядра в ожидании завершения операции ввода-вывода (синхронное чтение/запись на диск, мьютексы ядра, ожидания ответа от NFS/GlusterFS).

- **Почему его часто нельзя убить?** Сигнал `SIGKILL` обрабатывается ядром при переключении контекста процесса из пространства пользователя. Но пока процесс находится в классическом состоянии `TASK_UNINTERRUPTIBLE`, ядро гарантирует драйверу железа, что процесс не проснется посередине транзакции данных. Ядро просто не проверяет очередь сигналов для этого процесса, пока драйвер не вернет управление.
- **Современный нюанс (`TASK_KILLABLE`):** В современных ядрах Linux часть системных вызовов переведена в состояние `K`. В утилитах мониторинга они все еще могут отображаться как `D`, но ядро разрешает прервать их, если прилетает именно `SIGKILL (-9)`.
- **Что делать, если `kill -9` не помогает?** Сам процесс не потребляет CPU, но он может удерживать файлы и блокировки. Попытки убить его бесполезны. Необходимо устранять первопричину на уровне инфраструктуры: перезапускать зависшую службу NFS, проверять здоровье дискового массива (SATA/NVMe Link resets) через `dmesg`, либо отправлять хост в hard reboot.

3.2. Глубокий разбор статуса Z (Zombie)

Зомби не потребляет ресурсы CPU и RAM (его адресное пространство уже очищено), но он занимает структуру `task_struct` и запись в системной таблице процессов (Process Table). Если зомби станет слишком много, система упрется в лимит `kernel.pid_max` и не сможет порождать новые процессы, что приведет к отказу ОС.

- **Почему появляется?** При завершении процесса вызывается `exit()`. Ядро оставляет минимальную запись о нем, ожидая, пока родительский процесс (Parent) выполнит системный вызов `wait()` или `waitpid()`, чтобы считать код возврата. Если родитель спроектирован некорректно, заблокирован или ушел в бесконечный цикл, процесс зависает в состоянии зомби.
- **Как вычистить?** Посылать сигналы самому зомби бессмысленно — у него больше нет обработчика сигналов, это просто "призрак" в памяти ядра. Единственный способ убрать его — послать сигнал `SIGCHLD` родителю, чтобы заставить его прочитать статус, либо полностью уничтожить его **родительский процесс (PPID)**.  
    После гибели родителя зомби автоматически переподчиняется процессу `init` (`systemd` с PID 1). Ядро `systemd` устроено так, что оно непрерывно вызывает `wait()` для всех своих "приемышей", мгновенно очищая таблицу процессов.

3.3. Диагностика зомби и заблокированных процессов

**Найти процессы в состоянии Zombie и их родителей (строгий синтаксис без ложных срабатываний):**

bash

```
ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'
```

Use code with caution.

**Быстро узнать, на каком именно системном вызове завис процесс в состоянии D:**  
Если процесс с PID `5678` застрял в состоянии `D`, можно заглянуть в его стек вызовов в ядре без использования `strace` (который может зависнуть при попытке подключиться к `D`-процессу):

bash

```
cat /proc/5678/wchan
# Или посмотреть полный бэктрейс ядра:
cat /proc/5678/stack
```

Use code with caution.

_Вывод покажет конкретную функцию ядра (например, `blk_sk_lookup_firmware` или `nfs_...`), что сразу укажет на проблемный драйвер или подсистему._

Глава 4. Дисковая подсистема (I/O, Inodes & LVM)

4.1. Индексы файловой системы (Inodes)

В Linux имя файла — это всего лишь жесткая ссылка (hardlink), связывающая человекочитаемый путь со строкой в таблице директории. Все метаданные файла (размер, владелец, права доступа, метки времени, указатели на физические блоки данных на диске) хранятся в изолированной структуре — **Inode (Index Node)**. Имя файла внутри самой структуры inode **не хранится**.

Сценарий: «Место на диске есть, но записать файл нельзя»

При попытке создать файл или директорию система выдает ошибку `No space left on device`, хотя утилита `df -h` показывает, что свободно еще более 50% физического объема.

- **Причина:** На файловой системе закончились свободные дескрипторы inode.
    - _В Ext4_ общее количество inode жестко задается один раз при форматировании. Если на диске создается миллион файлов по 1 байту, гигабайты диска будут свободны, но лимит inode исчерпается.
    - _В XFS_ инноды выделяются динамически, но их суммарный объем ограничен процентом от емкости диска (параметр `maxpct`). При забивании диска мелкими файлами XFS тоже может упереться в этот лимит.
- **Диагностика:**
    
    bash
    
    ```
    df -i
    ```
    
    Use code with caution.
    
    _Смотрим колонку `IUse%`. Если там 100% — новые файлы создать невозможно._
- **Как лечить:** Найти директорию с аномальным количеством мелких файлов (кэш сессий приложений, очереди почты, `/var/lib/php/sessions/`) и очистить её.**Скрипт быстрого поиска топ-10 папок по количеству файлов:**
    
    bash
    
    ```
    find / -xdev -type f | awk -F/ 'NF>1{OFS="/"; NF--; print $0}' | sort | uniq -c | sort -rn | head -10
    ```
    
    Use code with caution.
    

Сценарий: «Удалили гигантский лог, но место на диске не освободилось»

Администратор выполнил `rm /var/log/heavy_app.log`, файл исчез из видимости, но `df -h` по-прежнему показывает 100% утилизации диска.

- **Причина:** Команда `rm` лишь удаляет жесткую ссылку из дерева директорий и уменьшает счетчик ссылок (link count) в inode файла на единицу. Однако, если запущенный процесс приложения все еще держит этот файл открытым через свой File Descriptor, ядро увеличивает счетчик открытых дескрипторов (open refs).Ядро Linux **физически не освободит блоки данных на диске**, пока суммарный счетчик ссылок (`link count` + `open refs`) для данного inode не станет равным нулю.
- **Диагностика (поиск удаленных, но удерживаемых процессов файлами):**  
    Используем `lsof` с флагами `-n` и `-P`, чтобы отключить долгий сетевой резолв на нагруженном сервере:
    
    bash
    
    ```
    lsof -nP | grep deleted
    ```
    
    Use code with caution.
    
    _Вывод покажет PID процесса, имя приложения и номер дескриптора (FD), который держит файл._
- **Как лечить БЕЗ перезапуска сервиса:**  
    Если сервис критически важный (например, Production СУБД) и его нельзя перезапускать, можно принудительно очистить блоки данных, обнулив файл через виртуальную файловую систему `/proc`. На примере PID `5678` и дескриптора `4`:
    
    bash
    
    ```
    : > /proc/5678/fd/4
    ```
    
    Use code with caution.
    
    Место на диске освободится **мгновенно**, а приложение продолжит работать.
- **⚠️ Критическое предупреждение:**  
    Этот трюк безопасен для обычных потоковых логов. Но если приложение использует сложную систему логирования, которая кеширует текущую позицию указателя в файле (`file offset`) или использует системный вызов `lseek()`, то следующая запись после обнуления запишется не в начало файла, а **в ту же позицию (смещение), где запись прервалась**. В результате ядро создаст **разреженный файл (Sparse File)**. На диске он будет занимать 0 байт, но его логический размер (в выводе `ls -lh`) останется огромным. Любая попытка прочитать его целиком или сделать бэкап заставит систему забивать нулями реальное пространство диска. Правильный превентивный метод борьбы — настройка `copytruncate` в `logrotate` или использование `truncate -s 0`.

4.2. VFS (Virtual File System) и кэширование записи

**Virtual File System (VFS)** — это абстрактный слой ядра Linux, который предоставляет приложениям единый POSIX-интерфейс (`open`, `read`, `write`, `close`) для работы с любыми типами файловых систем (локальными Ext4/XFS, сетевыми NFS/CephFS, виртуальными `procfs`/`sysfs`).

Механизм Dirty Pages (Грязные страницы)

Когда приложение выполняет системный вызов `write()`, ядро из соображений производительности не производит синхронную запись на физический накопитель. Вместо этого данные пишутся в оперативную память (Page Cache), а измененные страницы памяти помечаются флагом **`PG_dirty` (Грязные страницы)**.

Для приложения операция завершается за наносекунды. Сбросом этих страниц из RAM на физический диск занимаются специализированные фоновые потоки ядра — **`flusher threads`** (в списке процессов отображаются как `[writeback]`), которые работают асинхронно.

Тюнинг параметров сброса (sysctl)

Поведение `flusher threads` регулируется через параметры ядра в `/etc/sysctl.conf`.

- **`vm.dirty_background_ratio`** (дефолт ~10%): Процент от общей доступной памяти (Dirtyable Memory). При достижении этого порога ядро активирует фоновые потоки `writeback`. Они начинают сбрасывать данные на диск на заднем плане, **не блокируя** работу приложения.
- **`vm.dirty_ratio`** (дефолт ~20%): Жесткий блокирующий потолок. Если приложение генерирует данные быстрее, чем дисковая подсистема успевает их утилизировать, и объем грязных страниц достигает этого значения, ядро **полностью блокирует все новые системные вызовы `write()`** для всех процессов. Приложение принудительно переводится в состояние жесткого сна (`D-state`) и ждет, пока `flusher threads` не опустят объем грязных страниц ниже лимита. На Highload-системах это проявляется как внезапные дикие фризы (I/O Spikes / Latency spikes).

Оптимизация для High Load (СУБД, ClickHouse, Kafka, тяжелый I/O)

На серверах с большим объемом RAM (например, 256 ГБ) дефолтные 10% и 20% — это 25 ГБ и 50 ГБ грязных данных соответственно. Попытка сбросить 50 ГБ данных за раз гарантированно "поставит на колени" любой дисковый массив.

Чтобы сброс шел непрерывно, мелкими порциями, параметры переводят из процентов в **абсолютные байты**:

ini

```
# Активировать фоновый сброс при накоплении 64 МБ грязных страниц
vm.dirty_background_bytes = 67108864

# Намертво блокировать запись при накоплении 128 МБ грязных страниц
vm.dirty_bytes = 134217728
```

Use code with caution.

_Важно: При установке параметров с суффиксом `_bytes`, аналогичные параметры с суффиксом `_ratio` ядром автоматически сбрасываются в `0`._

Регулировка по времени (Таймауты)

- **`vm.dirty_expire_centisecs`** (дефолт `3000` = 30 секунд): Определяет "возраст" грязной страницы. Если страница остается грязной дольше этого времени, при следующем цикле бодрствования потоки `writeback` заберут её на диск.
- **`vm.dirty_writeback_centisecs`** (дефолт `500` = 5 секунд): Интервал времени, с которым фоновые потоки `writeback` "просыпаются" и проверяют систему.

Для систем с высокими требованиями к сохранности данных (и быстрыми NVMe) эти параметры часто снижают:

ini

```
vm.dirty_expire_centisecs = 1000   # 10 секунд
vm.dirty_writeback_centisecs = 200 # 2 секунды
```

Use code with caution.

Диагностика кэша записи в реальном времени

bash

```
cat /proc/meminfo | grep -E "Dirty|Writeback"
```

Use code with caution.

- `Dirty` — данные, которые изменены, но еще сидят в RAM.
- `Writeback` — данные, которые прямо в эту секунду контроллер диска физически сбрасывает на накопитель.

4.3. Устройство LVM (Logical Volume Manager)

**LVM** — это слой абстракции между физическими накопителями и файловой системой. Он позволяет объединять разнородные диски в единые пулы памяти, динамически нарезать виртуальные разделы и менять их размеры «на лету» без остановки сервисов.

Трехуровневая архитектура LVM

1. **PV (Physical Volume / Физический том):** Инициализированный для работы с LVM физический диск, NVMe-накопитель или раздел (например, `/dev/sdb`). При инициализации (`pvcreate`) диск разбивается на мелкие блоки — **Физические экстенты (PE — Physical Extents)**, обычно по 4 МБ.
2. **VG (Volume Group / Группа томов):** Виртуальный пул, объединяющий один или несколько PV в единое пространство (аналог программного JBOD). Создается через `vgcreate`.
3. **LV (Logical Volume / Логический том):** «Виртуальный раздел», который нарезается из пула VG (`lvcreate`) путем выделения определенного количества экстентов. Для операционной системы LV выглядит как обычное блочное устройство в `/dev/mapper/`.

Инструкция: Расширение диска внутри виртуалки на лету (Без перезагрузки)

Задача: в панели гипервизора (VMware, Proxmox) размер диска запущенной ВМ увеличили с 50 ГБ до 100 ГБ. Отдаем пространство ОС без остановки продакшена.

Шаг 1: Сканирование шины SCSI

Заставляем ядро пересканировать SCSI-шину, чтобы актуализировать размер блочного устройства (например, `/dev/sda`):

bash

```
echo 1 > /sys/class/block/sda/device/rescan
```

Use code with caution.

⚠️ Важное ветвление: Диск целиком vs Таблица разделов

- **Сценарий А (Best Practice):** LVM развернут прямо на "сыром" диске (`/dev/sda` является физическим томом PV). В этом случае переходите сразу к **Шагу 2**.
- **Сценарий Б (Legacy):** При установке ОС диск был размечен через MBR/GPT (например, PV — это раздел `/dev/sda3`). Тогда LVM не увидит место, пока не изменится геометрия таблицы разделов. Решается утилитой `growpart` (пакет `cloud-utils`):
    
    bash
    
    ```
    growpart /dev/sda 3   # Расширяет 3-й раздел на диске /dev/sda
    partx -u /dev/sda     # Заставляет ядро обновить таблицу разделов в памяти
    ```
    
    Use code with caution.
    

Шаг 2: Расширение Physical Volume (PV)

bash

```
pvresize /dev/sda
```

Use code with caution.

Шаг 3: Расширение Logical Volume (LV)

Добавляем все 100% освободившегося в VG пространства к нашему логическому тому (например, к корню системы):

bash

```
lvextend -l +100%FREE /dev/vg_system/lv_root
```

Use code with caution.

Шаг 4: Расширение файловой системы под размер тома

- **Для Ext4:**
    
    bash
    
    ```
    resize2fs /dev/vg_system/lv_root
    ```
    
    Use code with caution.
    
- **Для XFS:**  
    _В отличие от Ext4, утилите `xfs_growfs` в качестве аргумента передается **точка монтирования** целевой файловой системы:_
    
    bash
    
    ```
    xfs_growfs /
    ```
    
    Use code with caution.
    

Архитектурный нюанс: Опасность Overcommit в LVM Thin Provisioning

В современных инфраструктурах часто используют **Thin Pools (Тонкие пулы)**. Они позволяют создавать "виртуальные" LV, суммарный логический размер которых превышает реальный физический размер группы томов (механизм Overcommit). Например, в физический пул размером 100 ГБ можно нарезать пять тонких LV по 40 ГБ каждый.

- **Где сокрыта авария:** Если все приложения начнут одновременно писать реальные данные и суммарный физический объем пула достигнет 100%, произойдет **полный отказ дисковой подсистемы**.
- **Поведение ядра:** В отличие от обычного заполнения диска (когда ФС просто возвращает ошибку `No space left on device` конкретному приложению), при переполнении Thin Pool ядро Linux переводит весь пул в режим **I/O Error** или **Read-Only**. Процессы (особенно базы данных) моментально падают в аварийный останов (Crash).
- **Диагностика тонких томов:** Обычный `df -h` не показывает реальную утилизацию тонкого пула. Используйте команду:
    
    bash
    
    ```
    lvs -o+data_percent,metadata_percent
    ```
    
    Use code with caution.
    
    _Критически важно следить за колонкой `Data%`. Если она приближается к 80-90%, пул необходимо срочно расширять._

Глава 5. Сетевой стек и Тюнинг TCP/IP под High Load

5.1. Прохождение пакета через ядро (Linux Network Stack)

Когда сетевой пакет прилетает на сетевую карту (NIC), он проходит многоступенчатый путь через аппаратные и программные очереди, прежде чем приложение прочитает его из сокета.

Алгоритм обработки (Низкий уровень)

1. **Ring Buffer & DMA:** Пакет поступает на физический порт сетевой карты. Карта с помощью контроллера **DMA** мгновенно записывает сырые байты пакета напрямую в системную память (RAM) — в области, на которые указывают дескрипторы кольцевого буфера приема (**RX Ring Buffer**). После успешной записи карта генерирует аппаратное прерывание (**Hard IRQ**).
2. **Hard IRQ & Включение NAPI:** CPU приостанавливает текущие задачи. Чтобы поток входящих пакетов на высокой скорости не заспамил CPU миллионами прерываний (эффект IRQ Storm), драйвер использует механизм **NAPI (New API)**: он **отключает аппаратные прерывания** от этой сетевой карты и генерирует мягкое прерывание (**SoftIRQ** подтипа `NET_RX_SOFTIRQ`).
3. **SoftIRQ & Поллинг (NAPI Polling):** Драйвер в цикле (polling) забирает пакеты из RAM. На этом этапе ядро аллоцирует метаструктуру **`sk_buff` (Socket Buffer)**, которая "оборачивает" данные пакета для дальнейшего путешествия по стеку. Дескрипторы RX Ring Buffer очищаются и возвращаются сетевой карте. По окончании пачки аппаратные прерывания карты включаются снова.
4. **Входная очередь ядра (`netdev_max_backlog`):** Из NAPI пакеты передаются подсистеме Vlan/Bonding, а затем попадают во входную очередь сетевой подсистемы ядра. Если стек протоколов загружен, пакеты временно буферизируются здесь.
5. **Стек протоколов и Netfilter:** Функция `netif_receive_skb()` передает пакет вверх. Происходит последовательный разбор заголовков: L2 (Ethernet) -> L3 (IP) -> L4 (TCP/UDP). На этапе L3/L4 пакет прогоняется через хуки **Netfilter** (`iptables`/`nftables`). Здесь отрабатывают правила фильтрации, NAT и conntrack. Если пакет успешно прошел фильтры, выполняется маршрутизация.
6. **Буфер сокета (Receive Buffer):** Данные (payload) очищаются от сетевых заголовков и складываются в очередь чтения (`receive queue`) конкретного сокета приложения. Приложение, заблокированное на системном вызове `epoll_wait()`, `read()` или `recv()`, получает уведомление от ядра, просыпается, выполняет переключение контекста в Kernel Space и копирует данные из буфера сокета в свое пользовательское пространство (User Space).

5.2. Ошибки переполнения очередей (Диагностика и Траблшутинг)

Этап 1: Переполнение на уровне железа (RX Ring Buffer)

Если сетевой чип заполнил все дескрипторы кольцевого буфера в RAM, новые пакеты отбрасываются самой картой.

- **Диагностика:**
    
    bash
    
    ```
    ethtool -S eth0 | grep -E "drop|fifo|miss|discard"
    ```
    
    Use code with caution.
    
    _Если счетчики типа `rx_fifo_errors`, `rx_missed_errors` или `rx_discards` растут — кольцевой буфер переполнен._
- **Тюнинг:** Посмотреть текущий и максимальный размер буфера можно через `ethtool -g eth0`. Увеличить размер буфера до максимума:
    
    bash
    
    ```
    ethtool -G eth0 rx 4096 tx 4096
    ```
    
    Use code with caution.
    

Этап 2: Переполнение на стыке драйвера и стека ядра (`netdev_max_backlog`)

Если драйвер успешно вычитал пакеты из Ring Buffer, но стек протоколов ядра не успевает их обрабатывать, пакеты дропаются на входе в стек.

- **Диагностика:**
    
    bash
    
    ```
    cat /proc/net/softnet_stat
    ```
    
    Use code with caution.
    
    _Каждая строка файла соответствует одному ядру CPU. Нас интересует вторая колонка: это число пакетов, сброшенных из-за переполнения очереди `netdev_max_backlog`. Если оно растет — очередь слишком мала._
- **Тюнинг:** Увеличить размер входной очереди и бюджет обработки пакетов для одного цикла SoftIRQ в `/etc/sysctl.conf`:
    
    ini
    
    ```
    # Увеличиваем размер входной очереди пакетов (дефолт обычно 1000)
    net.core.netdev_max_backlog = 10000
    # Увеличиваем количество пакетов, обрабатываемых за один проход NAPI (дефолт 300)
    net.core.netdev_budget = 600
    ```
    
    Use code with caution.
    

Этап 3: Параллелизация обработки (RSS и RPS)

Чтобы SoftIRQ не утилизировал только одно ядро CPU (обычно `CPU0`), трафик необходимо размазывать по ядрам:

- **RSS (Receive Side Scaling):** Аппаратный механизм сетевой карты. Карта считает хэш от IP/портов пакета и раскладывает пакеты в разные RX-очереди, каждая из которых генерирует свой Hard IRQ на свое ядро CPU.
- **RPS (Receive Packet Steering):** Программный аналог RSS в ядре Linux. Позволяет драйверу пересылать `sk_buff` на обработку стека протоколов другим ядрам CPU через Inter-Processor Interrupts (IPI).
    - _Включить RPS для интерфейса eth0 (размазать обработку первой очереди на первые 8 ядер CPU, маска `ff`):_
        
        bash
        
        ```
        echo "ff" > /sys/class/net/eth0/queues/rx-0/rps_cpus
        ```
        
        Use code with caution.
        

5.3. Тюнинг TCP/IP: Борьба с очередями и SYN Flood

Механизм Handshake и двухуровневая система очередей

Процесс установления TCP-соединения (Three-way Handshake) на стороне ядра Linux жестко разделен на два этапа:

1. **Полуоткрытые соединения (SYN Backlog):** Клиент инициирует соединение и присылает пакет `SYN`. Драйвер ядра выделяет под это соединение структуру в памяти, переводит его в статус `SYN_RECV`, помещает в очередь **SYN backlog** и отправляет клиенту ответный `SYN-ACK`.
2. **Полностью установленные соединения (Listen Backlog):** Клиент отвечает пакетом `ACK`. Соединение переходит в статус `ESTABLISHED`. Ядро извлекает его из SYN-backlog и перемещает во вторую очередь — **Listen backlog** (очередь готовых сокетов). Соединение находится здесь до тех пор, пока приложение не заберет его из пространства ядра с помощью системного вызова `accept()`.

Системный тюнинг очередей (sysctl)

При высокой плотности запросов базовые размеры этих очередей переполняются мгновенно.

- **`net.ipv4.tcp_max_syn_backlog`** (дефолт ~512/1024): Максимальный размер очереди полуоткрытых соединений. Для High Load его увеличивают:
    
    ini
    
    ```
    net.ipv4.tcp_max_syn_backlog = 16384
    ```
    
    Use code with caution.
    
- **`net.core.somaxconn`** (дефолт ~128/4096): Жесткий системный лимит для очереди `Listen backlog`.
    
    - **⚠️ Критическая зависимость:** Значение, указанное в конфигурационных файлах веб-серверов (например, в Nginx: `listen 80 backlog=65536`), **не может быть выше**, чем системный параметр `somaxconn`. Если вы поднимете лимит в Nginx, но оставите дефолт в ядре, Linux урежет очередь приложения до своего системного максимума.
    
    ini
    
    ```
    net.core.somaxconn = 16384
    ```
    
    Use code with caution.
    

Защита от SYN Flood и оптимизация таймаутов

Механизм TCP Syncookies

ini

```
net.ipv4.tcp_syncookies = 1
```

Use code with caution.

Когда очередь `SYN backlog` заполняется на 100%, ядро активирует механизм криптографических куки. Оно перестает выделять дескрипторы памяти под новые `SYN`-запросы. Вместо этого параметры соединения хэшируются и зашифровываются прямо в поле `Sequence Number` исходящего ответа `SYN-ACK`. Если клиент легитимен, он возвращает этот номер в финальном пакете `ACK`. Ядро на лету расшифровывает номер и мгновенно создает готовое соединение в `Listen backlog`.

- **Важный нюанс:** Использование `syncookies` заставляет ядро отбрасывать расширенные TCP-опции (такие как `SACK` или `Window Scaling`). Чтобы этого не происходило, **обязательно** должен быть включен сбор таймстампов — тогда ядро спрячет TCP-опции в неиспользуемые биты временных меток:
    
    ini
    
    ```
    net.ipv4.tcp_timestamps = 1
    ```
    
    Use code with caution.
    

Борьба со "спящими" полуоткрытыми сессиями

По умолчанию ядро делает повторные `SYN-ACK` пакеты 5 раз (`tcp_synack_retries`), удерживая мертвую сессию около 180 секунд. Для высоконагруженных систем этот таймаут сокращают:

ini

```
net.ipv4.tcp_synack_retries = 2
net.ipv4.tcp_syn_retries = 2
```

Use code with caution.

Поведение при переполнении приложения (`tcp_abort_on_overflow`)

Если ваше приложение не успевает вызывать `accept()`, очередь `Listen backlog` заполняется. По умолчанию Linux просто игнорирует входящие `ACK` от клиентов. Клиент уверен, что соединение открыто, начинает слать данные, но сервер их молча дропает.

- Если сервер стоит за балансировщиком нагрузки (HAProxy, Envoy), этот параметр рекомендуется выставить в `1`:
    
    ini
    
    ```
    net.ipv4.tcp_abort_on_overflow = 1
    ```
    
    Use code with caution.
    
    _При переполнении очереди готовых сокетов ядро будет мгновенно отвечать балансировщику пакетом `RST` (Сброс соединения). Балансировщик сразу поймет, что эта нода перегружена, и перенаправит запрос на другой здоровый бэкенд._

5.4. Разбор состояний TIME_WAIT и CLOSE_WAIT

⏳ Состояние TIME_WAIT (Активное закрытие)

Состояние возникает на стороне того узла, **кто первый инициировал закрытие соединения** (вызвал системный вызов `close()`). Обычно активным инициатором выступает сервер (Nginx, отдавший файл без `Keep-Alive`).

- **Зачем это нужно ядру:** Сокет блокируется в этом статусе ровно на **2 * MSL**, что в ядре Linux составляет **60 секунд** (изменить этот таймаут через `sysctl` нельзя). Это необходимо, чтобы дать время долететь "заблудившимся" в сети пакетам старой сессии и гарантировать, что удаленный хост получил финальный пакет `ACK`.
- **В чем проблема под High Load:** Если сервер закрывает 10 000 соединений в секунду, в системе одновременно будут висеть 600 000 сокетов в статусе `TIME_WAIT`. Они стремительно исчерпывают пул свободных локальных (эфемерных) портов, и сервер физически не может открыть ни одного нового исходящего соединения (например, к СУБД), выдавая ошибку `Cannot assign requested address`.

Тюнинг под High Load (Борьба с TIME_WAIT)

1. **Расширение пула эфемерных портов:**
    
    ini
    
    ```
    net.ipv4.ip_local_port_range = 1024 65535
    ```
    
    Use code with caution.
    
2. **Повторное использование сокетов:** Разрешаем ядру безопасно переиспользовать сокеты в состоянии `TIME_WAIT` для новых исходящих соединений к тому же целевому IP/порту:
    
    ini
    
    ```
    net.ipv4.tcp_tw_reuse = 1
    ```
    
    Use code with caution.
    
    - **⚠️ Критическая зависимость:** Параметр `tcp_tw_reuse` **физически не работает**, если отключен сбор сетевых таймстампов (`net.ipv4.tcp_timestamps = 1`).
    - _Важно:_ Забудьте про старый параметр `tcp_tw_recycle` — он полностью удален из ядра Linux начиная с версии 4.12, так как он ломал соединения от клиентов за общим NAT.

🛑 Состояние CLOSE_WAIT (Пассивное закрытие)

Состояние возникает на стороне того узла, **кому прилетел входящий запрос на закрытие** (пакет `FIN`) от соседа.

- **Как это происходит под капотом:** Клиент присылает `FIN`. Ядро Linux автоматически отвечает пакетом `ACK` и переводит сокет в статус `CLOSE_WAIT`. На этом зона ответственности ядра заканчивается. Оно ждет, пока _ваше приложение_ обработает это событие и вызовет `close()` для этого дескриптора сокета.
- **В чем проблема:** Сокеты в состоянии `CLOSE_WAIT` **не имеют таймаутов автоочистки**. Они могут висеть неделями, удерживая File Descriptor процесса. Если их накопится много — процесс упрется в лимит `Max open files` (`EMFILE`), и сервер перестанет принимать новые запросы.
- **Как лечить:** **Тюнинг системных параметров ядра здесь абсолютно бессилен.** Если сервер забит сокетами в `CLOSE_WAIT`, это **100% архитектурный баг в коде приложения** (разработчики забыли обработать конец потока `EOF` и не закрыли дескриптор сокета) либо поток приложения намертво заблокирован (`Deadlock`). Лечится только перезапуском сервиса или исправлением кода.

🛡️ Важный сопутствующий лимит: Netfilter Conntrack

Все сетевые сессии (включая сотни тысяч в состоянии `TIME_WAIT`) заносятся в системную таблицу отслеживания соединений **Conntrack**. При резком наплыве трафика эта таблица переполняется. При этом в логах появляется запись `nf_conntrack: table full, dropping packet`, и ядро начинает намертво отбрасывать любые пакеты.

- **Тюнинг Conntrack под High Load:**
    
    ini
    
    ```
    # Увеличиваем максимальный размер таблицы соранений
    net.netfilter.nf_conntrack_max = 1048576
    
    # Ускоряем очистку закрытых сессий в состоянии TIME_WAIT из таблицы conntrack (дефолт 120 сек)
    net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30
    ```
    
    Use code with caution.
    

Шпаргалка по оперативной диагностике сокетов

Для анализа сетевого состояния используйте утилиту `ss`:

**1. Быстрая сводка по всем сокетам в системе:**

bash

```
ss -s
```

Use code with caution.

**2. Поиск процессов, удерживающих сокеты в `CLOSE_WAIT`:**

bash

```
ss -tpna | grep CLOSE_WAIT
```

Use code with caution.

_Вывод четко покажет имя бинарника и PID процесса, внутри которого зависла логика закрытия дескрипторов._

Глава 6. Namespaces, Cgroups & Анатомия Контейнеризации

Контейнер — это не виртуальная машина: у него нет собственного гипервизора или выделенного ядра. Контейнер — это обычный изолированный процесс в хостовой ОС, ограничения для которого прозрачно накладываются ядром с помощью двух механизмов: **Namespaces** (определяют, что процесс может _видеть_) и **Cgroups** (определяют, сколько ресурсов процесс может _потребить_).

6.1. Namespaces под капотом (Пространства имен)

**Namespaces (Пространства имен)** отвечают за ограничение видимости, создавая для группы процессов полную иллюзию того, что они запущены в отдельной, независимой ОС.

8 ключевых пространств имен в ядре Linux:

1. **PID (Process ID):** Изолирует дерево процессов. Внутри контейнера главный процесс получает виртуальный `PID 1`. При этом в хостовой ОС этот же процесс имеет свой реальный уникальный PID.
2. **NET (Network):** Изолирует сетевые устройства, таблицы маршрутизации, порты (сокеты) и правила `iptables`/`nftables`. Позволяет контейнеру иметь собственный виртуальный интерфейс (обычно `veth`) и свой IP-адрес.
3. **MNT (Mount):** Изолирует точки монтирования файловой системы. Процесс видит только ту иерархию директорий, которая была подменена для него (с помощью `pivot_root` или `chroot`), и не имеет доступа к корневой ФС хоста.
4. **IPC (Inter-Process Communication):** Изолирует механизмы межпроцессного взаимодействия: разделяемую память (Shared Memory), очереди сообщений POSIX и семафоры System V.
5. **UTS (UNIX Timesharing System):** Позволяет процессу задавать собственное имя хоста (`hostname`) и доменное имя.
6. **USER:** Изолирует идентификаторы пользователей и групп (UID/GID). Позволяет процессу обладать правами `root` (UID 0) внутри своего контейнера, но для хостовой системы выполняться от лица обычного непривилегированного пользователя. _Важно:_ Docker по умолчанию **не включает** этот namespace автоматически (требуется настройка `userns-remap` в `daemon.json`). В Podman он активен по умолчанию.
7. **CGROUP:** Изолирует видимость путей к контрольным группам в файловой системе `/sys/fs/cgroup`.
8. **TIME:** (Добавлено в ядре 5.6). Позволяет процессам внутри пространства имен иметь собственное системное время (offset относительно часов хоста) и свой независимый аптайм.

Практическая отладка distroless-контейнеров через `nsenter`

Если контейнер собран на базе ультра-минималистичного образа (Distroless / Scratch), внутри которого нет ни оболочки `bash`/`sh`, ни утилит диагностики, стандартная команда `docker exec` вернет ошибку.

**Решение:** Использовать утилиту `nsenter`. Она позволяет системному администратору со стороны хоста (где есть все необходимые инструменты: `tcpdump`, `strace`, `ip`) принудительно войти в пространства имен целевого контейнера.

1. **Находим реальный PID процесса контейнера в хостовой ОС:**
    
    bash
    
    ```
    docker inspect --format '{{ .State.Pid }}' <имя_или_ID_контейнера>
    ```
    
    Use code with caution.
    
2. **Проникаем в пространства имен контейнера:**
    
    bash
    
    ```
    nsenter -t <PID_из_шага_1> -m -u -n -p -F
    ```
    
    Use code with caution.
    
    - `-t <PID>` — целевой процесс-якорь, чьи пространства имен мы берем.
    - `-m`, `-u`, `-n`, `-p` — входим в Mount, UTS, Network и PID namespaces.
    - `-F` — заставляет `nsenter` сделать `fork` перед запуском оболочки (критично для корректной работы дерева процессов).

После этого ваша текущая хостовая сессия терминала проваливается внутрь контейнера. Команда `ip a` или `tcpdump` будет показывать трафик сетевого интерфейса контейнера, но при этом вам доступны абсолютно все бинарники, установленные на основном хосте.

6.2. Cgroups (Control Groups) v1 vs v2

**Cgroups (Контрольные группы)** — это механизм ядра Linux, который распределяет, квотирует и ограничивает физические ресурсы процессов (**CPU, RAM, дисковый ввод-вывод blkio, количество PID**).

Эволюция архитектуры: В чем принципиальная разница?

- **Cgroups v1 (Устаревший стандарт):** Каждый контроллер ресурсов (`cpu`, `memory`, `blkio`) существовал в виде отдельной, независимой иерархии в файловой системе. Подсистемы ядра не могли общаться между собой. Например, подсистема `blkio` (ограничение скорости диска) ничего не знала о подсистеме `memory`. Когда процесс агрессивно писал на диск, ядро забивало RAM грязными страницами (Page Cache), но `blkio` не мог затормозить этот процесс. Это приводило к непредсказуемым фризам и дедлокам ядра.
- **Cgroups v2 (Современный унифицированный стандарт):** Используется **единая унифицированная иерархия** (Unified Hierarchy). Все доступные контроллеры ресурсов жестко привязаны к одной и той же группе процессов. Это позволило ядру корректно реализовать механизмы сброса грязных страниц с учетом дисковых лимитов конкретного контейнера (Writeback Cgroup Tracking).

Анатомия лимитов в cgroups v2

Управление cgroups v2 происходит через псевдофайловую систему, примонтированную по пути `/sys/fs/cgroup/`.

Ограничение памяти и Cgroup OOM-Killer

- `memory.max` — жесткий лимит. Если процессы внутри cgroup достигают этого порога, ядро сначала пытается вычистить их Page Cache. Если это не помогает, активируется локальный **Cgroup OOM-Killer**. Он завершает самый прожорливый процесс _внутри этой конкретной группы_ (контейнер падает с Exit Code 137). Вся остальная ОС и другие контейнеры продолжают работать без сбоев.
- `memory.high` — мягкий дросселирующий лимит. При его превышении ядро не убивает контейнер, а начинает искусственно замедлять (throttling) его процессы, заставляя их тратить кванты времени на очистку собственной памяти.

Ограничение CPU (CFS Scheduler)

В cgroups v2 лимиты CPU задаются в едином файле `cpu.max`:

- Синтаксис файла: `[квота] [период]` (например, `200000 100000`).
- Это означает, что суммарно всем процессу/процессам разрешено использовать 200 000 микросекунд процессорного времени за каждый астрономический период в 100 000 микросекунд (эквивалентно строгому ограничению в **2 ядра CPU**). Если контейнер превышает квоту, планировщик ядра приостанавливает его потоки до начала следующего периода (CPU Throttling).

Практическая диагностика cgroups на хосте

**1. Как узнать, какая версия cgroups активна прямо сейчас?**

bash

```
mount | grep cgroup
```

Use code with caution.

- Если в выводе присутствует строка с типом `cgroup2` на пути `/sys/fs/cgroup`, у вас активна **v2**.
- Если вы видите множество отдельных точек монтирования вроде `/sys/fs/cgroup/cpu`, `/sys/fs/cgroup/memory`, то система работает на устаревшей версии **v1**.

**2. Как посмотреть реальные лимиты контейнера со стороны хоста (в cgroups v2)?**  
Зная PID главного процесса контейнера (например, `1234`), находим его конфигурационную папку в ядре:

bash

```
cat /proc/1234/cgroup
# Вывод покажет путь, например: 0::/system.slice/docker-<ID>.scope

# Переходим в эту директорию в /sys/fs/cgroup/ и читаем лимиты:
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/cpu.max
```

Use code with caution.

6.3. Прямая связь Cgroups с лимитами в Kubernetes

В манифестах Kubernetes инженеры описывают ресурсы подов: `requests` (гарантированный минимум) и `limits` (максимальный потолок). На уровне ядра Linux хостовой ноды рантайм-контейнеризации транслирует эти абстракции в конфигурационные файлы cgroups v2.

Лимиты памяти (Memory) -> Жесткий потолок и защита

1. `limits.memory: "512Mi"` (Жесткий предел)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../memory.max`

- **Механика работы:** Если процессы внутри пода суммарно перешагивают отметку в 512 МиБ, ядро активирует локальный **Cgroup OOM-Killer**. Самый прожорливый процесс внутри пода завершается с системным кодом **Exit Code 137** (`SIGKILL`).

2. `requests.memory: "256Mi"` (Гарантия и QoS)

Превращается в файлы: `/sys/fs/cgroup/kubepods.slice/.../memory.min` или `memory.low`

- **Механика работы:** Этот параметр сообщает планировщику памяти ядра, что 256 МиБ памяти этого пода являются неприкосновенными. Если на хост-ноде начнется жесткий дефицит RAM (`Memory Pressure`), ядро будет обходить этот под стороной при вытеснении кэша, пока его утилизация находится в пределах `requests`.

Лимиты процессора (CPU) -> Троттлинг и веса планировщика

1. `limits.cpu: "1"` (Ограничение сверху)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.max`

- **Механика работы:** Настройка конфигурирует планировщик задач ядра **CFS**. Время CPU делится на жесткие периоды, которые в Kubernetes составляют **100 мс**. В файл `cpu.max` записывается строка вида: `100000 100000` (квота и период в микросекундах). Суммарно все потоки вашего пода могут вычислять задачи не более 100 мс в рамках каждого стомиллисекундного окна.
- **Что происходит при превышении:** Ядро временно приостанавливает (замораживает) его потоки до начала следующего периода в 100 мс (**CPU Throttling**). Контейнер не падает, но его Response Time улетает вверх.

⚠️ Архитектурная ловушка многопоточности (Эффект микро-челки)

Частая проблема в Highload: вы задали приложению `limits.cpu: "1"`, графики мониторинга показывают среднюю загрузку CPU контейнера всего в 20-30%, но при этом приложение дико троттлится. Почему?

- Планировщик CFS считает квоту суммарно по всем ядрам. Если ваше приложение (например, на Go или Java) многопоточное и в начале 100-миллисекундного окна одновременно запустило вычисления в **10 потоках**, каждый из которых отработал всего по **10 мс**, то суммарная квота пода в 100 мс будет полностью исчерпана **за первые 10 миллисекунд** текущего периода!
- Оставшиеся 90 миллисекунд периода все потоки приложения будут намертво заморожены ядром, ожидая сброса таймера. Именно поэтому в современном Highload-мире часто практикуется либо полный отказ от CPU Limits (оставляя только Requests), либо использование CPU Manager со `static` политикой для пингования ядер.

2. `requests.cpu: "500m"` (Пропорциональное разделение)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.weight`

- **Механика работы:** В cgroups v2 этот параметр задает относительный "вес" (приоритет) процесса на CPU по шкале от 1 до 10000. Пока хост-нода не нагружена на 100%, ваш под может свободно утилизировать хоть все доступные ядра процессора хоста. Но как только на хосте начинается борьба за ресурсы (`CPU Distress`), планировщик CFS начинает делить свободные такты процессора строго пропорционально весам `cpu.weight` всех запущенных подов. Под с большим request-ом гарантированно вытеснит под с меньшим.

Практическая диагностика CPU Throttling внутри контейнера

Чтобы понять, страдает ли контейнер от заморозок ядра, достаточно прочитать системную метрику прямо изнутри cgroup контейнера:

bash

```
cat /sys/fs/cgroup/cpu.stat
```

Use code with caution.

**Ключевые метрики для анализа:**

- `nr_periods` — общее количество периодов планировщика, прошедших с момента старта контейнера.
- `nr_throttled` — сколько раз за эти периоды контейнер полностью исчерпывал свою квоту и принудительно ставился ядром на паузу.
- `throttled_usec` — суммарное чистое время в микросекундах, которое приложение провело в замороженном состоянии.

_Метрика здоровья:_ Разделите `nr_throttled` на `nr_periods`. Если полученное значение превышает **0.1-0.15 (более 10-15% периодов уходят в троттлинг)** — лимиты CPU для этого пода зажаты слишком сильно, их необходимо увеличивать либо пересматривать пул потоков приложения.
