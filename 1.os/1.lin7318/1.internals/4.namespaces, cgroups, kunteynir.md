# Namespaces, Cgroups & Анатомия Контейнеризации

> Контейнер — это не виртуальная машина: у него нет собственного гипервизора или выделенного ядра. Контейнер — это обычный изолированный процесс в хостовой ОС, ограничения для которого прозрачно накладываются ядром с помощью двух механизмов: **Namespaces** (определяют, что процесс может _видеть_) и **Cgroups** (определяют, сколько ресурсов процесс может _потребить_).

## Namespaces под капотом (Пространства имен)

**Namespaces (Пространства имен)** отвечают за ограничение видимости, создавая для группы процессов полную иллюзию того, что они запущены в отдельной, независимой ОС.

8 ключевых пространств имен в ядре Linux:

1. **PID (Process ID):** Изолирует дерево процессов. Внутри контейнера главный процесс получает виртуальный `PID 1`. При этом в хостовой ОС этот же процесс имеет свой реальный уникальный PID.
2. **NET (Network):** Изолирует сетевые устройства, таблицы маршрутизации, порты (сокеты) и правила `iptables`/`nftables`. Позволяет контейнеру иметь собственный виртуальный интерфейс (обычно `veth`) и свой IP-адрес.
3. **MNT (Mount):** Изолирует точки монтирования файловой системы. Процесс видит только ту иерархию директорий, которая была подменена для него (с помощью `pivot_root` или `chroot`), и не имеет доступа к корневой ФС хоста.
4. **IPC (Inter-Process Communication):** Изолирует механизмы межпроцессного взаимодействия: разделяемую память (Shared Memory), очереди сообщений POSIX и семафоры System V.
5. **UTS (UNIX Timesharing System):** Позволяет процессу задавать собственное имя хоста (`hostname`) и доменное имя.
6. **USER:** Изолирует идентификаторы пользователей и групп (UID/GID). Позволяет процессу обладать правами `root` (UID 0) внутри своего контейнера, но для хостовой системы выполняться от лица обычного непривилегированного пользователя. _Важно:_ Docker по умолчанию **не включает** этот namespace автоматически (требуется настройка `userns-remap` в `daemon.json`). В Podman он активен по умолчанию.
7. **CGROUP:** Изолирует видимость путей к контрольным группам в файловой системе `/sys/fs/cgroup`.
8. **TIME:** (Добавлено в ядре 5.6). Позволяет процессам внутри пространства имен иметь собственное системное время (offset относительно часов хоста) и свой независимый аптайм.

Практическая отладка distroless-контейнеров через `nsenter`

Если контейнер собран на базе ультра-минималистичного образа (Distroless / Scratch), внутри которого нет ни оболочки `bash`/`sh`, ни утилит диагностики, стандартная команда `docker exec` вернет ошибку.

**Решение:** Использовать утилиту `nsenter`. Она позволяет системному администратору со стороны хоста (где есть все необходимые инструменты: `tcpdump`, `strace`, `ip`) принудительно войти в пространства имен целевого контейнера.

1. **Находим реальный PID процесса контейнера в хостовой ОС:**
    
    bash
    
    ```
    docker inspect --format '{{ .State.Pid }}' <имя_или_ID_контейнера>
    ```
    
    Use code with caution.
    
2. **Проникаем в пространства имен контейнера:**
    
    bash
    
    ```
    nsenter -t <PID_из_шага_1> -m -u -n -p -F
    ```
    
    Use code with caution.
    
    - `-t <PID>` — целевой процесс-якорь, чьи пространства имен мы берем.
    - `-m`, `-u`, `-n`, `-p` — входим в Mount, UTS, Network и PID namespaces.
    - `-F` — заставляет `nsenter` сделать `fork` перед запуском оболочки (критично для корректной работы дерева процессов).

После этого ваша текущая хостовая сессия терминала проваливается внутрь контейнера. Команда `ip a` или `tcpdump` будет показывать трафик сетевого интерфейса контейнера, но при этом вам доступны абсолютно все бинарники, установленные на основном хосте.

6.2. Cgroups (Control Groups) v1 vs v2

**Cgroups (Контрольные группы)** — это механизм ядра Linux, который распределяет, квотирует и ограничивает физические ресурсы процессов (**CPU, RAM, дисковый ввод-вывод blkio, количество PID**).

Эволюция архитектуры: В чем принципиальная разница?

- **Cgroups v1 (Устаревший стандарт):** Каждый контроллер ресурсов (`cpu`, `memory`, `blkio`) существовал в виде отдельной, независимой иерархии в файловой системе. Подсистемы ядра не могли общаться между собой. Например, подсистема `blkio` (ограничение скорости диска) ничего не знала о подсистеме `memory`. Когда процесс агрессивно писал на диск, ядро забивало RAM грязными страницами (Page Cache), но `blkio` не мог затормозить этот процесс. Это приводило к непредсказуемым фризам и дедлокам ядра.
- **Cgroups v2 (Современный унифицированный стандарт):** Используется **единая унифицированная иерархия** (Unified Hierarchy). Все доступные контроллеры ресурсов жестко привязаны к одной и той же группе процессов. Это позволило ядру корректно реализовать механизмы сброса грязных страниц с учетом дисковых лимитов конкретного контейнера (Writeback Cgroup Tracking).

Анатомия лимитов в cgroups v2

Управление cgroups v2 происходит через псевдофайловую систему, примонтированную по пути `/sys/fs/cgroup/`.

Ограничение памяти и Cgroup OOM-Killer

- `memory.max` — жесткий лимит. Если процессы внутри cgroup достигают этого порога, ядро сначала пытается вычистить их Page Cache. Если это не помогает, активируется локальный **Cgroup OOM-Killer**. Он завершает самый прожорливый процесс _внутри этой конкретной группы_ (контейнер падает с Exit Code 137). Вся остальная ОС и другие контейнеры продолжают работать без сбоев.
- `memory.high` — мягкий дросселирующий лимит. При его превышении ядро не убивает контейнер, а начинает искусственно замедлять (throttling) его процессы, заставляя их тратить кванты времени на очистку собственной памяти.

Ограничение CPU (CFS Scheduler)

В cgroups v2 лимиты CPU задаются в едином файле `cpu.max`:

- Синтаксис файла: `[квота] [период]` (например, `200000 100000`).
- Это означает, что суммарно всем процессу/процессам разрешено использовать 200 000 микросекунд процессорного времени за каждый астрономический период в 100 000 микросекунд (эквивалентно строгому ограничению в **2 ядра CPU**). Если контейнер превышает квоту, планировщик ядра приостанавливает его потоки до начала следующего периода (CPU Throttling).

Практическая диагностика cgroups на хосте

**1. Как узнать, какая версия cgroups активна прямо сейчас?**

bash

```
mount | grep cgroup
```

Use code with caution.

- Если в выводе присутствует строка с типом `cgroup2` на пути `/sys/fs/cgroup`, у вас активна **v2**.
- Если вы видите множество отдельных точек монтирования вроде `/sys/fs/cgroup/cpu`, `/sys/fs/cgroup/memory`, то система работает на устаревшей версии **v1**.

**2. Как посмотреть реальные лимиты контейнера со стороны хоста (в cgroups v2)?**  
Зная PID главного процесса контейнера (например, `1234`), находим его конфигурационную папку в ядре:

bash

```
cat /proc/1234/cgroup
# Вывод покажет путь, например: 0::/system.slice/docker-<ID>.scope

# Переходим в эту директорию в /sys/fs/cgroup/ и читаем лимиты:
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.max
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/cpu.max
```

Use code with caution.

6.3. Прямая связь Cgroups с лимитами в Kubernetes

В манифестах Kubernetes инженеры описывают ресурсы подов: `requests` (гарантированный минимум) и `limits` (максимальный потолок). На уровне ядра Linux хостовой ноды рантайм-контейнеризации транслирует эти абстракции в конфигурационные файлы cgroups v2.

Лимиты памяти (Memory) -> Жесткий потолок и защита

1. `limits.memory: "512Mi"` (Жесткий предел)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../memory.max`

- **Механика работы:** Если процессы внутри пода суммарно перешагивают отметку в 512 МиБ, ядро активирует локальный **Cgroup OOM-Killer**. Самый прожорливый процесс внутри пода завершается с системным кодом **Exit Code 137** (`SIGKILL`).

2. `requests.memory: "256Mi"` (Гарантия и QoS)

Превращается в файлы: `/sys/fs/cgroup/kubepods.slice/.../memory.min` или `memory.low`

- **Механика работы:** Этот параметр сообщает планировщику памяти ядра, что 256 МиБ памяти этого пода являются неприкосновенными. Если на хост-ноде начнется жесткий дефицит RAM (`Memory Pressure`), ядро будет обходить этот под стороной при вытеснении кэша, пока его утилизация находится в пределах `requests`.

Лимиты процессора (CPU) -> Троттлинг и веса планировщика

1. `limits.cpu: "1"` (Ограничение сверху)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.max`

- **Механика работы:** Настройка конфигурирует планировщик задач ядра **CFS**. Время CPU делится на жесткие периоды, которые в Kubernetes составляют **100 мс**. В файл `cpu.max` записывается строка вида: `100000 100000` (квота и период в микросекундах). Суммарно все потоки вашего пода могут вычислять задачи не более 100 мс в рамках каждого стомиллисекундного окна.
- **Что происходит при превышении:** Ядро временно приостанавливает (замораживает) его потоки до начала следующего периода в 100 мс (**CPU Throttling**). Контейнер не падает, но его Response Time улетает вверх.

⚠️ Архитектурная ловушка многопоточности (Эффект микро-челки)

Частая проблема в Highload: вы задали приложению `limits.cpu: "1"`, графики мониторинга показывают среднюю загрузку CPU контейнера всего в 20-30%, но при этом приложение дико троттлится. Почему?

- Планировщик CFS считает квоту суммарно по всем ядрам. Если ваше приложение (например, на Go или Java) многопоточное и в начале 100-миллисекундного окна одновременно запустило вычисления в **10 потоках**, каждый из которых отработал всего по **10 мс**, то суммарная квота пода в 100 мс будет полностью исчерпана **за первые 10 миллисекунд** текущего периода!
- Оставшиеся 90 миллисекунд периода все потоки приложения будут намертво заморожены ядром, ожидая сброса таймера. Именно поэтому в современном Highload-мире часто практикуется либо полный отказ от CPU Limits (оставляя только Requests), либо использование CPU Manager со `static` политикой для пингования ядер.

2. `requests.cpu: "500m"` (Пропорциональное разделение)

Превращается в файл: `/sys/fs/cgroup/kubepods.slice/.../cpu.weight`

- **Механика работы:** В cgroups v2 этот параметр задает относительный "вес" (приоритет) процесса на CPU по шкале от 1 до 10000. Пока хост-нода не нагружена на 100%, ваш под может свободно утилизировать хоть все доступные ядра процессора хоста. Но как только на хосте начинается борьба за ресурсы (`CPU Distress`), планировщик CFS начинает делить свободные такты процессора строго пропорционально весам `cpu.weight` всех запущенных подов. Под с большим request-ом гарантированно вытеснит под с меньшим.

Практическая диагностика CPU Throttling внутри контейнера

Чтобы понять, страдает ли контейнер от заморозок ядра, достаточно прочитать системную метрику прямо изнутри cgroup контейнера:

bash

```
cat /sys/fs/cgroup/cpu.stat
```

Use code with caution.

**Ключевые метрики для анализа:**

- `nr_periods` — общее количество периодов планировщика, прошедших с момента старта контейнера.
- `nr_throttled` — сколько раз за эти периоды контейнер полностью исчерпывал свою квоту и принудительно ставился ядром на паузу.
- `throttled_usec` — суммарное чистое время в микросекундах, которое приложение провело в замороженном состоянии.

_Метрика здоровья:_ Разделите `nr_throttled` на `nr_periods`. Если полученное значение превышает **0.1-0.15 (более 10-15% периодов уходят в троттлинг)** — лимиты CPU для этого пода зажаты слишком сильно, их необходимо увеличивать либо пересматривать пул потоков приложения.
