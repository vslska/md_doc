# Управление объектами Kubernetes — kubectl: подходы и практика

>В Kubernetes выделяется три основных подхода к управлению объектами: императивные команды, императивная конфигурация и декларативная конфигурация. Для производственных сред стандартом является декларативная конфигурация. Не допускается смешивание различных подходов для управления одним и тем же объектом.

## Подходы к управлению: сравнение

|**Подход**|**Описание**|**Расположение файлов**|**Назначение**|**Сложность**|
|---|---|---|---|---|
|**Императивные команды**|Выполнение команд `kubectl create deployment ...`|Файлы не требуются|Оперативные задачи, отладка, обучение|Низкая|
|**Императивная конфигурация**|Применение команд `kubectl create/replace -f file.yaml`|Отдельные YAML-файлы|Простые сценарии эксплуатации, контроль версий|Средняя|
|**Декларативная конфигурация**|Использование команды `apply -f dir/`|Каталог манифестов (система контроля версий)|Производственные среды (Production), GitOps, командная работа|Высокая|

Принцип предотвращения конфликтов требует исключения совмещения подходов для управления конкретным ресурсом. Создание объекта посредством императивных команд исключает его последующее обновление через декларативный механизм во избежание неопределенного поведения.

---
## Императивные команды

Императивные команды предполагают непосредственное взаимодействие с активными объектами в кластере.

Примеры операций:

```bash
kubectl create deployment nginx --image=nginx:1.25

kubectl scale deployment nginx --replicas=3

kubectl delete deployment nginx
```

### Преимущества

- Высокая скорость выполнения: одна команда формирует требуемый результат.
- Применимость для обучения, отладки и разовых задач.
- Минимальный порог входа за счет отсутствия необходимости проектирования YAML-манифестов.

### Недостатки

- Отсутствие истории изменений и аудита действий пользователей.
- Отсутствие стандартизированных шаблонов для развертывания на других кластерах.
- Риск возникновения ошибок вследствие опечаток непосредственно в рабочей среде.

Императивные команды целесообразно использовать при тестировании гипотез, оперативном устранении неисправностей и в учебных целях, воздерживаясь от их применения для критически важных ресурсов в production.

---
## Императивная конфигурация объектов

Подход базируется на применении конфигурационных файлов к кластеру через явные команды создания или замены.

Примеры операций:

```bash
kubectl create -f nginx.yaml

kubectl replace -f nginx.yaml

kubectl delete -f nginx.yaml
```

Команда `replace` производит полную замену объекта в кластере. Если в кластере объект был изменен вручную (например, через `kubectl edit`), а в файле конфигурации соответствующее поле отсутствует, то при выполнении `replace` эти изменения будут стерты.

### Преимущества

- Хранение конфигураций в системе контроля версий.
- Интеграция в процессы CI/CD для валидации, ревью и аудита.
- Наличие шаблонов для повторного применения.

### Недостатки

- Необходимость ручного написания YAML-файлов.
- Потенциальная опасность команды `replace`, уничтожающей внешние изменения.
- Неудобство работы с каталогами файлов из-за требования явного перечисления.

Подход применяется в сценариях с полным контролем конфигурационных файлов и исключением ручных правок в кластере.

---
## Декларативная конфигурация объектов

Декларативный подход задает целевое состояние системы через файлы манифестов, при этом платформа самостоятельно определяет необходимые действия для синхронизации текущего состояния с желаемым.

Примеры операций:

```bash
kubectl apply -f configs/

kubectl apply -R -f configs/

kubectl diff -f configs/
```

В основе метода лежит механизм трехстороннего слияния (three-way merge), учитывающий последнюю примененную конфигурацию (сохраненную в аннотациях объекта), текущее состояние в кластере и новый манифест. Это позволяет вычислять минимальные изменения в виде патча, а не заменять объект целиком. Изменения, внесенные вне файлов (при отсутствии прямых конфликтов), сохраняются.

### Преимущества

- Безопасность обновлений с сохранением сторонних изменений при отсутствии коллизий.
- Эффективная обработка каталогов манифестов одной командой.
- Автоматическое определение типа операции (создание, обновление, удаление).
- Полная совместимость с концепцией GitOps.

### Недостатки

- Повышенная сложность отладки логики слияния.
- Необходимость понимания принципов работы аннотаций последней примененной конфигурации и стратегий слияния.
- Более высокий порог входа.  

Данный подход является стандартным решением для производственных сред, обеспечивая масштабируемость и совместимость с современными методологиями управления инфраструктурой.

## Сравнение команд

|**Задача**|**Императивная команда**|**Императивная конфигурация**|**Декларативная конфигурация**|
|---|---|---|---|
|**Создание**|`kubectl create deployment ...`|`kubectl create -f file.yaml`|`kubectl apply -f file.yaml`|
|**Обновление**|`kubectl scale ...`, `kubectl set image ...`|`kubectl replace -f file.yaml`|`kubectl apply -f file.yaml`|
|**Удаление**|`kubectl delete deployment ...`|`kubectl delete -f file.yaml`|`kubectl apply -f file.yaml --prune` / `delete -f`|
|**Просмотр изменений**|Не поддерживается|Не поддерживается|`kubectl diff -f file.yaml`|
|**Применение каталога**|Неудобно|Требуется перечисление файлов|`kubectl apply -R -f dir/`|
|**Откат**|Сложно|Через `replace` старым файлом|`kubectl rollout undo` + история системы контроля версий|

## Практика использования декларативного подхода

### Структура репозитория

```yaml
k8s-configs/
├── bases/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── configmap.yaml
├── overlays/
│   ├── dev/
│   │   └── patch-replicas.yaml
│   └── prod/
│       └── patch-replicas.yaml
└── Apply.sh
```

### Рабочий процесс

```bash
kubectl diff -f bases/

kubectl apply -f bases/

kubectl get all -l app=myapp

git add bases/deployment.yaml
git commit -m "feat: scale nginx to 3 replicas"
git push
```

При необходимости принудительного перезаписания объекта применяется принудительная замена либо редактирование конфигурации через командную строку:

```bash
kubectl replace --force -f file.yaml

kubectl edit deployment nginx
```

## Рекомендации по безопасному управлению объектами

- Перед применением изменений рекомендуется выполнять предварительный просмотр разницы через `kubectl diff -f manifest.yaml`.
- Использование сухого запуска на стороне сервера (`--dry-run=server`) позволяет проверить валидацию и политики приема объектов.
- Все изменения конфигураций подлежат фиксации в системе контроля версий.
- Для отката развертываний следует применять встроенные механизмы (`kubectl rollout undo`) вместо ручных правок.
- Управление однородными группами ресурсов рекомендуется осуществлять с применением меток и селекторов.
- Выбор единого подхода к управлению конкретным объектом исключает риск рассинхронизации состояния.

---
## Ключевые выводы

- Выбор подхода к управлению определяется решаемыми задачами: императивные команды подходят для отладки, а декларативные — для производственных сред.
- Декларативная команда `apply` безопаснее команды `replace` за счет использования патчей вместо полной замены объектов.
- Репозиторий кода выступает единственным источником достоверных данных (source of truth) для конфигурации кластера.
- Использование команды `diff` позволяет контролировать вносимые изменения перед их применением.
- Совмещение различных подходов для одного объекта приводит к конфликтам и неопределенному поведению системы
