## Что такое Namespace

|**Аспект**|**Описание**|
|---|---|
|**Определение**|Механизм логической изоляции групп ресурсов в рамках одного физического кластера|
|**Уникальность**|Имя ресурса должно быть уникально **внутри** неймспейса, но может повторяться в разных|
|**Область действия**|Применимо только к namespaced-ресурсам (`Pod`, `Deployment`, `Service`), но не к кластерным (`Node`, `PV`, `StorageClass`)|
|**Иерархия**|Не могут быть вложены друг в друга. Каждый ресурс принадлежит ровно одному неймспейсу|


``` mermaid
graph TD
    Cluster[Kubernetes Cluster] --> NS1[namespace: dev]
    Cluster --> NS2[namespace: staging]
    Cluster --> NS3[namespace: production]
    
    NS1 --> Pod1[Pod: api-v1]
    NS1 --> Svc1[Service: api]
    
    NS2 --> Pod2[Pod: api-v2]
    NS2 --> Svc2[Service: api]
    
    NS3 --> Pod3[Pod: api-v3]
    NS3 --> Svc3[Service: api]
```

Пространства имён предназначены главным образом для организации и квотирования ресурсов, а не для обеспечения безопасности, хотя к ним и можно привязать политики RBAC.

## Когда использовать несколько неймспейсов

### Рекомендуемые сценарии

|**Сценарий**|**Пример**|**Почему неймспейс, а не метки?**|
|---|---|---|
|**Разные команды/проекты**|`team-alpha`, `team-beta`|Изоляция прав доступа (RBAC), квот, лимитов|
|**Разные среды**|`dev`, `staging`, `production`|Разные политики, ресурсы, доступ к внешним сервисам|
|**Мультитенант**|`customer-a`, `customer-b`|Изоляция данных, квотирование, аудит по тенанту|
|**Квоты и лимиты**|`ResourceQuota`, `LimitRange`|Эти объекты работают **только** в рамках неймспейса|

### Когда НЕ использовать неймспейсы

|**Сценарий**|**Лучше использовать**|**Почему**|
|---|---|---|
|**Разные версии одного приложения**|Метки: `version=v1`, `version=v2`|Проще управлять, не нужно дублировать конфиги|
|**Небольшие проекты (1-2 человека)**|Один неймспейс `default` или `app-name`|Излишняя сложность без выгоды|
|**Разделение по компонентам**|Метки: `tier=frontend`, `tier=backend`|Компоненты всё равно связаны сетью, проще в одном месте|

Для производственных сред (production) использование пространства имён `default` не рекомендуется; создание явных неймспейсов (`prod`, `app-name`) значительно упрощает аудит и администрирование.

## Системные неймспейсы

|**Неймспейс**|**Назначение**|**Можно ли использовать?**|
|---|---|---|
|**`default`**|Стартовый неймспейс, если не указан другой|Только для тестов, не для production|
|**`kube-system`**|Системные компоненты K8s (`kube-dns`, `kube-proxy`, metrics-server)|Не размещай свои приложения здесь|
|**`kube-public`**|Публичные ресурсы, доступные для чтения всем (даже неаутентифицированным)|Только если действительно нужно публичное чтение|
|**`kube-node-lease`**|Объекты `Lease` для heartbeat'ов нод (внутренняя механика)|Только для системы|

Запрещается создавать пространства имён с префиксом `kube-`, так как они зарезервированы для системных нужд.

## Работа с неймспейсами: kubectl

### Просмотр и создание

```bash
kubectl get namespaces
kubectl get ns

kubectl describe namespace production

kubectl create namespace my-app

kubectl delete namespace my-app
```

### Переключение контекста и неймспейса

```bash
kubectl get pods --namespace=production
kubectl get pods -n production

kubectl config set-context --current --namespace=production

kubectl config view --minify | grep namespace:

kubectl config set-context --current --namespace=production && \
  kubectl get pods && \
  kubectl config set-context --current --namespace=default
```

### Манифест неймспейса

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: production
    team: platform
  annotations:
    description: "Production environment for customer-facing apps"
```

## Namespaces и DNS

При создании сервиса (`Service`) Kubernetes автоматически генерирует соответствующую DNS-запись:

```
<service-name>.<namespace>.svc.cluster.local
```

### Практическое взаимодействие

```yaml
# В неймспейсе `dev` создан Service: api
# Из пода в том же неймспейсе:
curl http://api          # работает: короткое имя, тот же неймспейс

# Из пода в неймспейсе `production`:
curl http://api          # не найдёт: ищет api.production.svc.cluster.local
curl http://api.dev      # работает: <service>.<namespace>
curl http://api.dev.svc.cluster.local  # FQDN, всегда работает
```

### Риск DNS-коллизий

Создание пространства имён с именем публичного домена (например, `com`) и размещение внутри него сервиса с коротким именем может привести к перехвату внешних запросов внутри подов (`curl http://google` обратится к внутреннему сервису вместо внешнего ресурса). Для предотвращения подобных ситуаций рекомендуется ограничивать права создания неймспейсов через RBAC и использовать Admission Webhooks.

## Какие ресурсы НЕ находятся в неймспейсах

Часть объектов Kubernetes является кластерными (cluster-scoped) и не привязывается к пространствам имён.

### Проверка принадлежности

```bash
kubectl api-resources --namespaced=true

kubectl api-resources --namespaced=false
```

### Примеры кластерных ресурсов

|**Ресурс**|**Почему не в неймспейсе**|
|---|---|
|`Node`|Физическая или виртуальная машина — одна на весь кластер|
|`PersistentVolume` (PV)|Хранилище может использоваться разными неймспейсами|
|`StorageClass`|Шаблон для динамического создания PV — глобальный|
|`Namespace`|Сам является контейнером, не может находиться внутри себя|
|`ClusterRole` / `ClusterRoleBinding`|Права доступа на уровне всего кластера|
|`CustomResourceDefinition` (CRD)|Определение нового типа ресурса — глобальное|

## Автоматическая маркировка неймспейсов

Начиная с Kubernetes 1.22, система автоматически добавляет неизменяемую метку к создаваемым пространствам имён:

```yaml
metadata:
  labels:
    kubernetes.io/metadata.name: <имя-неймспейса>
```

Это упрощает конфигурацию политик сетевой безопасности (`NetworkPolicy`), позволяя ссылаться на неймспейсы по их именам через селекторы без жесткого зашивания параметров.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-monitoring
spec:
  podSelector: {}
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: monitoring
```

## Чек-лист по работе с неймспейсами

- При создании ресурсов явно указывать пространство имён, не полагаясь на значение по умолчанию (`default`).
- Всегда прописывать поле `metadata.namespace` в манифестах для обеспечения идемпотентности и предсказуемости деплоя.
- Перед удалением неймспейса выполнять предварительную проверку содержимого (`kubectl get all -n my-app`) и тест с флагом `--dry-run=server`.
- Проверять текущий рабочий неймспейс при отладке окружения.
- Передавать неймспейс в скриптах в качестве параметров, избегая жесткого кодирования.
- Привязывать роли RBAC к конкретным пространствам имён, если не требуется предоставление доступа на уровне всего кластера.

## Ключевые выводы

1. **Изоляция не равна безопасности**: пространства имён структурируют ресурсы, но для подлинной изоляции необходима связка RBAC и сетевых политик.
2. **Умеренность в структуре**: рекомендуется начинать с одного неймспейса, вводя дополнительные изолированные пространства только при реальной организационной или технической необходимости[cite: 7].
3. **Зависимость DNS-имён**: кросс-неймспейс коммуникация требует учета структуры `<service>.<namespace>.svc.cluster.local`[cite: 7].
4. **Разделение областей видимости**: системные объекты вроде `Node`, `PV` и `StorageClass` функционируют глобально на уровне кластера[cite: 7].
5. **Приоритет явных имен**: пространство `default` предназначено преимущественно для тестирования; в продуктивных средах применяются осмысленные уникальные имена[cite: 7].
