  # Имена и идентификаторы объектов Kubernetes

>Каждый объект в Kubernetes имеет **имя**, которое читается человеком и является уникальным в рамках типа и пространства имен, а также **UID**, выступающий в роли уникального системного идентификатора. Имена ресурсов должны отвечать строгим стандартам DNS-именования, тогда как для массового создания объектов применяется параметр `generateName`.

## Как Kubernetes уникально идентифицирует объект

Однозначное определение объекта формируется комбинацией из четырех атрибутов:

```
[Группа API] + [Тип ресурса] + [Пространство имён] + [Имя]
```

|**Атрибут**|**Пример**|**Пояснение**|
|---|---|---|
|**Группа API**|`apps`, `networking.k8s.io`, `""` (core)|Логическая группировка ресурсов|
|**Тип ресурса**|`deployments`, `pods`, `services`|Kind объекта (в нижнем регистре, во множественном числе)|
|**Пространство имён**|`default`, `kube-system`, `my-app`|Изоляция: ресурсы с одинаковым именем могут функционировать в разных пространствах имён|
|**Имя**|`nginx-deployment`, `my-pod-abc123`|Уникальное наименование в рамках сочетания типа и пространства имён|

### Примеры уникальности

- Допускается создание разных типов ресурсов с одинаковым именем в пределах одного пространства имен (`Pod` и `Deployment` с именем `myapp` в пространстве `default`).
- Допускается существование одинаковых типов ресурсов с одинаковым именем в различных пространствах имен (`Pod` с именем `myapp` в пространствах `dev` и `prod`).
- Конфликт возникает при попытке создания объектов одинакового типа с одинаковым именем в одном пространстве имен.

Версия API (`v1`, `v1beta1`) не входит в состав уникального идентификатора. Объекты `apps/v1/Deployment` и `apps/v1beta1/Deployment` с идентичным именем представляют собой один и тот же объект в различных версиях представления.

## Имя (Name) и UID

| **Характеристика** | **Name**                                                          | **UID**                                                    |
| ------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| **Кто задаёт**     | Пользователь или генератор `generateName`                         | Система автоматически                                      |
| **Формат**         | Строка в соответствии с правилами именования                      | UUID (например, `a1b2c3d4-e5f6-7890-abcd-ef1234567890`)    |
| **Уникальность**   | В рамках типа ресурса и пространства имен                         | Во всем кластере на протяжении всего времени существования |
| **Изменяемость**   | Не подлежит изменению после создания                              | Не изменяется никогда                                      |
| **Назначение**     | Человекочитаемый адрес для API, URL и интерфейса командной строки | Внутренние ссылки, механизмы аудита и отслеживания истории |

### Назначение UID

При удалении и последующем создании объекта с тем же именем визуальные характеристики сохраняются, однако системный идентификатор UID изменяется. Использование UID позволяет контроллерам корректно отслеживать объекты, обеспечивает точный аудит исторических событий и корректную работу сборщика мусора при удалении старых сущностей. Просмотр UID выполняется через следующие команды:

```bash
kubectl get pod myapp -o jsonpath='{.metadata.uid}'
```

## Правила именования: стандарты ограничений

Kubernetes применяет различные правила проверки в зависимости от типа целевого ресурса.

### Сравнение стандартов именования

|**Стандарт**|**Макс. длина**|**Допустимые символы**|**Начало**|**Конец**|**Где применяется**|
|---|---|---|---|---|---|
|**DNS Subdomain** (RFC 1123)|253|`a-z`, `0-9`, `-`, `.`|буквенно-цифровой|буквенно-цифровой|Большинство ресурсов: `Pod`, `Deployment`, `Namespace`, `ServiceAccount`|
|**Label Name** (RFC 1123)|63|`a-z`, `0-9`, `-`|**буква**|буквенно-цифровой|Ключи и значения меток и аннотаций|
|**Label Name** (RFC 1035)|63|`a-z`, `0-9`, `-`|**буква**|буквенно-цифровой|Отдельные ресурсы: `Service` (по умолчанию), `Secret`|
|**Path Segment**|—|Любые символы, кроме `.`, `..`, `/`, `%`|—|—|Ресурсы, используемые в URL-путях|

### Примеры валидных и невалидных имён

- Корректные примеры DNS Subdomain: `my-app.example.com`, `app-v1.2.3`, `nginx-deployment-prod`.
- Ошибки в именах DNS Subdomain: заглавные буквы (`MyApp`), начинающиеся с точки (`.app`), оканчивающиеся на дефис (`app-`), превышающие лимит в 253 символа.
- Корректные примеры RFC 1123 Label: `myapp`, `app-v1`, `nginx123`.
- Ошибки в именах RFC 1123 Label: начинающиеся с цифры (`123-app`), содержащие знак подчеркивания (`app_1`) или точку (`my.app`).

Валидация имени перед созданием ресурса проверяется в режиме сухого запуска:

```bash
kubectl create pod test-APP --image=nginx --dry-run=server
```

## Генерация имён: использование generateName

Параметр `generateName` применяется в сценариях, требующих автоматического формирования уникальных имен (например, в объектах `Job` или при проведении тестов).

### Принцип работы

```yaml
apiVersion: v1
kind: Pod
metadata:
  generateName: test-pod-
spec:
  containers:
  - name: nginx
    image: nginx:1.25
```

Применение манифеста приводит к тому, что сервер добавляет к префиксу случайный суффикс. Начиная с версии Kubernetes 1.31, сервер выполняет до восьми попыток генерации уникального имени. В случае возникновения конфликтов со всеми существующими именами возвращается ошибка `HTTP 409 Conflict`. Суффикс формируется из пяти случайных символов в кодировке base36.

`generateName` целесообразно использовать для объектов `Job`, `CronJob`, тестовых сценариев и создания дочерних ресурсов в операторах. Использование не рекомендуется для ресурсов, на которые ссылаются другие объекты (например, селекторы `Service`), или когда имя жестко зашито в исходном коде приложения.

## Практика: работа с именами и UID

### Просмотр имён и UID

```bash
kubectl get pods

kubectl get pods -o jsonpath='{.items[*].metadata.name}{"\n"}{.items[*].metadata.uid}'

kubectl get pod myapp -o yaml | grep -A2 'name:\|uid:'

kubectl get pod myapp -o jsonpath='{.metadata.name}{"."}{.metadata.namespace}'
```

### Очистка объектов по префиксу

```bash
kubectl get pods -o name | grep '^pod/test-pod-' | xargs -r kubectl delete

kubectl delete pods -l test-run=2024-06-05
```

## Рекомендации по работе с именами

- Перед созданием объекта рекомендуется проверять его отсутствие в целевом пространстве имён.
- Для группировки ресурсов следует использовать метки, оставляя имя уникальным идентификатором, а не носителем метаданных.
- При генерации имен через префиксы полезно добавлять аннотации и метки для трассировки.
- Для связанных объектов (таких как `Service` и `ConfigMap`) нужно использовать статические и предсказуемые имена.
- В процессе отладки следует сопоставлять UID объектов для подтверждения факта создания новых сущностей при совпадении их имен.
- При разработке операторов рекомендуется применять функцию `controllerutil.SetControllerReference` для привязки через UID, а не по текстовому имени.

## Ключевые выводы

- Уникальность объекта определяется совокупностью четырех атрибутов: группы, типа, пространства имен и имени.
- Имя предназначено для идентификации пользователем, в то время как UID используется системными механизмами.
- Соблюдение стандартов именования необходимо для бесшовной интеграции с сетевыми компонентами и балансировщиками.
- Параметр `generateName` эффективен для автоматизации создания динамических ресурсов, не имеющих внешних жестких ссылок.
