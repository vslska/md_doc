## Фазы пода (Pod Phases)

Поле `status.phase` содержит высокоуровневое описание текущего состояния пода.

|**Фаза**|**Описание**|**Когда возникает**|
|---|---|---|
|**`Pending`**|Под принят кластером, но контейнеры ещё не запущены|Ожидание планирования, скачивание образов, инициализация томов|
|**`Running`**|Под привязан к ноде, не менее одного контейнера запущено или перезапускается|Основное состояние работающего приложения|
|**`Succeeded`**|Все контейнеры успешно завершены (код выхода 0) и не будут перезапущены|Завершённые `Job`, одноразовые задачи|
|**`Failed`**|Все контейнеры завершены, хотя бы один завершился с ошибкой (код не равен 0)|Сбой приложения, исчерпание попыток перезапуска|
|**`Unknown`**|Не удалось получить статус пода из-за проблемы связи с нодой|Сбой ноды, сетевое разделение, отсутствие ответа от `kubelet`|

Проверка фазы пода и получение подробной информации о состоянии выполняются следующими командами:

```bash
kubectl get pod my-pod -o jsonpath='{.status.phase}'

kubectl describe pod my-pod | grep -A10 'Status:'
```

Поле `phase` не является исчерпывающим состоянием; для детального анализа необходимо обращаться к `status.conditions` и `containerStatuses`.

## Состояния контейнеров (Container States)

Каждый контейнер в поде находится в одном из трех возможных состояний:

|**Состояние**|**Описание**|**Частые причины**|
|---|---|---|
|**`Waiting`**|Контейнер еще не запущен, выполняется подготовка|Скачивание образа, ожидание секретов, ошибки `ImagePullBackOff`, `ErrImagePull`|
|**`Running`**|Контейнер выполняется без проблем|Нормальная работа приложения|
|**`Terminated`**|Контейнер завершил работу (успешно или с ошибкой)|Код выхода 0 (успех) или отличный от 0 (ошибка), `OOMKilled`, `Evicted`|

Для просмотра состояния контейнеров и кодов выхода завершенных процессов применяются команды:

```bash
kubectl describe pod my-pod | grep -A5 'State:'

kubectl get pod my-pod -o jsonpath='{.status.containerStatuses[*].lastState.terminated.exitCode}'
```

### Частые статусы в выводе команды kubectl get pods

|**Статус**|**Значение**|**Причина**|
|---|---|---|
|**`CrashLoopBackOff`**|Контейнер падает, перезапускается и снова падает|Ошибка приложения, неверная конфигурация, нехватка ресурсов|
|**`ImagePullBackOff`**|Не удалось скачать образ|Неверное имя образа, отсутствие доступа к реестру, сетевая проблема|
|**`ErrImagePull`**|Ошибка при скачивании образа, предшествующая статусу `ImagePullBackOff`|Временная проблема сети или реестра|
|**`OOMKilled`**|Контейнер превысил лимит памяти и был принудительно завершен ядром|Слишком низкий `limits.memory`, утечка памяти в приложении|
|**`Evicted`**|Под удален из-за критической нехватки ресурсов на ноде|Давление на диск или память, перегрузка узла|

## Политика перезапуска (restartPolicy)

Политика перезапуска определяет реакцию Kubernetes на завершение работы контейнеров.

### Уровни применения

|**Уровень**|**Поле**|**Применимость**|
|---|---|---|
|**Пода**|`spec.restartPolicy`|Применяется ко всем контейнерам в поде, кроме sidecar|
|**Контейнера**|`spec.containers[*].restartPolicy`|Переопределяет политику пода для конкретного контейнера (начиная с версии 1.35 в статусе бета)|
|**Sidecar**|`initContainers[*].restartPolicy: Always`|Инициализирующий контейнер типа sidecar игнорирует общую политику пода и всегда перезапускается|

### Значения политики перезапуска

|**Значение**|**Поведение при выходе 0 (успех)**|**Поведение при выходе с ошибкой (код не 0)**|**Когда использовать**|
|---|---|---|---|
|**`Always`** (по умолчанию)|Перезапускает|Перезапускает|Долгоживущие сервисы (Deployment, StatefulSet)|
|**`OnFailure`**|Не перезапускает|Перезапускает|Пакетные задачи (Job) для повторного выполнения при сбое|
|**`Never`**|Не перезапускает|Не перезапускает|Одноразовые задачи, отладка, миграции|

### Примеры конфигураций

```yaml
# Deployment: всегда перезапускать (единственное допустимое значение)
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      restartPolicy: Always
      containers:
      - name: app
        image: my-app:1.0

# Job: перезапускать только при ошибке
apiVersion: batch/v1
kind: Job
spec:
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      - name: task
        image: busybox
        command: ['sh', '-c', 'echo "Processing..."; exit 0']

# Pod со вспомогательным sidecar-контейнером
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-sidecar
spec:
  restartPolicy: OnFailure
  initContainers:
  - name: log-shipper
    image: fluentd:latest
    restartPolicy: Always
  containers:
  - name: main-app
    image: my-app:1.0
```

Sidecar-контейнеры представляют собой инициализирующие контейнеры (`initContainers`) с конфигурацией `restartPolicy: Always`, которые запускаются перед основными компонентами и продолжают работать параллельно с ними в течение всего жизненного цикла пода.

## Экспоненциальная задержка перезапуска (CrashLoopBackOff)

При возникновении повторяющихся сбоев Kubernetes применяет задержку перед следующей попыткой перезапуска для предотвращения перегрузки системы.

### Алгоритм задержки по умолчанию

```
Попытка 1: 10 сек
Попытка 2: 20 сек
Попытка 3: 40 сек
Максимальное значение: 300 сек (5 минут)

Если контейнер стабильно работает в течение 10 минут и более, счетчик сбрасывается.
```

### Настройка задержки на уровне ноды

Конфигурация задается в файле параметров `kubelet`:

```yaml
kind: KubeletConfiguration
crashLoopBackOff:
  maxContainerRestartPeriod: "60s"
```

### Отладка CrashLoopBackOff

Для выявления причин сбоев используются следующие команды:

```bash
# Просмотр логов предыдущей попытки запуска
kubectl logs my-pod --previous

# Просмотр логов конкретного контейнера
kubectl logs my-pod -c app

# Проверка событий пода
kubectl describe pod my-pod | grep -A10 'Events:'

# Проверка использования ресурсов
kubectl top pod my-pod
kubectl describe pod my-pod | grep -A5 'Limits'

# Проверка параметров зондов здоровья
kubectl describe pod my-pod | grep -A10 'Liveness\|Readiness'
```

## Зонды (Probes): проверка здоровья

|**Тип**|**Назначение**|**Действие при провале**|**Когда проверять**|
|---|---|---|---|
|**`startupProbe`**|Определение факта запуска приложения|Ожидание завершения без уничтожения контейнера|Только при старте до прохождения проверки|
|**`livenessProbe`**|Проверка работоспособности и отсутствия зависаний|Перезапуск контейнера|Периодически на протяжении всего жизненного цикла|
|**`readinessProbe`**|Определение готовности принимать входящий трафик|Исключение из балансировки (удаление из конечных точек Endpoints)|Периодически, особенно после завершения старта|

### Пример совместного использования зондов

```yaml
spec:
  containers:
  - name: web-app
    image: my-app:1.0
    ports:
    - containerPort: 8080
    
    startupProbe:
      httpGet: { path: /startup, port: 8080 }
      periodSeconds: 10
      failureThreshold: 6
    
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
    
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2
```

### Типы проверок

|**Механизм**|**Пример**|**Когда использовать**|
|---|---|---|
|**`httpGet`**|`httpGet: { path: /health, port: 8080 }`|Веб-приложения, предоставляющие HTTP-эндпоинт|
|**`tcpSocket`**|`tcpSocket: { port: 5432 }`|Базы данных и сетевые службы без HTTP-интерфейса|
|**`exec`**|`exec: { command: ['pg_isready'] }`|Выполнение произвольной команды внутри контейнера|
|**`grpc`**|`grpc: { port: 9090, service: "health" }`|Сервисы, использующие протокол gRPC (поддерживается с версии 1.24 в статусе бета)|

## Завершение работы пода (Termination)

### Процесс корректного завершения

1. Инициируется удаление пода пользователем через `kubectl delete pod` либо управляющим контроллером.
2. Сервер API устанавливает метку `.metadata.deletionTimestamp` и запускает таймер `.spec.terminationGracePeriodSeconds` (по умолчанию составляет 30 секунд).
3. Компонент `kubelet` на целевой ноде выполняет следующие действия:
    - при наличии настроенного хука `preStop` запускает его выполнение;
    - отправляет сигнал `SIGTERM` главному процессу (PID 1) внутри каждого контейнера;
    - ожидает завершения процессов до истечения периода ожидания (`grace period`).
4. Если по истечении отведенного времени процессы продолжают работу, `kubelet` принудительно отправляет сигнал `SIGKILL` всем оставшимся процессам.
5. Выполняется очистка сетевых ресурсов, томов и удаление объекта пода из API Server.

### Настройка параметров завершения

```yaml
spec:
  terminationGracePeriodSeconds: 60
  
  containers:
  - name: app
    image: my-app:1.0
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "nginx -s quit"]
```

### Принудительное удаление

Удаление с измененным интервалом ожидания или принудительная очистка выполняются командами:

```bash
kubectl delete pod my-pod --grace-period=10

kubectl delete pod my-pod --force --grace-period=0
```

Использование флага `--force` не гарантирует корректного завершения работы приложения и применяется преимущественно для зависших ресурсов.

## Условия пода (Pod Conditions)

Поле `status.conditions` содержит детализированную информацию о состоянии пода.

|**Условие**|**Значение**|**Описание**|
|---|---|---|
|`PodScheduled`|`True` / `False`|Под успешно назначен на узел выполнения|
|`PodReadyToStartContainers`|`True` / `False`|Песочница создана, сеть настроена, тома успешно смонтированы|
|`Initialized`|`True` / `False`|Все инициализирующие контейнеры завершили работу|
|`ContainersReady`|`True` / `False`|Все контейнеры прошли проверки готовности|
|`Ready`|`True` / `False`|Суммарный статус готовности пода принимать трафик|
|`DisruptionTarget`|`True` / `False`|Под помечен на удаление вследствие прерывания (дрейн узла, эвикция)|
|`PodResizePending` / `InProgress`|`True` / `False`|Запрошено или выполняется изменение выделенных ресурсов пода|

Для просмотра условий и проверки статуса готовности используются команды:

```bash
kubectl get pod my-pod -o jsonpath='{.status.conditions}'

kubectl get pod my-pod -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'
```

### Пользовательские условия готовности (Readiness Gates)

```yaml
spec:
  readinessGates:
  - conditionType: "www.example.com/custom-check"
```

Приложение может самостоятельно обновлять данное условие через запросы `PATCH /status`. Под переходит в статус `Ready` только при условии выполнения всех базовых проверок и пользовательских ворот готовности (`readinessGates`).

## Изменение размера пода (Pod Resize)

Функциональность изменения ресурсов процессора и памяти без пересоздания пода поддерживается начиная с версии 1.35.

### Подходы к изменению ресурсов

|**Подход**|**Описание**|**Когда использовать**|
|---|---|---|
|**На месте (In-place)**|Обновление `.spec.containers[*].resources` с применением изменений силами `kubelet` без пересоздания пода|Для критичных нагрузок, где пересоздание нежелательно; для быстрого масштабирования|
|**Через замену (Recreate)**|Обновление шаблона в объекте управления с созданием новых подов контроллером|Стандартный подход, совместимый со всеми версиями кластера|

### Пример изменения размера на месте

Запрос на изменение ресурсов отправляется через субресурс `resize`:

```bash
kubectl patch pod my-pod --subresource=resize --type=merge -p '{
  "spec": {
    "containers": [{
      "name": "app",
      "resources": {
        "requests": { "memory": "512Mi", "cpu": "500m" },
        "limits": { "memory": "1Gi", "cpu": "1" }
      }
    }]
  }
}'

kubectl get pod my-pod -o jsonpath='{.status.conditions[?(@.type=="PodResizeInProgress")]}'
```

## Сборка мусора подов (Pod GC)

Завершенные поды не удаляются из кластера автоматически и требуют наличия механизмов очистки.

### Автоматическое удаление

|**Сценарий**|**Механизм**|**Настройка**|
|---|---|---|
|**Завершённые поды**|Контроллер `PodGC` удаляет объекты при превышении пороговых значений|Параметр `--terminated-pod-gc-threshold` в `kube-controller-manager`|
|**Осиротевшие поды**|Поды, привязанные к удаленным узлам|Выполняется автоматически при обнаружении отсутствия ноды|
|**Поды на нездоровых нодах**|Узел в статусе `NotReady` с установленным тейнтом вывода из эксплуатации|Выполняется автоматически при очистке узла|

### Ручная очистка и управление жизненным циклом задач

```yaml
# Удаление всех завершенных и упавших подов
kubectl delete pod --field-selector=status.phase=Succeeded -A
kubectl delete pod --field-selector=status.phase=Failed -A

# Настройка автоматического удаления объекта Job после завершения
apiVersion: batch/v1
kind: Job
spec:
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      - name: task
        image: busybox
        command: ['sh', '-c', 'echo "Done"']
```

## Ключевые выводы

1. Статус пода определяется на уровне высокоуровневой фазы (`phase`), детализированных условий (`conditions`) и состояний контейнеров (`containerStatuses`).
2. Политика перезапуска (`restartPolicy`) выбирается в зависимости от типа рабочей нагрузки: `Always` для сервисов, `OnFailure` для задач и `Never` для одноразовых операций.
3. Зонды здоровья (`startup`, `liveness`, `readiness`) выступают основой надежности приложений и корректной маршрутизации трафика.
4. Корректное завершение работы обеспечивается настройкой `terminationGracePeriodSeconds` и обработчиков `preStop`.
5. Регулярный мониторинг и анализ состояния подов позволяют своевременно выявлять сбои и оптимизировать конфигурацию инфраструктуры.
