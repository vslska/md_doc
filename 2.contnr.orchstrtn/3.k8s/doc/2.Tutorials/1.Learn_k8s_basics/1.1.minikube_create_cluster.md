## Теория: Kubernetes кластер

### Что такое Kubernetes кластер?

**Kubernetes кластер** представляет собой группу физических или виртуальных машин, которые функционируют совместно как единый механизм для выполнения контейнеризированных приложений.

```
┌─────────────────────────────────────────────────────────┐
│                   Kubernetes Cluster                    │
│                                                         │
│  ┌──────────────────────────────────────────────────┐   │
│  │              Control Plane                       │   │
│  │  ┌─────────┐ ┌─────────┐ ┌──────────┐ ┌──────┐   │   │
│  │  │API Server││  etcd   │ │ Scheduler│ │  CM  │   │   │
│  │  └─────────┘ └─────────┘ └──────────┘ └──────┘   │   │
│  └──────────────────────────────────────────────────┘   │
│                          │                              │
│                          ▼                              │
│  ┌──────────────────────────────────────────────────┐   │
│  │                   Nodes                          │   │
│  │  ┌─────────┐  ┌─────────┐  ┌─────────┐           │   │
│  │  │ Node 1  │  │ Node 2  │  │ Node 3  │  ...      │   │
│  │  │┌───────┐│  │┌───────┐│  │┌───────┐│           │   │
│  │  ││ Pod   ││  ││ Pod   ││  ││ Pod   ││           │   │
│  │  │└───────┘│  │└───────┘│  │└───────┘│           │   │
│  │  └─────────┘  └─────────┘  └─────────┘           │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

### Два типа ресурсов в кластере

#### Control Plane (Плоскость управления)

Назначение: централизованное управление кластером и координация всех выполняемых в нем действий.
Компоненты:

- **API Server** — универсальная точка входа для всех запросов от интерфейса командной строки `kubectl`, контроллеров и узлов. 
- **etcd** — распределенное хранилище данных, в котором фиксируется текущее состояние кластера.
- **Scheduler** — планировщик, определяющий вычислительный узел для запуска нового Pod'а.
- **Controller Manager** — диспетчер контроллеров, управляющий объектами Deployment, ReplicaSet и другими сущностями.
#### Nodes (Узлы)

Назначение: рабочие машины, на которых непосредственно развертываются приложения.

Компоненты на каждом узле:

- **kubelet** — агент, осуществляющий связь с Control Plane и администрирование Pod'ов.
- **Container Runtime** — среда выполнения для запуска контейнеров, такая как `containerd`, `CRI-O` или `Docker`.
- **kube-proxy** — сетевой компонент, выполняющий маршрутизацию трафика.

### Production и Development

| Характеристика | Production кластер                                                   | Minikube (для обучения)                      |
| -------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| Количество нод | От 3 и более для обеспечения высокой доступности (HA)<br><br>        | 1                                            |
| Control Plane  | Развертывается на отдельном оборудовании или виртуальных машинах<br> | Интегрирован в единую виртуальную машину<br> |
| Масштаб        | Сотни или тысячи Pod'ов<br><br>                                      | Десятки Pod'ов<br><br>                       |
| Назначение     | Запуск промышленных приложений<br><br>                               | Обучение, разработка и тестирование<br><br>  |
| Доступность    | 99.9% и выше<br>                                                     | Не критический параметр<br><br>              |

Необходимость использования не менее трех узлов в производственной среде обусловлена тем, что при отказе одной ноды сохраняется кворум хранилища `etcd`, экземпляр Control Plane и общая отказоустойчивость кластера.

## Что такое Minikube?

**Minikube** — легковесная реализация Kubernetes, предназначенная для развертывания локального кластера на персональной рабочей станции.

### Особенности Minikube

Преимущества:

- Высокая скорость развертывания (в пределах 1–2 минут).  
- Отсутствие необходимости в задействовании облачных ресурсов или выделенных серверов.
- Оптимальные условия для обучения и локальной разработки.
- Поддержка операционных систем Linux, macOS и Windows.

Ограничения:

- Наличие только одного узла без поддержки высокой доступности (HA).
- Ограниченные системные ресурсы (процессорное время и оперативная память).
- Неприменимость для промышленных нагрузок (production).
### Драйверы Minikube

Minikube поддерживает применение различных драйверов виртуализации:

- **Docker** — наиболее популярный и быстродействующий вариант, использующий контейнеры.
- **VirtualBox** — классический метод с применением виртуальных машин.
- **HyperKit** — нативный инструмент виртуализации для macOS. 
- **Hyper-V** — нативная технология виртуализации для Windows.
- **KVM2** — нативный быстродействующий драйвер для Linux.

Рекомендуется использовать драйвер **Docker** ввиду его максимальной простоты и производительности.

## Практика: Запуск Minikube

### Проверка установки

Проверка наличия и версий утилиты `minikube`:

```bash
minikube version
```

Ожидаемый результат:

```bash
minikube version: v1.32.0
```

При отсутствии установленного приложения выполняется его установка в зависимости от операционной системы:

```Bash
# macOS
brew install minikube

# Linux (a64)
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-a64
sudo install minikube-linux-a64 /usr/local/bin/minikube

# Windows (Chocolatey)
choco install minikube
```

Проверка наличия и версии клиентской утилиты `kubectl`:

```Bash
kubectl version --client
```

Ожидаемый результат:

```bash
Client Version: v1.29.0
```

При отсутствии `kubectl` выполняется установка:

```Bash
# macOS
brew install kubectl

# Linux
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/a64/kubectl"
sudo install kubectl /usr/local/bin/kubectl

# Windows
choco install kubectl
```

Проверка версии среды Docker:

```Bash
docker --version
```

Ожидаемый результат:

```bash
Docker version 24.0.7
```

При отсутствии Docker инсталляция выполняется с официального ресурса разработчика.

### Запуск кластера

Инициализация кластера выполняется командой:

```Bash
minikube start
```

### Последовательность процессов при инициализации

1. Проверка доступности драйвера и выбор Docker в качестве базовой среды.
2. Создание изолированного контейнера для размещения компонентов Kubernetes.
3. Загрузка базового образа с предустановленными бинарными файлами.
4. Запуск управляющих компонентов Control Plane (генерация сертификатов, инициализация `etcd`, API Server, Controller Manager и Scheduler).
5. Конфигурация сетевой подсистемы CNI (Container Network Interface) для взаимодействия Pod'ов.
6. Интеграция конфигурации в файл `~/.kube/config` с добавлением контекста `minikube`.
7. Активация системных дополнений (addons), включая `default-storageclass` и `storage-provisioner`. 
8. Проверка готовности и подтверждение успешности развертывания.

### Проверка статуса

Оценка текущего состояния служб minikube:

```bash
minikube status
```

Ожидаемый результат:

```bash
minikube
type: Control Plane
host: Running
kubelet: Running
apiserver: Running
kubeconfig: Configured
```

Расшифровка показателей статуса:

- `host` — состояние виртуального контейнера или машины.
- `kubelet` — активность локального агента ноды.
- `apiserver` — доступность управляющего интерфейса API Server.
- `kubeconfig` — корректность конфигурации клиентского доступа.

Дополнительные верификационные команды:

```bash
# Проверка доступности API-сервера
kubectl cluster-info

# Просмотр списка узлов кластера
kubectl get nodes
```

Примечание: В рамках Minikube функционирует единственный узел, совмещающий роли Control Plane и Worker Node, в то время как в продуктивных средах эти роли разделены.

## Что внутри minikube?

### Просмотр системных Pod'ов

Для анализа служебных процессов используется пространство имен `kube-system`:

```bash
kubectl get pods -n kube-system
```

Ожидаемый результат:

```bash
NAME                                    READY   STATUS    RESTARTS   AGE
coredns-5644d7b6d9-mh9ll                1/1     Running   0          2m
coredns-5644d7b6d9-pqd2t                1/1     Running   0          2m
etcd-minikube                           1/1     Running   0          2m
kube-apiserver-minikube                 1/1     Running   0          2m
kube-controller-manager-minikube        1/1     Running   0          2m
kube-proxy-rnlps                        1/1     Running   0          2m
kube-scheduler-minikube                 1/1     Running   0          2m
storage-provisioner                     1/1     Running   0          2m
```

### Назначение системных компонентов

|Имя Pod'а / Компонент|Функциональное назначение|
|---|---|
|`coredns-*`|Служба разрешения доменных имен для сервисов (service discovery)<br><br>|
|`etcd-minikube`|Распределенное хранилище состояния кластера<br><br>|
|`kube-apiserver-minikube`|Интерфейс взаимодействия с API<br><br>|
|`kube-controller-manager-minikube`|Менеджер фоновых контроллеров<br><br>|
|`kube-scheduler-minikube`|Планировщик размещения Pod'ов<br><br>|
|`kube-proxy-*`|Сетевой прокси-агент маршрутизации<br><br>|
|`storage-provisioner`|Модуль динамического создания постоянных хранилищ<br><br>|

Данные компоненты реализованы в виде статически запускаемых Pod'ов, управление которыми выполняет локальный демон `kubelet` на основе манифестов из директории `/etc/kubernetes/manifests/`.

Просмотр логов управляющего API Server:

```bash
kubectl logs -n kube-system kube-apiserver-minikube
```

## Практические задания

### Задание 1: Проверка конфигурации kubectl

Инспекция файла конфигурации `kubeconfig`:

```bash
kubectl config view
```

### Задание 2: Управление контекстами выполнения

```bash
# Вывод всех доступных контекстов
kubectl config get-contexts

# Активация контекста minikube
kubectl config use-context minikube
```

### Задание 3: Анализ детальной информации об узле

```bash
kubectl describe node minikube
```

### Задание 4: Управление жизненным циклом Minikube

```bash
# Остановка кластера с сохранением состояния
minikube stop

# Проверка статуса
minikube status

# Повторный запуск
minikube start

# Проверка работоспособности
kubectl get nodes
```

При остановке кластера данные Pod'ов сохраняются в хранилище `etcd` и автоматически восстанавливаются при последующем запуске.

### Задание 5: Пересоздание кластера

```bash
# Полное удаление окружения
minikube delete

# Создание нового экземпляра кластера
minikube start

# Верификация
kubectl get nodes
```

При повторном создании процедура выполняется быстрее за счет локального кэширования базового контейнерного образа.

## Troubleshooting

### Устранение зависания при запуске

При зависании команды `minikube start` рекомендуется выполнить очистку и запуск с расширенным логированием:

```bash
minikube delete
minikube start --alsologtostderr -v=7
```

### Восстановление подключения kubectl

В случае потери связи клиентского приложения с кластером проверяется активный контекст:

```bash
kubectl config current-context
kubectl config use-context minikube
```

### Управление выделением аппаратных ресурсов

При нехватке системных ресурсов параметры инициализации задаются явно:

```bash
minikube start --cpus=4 --memory=8192
```

- Пересоздание среды с помощью `minikube delete`.

## Ключевые выводы

1. **Kubernetes кластер** объединяет управляющие службы Control Plane и рабочие узлы Nodes для выполнения распределенных задач.
2. **Minikube** представляет собой одноузловую реализацию кластера для локальной разработки и обучения.
3. **kubectl** служит основным инструментом взаимодействия с REST API интерфейсом кластера. 
4. **kubeconfig** определяет параметры подключения клиента к целевым кластерам.
5. **Системные Pod'ы** реализуют ключевые функции Control Plane внутри изолированной среды выполнения.
