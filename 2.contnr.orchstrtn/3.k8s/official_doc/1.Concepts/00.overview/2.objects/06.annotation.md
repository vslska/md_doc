
# Аннотации (Annotations)

> С помощью аннотаций Kubernetes можно прикреплять к объектам произвольные метаданные, **не используемые для идентификации**. Клиенты — инструменты и библиотеки — могут извлекать эти метаданные.

## Прикрепление метаданных к объектам

Для метаданных объекта можно использовать либо метки (labels), либо аннотации. Метки служат для **выбора объектов** и поиска коллекций, удовлетворяющих условиям. Аннотации, в отличие от них, **не используются для идентификации и выбора** объектов. Метаданные в аннотации могут быть небольшими или большими, структурированными или нет, и могут содержать символы, недопустимые в метках. В metadata одного объекта можно одновременно использовать и метки, и аннотации.

Аннотации, как и метки, — это отображения «ключ/значение»:

```json
"metadata": {
  "annotations": {
    "key1" : "value1",
    "key2" : "value2"
  }
}
```

> **Примечание:** ключи и значения в отображении **должны быть строками**. То есть нельзя использовать числа, булевы значения, списки или другие типы ни для ключей, ни для значений.

Примеры информации, которую можно записывать в аннотации:

- Поля, управляемые слоем декларативной конфигурации. Их прикрепление в виде аннотаций отличает их от значений по умолчанию, задаваемых клиентами или серверами, от автоматически генерируемых полей и полей, задаваемых системами автоматического масштабирования.
- Информация о сборке, релизе или образе: метки времени, ID релиза, git-ветка, номера PR, хеши образов, адрес реестра.
- Указатели на репозитории логирования, мониторинга, аналитики или аудита.
- Информация о клиентской библиотеке или инструменте для отладки: например, имя, версия, данные сборки.
- Сведения о происхождении (provenance) от пользователя, инструмента или системы — например, URL связанных объектов из других компонентов экосистемы.
- Метаданные лёгких инструментов rollout: например, конфигурация или контрольные точки.
- Телефонные или пейджерные номера ответственных лиц либо записи каталога, указывающие, где найти эту информацию (например, сайт команды).
- Директивы конечного пользователя реализации — изменить поведение или задействовать нестандартные возможности.

Вместо аннотаций такую информацию можно хранить во внешней базе данных или каталоге, но тогда гораздо сложнее создавать общие клиентские библиотеки и инструменты для развёртывания, управления, интроспекции и подобных задач.

## Синтаксис и набор символов

Аннотации — это пары «ключ/значение». Допустимый ключ аннотации состоит из двух сегментов: **необязательного префикса** и **имени**, разделённых косой чертой (`/`).

- **Имя** — обязательно, не более 63 символов, начинается и заканчивается буквой или цифрой (`[a-z0-9A-Z]`), между ними допускаются дефисы (`-`), подчёркивания (`_`), точки (`.`) и буквенно-цифровые символы.
- **Префикс** — необязателен. Если указан, должен быть DNS-поддоменом: последовательность DNS-меток, разделённых точками (`.`), общей длиной не более 253 символов, после чего идёт косая черта (`/`).

Если префикс опущен, ключ аннотации считается **приватным для пользователя**. Автоматизированные системные компоненты (например, kube-scheduler, kube-controller-manager, kube-apiserver, kubectl или другая сторонняя автоматизация), добавляющие аннотации к объектам конечных пользователей, **обязаны указывать префикс**.

Префиксы `kubernetes.io/` и `k8s.io/` зарезервированы за核心-компонентами Kubernetes.

Допустимые значения аннотаций **не имеют ограничений по набору символов** — в отличие от значений меток, значение аннотации может быть любой строкой, включая специальные символы, пробелы и структурированные данные (например, JSON или YAML). Если планируется хранить двоичные данные (например, CBOR), проект Kubernetes рекомендует кодировать их в base64. При этом суммарный размер всех аннотаций на одном объекте (ключи и значения вместе) **не должен превышать 256 KiB**.

Например, ниже приведён манифест Pod'а с аннотацией `imageregistry: https://hub.docker.com/`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: annotations-demo
  annotations:
    imageregistry: "https://hub.docker.com/"
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```
