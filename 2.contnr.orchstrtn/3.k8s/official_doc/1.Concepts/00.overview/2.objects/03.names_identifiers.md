## Принцип уникальной идентификации объекта

Каждый объект в Kubernetes имеет **имя (Name)**, уникальное в рамках определённого типа ресурса, и **UID**, уникальный в пределах всего кластера .

Однозначная идентификация объекта определяется комбинацией четырёх атрибутов:

| Атрибут | Пример | Пояснение |
|---|---|---|
| Группа API | `apps`, `""` (core) | Логическая группировка ресурсов |
| Тип ресурса | `deployments`, `pods` | Тип ресурса (Kind) |
| Пространство имён | `default`, `kube-system` | Применимо только к ресурсам с областью видимости пространства имён |
| Имя | `nginx-deployment` | Уникальное имя в рамках комбинации типа ресурса и пространства имён |

**Версия API не входит в состав уникального идентификатора**. Доступ к `apps/v1/Deployment` и `apps/v1beta1/Deployment` с одинаковым именем осуществляется к одному и тому же базовому объекту, лишь представленному в разных версиях; невозможно создать два объекта с одинаковыми именем и типом ресурса в одном пространстве имён, используя разные версии API .

В пределах одного пространства имён могут сосуществовать разные типы ресурсов с одинаковым именем (например, `Pod` и `Deployment`, оба с именем `myapp-1234`); после удаления объекта можно создать новый объект с тем же именем .

> **Примечание**: если объект представляет физическую сущность (например, Node представляет физический хост), и хост пересоздан под тем же именем без удаления и повторного создания объекта Node, Kubernetes будет рассматривать новый хост как старый, что может привести к несогласованности данных .

Для пользовательских неуникальных атрибутов используются Labels и Annotations.

## Name и UID

| Характеристика | Name | UID |
|---|---|---|
| Кто задаёт | Пользователь или генерация через `generateName` | Автоматически генерируется системой |
| Формат | Строка, соответствующая правилам именования | UUID (например, `a1b2c3d4-...`) |
| Уникальность | В рамках типа ресурса и пространства имён | В пределах всего кластера, на протяжении всего жизненного цикла |
| Изменяемость | Не изменяется после создания | Никогда не изменяется |
| Назначение | Человекочитаемая адресация, URL, CLI | Внутренние ссылки, аудит, отслеживание истории |

UID предназначен для различения схожих сущностей, существовавших в кластере в разное время. Когда контроллеру необходимо отслеживать исторические экземпляры объекта, следует использовать UID, а не имя .

## Ограничения имён

Kubernetes применяет различные правила проверки в зависимости от типа ресурса.

| Стандарт | Максимальная длина | Допустимые символы | Начальный символ | Конечный символ |
|---|---|---|---|---|
| DNS Subdomain (RFC 1123) | 253 | `a-z`, `0-9`, `-`, `.` | Буква или цифра | Буква или цифра |
| RFC 1123 Label | 63 | `a-z`, `0-9`, `-` | **Буква** | Буква или цифра |
| RFC 1035 Label | 63 | `a-z`, `0-9`, `-` | **Буква** | Буква или цифра |
| Path Segment | — | Любые символы, кроме `.`, `..`, `/`, `%` | — | — |

**О начале с цифры**: хотя RFC 1123 технически допускает начало метки с цифры, текущая реализация Kubernetes требует, чтобы метки RFC 1035 и RFC 1123 начинались с буквы. Исключение составляет случай, когда для объектов Service включён feature gate `RelaxedServiceNameValidation`, позволяющий именам Service начинаться с цифры .

**О заглавных буквах**: имена ресурсов должны состоять только из строчных букв; имена, содержащие заглавные буквы, будут отклонены API Server .

Пример корректного манифеста Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-demo
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```

Некоторые типы ресурсов имеют дополнительные ограничения имён.

## generateName: автоматическая генерация имён

Если в запросе на создание ресурса указан `generateName` вместо `name`, сервер сгенерирует имя. Указанное значение используется как префикс, к которому сервер добавляет сгенерированный суффикс .

```yaml
apiVersion: v1
kind: Pod
metadata:
  generateName: test-pod-
spec:
  containers:
  - name: nginx
    image: nginx:1.25
```

Даже для автоматически сгенерированных имён возможны конфликты с существующими именами, что приводит к ответу `HTTP 409 Conflict`. **Начиная с Kubernetes v1.31**, сервер предпринимает до 8 попыток генерации уникального имени, прежде чем вернуть 409, что значительно снижает вероятность коллизий .

Сценарии применения `generateName`: Job, CronJob, тестовые ресурсы, дочерние ресурсы, создаваемые операторами. Не рекомендуется для ресурсов, на которые ссылаются другие объекты (например, селекторы Service), или когда имя жёстко закодировано в приложении.

## Практические команды

```bash
# Просмотр имён и UID
kubectl get pods -o jsonpath='{.items[*].metadata.name}{"\n"}{.items[*].metadata.uid}'

# Просмотр UID конкретного Pod
kubectl get pod myapp -o jsonpath='{.metadata.uid}'

# Проверка имени в режиме dry-run на стороне сервера (без создания)
kubectl create pod test-APP --image=nginx --dry-run=server

# Очистка объектов по префиксу
kubectl get pods -o name | grep '^pod/test-pod-' | xargs -r kubectl delete
```

## Рекомендации

- Имя служит уникальным идентификатором и не должно использоваться для хранения метаданных; для группировки ресурсов используйте Labels.
- Для связанных объектов (Service и ConfigMap и т.п.) используйте статические предсказуемые имена.
- При отладке сравнивайте UID, чтобы подтвердить, был ли объект пересоздан (при одинаковом имени UID будет различаться).
- В операторах для привязки отношений владения используйте UID, а не текстовое имя.
