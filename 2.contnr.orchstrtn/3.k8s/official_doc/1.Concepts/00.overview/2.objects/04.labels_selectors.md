Метки — это пары «ключ/значение», прикрепляемые к объектам, например к Pod'ам. Метки предназначены для указания **идентифицирующих атрибутов** объектов, значимых и релевантных пользователям, но **не подразумевающих семантику для ядра системы** напрямую. Метки можно использовать для организации и выбора подмножеств объектов. Их можно прикреплять при создании объекта и добавлять/изменять в любое время. У каждого объекта может быть набор меток «ключ/значение». **Каждый ключ должен быть уникален для данного объекта.**

```json
"metadata": {
  "labels": {
    "key1" : "value1",
    "key2" : "value2"
  }
}
```

Метки обеспечивают эффективные запросы и watch и идеальны для использования в UI и CLI. **Неидентифицирующую информацию** следует записывать с помощью аннотаций.

## Motivation

Метки позволяют пользователям отображать собственные организационные структуры на системные объекты слабо связанным образом, без необходимости клиентам хранить эти соответствия.

Развёртывания сервисов и конвейеры пакетной обработки часто являются **многомерными сущностями** (например, несколько партиций или развёртываний, несколько треков релизов, несколько уровней, несколько микросервисов на уровне). Управление часто требует **сквозных операций**, что ломает инкапсуляцию строго иерархических представлений, особенно жёстких иерархий, определяемых инфраструктурой, а не пользователями.

Примеры меток:

- `"release": "stable"`, `"release": "canary"`
- `"environment": "dev"`, `"environment": "qa"`, `"environment": "production"`
- `"tier": "frontend"`, `"tier": "backend"`, `"tier": "cache"`
- `"partition": "customerA"`, `"partition": "customerB"`
- `"track": "daily"`, `"track": "weekly"`

Это примеры часто используемых меток; вы свободны разрабатывать собственные соглашения. Помните: ключ метки должен быть уникален для данного объекта.

## Синтаксис и набор символов

Метки — пары «ключ/значение». Допустимый ключ метки состоит из двух сегментов: **необязательного префикса** и **имени**, разделённых косой чертой (`/`).

- **Имя** — обязательно, не более 63 символов, начинается и заканчивается буквой или цифрой (`[a-z0-9A-Z]`), между ними допускаются дефисы (`-`), подчёркивания (`_`), точки (`.`) и буквенно-цифровые символы.
- **Префикс** — необязателен. Если указан, должен быть DNS-поддоменом: последовательность DNS-меток, разделённых точками (`.`), общей длиной не более 253 символов, после чего идёт косая черта (`/`).

Если префикс опущен, ключ метки считается **приватным для пользователя**. Автоматизированные системные компоненты (например, kube-scheduler, kube-controller-manager, kube-apiserver, kubectl или другая сторонняя автоматизация), добавляющие метки к объектам конечных пользователей, **обязаны указывать префикс**.

Префиксы `kubernetes.io/` и `k8s.io/` зарезервированы за核心-компонентами Kubernetes.

Допустимое значение метки:

- не более 63 символов (может быть пустым);
- если не пустое — начинается и заканчивается буквой или цифрой (`[a-z0-9A-Z]`);
- между ними допускаются дефисы (`-`), подчёркивания (`_`), точки (`.`) и буквенно-цифровые символы.

Пример манифеста Pod'а с двумя метками `environment: production` и `app: nginx`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: label-demo
  labels:
    environment: production
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
```

## Селекторы меток (Label Selectors)

В отличие от имён и UID, метки **не обеспечивают уникальность**. Как правило, многие объекты несут одни и те же метки.

С помощью **селектора меток** клиент/пользователь может идентифицировать набор объектов. Селектор меток — **основной примитив группировки** в Kubernetes.

API поддерживает два типа селекторов: **на основе равенства** и **на основе множеств**. Селектор меток может состоять из нескольких требований, разделённых запятыми. При нескольких требованиях все они должны быть выполнены, то есть запятая действует как логический **AND** (`&&`).

Семантика пустых или неуказанных селекторов зависит от контекста; типы API, использующие селекторы, должны документировать их допустимость и значение.

> **Примечание:** для некоторых типов API, например для ReplicaSet, селекторы меток двух экземпляров **не должны пересекаться** в пределах пространства имён, иначе контроллер может увидеть в этом конфликтующие инструкции и не сможет определить, сколько реплик должно быть.

> **⚠️ Внимание:** для условий на основе равенства и на основе множеств **нет логического OR** (`||`). Структурируйте фильтры соответственно.

### Требования на основе равенства

Требования на основе равенства или неравенства позволяют фильтровать по ключам и значениям меток. Совпадающие объекты должны удовлетворять **всем** указанным ограничениям, хотя могут иметь и дополнительные метки. Допускаются три оператора: `=`, `==`, `!=`. Первые два означают равенство (синонимы), последний — неравенство. Например:

```
environment = production
tier != frontend
```

Первое выбирает все ресурсы с ключом `environment` и значением `production`. Второе выбирает все ресурсы с ключом `tier` и значением, отличным от `frontend`, **а также все ресурсы без метки с ключом `tier`**. Можно отфильтровать ресурсы в `production`, исключив `frontend`, через запятую: `environment=production,tier!=frontend`.

Один из сценариев использования требований на основе равенства — задание критериев выбора узлов для Pod'ов. Например, Pod ниже выбирает узлы, где метка `accelerator` существует и равна `nvidia-tesla-p100`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cuda-test
spec:
  containers:
    - name: cuda-test
      image: "registry.k8s.io/cuda-vector-add:v0.1"
      resources:
        limits:
          nvidia.com/gpu: 1
  nodeSelector:
    accelerator: nvidia-tesla-p100
```

### Требования на основе множеств

Требования на основе множеств позволяют фильтровать ключи по набору значений. Поддерживаются три оператора: `in`, `notin` и `exists` (только идентификатор ключа). Например:

```
environment in (production, qa)
tier notin (frontend, backend)
partition
!partition
```

- Первый пример выбирает все ресурсы с ключом `environment` и значением `production` или `qa`.
- Второй выбирает все ресурсы с ключом `tier` и значениями, отличными от `frontend` и `backend`, **а также все ресурсы без метки с ключом `tier`**.
- Третий выбирает все ресурсы, содержащие метку с ключом `partition`; значения не проверяются.
- Четвёртый выбирает все ресурсы **без** метки с ключом `partition`; значения не проверяются.

Аналогично запятая действует как **AND**. Так, фильтрация ресурсов с ключом `partition` (независимо от значения) и с `environment`, отличным от `qa`, достигается через `partition,environment notin (qa)`. Селектор на основе множеств — общая форма равенства, поскольку `environment=production` эквивалентно `environment in (production)`; аналогично для `!=` и `notin`.

Требования на основе множеств можно смешивать с требованиями на основе равенства. Например: `partition in (customerA, customerB),environment!=qa`.

## API

### Фильтрация LIST и WATCH

Для операций list и watch можно указать селекторы меток, чтобы отфильтровать возвращаемые наборы объектов; фильтр задаётся параметром запроса. (Подробнее о watch в Kubernetes см. «efficient detection of changes».) Допустимы оба типа требований (в виде, как они выглядели бы в строке URL-запроса):

- требования на основе равенства: `?labelSelector=environment%3Dproduction,tier%3Dfrontend`
- требования на основе множеств: `?labelSelector=environment+in+%28production%2Cqa%29%2Ctier+in+%28frontend%29`

Оба стиля селекторов меток можно использовать для list или watch ресурсов через REST-клиент. Например, обращаясь к apiserver через kubectl с требованиями на основе равенства:

```bash
kubectl get pods -l environment=production,tier=frontend
```

или с требованиями на основе множеств:

```bash
kubectl get pods -l 'environment in (production),tier in (frontend)'
```

Как уже упоминалось, требования на основе множеств выразительнее. Например, они могут реализовать оператор **OR** по значениям:

```bash
kubectl get pods -l 'environment in (production, qa)'
```

или ограничить негативное совпадение через оператор `notin`:

```bash
kubectl get pods -l 'environment,environment notin (frontend)'
```

## Ссылки на множества в API-объектах

Некоторые объекты Kubernetes, например Service и ReplicationController, также используют селекторы меток для указания наборов других ресурсов, таких как Pod'ы.

### Service и ReplicationController

Набор Pod'ов, на которые нацелен Service, определяется **селектором меток**. Аналогично популяция Pod'ов, которыми должен управлять ReplicationController, также определяется селектором меток.

Селекторы меток для обоих объектов задаются в json или yaml файлах через map, и поддерживаются **только требования на основе равенства**:

```json
"selector": {
    "component" : "redis",
}
```

или

```yaml
selector:
  component: redis
```

Этот селектор (в json или yaml) эквивалентен `component=redis` или `component in (redis)`.

### Ресурсы, поддерживающие требования на основе множеств

Более новые ресурсы, такие как Job, Deployment, ReplicaSet и DaemonSet, поддерживают и требования на основе множеств:

```yaml
selector:
  matchLabels:
    component: redis
  matchExpressions:
    - { key: tier, operator: In, values: [cache] }
    - { key: environment, operator: NotIn, values: [dev] }
```

`matchLabels` — это map пар `{key,value}`. Одна пара `{key,value}` в `matchLabels` эквивалентна элементу `matchExpressions`, где поле `key` — это «key», оператор — `In`, а массив `values` содержит только «value». `matchExpressions` — список требований селектора Pod'ов. Допустимые операторы: `In`, `NotIn`, `Exists`, `DoesNotExist`. Набор `values` должен быть непустым для `In` и `NotIn`. Все требования из `matchLabels` и `matchExpressions` объединяются через **AND** — все должны быть выполнены для совпадения.

### Выбор наборов узлов

Один из сценариев использования меток — ограничить набор узлов, на которые может быть запланирован Pod. Подробнее см. документацию по выбору узлов (node selection).

## Эффективное использование меток

Можно применять одну метку к любым ресурсам, но это не всегда лучшая практика. Есть много сценариев, где следует использовать несколько меток, чтобы отличать наборы ресурсов друг от друга.

Например, разные приложения будут использовать разные значения метки `app`, но многоуровневое приложение, такое как guestbook, дополнительно нуждается в различении каждого уровня.

В примерах ниже метка `app` включена для удобства ручных запросов и простого использования CLI. Метка `app.kubernetes.io/name` следует рекомендованным соглашениям Kubernetes и лучше подходит для инструментов и автоматизации.

Frontend может нести следующие метки:

```yaml
labels:
  app: guestbook
  app.kubernetes.io/name: guestbook
  tier: frontend
```

а Redis master и replica — разные метки `tier` и, возможно, дополнительную метку `role`:

```yaml
labels:
  app: guestbook
  app.kubernetes.io/name: guestbook
  tier: backend
  role: master
```

и

```yaml
labels:
  app: guestbook
  app.kubernetes.io/name: guestbook
  tier: backend
  role: replica
```

Метки позволяют нарезать ресурсы по любому измерению, заданному меткой:

```bash
kubectl apply -f examples/guestbook/all-in-one/guestbook-all-in-one.yaml
kubectl get pods -Lapp -Ltier -Lrole
```

## Обновление меток

Иногда нужно переразметить существующие Pod'ы и другие ресурсы перед созданием новых. Это можно сделать через `kubectl label`. Например, если нужно пометить все NGINX-Pod'ы как `tier=fe`:

```bash
kubectl label pods -l app=nginx tier=fe
```

```
pod/my-nginx-2035384211-j5fhi labeled
pod/my-nginx-2035384211-u2c7e labeled
pod/my-nginx-2035384211-u3t6x labeled
```

Сначала фильтруются все Pod'ы с меткой `app=nginx`, затем им ставится метка `tier=fe`. Посмотреть помеченные Pod'ы:

```bash
kubectl get pods -l app=nginx -L tier
```

```
NAME                        READY     STATUS    RESTARTS   AGE       TIER
my-nginx-2035384211-j5fhi   1/1       Running   0          23m       fe
my-nginx-2035384211-u2c7e   1/1       Running   0          23m       fe
my-nginx-2035384211-u3t6x   1/1       Running   0          23m       fe
```

Выводятся все Pod'ы с `app=nginx` с дополнительным столбцом `tier` (задаётся через `-L` или `--label-columns`).

Подробнее см. `kubectl label`.
