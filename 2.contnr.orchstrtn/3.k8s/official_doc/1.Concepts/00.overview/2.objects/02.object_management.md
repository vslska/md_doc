## Общие принципы

`kubectl` поддерживает несколько способов создания объектов и управления ими. Ключевое правило: **для одного объекта следует применять только один подход**. Смешивание техник приводит к неопределённому поведению.

| Подход | Объект воздействия | Рекомендуемая среда | Поддерживаемое число авторов |
|---|---|---|---|
| Императивные команды | Живые объекты в кластере | Разработка, разовые задачи | 1+ |
| Императивная конфигурация | Отдельные файлы | Production | 1 |
| Декларативная конфигурация | Каталоги файлов | Production | 1+ |

## Императивные команды

Команды выполняются напрямую над объектами в кластере; пользователь передаёт операцию через аргументы и флаги `kubectl`. История предыдущих конфигураций не сохраняется.

```bash
kubectl create deployment nginx --image=nginx
kubectl scale deployment nginx --replicas=3
kubectl delete deployment nginx
```

**Преимущества**: одно действие — одно изменение; минимальный порог входа; подходит для обучения, отладки и разовых операций.

**Недостатки**: отсутствие аудита и истории изменений; нет шаблона для воспроизведения в другом кластере; нет интеграции с ревью.

## Императивная конфигурация

Операция (`create`, `replace`, `delete`) задаётся явно, вместе с одним или несколькими файлами YAML/JSON, содержащими полное определение объекта.

```bash
kubectl create -f nginx.yaml
kubectl replace -f nginx.yaml
kubectl delete -f nginx.yaml
```

**Критически важно**: `kubectl replace` полностью заменяет `spec` объекта содержимым файла. Все изменения, сделанные в живом объекте и отсутствующие в файле, **будут потеряны**. Это особенно опасно для объектов, чьи поля управляются кластером независимо — например, `Service` типа `LoadBalancer`, у которого поле `externalIPs` обновляется контроллером облака. Такие поля необходимо явно включать в конфигурационный файл перед `replace` .

**Преимущества**: конфигурации хранятся в системе контроля версий; возможны ревью и аудит; есть шаблон для повторного применения.

**Недостатки**: требуется понимание схемы объектов и написание YAML; работает с файлами, а не с каталогами; обновления живых объектов должны отражаться в файлах, иначе теряются при следующем `replace`.

## Декларативная конфигурация

Пользователь работает с файлами, но не указывает операцию — `kubectl` сам определяет для каждого объекта, нужно ли его создать, обновить или удалить. Это позволяет обрабатывать целые каталоги.

```bash
kubectl diff -f configs/
kubectl apply -f configs/
kubectl diff -R -f configs/
kubectl apply -R -f configs/
```

В основе лежит механизм трёхстороннего слияния: учитываются последняя применённая конфигурация (сохранённая в аннотации `last-applied-configuration`), текущее состояние в кластере и новый манифест. Вычисляется минимальный патч, а не полная замена объекта. Изменения, внесённые в живой объект другими источниками, сохраняются, если они не конфликтуют с новым манифестом.

**Преимущества**: безопасные обновления с сохранением сторонних изменений; автоматическое определение операции по каждому объекту; эффективная работа с каталогами; совместимость с GitOps.

**Недостатки**: сложнее отлаживать при неожиданных результатах; требуется понимание логики слияния и аннотаций; выше порог входа.

### Трёхстороннее слияние и аннотация `last-applied-configuration`

`kubectl apply` (клиентский) сохраняет предыдущую применённую конфигурацию в аннотации объекта. При следующем применении вычисляется патч между этой аннотацией, новым файлом и текущим состоянием кластера. Это позволяет не затирать поля, изменённые другими авторами, если они не входят в новый манифест. Однако если объект был создан императивной командой (без `apply`), аннотация отсутствует, и первый `apply` может повести себя неожиданно.

### Server-Side Apply (SSA)

Современная альтернатива клиентскому `apply` — серверное применение, при котором управление полями (field management) переносится на API-сервер. Вместо аннотации `last-applied-configuration` используется поле `managedFields`, отслеживающее, какой менеджер владеет каким полем.

```bash
kubectl apply -f manifest.yaml --server-side
```

SSA обеспечивает более точное обнаружение конфликтов: если два менеджера пытаются управлять одним полем, возникает конфликт, разрешаемый через `--force-conflicts` или изменение манифеста. SSA также поддерживает смену версии API в манифесте, чего клиентский apply не позволяет . Переход с клиентского apply на SSA выполняется флагом `--server-side`; по умолчанию миграция происходит без конфликтов, если поля не управлялись другими инструментами .

## Предварительная проверка изменений

### `kubectl diff`

Показывает разницу между текущим живым объектом и тем, что будет применено из файла. Вывод всегда в YAML. Код возврата: `0` — различий нет, `1` — различия есть, `>1` — ошибка .

```bash
kubectl diff -f manifest.yaml
kubectl diff -R -f configs/
```

### `--dry-run=server`

Отправляет запрос на API-сервер без сохранения объекта. Позволяет проверить валидацию, политики допуска и конфликты полей на стороне сервера до фактического применения .

```bash
kubectl apply -f manifest.yaml --dry-run=server
kubectl apply -f manifest.yaml --server-side --dry-run=server
```

## Сравнение команд по задачам

| Задача | Императивные команды | Императивная конфигурация | Декларативная конфигурация |
|---|---|---|---|
| Создание | `kubectl create deployment ...` | `kubectl create -f file.yaml` | `kubectl apply -f file.yaml` |
| Обновление | `kubectl scale`, `kubectl set image` | `kubectl replace -f file.yaml` | `kubectl apply -f file.yaml` |
| Удаление | `kubectl delete deployment ...` | `kubectl delete -f file.yaml` | `kubectl delete -f file.yaml` (или `apply --prune` в поддерживаемых версиях) |
| Просмотр изменений | Не поддерживается | Не поддерживается | `kubectl diff -f file.yaml` |
| Каталог файлов | Неудобно | Требуется перечисление | `kubectl apply -R -f dir/` |
| Откат | Сложно | Замена старым файлом | История в системе контроля версий |

## Практические рекомендации

- Перед применением всегда выполняйте `kubectl diff`, чтобы увидеть, что именно изменится.
- Для production используйте декларативный подход с хранением манифестов в Git; репозиторий выступает единственным источником достоверных данных.
- Для валидации на стороне сервера применяйте `--dry-run=server` перед фактическим `apply`.
- Не смешивайте подходы для одного объекта: если объект создан императивной командой, не управляйте им через `apply` без явного добавления аннотации (`kubectl apply --save-config` или переход на SSA).
- Для отката используйте `kubectl rollout undo` (для Deployment) и историю Git, а не ручное редактирование.
- При работе с полями, управляемыми кластером (например, `externalIPs` у LoadBalancer), декларативный подход безопаснее `replace`, так как не затирает изменения, отсутствующие в манифесте.
