API-сервер Kubernetes хранит объекты, опираясь на хранилище, совместимое с etcd (часто это сам etcd). Каждый объект сериализуется с использованием конкретной версии этого API-типа — например, представление `v1` для ConfigMap. Kubernetes использует термин **storage version** (версия хранения), чтобы описать, как объект хранится в вашем кластере.

API Kubernetes также полагается на автоматическую конвертацию: например, если у вас есть HorizontalPodAutoscaler, вы можете взаимодействовать с ним, используя любую комбинацию версий `v1` и `v2` API HorizontalPodAutoscaler. Kubernetes отвечает за конвертацию каждого API-вызова, так что клиенты не видят, какая версия фактически сериализована.

Для администраторов кластера понятие версии хранения объекта важно, поскольку именно оно связывает API-представление объекта с фактической кодировкой в бэкенде хранения. Это может быть существенно, когда важна бинарная кодировка объекта — например, для шифрования at rest или при устаревании (deprecation) API.

Один и тот же API может иметь несколько версий хранения, которые API-сервер затем конвертирует в схему объекта. **Один объект, являющийся частью этого ресурса, в любой момент времени должен иметь только одну версию хранения.** Это означает, что API-сервер знает бинарные кодировки объектов и способен динамически конвертировать между всеми хранимыми версиями и API-представлением объекта.

Версия объекта полностью отделена от версии хранения. Например, объекты API `v1alpha1` и `v1beta1` для одного и того же ресурса будут закодированы в хранилище одинаково, если версия хранения не была обновлена между этими двумя объектами.

## Соответствие версии хранения и ресурса

У каждого ресурса в любой момент времени есть **одна активная версия хранения**, то есть любая запись объекта сохранит объект в этой версии хранения. Однако версия хранения может быть обновлена, так что объекты могут храниться в разных версиях. **Один объект в любой момент времени хранится только в одной версии хранения.**

Чтения из API-сервера конвертируют сохранённые данные в API-представление объекта. Благодаря этому старые версии хранения могут существовать неограниченно долго, пока объект не обновляется. Записи, напротив, конвертируют сохранённый объект в новое представление при обновлении.

## Версии хранения для пользовательских ресурсов (Custom Resources)

Пользовательские ресурсы определяются динамически и поэтому отличаются от встроенных типов Kubernetes своей версией хранения. Встроенные объекты обычно имеют кодировку хранения, определённую отдельно от их API-типов: хранимый объект выступает как «хаб», и конкретная версия ресурса не имеет значения, кроме как поля в схеме объекта.

Однако для пользовательских ресурсов **конкретная версия ресурса должна быть задана как версия хранения**. Схема, определённая этой конкретной версией пользовательского ресурса, будет использоваться как кодировка ресурса в слое хранения. Подробнее о настройке API и версионировании см. advanced CRD featureset.

Пример CustomResourceDefinition для crontabs:

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crontabs.example.com
spec:
  group: example.com
  # список версий, поддерживаемых этим CustomResourceDefinition
  versions:
  - name: v1beta1
    # Каждая версия может быть включена/отключена флагом Served.
    served: true
    # Одна и только одна версия должна быть помечена как версия хранения.
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          host:
            type: string
          port:
            type: string
  - name: v1
    served: true
    storage: false
    schema:
      openAPIV3Schema:
        type: object
        properties:
          host:
            type: string
          port:
            type: string
          time:
            type: string
  conversion:
    strategy: None
  scope: Namespaced
  names:
    plural: crontabs
    singular: crontab
    kind: CronTab
    shortNames:
    - ct
```

Здесь `v1beta1` используется как версия хранения, то есть любые обновления или создания crontab'ов будут сохраняться со схемой объекта API `v1beta1`. В данном случае это фактически означает, что объект API `v1` **никогда не сможет сохранить поле `time`**, поскольку оно не входит в определение версии хранения. Эта схема используется в слое хранения как бинарная кодировка самого объекта. Попытка задать две версии как версию хранения одновременно считается недопустимой, поскольку это означало бы, что две схемы данных считаются допустимыми способами хранения объектов одновременно.

При изменении версии, используемой для хранения, эта версия API будет использоваться для сохранения любых новых или обновлённых CR. Просмотр (watch) или чтение (get) объекта будет возвращать объект, но лишь конвертируя его из старой версии хранения, не затрагивая сам объект. Только обновление или создание влекут эффект и используют новую версию хранения.

## Связь версий хранения с шифрованием at rest

Существуют инструменты для шифрования at-rest-хранилища кластера, особенно для секретов кластера. Это добавляет дополнительный уровень защиты от утечки данных, поскольку фактические сохранённые данные в кластере зашифрованы. Это означает, что API-сервер фактически расшифровывает данные при их извлечении из хранилища. API-сервер должен иметь ключ для этой версии хранения, чтобы правильно декодировать объект.

В этом случае версия хранения — больше, чем просто бинарная кодировка объекта. Пока сохранённые данные можно каким-либо образом конвертировать в API-объект, они могут использоваться как версия хранения.

## Миграция на другую версию хранения

Наличие нескольких версий хранения для одного ресурса может создавать проблемы для администраторов кластера. Администратор кластера не может удалить старые версии API для CRD, которые могут быть неподдерживаемыми, пока не убедится, что все объекты больше не используют связанную с ними версию хранения. При большом количестве объектов и непрозрачном представлении о том, какие из них новые, а какие всё ещё опираются на старые версии хранения, трудно определить, когда версию можно безопасно удалить. Преждевременное удаление версии может означать полную невозможность прочитать объект.

Другая важная проблема — использование ключей шифрования, как описано в разделе выше. Поскольку ресурс должен активно использоваться для обновления версии хранения, при ротации ключа и старый, и новый ключи шифрования должны оставаться в использовании, пока администратор не убедится, что все объекты были записаны хотя бы один раз. Это создаёт как риски безопасности, так и проблемы удобства использования, поскольку ключ нельзя полностью вывести из использования до этого момента.

Примеры того, как выполнить миграцию, чтобы все объекты использовали более новую версию хранения без ручного вмешательства, см. в разделе storage version migration.
