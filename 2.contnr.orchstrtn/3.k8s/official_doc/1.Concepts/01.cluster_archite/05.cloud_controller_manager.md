## Назначение и статус

`cloud-controller-manager` (CCM) — компонент плоскости управления Kubernetes, который встраивает облачно-специфичную логику управления. Он связывает кластер с API облачного провайдера и отделяет компоненты, взаимодействующие с облачной платформой, от компонентов, работающих только с кластером. Такое разделение позволяет облачным провайдерам выпускать функции независимо от основного проекта Kubernetes .

> **Статус функции**: *Beta с Kubernetes v1.11.*

CCM построен на основе плагинной архитектуры, позволяющей разным облачным провайдерам интегрировать свои платформы с Kubernetes.

## Дизайн и развёртывание

CCM работает в плоскости управления как набор реплицированных процессов (обычно контейнеры в Pod'ах). Каждый экземпляр CCM реализует несколько контроллеров в одном процессе. CCM также можно запускать как add-on Kubernetes, а не как часть плоскости управления .

**Важное изменение в современных версиях**: начиная с Kubernetes v1.31, upstream-компоненты (kubelet, kube-controller-manager) принимают только два значения флага `--cloud-provider`: пустое (без облачной интеграции) или `external` (интеграция через внешний CCM). Исторические значения вроде `aws`, `azure`, `gce` больше не действительны для встроенных провайдеров (in-tree) в текущем ядре Kubernetes. В v1.33 флаг `--cloud-provider` был полностью удалён из kube-apiserver .

При использовании внешнего CCM:
- `kube-apiserver` и `kube-controller-manager` **не должны** указывать `--cloud-provider`.
- `kubelet` должен запускаться с `--cloud-provider=external` .

Kubelet с `--cloud-provider=external` при инициализации добавляет taint `node.cloudprovider.kubernetes.io/uninitialized:NoSchedule`. Это означает, что узел требует второй инициализации от внешнего контроллера перед планированием на него рабочих нагрузок. Если CCM недоступен, новые узлы кластера останутся незапланируемыми .

## Контроллеры CCM

### Node controller

Отвечает за обновление объектов Node при создании новых серверов в облачной инфраструктуре. Получает информацию о хостах в тенанте облачного провайдера и выполняет:

- Обновление Node уникальным идентификатором сервера из облачного API.
- Аннотирование и маркировку Node облачно-специфичной информацией (регион, доступные ресурсы CPU/память).
- Получение hostname и сетевых адресов узла.
- Проверку здоровья узла: если узел не отвечает, контроллер запрашивает облачный API, не деактивирован/удалён/прекращён ли сервер. Если сервер удалён из облака, контроллер удаляет объект Node из кластера Kubernetes .

Некоторые реализации провайдеров разделяют это на node controller и отдельный node lifecycle controller.

### Route controller

Отвечает за настройку маршрутов в облаке так, чтобы контейнеры на разных узлах кластера могли взаимодействовать друг с другом. В зависимости от провайдера route controller может также выделять блоки IP-адресов для сети Pod'ов .

### Service controller

Интегрирует Service с облачными инфраструктурными компонентами: управляемыми балансировщиками нагрузки, IP-адресами, сетевой фильтрацией пакетов и проверкой здоровья целей. Service controller взаимодействует с API облачного провайдера для настройки балансировщиков и других компонентов, когда объявляется Service, требующий их .

## RBAC-права CCM

### Node controller

Требует полного доступа к чтению и изменению объектов Node (get, list, create, update, patch, watch, delete), а также patch для `nodes/status`.

### Route controller

Требует get-доступа к объектам Node для настройки маршрутов при их создании.

### Service controller

Требует list, get и watch для Service, а также patch и update для субресурса `services/status` .

### Прочее

Для работы ядра CCM требуется создание объектов Event (create, patch, update) и ServiceAccount (create). Также требуется доступ к PersistentVolumes (get, list, watch, update).

### Пример ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cloud-controller-manager
rules:
- apiGroups: [""]
  resources: ["events"]
  verbs: ["create", "patch", "update"]
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["*"]
- apiGroups: [""]
  resources: ["nodes/status"]
  verbs: ["patch"]
- apiGroups: [""]
  resources: ["services"]
  verbs: ["list", "watch"]
- apiGroups: [""]
  resources: ["services/status"]
  verbs: ["patch", "update"]
- apiGroups: [""]
  resources: ["serviceaccounts"]
  verbs: ["create"]
- apiGroups: [""]
  resources: ["persistentvolumes"]
  verbs: ["get", "list", "update", "watch"]
```

## Выбор лидера и доступность

Как и `kube-controller-manager`, CCM использует выбор лидера для обеспечения высокой доступности (включён по умолчанию). Несколько реплик CCM работают одновременно, но только одна активна .

**Известная проблема**: CCM не освобождает аренду выбора лидера при корректном завершении работы, в отличие от других controller manager'ов. Это может приводить к простою при обновлении Pod'ов CCM, особенно при больших значениях `lease-duration` (например, 137 секунд). В issue #119905 предлагается добавить опцию `ReleaseOnCancel` для сокращения времени переключения .

## Практические аспекты

### Проверка состояния узлов

```bash
# Проверить, что узлы получили providerID от CCM
kubectl get nodes -o custom-columns=NAME:.metadata.name,PROVIDER_ID:.spec.providerID,TAINTS:.spec.taints
```

Узлы с внешним CCM должны иметь заполненное поле `spec.providerID` и не иметь taint `node.cloudprovider.kubernetes.io/uninitialized` .

### Отладка

```bash
# Логи CCM (если развёрнут как Deployment/DaemonSet)
kubectl logs -n kube-system -l component=cloud-controller-manager

# Проверка прав RBAC
kubectl auth can-i update services/status \
  --as=system:serviceaccount:kube-system:cloud-controller-manager
```

### Особенности managed-кластеров

В управляемых облачных кластерах (EKS, GKE, AKS) CCM обычно управляется провайдером и может быть недоступен для прямого просмотра или изменения. Не следует внедрять флаги в worker-узлы на основе руководств для self-managed кластеров — используйте поддерживаемую конфигурацию управляемого сервиса .
