## Что очищает сборщик мусора

**Garbage collection** — собирательный термин для различных механизмов, которые Kubernetes использует для очистки ресурсов кластера. К очищаемым ресурсам относятся: завершённые Pod'ы, завершённые Job'ы, объекты без owner references, неиспользуемые контейнеры и образы, динамически выделенные PersistentVolume с политикой reclaim `Delete`, устаревшие CertificateSigningRequest, удалённые узлы (при использовании cloud controller manager) и Node Lease objects .

## Уровни сборки мусора

В Kubernetes существуют два независимых уровня GC:

1. **Уровень плоскости управления** — удаление объектов API через owner references и finalizers.
2. **Уровень узла (kubelet)** — удаление неиспользуемых контейнеров и образов на диске.

## Owner references и зависимые объекты

Многие объекты Kubernetes связаны друг с другом через **owner references**. Owner reference сообщает плоскости управления, какие объекты зависят от других. Kubernetes использует owner references, чтобы дать плоскости управления и другим API-клиентам возможность очистить связанные ресурсы перед удалением объекта. В большинстве случаев Kubernetes управляет owner references автоматически .

Owner references отличаются от механизма labels и selectors. Например, Service создаёт объекты EndpointSlice. Service использует labels, чтобы плоскость управления определяла, какие EndpointSlice относятся к этому Service. Помимо labels, каждый EndpointSlice, управляемый от имени Service, имеет owner reference. Owner references помогают разным частям Kubernetes избегать вмешательства в объекты, которые они не контролируют .

### Правила области видимости

| Зависимый объект | Владелец | Допустимо |
|---|---|---|
| Namespaced | Namespaced, тот же namespace | Да |
| Namespaced | Cluster-scoped | Да |
| Namespaced | Namespaced, другой namespace | Нет (owner reference игнорируется) |
| Cluster-scoped | Cluster-scoped | Да |
| Cluster-scoped | Namespaced | Нет (с v1.20+, unresolvable owner reference) |

**Кросс-неймспейсные owner references запрещены по дизайну**. Namespaced-зависимый объект может указывать cluster-scoped или namespaced-владельца. Namespaced-владелец должен существовать в том же namespace, что и зависимый объект. Если это не так, owner reference считается отсутствующим, и зависимый объект подлежит удалению после проверки отсутствия всех владельцев .

Cluster-scoped-зависимые объекты могут указывать только cluster-scoped-владельцев. В v1.20+, если cluster-scoped-зависимый объект указывает namespaced-тип как владельца, это считается unresolvable owner reference, и объект не может быть собран сборщиком мусора .

В v1.20+, если garbage collector обнаруживает недопустимый кросс-неймспейсный ownerReference или cluster-scoped-зависимый объект с ownerReference на namespaced-тип, генерируется предупреждающее событие с причиной `OwnerRefInvalidNamespace`. Проверить такие события можно командой:

```bash
kubectl get events -A --field-selector=reason=OwnerRefInvalidNamespace
```

## Каскадное удаление

При удалении объекта можно управлять тем, удаляет ли Kubernetes зависимые объекты автоматически. Этот процесс называется **каскадным удалением (cascading deletion)**. Существует два типа каскадного удаления .

### Foreground cascading deletion

При foreground-удалении владелец сначала переходит в состояние «удаление в процессе»:

- API-сервер устанавливает `metadata.deletionTimestamp` в момент пометки объекта на удаление.
- API-сервер также устанавливает `metadata.finalizers` в значение `foregroundDeletion`.
- Объект остаётся видимым через API до завершения процесса удаления.

После этого контроллер удаляет известные ему зависимые объекты. После удаления всех известных зависимых объектов контроллер удаляет владельца. В этот момент объект больше не виден в API .

При foreground-удалении удаление владельца блокируют только те зависимые объекты, которые имеют поле `ownerReference.blockOwnerDeletion=true` и находятся в кэше garbage collection controller. Кэш может не содержать объекты, типы ресурсов которых не удаётся успешно list/watch, или объекты, созданные одновременно с удалением владельца .

### Background cascading deletion

При background-удалении API-сервер удаляет владельца немедленно, а garbage collector controller очищает зависимые объекты в фоне. Если присутствует finalizer, он гарантирует, что объекты не будут удалены до завершения всех необходимых задач очистки. **По умолчанию Kubernetes использует background cascading deletion**, если вручную не выбрано foreground-удаление или orphan-режим .

### Orphaned dependents

При удалении владельца оставленные зависимые объекты называются **orphan objects (осиротевшими)**. По умолчанию Kubernetes удаляет зависимые объекты. Поведение можно изменить, выбрав orphan-режим .

### Практические команды

```bash
# Foreground: дождаться полной очистки зависимых
kubectl delete deployment my-app --cascade=foreground

# Background: по умолчанию
kubectl delete deployment my-app --cascade=background

# Orphan: сохранить зависимые объекты
kubectl delete deployment my-app --cascade=orphan
```

## Finalizers

Finalizers — это namespaced-ключи, которые указывают Kubernetes подождать до выполнения определённых условий, прежде чем полностью удалить помеченный на удаление ресурс. Finalizers уведомляют контроллеры о необходимости очистить ресурсы, которыми владел удаляемый объект .

Когда объект с finalizers помечается на удаление, API-сервер:

- Добавляет `metadata.deletionTimestamp` с временем начала удаления.
- Не позволяет удалить объект, пока все элементы не будут удалены из `metadata.finalizers`.
- Возвращает статус-код 202 (HTTP «Accepted»).

Контроллер, управляющий finalizer, замечает обновление и пытается выполнить требования finalizer. Когда условие выполнено, контроллер удаляет ключ из поля finalizers. Когда поле finalizers пусто, объект с установленным `deletionTimestamp` автоматически удаляется .

**Распространённый пример**: finalizer `kubernetes.io/pv-protection` предотвращает случайное удаление PersistentVolume. Пока PV используется Pod'ом, Kubernetes добавляет этот finalizer. При попытке удалить PV он переходит в статус `Terminating`, но не удаляется. Когда Pod перестаёт использовать PV, Kubernetes очищает finalizer, и том удаляется .

**Важно**: после запроса на удаление объект нельзя «воскресить» — единственный способ — удалить его и создать новый похожий объект. Не следует вручную удалять finalizers для «зависших» объектов без понимания последствий .

## Сборка мусора контейнеров и образов (kubelet)

Kubelet выполняет garbage collection неиспользуемых образов каждые пять минут и неиспользуемых контейнеров каждую минуту. **Не рекомендуется использовать внешние инструменты garbage collection**, так как они могут нарушить поведение kubelet и удалить контейнеры, которые должны существовать .

### Жизненный цикл образов контейнеров

Kubernetes управляет жизненным циклом всех образов через image manager, который является частью kubelet, при содействии cadvisor. Kubelet учитывает следующие лимиты использования диска при принятии решений о garbage collection :

- `HighThresholdPercent`
- `LowThresholdPercent`

Использование диска выше настроенного значения `HighThresholdPercent` запускает garbage collection, который удаляет образы в порядке от самого старого по времени последнего использования. Kubelet удаляет образы, пока использование диска не достигнет значения `LowThresholdPercent`.

### Максимальное время неиспользования образа

Можно указать максимальное время, в течение которого локальный образ может оставаться неиспользуемым, независимо от использования диска. Это настройка kubelet, задаваемая для каждого узла через поле `imageMaximumGCAge` в конфигурационном файле kubelet. Значение задаётся как Kubernetes duration, например `12h45m` .

**Примечание**: эта функция не отслеживает использование образов между перезапусками kubelet. Если kubelet перезапущен, отслеживаемый возраст образов сбрасывается, и kubelet будет ждать полный период `imageMaximumGCAge` до того, как образы получат право на garbage collection по возрасту .

### Сборка мусора контейнеров

Kubelet собирает неиспользуемые контейнеры на основе переменных :

| Переменная | Описание | Отключение |
|---|---|---|
| `MinAge` | Минимальный возраст, при котором kubelet может собрать контейнер | Установить в 0 |
| `MaxPerPodContainer` | Максимальное количество мёртвых контейнеров на каждый Pod | Установить < 0 |
| `MaxContainers` | Максимальное количество мёртвых контейнеров в кластере | Установить < 0 |

Kubelet также собирает неидентифицированные и удалённые контейнеры, обычно начиная с самых старых. `MaxPerPodContainer` и `MaxContainers` могут конфликтовать, если сохранение максимального количества контейнеров на Pod превышает допустимое общее количество мёртвых контейнеров. В этой ситуации kubelet корректирует `MaxPerPodContainer`: в худшем случае понижает его до 1 и вытесняет самые старые контейнеры. Контейнеры, принадлежащие удалённым Pod'ам, удаляются, когда их возраст превышает `MinAge` .

**Kubelet собирает только те контейнеры, которыми он управляет** .

## Настройка через KubeletConfiguration

Параметры GC контейнеров и образов настраиваются через конфигурационный файл kubelet (ресурс `KubeletConfiguration`). Типичные значения по умолчанию :

| Параметр | Значение по умолчанию |
|---|---|
| `imageGCHighThresholdPercent` | 85% |
| `imageGCLowThresholdPercent` | 80% |
| `minimumContainerAge` | 0 минут (все завершённые контейнеры собираются) |
| `maxPerPodContainer` | 1 |
| `maxContainers` | -1 (без глобального лимита) |

## Практические команды

```bash
# Проверить события, связанные с удалением
kubectl get events -A --field-selector reason=SuccessfulDelete

# Проверить невалидные owner references
kubectl get events -A --field-selector reason=OwnerRefInvalidNamespace

# Посмотреть финализаторы объекта (признак «зависшего» удаления)
kubectl get <resource> <name> -o jsonpath='{.metadata.finalizers}'

# Проверить использование диска на узле
kubectl top node <node-name>
```
