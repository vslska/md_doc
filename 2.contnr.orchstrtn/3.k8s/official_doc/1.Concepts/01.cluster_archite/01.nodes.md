## Что такое узел

**Узел (Node)** — это виртуальная или физическая машина, на которой Kubernetes запускает Pod'ы с контейнерами. Каждый узел управляется плоскостью управления и содержит сервисы, необходимые для запуска Pod'ов: kubelet, container runtime и, как правило, kube-proxy . В учебных или ограниченных по ресурсам средах кластер может состоять из одного узла; в production обычно используется несколько узлов.

## Способы добавления узлов в кластер

Существует два основных способа:

1. **Саморегистрация kubelet** — kubelet на узле сам регистрируется в плоскости управления (предпочтительный подход, используется большинством дистрибутивов).
2. **Ручное создание объекта Node** — администратор создаёт объект `Node` через `kubectl` .

После создания объекта Node или саморегистрации kubelet плоскость управления проверяет валидность нового объекта. Если узел здоров (все необходимые сервисы работают), он может принимать Pod'ы. В противном случае узел игнорируется для любой кластерной активности, пока не станет здоровым .

> [!TIP] **Важно**: 
 Kubernetes сохраняет объект невалидного Node и продолжает проверять его здоровье. Чтобы прекратить эти проверки, необходимо явно удалить объект Node. Имя объекта Node должно быть валидным DNS-поддоменом (RFC 1123 subdomain) .


## Уникальность имени узла

Имя идентифицирует Node. Два узла не могут одновременно иметь одинаковое имя. Kubernetes также предполагает, что ресурс с одинаковым именем — это один и тот же объект. Для Node это означает неявное предположение, что экземпляр с тем же именем будет иметь то же состояние (например, сетевые настройки, содержимое корневого диска) и атрибуты вроде меток узла. Это может привести к несогласованности, если экземпляр был изменён без изменения имени .

Если узел нужно заменить или существенно обновить, существующий объект Node необходимо сначала удалить из API-сервера, а затем добавить заново после обновления .

## Саморегистрация узлов

При флаге kubelet `--register-node=true` (значение по умолчанию) kubelet пытается зарегистрироваться в API-сервере. Для саморегистрации kubelet запускается со следующими опциями :

| Флаг | Назначение |
|---|---|
| `--kubeconfig` | Путь к учётным данным для аутентификации в API-сервере |
| `--cloud-provider` | Способ взаимодействия с облачным провайдером для чтения метаданных о себе |
| `--register-node` | Автоматическая регистрация в API-сервере |
| `--register-with-taints` | Регистрация узла с заданным списком taints (через запятую, `<key>=<value>:<effect>`). Не действует, если `register-node` = false |
| `--node-ip` | Необязательный список IP-адресов узла через запятую. Можно указать только один адрес для каждого семейства адресов |
| `--node-labels` | Метки, добавляемые при регистрации узла |
| `--node-status-update-frequency` | Частота публикации статуса узла в API-сервере |

Когда включены режим авторизации Node и admission-плагин NodeRestriction, kubelet имеет право создавать и изменять только свой собственный ресурс Node .

**Критически важно**: метки, заданные через `--node-labels`, применяются **только при регистрации**. Если перезапустить kubelet с новым набором `--node-labels`, но использовать то же имя Node, изменения не вступят в силу. При необходимости обновления конфигурации узла рекомендуется перерегистрировать узел. Это также гарантирует, что все Pod'ы будут вытеснены и корректно перепланированы .

## Ручное управление узлами

Объекты Node можно создавать и изменять через `kubectl`. Для ручного создания объектов Node флаг kubelet `--register-node` устанавливается в `false`. Объекты Node можно изменять независимо от настройки `--register-node`: например, устанавливать метки на существующем узле или помечать его как unschedulable .

Роли узлов задаются добавлением одной или нескольких меток `node-role.kubernetes.io/<role>: <role>`, где `<role>` ограничен правилами синтаксиса меток. Kubernetes игнорирует значение метки для ролей узлов; по соглашению можно установить то же значение, что и роль в ключе метки .

**Пометка узла как unschedulable** (cordon) предотвращает размещение новых Pod'ов планировщиком, но не влияет на существующие Pod'ы. Это полезно как подготовительный шаг перед перезагрузкой или обслуживанием узла:

```bash
kubectl cordon $NODENAME
```

Pod'ы, входящие в DaemonSet, терпят запуск на unschedulable-узле. DaemonSet'ы обычно предоставляют локальные для узла сервисы, которые должны работать, даже если узел вытесняется от рабочих нагрузок приложений .

## Статус узла

Статус Node содержит следующую информацию: адреса (Addresses), условия (Conditions), ёмкость и allocatable (Capacity and Allocatable), информация (Info). Просмотр статуса:

```bash
kubectl describe node <node-name>
```

### Условия узла (Node Conditions)

| Условие | Описание |
|---|---|
| `Ready` | `True` — узел здоров и готов принимать Pod'ы; `False`/`Unknown` — не готов |
| `MemoryPressure` | Нехватка памяти на узле |
| `DiskPressure` | Нехватка места на диске |
| `PIDPressure` | Слишком много процессов |
| `NetworkUnavailable` | Проблемы с сетевым плагином |

При проблемах Kubernetes добавляет автоматические taints, чтобы планировщик не размещал новые Pod'ы: `node.kubernetes.io/not-ready:NoSchedule` и `node.kubernetes.io/unreachable:NoExecute` .

## Heartbeats узлов

Kubernetes использует два механизма для отслеживания доступности узлов:

1. **Обновления `.status` Node** — kubelet периодически отправляет полный статус узла в API-сервер.
2. **Объекты Lease в namespace `kube-node-lease`** — для каждого Node существует связанный объект Lease. Каждый heartbeat kubelet — это update-запрос к объекту Lease, обновляющий поле `spec.renewTime`. Плоскость управления использует временную метку этого поля для определения доступности узла .

Использование Lease-объектов легче для etcd при большом количестве узлов, чем полные обновления статуса.

## Node Controller

Node controller — компонент плоскости управления, управляющий различными аспектами жизненного цикла узлов :

- **Назначение CIDR-блока** узлу при регистрации (если включено назначение CIDR).
- **Синхронизация с облачным провайдером**: при работе в облаке и недоступности узла контроллер запрашивает у провайдера, доступна ли VM для этого узла; если нет — удаляет узел из своего списка.
- **Мониторинг здоровья**: если узел становится недоступным, обновляет условие `Ready` в статусе Node на `Unknown`. Если узел остаётся недоступным, инициирует eviction всех Pod'ов на недоступном узле. По умолчанию контроллер ждёт 5 минут между пометкой узла как `Unknown` и отправкой первого запроса на eviction .

По умолчанию node controller проверяет состояние каждого узла каждые 5 секунд (настраивается флагом `--node-monitor-period` на **kube-controller-manager**) .

### Ограничения скорости eviction

В большинстве случаев node controller ограничивает скорость eviction значением `--node-eviction-rate` (по умолчанию 0.1) в секунду — не более 1 узла за 10 секунд .

Поведение меняется, когда узел в данной зоне доступности становится нездоровым. Контроллер проверяет долю нездоровых узлов в зоне одновременно :

- Если доля нездоровых узлов не менее `--unhealthy-zone-threshold` (по умолчанию 0.55), скорость eviction снижается.
- Если кластер мал (≤ `--large-cluster-size-threshold` узлов, по умолчанию 50), eviction останавливается.
- Иначе скорость снижается до `--secondary-node-eviction-rate` (по умолчанию 0.01) в секунду.

Эти политики реализованы per availability zone, поскольку одна зона может стать изолированной от плоскости управления, пока другие остаются связанными. Если кластер не охватывает несколько зон доступности облачного провайдера, механизм eviction не учитывает недоступность per-zone .

Если все узлы в зоне нездоровы, node controller эвиктит с нормальной скоростью `--node-eviction-rate`. Особый случай — когда все зоны полностью нездоровы (ни один узел в кластере не здоров): контроллер предполагает проблему с connectivity между плоскостью управления и узлами и не выполняет eviction .

Node controller также отвечает за eviction Pod'ов на узлах с taints `NoExecute`, если эти Pod'ы не терпят данный taint, и добавляет taints, соответствующие проблемам узла (unreachable, not ready) .

## Отслеживание ресурсов

Объекты Node отслеживают информацию о ёмкости ресурсов: доступный объём памяти, количество CPU и т.д. Узлы, регистрирующиеся самостоятельно, сообщают свою ёмкость при регистрации. При ручном добавлении Node необходимо установить информацию о ёмкости при добавлении .

Планировщик Kubernetes гарантирует наличие достаточных ресурсов для всех Pod'ов на узле: он проверяет, что сумма requests контейнеров на узле не превышает ёмкость узла. Эта сумма включает все контейнеры, управляемые kubelet, но исключает контейнеры, запущенные напрямую container runtime, и процессы вне контроля kubelet .

| Понятие | Описание |
|---|---|
| **Capacity** | Физические ресурсы узла (всё, что есть) |
| **Allocatable** | Ресурсы, доступные для Pod'ов (Capacity минус системные резервы) |

Для явного резервирования ресурсов для процессов, не являющихся Pod'ами, используется резервирование ресурсов для system daemons .

## Топология узлов

Функция Topology Manager стабильна с Kubernetes 1.27 (feature gate удалён). При включённом TopologyManager kubelet может использовать topology hints при принятии решений о назначении ресурсов. Это позволяет учитывать топологию оборудования (NUMA, GPU, NIC) при распределении ресурсов Pod'ам .

## Практические команды

```bash
# Просмотр узлов
kubectl get nodes -o wide

# Детальный статус узла
kubectl describe node <node-name>

# Пометить узел как unschedulable (без удаления Pod'ов)
kubectl cordon <node-name>

# Безопасно вытеснить Pod'ы с узла перед обслуживанием
kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data

# Вернуть узел в строй
kubectl uncordon <node-name>

# Проверка Lease-объектов (heartbeats)
kubectl get lease -n kube-node-lease
```
