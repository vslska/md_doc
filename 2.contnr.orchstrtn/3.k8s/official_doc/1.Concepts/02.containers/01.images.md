# Образы контейнеров в Kubernetes

>Образ контейнера представляет собой исполняемый пакет, содержащий приложение и все необходимые зависимости. Имя образа формируется по стандарту: `[registry/]name[:tag|@digest]`, параметр `imagePullPolicy` определяет стратегию загрузки (`Always`, `IfNotPresent`, `Never`), а для работы с закрытыми репозиториями используются `imagePullSecrets` или провайдеры учетных данных. В production-средах рекомендуется использовать `digest` вместо тега `:latest`.

## Именование образов

### Формат именования

Структура ссылки на образ имеет следующий вид:

```
[<registry>/][<namespace>/]<name>[:<tag>|@<digest>]
```

### Примеры и интерпретация

- `busybox` преобразуется в `docker.io/library/busybox:latest` (публичный Docker Hub, тег latest).
- `busybox:1.32.0` соответствует `docker.io/library/busybox:1.32.0`.
- `registry.k8s.io/pause:3.5` указывает на кастомный registry с конкретным тегом.
- `registry.k8s.io/pause@sha256:1ff6c18...` ссылается по **digest** (неизменяемый идентификатор).
- `registry.k8s.io/pause:3.5@sha256:1ff6c18...` содержит тег и digest одновременно (приоритет имеет digest).
- `fictional.registry.example:10443/imagename` использует сторонний registry с нестандартным портом.

### Сравнение Tag и Digest

|**Характеристика**|**Tag**|**Digest**|
|---|---|---|
|**Формат**|`:v1.42.0`, `:latest`|`@sha256:1ff6c18...`|
|**Изменяемость**|Может изменяться (перемещаться на другую версию)|Неизменяемый идентификатор|
|**Идентификация**|Логическая версия|Конкретное содержимое (криптографический хеш)|
|**Production**|Рискованно (допустимо только для семантических версий)|Рекомендуется для обеспечения стабильности|
|**Откат**|Затруднен при перезаписи тегов|Абсолютная точность и воспроизводимость отката|

### Правила формирования тегов

- Максимальная длина тега составляет 128 символов.
- Допустимый шаблон символов: `[a-zA-Z0-9_][a-zA-Z0-9._-]{0,127}`.
- При отсутствии тега автоматически подразумевается `:latest`.

## Политика загрузки imagePullPolicy

### Режимы загрузки образов

| **Значение**       | **Поведение**                                                                                   | **Когда использовать**                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **`IfNotPresent`** | Загружать образ только при его отсутствии в локальном кэше узла                                 | Production-окружения (значение по умолчанию для тегов, отличных от `latest`) |
| **`Always`**       | Всегда запрашивать реестр для проверки актуальности образа (даже если он присутствует локально) | Разработка, использование тега `:latest`, частые обновления                  |
| **`Never`**        | Никогда не инициировать загрузку из сети, использовать исключительно локальный образ            | Автономные среды (offline), предварительно загруженные образы                |

 
### Автоматическое назначение imagePullPolicy

Если параметр `imagePullPolicy` не указан явно в манифесте, `kubelet` присваивает его автоматически по следующим правилам:

|**Условие**|**Автоматически назначаемое значение**|
|---|---|
|Указан **digest** (`@sha256:...`)|`IfNotPresent`|
|Указан тег **`:latest`**|`Always`|
|Тег **не указан**|`Always`|
|Указан тег, отличный от `:latest` (например, `:v1.42.0`)|`IfNotPresent`|

> **Важно**: Параметр `imagePullPolicy` фиксируется один раз в момент создания объекта. Последующее изменение тега на `:latest` в запущенном ресурсе не приводит к автоматическому пересмотру политики загрузки.

### Пример конфигурации

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
  - name: app
    image: my-registry.example.com/my-app:v1.42.0
    imagePullPolicy: IfNotPresent
```

## Диагностика ошибок ImagePullBackOff

Статус `ImagePullBackOff` присваивается контейнеру, когда `kubelet` не может успешно загрузить указанный образ.

### Основные причины

- Ошибки в наименовании образа, опечатки в адресе реестра или теге.
- Использование закрытого (приватного) реестра без предоставления учетных данных (`imagePullSecrets`).
- Проблемы с сетевым доступом, разрешением имен DNS или блокировки межсетевым экраном.
- Фактическое отсутствие образа в целевом репозитории.

### Логика повторных попыток

- Kubernetes увеличивает интервал ожидания между попытками скачивания по принципу экспоненциальной задержки (exponential backoff).
- Максимальная задержка ограничена **300 секундами (5 минутами)**.

### Команды для отладки

```bash
# Просмотр событий пода для выявления ошибок загрузки
kubectl describe pod my-app | grep -A10 'Events:'

# Проверка статуса контейнера
kubectl get pod my-app -o jsonpath='{.status.containerStatuses[0].state}'

# Проверка привязки секретов аутентификации к поду
kubectl get pod my-app -o jsonpath='{.spec.imagePullSecrets}'

# Проверка содержимого секрета
kubectl get secret my-registry-secret -o yaml
```

## Параллельная загрузка образов

По умолчанию `kubelet` выполняет загрузку образов последовательно. Для ускорения развертывания можно включить параллельный режим на уровне конфигурации демона:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
serializeImagePulls: false              # Включение параллельной загрузки
maxParallelImagePulls: 5                # Ограничение максимального числа параллельных потоков загрузки
```

### Ограничения

- Параллелизация работает между разными подами, но образы инициализирующих (`init`) и основных (`app`) контейнеров внутри одного пода не загружаются параллельно между собой.
- Значение `maxParallelImagePulls` требует отключения последовательной загрузки (`serializeImagePulls: false`).

## Мультиархитектурные образы (Multi-arch images / Image index)

Мультиархитектурные образы объединяют варианты одного приложения для различных аппаратных платформ (`amd64`, `arm64` и др.) под единым именем. `kubelet` автоматически распознает архитектуру хоста и запрашивает соответствующий манифест.

```yaml
containers:
- name: pause
  image: registry.k8s.io/pause:3.5    # Автоматический выбор совместимой архитектуры узла
```

## Аутентификация в приватных реестрах (Private Registries)

### Доступные методы аутентификации

| **Способ**                              | **Область действия**      | **Когда использовать**                                        |
| --------------------------------------- | ------------------------- | ------------------------------------------------------------- |
| **1. imagePullSecrets** (рекомендуется) | Уровень пода (Pod-level)  | Стандартный подход, обеспечивающий гибкость                   |
| **2. Node-level credentials**           | Уровень узла (Node-level) | Предоставление доступа ко всем образам для всех подов на узле |
| **3. Credential provider plugin**       | Уровень узла (Node-level) | Динамическое получение учетных данных через внешние плагины   |
| **4. Preloaded images**                 | Уровень узла (Node-level) | Использование заранее загруженных на узел образов             |
| **5. Cloud-specific extensions**        | Уровень узла (Node-level) | Интеграция с облачными реестрами AWS ECR, GCP GCR, Azure ACR  |

## Использование imagePullSecrets

### Создание секрета

```bash
# Способ 1: через командную строку kubectl
kubectl create secret docker-registry my-registry-secret \
  --docker-server=my-registry.example.com \
  --docker-username=myuser \
  --docker-password=mypassword \
  --docker-email=myemail@example.com \
  --namespace=my-namespace

# Способ 2: на основе существующего файла конфигурации Docker
kubectl create secret docker-registry my-registry-secret \
  --from-file=.dockerconfigjson=/home/user/.docker/config.json \
  --namespace=my-namespace
```

### Подключение в манифесте пода

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: my-namespace
spec:
  containers:
  - name: app
    image: my-registry.example.com/my-app:v1.42.0
  imagePullSecrets:
  - name: my-registry-secret    # Ссылка на секрет в том же пространстве имен
```

### Автоматизация через ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: default
  namespace: my-namespace
imagePullSecrets:
  - name: my-registry-secret
```

Привязка секрета к `ServiceAccount` позволяет автоматически применять его ко всем новым подам в пределах пространства имен.

## Аутентификация на уровне узла (Node-level credentials)

Конфигурация выполняется путем авторизации в системе контейнеризации непосредственно на хосте и размещения файла конфигурации (`~/.docker/config.json`) на всех узлах кластера. Данный метод требует административного доступа к нодам и не подходит для динамических инфраструктур с автоматическим масштабированием.

---
## Плагины провайдеров учетных данных (Credential Provider Plugin)

Механизм позволяет динамически запрашивать учетные данные у облачных провайдеров через метаданные и IAM. Конфигурация описывается в `KubeletConfiguration`:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
imageCredentialProviderConfig:
  - registryMatch: "*.dkr.ecr.*.amazonaws.com"
    credentialProvider: /usr/local/bin/ecr-credential-provider
  - registryMatch: "gcr.io"
    credentialProvider: /usr/local/bin/gcr-credential-provider
```

---
## Предзагруженные образы (Preloaded Images)

Образы могут быть предварительно скачаны на физические узлы заранее. В манифестах для таких контейнеров указывается политика `imagePullPolicy: IfNotPresent` или `Never`.

Для проверки учетных данных локальных образов начиная с версии `v1.35` применяется политика верификации в `KubeletConfiguration`:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
imagePullCredentialsVerificationPolicy: AlwaysVerify
```

## Интерпретация файла config.json и шаблоны Wildcard

В отличие от стандартного Docker, Kubernetes поддерживает использование подстановочных символов (wildcard patterns) в конфигурационных файлах реестров:

```json
{
  "auths": {
    "my-registry.example.com": { "auth": "..." },
    "*.my-registry.example.com": { "auth": "..." },
    "*.kubernetes.io": { "auth": "..." }
  }
}
```

Символ `*` должен соответствовать ровно одному уровню поддомена, наличие точки обязательно.

---
## Контроллер доступа AlwaysPullImages

Плагин `AlwaysPullImages` принудительно переопределяет параметр `imagePullPolicy` на значение `Always` для всех создаваемых подов в кластере. Это повышает безопасность в средах с несколькими арендаторами, гарантируя актуальность загружаемых версий, но увеличивает нагрузку на реестр и время запуска приложений.

---
## Инженерные рекомендации (Best Practices)

- Использовать хэш-сумму (`digest`) вместо тега `:latest` для критических production-нагрузок: `image: [my-registry.example.com/my-app@sha256:1ff6c18](https://my-registry.example.com/my-app@sha256:1ff6c18)...`.
- Применять строгое семантическое версионирование для тегов образов (`:v1.42.0`).
- Использовать `imagePullSecrets` для работы с изолированными приватными реестрами.
- Настраивать автоматическое добавление секретов через `ServiceAccount`.
- Включать параллельную загрузку образов для оптимизации времени холодного старта подов.
- Организовывать мониторинг и системные оповещения при возникновении статуса `ImagePullBackOff`.

## Типовые сценарии устранения неполадок (Troubleshooting)

### Устранение ошибки ImagePullBackOff

1. Проверить корректность имени образа и тега в манифесте.
2. Проверить наличие и правильность привязки `imagePullSecrets`.
3. Убедиться в сетевой доступности внешнего или внутреннего реестра с помощью диагностических утилит.
4. Проверить журналы работы `kubelet` для выявления системных ошибок авторизации.

### Обновление недействительных учетных данных

```bash
# Удаление устаревшего секрета
kubectl delete secret my-registry-secret

# Пересоздание секрета с актуальными данными
kubectl create secret docker-registry my-registry-secret \
  --docker-server=my-registry.example.com \
  --docker-username=myuser \
  --docker-password=mypassword

# Пересоздание зависимого пода для применения новых параметров
kubectl delete pod my-app
kubectl apply -f pod.yaml
```
