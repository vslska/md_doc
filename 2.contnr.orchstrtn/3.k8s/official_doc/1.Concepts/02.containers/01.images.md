## Что такое образ

Образ контейнера представляет собой двоичные данные, инкапсулирующие приложение и все его программные зависимости. Это исполняемые программные пакеты, которые могут работать автономно и делают чётко определённые предположения о своей среде выполнения. Обычно образ создаётся и помещается в реестр до того, как на него ссылаются в Pod'е .

## Имена образов

Имя образа может включать хост реестра и порт: `fictional.registry.example:10443/imagename`. Если хост реестра не указан, Kubernetes использует публичный реестр Docker; это поведение можно изменить настройкой реестра по умолчанию в конфигурации container runtime .

После имени можно указать **тег** или **дайджест**. Теги идентифицируют разные версии одной серии образов; дайджесты — уникальный неизменяемый идентификатор конкретной версии, хеш содержимого образа. Теги можно перемещать на другие образы, дайджесты фиксированы .

Тег состоит из строчных и заглавных букв, цифр, подчёркиваний, точек и дефисов, до 128 символов, по шаблону `[a-zA-Z0-9_][a-zA-Z0-9._-]{0,127}`. Если тег не указан, подразумевается `latest`. Дайджест состоит из алгоритма хеширования (например, `sha256`) и значения хеша .

| Пример | Интерпретация |
|---|---|
| `busybox` | `docker.io/library/busybox:latest` |
| `busybox:1.32.0` | `docker.io/library/busybox:1.32.0` |
| `registry.k8s.io/pause:3.5` | Кастомный реестр, тег `3.5` |
| `registry.k8s.io/pause@sha256:1ff6c18...` | Кастомный реестр, дайджест |
| `registry.k8s.io/pause:3.5@sha256:1ff6c18...` | Тег и дайджест; для pull используется только дайджест |

**Для production не рекомендуется использовать тег `:latest`**: сложнее отследить, какая версия образа работает, и труднее корректно откатиться. Вместо этого указывайте осмысленный тег (например, `v1.42.0`) и/или дайджест. Указание образа по дайджесту фиксирует код: изменение в реестре не приведёт к смешиванию версий .

## Политика загрузки образов (imagePullPolicy)

Значение `imagePullPolicy` и тег образа влияют на то, когда kubelet пытается загрузить образ :

| Значение | Поведение |
|---|---|
| **IfNotPresent** | Образ загружается только если его нет локально |
| **Always** | Kubelet запрашивает container runtime загрузить образ; runtime обращается к реестру, разрешает тег или имя в дайджест и скачивает отсутствующие слои. Если все слои уже есть, используется кэш |
| **Never** | Kubelet не пытается загрузить образ; если образа нет локально, запуск завершается ошибкой |

### Автоматическое назначение imagePullPolicy

Если поле `imagePullPolicy` не указано, кластер устанавливает его при соблюдении определённых условий :

| Условие | Назначаемое значение |
|---|---|
| Указан дайджест | `IfNotPresent` |
| Тег `:latest` | `Always` |
| Тег не указан | `Always` |
| Тег, отличный от `:latest` | `IfNotPresent` |

**Важно**: значение `imagePullPolicy` устанавливается при первом создании объекта и **не обновляется** при последующем изменении тега или дайджеста. Если создать Deployment с тегом не `:latest`, а затем обновить образ на `:latest`, политика не изменится на `Always` — её нужно менять вручную .

### Принудительная загрузка

Чтобы всегда принудительно загружать образ, можно установить `imagePullPolicy: Always`, использовать тег `:latest` без указания политики, не указывать тег вовсе или включить admission-контроллер `AlwaysPullImages` .

## ImagePullBackOff

Статус `ImagePullBackOff` означает, что контейнер не смог запуститься, потому что Kubernetes не смог загрузить образ (неверное имя, приватный реестр без `imagePullSecret` и т.п.). Часть `BackOff` указывает, что Kubernetes продолжит попытки с увеличивающейся задержкой. Задержка растёт до скомпилированного предела — **300 секунд (5 минут)** .

## Параллельная загрузка образов

По умолчанию kubelet загружает образы последовательно: только один запрос к image service за раз. Узлы принимают решения о загрузке изолированно; два разных узла могут загружать один образ параллельно .

Для включения параллельной загрузки установите `serializeImagePulls: false` в конфигурации kubelet. При этом можно ограничить число одновременных загрузок через `maxParallelImagePulls` (стабильно с v1.35). Kubelet **никогда не загружает параллельно несколько образов для одного Pod'а**: образы init-контейнера и основного контейнера одного Pod'а не загружаются параллельно, но образы для разных Pod'ов — могут .

## Мультиархитектурные образы

Реестр может предоставлять **image index**, который указывает на несколько манифестов образов для архитектурно-специфичных версий. Идея в том, чтобы иметь одно имя образа (например, `pause`) и позволять разным системам получать нужный бинарный образ для своей архитектуры. Kubernetes обычно создаёт образы с суффиксом `-$(ARCH)` для обратной совместимости .

## Приватные реестры: способы аутентификации

Приватные реестры могут требовать аутентификации для обнаружения и/или загрузки образов. Учётные данные можно предоставить несколькими способами :

| Способ | Область действия |
|---|---|
| **imagePullSecrets** в Pod'е | Только Pod'ы, предоставившие свои ключи |
| **Настройка узлов** для аутентификации | Все Pod'ы на узле; требует конфигурации администратором |
| **Kubelet credential provider plugin** | Динамическое получение учётных данных через плагин |
| **Pre-pulled images** | Все Pod'ы используют кэшированные на узле образы; требует root-доступа |
| **Vendor-specific расширения** | Зависит от облачного провайдера |

### imagePullSecrets (рекомендуемый подход)

Все `imagePullSecrets` должны быть Secret'ами в том же namespace, что и Pod, типа `kubernetes.io/dockercfg` или `kubernetes.io/dockerconfigjson` .

```bash
kubectl create secret docker-registry <name> \
  --docker-server=<registry> \
  --docker-username=<user> \
  --docker-password=<password> \
  --docker-email=<email>
```

```yaml
spec:
  containers:
  - name: foo
    image: janedoe/awesomeapp:v1
  imagePullSecrets:
  - name: myregistrykey
```

Секрет можно привязать к ServiceAccount, чтобы автоматически применять его ко всем новым Pod'ам в namespace .

### Kubelet credential provider plugin

Плагин позволяет kubelet динамически запрашивать учётные данные для реестра. Это наиболее надёжный и универсальный способ для приватных реестров, но требует настройки на уровне kubelet. Особенно полезен для статических Pod'ов, которые не могут ссылаться на другие API-ресурсы (ServiceAccount, Secret) в своей спецификации .

### Pre-pulled images

Подход подходит, если есть контроль над конфигурацией узлов, но **не работает надёжно**, если облачный провайдер управляет узлами и заменяет их автоматически. При `imagePullPolicy: IfNotPresent` или `Never` используется локальный образ. Если полагаться на pre-pulled образы как замену аутентификации, необходимо убедиться, что все узлы кластера имеют одинаковые предзагруженные образы .

### Верификация учётных данных для образов

**Статус**: Beta с Kubernetes v1.35; включено по умолчанию .

При включённом feature gate `KubeletEnsureSecretPulledImages` Kubernetes проверяет учётные данные для каждого образа, требующего аутентификации, даже если образ уже присутствует на узле. Поведение контролируется полем `imagePullCredentialsVerificationPolicy` в конфигурации kubelet: `NeverVerify`, `NeverVerifyPreloadedImages` (по умолчанию), `NeverVerifyAllowListedImages`, `AlwaysVerify` .

## Интерпретация config.json

Kubernetes поддерживает glob-паттерны в `auths` файла `config.json`, в отличие от Docker, который допускает только корневые URL. Ограничение: glob-паттерны (`*`) должны включать точку для каждого поддомена, количество совпадающих поддоменов должно быть равно количеству паттернов `*.` :

- `*.kubernetes.io` соответствует `abc.kubernetes.io`, но не `kubernetes.io`.
- `*.*.kubernetes.io` соответствует `abc.def.kubernetes.io`, но не `abc.kubernetes.io`.

Kubelet выполняет загрузку последовательно для каждой найденной учётной записи; при наличии нескольких записей для разных путей возможно несколько источников аутентификации .

## AlwaysPullImages admission controller

Принудительно переопределяет `imagePullPolicy` на `Always` для всех новых Pod'ов. Полезен в multitenant-кластерах: без него любой Pod может использовать приватный образ, уже загруженный на узел, просто зная его имя, без проверки авторизации. С контроллером образ всегда загружается перед запуском контейнеров, что требует действительных учётных данных .
