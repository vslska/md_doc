## Общая модель

В Kubernetes `VolumeSnapshot` представляет снимок тома в системе хранения. Подобно тому как API-ресурсы `PersistentVolume` и `PersistentVolumeClaim` используются для создания томов, ресурсы `VolumeSnapshotContent` и `VolumeSnapshot` используются для создания снимков томов.

**`VolumeSnapshotContent`** — снимок тома в кластере, созданный администратором. Это ресурс кластера, как и `PersistentVolume`.

**`VolumeSnapshot`** — запрос снимка тома от пользователя. Аналогичен `PersistentVolumeClaim`.

**`VolumeSnapshotClass`** позволяет указать различные атрибуты, принадлежащие `VolumeSnapshot`. Эти атрибуты могут различаться для снимков, сделанных с одного тома в системе хранения, и поэтому не могут быть выражены через тот же `StorageClass`, что и `PersistentVolumeClaim`.

Снимки томов дают пользователям стандартизированный способ копирования содержимого тома на определённый момент времени без создания полностью нового тома. Это позволяет, например, администраторам баз данных делать резервные копии перед изменениями.

## Важные предварительные условия

- **API-объекты `VolumeSnapshot`, `VolumeSnapshotContent`, `VolumeSnapshotClass` — это CRD**, а не часть core API.
- **Поддержка `VolumeSnapshot` доступна только для CSI-драйверов**.
- В рамках развёртывания `VolumeSnapshot` команда Kubernetes предоставляет **snapshot controller** (развёртывается в плоскости управления) и sidecar-контейнер **`csi-snapshotter`** (развёртывается вместе с CSI-драйвером). Snapshot controller следит за объектами `VolumeSnapshot` и `VolumeSnapshotContent` и отвечает за создание и удаление `VolumeSnapshotContent`. Sidecar `csi-snapshotter` следит за `VolumeSnapshotContent` и запускает операции `CreateSnapshot` и `DeleteSnapshot` против CSI-эндпоинта.
- Также есть **validating webhook server**, обеспечивающий строгую валидацию объектов снимков. Он должен устанавливаться дистрибутивами Kubernetes вместе со snapshot controller и CRD, а не CSI-драйверами, и должен быть установлен во всех кластерах с включённой функцией снимков.
- CSI-драйверы могут **не иметь** реализации функциональности снимков. CSI-драйверы с поддержкой снимков, вероятно, используют `csi-snapshotter`.
- **Установка CRD и snapshot controller — ответственность дистрибутива Kubernetes**.

Для продвинутых случаев (например, групповые снимки нескольких томов) см. внешнюю документацию CSI Volume Group Snapshot.

В кластерах, где снимок доступен только из части кластера (например, снимок тома в одной зоне multi-zone кластера без общего хранилища), топология снимка может быть записана и учтена при восстановлении из него.

## Жизненный цикл VolumeSnapshot и VolumeSnapshotContent

`VolumeSnapshotContent` — ресурсы кластера. `VolumeSnapshot` — запросы на эти ресурсы.

### Provisioning (создание снимка)

**Pre-provisioned**: администратор кластера создаёт несколько `VolumeSnapshotContent` с деталями реального снимка на системе хранения, доступного пользователям кластера. Они существуют в API Kubernetes и доступны для потребления.

**Dynamic**: вместо использования заранее существующего снимка можно запросить динамическое создание снимка из `PersistentVolumeClaim`. `VolumeSnapshotClass` указывает параметры, специфичные для провайдера хранения.

### Binding (связывание)

Snapshot controller обрабатывает связывание объекта `VolumeSnapshot` с подходящим `VolumeSnapshotContent` в обоих сценариях — pre-provisioned и dynamically provisioned. Связывание — это отображение **один-к-одному**. В случае pre-provisioned связывания `VolumeSnapshot` останется несвязанным, пока не будет создан запрошенный `VolumeSnapshotContent`.

### Защита PersistentVolumeClaim как источника снимка

Цель этой защиты — гарантировать, что используемые `PersistentVolumeClaim` не удаляются из системы во время создания снимка (это может привести к потере данных). Пока снимок создаётся с `PersistentVolumeClaim`, этот claim считается используемым. При удалении используемого claim'а как источника снимка удаление откладывается до того, как снимок станет `readyToUse` или будет `aborted`.

### Delete (удаление)

Удаление запускается удалением объекта `VolumeSnapshot`, и затем соблюдается `DeletionPolicy`. Если `DeletionPolicy` — `Delete`, нижележащий снимок в хранилище удаляется вместе с объектом `VolumeSnapshotContent`. Если `DeletionPolicy` — `Retain`, и снимок, и `VolumeSnapshotContent` сохраняются.

## VolumeSnapshot

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: new-snapshot-test
spec:
  volumeSnapshotClassName: csi-hostpath-snapclass
  source:
    persistentVolumeClaimName: pvc-test
```

`persistentVolumeClaimName` — имя `PersistentVolumeClaim` — источника данных для снимка. Это поле **обязательно** для динамического создания снимка.

Снимок может запросить конкретный класс через `volumeSnapshotClassName`. Если ничего не установлено, используется класс по умолчанию, если доступен.

Для **pre-provisioned снимков** необходимо указать `volumeSnapshotContentName` как источник:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: test-snapshot
spec:
  source:
    volumeSnapshotContentName: test-content
```

Поле `volumeSnapshotContentName` **обязательно** для pre-provisioned снимков.

## VolumeSnapshotContent

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotContent
metadata:
  name: snapcontent-72d9a349-aacd-42d2-a240-d775650d2455
spec:
  deletionPolicy: Delete
  driver: hostpath.csi.k8s.io
  source:
    volumeHandle: ee0cfb94-f8d4-11e9-b2d8-0242ac110002
  sourceVolumeMode: Filesystem
  volumeSnapshotClassName: csi-hostpath-snapclass
  volumeSnapshotRef:
    name: new-snapshot-test
    namespace: default
    uid: 72d9a349-aacd-42d2-a240-d775650d2455
```

- **`volumeHandle`** — уникальный идентификатор тома, созданного на бэкенде хранения и возвращённого CSI-драйвером при создании тома. **Обязательно** для динамического создания снимка.
- **`sourceVolumeMode`** — режим тома, с которого делается снимок. Значение может быть `Filesystem` или `Block`. Если не указан, Kubernetes обрабатывает снимок так, как если бы режим исходного тома был неизвестен.
- **`volumeSnapshotRef`** — ссылка на соответствующий `VolumeSnapshot`. При создании `VolumeSnapshotContent` как pre-provisioned снимка `VolumeSnapshot`, указанный в `volumeSnapshotRef`, может ещё не существовать.

Для **pre-provisioned снимков** администратор создаёт `VolumeSnapshotContent` с полем `snapshotHandle` — уникальным идентификатором снимка, созданного на бэкенде хранения. **Обязательно** для pre-provisioned снимков; указывает CSI snapshot id на системе хранения, который представляет этот `VolumeSnapshotContent`.

## Преобразование режима тома снимка

Если API `VolumeSnapshots`, установленный в кластере, поддерживает поле `sourceVolumeMode`, API имеет возможность предотвратить преобразование режима тома неавторизованными пользователями. Проверить поддержку можно командой:

```bash
kubectl get crd volumesnapshotcontent -o yaml
```

Чтобы разрешить создание `PersistentVolumeClaim` из существующего `VolumeSnapshot` с другим режимом тома, отличным от исходного, к `VolumeSnapshotContent`, соответствующему `VolumeSnapshot`, добавляется аннотация `snapshot.storage.kubernetes.io/allow-volume-mode-change: "true"`. Для pre-provisioned снимков `spec.sourceVolumeMode` должен быть заполнен администратором кластера.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotContent
metadata:
  name: new-snapshot-content-test
  annotations:
    - snapshot.storage.kubernetes.io/allow-volume-mode-change: "true"
spec:
  deletionPolicy: Delete
  driver: hostpath.csi.k8s.io
  source:
    snapshotHandle: 7bdd0de3-aaeb-11e8-9aae-0242ac110002
  sourceVolumeMode: Filesystem
  volumeSnapshotRef:
    name: new-snapshot-test
    namespace: default
```

## Топология снимков

В некоторых кластерах снимок доступен только из части кластера (например, в multi-zone кластере без общего хранилища). При включённом feature gate `VolumeSnapshotTopology`:

- Администратор кластера может задать `allowedTopologies` в `VolumeSnapshotClass`, чтобы запросить, откуда должны быть доступны динамически создаваемые снимки.
- CSI-драйвер сообщает, откуда доступен снимок, и sidecar `csi-snapshotter` записывает это в `VolumeSnapshotContent.spec.nodeAffinity`.
- При создании тома из снимка эта топология используется для размещения восстановленного тома там, где данные снимка доступны.

Это **alpha-функция CSI sidecar'ов**, включается feature gate `VolumeSnapshotTopology` на `csi-snapshotter` и `external-provisioner`.

## Восстановление томов из снимков

Можно создать новый том, предзаполненный данными из снимка, используя поле `dataSource` в объекте `PersistentVolumeClaim`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restore-pvc
spec:
  storageClassName: csi-hostpath-sc
  dataSource:
    name: new-snapshot-test
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

## VolumeSnapshotClass

Каждый `VolumeSnapshotClass` содержит поля `driver`, `deletionPolicy` и `parameters`, используемые при динамическом создании `VolumeSnapshot`, принадлежащего классу.

Имя объекта `VolumeSnapshotClass` значимо — именно так пользователи запрашивают конкретный класс. Администраторы задают имя и другие параметры класса при первом создании объектов `VolumeSnapshotClass`, и **объекты не могут быть обновлены после создания**.

Установка CRD — ответственность дистрибутива Kubernetes. Без необходимых CRD создание `VolumeSnapshotClass` завершается ошибкой.

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-hostpath-snapclass
driver: hostpath.csi.k8s.io
deletionPolicy: Delete
parameters:
```

### Класс по умолчанию

Администраторы могут указать `VolumeSnapshotClass` по умолчанию для `VolumeSnapshot`, которые не запрашивают конкретный класс, добавив аннотацию `snapshot.storage.kubernetes.io/is-default-class: "true"`:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-hostpath-snapclass
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: hostpath.csi.k8s.io
deletionPolicy: Delete
parameters:
```

Если существует несколько CSI-драйверов, для каждого из них может быть указан свой класс по умолчанию.

### Зависимости VolumeSnapshotClass

При создании `VolumeSnapshot` без указания `VolumeSnapshotClass` Kubernetes автоматически выбирает класс по умолчанию, у которого CSI-драйвер совпадает с CSI-драйвером `StorageClass` исходного PVC. Это позволяет нескольким классам по умолчанию сосуществовать в кластере, если каждый связан с уникальным CSI-драйвером.

**Важно**: для каждого CSI-драйвера должен быть только **один** класс по умолчанию. Если создано несколько классов по умолчанию с одним CSI-драйвером, создание `VolumeSnapshot` завершится ошибкой, так как Kubernetes не сможет определить, какой использовать.

### Driver

`VolumeSnapshotClass` имеет `driver`, определяющий, какой CSI-плагин тома используется для создания `VolumeSnapshot`. Поле **обязательно**.

### DeletionPolicy

`deletionPolicy` определяет, что происходит с `VolumeSnapshotContent` при удалении связанного `VolumeSnapshot`. Может быть `Retain` или `Delete`. Поле **обязательно**.

- **`Delete`** — нижележащий снимок в хранилище удаляется вместе с объектом `VolumeSnapshotContent`.
- **`Retain`** — и нижележащий снимок, и `VolumeSnapshotContent` сохраняются.

### Parameters

`parameters` описывают снимки, принадлежащие классу. Допустимые параметры зависят от драйвера.
