## Назначение и общая модель

Управление хранилищем — отдельная задача от управления вычислительными экземплярами. Подсистема PersistentVolume предоставляет API, абстрагирующий детали предоставления хранилища от его потребления. Для этого введены два API-ресурса: **PersistentVolume** и **PersistentVolumeClaim**.

**PersistentVolume (PV)** — это часть хранилища в кластере, предоставленная администратором или динамически созданная с использованием StorageClass. Это ресурс кластера, как и узел. PV — это плагины томов, как и Volumes, но с жизненным циклом, независимым от любого отдельного Pod'а, использующего PV. Этот API-объект фиксирует детали реализации хранилища (NFS, iSCSI или облачная система).

**PersistentVolumeClaim (PVC)** — это запрос хранилища от пользователя. Pod'ы потребляют ресурсы узла, а PVC потребляют ресурсы PV. PVC может запрашивать конкретный размер и режимы доступа.

Хотя PVC позволяют потреблять абстрактные ресурсы хранилища, пользователям часто нужны PV с разными свойствами (например, производительностью). Администраторам нужно предлагать разнообразные PV, не раскрывая детали реализации. Для этих нужд существует ресурс **StorageClass**.

## Жизненный цикл PV и PVC

### Provisioning (предоставление)

**Статическое**: администратор создаёт несколько PV с деталями реального хранилища. Они существуют в API Kubernetes и доступны для потребления.

**Динамическое**: когда ни один статический PV не соответствует PVC, кластер может динамически создать том специально для PVC на основе StorageClass. PVC должен запросить storage class, и администратор должен создать и настроить этот класс. PVC, запрашивающие класс `""`, фактически отключают динамическое провижининг для себя. Для включения динамического провижининга на основе StorageClass необходимо включить admission controller `DefaultStorageClass` на API-сервере.

### Binding (связывание)

Пользователь создаёт PVC с запрошенным объёмом и режимами доступа. Контур управления в плоскости управления следит за новыми PVC, находит подходящий PV и связывает их. Если PV был динамически создан для нового PVC, контур всегда свяжет этот PV с PVC. Иначе пользователь всегда получит как минимум запрошенное, но том может быть больше запрошенного. После связывания привязки PVC эксклюзивны. Связь PVC-PV — это отображение один-к-одному с использованием `ClaimRef`, который является двунаправленной привязкой между PV и PVC.

PVC остаются несвязанными бесконечно, если подходящий том не существует. PVC будут связаны по мере появления подходящих томов. Например, кластер с множеством PV по 50Gi не подойдёт для PVC, запрашивающего 100Gi. PVC может быть связан, когда в кластер добавят PV на 100Gi.

### Using (использование)

Pod'ы используют claims как тома. Кластер проверяет claim, находит связанный том и монтирует его для Pod'а. Для томов, поддерживающих несколько режимов доступа, пользователь указывает желаемый режим при использовании claim как тома в Pod'е. После того как claim связан, связанный PV принадлежит пользователю столько, сколько нужно. Pod'ы получают доступ к claim через секцию `persistentVolumeClaim` в блоке `volumes`.

### Storage Object in Use Protection

Функция защиты используемых объектов хранилища гарантирует, что PVC, активно используемые Pod'ом, и PV, связанные с PVC, не удаляются из системы, так как это может привести к потере данных.

PVC активно используется Pod'ом, когда существует объект Pod, использующий PVC. Если пользователь удаляет PVC, активно используемый Pod'ом, PVC не удаляется немедленно. Удаление PVC откладывается, пока PVC не перестанет активно использоваться любыми Pod'ами. Аналогично, если администратор удаляет PV, связанный с PVC, PV не удаляется немедленно — удаление откладывается, пока PV не перестанет быть связанным с PVC.

Защита PVC видна, когда статус PVC — `Terminating`, а список `Finalizers` включает `kubernetes.io/pvc-protection`. Защита PV видна, когда статус PV — `Terminating`, а `Finalizers` включает `kubernetes.io/pv-protection`.

### Reclaiming (освобождение)

Политика возврата PV определяет, что кластер делает с томом после освобождения от claim.

**Retain**: позволяет ручное восстановление ресурса. При удалении PVC PV всё ещё существует, и том считается «released». Но он ещё не доступен для другого claim, так как данные предыдущего claim остаются на томе. Администратор может вручную восстановить том: удалить PV (ассоциированный ресурс хранения во внешней инфраструктуре всё ещё существует), вручную очистить данные и удалить ассоциированный ресурс хранения. Для повторного использования того же ресурса создайте новый PV с тем же определением.

**Delete**: удаляет и объект PV из Kubernetes, и ассоциированный ресурс хранения во внешней инфраструктуре. Динамически созданные тома наследуют политику возврата своего StorageClass, которая по умолчанию — `Delete`. Администратор должен настроить StorageClass в соответствии с ожиданиями пользователей; иначе PV нужно отредактировать или пропатчить после создания. Изменить политику возврата можно командой:

```bash
kubectl patch pv <your-pv-name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
```


**Recycle** (устарело): выполняет базовую очистку (`rm -rf /thevolume/*`) и делает том доступным снова. **Устарело**, рекомендуется динамическое провижининг. В Kubernetes 1.37 только типы `nfs` и `hostPath` поддерживают recycling.

### PersistentVolume deletion protection finalizer

**Стабильно с v1.33**. Finalizers на PV гарантируют, что PV с политикой `Delete` удаляются только после удаления резервного хранилища.

- `external-provisioner.volume.kubernetes.io/finalizer` (с v1.31) добавляется к динамически и статически созданным CSI-томам.
- `kubernetes.io/pv-controller` (с v1.31) добавляется к динамически созданным in-tree plugin томам и пропускается для статически созданных.

При включении `CSIMigration{provider}` для конкретного in-tree плагина finalizer `kubernetes.io/pv-controller` заменяется на `external-provisioner.volume.kubernetes.io/finalizer`.

Finalizers гарантируют, что объект PV удаляется только после удаления тома из хранилища при политике `Delete`, независимо от порядка удаления PV и PVC.

## Резервирование PersistentVolume

Можно предварительно связать PVC с конкретным PV. Указав PV в PVC, вы объявляете привязку между конкретным PV и PVC. Если PV существует и не зарезервирован через `claimRef`, PV и PVC будут связаны. Связывание происходит независимо от некоторых критериев соответствия, включая node affinity; плоскость управления всё равно проверяет валидность storage class, режимов доступа и запрошенного размера.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: foo-pvc
  namespace: foo
spec:
  storageClassName: "" # Пустая строка должна быть указана явно, иначе будет установлен default StorageClass
  volumeName: foo-pv
```

Этот метод не гарантирует привилегий связывания. Если другие PVC могут использовать указанный PV, сначала зарезервируйте том, указав соответствующий PVC в `claimRef` PV.

## Расширение PVC (Stable с v1.24)

Расширение PVC включено по умолчанию. Поддерживаются типы: `csi` (включая некоторые CSI migrated), `flexVolume` (устарел), `portworxVolume` (устарел). Расширить PVC можно только если `allowVolumeExpansion` в StorageClass установлен в `true`.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: example-vol-default
provisioner: vendor-name.example/magicstorage
allowVolumeExpansion: true
```

Для запроса большего тома отредактируйте PVC и укажите больший размер. Это запускает расширение тома, лежащего в основе PV. **Новый PV никогда не создаётся** — существующий том изменяется в размере.

**Предупреждение**: прямое редактирование размера PV может предотвратить автоматическое изменение размера. Если отредактировать `capacity` PV, а затем `.spec` PVC, чтобы размер PVC совпал с PV, изменение размера хранилища не произойдёт — плоскость управления увидит, что желаемое состояние обоих ресурсов совпадает, и решит, что размер был увеличен вручную.

**Восстановление после сбоя расширения (GA в v1.34)**: если указан слишком большой размер, расширение будет повторяться бесконечно. В v1.34 можно уменьшить запрошенный размер PVC (пока расширение не завершено), и Kubernetes автоматически исправит ситуацию, вернув квоту . Новый размер должен быть **выше исходного размера в `.status.capacity`** — Kubernetes не поддерживает уменьшение PV.

## Типы PersistentVolume

PV реализованы как плагины. Kubernetes поддерживает: `csi`, `fc`, `hostPath` (только для одноузлового тестирования), `iscsi`, `local`, `nfs`.

Устаревшие, но доступные типы (требуют установки соответствующих CSI-драйверов, кроме flexVolume, cephfs, rbd): `awsElasticBlockStore`, `azureDisk`, `azureFile`, `cinder`, `flexVolume`, `gcePersistentDisk`, `portworxVolume`, `vsphereVolume`.

## Атрибуты PV

Имя объекта PV должно быть валидным DNS subdomain именем.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv0003
spec:
  capacity:
    storage: 5Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Recycle
  storageClassName: slow
  mountOptions:
    - hard
    - nfsvers=4.1
  nfs:
    path: /tmp
    server: 172.17.0.2
```

### Capacity

Обычно PV имеет конкретную ёмкость хранилища, задаваемую атрибутом `capacity` (значение Quantity). В настоящее время размер хранилища — единственный ресурс, который можно задать или запросить.

### Volume Mode (Stable с v1.18)

Kubernetes поддерживает два `volumeModes`: **Filesystem** (по умолчанию) и **Block**.

- **Filesystem**: том монтируется в Pod'ы в каталог. Если том основан на блочном устройстве и устройство пустое, Kubernetes создаёт файловую систему перед первым монтированием.
- **Block**: том предоставляется как сырое блочное устройство без файловой системы. Полезно для максимально быстрого доступа без слоя ФС. Приложение в Pod'е должно уметь работать с сырым блочным устройством.

### Access Modes

| Режим | Сокращение | Описание |
|---|---|---|
| **ReadWriteOnce** | RWO | Том монтируется read-write **одним узлом**. Несколько Pod'ов на одном узле могут обращаться к тому |
| **ReadOnlyMany** | ROX | Том монтируется read-only **многими узлами** |
| **ReadWriteMany** | RWX | Том монтируется read-write **многими узлами** |
| **ReadWriteOncePod** | RWOP | Том монтируется read-write **одним Pod'ом**. Стабильно с v1.29. Только для CSI-томов и Kubernetes 1.22+. Требует csi-provisioner:v3.0.0+, csi-attacher:v3.3.0+, csi-resizer:v1.3.0+ |

**Важно**: режимы доступа используются для сопоставления PVC и PV. В некоторых случаях они также ограничивают, где PV может быть смонтирован. **Режимы доступа не обеспечивают защиту от записи после монтирования**. Даже если PV создан как `ReadOnlyMany`, это не гарантирует, что он будет read-only. Исключение — `ReadWriteOncePod`, который ограничивает монтирование одним Pod'ом. **Том может быть смонтирован только с одним режимом доступа одновременно**, даже если поддерживает многие.

**Поддержка режимов по плагинам** (примеры):

| Плагин | RWO | ROX | RWX | RWOP |
|---|---|---|---|---|
| AzureFile | ✓ | ✓ | ✓ | - |
| CephFS | ✓ | ✓ | ✓ | - |
| CSI | зависит от драйвера | зависит от драйвера | зависит от драйвера | зависит от драйвера |
| FC | ✓ | ✓ | - | - |
| HostPath | ✓ | - | - | - |
| iSCSI | ✓ | ✓ | - | - |
| NFS | ✓ | ✓ | ✓ | - |

### Class

PV может иметь класс, задаваемый через `storageClassName`. PV определённого класса может быть связан только с PVC, запрашивающими этот класс. PV без `storageClassName` не имеет класса и может быть связан только с PVC, не запрашивающими конкретный класс.

### Mount Options

Администратор может указать дополнительные опции монтирования. Поддерживаются: `csi`, `iscsi`, `nfs`. Опции **не валидируются**; при неверной опции монтирование завершится ошибкой.

### Node Affinity

Для большинства типов томов это поле не нужно. **Явно задавать требуется для локальных томов**. PV может указать node affinity для ограничения узлов, с которых том доступен. Pod'ы, использующие PV, будут планироваться только на узлы, выбранные node affinity.

**Обновление node affinity** (Alpha в v1.35, отключено по умолчанию): при включённом feature gate `MutablePVNodeAffinity` поле `.spec.nodeAffinity` PV становится изменяемым. Позволяет обновлять affinity при миграции данных без прерывания работающих Pod'ов. Новое node affinity должно соответствовать узлам, где том сейчас используется. Pod'ы, нарушающие новое affinity, могут продолжать работать, но Kubernetes не поддерживает такую конфигурацию — их следует завершить. Из-за кэширования в памяти Pod'ы, созданные после обновления, могут ещё короткое время планироваться по старому affinity.

### Phase

| Фаза | Описание |
|---|---|
| **Available** | Свободный ресурс, ещё не связанный с claim |
| **Bound** | Том связан с claim |
| **Released** | Claim удалён, но ассоциированный ресурс хранения ещё не восстановлен кластером |
| **Failed** | Том не прошёл автоматическое восстановление |

Имя PVC, связанного с PV, можно увидеть через `kubectl describe persistentvolume <name>`.

**Timestamp перехода фазы** (стабильно с v1.31): поле `.status.lastPhaseTransitionTime` записывает временную метку последнего перехода фазы.

## PersistentVolumeClaims

Имя PVC должно быть валидным DNS subdomain именем.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myclaim
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Filesystem
  resources:
    requests:
      storage: 8Gi
  storageClassName: slow
  selector:
    matchLabels:
      release: "stable"
    matchExpressions:
      - {key: environment, operator: In, values: [dev]}
```

### Volume Name

PVC может использовать `volumeName` для явной привязки к конкретному PV. Можно оставить `volumeName` незаданным, указав, что Kubernetes должен создать новый PV, соответствующий claim. Если указанный PV уже связан с другим PVC, привязка застрянет в состоянии pending.

### Resources

PVC, как и Pod'ы, могут запрашивать конкретные объёмы ресурса. В данном случае запрос — на хранилище. Для томов Filesystem запрос storage относится к «внешнему» размеру тома (выделенному размеру из бэкенда хранилища). Записываемый размер может быть немного меньше для провайдеров, создающих файловую систему поверх блочного устройства, из-за накладных расходов ФС.

### Selector

PVC может указать label selector для фильтрации набора томов. Только тома, чьи метки соответствуют селектору, могут быть связаны. Селектор состоит из `matchLabels` и `matchExpressions` (операторы: `In`, `NotIn`, `Exists`, `DoesNotExist`). Все требования объединяются через AND.

### Class

PVC запрашивает класс через `storageClassName`. Только PV запрошенного класса могут быть связаны.

PVC с `storageClassName: ""` всегда интерпретируется как запрос PV без класса; может быть связан только с PV без класса (без аннотации или с `""`). PVC без `storageClassName` обрабатывается иначе в зависимости от того, включён ли admission plugin `DefaultStorageClass`:
- Если включён, администратор может указать default StorageClass (аннотация `storageclass.kubernetes.io/is-default-class: "true"`). Все PVC без `storageClassName` могут быть связаны только с PV этого default.
- Если выключен, понятия default StorageClass нет. PVC с `storageClassName: ""` могут быть связаны только с PV с `storageClassName: ""`. PVC с отсутствующим `storageClassName` могут быть обновлены позже, когда default станет доступен.

**Важно**: PVC с непустым selector **не может** иметь динамически созданный PV.

### Retroactive default StorageClass assignment (Stable с v1.28)

Можно создать PVC без `storageClassName`, даже если default StorageClass не существует. Когда default StorageClass становится доступным, плоскость управления обновляет существующие PVC без `storageClassName`, устанавливая его в новый default. PVC с `storageClassName: ""` **не обновляется**.

### Unused PVC tracking (Beta в v1.37, включено по умолчанию)

PVC protection controller добавляет condition `Unused` к каждому PVC, указывая, ссылается ли на него какой-либо non-terminal Pod. Состояния:
- `Unused=True` (reason `NoPodsUsingPVC`): нет non-terminal Pod'ов, ссылающихся на PVC. `lastTransitionTime` записывает, когда PVC стал неиспользуемым.
- `Unused=False` (reason `PodUsingPVC`): хотя бы один non-terminal Pod ссылается на PVC.

Pod считается non-terminal, если его фаза не `Succeeded` или `Failed`. Pending Pod (даже ещё не запланированный) считается использующим PVC. `lastTransitionTime` можно использовать для поиска PVC, неиспользуемых длительное время. Condition **не обновляется** для PVC с `deletionTimestamp`.

## Claims As Volumes

Pod'ы получают доступ к хранилищу, используя claim как том. **Claim должен существовать в том же namespace, что и Pod**. Кластер находит claim в namespace Pod'а и использует его для получения PV. Том монтируется на хост и в Pod.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
    - name: myfrontend
      image: nginx
      volumeMounts:
      - mountPath: "/var/www/html"
        name: mypd
  volumes:
    - name: mypd
      persistentVolumeClaim:
        claimName: myclaim
```

**Важно о namespace**: привязки PV эксклюзивны, и поскольку PVC — namespaced объекты, монтирование claims с режимами «Many» (ROX, RWX) возможно **только в пределах одного namespace**.

## Raw Block Volume Support (Stable с v1.18)

Поддерживаются плагины: CSI (включая некоторые CSI migrated), FC, iSCSI, Local volume.

```yaml
# PV
apiVersion: v1
kind: PersistentVolume
metadata:
  name: block-pv
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
  persistentVolumeReclaimPolicy: Retain
  fc:
    targetWWNs: ["50060e801049cfd1"]
    lun: 0
    readOnly: false
---
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: block-pvc
spec:
  accessModes:
    - ReadWriteOnce
  volumeMode: Block
  resources:
    requests:
      storage: 10Gi
---
# Pod
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-block-volume
spec:
  containers:
    - name: fc-container
      image: fedora:26
      command: ["/bin/sh", "-c"]
      args: [ "tail -f /dev/null" ]
      volumeDevices:
        - name: data
          devicePath: /dev/xvda
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: block-pvc
```

**Важно**: при добавлении raw block device для Pod'а указывается `devicePath` в контейнере вместо `mountPath`.

**Матрица связывания для статически созданных томов**:

| PV volumeMode | PVC volumeMode | Результат |
|---|---|---|
| unspecified | unspecified | BIND |
| unspecified | Block | NO BIND |
| unspecified | Filesystem | BIND |
| Block | unspecified | NO BIND |
| Block | Block | BIND |
| Block | Filesystem | NO BIND |
| Filesystem | Filesystem | BIND |
| Filesystem | Block | NO BIND |
| Filesystem | unspecified | BIND |

## Volume Snapshot and Restore (Stable с v1.20)

Volume snapshots поддерживают только out-of-tree CSI-плагины.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: restore-pvc
spec:
  storageClassName: csi-hostpath-sc
  dataSource:
    name: new-snapshot-test
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

## Volume Cloning

Доступно только для CSI-плагинов.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: cloned-pvc
spec:
  storageClassName: my-csi-plugin
  dataSource:
    name: existing-src-pvc-name
    kind: PersistentVolumeClaim
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

## Volume populators and data sources

Клонирование и восстановление из снапшота предзаполняют новый том из встроенного источника данных. Volume populators расширяют этот механизм, позволяя предзаполнять PVC из других типов источников (custom resource) через `dataSourceRef`.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: populated-pvc
spec:
  dataSourceRef:
    name: example-name
    kind: ExampleDataSource
    apiGroup: example.storage.k8s.io
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

`dataSourceRef` может содержать ссылку на любой объект в том же namespace, кроме core-объектов (кроме PVC). `dataSource` допускает только PVC и VolumeSnapshot. Для `dataSourceRef` требуется feature gate `AnyVolumeDataSource` на kube-apiserver и kube-controller-manager.

## Writing Portable Configuration

При написании шаблонов конфигурации, работающих на разных кластерах:
1. Включайте PVC в пакет конфигурации (рядом с Deployment, ConfigMap и т.д.).
2. **Не включайте PV** в конфигурацию — пользователь может не иметь прав на создание PV.
3. Дайте пользователю возможность указать storage class name при инстанцировании шаблона. Если указан — поместите в `persistentVolumeClaim.storageClassName`. Если нет — оставьте `nil`, и PV будет автоматически создан с default StorageClass.
4. В инструментарии отслеживайте PVC, которые не связываются со временем, и сообщайте пользователю — это может указывать на отсутствие динамической поддержки хранилища или отсутствие системы хранения.
