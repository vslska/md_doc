## Назначение и общая модель

Тома Kubernetes предоставляют контейнерам в Pod'е доступ к данным через файловую систему и возможность обмениваться ими. Разные типы томов решают разные задачи: наполнение конфигурационного файла из ConfigMap или Secret, предоставление временного пространства для Pod'а, совместное использование файловой системы между контейнерами одного Pod'а или между разными Pod'ами (даже на разных узлах), долговременное хранение данных, переживающее перезапуск или замену Pod'а, передача информации о самом Pod'е в приложение, а также доступ только для чтения к данным из другого образа контейнера.

Тома решают две ключевые проблемы. **Сохранение данных**: файлы на диске внутри контейнера эфемерны — при сбое или остановке контейнера все созданные или изменённые файлы теряются, и kubelet перезапускает контейнер с чистым состоянием. **Общее хранилище**: когда несколько контейнеров в Pod'е должны обмениваться файлами, настроить и получить доступ к общей файловой системе бывает сложно.

### Как работают тома

Kubernetes поддерживает множество типов томов. Pod может одновременно использовать любое количество типов томов. **Эфемерные** типы томов имеют жизненный цикл, привязанный к конкретному Pod'у, а **постоянные** существуют дольше жизненного цикла любого отдельного Pod'а. Когда Pod прекращает существование, Kubernetes уничтожает эфемерные тома, но **не уничтожает постоянные**. Для любого типа тома в данном Pod'е данные сохраняются при перезапусках контейнеров.

По своей сути том — это каталог, возможно с данными, доступный контейнерам в Pod'е. То, как этот каталог создаётся, какой носитель его поддерживает и каково его содержимое, определяется конкретным типом тома.

Чтобы использовать том, укажите тома в `.spec.volumes` и объявите, куда монтировать их в контейнерах, в `.spec.containers[*].volumeMounts`. При запуске Pod'а процесс в контейнере видит файловую систему, составленную из начального содержимого образа контейнера плюс тома (если определены), смонтированные внутри контейнера. Для каждого контейнера в Pod'е необходимо **независимо** указывать, куда монтировать каждый используемый том.

Тома не могут монтироваться внутри других томов (см. `subPath` для связанного механизма). Том также не может содержать жёсткую ссылку на что-либо в другом томе.

## configMap

ConfigMap предоставляет способ внедрения конфигурационных данных в Pod'ы. Данные, хранящиеся в ConfigMap, могут быть использованы в томе типа `configMap` и затем прочитаны контейнеризованными приложениями.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: configmap-pod
spec:
  containers:
    - name: test
      image: busybox:1.28
      command: ['sh', '-c', 'echo "The app is running!" && tail -f /dev/null']
      volumeMounts:
        - name: config-vol
          mountPath: /etc/config
  volumes:
    - name: config-vol
      configMap:
        name: log-config
        items:
          - key: log_level
            path: log_level.conf
```

**Важные ограничения**:
- ConfigMap необходимо создать до использования.
- ConfigMap всегда монтируется как **readOnly**.
- Контейнер, использующий ConfigMap как `subPath`-монтирование, **не получает обновления** при изменении ConfigMap.
- Текстовые данные представляются как файлы в кодировке UTF-8; для других кодировок используйте `binaryData`.

## downwardAPI

Том `downwardAPI` делает данные downward API доступными приложениям в виде файлов только для чтения в простом текстовом формате.

**Ограничение**: контейнер, использующий downward API как `subPath`-монтирование, не получает обновления при изменении значений полей.

## emptyDir

Для Pod'а, определяющего том `emptyDir`, том создаётся при назначении Pod'а на узел. Изначально том пуст. Все контейнеры в Pod'е могут читать и писать одни и те же файлы в томе `emptyDir`, хотя том может быть смонтирован по одинаковым или разным путям в каждом контейнере. **При удалении Pod'а с узла по любой причине данные в `emptyDir` удаляются безвозвратно**.

**Важно**: сбой контейнера не удаляет Pod с узла. Данные в `emptyDir` **сохраняются** при сбоях контейнера.

Типичные применения: временное пространство (например, для дисковой сортировки слиянием), чекпоинтинг длительных вычислений для восстановления после сбоев, файлы, которые контейнер-контент-менеджер загружает, пока веб-сервер отдаёт данные.

### Носитель и лимит размера

Поле `emptyDir.medium` управляет местом хранения. По умолчанию `emptyDir` хранится на носителе, поддерживающем узел (диск, SSD, сетевое хранилище). Если установить `emptyDir.medium: "Memory"`, Kubernetes смонтирует **tmpfs** (файловую систему в RAM). Хотя tmpfs очень быстр, **записанные файлы учитываются в лимите памяти контейнера**, который их записал.

Можно указать `sizeLimit` для ограничения ёмкости тома. Хранилище выделяется из эфемерного хранилища узла. Если оно заполнено из другого источника (логи, слои образов), `emptyDir` может исчерпать ёмкость раньше этого лимита. Если размер не указан, тома в памяти получают размер, равный allocatable памяти узла.

```yaml
volumes:
- name: cache-volume
  emptyDir:
    sizeLimit: 500Mi
    medium: Memory
```

### Режим доступа (Alpha в v1.37)

Поле `emptyDir.mode` позволяет установить Unix-биты прав на каталог `emptyDir` (от `0000` до `01777` в восьмеричной записи). Если не указано, каталог создаётся с правами по умолчанию `0777`. Полезно для ограничения доступа владельцем и группой (`0750`) или установки sticky bit (`01777`). Если в security context Pod'а задан `fsGroup`, права группы, применённые `fsGroup`, переопределяют указанный `mode`. Поле не действует на Windows.

## hostPath

Том `hostPath` монтирует файл или каталог из файловой системы узла в Pod. Это не то, что нужно большинству Pod'ов, но мощный «аварийный выход» для некоторых приложений.

**Предупреждение о безопасности**: использование `hostPath` сопряжено с множеством рисков. Если можно избежать `hostPath`, следует это сделать. Доступ к файловой системе хоста может раскрыть привилегированные системные учётные данные (например, kubelet) или привилегированные API (например, сокет container runtime), которые можно использовать для побега из контейнера или атаки на другие части кластера. Pod'ы с идентичной конфигурацией могут вести себя по-разному на разных узлах из-за разных файлов. Использование `hostPath` **не учитывается как эфемерное хранилище** — необходимо самостоятельно отслеживать использование диска.

### Типы hostPath

| Значение | Поведение |
|---|---|
| `""` (по умолчанию) | Проверки не выполняются перед монтированием |
| `DirectoryOrCreate` | Если по пути ничего нет, создаётся пустой каталог с правами `0755`, владельцем и группой kubelet |
| `Directory` | По пути должен существовать каталог |
| `FileOrCreate` | Если по пути ничего нет, создаётся пустой файл с правами `0644`. **Не создаёт родительский каталог** — если его нет, Pod не запустится |
| `File` | По пути должен существовать файл |
| `Socket` | По пути должен существовать UNIX-сокет |
| `CharDevice` | Только Linux: по пути должно быть символьное устройство |
| `BlockDevice` | Только Linux: по пути должно быть блочное устройство |

Некоторые файлы или каталоги, созданные на хостах, могут быть доступны только root. Тогда нужно либо запускать процесс от root в привилегированном контейнере, либо изменить права на хосте.

## image (Stable в v1.36)

Том `image` представляет OCI-объект (образ контейнера или артефакт), доступный на хосте kubelet.

```yaml
volumes:
- name: volume
  image:
    reference: quay.io/crio/artifact:v2
    pullPolicy: IfNotPresent
```

Том разрешается при старте Pod'а в зависимости от `pullPolicy`:
- **Always**: kubelet всегда пытается загрузить reference. При сбое Pod переходит в `Failed`.
- **Never**: kubelet никогда не загружает reference и использует только локальный образ или артефакт. Pod переходит в `Failed`, если какие-либо слои образа отсутствуют локально или манифест образа не кэширован.
- **IfNotPresent**: kubelet загружает, если reference отсутствует на диске. Pod переходит в `Failed`, если reference отсутствует и загрузка не удалась.

Том **переразрешается**, если Pod удалён и создан заново, поэтому новый удалённый контент станет доступен при пересоздании Pod'а. Сбой разрешения или загрузки образа при старте Pod'а блокирует запуск контейнеров и может добавить значительную задержку. Сбои повторяются с обычным backoff томов и сообщаются в reason и message Pod'а.

OCI-объект монтируется в **один каталог** и монтируется **только для чтения**. `subPath` или `subPathExpr` для контейнеров поддерживаются только с Kubernetes v1.33. Поле `spec.securityContext.fsGroupChangePolicy` не действует на этот тип тома. Admission controller `AlwaysPullImages` также работает для этого источника тома, как и для образов контейнеров.

## iscsi

Том `iscsi` позволяет смонтировать существующий iSCSI-том (SCSI over IP) в Pod. В отличие от `emptyDir`, содержимое `iscsi` **сохраняется** — том лишь отмонтируется. Это значит, что iSCSI-том можно предварительно наполнить данными и делиться ими между Pod'ами.

**Особенность iSCSI**: том может быть смонтирован **только для чтения** несколькими потребителями одновременно. Однако в режиме **чтения-записи** iSCSI-том может быть смонтирован **только одним потребителем**. Одновременная запись не допускается.

Требуется собственный запущенный iSCSI-сервер с созданным томом.

## local

Том `local` представляет смонтированное локальное устройство хранения (диск, раздел или каталог). Локальные тома могут использоваться **только как статически созданные PersistentVolume**. Динамическое провижининг не поддерживается.

По сравнению с `hostPath`, локальные тома используются надёжно и переносимо **без ручного планирования Pod'ов на узлы**. Система знает об ограничениях узла, смотря на `nodeAffinity` в PersistentVolume.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: example-pv
spec:
  capacity:
    storage: 100Gi
  volumeMode: Filesystem
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Delete
  storageClassName: local-storage
  local:
    path: /mnt/disks/ssd1
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - example-node
```

**Важно**: при использовании локальных томов необходимо задать `nodeAffinity` у PersistentVolume — планировщик использует его для размещения Pod'ов на правильном узле. `volumeMode` можно установить в `"Block"` (вместо `"Filesystem"`) для предоставления локального тома как raw block device. Рекомендуется создавать StorageClass с `volumeBindingMode: WaitForFirstConsumer`, чтобы отложить привязку тома и учесть другие ограничения Pod'а (ресурсы узла, node selectors, affinity). При использовании локальных томов **требуется ручная очистка и удаление** PersistentVolume, если не используется внешний статический provisioner.

## nfs

Том `nfs` позволяет смонтировать существующий NFS-ресурс (Network File System) в Pod. Содержимое `nfs` **сохраняется** — том лишь отмонтируется. NFS может быть смонтирован **несколькими писателями одновременно**.

```yaml
volumes:
- name: test-volume
  nfs:
    server: my-nfs-server.example.com
    path: /my-nfs-volume
    readOnly: true
```

Требуется собственный запущенный NFS-сервер с экспортированным ресурсом. В спецификации Pod'а **нельзя указать опции монтирования NFS** — их можно задать на стороне сервера или в `/etc/nfsmount.conf`, либо монтировать NFS через PersistentVolumes (которые позволяют задавать опции).

---

## persistentVolumeClaim

Том `persistentVolumeClaim` используется для монтирования PersistentVolume в Pod. PVC — способ для пользователей «заявить» долговременное хранилище (например, iSCSI-том), не зная деталей конкретной облачной среды.

---

## portworxVolume (Deprecated с v1.25)

`portworxVolume` — эластичный блочный слой хранения, работающий гиперконвергентно с Kubernetes. Том может создаваться динамически через Kubernetes или быть предварительно выделенным. **Устарел с Kubernetes v1.25**. В Kubernetes 1.37 все операции для in-tree Portworx volumes перенаправляются на CSI-драйвер `pxd.portworx.com` по умолчанию (CSI migration стабильна с v1.33).

## projected

Том `projected` отображает несколько существующих источников томов в один каталог. Источники могут включать `secret`, `configMap`, `downwardAPI` и `serviceAccountToken`.

```yaml
volumes:
- name: projected-volume
  projected:
    sources:
    - configMap:
        name: my-config
    - secret:
        name: my-secret
    - downwardAPI:
        items:
        - path: "labels"
          fieldRef:
            fieldPath: metadata.labels
    - serviceAccountToken:
        path: token
        expirationSeconds: 3600
```

**Важно**: контейнер, использующий `projected` как `subPath`-монтирование, **не получает обновления** для этих источников тома.

---

## secret

Том `secret` используется для передачи конфиденциальной информации (пароли, токены) в Pod'ы. Секреты хранятся в Kubernetes API и монтируются как файлы, не связывая приложение напрямую с Kubernetes. Тома `secret` поддерживаются **tmpfs** (файловой системой в RAM), поэтому никогда не записываются на энергонезависимое хранилище.

**Ограничения**:
- Secret необходимо создать в API Kubernetes до использования.
- Secret всегда монтируется как **readOnly**.
- Контейнер, использующий Secret как `subPath`-монтирование, **не получает обновления** Secret.

## subPath

Иногда полезно использовать один том для нескольких целей в одном Pod'е. Свойство `volumeMounts[*].subPath` указывает подпуть внутри referenced-тома вместо его корня.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-lamp-site
spec:
  containers:
  - name: mysql
    image: mysql
    volumeMounts:
    - mountPath: /var/lib/mysql
      name: site-data
      subPath: mysql
  - name: php
    image: php:7.0-apache
    volumeMounts:
    - mountPath: /var/www/html
      name: site-data
      subPath: html
  volumes:
  - name: site-data
    persistentVolumeClaim:
      claimName: my-lamp-site-data
```

### subPath с раскрытием переменных окружения (Stable с v1.17)

Поле `subPathExpr` позволяет строить имена каталогов `subPath` из переменных окружения downward API. `subPath` и `subPathExpr` **взаимоисключающи**.

```yaml
spec:
  containers:
  - name: container1
    env:
    - name: POD_NAME
      valueFrom:
        fieldRef:
          apiVersion: v1
          fieldPath: metadata.name
    volumeMounts:
    - name: workdir1
      mountPath: /logs
      subPathExpr: $(POD_NAME)
  volumes:
  - name: workdir1
    hostPath:
      path: /var/log/pods
```

**Синтаксис**: используется круглые скобки `$(VAR)`, а не фигурные.

## Resources

Носитель хранения (диск или SSD) для тома `emptyDir` определяется носителем файловой системы, содержащей корневой каталог kubelet (обычно `/var/lib/kubelet`). **Нет ограничения** на то, сколько места может потребить `emptyDir` или `hostPath`, и нет изоляции между контейнерами или Pod'ами.

Для запроса пространства через спецификацию ресурсов используется `ephemeral-storage`. Kubelet учитывает использование `emptyDir` (кроме tmpfs), каталоги логов уровня узла и записываемые слои контейнеров. Если Pod использует больше эфемерного хранилища, чем разрешено, kubelet выставляет сигнал eviction.

## Out-of-tree volume plugins

Out-of-tree плагины томов включают **Container Storage Interface (CSI)** и FlexVolume (устарел). Эти плагины позволяют поставщикам хранилищ создавать собственные плагины без добавления исходного кода в репозиторий Kubernetes.

Ранее все плагины были «in-tree» — встроенными, компилировались и поставлялись с ядром Kubernetes. Добавление новой системы хранения требовало проверки кода в основном репозитории. CSI и FlexVolume позволяют разрабатывать плагины независимо и развёртывать их как расширения.

### csi

CSI определяет стандартный интерфейс для систем оркестрации контейнеров (таких как Kubernetes) для предоставления произвольных систем хранения контейнерным нагрузкам.

После развёртывания CSI-совместимого драйвера пользователи могут использовать тип тома `csi` для подключения или монтирования томов, предоставляемых драйвером. Том `csi` может использоваться в Pod'е тремя способами: через ссылку на PersistentVolumeClaim, с generic ephemeral volume, с CSI ephemeral volume (если драйвер поддерживает).

**Поля для настройки CSI persistent volume**:
- `driver`: имя драйвера, должно соответствовать значению, возвращаемому CSI-драйвером в `GetPluginInfoResponse`.
- `volumeHandle`: уникальный идентификатор тома, должен соответствовать `volume.id` в `CreateVolumeResponse`.
- `readOnly`: опциональный boolean, указывающий, должен ли том быть ControllerPublished как read-only.
- `fsType`: тип файловой системы для монтирования.
- `volumeAttributes`: карта строковых свойств тома.
- `controllerPublishSecretRef`, `nodeExpandSecretRef`, `nodePublishSecretRef`, `nodeStageSecretRef`: ссылки на Secret для различных CSI-вызовов.

**CSI raw block volume**: стабильно с v1.18. **CSI ephemeral volumes**: стабильно с v1.25. **Windows CSI proxy**: стабильно с v1.22 — для Windows-узлов привилегированные операции выполняются через `csi-proxy`, предварительно устанавливаемый на каждом Windows-узле.

### Миграция с in-tree на CSI (Stable с v1.25)

Функция `CSIMigration` направляет операции против существующих in-tree плагинов на соответствующие CSI-плагины. Операторам не нужно менять конфигурацию существующих StorageClass, PersistentVolume или PersistentVolumeClaim при переходе на CSI-драйвер, заменяющий in-tree плагин. Существующие PV, созданные in-tree плагином, можно использовать и после завершения миграции. В рамках миграции необходимо установить и настроить соответствующий CSI-драйвер.

### flexVolume (Deprecated с v1.23)

FlexVolume — out-of-tree интерфейс плагинов, использующий exec-модель для взаимодействия с драйверами хранения. Бинарники драйверов должны быть установлены по предопределённому пути на каждом узле (в некоторых случаях и на узлах плоскости управления). **Устарел**. Рекомендуется использовать out-of-tree CSI-драйвер.

## Mount propagation

**Предупреждение**: mount propagation — низкоуровневая функция, которая работает несовместимо на всех типах томов. Рекомендуется использовать только с `hostPath` или memory-backed `emptyDir`.

Mount propagation позволяет делиться томами, смонтированными контейнером, с другими контейнерами в том же Pod'е или даже с другими Pod'ами на том же узле. Управляется полем `mountPropagation` в `containers[*].volumeMounts`.

| Значение | Поведение |
|---|---|
| **None** (по умолчанию) | Монтирование не получает последующих монтирований, созданных хостом в этот том или его подкаталоги. Монтирования контейнера не видны на хосте. Эквивалент `rprivate` |
| **HostToContainer** | Монтирование получает все последующие монтирования, созданные хостом в этот том или его подкаталоги. Если Pod с `Bidirectional` монтирует что-то туда, контейнер с `HostToContainer` увидит это. Эквивалент `rslave` |
| **Bidirectional** | Ведёт себя как `HostToContainer`, но все монтирования, созданные контейнером, распространяются обратно на хост и во все контейнеры всех Pod'ов, использующих тот же том. Эквивалент `rshared`. **Опасно**: может повредить ОС хоста, разрешено только в привилегированных контейнерах. Типичное использование — Pod с драйвером FlexVolume или CSI |

## Read-only mounts

Монтирование можно сделать read-only, установив `.spec.containers[*].volumeMounts[*].readOnly: true`. Это **не делает сам том read-only** — только конкретный контейнер не сможет писать в него. Другие контейнеры в Pod'е могут монтировать тот же том как read-write.

**Важно для Linux**: read-only монтирования **не являются рекурсивно read-only по умолчанию**. Если Pod монтирует `/mnt` хоста как `hostPath`, и внутри `/mnt/<SUBMOUNT>` смонтирована другая файловая система (tmpfs, NFS, USB), том в контейнере также будет иметь записываемый `/mnt/<SUBMOUNT>`, даже если само монтирование указано как read-only.

### Recursive read-only mounts (Stable с v1.33)

Рекурсивно read-only монтирования включаются установкой `recursiveReadOnly` для Pod'а. Допустимые значения:

- **Disabled** (по умолчанию): нет эффекта.
- **Enabled**: делает монтирование рекурсивно read-only. Требует: `readOnly: true`; `mountPropagation` не установлен или `None`; Linux-ядро v5.12+; CRI-runtime поддерживает рекурсивно read-only монтирования; OCI-runtime поддерживает их. Если что-то не выполнено — Pod не запустится.
- **IfPossible**: пытается применить `Enabled`, откатывается на `Disabled`, если функция не поддерживается ядром или runtime class.

```yaml
volumeMounts:
- name: mnt
  mountPath: /mnt-rro
  readOnly: true
  mountPropagation: None
  recursiveReadOnly: Enabled
```

**Поддерживаемые runtime**: CRI-level — containerd с v2.0, CRI-O с v1.30; OCI-level — runc с v1.1, crun с v1.8.6.

## File owner

**Group ownership (GID)**: принадлежность файлов тома группе управляется через `pod.spec.securityContext.fsGroup`.

**User ownership (UID)** (Alpha в v1.37, отключено по умолчанию): при включённом feature gate `AtomicWriteVolumeUserFields` поля UID владельца файлов для томов `configMap`, `secret`, `downwardAPI` и `projected` становятся доступны. `defaultUser` на уровне тома задаёт UID владельца для всех файлов данных при создании. На уровне item поле `user` управляет UID владельца отдельного файла и имеет приоритет над `defaultUser`.

```yaml
volumes:
- name: volA
  configMap:
    defaultUser: 1000
    name: cm1
    items:
    - key: foo
      path: foo
    - key: bar
      path: bar
      user: 1001
```

## Bind mount options (Alpha в v1.37)

Поле `.spec.containers[*].volumeMounts[*].bindMountOptions` позволяет применять security-флаги Linux bind mount к любому монтированию тома. Допустимые значения: `noexec` (запрещает выполнение бинарников на томе), `nodev` (игнорирует специальные файлы устройств), `nosuid` (игнорирует биты set-user-identifier/set-group-identifier). Опции применяются **для каждого контейнера отдельно**, поэтому разные контейнеры в одном Pod'е могут монтировать один том с разными опциями. **Не поддерживается с image volumes**. Требует поддержки `mount_options` в CRI-сообщении Mount; если runtime не поддерживает — kubelet отклоняет Pod'ы с `bindMountOptions`. Не действует на Windows.
