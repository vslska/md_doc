## Общая модель

Узлы имеют **локальное эфемерное хранилище**, основанное на локально подключённых записываемых устройствах или, иногда, на RAM. «Эфемерное» означает отсутствие долгосрочных гарантий сохранности данных.

Pod'ы используют эфемерное локальное хранилище для временного пространства (scratch), кэширования и логов. Kubelet может предоставлять Pod'ам временное пространство через локальное эфемерное хранилище, монтируя тома `emptyDir` в контейнеры. Kubelet также использует этот тип хранилища для хранения логов контейнеров уровня узла, образов контейнеров и записываемых слоёв работающих контейнеров .

**Предупреждение**: при отказе узла данные в его эфемерном хранилище могут быть потеряны. Приложения не могут ожидать никаких гарантий производительности (например, IOPS диска) от локального эфемерного хранилища .

**Важно для ResourceQuota**: чтобы квота работала для `ephemeral-storage`, администратор должен установить квоту в namespace, а пользователь — указать `limits` для `ephemeral-storage` в спецификации Pod'а. Если пользователь не указал лимит, квота не применяется .

## Конфигурации локального эфемерного хранилища

Kubernetes поддерживает несколько способов настройки локального эфемерного хранилища на узле.

### Single filesystem

Все различные типы эфемерных локальных данных (`emptyDir` тома, записываемые слои, образы контейнеров, логи) размещаются в одной файловой системе. Kubelet записывает логи в файлы внутри настроенного каталога логов (`/var/log` по умолчанию) и имеет базовый каталог для других локально хранимых данных (`/var/lib/kubelet` по умолчанию). Обычно оба каталога находятся в корневой файловой системе системы, и kubelet спроектирован с учётом этой компоновки .

### Runtime filesystem

Одна файловая система на узле используется для эфемерных данных работающих Pod'ов (логи и тома `emptyDir`). Она также может использоваться для других данных, например системных логов, не связанных с Kubernetes, и даже может быть корневой файловой системой. Kubelet также записывает логи контейнеров уровня узла в первую файловую систему. Отдельная файловая система, поддерживаемая другим логическим устройством хранения, используется для хранения слоёв образов контейнеров и записываемых слоёв. Это расположение настраивается в container runtime, а не в kubelet. Первая файловая система не содержит слоёв образов или записываемых слоёв .

### Split image filesystem

Слои образов контейнеров находятся в отдельной файловой системе, а записываемые слои контейнеров — в той же файловой системе, что и эфемерные данные kubelet (логи и тома `emptyDir`). Эта компоновка требует поддержки сигналов eviction `containerfs`. Страница node-pressure eviction называет эти наблюдаемые файловые системы `nodefs`, `imagefs` и `containerfs`; эти имена не всегда означают отдельные точки монтирования .

Kubelet может измерять использование локального хранилища, если узел настроен с использованием одной из поддерживаемых конфигураций. **При другой конфигурации kubelet не применяет лимиты ресурсов для эфемерного локального хранилища** .

**Важные примечания**:
- Kubelet отслеживает тома `emptyDir` с `medium: Memory` (tmpfs) как **использование памяти контейнера**, а не как локальное эфемерное хранилище .
- Kubelet может отслеживать эфемерное хранилище только на файловых системах, которые он наблюдает через поддерживаемые компоновки. При монтировании дополнительных файловых систем по путям вроде `/var/lib/kubelet`, `/var/log` или в каталог хранения container runtime вне этих компоновок kubelet может некорректно сообщать об эфемерном хранилище .

## Requests и limits для локального эфемерного хранилища

Каждый контейнер Pod'а может указать одно или оба поля:

- `spec.containers[].resources.limits.ephemeral-storage`
- `spec.containers[].resources.requests.ephemeral-storage`

Значения измеряются в байтах. Можно использовать целое число или суффиксы `E, P, T, G, M, k`, а также степени двойки `Ei, Pi, Ti, Gi, Mi, Ki`. Например, `128974848`, `129e6`, `129M` и `123Mi` представляют примерно одно и то же значение .

**Внимание к регистру суффиксов**: запрос `400m` для `ephemeral-storage` — это запрос **0.4 байта**. Вероятно, имелось в виду `400Mi` (400 мебибайт) или `400M` (400 мегабайт) .

### Пример

Pod с двумя контейнерами, каждый с request `2Gi` и limit `4Gi`. Суммарно Pod имеет request `4Gi` и limit `8Gi` эфемерного хранилища. Из этого лимита `500Mi` может быть израсходовано томом `emptyDir` с `sizeLimit: 500Mi` .

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: images.my-company.example/app:v4
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  - name: log-aggregator
    image: images.my-company.example/log-aggregator:v6
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  volumes:
    - name: ephemeral
      emptyDir:
        sizeLimit: 500Mi
```

## Планирование Pod'ов с requests ephemeral-storage

При создании Pod'а планировщик выбирает узел. Каждый узел имеет максимальный объём локального эфемерного хранилища, который он может предоставить Pod'ам (см. Node Allocatable). Планировщик гарантирует, что сумма requests запланированных контейнеров меньше ёмкости узла .

## Управление потреблением эфемерного хранилища

Если kubelet управляет локальным эфемерным хранилищем как ресурсом, он измеряет использование хранилища в:

- томах `emptyDir`, кроме томов с `medium: Memory` (tmpfs);
- каталогах, содержащих логи уровня узла;
- записываемых слоях контейнеров .

Если Pod использует больше эфемерного хранилища, чем разрешено, kubelet выставляет сигнал eviction, который запускает вытеснение Pod'а.

**Изоляция на уровне контейнера**: если записываемый слой и использование логов контейнера превышают его лимит хранилища, kubelet помечает Pod на вытеснение.

**Изоляция на уровне Pod'а**: kubelet вычисляет общий лимит хранилища Pod'а как сумму лимитов контейнеров. Если сумма использования локального эфемерного хранилища от всех контейнеров и томов `emptyDir` Pod'а превышает общий лимит, kubelet также помечает Pod на вытеснение .

**Предупреждение**: если kubelet не измеряет локальное эфемерное хранилище, Pod, превысивший лимит, **не будет вытеснен** за нарушение лимитов ресурсов локального хранилища. Однако если свободное место в файловой системе для записываемых слоёв, логов уровня узла или томов `emptyDir` становится низким, узел помечает себя taint'ом нехватки локального хранилища, и этот taint запускает вытеснение Pod'ов, которые специально не терпят этот taint .

### Способы измерения

#### Periodic scanning

Kubelet выполняет регулярные запланированные проверки, сканируя каждый том `emptyDir`, каталог логов контейнеров и записываемый слой контейнера. Сканирование измеряет, сколько места используется.

**Примечание**: в этом режиме kubelet не отслеживает открытые файловые дескрипторы для удалённых файлов. Если файл создан внутри `emptyDir`, открыт, а затем удалён, пока дескриптор ещё открыт, inode удалённого файла сохраняется до закрытия файла, но kubelet не классифицирует это пространство как используемое .

#### Filesystem project quota (Beta в v1.31, отключено по умолчанию)

Project quotas — функция уровня ОС для управления использованием хранилища на файловых системах. С Kubernetes можно включить project quotas для мониторинга использования хранилища. Файловая система, поддерживающая тома `emptyDir` на узле, должна поддерживать project quota (например, XFS и ext4fs) .

**Важно**: project quotas позволяют **отслеживать** использование хранилища, но **не обеспечивают соблюдение лимитов** .

Kubernetes использует project ID начиная с **1048576**. Используемые ID регистрируются в `/etc/projects` и `/etc/projid`. Если project ID в этом диапазоне используются для других целей, их необходимо зарегистрировать в этих файлах, чтобы Kubernetes их не использовал .

Квоты быстрее и точнее сканирования каталогов: при назначении каталога проекту все файлы, созданные в нём, создаются в этом проекте, и ядру нужно лишь отслеживать количество блоков, используемых файлами проекта. Если файл создан и удалён, но имеет открытый дескриптор, он продолжает потреблять пространство; отслеживание квот учитывает это точно, тогда как сканирование каталогов упускает использование удалённых файлов .

Для использования квот Pod должен находиться в **user namespace**. Внутри user namespaces ядро ограничивает изменения `projectID` на файловой системе, обеспечивая надёжность метрик хранилища, вычисляемых квотами .

**Для включения project quotas** :
1. Включить feature gate `LocalStorageCapacityIsolationFSQuotaMonitoring=true` через поле `featureGates` в конфигурации kubelet.
2. Убедиться, что feature gate `UserNamespacesSupport` включён, а ядро, CRI-реализация и OCI-runtime поддерживают user namespaces.
3. Убедиться, что корневая (или опциональная runtime) файловая система имеет включённые project quotas. Все XFS поддерживают project quotas. Для ext4 нужно включить отслеживание project quota, пока файловая система не смонтирована:

   ```bash
   sudo tune2fs -O project -Q prjquota /dev/block-device
   ```

4. Убедиться, что файловая система смонтирована с включёнными project quotas. Для XFS и ext4 опция монтирования называется `prjquota`.

**Если project quotas не нужны**: отключить feature gate `LocalStorageCapacityIsolationFSQuotaMonitoring` через поле `featureGates` в конфигурации kubelet .
