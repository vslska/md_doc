> **Состояние функции:** стабильно с Kubernetes v1.24.

Когда Pod работает на узле, **сам Pod** тоже потребляет часть системных ресурсов — сверх того, что нужно контейнерам внутри него. В Kubernetes **Pod Overhead** — это способ учесть ресурсы, которые потребляет инфраструктура Pod'а, **поверх** запросов и лимитов контейнеров.

Overhead Pod'а устанавливается **в момент admission** (при создании) на основе значения `overhead`, связанного с RuntimeClass этого Pod'а.

Overhead учитывается:
- при **планировании** — в дополнение к сумме запросов контейнеров;
- при **расчёте размера cgroup** Pod'а в kubelet;
- при **ранжировании Pod'ов для eviction**.

## Как настроить

Нужно использовать RuntimeClass, в котором определено поле `overhead`.

## Пример

Допустим, есть RuntimeClass с виртуализированным контейнерным runtime (в примере — Kata Containers + Firecracker), который тратит около **120 MiB на Pod** под виртуалку и гостевую ОС:

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata-fc
handler: kata-fc
overhead:
  podFixed:
    memory: "120Mi"
    cpu: "250m"
```

Workload'ы, указывающие RuntimeClass `kata-fc`, будут учитывать этот overhead в:
- расчёте **ResourceQuota**;
- **планировании** на узел;
- размере **cgroup** Pod'а.

Пример Pod'а:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
spec:
  runtimeClassName: kata-fc
  containers:
  - name: busybox-ctr
    image: busybox:1.28
    stdin: true
    tty: true
    resources:
      limits:
        cpu: 500m
        memory: 100Mi
  - name: nginx-ctr
    image: nginx
    resources:
      limits:
        cpu: 1500m
        memory: 100Mi
```

> **Примечание:** если в Pod'е заданы только `limits`, kubelet выведет из них `requests` и установит их равными `limits`.

В момент admission контроллер RuntimeClass **дописывает** в PodSpec поле `overhead` из RuntimeClass. Если в PodSpec `overhead` уже задан — Pod **отклоняется**. В примере выше указано только имя RuntimeClass, поэтому admission-контроллер сам добавит overhead.

Проверить, что получилось:

```bash
kubectl get pod test-pod -o jsonpath='{.spec.overhead}'
```

```
map[cpu:250m memory:120Mi]
```

## Как это учитывается

### ResourceQuota

Если задана `ResourceQuota`, в неё идёт **сумма запросов контейнеров + overhead**.

### Планирование

Kube-scheduler, выбирая узел для нового Pod'а, учитывает **overhead + сумму запросов контейнеров**. В примере: `2000m CPU + 250m = 2250m CPU`, `200Mi + 120Mi = 320Mi`. Планировщик ищет узел, где доступно **2.25 CPU и 320 MiB памяти**.

### cgroup Pod'а

Когда Pod запланирован на узел, kubelet на этом узле создаёт **cgroup для Pod'а**. Внутри неё container runtime создаёт контейнеры.

- Если у каждого контейнера задан **лимит** (Guaranteed QoS или Burstable QoS с лимитами), kubelet ставит **верхний лимит** на cgroup Pod'а: `cpu.cfs_quota_us` для CPU и `memory.limit_in_bytes` для памяти. Лимит = **сумма лимитов контейнеров + overhead**.
- Для CPU, если Pod Guaranteed или Burstable QoS, kubelet ставит `cpu.shares` на основе **суммы requests контейнеров + overhead**.

Проверим на примере. Суммарные requests контейнеров:

```bash
kubectl get pod test-pod -o jsonpath='{.spec.containers[*].resources.limits}'
```

```
map[cpu: 500m memory:100Mi] map[cpu:1500m memory:100Mi]
```

То есть `2000m CPU` и `200MiB` памяти.

А что видит узел:

```bash
kubectl describe node | grep test-pod -B2
```

```
  Namespace    Name       CPU Requests  CPU Limits   Memory Requests  Memory Limits  AGE
  ---------    ----       ------------  ----------   ---------------  -------------  ---
  default      test-pod   2250m (56%)   2250m (56%)  320Mi (1%)       320Mi (1%)     36m
```

`2250m` и `320Mi` — это уже **с overhead**.

### Проверка cgroup Pod'а (для продвинутых)

На узле, где работает Pod:

```bash
# На узле, где запланирован Pod
POD_ID="$(sudo crictl pods --name test-pod -q)"
```

Путь к cgroup Pod'а:

```bash
sudo crictl inspectp -o=json $POD_ID | grep cgroupsPath
```

```
  "cgroupsPath": "/kubepods/podd7f4b509-cf94-4951-9417-d1087c92a5b2/7ccf55aee35dd16aca4189c952d83487297f3cd760f1bbf09620e206e7d0c27a"
```

Cgroup Pod'а — на уровень выше:

```
kubepods/podd7f4b509-cf94-4951-9417-d1087c92a5b2
```

Проверяем лимит памяти:

```bash
cat /sys/fs/cgroup/memory/kubepods/podd7f4b509-cf94-4951-9417-d1087c92a5b2/memory.limit_in_bytes
```

```
335544320
```

Это ровно **320 MiB**, как и ожидалось.

> Это продвинутый пример — в реальной работе проверять cgroup'ы на узле вручную не нужно.

## Наблюдаемость

В **kube-state-metrics** есть метрики `kube_pod_overhead_*`. Они помогают понять, когда overhead реально используется, и наблюдать за стабильностью workload'ов с заданным overhead.
