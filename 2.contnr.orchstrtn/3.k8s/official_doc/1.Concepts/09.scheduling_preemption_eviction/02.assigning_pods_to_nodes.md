Можно ограничить Pod так, чтобы он работал **только на определённых узлах**, или чтобы он **предпочитал** определённые узлы. Есть несколько способов это сделать, и рекомендованные подходы все используют **селекторы меток** для облегчения выбора. Часто такие ограничения задавать не нужно: планировщик автоматически сделает разумное размещение (например, распределит Pod'ы по узлам, чтобы не размещать их на узле с недостатком свободных ресурсов). Однако есть обстоятельства, когда вы можете захотеть контролировать, на какой узел разворачивается Pod, — например, чтобы Pod оказался на узле с подключённым SSD или чтобы разместить Pod'ы двух разных сервисов, которые много общаются, в одной зоне доступности.

Можно использовать любой из следующих методов, чтобы выбрать, где Kubernetes планирует конкретные Pod'ы:

- поле `nodeSelector`, сопоставляемое с метками узлов;
- affinity и anti-affinity;
- поле `nodeName`;
- ограничения распространения топологии Pod'ов (Pod topology spread constraints).

## Метки узлов

Как и многие другие объекты Kubernetes, узлы имеют **метки**. Метки можно прикреплять вручную. Kubernetes также заполняет **стандартный набор меток** на всех узлах кластера.

> **Примечание:** значение этих меток зависит от облачного провайдера и **не гарантируется надёжным**. Например, значение `kubernetes.io/hostname` может совпадать с именем узла в одних средах и отличаться в других.

### Изоляция/ограничение узлов

Добавление меток к узлам позволяет нацеливать Pod'ы для планирования на конкретные узлы или группы узлов. Эту функциональность можно использовать, чтобы гарантировать, что конкретные Pod'ы работают только на узлах с определёнными свойствами изоляции, безопасности или соответствия нормативам.

Если вы используете метки для изоляции узлов, выбирайте **ключи меток, которые kubelet не может изменить**. Это не даёт скомпрометированному узлу установить эти метки на себя, чтобы планировщик направил workload'ы на скомпрометированный узел.

Admission-плагин **`NodeRestriction`** не даёт kubelet устанавливать или изменять метки с префиксом `node-restriction.kubernetes.io/`.

Чтобы использовать этот префикс для изоляции узлов:

- Убедитесь, что используется **Node authorizer** и включён admission-плагин **`NodeRestriction`**.
- Добавьте метки с префиксом `node-restriction.kubernetes.io/` к узлам и используйте эти метки в селекторах узлов. Например: `example.com.node-restriction.kubernetes.io/fips=true` или `example.com.node-restriction.kubernetes.io/pci-dss=true`.

## nodeSelector

`nodeSelector` — **простейшая рекомендованная** форма ограничения выбора узла. Можно добавить поле `nodeSelector` в спецификацию Pod'а и указать метки узлов, которые должен иметь целевой узел. Kubernetes планирует Pod **только на узлы**, у которых есть **каждая** из указанных меток.

См. «Assign Pods to Nodes».

## Affinity и anti-affinity

`nodeSelector` — простейший способ ограничить Pod'ы узлами с конкретными метками. **Affinity и anti-affinity** расширяют типы ограничений, которые можно определить. Некоторые преимущества affinity и anti-affinity:

- Язык affinity/anti-affinity **выразительнее**. `nodeSelector` выбирает только узлы со всеми указанными метками. Affinity/anti-affinity даёт больше контроля над логикой выбора.
- Можно указать, что правило **мягкое (preferred)**, чтобы планировщик всё равно запланировал Pod, если не найдёт подходящего узла.
- Можно ограничить Pod, используя **метки других Pod'ов**, работающих на узле (или в другом топологическом домене), а не только метки узлов, что позволяет определять правила совместного размещения Pod'ов на узле.

Affinity состоит из двух типов:

- **Node affinity** — работает как поле `nodeSelector`, но выразительнее и позволяет задавать мягкие правила.
- **Inter-pod affinity/anti-affinity** — позволяет ограничивать Pod'ы по меткам других Pod'ов.

### Node affinity

Node affinity концептуально похожа на `nodeSelector`: позволяет ограничить, на каких узлах может быть запланирован Pod, на основе меток узлов. Есть два типа node affinity:

| Тип | Поведение |
|---|---|
| **`requiredDuringSchedulingIgnoredDuringExecution`** | Планировщик **не может** запланировать Pod, если правило не выполнено. Работает как `nodeSelector`, но с более выразительным синтаксисом |
| **`preferredDuringSchedulingIgnoredDuringExecution`** | Планировщик **пытается** найти узел, удовлетворяющий правилу. Если подходящего узла нет, планировщик всё равно планирует Pod |

> **Примечание:** в этих типах `IgnoredDuringExecution` означает, что если метки узла изменятся **после** того, как Kubernetes запланировал Pod, Pod **продолжит работать**.

Node affinity задаётся через поле `.spec.affinity.nodeAffinity` в спецификации Pod'а.

Пример:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: with-node-affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - antarctica-east1
            - antarctica-west1
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
          - key: another-node-label-key
            operator: In
            values:
            - another-node-label-value
  containers:
  - name: with-node-affinity
    image: registry.k8s.io/pause:3.8
```

В этом примере применяются правила:

- Узел **должен** иметь метку с ключом `topology.kubernetes.io/zone`, и значение этой метки должно быть `antarctica-east1` или `antarctica-west1`.
- Узел **предпочтительно** имеет метку с ключом `another-node-label-key` и значением `another-node-label-value`.

Поле `operator` задаёт логический оператор для интерпретации правил: `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`.

`NotIn` и `DoesNotExist` позволяют определить поведение **node anti-affinity**. Альтернативно можно использовать **taint'ы узлов**, чтобы отталкивать Pod'ы от конкретных узлов.

> **Примечание:**
> - Если заданы и `nodeSelector`, и `nodeAffinity`, **оба** должны быть выполнены, чтобы Pod был запланирован на узел.
> - Если в `nodeSelectorTerms`, связанных с типами `nodeAffinity`, указано **несколько terms**, Pod может быть запланирован на узел, если **хотя бы один** из terms выполнен (terms объединяются через **OR**).
> - Если в одном поле `matchExpressions`, связанном с term в `nodeSelectorTerms`, указано **несколько expressions**, Pod может быть запланирован на узел, только если **все** expressions выполнены (expressions объединяются через **AND**).

### Вес node affinity

Можно задать **вес от 1 до 100** для каждого экземпляра типа affinity `preferredDuringSchedulingIgnoredDuringExecution`. Когда планировщик находит узлы, удовлетворяющие всем другим требованиям планирования Pod'а, он перебирает каждое preferred-правило, которому узел удовлетворяет, и **добавляет значение веса** этого выражения к сумме.

Итоговая сумма добавляется к оценке других priority-функций для узла. Узлы с **наивысшей итоговой оценкой** имеют приоритет, когда планировщик принимает решение о планировании Pod'а.

Пример:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: with-affinity-preferred-weight
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/os
            operator: In
            values:
            - linux
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
          - key: label-1
            operator: In
            values:
            - key-1
      - weight: 50
        preference:
          matchExpressions:
          - key: label-2
            operator: In
            values:
            - key-2
  containers:
  - name: with-node-affinity
    image: registry.k8s.io/pause:3.8
```

Если есть два возможных узла, удовлетворяющих правилу `preferredDuringSchedulingIgnoredDuringExecution` — один с меткой `label-1:key-1`, другой с `label-2:key-2` — планировщик учитывает вес каждого узла, добавляет вес к другим оценкам узла и планирует Pod на узел с **наивысшей итоговой оценкой**.

> **Примечание:** чтобы Kubernetes успешно запланировал Pod'ы в этом примере, у вас должны быть существующие узлы с меткой `kubernetes.io/os=linux`.

### Node affinity для профиля планирования

**Beta с Kubernetes v1.20.**

При настройке нескольких профилей планирования можно связать профиль с node affinity — полезно, если профиль применяется только к определённому набору узлов. Для этого добавьте `addedAffinity` в поле `args` плагина `NodeAffinity` в конфигурации планировщика:

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration

profiles:
  - schedulerName: default-scheduler
  - schedulerName: foo-scheduler
    pluginConfig:
      - name: NodeAffinity
        args:
          addedAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              nodeSelectorTerms:
              - matchExpressions:
                - key: scheduler-profile
                  operator: In
                  values:
                  - foo
```

`addedAffinity` применяется ко всем Pod'ам, у которых `.spec.schedulerName` равен `foo-scheduler`, **в дополнение** к `NodeAffinity`, указанной в PodSpec. То есть для соответствия Pod'у узлы должны удовлетворять и `addedAffinity`, и `.spec.NodeAffinity` Pod'а.

Поскольку `addedAffinity` **не видна конечным пользователям**, её поведение может быть для них неожиданным. Используйте метки узлов с чёткой корреляцией с именем профиля планировщика.

> **Примечание:** контроллер DaemonSet, создающий Pod'ы для DaemonSet'ов, **не поддерживает** профили планирования. Когда контроллер DaemonSet создаёт Pod'ы, стандартный планировщик Kubernetes размещает эти Pod'ы и соблюдает любые правила `nodeAffinity` в контроллере DaemonSet.

### Inter-pod affinity и anti-affinity

Inter-pod affinity и anti-affinity позволяют ограничить, на каких узлах могут быть запланированы Pod'ы, на основе **меток Pod'ов, уже работающих на этом узле**, а не меток узла.

**Типы.** Inter-pod affinity и anti-affinity имеют форму «этот Pod должен (или, в случае anti-affinity, не должен) работать в X, если X уже работает с одним или несколькими Pod'ами, удовлетворяющими правилу Y», где X — топологический домен (узел, стойка, зона или регион облачного провайдера и т.п.), а Y — правило, которое Kubernetes пытается выполнить.

Эти правила (Y) выражаются как **селекторы меток** с опциональным списком пространств имён. Pod'ы — объекты с пространством имён в Kubernetes, поэтому метки Pod'ов неявно имеют пространства имён. Любые селекторы меток Pod'ов должны указывать пространства имён, в которых Kubernetes должен искать эти метки.

Топологический домен (X) выражается через **`topologyKey`** — ключ метки узла, который система использует для обозначения домена.

> **Примечание:** inter-pod affinity и anti-affinity требуют **существенных объёмов обработки**, что может значительно замедлить планирование в больших кластерах. **Не рекомендуется** использовать их в кластерах крупнее нескольких сотен узлов.

> **Примечание:** pod anti-affinity требует, чтобы узлы были **последовательно помечены**, то есть каждый узел в кластере должен иметь подходящую метку, соответствующую `topologyKey`. Если некоторые или все узлы не имеют указанной метки `topologyKey`, это может привести к нежелательному поведению.

Подобно node affinity, есть два типа Pod affinity и anti-affinity:

- `requiredDuringSchedulingIgnoredDuringExecution`
- `preferredDuringSchedulingIgnoredDuringExecution`

Например, можно использовать affinity `requiredDuringSchedulingIgnoredDuringExecution`, чтобы сказать планировщику разместить Pod'ы двух сервисов в одной зоне облачного провайдера, поскольку они много общаются. Аналогично можно использовать anti-affinity `preferredDuringSchedulingIgnoredDuringExecution`, чтобы распределить Pod'ы сервиса по нескольким зонам облачного провайдера.

Для inter-pod affinity используется поле `affinity.podAffinity` в спецификации Pod'а. Для inter-pod anti-affinity — `affinity.podAntiAffinity`.

### Поведение планирования

При планировании нового Pod'а планировщик Kubernetes оценивает правила affinity/anti-affinity Pod'а в контексте **текущего состояния кластера**:

| Категория | Что учитывается |
|---|---|
| **Жёсткие ограничения (Node Filtering)** | `podAffinity.requiredDuringSchedulingIgnoredDuringExecution` и `podAntiAffinity.requiredDuringSchedulingIgnoredDuringExecution`: планировщик гарантирует, что новый Pod назначен узлам, удовлетворяющим этим обязательным правилам affinity и anti-affinity на основе **существующих Pod'ов** |
| **Мягкие ограничения (Scoring)** | `podAffinity.preferredDuringSchedulingIgnoredDuringExecution` и `podAntiAffinity.preferredDuringSchedulingIgnoredDuringExecution`: планировщик оценивает узлы по тому, насколько хорошо они удовлетворяют этим предпочтительным правилам affinity и anti-affinity, чтобы оптимизировать размещение Pod'а |
| **Игнорируемые поля** | Preferred-правила affinity **существующих** Pod'ов (`podAffinity.preferredDuringSchedulingIgnoredDuringExecution`) не учитываются при решении о планировании новых Pod'ов. Аналогично preferred-правила anti-affinity существующих Pod'ов игнорируются при планировании |

### Планирование группы Pod'ов с inter-pod affinity к самим себе

Если текущий планируемый Pod — **первый** в серии Pod'ов, имеющих affinity к самим себе, ему **разрешено** быть запланированным, если он проходит все остальные проверки affinity. Это определяется проверкой, что ни один другой Pod в кластере не соответствует namespace и селектору этого Pod'а, что Pod соответствует своим собственным terms и что выбранный узел соответствует всем запрошенным топологиям. Это гарантирует, что **не будет deadlock'а**, даже если все Pod'ы имеют заданную inter-pod affinity.

### Пример Pod affinity

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: with-pod-affinity
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: security
            operator: In
            values:
            - S1
        topologyKey: topology.kubernetes.io/zone
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: security
              operator: In
              values:
              - S2
          topologyKey: topology.kubernetes.io/zone
  containers:
  - name: with-pod-affinity
    image: registry.k8s.io/pause:3.8
```

В этом примере одно правило Pod affinity и одно правило Pod anti-affinity. Правило affinity использует **жёсткое** `requiredDuringSchedulingIgnoredDuringExecution`, а anti-affinity — **мягкое** `preferredDuringSchedulingIgnoredDuringExecution`.

- Правило affinity: планировщику **разрешено** размещать пример Pod'а на узле, только если этот узел принадлежит конкретной зоне, где другие Pod'ы помечены `security=S1`. Например, если есть зона «Zone V» с узлами `topology.kubernetes.io/zone=V`, планировщик может назначить Pod любому узлу в Zone V, если в Zone V есть хотя бы один Pod с меткой `security=S1`. И наоборот, если в Zone V нет Pod'ов с `security=S1`, планировщик **не назначит** Pod ни одному узлу в этой зоне.
- Правило anti-affinity: планировщик должен **избегать** размещения Pod'а на узле, если этот узел принадлежит конкретной зоне, где другие Pod'ы помечены `security=S2`. Например, если есть зона «Zone R» с узлами `topology.kubernetes.io/zone=R`, планировщик должен избегать назначения Pod'а любому узлу в Zone R, если в Zone R есть хотя бы один Pod с меткой `security=S2`. И наоборот, anti-affinity **не влияет** на планирование в Zone R, если Pod'ов с `security=S2` нет.

В поле `operator` для Pod affinity и anti-affinity можно использовать `In`, `NotIn`, `Exists` и `DoesNotExist`.

В принципе `topologyKey` может быть любым допустимым ключом метки, за следующими исключениями из соображений производительности и безопасности:

- Для Pod affinity и anti-affinity **пустое поле `topologyKey` не допускается** ни в `requiredDuringSchedulingIgnoredDuringExecution`, ни в `preferredDuringSchedulingIgnoredDuringExecution`.
- Для правил Pod anti-affinity `requiredDuringSchedulingIgnoredDuringExecution` admission-контроллер `LimitPodHardAntiAffinityTopology` ограничивает `topologyKey` значением `kubernetes.io/hostname`. Можно изменить или отключить этот admission-контроллер, если нужно разрешить пользовательские топологии.

Помимо `labelSelector` и `topologyKey`, можно опционально указать список пространств имён, с которыми должен сопоставляться `labelSelector`, используя поле `namespaces` на том же уровне, что и `labelSelector` и `topologyKey`. Если опущено или пусто, `namespaces` по умолчанию равно пространству имён Pod'а, где появляется определение affinity/anti-affinity.

### Namespace Selector

**Стабильно с Kubernetes v1.24.**

Можно также выбирать совпадающие пространства имён через **`namespaceSelector`** — это запрос по меткам к набору пространств имён. Term affinity применяется к пространствам имён, выбранным **и** `namespaceSelector`, **и** полем `namespaces`. Заметьте: пустой `namespaceSelector` (`{}`) соответствует **всем** пространствам имён, тогда как `null` или пустой список `namespaces` и `null` `namespaceSelector` соответствуют пространству имён Pod'а, где определено правило.

### matchLabelKeys

**Стабильно с Kubernetes v1.33.** Впервые появилось в v1.29. Отключить нельзя (функция заблокирована); если явно задать значение для feature gate `MatchLabelKeysInPodAffinity`, Kubernetes его проигнорирует без ошибки.

> **Примечание:** поле `matchLabelKeys` — beta-уровня и включено по умолчанию в Kubernetes 1.37. Чтобы отключить его, нужно явно отключить через feature gate `MatchLabelKeysInPodAffinity`.

Kubernetes включает опциональное поле **`matchLabelKeys`** для Pod affinity или anti-affinity. Поле задаёт ключи меток, которые должны совпадать с метками входящего Pod'а при выполнении Pod (anti)affinity.

Ключи используются для поиска значений из меток Pod'а; эти пары «ключ-значение» объединяются (через **AND**) с ограничениями соответствия, определёнными через поле `labelSelector`. Объединённая фильтрация выбирает набор существующих Pod'ов, которые будут учтены в расчёте Pod (anti)affinity.

> **⚠️ Внимание:** **не рекомендуется** использовать `matchLabelKeys` с метками, которые могут обновляться напрямую на Pod'ах. Даже если вы отредактируете метку Pod'а, указанную в `matchLabelKeys`, напрямую (то есть не через Deployment), kube-apiserver **не отразит** обновление метки в объединённом `labelSelector`.

Распространённый сценарий — использовать `matchLabelKeys` с `pod-template-hash` (устанавливается на Pod'ах, управляемых как часть Deployment, где значение уникально для каждой ревизии). Использование `pod-template-hash` в `matchLabelKeys` позволяет нацеливаться на Pod'ы, принадлежащие **той же ревизии**, что и входящий Pod, чтобы rolling upgrade не нарушил affinity.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: application-server
...
spec:
  template:
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - database
            topologyKey: topology.kubernetes.io/zone
            # Only Pods from a given rollout are taken into consideration when calculating pod affinity.
            # If you update the Deployment, the replacement Pods follow their own affinity rules
            # (if there are any defined in the new Pod template)
            matchLabelKeys:
            - pod-template-hash
```

### mismatchLabelKeys

**Стабильно с Kubernetes v1.33.** Впервые появилось в v1.29. Отключить нельзя (функция заблокирована); если явно задать значение для feature gate `MatchLabelKeysInPodAffinity`, Kubernetes его проигнорирует без ошибки.

> **Примечание:** поле `mismatchLabelKeys` — beta-уровня и включено по умолчанию в Kubernetes 1.37. Чтобы отключить его, нужно явно отключить через feature gate `MatchLabelKeysInPodAffinity`.

Kubernetes включает опциональное поле **`mismatchLabelKeys`** для Pod affinity или anti-affinity. Поле задаёт ключи меток, которые **не должны** совпадать с метками входящего Pod'а при выполнении Pod (anti)affinity.

> **⚠️ Внимание:** **не рекомендуется** использовать `mismatchLabelKeys` с метками, которые могут обновляться напрямую на Pod'ах. Даже если вы отредактируете метку Pod'а, указанную в `mismatchLabelKeys`, напрямую (то есть не через Deployment), kube-apiserver **не отразит** обновление метки в объединённом `labelSelector`.

Один из примеров использования — обеспечить, чтобы Pod'ы попадали в топологический домен (узел, зона и т.д.), где планируются только Pod'ы того же тенанта или команды. Иными словами, вы хотите избежать одновременной работы Pod'ов двух разных тенантов в одном топологическом домене.

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    # Assume that all relevant Pods have a "tenant" label set
    tenant: tenant-a
...
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      # ensure that Pods associated with this tenant land on the correct node pool
      - matchLabelKeys:
          - tenant
        labelSelector: {}
        topologyKey: node-pool
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      # ensure that Pods associated with this tenant can't schedule to nodes used for another tenant
      - mismatchLabelKeys:
        - tenant # whatever the value of the "tenant" label for this Pod, prevent
                 # scheduling to nodes in any pool where any Pod from a different
                 # tenant is running.
        labelSelector:
          # We have to have the labelSelector which selects only Pods with the tenant label,
          # otherwise this Pod would have anti-affinity against Pods from daemonsets as well, for example,
          # which aren't supposed to have the tenant label.
          matchExpressions:
          - key: tenant
            operator: Exists
        topologyKey: node-pool
```

### Более практичные сценарии

Inter-pod affinity и anti-affinity могут быть ещё полезнее в сочетании с коллекциями более высокого уровня, такими как ReplicaSet, StatefulSet, Deployment и т.д. Эти правила позволяют настроить, что набор workload'ов должен быть совместно размещён в одной определённой топологии; например, предпочитать размещать два связанных Pod'а на одном узле.

Пример: представьте кластер из трёх узлов. Вы используете кластер для запуска веб-приложения и in-memory кеша (например, Redis). Предположим, что задержка между веб-приложением и кешем должна быть как можно ниже. Можно использовать inter-pod affinity и anti-affinity, чтобы как можно плотнее разместить веб-серверы с кешем.

**Deployment для кеша Redis:** реплики получают метку `app=store`. Правило `podAntiAffinity` говорит планировщику **избегать** размещения нескольких реплик с меткой `app=store` на одном узле. Это создаёт каждый кеш на отдельном узле.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis-cache
spec:
  selector:
    matchLabels:
      app: store
  replicas: 3
  template:
    metadata:
      labels:
        app: store
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - store
            topologyKey: "kubernetes.io/hostname"
      containers:
      - name: redis-server
        image: redis:3.2-alpine
```

**Deployment для веб-серверов:** реплики получают метку `app=web-store`. Правило Pod affinity говорит планировщику размещать каждую реплику на узле, где есть Pod с меткой `app=store`. Правило Pod anti-affinity говорит планировщику **никогда** не размещать несколько серверов `app=web-store` на одном узле.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-server
spec:
  selector:
    matchLabels:
      app: web-store
  replicas: 3
  template:
    metadata:
      labels:
        app: web-store
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-store
            topologyKey: "kubernetes.io/hostname"
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - store
            topologyKey: "kubernetes.io/hostname"
      containers:
      - name: web-app
        image: nginx:1.16-alpine
```

Создание этих двух Deployment'ов даёт следующую раскладку кластера, где каждый веб-сервер размещён совместно с кешем, на трёх отдельных узлах:

```
node-1        node-2        node-3
webserver-1   webserver-2   webserver-3
cache-1       cache-2       cache-3
```

Общий эффект: каждый экземпляр кеша, скорее всего, будет доступен одному клиенту, работающему на том же узле. Этот подход направлен на минимизацию как **перекоса** (несбалансированной нагрузки), так и **задержки**.

Могут быть и другие причины использовать Pod anti-affinity. См. туториал по ZooKeeper для примера StatefulSet, настроенного с anti-affinity для высокой доступности, использующего ту же технику.

## nodeName

`nodeName` — более **прямая** форма выбора узла, чем affinity или `nodeSelector`. `nodeName` — поле в спецификации Pod'а. Если поле `nodeName` не пусто, планировщик **игнорирует** Pod, а kubelet на указанном узле пытается разместить Pod на этом узле. Использование `nodeName` **переопределяет** использование `nodeSelector` или правил affinity и anti-affinity.

Некоторые ограничения использования `nodeName` для выбора узлов:

- Если указанный узел **не существует**, Pod не запустится, а в некоторых случаях может быть автоматически удалён.
- Если на указанном узле **недостаточно ресурсов** для Pod'а, Pod упадёт, и причина будет указана (например, `OutOfmemory` или `OutOfcpu`).
- Имена узлов в облачных средах **не всегда предсказуемы или стабильны**.

> **⚠️ Предупреждение:** `nodeName` предназначен для использования **кастомными планировщиками** или расширенными сценариями, где нужно **обойти** любые настроенные планировщики. Обход планировщиков может привести к падению Pod'ов, если назначенные узлы перегружены. Можно использовать node affinity или поле `nodeSelector`, чтобы назначить Pod конкретному узлу **без обхода** планировщиков.

Пример спецификации Pod'а с полем `nodeName`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx
  nodeName: kube-01
```

Этот Pod будет работать **только** на узле `kube-01`.

## nominatedNodeName

**Beta с Kubernetes v1.35; включено по умолчанию.**

`nominatedNodeName` может использоваться внешними компонентами, чтобы **номинировать** узел для pending-Pod'а. Эта номинация — **best effort**: она может быть проигнорирована, если планировщик решит, что Pod не может пойти на номинированный узел.

Также это поле может быть **(пере)записано** планировщиком:

- если планировщик находит узел для номинации через **preemption**;
- если планировщик решает, куда пойдёт Pod, и перемещает его в цикл привязки. Заметьте: в этом случае `nominatedNodeName` ставится только тогда, когда Pod должен пройти через точки расширения `WaitOnPermit` или `PreBind`.

Пример статуса Pod'а с полем `nominatedNodeName`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
...
status:
  nominatedNodeName: kube-01
```

## Ограничения распространения топологии Pod'ов

Можно использовать **topology spread constraints**, чтобы контролировать, как Pod'ы распределяются по кластеру между доменами отказа, такими как регионы, зоны, узлы или любые другие определённые вами топологические домены. Это может делаться для улучшения производительности, ожидаемой доступности или общего использования ресурсов.

Подробнее см. «Pod topology spread constraints».

## Метки топологии Pod'а

**Beta с Kubernetes v1.35; включено по умолчанию.**

Pod'ы **наследуют** метки топологии (`topology.kubernetes.io/zone` и `topology.kubernetes.io/region`) от назначенного им узла, если эти метки присутствуют. Эти метки затем можно использовать через Downward API, чтобы дать workload'у **осведомлённость о топологии узла**.

Пример Pod'а, использующего downward API для своей зоны и региона:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-with-topology-labels
spec:
  containers:
    - name: app
      image: alpine
      command: ["sh", "-c", "env"]
      env:
        - name: MY_ZONE
          valueFrom:
            fieldRef:
              fieldPath: metadata.labels['topology.kubernetes.io/zone']
        - name: MY_REGION
          valueFrom:
            fieldRef:
              fieldPath: metadata.labels['topology.kubernetes.io/region']
```

## Операторы

Все логические операторы, которые можно использовать в поле `operator` для `nodeAffinity` и `podAffinity`:

| Оператор | Поведение |
|---|---|
| `In` | Значение метки присутствует в заданном наборе строк |
| `NotIn` | Значение метки отсутствует в заданном наборе строк |
| `Exists` | Метка с этим ключом существует на объекте |
| `DoesNotExist` | Метки с этим ключом не существует на объекте |

Следующие операторы можно использовать **только с `nodeAffinity`**:

| Оператор | Поведение |
|---|---|
| `Gt` | Значение поля будет разобрано как целое, и целое, полученное в результате разбора значения метки, больше этого целого |
| `Lt` | Значение поля будет разобрано как целое, и целое, полученное в результате разбора значения метки, меньше этого целого |

> **Примечание:** операторы `Gt` и `Lt` **не работают** с нецелыми значениями. Если заданное значение не разбирается как целое, Pod **не будет запланирован**. Также `Gt` и `Lt` **недоступны** для `podAffinity`.
