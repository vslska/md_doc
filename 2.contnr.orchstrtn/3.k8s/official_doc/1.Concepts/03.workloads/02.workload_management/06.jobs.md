## Архитектурная модель и принципы функционирования

**Job** создаёт один или несколько Pod и повторяет попытки их запуска, пока заданное количество Pod не завершится успешно. По мере успешного завершения Pod Job учитывает количество выполнений. Когда достигается заданное число успешных завершений, задача (то есть Job) считается выполненной. При удалении Job удаляются и созданные им Pod. При приостановке Job все активные Pod удаляются до возобновления его работы.

В простейшем случае создают один объект Job, чтобы гарантированно выполнить один Pod до завершения. Если первый Pod завершится с ошибкой или будет удалён (например, из-за аппаратного сбоя узла или его перезагрузки), Job запустит новый Pod.

Job также можно использовать для параллельного запуска нескольких Pod.

Если требуется запускать Job по расписанию — как для одной задачи, так и для нескольких параллельных задач, — см. раздел о CronJob.

## Пример запуска Job

Ниже приведён пример конфигурации Job. Она вычисляет число π с точностью до 2000 знаков и выводит результат. Выполнение занимает около 10 секунд.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: pi
spec:
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34.0
        command: ["perl",  "-Mbignum=bpi", "-wle", "print bpi(2000)"]
      restartPolicy: Never
  backoffLimit: 4
```

Запустите пример следующей командой:

```bash
kubectl apply -f https://kubernetes.io/examples/controllers/job.yaml
```

Результат будет примерно таким:

```bash
job.batch/pi created
```

## Описание спецификации Job

Как и любая другая конфигурация Kubernetes, Job должен содержать поля `apiVersion`, `kind` и `metadata`.

Когда control plane создаёт новые Pod для Job, имя Job (`.metadata.name`) используется как одна из составляющих имён этих Pod. Имя Job должно быть допустимым именем DNS-поддомена, однако это может привести к неожиданным результатам при формировании имён хостов Pod. Для наилучшей совместимости рекомендуется соблюдать более строгие правила именования DNS-меток. Даже если имя соответствует требованиям к DNS-поддомену, его длина не должна превышать 63 символа.

Job также должен содержать раздел `.spec`.

### Метки Job

Для меток `job-name` и `controller-uid` используется префикс `batch.kubernetes.io/`.

### Шаблон Pod

`.spec.template` — единственное обязательное поле в `.spec`.

`.spec.template` представляет собой шаблон Pod. Его схема полностью совпадает со схемой Pod, за исключением того, что шаблон вложен в другой объект и не содержит полей `apiVersion` и `kind`.

Помимо обязательных полей Pod, шаблон Pod в Job должен задавать соответствующие метки (см. раздел о селекторе Pod) и подходящую политику перезапуска.

Допустимы только значения `Never` и `OnFailure` для `RestartPolicy`.

### Селектор Pod

Поле `.spec.selector` необязательно. В подавляющем большинстве случаев указывать его не следует. См. раздел об указании собственного селектора Pod.

### Параллельное выполнение Job

Существует три основных типа задач, подходящих для выполнения с помощью Job.

- Непараллельные Job
    
    - Обычно запускается только один Pod, если только он не завершится с ошибкой.
        
    - Job считается выполненным, как только Pod успешно завершится.
        
    
- Параллельные Job с фиксированным количеством завершений
    
    - Укажите положительное ненулевое значение `.spec.completions`.
        
    - Job представляет собой общую задачу и считается выполненным, когда успешно завершится заданное количество Pod, равное `.spec.completions`.
        
    - Если используется `.spec.completionMode="Indexed"`, каждому Pod назначается уникальный индекс в диапазоне от `0` до `.spec.completions-1`.
        
    
- Параллельные Job с очередью задач
    
    - Не указывайте `.spec.completions`; по умолчанию используется значение `.spec.parallelism`.
        
    - Pod должны координировать работу друг с другом или с внешней службой, чтобы определить, какие задачи выполнять. Например, Pod может получать из очереди пакеты, содержащие до N элементов.
        
    - Каждый Pod самостоятельно определяет, завершили ли работу остальные Pod и, следовательно, выполнена ли Job целиком.
        
    - После успешного завершения любого Pod из Job новые Pod не создаются.
        
    - Если хотя бы один Pod завершился успешно и все Pod завершили работу, Job считается успешно выполненным.
        
    - После успешного завершения любого Pod остальные Pod не должны продолжать выполнять задачи этой Job или записывать результаты. Они должны завершать работу.
        
    

Для непараллельной Job можно не указывать ни `.spec.completions`, ни `.spec.parallelism`. Если оба поля не заданы, их значения по умолчанию равны `1`.

Для Job с фиксированным количеством завершений задайте `.spec.completions`, равное требуемому количеству успешных завершений. Поле `.spec.parallelism` можно указать явно или оставить без значения — в последнем случае оно будет равно `1`.

Для Job с очередью задач необходимо не указывать `.spec.completions` и задать `.spec.parallelism` как неотрицательное целое число.

Подробнее об использовании разных типов Job см. в разделе о шаблонах выполнения Job.

### Управление параллелизмом

Требуемое количество параллельно выполняемых Pod задаётся полем `.spec.parallelism`, которое может принимать любое неотрицательное значение. Если поле не указано, по умолчанию используется `1`. Если указать `0`, выполнение Job фактически приостанавливается до тех пор, пока значение не будет увеличено.

Фактическое количество одновременно работающих Pod может отличаться от заданного по нескольким причинам:

- Для Job с фиксированным количеством завершений фактическое количество одновременно работающих Pod не превышает число оставшихся завершений. Более высокие значения `.spec.parallelism` фактически игнорируются.
    
- Для Job с очередью задач новые Pod не запускаются после успешного завершения любого Pod, однако уже работающим Pod разрешается закончить выполнение.
    
- Контроллер Job может не успеть отреагировать на изменения.
    
- Если контроллеру Job не удалось создать Pod по какой-либо причине (например, из-за ограничений `ResourceQuota` или недостатка разрешений), Pod может оказаться меньше, чем запрошено.
    
- Контроллер Job может ограничивать создание новых Pod из-за большого количества предыдущих сбоев Pod в той же Job.
    
- При корректном завершении Pod требуется время на остановку.
    

### Режим завершения

Состояние функции: стабильная начиная с Kubernetes v1.24

Для Job с фиксированным количеством завершений, то есть с ненулевым `.spec.completions`, можно задать режим завершения в поле `.spec.completionMode`.

- `NonIndexed` (по умолчанию): Job считается выполненной, когда успешно завершилось количество Pod, равное `.spec.completions`. Иными словами, успешное завершение любого Pod считается равнозначным завершению другого. Если `.spec.completions` не задано, режим неявно считается `NonIndexed`.

- `Indexed`: каждому Pod назначается индекс завершения в диапазоне от `0` до `.spec.completions-1`. Получить индекс можно четырьмя способами:

- Через аннотацию Pod `batch.kubernetes.io/job-completion-index`.
    
- Через метку Pod `batch.kubernetes.io/job-completion-index` (начиная с версии v1.28). Для использования этой метки должен быть включён механизм управления функциями `PodIndexLabel`; по умолчанию он включён.
    
- Из имени хоста Pod, формируемого по шаблону `$(job-name)-$(index)`. При использовании Indexed Job совместно с Service Pod могут обращаться друг к другу через DNS по предсказуемым именам хостов. Подробнее см. раздел о взаимодействии Pod друг с другом в Job.
    
- Из переменной окружения `JOB_COMPLETION_INDEX` внутри контейнеризованной задачи.
    

Job считается выполненной, когда для каждого индекса успешно завершился один Pod. Подробнее об этом режиме см. раздел об Indexed Job для параллельной обработки со статическим распределением задач.

Примечание.

В редких случаях для одного индекса может быть запущено несколько Pod, например из-за сбоя узла, перезапуска kubelet или вытеснения Pod. В таком случае в общее число завершений засчитывается только первый успешно завершившийся Pod, и только он обновляет состояние Job. После обнаружения остальные работающие или завершившиеся Pod с тем же индексом будут удалены контроллером Job.

### Интеграция с API Workload

Состояние функции: Alpha начиная с Kubernetes v1.36; по умолчанию отключена

Подробнее об этой функции

Если включён механизм управления функциями `WorkloadWithJob`, перед созданием Pod контроллер Job преобразует конфигурацию планирования `.spec.scheduling` в объекты Workload и PodGroup (`scheduling.k8s.io/v1beta1`). Это позволяет явно задавать требования к планированию Job, например gang scheduling (совместное размещение всех Pod либо отказ от размещения), совместное размещение с учётом топологии и правила обработки прерываний.

Если `.spec.scheduling` не задано, Job использует базовую политику планирования Basic, сохраняющую стандартное поведение: каждый Pod планируется независимо, как в обычной Job. Контроллер всё равно создаёт объекты Workload и PodGroup для каждой подходящей Job, в том числе для Job с политикой Basic. Поэтому наблюдаемые объекты остаются согласованными независимо от выбранной политики.

#### Конфигурация планирования

Поле `.spec.scheduling` поддерживает следующие параметры:

- `schedulingPolicy`: необходимо указать ровно одно значение — `basic` или `gang`. При использовании `gang` все Pod должны иметь возможность быть запланированными совместно, прежде чем любой из них будет привязан к узлу. Если `gang.minCount` не задано, по умолчанию используется `.spec.parallelism` Job. См. политики планирования PodGroup.
    
- `schedulingConstraints`: ограничения на совместное размещение Pod Job с учётом топологии.
    
- `disruptionMode`: определяет, прерываются ли Pod по отдельности (`single`) или группой (`all`). См. раздел о прерываниях и приоритетах.
    
- `resourceClaims`: динамические запросы ресурсов, совместно используемых Pod Job.
    

После создания Job все поля `.spec.scheduling` неизменяемы, кроме `schedulingPolicy.gang.minCount`, которое можно менять для эластичного масштабирования группы.

#### Gang scheduling

Следующая Job запрашивает совместное планирование восьми Pod в пределах одной зоны с групповым прерыванием:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: distributed-training
  namespace: training
spec:
  parallelism: 8
  completions: 8
  completionMode: Indexed
  scheduling:
    schedulingPolicy:
      gang: {}                # minCount omitted -> defaults to parallelism (8)
    schedulingConstraints:
      key:
      - level: topology.kubernetes.io/zone
    disruptionMode:
      all: {}                 # the entire group is disrupted together
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: trainer
        image: training-image:latest
        resources:
          limits:
            nvidia.com/gpu: 1
```

При обработке этой Job контроллер:

- Создаёт объект Workload в том же пространстве имён. В нём содержится `podGroupTemplate`, сформированный на основе `.spec.scheduling` (в данном случае — политика `gang` с `minCount: 8`).
    
- Создаёт объект PodGroup на основе этого шаблона. PodGroup представляет собой единицу планирования во время выполнения и содержит встроенную копию политики.
    
- Создаёт Pod, указывая в `.spec.schedulingGroup.podGroupName` имя PodGroup и связывая каждый Pod с соответствующей группой планирования.
    

Контроллер обнаруживает эти объекты по ссылкам в спецификациях (`Workload.spec.controllerRef` и `PodGroup.spec.workloadRef`), а не по именам. Для созданных контроллером объектов указывается `ownerReferences` со ссылкой на Job, поэтому при удалении Job они также удаляются сборщиком мусора.

#### Планирование по умолчанию (Basic)

Если `.spec.scheduling` не указано, Job по умолчанию использует Basic. Это означает, что совместное планирование группы Pod не требуется. Pod планируются так же, как в обычной Job, но при этом всё равно создаются Workload и PodGroup с политикой Basic.

```
apiVersion: batch/v1
kind: Job
metadata:
  name: batch-processor
  namespace: batch
spec:
  parallelism: 10
  completions: 10
  # .spec.scheduling omitted -> defaults to Basic scheduling.
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: processor
        image: processor-image:v1
```

#### Контроллеры более высокого уровня

Для автономной Job контроллер Job управляет как Workload, так и PodGroup. Если же у Job есть `ownerReference` на родительский контроллер, который формирует Workload (например, JobSet), контроллер Job передаёт управление Workload родительскому контроллеру. Создание runtime-объекта PodGroup зависит от того, что именно делегирует родительский контроллер:

- Если родительский контроллер задаёт в Job аннотацию `scheduling.k8s.io/group-template-name`, контроллер Job создаёт PodGroup и управляет им, используя указанный родителем `PodGroupTemplate`.
    
- В противном случае родительский контроллер управляет обоими объектами, а контроллер Job не создаёт ни один из них. Он обнаруживает уже существующие объекты и использует их при создании Pod.
    

Если шаблон Pod в Job уже содержит `.spec.template.spec.schedulingGroup`, контроллер Job не создаёт ни один из этих объектов. Это позволяет вам или контроллеру более высокого уровня самостоятельно управлять жизненным циклом Workload и PodGroup.

#### Поведение CronJob

Job, создаваемые CronJob, являются автономными: CronJob не создаёт объекты Workload и не управляет ими. Если в `jobTemplate` CronJob задано `.spec.scheduling`, контроллер Job создаёт отдельные Workload и PodGroup для каждого экземпляра Job на основе его `.spec.scheduling`. Если поле не указано, используется политика Basic. Эти объекты удаляются сборщиком мусора после завершения или удаления соответствующей Job.

#### Ограничения альфа-версии

- Каждая Job соответствует ровно одному PodGroup; все Pod в Job используют единую политику планирования.
    
- Изменять можно только `schedulingPolicy.gang.minCount`. Все остальные поля `.spec.scheduling` неизменяемы после создания.
    
- Приостановленные Job сохраняют объекты Workload и PodGroup. Эти объекты не удаляются при приостановке и не создаются заново при возобновлении.
    

### Обработка сбоев Pod и контейнеров

Контейнер в Pod может завершиться с ошибкой по разным причинам: например, процесс завершился с ненулевым кодом возврата или контейнер был остановлен из-за превышения лимита памяти. Если при этом `.spec.template.spec.restartPolicy = "OnFailure"`, Pod остаётся на узле, а контейнер запускается повторно. Поэтому программа должна корректно обрабатывать локальный перезапуск либо следует указать `.spec.template.spec.restartPolicy = "Never"`. Подробнее см. раздел о жизненном цикле Pod и `restartPolicy`.

Весь Pod также может завершиться с ошибкой по разным причинам, например если его удалили с узла из-за обновления, перезагрузки или удаления узла либо если контейнер завершился с ошибкой при `.spec.template.spec.restartPolicy = "Never"`. В этом случае контроллер Job запускает новый Pod. Следовательно, приложение должно корректно работать при перезапуске в новом Pod. В частности, оно должно обрабатывать временные файлы, блокировки, незавершённый вывод и другие последствия предыдущих запусков.

По умолчанию каждый сбой Pod учитывается в лимите повторных попыток `.spec.backoffLimit`. Подробнее см. раздел о политике повторных попыток при сбоях Pod. Однако обработку сбоев можно настроить с помощью политики сбоев Pod в Job.

Кроме того, для Indexed Job можно учитывать сбои Pod независимо для каждого индекса, задав поле `.spec.backoffLimitPerIndex`. Подробнее см. раздел об ограничении повторных попыток для каждого индекса.

Обратите внимание: даже если задать `.spec.parallelism = 1`, `.spec.completions = 1` и `.spec.template.spec.restartPolicy = "Never"`, одна и та же программа иногда может запуститься дважды.

Если и `.spec.parallelism`, и `.spec.completions` больше `1`, несколько Pod могут работать одновременно. Поэтому Pod должны корректно обрабатывать параллельное выполнение.

Если задано поле `.spec.podFailurePolicy`, контроллер Job не считает завершающийся Pod (то есть Pod с установленным полем `.metadata.deletionTimestamp`) завершившимся с ошибкой, пока Pod не перейдёт в терминальное состояние (`.status.phase` станет `Failed` или `Succeeded`). Однако контроллер создаёт замещающий Pod сразу после обнаружения начала завершения. После перехода Pod в терминальное состояние контроллер проверяет `.backoffLimit` и `.podFailurePolicy` соответствующей Job с учётом завершившегося Pod.

Если хотя бы одно из этих условий не выполняется, контроллер Job считает завершающийся Pod немедленно завершившимся с ошибкой, даже если позднее он перейдёт в состояние `Succeeded`.

### Политика повторных попыток при сбоях Pod

В некоторых случаях необходимо завершить Job после определённого количества повторных попыток, например из-за логической ошибки в конфигурации. Для этого задайте `.spec.backoffLimit`, определяющее количество повторных попыток до признания Job неуспешной.

По умолчанию `.spec.backoffLimit` равно `6`, если не задано ограничение повторных попыток для каждого индекса (только для Indexed Job). Если указано `.spec.backoffLimitPerIndex`, значение `.spec.backoffLimit` по умолчанию равно `2147483647` (`MaxInt32`).

Неуспешные Pod, принадлежащие Job, контроллер Job создаёт повторно с экспоненциально возрастающей задержкой (`10s`, `20s`, `40s` и т. д.), но не более десяти минут.

Количество повторных попыток вычисляется двумя способами:

- По количеству Pod, у которых `.status.phase = "Failed"`.
    
- При использовании `restartPolicy = "OnFailure"` — по количеству повторных запусков всех контейнеров в Pod, состояние которых `.status.phase` равно `Pending` или `Running`.
    

Если хотя бы один из этих показателей достигает `.spec.backoffLimit`, Job считается завершившейся с ошибкой.

Примечание.

Если для Job задано `restartPolicy = "OnFailure"`, учитывайте, что Pod, выполняющий задачу, будет остановлен после достижения лимита повторных попыток. Это может затруднить отладку исполняемой программы Job. При отладке рекомендуется задавать `restartPolicy = "Never"` или использовать систему журналирования, чтобы не потерять вывод неуспешных запусков.

### Ограничение повторных попыток для каждого индекса

Состояние функции: стабильная начиная с Kubernetes v1.33

Эта функция является стабильной начиная с Kubernetes v1.33. Впервые она появилась в версии v1.28. Отключить её или отказаться от её использования больше нельзя: функция зафиксирована. Если явно задать значение соответствующего механизма управления функциями `JobBackoffLimitPerIndex`, Kubernetes проигнорирует его и не сообщит об ошибке.

При запуске Indexed Job можно обрабатывать повторные попытки после сбоев Pod независимо для каждого индекса. Для этого задайте `.spec.backoffLimitPerIndex`, определяющее максимальное количество сбоев Pod для одного индекса.

Если для индекса превышен лимит повторных попыток, Kubernetes считает этот индекс завершившимся с ошибкой и добавляет его в поле `.status.failedIndexes`. Индексы, для которых Pod успешно завершились, записываются в `.status.completedIndexes` независимо от того, задано ли поле `backoffLimitPerIndex`.

Сбой одного индекса не прерывает выполнение остальных. Когда все индексы Job завершат работу, если хотя бы один из них завершился с ошибкой, контроллер Job пометит всю Job как неуспешную, установив условие `Failed` в её состоянии. Это произойдёт даже в том случае, если успешно обработана значительная часть индексов, возможно почти все.

Максимальное количество индексов, которые могут завершиться с ошибкой, можно дополнительно ограничить с помощью `.spec.maxFailedIndexes`. Когда число таких индексов превышает указанное значение, контроллер Job инициирует завершение всех оставшихся работающих Pod. После завершения всех Pod контроллер пометит всю Job как неуспешную, установив условие `Failed` в её состоянии.

Пример манифеста Job с параметром `backoffLimitPerIndex`:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: job-backoff-limit-per-index-example
spec:
  completions: 10
  parallelism: 3
  completionMode: Indexed  # required for the feature
  backoffLimitPerIndex: 1  # maximal number of failures per index
  maxFailedIndexes: 5      # maximal number of failed indexes before terminating the Job execution
  template:
    spec:
      restartPolicy: Never # required for the feature
      containers:
      - name: example
        image: python
        command:           # The jobs fails as there is at least one failed index
                           # (all even indexes fail in here), yet all indexes
                           # are executed as maxFailedIndexes is not exceeded.
        - python3
        - -c
        - |
          import os, sys
          print("Hello world")
          if int(os.environ.get("JOB_COMPLETION_INDEX")) % 2 == 0:
            sys.exit(1)
```

В этом примере контроллер Job допускает одну повторную попытку для каждого индекса. Если общее количество индексов, завершившихся с ошибкой, превысит `5`, выполнение всей Job будет остановлено.

После завершения Job её состояние выглядит следующим образом:

```
kubectl get -o yaml job job-backoff-limit-per-index-example
```

```
status:
  completedIndexes: 1,3,5,7,9
  failedIndexes: 0,2,4,6,8
  succeeded: 5          # 1 succeeded pod for each of 5 succeeded indexes
  failed: 10            # 2 failed pods (1 retry) for each of 5 failed indexes
  conditions:
  - message: Job has failed indexes
    reason: FailedIndexes
    status: "True"
    type: FailureTarget
  - message: Job has failed indexes
    reason: FailedIndexes
    status: "True"
    type: Failed
```

Контроллер Job добавляет условие Job `FailureTarget`, чтобы инициировать завершение Job и очистку ресурсов. После завершения всех Pod этой Job контроллер добавляет условие `Failed` с теми же значениями `reason` и `message`, что и у условия `FailureTarget`. Подробнее см. раздел о завершении Pod в Job.

Также можно использовать ограничение повторных попыток для каждого индекса совместно с политикой сбоев Pod. В этом случае доступно новое действие `FailIndex`, позволяющее избежать ненужных повторных попыток для индекса, Pod которого завершился с ошибкой.

### Политика сбоев Pod

Эта функция является стабильной начиная с Kubernetes v1.31. Переключать её больше нельзя, поскольку соответствующий механизм управления функциями удалён.

Политика сбоев Pod, задаваемая полем `.spec.podFailurePolicy`, позволяет кластеру обрабатывать сбои Pod на основе кодов завершения контейнеров и условий Pod.

В некоторых ситуациях требуется более гибко управлять обработкой сбоев Pod, чем позволяет стандартная политика повторных попыток, основанная на `.spec.backoffLimit` Job. Например:

- Чтобы снизить стоимость выполнения рабочих нагрузок и избежать ненужных перезапусков Pod, можно завершать Job сразу после того, как один из её Pod завершится с кодом, указывающим на программную ошибку.
    
- Чтобы гарантировать завершение Job даже при прерываниях, можно игнорировать сбои Pod, вызванные прерываниями (например, вытеснением по приоритету, удалением по запросу API или вытеснением на основе taint), и не учитывать их в лимите повторных попыток `.spec.backoffLimit`.
    

Для этих сценариев можно настроить политику сбоев Pod в поле `.spec.podFailurePolicy`. Она обрабатывает сбои на основе кодов завершения контейнеров и условий Pod.

Пример манифеста Job с `podFailurePolicy`:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: job-pod-failure-policy-example
spec:
  completions: 12
  parallelism: 3
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: main
        image: docker.io/library/bash:5
        command: ["bash"]        # example command simulating a bug which triggers the FailJob action
        args:
        - -c
        - echo "Hello world!" && sleep 5 && exit 42
  backoffLimit: 6
  podFailurePolicy:
    rules:
    - action: FailJob
      onExitCodes:
        containerName: main      # optional
        operator: In             # one of: In, NotIn
        values: [42]
    - action: Ignore             # one of: Ignore, FailJob, Count
      onPodConditions:
      - type: DisruptionTarget   # indicates Pod disruption
```

В этом примере первое правило политики указывает, что Job должна быть помечена как неуспешная, если основной контейнер завершится с кодом `42`. Для основного контейнера действуют следующие правила:

- Код завершения `0` означает, что контейнер завершился успешно.
    
- Код завершения `42` означает, что вся Job завершилась с ошибкой.
    
- Любой другой код означает, что контейнер завершился с ошибкой, а значит, завершился с ошибкой и весь Pod. Pod будет создан повторно, если общее число повторных попыток ещё не достигло `backoffLimit`. При достижении этого лимита вся Job будет помечена как неуспешная.
    

Примечание.

Поскольку в шаблоне Pod задано `restartPolicy: Never`, kubelet не перезапускает основной контейнер в этом Pod.

Второе правило политики сбоев Pod задаёт действие `Ignore` для Pod с условием `DisruptionTarget`. Благодаря этому сбои, вызванные прерыванием работы Pod, не учитываются в лимите повторных попыток `.spec.backoffLimit`.

Примечание.

Если Job завершается с ошибкой из-за политики сбоев Pod или стандартной политики повторных попыток и при этом выполняется несколько Pod, Kubernetes останавливает все Pod этой Job, которые ещё находятся в состоянии `Pending` или `Running`.

Основные требования и особенности API:

- Чтобы использовать поле `.spec.podFailurePolicy`, в шаблоне Pod Job необходимо задать `.spec.restartPolicy: Never`.
- Правила в `spec.podFailurePolicy.rules` проверяются по порядку. Как только правило соответствует сбою Pod, остальные правила не проверяются. Если ни одно правило не подошло, применяется стандартная обработка.
- Правило можно ограничить конкретным контейнером, указав его имя в `spec.podFailurePolicy.rules[*].onExitCodes.containerName`. Если имя не указано, правило применяется ко всем контейнерам. Если указано, оно должно совпадать с именем одного из контейнеров или init-контейнеров в шаблоне Pod.
- Действие, выполняемое при совпадении правила политики сбоев Pod, задаётся полем `spec.podFailurePolicy.rules[*].action`. Допустимые значения:
    
    - `FailJob`: пометить Job как неуспешную и остановить все работающие Pod.
    - `Ignore`: не увеличивать счётчик `.spec.backoffLimit` и создать замещающий Pod.
    - `Count`: использовать стандартную обработку Pod, увеличив счётчик `.spec.backoffLimit`.
    - `FailIndex`: использовать совместно с ограничением повторных попыток для каждого индекса, чтобы избежать ненужных повторных запусков для индекса, Pod которого завершился с ошибкой.

> **Примечание.**
  При использовании `podFailurePolicy` контроллер Job проверяет соответствие правилам только для Pod в состоянии `Failed`. Pod с установленным временем удаления, но ещё не перешедшие в терминальное состояние (`Failed` или `Succeeded`), считаются завершающимися. Поэтому за такими Pod сохраняется завершающий финализатор отслеживания до перехода в терминальное состояние. Начиная с Kubernetes 1.27 kubelet переводит удаляемые Pod в терминальное состояние. Это позволяет контроллеру Job удалять их финализаторы.

> **Примечание.**
  Начиная с Kubernetes v1.28, при использовании политики сбоев Pod контроллер Job пересоздаёт завершающиеся Pod только после их перехода в терминальное состояние `Failed`. Это поведение аналогично `podReplacementPolicy: Failed`. Подробнее см. раздел о политике замены Pod.

Если при использовании `podFailurePolicy` Job завершается с ошибкой из-за совпадения Pod с правилом, у которого действие `FailJob`, контроллер Job инициирует завершение Job, добавляя условие `FailureTarget`. Подробнее см. раздел о завершении и очистке Job.

### Политика успешного завершения

При создании Indexed Job можно определить, когда её следует считать успешно завершённой, используя `.spec.successPolicy` и учитывая успешно завершившиеся Pod.

По умолчанию Job считается успешной, когда количество успешно завершившихся Pod достигает `.spec.completions`. В некоторых случаях может потребоваться более гибко определять успешное завершение:

- При выполнении симуляций с разными параметрами для успешного завершения всей Job может быть необязательно, чтобы завершились успешно все симуляции.
    
- При использовании модели «ведущий — рабочие» (leader-worker) успех Job может определяться только результатом работы ведущего Pod. Такой подход используется, например, в MPI и PyTorch.
    

Для этих сценариев можно задать политику успешного завершения в поле `.spec.successPolicy`. Она определяет успех Job на основе успешно завершившихся Pod. После выполнения условий политики контроллер Job останавливает оставшиеся Pod.

Политика состоит из правил. Каждое правило может иметь одну из следующих форм:

- Если указано только `succeededIndexes`, контроллер Job помечает её как успешную, когда успешно завершатся все индексы из этого списка. `succeededIndexes` должен содержать диапазоны индексов от `0` до `.spec.completions-1`.
    
- Если указано только `succeededCount`, контроллер Job помечает её как успешную, когда число успешно завершившихся индексов достигнет значения `succeededCount`.
    
- Если указаны оба поля — `succeededIndexes` и `succeededCount`, — контроллер Job помечает её как успешную, когда число успешно завершившихся индексов из заданного подмножества достигнет `succeededCount`.
    

Если в `.spec.successPolicy.rules` указано несколько правил, контроллер Job проверяет их по порядку. Как только одно из правил выполнено, остальные игнорируются.

Пример манифеста Job с `successPolicy`:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: job-success
spec:
  parallelism: 10
  completions: 10
  completionMode: Indexed # Required for the success policy
  successPolicy:
    rules:
    - succeededIndexes: 0,2-3
      succeededCount: 1
  template:
    spec:
      containers:
      - name: main
        image: python
        command:          # Provided that at least one of the Pods with 0, 2, and 3 indexes has succeeded,
                          # the overall Job is a success.
        - python3
        - -c
        - |
          import os, sys
          if os.environ.get("JOB_COMPLETION_INDEX") == "2":
            sys.exit(0)
          else:
            sys.exit(1)
      restartPolicy: Never
```

В этом примере заданы оба поля — `succeededIndexes` и `succeededCount`. Поэтому контроллер Job пометит её как успешно завершённую и остановит оставшиеся Pod, как только успешно завершится Pod с одним из индексов `0`, `2` или `3`. Для Job, удовлетворяющей политике успешного завершения, устанавливается условие `SuccessCriteriaMet` с причиной `SuccessPolicy`. После инициирования удаления оставшихся Pod устанавливается условие `Complete`.

Обратите внимание, что `succeededIndexes` задаётся диапазонами, в которых первое и последнее значения разделяются дефисом.

Примечание.

Если одновременно заданы политика успешного завершения и политики, приводящие к завершению Job, например `.spec.backoffLimit` и `.spec.podFailurePolicy`, при выполнении условий любой из политик завершения контроллер Job отдаёт приоритет политике завершения и игнорирует политику успешного завершения.

### Завершение и очистка Job

После завершения Job новые Pod больше не создаются, но существующие Pod обычно не удаляются. Это позволяет просматривать журналы завершившихся Pod, чтобы проверять ошибки, предупреждения и другие диагностические сообщения. Сам объект Job также сохраняется, чтобы можно было проверить его состояние. После этого пользователь должен самостоятельно удалить старые Job, предварительно проверив их состояние. Для удаления используйте `kubectl`, например `kubectl delete jobs/pi` или `kubectl delete -f ./job.yaml`. При удалении Job с помощью `kubectl` удаляются и все созданные ею Pod.

По умолчанию Job выполняется без прерываний, пока не произойдёт сбой Pod (`restartPolicy=Never`) или ошибка завершения контейнера (`restartPolicy=OnFailure`). В этом случае Job учитывает `.spec.backoffLimit`, описанный выше. Когда лимит достигнут, Job помечается как неуспешная, а все работающие Pod останавливаются.

Другой способ завершить Job — задать предельное время выполнения. Для этого установите в `.spec.activeDeadlineSeconds` количество секунд. Этот параметр ограничивает общую продолжительность выполнения Job независимо от числа созданных Pod. Когда время истекает, все работающие Pod останавливаются, а состояние Job становится `type: Failed` с причиной `DeadlineExceeded`.

Обратите внимание: `.spec.activeDeadlineSeconds` имеет приоритет над `.spec.backoffLimit`. Поэтому Job, повторно запускающая один или несколько неуспешных Pod, перестанет создавать новые Pod после достижения временного лимита, даже если лимит повторных попыток ещё не исчерпан.

Пример:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: pi-with-timeout
spec:
  backoffLimit: 5
  activeDeadlineSeconds: 100
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34.0
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
      restartPolicy: Never
```

Обратите внимание: поле `activeDeadlineSeconds` существует как в спецификации Job, так и в спецификации шаблона Pod внутри Job. Убедитесь, что задаёте его на нужном уровне.

Помните, что `restartPolicy` применяется к Pod, а не к самой Job. После перехода Job в состояние `type: Failed` автоматического перезапуска Job не происходит. Таким образом, механизмы завершения Job, активируемые параметрами `.spec.activeDeadlineSeconds` и `.spec.backoffLimit`, приводят к окончательному сбою, для устранения которого требуется вмешательство пользователя.

### Терминальные состояния Job

У Job есть два возможных терминальных состояния, каждому из которых соответствует условие Job:

- `Succeeded`: условие Job `Complete`.
    
- `Failed`: условие Job `Failed`.
    

Job может завершиться с ошибкой по следующим причинам:

- Количество сбоев Pod превысило значение `.spec.backoffLimit`, заданное в спецификации Job. Подробнее см. раздел о политике повторных попыток при сбоях Pod.
    
- Время выполнения Job превысило значение `.spec.activeDeadlineSeconds`.
    
- В Indexed Job, использующей `.spec.backoffLimitPerIndex`, появились индексы, завершившиеся с ошибкой. Подробнее см. раздел об ограничении повторных попыток для каждого индекса.
    
- Количество индексов, завершившихся с ошибкой, превысило значение `spec.maxFailedIndexes`. Подробнее см. раздел об ограничении повторных попыток для каждого индекса.
    
- Для неуспешного Pod сработало правило `.spec.podFailurePolicy` с действием `FailJob`. Подробнее о влиянии правил политики сбоев Pod на определение результата см. раздел о политике сбоев Pod.
    

Job считается успешно завершённой по следующим причинам:

- Количество успешно завершившихся Pod достигло заданного значения `.spec.completions`.
    
- Выполнены критерии, заданные в `.spec.successPolicy`. Подробнее см. раздел о политике успешного завершения.
    

Начиная с Kubernetes v1.31 контроллер Job откладывает установку терминальных условий `Failed` или `Complete` до завершения всех Pod этой Job.

В Kubernetes v1.30 и более ранних версиях контроллер Job добавлял терминальное условие `Complete` или `Failed`, как только запускался процесс завершения Job и удалялись все финализаторы Pod. Однако на момент установки условия некоторые Pod ещё могли работать или завершаться.

В Kubernetes v1.31 и более поздних версиях контроллер устанавливает терминальные условия Job только после завершения всех Pod. Это поведение можно контролировать с помощью механизмов управления функциями `JobManagedBy` и `JobPodReplacementPolicy` (оба включены по умолчанию).

### Завершение Pod в Job

Когда Job удовлетворяет критериям успеха или неудачи, контроллер Job добавляет условие `FailureTarget` или `SuccessCriteriaMet`, чтобы инициировать завершение Pod.

Такие факторы, как `terminationGracePeriodSeconds`, могут увеличить время между добавлением контроллером Job условия `FailureTarget` или `SuccessCriteriaMet` и завершением всех Pod с последующей установкой терминального условия (`Failed` или `Complete`).

Чтобы определить, завершилась ли Job успешно или с ошибкой, можно использовать условия `FailureTarget` и `SuccessCriteriaMet`, не дожидаясь установки терминального условия контроллером.

Например, может потребоваться решить, когда создавать новую Job взамен завершившейся с ошибкой. Если создать замену сразу после появления условия `FailureTarget`, новая Job начнёт работу раньше, но некоторое время Pod старой и новой Job могут выполняться одновременно, расходуя дополнительные вычислительные ресурсы.

Если ресурсы кластера ограничены, можно дождаться появления условия `Failed`. Это задержит запуск новой Job, но позволит сэкономить ресурсы, дождавшись удаления всех Pod предыдущей Job.

### Автоматическая очистка завершённых Job

Завершённые Job обычно больше не нужны в системе. Их накопление увеличивает нагрузку на API server. Если Job управляются контроллером более высокого уровня, например CronJob, очистку можно поручить CronJob, используя заданную политику очистки на основе количества хранимых объектов.

### Механизм TTL для завершённых Job

Состояние функции: стабильная начиная с Kubernetes v1.23

Другой способ автоматически очищать завершённые Job — использовать механизм TTL, предоставляемый контроллером TTL для завершённых ресурсов. Для этого задайте поле `.spec.ttlSecondsAfterFinished` в Job.

При очистке Job контроллер TTL удаляет её вместе с зависимыми объектами, например Pod. При этом соблюдаются гарантии жизненного цикла Job, включая обработку финализаторов.

Например:

```
apiVersion: batch/v1
kind: Job
metadata:
  name: pi-with-ttl
spec:
  ttlSecondsAfterFinished: 100
  template:
    spec:
      containers:
      - name: pi
        image: perl:5.34.0
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
      restartPolicy: Never
```

Job `pi-with-ttl` можно будет автоматически удалить через 100 секунд после завершения.

Если задать значение `0`, Job можно будет удалить сразу после завершения. Если поле не указано, контроллер TTL не будет очищать эту Job после завершения.

Примечание.

Рекомендуется задавать поле `ttlSecondsAfterFinished`, поскольку для Job, созданных напрямую, а не через другие API рабочих нагрузок, например CronJob, по умолчанию используется политика удаления `orphanDependents`. В результате Pod, созданные такой Job, могут остаться после её полного удаления. Хотя control plane в конечном счёте удаляет Pod завершённой или завершившейся с ошибкой Job с помощью сборщика мусора, оставшиеся Pod могут ухудшать производительность кластера, а в худшем случае — привести к его отказу из-за чрезмерной нагрузки.

С помощью `LimitRanges` и `ResourceQuotas` можно ограничить количество ресурсов, потребляемых определённым пространством имён.

### Шаблоны выполнения Job

Объект Job можно использовать для обработки набора независимых, но связанных элементов работы. Это могут быть электронные письма для отправки, кадры для рендеринга, файлы для перекодирования, диапазоны ключей в базе данных NoSQL для сканирования и т. д.

В сложной системе может быть несколько разных наборов элементов работы. Здесь рассматривается один набор, которым пользователь хочет управлять как единым целым, — пакетная задача.

Существует несколько шаблонов параллельных вычислений, каждый со своими преимуществами и недостатками. Основные компромиссы:

- Отдельный объект Job для каждого элемента работы или один Job для всех элементов. Отдельная Job для каждого элемента создаёт дополнительные издержки для пользователя и системы при управлении большим количеством объектов. Одна Job лучше подходит для большого числа элементов.
    
- Количество созданных Pod равно количеству элементов работы или каждый Pod обрабатывает несколько элементов. Если каждому элементу соответствует отдельный Pod, обычно требуется меньше изменений существующего кода и контейнеров. Для большого числа элементов эффективнее, когда каждый Pod обрабатывает несколько задач.
    
- Использование очереди задач. Такой подход требует запуска службы очередей и изменения существующей программы или контейнера для работы с очередью. Другие подходы проще адаптировать к уже существующему контейнеризированному приложению.
    
- Взаимодействие Pod друг с другом. Если Job связана с headless Service, Pod внутри Job могут взаимодействовать и совместно выполнять вычисления.
    

Компромиссы представлены в таблице ниже. Столбцы со второго по четвёртый соответствуют перечисленным выше аспектам. Названия шаблонов также служат ссылками на примеры и подробные описания.

|Шаблон|Один объект Job|Pod меньше, чем элементов работы?|Можно использовать приложение без изменений?|
|---|---|---|---|
|Очередь с отдельным Pod для каждого элемента|✓||Иногда|
|Очередь с переменным количеством Pod|✓|✓||
|Indexed Job со статическим распределением работы|✓||✓|
|Job с взаимодействием Pod друг с другом|✓|Иногда|Иногда|
|Развёртывание шаблонов Job|||✓|

Если в `.spec.completions` указано количество завершений, все Pod, создаваемые контроллером Job, получают одинаковую спецификацию. Это означает, что у всех Pod одной задачи будут одинаковые командная строка, образ, тома и (почти) одинаковые переменные окружения. Перечисленные шаблоны позволяют организовать работу Pod с разными элементами.

В таблице указаны обязательные значения `.spec.parallelism` и `.spec.completions` для каждого шаблона. Здесь W — количество элементов работы.

|Шаблон|`.spec.completions`|`.spec.parallelism`|
|---|---|---|
|Очередь с отдельным Pod для каждого элемента|W|Любое|
|Очередь с переменным количеством Pod|`null`|Любое|
|Indexed Job со статическим распределением работы|W|Любое|
|Job с взаимодействием Pod друг с другом|W|W|
|Развёртывание шаблонов Job|1|Рекомендуется 1|

## Расширенные сценарии использования

### Приостановка Job

Состояние функции: стабильная начиная с Kubernetes v1.24

После создания Job контроллер немедленно начинает создавать Pod для выполнения её требований и продолжает делать это до завершения Job. Однако иногда требуется временно приостановить выполнение и возобновить его позже либо создавать Job в приостановленном состоянии, чтобы пользовательский контроллер решил, когда запускать их.

Чтобы приостановить Job, установите `.spec.suspend` в `true`. Для возобновления установите значение `false`. Если создать Job с `.spec.suspend: true`, она сразу перейдёт в приостановленное состояние.

В Kubernetes 1.35 и более поздних версиях поле `.status.startTime` очищается при приостановке Job, если включён механизм управления функциями `MutableSchedulingDirectivesForSuspendedJobs`.

При возобновлении Job поле `.status.startTime` устанавливается в текущее время. Это означает, что таймер `.spec.activeDeadlineSeconds` останавливается при приостановке и запускается заново при возобновлении Job.

При приостановке Job все работающие Pod, не имеющие статуса `Completed`, завершаются сигналом `SIGTERM`. При этом соблюдается период корректного завершения Pod, и Pod должен обработать сигнал в течение этого времени. Например, он может сохранить прогресс для последующего продолжения работы или отменить внесённые изменения. Pod, завершённые таким образом, не учитываются в количестве завершений Job.

Пример определения Job в приостановленном состоянии:

```
kubectl get job myjob -o yaml
```

```
apiVersion: batch/v1
kind: Job
metadata:
  name: myjob
spec:
  suspend: true
  parallelism: 1
  completions: 5
  template:
    spec:
      ...
```

Приостановку и возобновление Job также можно переключать с помощью команды `kubectl patch`.

Приостановите работающую Job:

```
kubectl patch job/myjob --type=strategic --patch '{"spec":{"suspend":true}}'
```

Возобновите приостановленную Job:

```
kubectl patch job/myjob --type=strategic --patch '{"spec":{"suspend":false}}'
```

По состоянию Job можно определить, приостановлена ли она сейчас или была приостановлена ранее:

```
kubectl get jobs/myjob -o yaml
```

```
apiVersion: batch/v1
kind: Job
# .metadata and .spec omitted
status:
  conditions:
  - lastProbeTime: "2021-02-05T13:14:33Z"
    lastTransitionTime: "2021-02-05T13:14:33Z"
    status: "True"
    type: Suspended
  startTime: "2021-02-05T13:13:48Z"
```

Условие Job с типом `Suspended` и статусом `True` означает, что Job приостановлена. Поле `lastTransitionTime` позволяет определить, как долго она находится в этом состоянии. Если статус условия равен `False`, Job ранее была приостановлена, но сейчас снова выполняется. Если такого условия в состоянии Job нет, она никогда не приостанавливалась.

При приостановке и возобновлении Job также создаются события:

```
kubectl describe jobs/myjob
```

```
Name:           myjob
...
Events:
  Type    Reason            Age   From            Message
  ----    ------            ----  ----            -------
  Normal  SuccessfulCreate  12m   job-controller  Created pod: myjob-hlrpl
  Normal  SuccessfulDelete  11m   job-controller  Deleted pod: myjob-hlrpl
  Normal  Suspended         11m   job-controller  Job suspended
  Normal  SuccessfulCreate  3s    job-controller  Created pod: myjob-jvb44
  Normal  Resumed           3s    job-controller  Job resumed
```

Последние четыре события, особенно `Suspended` и `Resumed`, напрямую связаны с изменением поля `.spec.suspend`. Между этими событиями Pod не создавались, однако сразу после возобновления Job их создание продолжилось.

### Изменяемые директивы планирования

Состояние функции: стабильная начиная с Kubernetes v1.27

Во многих случаях для параллельной Job требуется задать ограничения размещения Pod, например запускать все Pod в одной зоне либо использовать только GPU моделей X или Y, не смешивая их.

Поле `suspend` — первый шаг к реализации такого поведения. Приостановка позволяет пользовательскому контроллеру очереди решать, когда запускать Job. Однако после возобновления Job этот контроллер уже не может влиять на то, на каких узлах будут размещены её Pod.

Эта функция позволяет изменять директивы планирования Job до её запуска. Благодаря этому пользовательские контроллеры очередей могут влиять на размещение Pod, делегируя непосредственное назначение Pod узлам планировщику `kube-scheduler`.

В шаблоне Pod Job разрешено изменять следующие поля: привязку к узлам (node affinity), селектор узлов, tolerations, метки, аннотации и ограничения планирования (scheduling gates).

### Изменяемые директивы планирования приостановленных Job

Состояние функции: Beta начиная с Kubernetes v1.36; включена по умолчанию

В Kubernetes 1.34 и более ранних версиях директивы планирования Pod можно изменять только у приостановленных Job, которые ранее не возобновлялись. В Kubernetes 1.35 это разрешено для любых приостановленных Job, если включён механизм управления функциями `MutableSchedulingDirectivesForSuspendedJobs`.

Кроме того, этот механизм позволяет очищать поле `.status.startTime` при приостановке Job.

### Изменение ресурсов Pod в приостановленных Job

Состояние функции: Beta начиная с Kubernetes v1.36; включена по умолчанию

Администратор кластера может настроить механизмы контроля допуска (admission controls) Kubernetes, изменяющие запросы ресурсов или лимиты Job в соответствии с правилами политики.

Эта функция также позволяет изменять шаблон Pod приостановленной Job, чтобы менять требования к ресурсам её Pod. Это отличается от изменения ресурсов работающего Pod на месте (in-place Pod resize), при котором ресурсы обновляются по одному Pod за раз для уже работающих Pod.

Клиент, задающий новые запросы ресурсов или лимиты, может отличаться от клиента, создавшего Job, и не обязан иметь права администратора кластера.

### Указание собственного селектора Pod

Обычно при создании объекта Job поле `.spec.selector` не указывают. При создании Job система автоматически заполняет его значением, которое не пересекается с селекторами других Job.

Однако в некоторых случаях может потребоваться переопределить автоматически заданный селектор. Для этого укажите `.spec.selector` в Job.

Будьте осторожны. Если заданный селектор меток не уникален для Pod этой Job и совпадает с метками посторонних Pod, возможны следующие последствия: Pod другой Job могут быть удалены, текущая Job может засчитать чужие Pod как завершившие работу, либо одна или обе Job не смогут создавать Pod или завершиться. Неуникальный селектор также может привести к непредсказуемому поведению других контроллеров, например ReplicationController, и управляемых ими Pod. Kubernetes не предотвращает ошибки при задании `.spec.selector`.

Рассмотрим пример ситуации, в которой может пригодиться эта возможность.

Предположим, Job `old` уже выполняется. Требуется, чтобы существующие Pod продолжали работать, но новые Pod использовали другой шаблон, а сама Job получила новое имя. Обновить Job нельзя, поскольку эти поля не подлежат изменению. Поэтому удалите Job `old`, оставив её Pod работающими, с помощью команды `kubectl delete jobs/old --cascade=orphan`. Перед удалением сохраните используемый ею селектор:

```
kubectl get job old -o yaml
```

Результат будет примерно таким:

```
kind: Job
metadata:
  name: old
  ...
spec:
  selector:
    matchLabels:
      batch.kubernetes.io/controller-uid: a8f3d00d-c6d2-11e5-9f87-42010af00002
  ...
```

Затем создайте новую Job с именем `new` и явно укажите тот же селектор. Поскольку существующие Pod имеют метку `batch.kubernetes.io/controller-uid=a8f3d00d-c6d2-11e5-9f87-42010af00002`, ими также будет управлять Job `new`.

В новой Job необходимо указать `manualSelector: true`, поскольку используется не селектор, автоматически генерируемый системой.

```
kind: Job
metadata:
  name: new
  ...
spec:
  manualSelector: true
  selector:
    matchLabels:
      batch.kubernetes.io/controller-uid: a8f3d00d-c6d2-11e5-9f87-42010af00002
  ...
```

Сама новая Job получит UID, отличный от `a8f3d00d-c6d2-11e5-9f87-42010af00002`. Параметр `manualSelector: true` сообщает системе, что это расхождение задано намеренно и его следует допустить.

### Отслеживание Job с помощью финализаторов

Состояние функции: стабильная начиная с Kubernetes v1.26

Control plane отслеживает Pod, принадлежащие каждой Job, и обнаруживает их удаление из API server. Для этого контроллер Job создаёт Pod с финализатором `batch.kubernetes.io/job-tracking`. Контроллер удаляет финализатор только после того, как учитывает Pod в состоянии Job. После этого другие контроллеры или пользователи могут удалить Pod.

Примечание.

Если Pod из Job застряли в состоянии завершения из-за финализатора отслеживания, см. раздел о Pod, который остаётся в состоянии `Terminating`.

### Эластичные Indexed Job

Состояние функции: стабильная начиная с Kubernetes v1.31; включена по умолчанию

Indexed Job можно масштабировать вверх или вниз, одновременно изменяя `.spec.parallelism` и `.spec.completions` так, чтобы их значения оставались равными. При уменьшении масштаба Kubernetes удаляет Pod с наибольшими индексами.

Эластичные Indexed Job подходят для пакетных рабочих нагрузок, которым требуется изменять масштаб индексированной задачи, например для заданий MPI, Horovod, Ray и обучения моделей PyTorch.

Примечание.

Если включён механизм управления функциями `WorkloadWithJob` и Job использует gang scheduling, размер группы определяется изменяемым параметром `schedulingPolicy.gang.minCount` либо `.spec.parallelism`, если `minCount` не задан.

Масштабировать группу можно двумя способами:

- напрямую изменить `.spec.scheduling.schedulingPolicy.gang.minCount`;
    
- изменить `.spec.parallelism`, если `minCount` не задан.
    

При любом из этих изменений контроллер повторно формирует Workload и синхронизирует размер PodGroup, масштабируя группу без пересоздания Job. Обновления применяются только к Pod, которые будут оцениваться в будущих циклах планирования, и не затрагивают уже запланированные Pod. Значение `gang.minCount`, превышающее `.spec.parallelism`, отклоняется, поскольку такую группу невозможно удовлетворить.

### Отложенное создание замещающих Pod

Состояние функции: стабильная начиная с Kubernetes v1.34

По умолчанию контроллер Job создаёт Pod на замену сразу после того, как исходный Pod завершился с ошибкой или начал завершаться (у него появилось время удаления). Поэтому в определённый момент времени количество работающих Pod одной Job может превышать значение `parallelism` или число Pod на один индекс в Indexed Job.

Можно настроить создание замещающих Pod только после того, как завершающийся Pod перейдёт в терминальное состояние (`status.phase: Failed`). Для этого задайте `.spec.podReplacementPolicy: Failed`.

Политика замены по умолчанию зависит от того, задана ли для Job политика сбоев Pod. Если политика сбоев не указана, пропуск поля `podReplacementPolicy` включает политику `TerminatingOrFailed`: control plane немедленно создаёт замещающий Pod после удаления исходного Pod, как только обнаруживает установленное поле `deletionTimestamp`.

Для Job с заданной политикой сбоев Pod по умолчанию используется `podReplacementPolicy: Failed`, и другие значения недопустимы. Подробнее см. раздел о политике сбоев Pod.

```
kind: Job
metadata:
  name: new
  ...
spec:
  podReplacementPolicy: Failed
  ...
```

Если в кластере включён соответствующий механизм управления функциями, можно проверить поле `.status.terminating` в Job. Оно содержит количество Pod, принадлежащих Job и находящихся в процессе завершения.

```
kubectl get jobs/myjob -o yaml
```

```
apiVersion: batch/v1
kind: Job
# .metadata and .spec omitted
status:
  terminating: 3 # three Pods are terminating and have not yet reached the Failed phase
```

### Делегирование управления Job внешнему контроллеру

Состояние функции: стабильная начиная с Kubernetes v1.35; включена по умолчанию

Эта функция позволяет отключить встроенный контроллер Job для конкретной Job и передать её согласование внешнему контроллеру.

Контроллер, отвечающий за согласование Job, указывается с помощью пользовательского значения поля `spec.managedBy` — любого значения, отличного от `kubernetes.io/job-controller`. После создания Job это поле изменить нельзя.

Примечание.

При использовании этой функции убедитесь, что указанный контроллер установлен. В противном случае согласование Job может вообще не выполняться.

Примечание.

При разработке внешнего контроллера Job учитывайте, что он должен работать в соответствии с определениями полей спецификации и состояния объекта Job в API.

Подробно изучите API Job. Также рекомендуется запускать сквозные тесты соответствия требованиям (e2e conformance tests) для объекта Job, чтобы проверить реализацию.

Наконец, внешний контроллер Job не должен использовать финализатор `batch.kubernetes.io/job-tracking`, зарезервированный для встроенного контроллера.

## Альтернативы

### Отдельные Pod

Если узел, на котором работает Pod, перезагружается или выходит из строя, Pod завершается и не запускается повторно. Job же создаёт новые Pod взамен завершившихся. Поэтому рекомендуется использовать Job вместо отдельного Pod, даже если приложению требуется всего один Pod.

### Replication Controller

Job дополняют ReplicationController. ReplicationController управляет Pod, которые обычно не должны завершаться, например веб-серверами, а Job управляет Pod, которые должны завершать работу, например пакетными задачами.

Как описано в разделе о жизненном цикле Pod, Job подходит только для Pod с `RestartPolicy`, равным `OnFailure` или `Never`.

Примечание.

Если `RestartPolicy` не задан, по умолчанию используется `Always`.

### Job запускает Pod-контроллер

Другой вариант — использовать одну Job для создания Pod, который затем создаёт другие Pod и действует как пользовательский контроллер для них. Такой подход обеспечивает максимальную гибкость, но может быть сложнее в настройке и хуже интегрируется с Kubernetes.

Преимущество этого подхода заключается в том, что весь процесс получает гарантию завершения, обеспечиваемую объектом Job, при этом сохраняется полный контроль над создаваемыми Pod и распределением задач между ними.
