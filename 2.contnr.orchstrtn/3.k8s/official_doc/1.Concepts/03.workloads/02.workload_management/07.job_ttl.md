## Политика удержания объектов и TTL-управление

После завершения задания полезно сохранять его объект в API, а не удалять сразу. Это позволяет определить, завершилось ли задание успешно или с ошибкой.

Контроллер TTL-after-finished в Kubernetes предоставляет механизм TTL (времени жизни), ограничивающий срок хранения объектов Job после завершения их выполнения.

---
## Очистка завершённых заданий

Контроллер **TTL-after-finished** поддерживает только объекты Job. С его помощью можно автоматически удалять завершённые задания (со статусом `Complete` или `Failed`), задав для Job поле `.spec.ttlSecondsAfterFinished`.

Контроллер **TTL-after-finished**  считает, что задание можно удалить по истечении указанного количества секунд после завершения его выполнения. Отсчёт начинается, когда условие состояния Job меняется на `Complete` или `Failed`. По истечении TTL задание становится доступным для каскадного удаления. При этом контроллер удаляет задание вместе со всеми зависимыми объектами.

Kubernetes соблюдает гарантии жизненного цикла объектов Job, например ожидает выполнения финализаторов.

Значение TTL в секундах можно задать в любое время. Ниже приведены примеры настройки поля `.spec.ttlSecondsAfterFinished` для Job:

- Указать это поле в манифесте Job, чтобы задание автоматически удалялось через некоторое время после завершения.
- Вручную задать это поле для уже существующих завершённых заданий, чтобы они стали доступны для очистки.
- Использовать мутирующий вебхук допуска, чтобы динамически задавать это поле при создании Job. Администраторы кластера могут применять такой подход для обеспечения соблюдения политики TTL для завершённых заданий.
- Использовать мутирующий вебхук допуска, чтобы динамически задавать это поле после завершения Job, выбирая значение TTL в зависимости от статуса и меток задания. В этом случае вебхук должен отслеживать изменения `.status` объекта Job и задавать TTL только при переводе задания в завершённое состояние.
- Написать собственный контроллер для управления очисткой заданий, соответствующих определённому селектору.

## Особенности и ограничения

### Изменение TTL завершённых заданий

Период TTL, заданный, например, полем `.spec.ttlSecondsAfterFinished` объекта Job, можно изменить после создания или завершения задания. Если увеличить TTL после истечения текущего значения `ttlSecondsAfterFinished`, Kubernetes не гарантирует, что задание сохранится, даже если API успешно обработает запрос на увеличение TTL.

### Расхождение времени

Поскольку контроллер TTL-after-finished использует временные метки, сохранённые в объектах Job Kubernetes, чтобы определить, истёк ли TTL, эта функция чувствительна к расхождению времени в кластере. Из-за этого плоскость управления может удалить объекты Job раньше или позже нужного момента.

Часы не всегда показывают точное время, однако расхождение должно быть минимальным. Учитывайте этот риск при задании ненулевого TTL.
