## Что такое StatefulSets

Это API-ресурс Kubernetes для управления приложениями с сохраняемым состоянием (stateful applications).

Он управляет развёртыванием и масштабированием группы Pod, гарантируя определённый порядок их создания и уникальность каждого Pod.

Как и Deployment, StatefulSet управляет Pod, созданными на основе одинаковой спецификации контейнеров. Но, в отличие от Deployment, он сохраняет за каждым Pod постоянную идентичность. Такие Pod создаются по одному шаблону, но не являются взаимозаменяемыми: у каждого есть постоянный идентификатор, который сохраняется даже при повторном назначении на другой узел.

StatefulSet также можно использовать для организации постоянного хранилища. Хотя отдельные Pod могут выходить из строя, их постоянные идентификаторы позволяют сопоставлять существующие тома с новыми Pod, которые заменяют вышедшие из строя.

---
## Использование StatefulSet

StatefulSet подходит для приложений, которым необходима одна или несколько следующих возможностей:

- Стабильные уникальные сетевые идентификаторы.
- Стабильное постоянное хранилище.
- Упорядоченное развёртывание и масштабирование с корректным завершением работы.
- Упорядоченные автоматические последовательные обновления (rolling updates).

В данном контексте стабильность означает сохранение идентичности при назначении Pod на узлы и повторном назначении после сбоев.

Если приложению не нужны постоянные идентификаторы или определённый порядок развёртывания, удаления и масштабирования, лучше использовать ресурс, который управляет набором stateless-реплик. Для таких приложений могут лучше подойти Deployment или ReplicaSet.

## Ограничения

- Хранилище для каждого Pod должно либо автоматически предоставляться через механизм динамического выделения томов (PersistentVolume Provisioner) на основе запрошенного класса хранилища (StorageClass), либо быть заранее подготовлено администратором.
- При удалении StatefulSet или уменьшении количества его реплик связанные тома автоматически не удаляются. Это сделано для защиты данных, которая обычно важнее автоматической очистки всех связанных ресурсов.
- Для сетевой идентичности Pod StatefulSet требуется Headless Service. Создать этот Service необходимо самостоятельно.
- StatefulSet не гарантирует определённый порядок завершения Pod при удалении самого ресурса. Чтобы обеспечить упорядоченное и корректное завершение работы, перед удалением можно уменьшить количество реплик до `0`.
- При использовании Rolling Updates со стандартной политикой управления Pod `OrderedReady` может возникнуть состояние, из которого нельзя выйти без ручного вмешательства.

## Компоненты

Ниже приведён пример компонентов StatefulSet.

Файл `controllers/statefulset.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  ports:
  - port: 80
    name: web
  clusterIP: None
  selector:
    app: nginx
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  selector:
    matchLabels:
      app: nginx # has to match .spec.template.metadata.labels
  serviceName: "nginx"
  replicas: 3 # by default is 1
  minReadySeconds: 10 # by default is 0
  template:
    metadata:
      labels:
        app: nginx # has to match .spec.selector.matchLabels
    spec:
      terminationGracePeriodSeconds: 10
      containers:
      - name: nginx
        image: registry.k8s.io/nginx-slim:0.24
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "my-storage-class"
      resources:
        requests:
          storage: 1Gi
```

> **Примечание**
  Для простоты в примере используется режим доступа `ReadWriteOnce`. Для производственных сред Kubernetes рекомендует вместо него использовать `ReadWriteOncePod`.

В этом примере:

- Headless Service с именем `nginx` определяет сетевой домен Pod.
- StatefulSet с именем `web` настроен на запуск трёх реплик контейнера nginx в отдельных Pod с уникальными идентификаторами.
- `volumeClaimTemplates` обеспечивает постоянное хранилище с помощью PersistentVolume, предоставляемых механизмом динамического выделения томов.

Имя объекта StatefulSet должно соответствовать формату DNS-метки (DNS label).

### Селектор Pod

Поле `.spec.selector` должно соответствовать меткам в `.spec.template.metadata.labels`. Если селектор не совпадает с метками шаблона Pod, при создании StatefulSet API-сервер вернёт ошибку проверки.

### Шаблоны запросов на выделение томов

Поле `.spec.volumeClaimTemplates` позволяет создавать PersistentVolumeClaim (PVC), обеспечивающие StatefulSet постоянным хранилищем, если выполняется одно из условий:

- Указанный в запросе класс хранилища настроен на динамическое выделение томов.
- В кластере уже есть PersistentVolume с подходящим классом хранилища и достаточным объёмом свободного места.

### Минимальное время готовности

> *Состояние функции: Stable начиная с Kubernetes v1.25.*

Необязательное поле `.spec.minReadySeconds` задаёт минимальное количество секунд, в течение которых новый Pod должен оставаться работающим и готовым к обслуживанию запросов без сбоев контейнеров, чтобы считаться доступным.

Это поле используется для отслеживания хода обновления при стратегии Rolling Update.

По умолчанию значение равно `0`: Pod считается доступным сразу после перехода в состояние Ready. Подробнее о проверках готовности см. в разделе о пробах контейнеров (Container Probes).

## Идентичность Pod

Каждый Pod в StatefulSet имеет уникальную идентичность, которая включает порядковый номер, стабильный сетевой идентификатор и постоянное хранилище. Эта идентичность сохраняется независимо от того, на какой узел назначен Pod.

### Порядковый номер

Если StatefulSet содержит \(N\) реплик, каждому Pod присваивается уникальный целочисленный порядковый номер (ordinal). По умолчанию номера начинаются с `0` и заканчиваются на `N-1`.

Контроллер StatefulSet также добавляет метку с этим индексом: `apps.kubernetes.io/pod-index`.

### Начальный порядковый номер

> *Состояние функции: Stable начиная с Kubernetes v1.31; включена по умолчанию.*

Необязательное поле `.spec.ordinals` позволяет настроить порядковые номера, присваиваемые Pod. По умолчанию оно равно `nil`.

В этом поле можно задать следующий параметр:

- `.spec.ordinals.start` — начальный порядковый номер. Если он указан, Pod получают номера от `.spec.ordinals.start` до `.spec.ordinals.start + .spec.replicas - 1`.

### Стабильный сетевой идентификатор

Имя узла (hostname) каждого Pod в StatefulSet формируется из имени StatefulSet и порядкового номера Pod по шаблону:

`$(statefulset name)-$(ordinal)`

В приведённом выше примере будут созданы три Pod: `web-0`, `web-1` и `web-2`.

**StatefulSet** может использовать Headless Service для управления доменом своих Pod. Домен, управляемый этим Service, имеет следующий формат:

`$(service name).$(namespace).svc.cluster.local`

Здесь `cluster.local` — домен кластера.

При создании каждому Pod назначается соответствующий DNS-поддомен следующего вида:

`$(podname).$(governing service domain)`

Управляющий Service определяется полем `serviceName` в **StatefulSet** .

В зависимости от настроек DNS кластера имя нового Pod может быть недоступно для разрешения сразу после его запуска. Такое поведение возможно, если другие клиенты кластера запрашивали DNS-имя Pod'а до его создания. В этом случае отрицательное кэширование DNS сохраняет результаты неудачных запросов и продолжает использовать их даже после запуска Pod — как минимум в течение нескольких секунд.

Если необходимо обнаруживать Pod сразу после создания, можно воспользоваться одним из следующих способов:

- Запрашивать Kubernetes API напрямую, например через механизм `watch`, вместо DNS.
- Уменьшить время кэширования в DNS-провайдере Kubernetes. Обычно для этого изменяют ConfigMap CoreDNS, который по умолчанию кэширует записи в течение 30 секунд.

Как отмечалось в разделе об ограничениях, создать Headless Service, отвечающий за сетевую идентичность Pod, необходимо самостоятельно.

Ниже показано, как домен кластера, имя Service и имя StatefulSet влияют на DNS-имена Pod.

|Домен кластера|Service (ns/name)|StatefulSet (ns/name)|Домен StatefulSet|DNS Pod|Hostname Pod|
|---|---|---|---|---|---|
|cluster.local|default/nginx|default/web|nginx.default.svc.cluster.local|web-NaN.nginx.default.svc.cluster.local|web-NaN|
|cluster.local|foo/nginx|foo/web|nginx.foo.svc.cluster.local|web-NaN.nginx.foo.svc.cluster.local|web-NaN|
|kube.local|foo/nginx|foo/web|nginx.foo.svc.kube.local|web-NaN.nginx.foo.svc.kube.local|web-NaN|

>**Примечание**
 Если домен кластера не настроен иначе, используется `cluster.local`.

### Постоянное хранилище

Для каждой записи `VolumeClaimTemplate`, заданной в StatefulSet, создаётся отдельный PersistentVolumeClaim для каждого Pod.

В приведённом выше примере с nginx каждый Pod получает один PersistentVolume с классом хранилища `my-storage-class` и выделенным объёмом `1Gi`.

Если класс хранилища не указан, используется класс по умолчанию.

Когда Pod назначается на узел или переназначается на другой узел, его `volumeMounts` подключают PersistentVolume, связанные с его PersistentVolumeClaim.

Обратите внимание: PersistentVolume, связанные с запросами на выделение томов Pod, не удаляются автоматически при удалении Pod или StatefulSet. Их необходимо удалять вручную.

### Метка с именем Pod

При создании Pod контроллер StatefulSet добавляет метку `statefulset.kubernetes.io/pod-name`, значение которой совпадает с именем Pod.

Эта метка позволяет привязать Service к конкретному Pod в StatefulSet.

### Метка с индексом Pod

> *Состояние функции: Stable начиная с Kubernetes v1.32; включена по умолчанию.*

При создании Pod контроллер StatefulSet добавляет метку `apps.kubernetes.io/pod-index`. Её значение соответствует порядковому номеру Pod.

Эта метка позволяет направлять трафик на Pod с определённым индексом, фильтровать журналы и метрики по индексу и выполнять другие подобные задачи.

Для этой функции переключатель `PodIndexLabel` включён и заблокирован по умолчанию. Чтобы отключить функцию, необходимо использовать эмулируемую сервером версию `v1.31`.

## Гарантии развёртывания и масштабирования

- Если StatefulSet содержит \(N\) реплик, Pod создаются последовательно, в порядке от `0` до `N-1`.
- При удалении Pod завершаются в обратном порядке: от `N-1` до `0`.
- Перед масштабированием очередного Pod все предыдущие Pod должны находиться в состояниях Running и Ready. Если задано `.spec.minReadySeconds`, предыдущие Pod также должны оставаться доступными (Ready) не менее указанного количества секунд.
- Перед завершением Pod все следующие за ним Pod должны быть полностью остановлены.

Не следует задавать для StatefulSet значение `0` в `pod.Spec.TerminationGracePeriodSeconds`. Это небезопасная практика, которую настоятельно не рекомендуется использовать.

Когда создаётся StatefulSet из примера с nginx, Pod запускаются в порядке `web-0`, `web-1`, `web-2`.

`web-1` не будет создан, пока `web-0` не перейдёт в состояния Running и Ready. Аналогично, `web-2` не будет создан, пока `web-1` не станет Running и Ready.

Если `web-0` выйдет из строя после того, как `web-1` уже стал Running и Ready, но до запуска `web-2`, создание `web-2` будет отложено до тех пор, пока `web-0` не будет успешно запущен повторно и не станет Running и Ready.

Предположим, что количество реплик уменьшают до `1`, изменяя StatefulSet. В таком случае первым будет завершён `web-2`. `web-1` не будет завершён, пока `web-2` полностью не остановится и не будет удалён.

Если после завершения `web-2`, но до завершения `web-1`, выйдет из строя `web-0`, завершение `web-1` будет отложено до тех пор, пока `web-0` снова не станет Running и Ready.

### Политики управления Pod

StatefulSet позволяет ослабить требования к порядку создания и завершения Pod, сохраняя при этом гарантии уникальности и постоянства идентичности. Для этого используется поле `.spec.podManagementPolicy`.

#### Упорядоченное управление Pod — OrderedReady

`OrderedReady` — политика управления Pod по умолчанию для StatefulSet. Она реализует поведение, описанное в разделе «Гарантии развёртывания и масштабирования».

#### Параллельное управление Pod — Parallel

Политика `Parallel` указывает контроллеру StatefulSet создавать и завершать все Pod параллельно, не дожидаясь, пока предыдущие Pod перейдут в состояния Running и Ready или полностью завершатся.

При масштабировании это означает, что все Pod создаются или завершаются одновременно.

При последовательных обновлениях, если `.spec.updateStrategy.rollingUpdate.maxUnavailable` больше `1`, контроллер StatefulSet может одновременно завершать и создавать до `maxUnavailable` Pod. Это также называется bursting.

Такой подход ускоряет обновление, но может привести к тому, что Pod будут становиться готовыми не по порядку. Это может быть неприемлемо для приложений, которым необходим строгий порядок запуска.

## Стратегии обновления

Поле `.spec.updateStrategy` позволяет настраивать автоматические обновления контейнеров, меток, запросов и ограничений ресурсов, а также аннотаций Pod в StatefulSet.

Возможны три значения.

### `OnDelete`

Если для `.spec.updateStrategy.type` установлено значение `OnDelete`, контроллер StatefulSet не будет автоматически обновлять Pod. Чтобы создать новые Pod с изменениями из `.spec.template`, пользователь должен вручную удалить существующие Pod.

### `RollingUpdate`

Стратегия `RollingUpdate` автоматически обновляет Pod по очереди. Это стратегия по умолчанию.

### `Recreate`

> *Состояние функции: Alpha начиная с Kubernetes v1.37; отключена по умолчанию.*

Стратегия `Recreate` сначала удаляет все Pod StatefulSet, а затем создаёт новые на основе обновлённого `.spec.template`.

Для её использования необходимо включить переключатель `StatefulSetRecreateStrategy`. Подробнее см. раздел «Recreate» ниже.

---
## Последовательные обновления — Rolling Updates

Если для `.spec.updateStrategy.type` задано значение `RollingUpdate`, контроллер StatefulSet удаляет и пересоздаёт Pod по одному. Порядок обновления обратный порядку создания: сначала Pod с наибольшим порядковым номером, затем остальные по убыванию.

Плоскость управления Kubernetes дожидается, пока обновлённый Pod перейдёт в состояния Running и Ready, прежде чем обновлять предыдущий Pod с меньшим номером.

Если задано `.spec.minReadySeconds`, плоскость управления дополнительно ждёт указанное количество секунд после перехода Pod в Ready, прежде чем продолжить обновление.

### Обновления с разделением по порядковому номеру

Стратегию `RollingUpdate` можно разделить на этапы с помощью параметра `.spec.updateStrategy.rollingUpdate.partition`.

Если параметр задан, при обновлении `.spec.template` обновляются только Pod, порядковый номер которых больше или равен значению `partition`.

Pod с меньшими порядковыми номерами не обновляются. Даже если такой Pod удалить, он будет создан заново с предыдущей версией конфигурации.

Если `.spec.updateStrategy.rollingUpdate.partition` больше `.spec.replicas`, изменения `.spec.template` не будут применены к Pod.

В большинстве случаев разделение не требуется, но оно полезно, когда нужно поэтапно развернуть обновление, провести канареечный релиз (canary release) или постепенно обновлять приложение.

### Максимальное количество недоступных Pod

> *Состояние функции: Beta начиная с Kubernetes v1.35.*

Максимальное количество Pod, которые могут быть недоступны во время обновления, задаётся полем `.spec.updateStrategy.rollingUpdate.maxUnavailable`.

Значение можно указать абсолютным числом, например `5`, или процентом от желаемого количества Pod, например `10%`. Процент преобразуется в целое число с округлением вверх.

Значение `0` недопустимо. По умолчанию используется `1`.

Это поле применяется к Pod с порядковыми номерами от `0` до `replicas - 1`. Любой недоступный Pod в этом диапазоне учитывается в значении `maxUnavailable`.

> **Примечание**
  Поле `maxUnavailable` находится на стадии Beta и включено по умолчанию.

### Принудительный откат

При использовании `RollingUpdate` со стандартной политикой управления Pod `OrderedReady` может возникнуть состояние, требующее ручного вмешательства.

Если шаблон Pod обновлён до конфигурации, при которой Pod никогда не переходит в состояния Running и Ready, например из-за ошибки в исполняемом файле или конфигурации приложения, StatefulSet остановит обновление и будет ждать.

В такой ситуации недостаточно просто вернуть шаблон Pod к рабочей конфигурации. Из-за известной проблемы StatefulSet продолжит ждать, пока проблемный Pod не станет Ready. Поскольку этого не произойдёт, автоматический откат не начнётся.

После возврата шаблона к рабочей версии необходимо также удалить все Pod, которые StatefulSet уже пытался запустить с ошибочной конфигурацией. После этого StatefulSet начнёт пересоздавать Pod на основе исправленного шаблона.

## Recreate

> *Состояние функции: Alpha начиная с Kubernetes v1.37; отключена по умолчанию.*

Если для `.spec.updateStrategy.type` задано значение `Recreate`, контроллер StatefulSet одновременно удаляет все принадлежащие ему Pod и ждёт их полного завершения. Только после этого он создаёт новые Pod на основе обновлённого `.spec.template`.

В отличие от `RollingUpdate`, старая и новая версии Pod никогда не работают одновременно. Поэтому на время обновления возникает простой.

Эта стратегия аналогична `Recreate` в Deployment и подходит для приложений, которые не могут одновременно запускать две версии. Например, это могут быть приложения, которым нужен исключительный доступ к общему ресурсу, или приложения, использующие несовместимые между версиями форматы данных на диске.

При удалении завершаются все Pod одновременно — независимо от политики управления Pod.

После завершения всех Pod новые создаются в соответствии с выбранной политикой:

- `OrderedReady` (по умолчанию) — Pod создаются по одному, в порядке возрастания порядковых номеров. Следующий Pod создаётся только после того, как предыдущий перейдёт в состояния Running и Ready.
- `Parallel` — все Pod создаются одновременно.

Поскольку функция находится на стадии Alpha, для её использования необходимо включить переключатель `StatefulSetRecreateStrategy` в `kube-controller-manager` и `kube-apiserver`.

## История ревизий

`ControllerRevision` — это ресурс Kubernetes API, который контроллеры, например контроллер StatefulSet, используют для отслеживания изменений конфигурации.

StatefulSet хранит историю ревизий с помощью `ControllerRevision`. Это позволяет отслеживать версии конфигурации и выполнять откаты.

### Как StatefulSet отслеживает изменения с помощью ControllerRevision

Когда вы обновляете шаблон Pod StatefulSet (`spec.template`), контроллер:

1. Создаёт новый объект ControllerRevision.
2. Сохраняет снимок шаблона Pod и метаданных.
3. Присваивает ревизии следующий порядковый номер.

#### Основные свойства

Подробнее о свойствах и других особенностях см. документацию [`ControllerRevision`](https://kubernetes.io/docs/reference/kubernetes-api/apps/controller-revision-v1/).

### Управление историей ревизий

Количество сохраняемых ревизий задаётся полем `.spec.revisionHistoryLimit`:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: webapp
spec:
  revisionHistoryLimit: 5  # Keep last 5 revisions
  # ... other spec fields ...
```

- По умолчанию: сохраняются 10 ревизий, если значение не задано.
- Очистка: при превышении лимита самые старые ревизии удаляются сборщиком мусора.

#### Откат к предыдущей версии

Вернуться к предыдущей конфигурации можно с помощью следующих команд:

```bash
# View revision history
kubectl rollout history statefulset/webapp

# Rollback to a specific revision
kubectl rollout undo statefulset/webapp --to-revision=3
```

При этом:

- Будет применён шаблон Pod из ревизии `3`.
- Будет создан новый объект ControllerRevision с обновлённым номером ревизии.

#### Просмотр ControllerRevision

Чтобы посмотреть связанные ревизии:

```bash
# List all revisions for the StatefulSet
kubectl get controllerrevisions -l app.kubernetes.io/name=webapp

# View detailed configuration of a specific revision
kubectl get controllerrevision/webapp-3 -o yaml
```

#### Рекомендации

##### Политика хранения

- Для большинства приложений устанавливайте `revisionHistoryLimit` в диапазоне 5–10.
- Увеличивайте лимит только при необходимости хранить расширенную историю для откатов.

##### Мониторинг

- Регулярно проверяйте ревизии:

```
kubectl get controllerrevisions
```
 
- Настройте оповещения при быстром росте количества ревизий.
 
##### Чего следует избегать

- Не редактируйте объекты ControllerRevision вручную. 
- Не используйте ревизии в качестве резервных копий — для этого предназначены специализированные инструменты резервного копирования.
- Не устанавливайте `revisionHistoryLimit: 0`, поскольку это отключает возможность отката.

## Хранение PersistentVolumeClaim

> *Состояние функции: Stable начиная с Kubernetes v1.32; включена по умолчанию.*

Необязательное поле `.spec.persistentVolumeClaimRetentionPolicy` определяет, удалять ли PVC и каким образом при определённых событиях жизненного цикла StatefulSet.

Чтобы использовать это поле, необходимо включить переключатель `StatefulSetAutoDeletePVC` на API-сервере и в контроллере управления.

Для каждого StatefulSet можно настроить две политики:

### `whenDeleted`

Определяет, что происходит с томами при удалении StatefulSet.

### `whenScaled`

Определяет, что происходит с томами при уменьшении количества реплик StatefulSet.

Для каждой политики можно задать одно из двух значений: `Delete` или `Retain`.

#### `Delete`

PVC, созданные на основе `volumeClaimTemplate` StatefulSet, удаляются для каждого Pod, к которому применяется соответствующая политика.

При `whenDeleted` все PVC, созданные на основе `volumeClaimTemplate`, удаляются после удаления соответствующих Pod.

При `whenScaled` удаляются только PVC тех Pod, которые исключаются при уменьшении количества реплик. Удаление происходит после завершения этих Pod.

#### `Retain` (по умолчанию)

PVC, созданные на основе `volumeClaimTemplate`, сохраняются при удалении соответствующих Pod. Это поведение использовалось до появления данной функции.

Обратите внимание: эти политики применяются только при удалении Pod вследствие удаления StatefulSet или уменьшения количества реплик.

Например, если Pod StatefulSet выходит из строя из-за сбоя узла и плоскость управления создаёт замену, StatefulSet сохраняет существующий PVC. Том остаётся без изменений, а кластер подключает его к узлу, на котором запускается новый Pod.

По умолчанию используется `Retain`, что соответствует прежнему поведению StatefulSet.

Пример настройки:

```yaml
apiVersion: apps/v1
kind: StatefulSet
...
spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain
    whenScaled: Delete
...
```

Контроллер StatefulSet добавляет к PVC ссылки на владельца (owner references). После завершения Pod сборщик мусора удаляет PVC в соответствии с этими ссылками.

Это позволяет Pod корректно отключить тома перед удалением PVC, а также, в зависимости от политики хранения, перед удалением соответствующего PV и физического тома.

Если для `whenDeleted` задано значение `Delete`, в PVC, связанных с StatefulSet, добавляется ссылка на сам объект StatefulSet в качестве владельца.

Политика `whenScaled` должна удалять PVC только тогда, когда Pod исключается в результате уменьшения количества реплик, а не при удалении Pod по другим причинам.

При синхронизации состояния контроллер StatefulSet сравнивает желаемое количество реплик с фактическим количеством Pod в кластере. Pod, порядковый номер которых превышает новое количество реплик, помечаются как подлежащие удалению.

Если для `whenScaled` задано значение `Delete`, перед удалением такого Pod контроллер назначает его владельцем соответствующего PVC, созданного на основе шаблона StatefulSet. Благодаря этому PVC удаляется сборщиком мусора после завершения соответствующего Pod.

Таким образом, если контроллер аварийно завершится и запустится снова, Pod не будут удаляться до обновления ссылок на владельца в соответствии с заданной политикой.

Если Pod, помеченный для удаления, принудительно удалят во время простоя контроллера, ссылка на владельца могла быть настроена, а могла и не быть — это зависит от момента сбоя контроллера.

Для обновления всех ссылок может потребоваться несколько циклов синхронизации, поэтому у одних Pod ссылки уже могут быть настроены, а у других — нет.

Поэтому рекомендуется дождаться восстановления контроллера, чтобы он проверил ссылки на владельца перед завершением Pod. Если это невозможно, оператор должен самостоятельно проверить ссылки на владельца в PVC, чтобы убедиться, что при принудительном удалении Pod будут удалены именно ожидаемые объекты.

### Количество реплик

Необязательное поле `.spec.replicas` задаёт желаемое количество Pod. По умолчанию используется значение `1`.

Если вручную изменить количество реплик StatefulSet командой `kubectl scale statefulset statefulset --replicas=X`, а затем применить манифест, например с помощью `kubectl apply -f statefulset.yaml`, значение из манифеста перезапишет результат ручного масштабирования.

Если масштабированием StatefulSet управляет HorizontalPodAutoscaler (HPA) или другой аналогичный механизм горизонтального масштабирования, не задавайте поле `.spec.replicas`. Вместо этого позвольте плоскости управления Kubernetes автоматически управлять этим полем.
