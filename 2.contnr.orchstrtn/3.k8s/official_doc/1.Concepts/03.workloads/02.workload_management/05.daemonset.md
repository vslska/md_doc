# DaemonSet

> **DaemonSet** определяет набор Pod, обеспечивающих работу служб на отдельных узлах. Такие службы могут быть необходимы для функционирования кластера, например сетевые вспомогательные компоненты, или входить в состав дополнений к кластеру.

## Назначение и сценарии использования

DaemonSet гарантирует, что на всех или некоторых узлах (Nodes) запущена копия Pod. Механика работы контроллера автоматизирует управление жизненным циклом этих Pod:
* **При добавлении узлов** в кластер на них автоматически создаются новые Pod.
* **При удалении узлов** соответствующие Pod удаляются автоматически.
* **При удалении самого DaemonSet** также удаляются все созданные им Pod.

### Типичные сценарии использования:

* Запуск службы хранения данных кластера на каждом узле.
* Запуск службы сбора журналов на каждом узле.
* Запуск службы мониторинга узлов на каждом узле.

В простом случае для каждого типа службы используется один DaemonSet, охватывающий все узлы. В более сложных конфигурациях для одного типа службы можно использовать несколько DaemonSet с разными параметрами запуска и/или разными запросами ресурсов памяти и CPU для узлов с различными аппаратными характеристиками.

## Описание спецификации DaemonSet

### Создание DaemonSet

DaemonSet можно описать в YAML-файле. Например, файл `daemonset.yaml` ниже описывает DaemonSet, который запускает Docker-образ fluentd-elasticsearch:

```
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd-elasticsearch
  namespace: kube-system
  labels:
    k8s-app: fluentd-logging
spec:
  selector:
    matchLabels:
      name: fluentd-elasticsearch
  template:
    metadata:
      labels:
        name: fluentd-elasticsearch
    spec:
      tolerations:
      # these tolerations are to have the daemonset runnable on control plane nodes
      # remove them if your control plane nodes should not run pods
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      - key: node-role.kubernetes.io/master
        operator: Exists
        effect: NoSchedule
      containers:
      - name: fluentd-elasticsearch
        image: quay.io/fluentd_elasticsearch/fluentd:v5.0.1
        resources:
          limits:
            memory: 200Mi
          requests:
            cpu: 100m
            memory: 200Mi
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      # it may be desirable to set a high priority class to ensure that a DaemonSet Pod
      # preempts running Pods
      # priorityClassName: important
      terminationGracePeriodSeconds: 30
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
```

Создайте DaemonSet на основе YAML-файла:

```
kubectl apply -f https://k8s.io/examples/controllers/daemonset.yaml
```

### Обязательные поля

Как и любая другая конфигурация Kubernetes, DaemonSet должен содержать поля `apiVersion`, `kind` и `metadata`. Общие сведения о работе с файлами конфигурации см. в разделах о запуске приложений без сохранения состояния и управлении объектами с помощью `kubectl`.

Имя объекта DaemonSet должно соответствовать требованиям к имени DNS-поддомена.

Также DaemonSet должен содержать раздел [`.spec`](https://git.k8s.io/community/contributors/devel/sig-architecture/api-conventions.md?utm_source=chatgpt.com#spec-and-status).

### Шаблон Pod

Поле `.spec.template` — одно из обязательных полей раздела `.spec`.

`.spec.template` представляет собой шаблон Pod. Его схема полностью совпадает со схемой объекта Pod, за исключением того, что шаблон вложен в другой объект и не содержит полей `apiVersion` и `kind`.

Помимо обязательных полей Pod, шаблон Pod в DaemonSet должен задавать соответствующие метки (см. раздел о селекторе Pod).

В шаблоне Pod для DaemonSet поле `RestartPolicy` должно иметь значение `Always` либо не указываться вовсе. По умолчанию используется значение `Always`.

### Селекторный модуль

Поле `.spec.selector` задаёт селектор Pod. Оно работает так же, как `.spec.selector` у объекта Job.

Необходимо указать селектор Pod, соответствующий меткам в `.spec.template`. После создания DaemonSet изменить его `.spec.selector` нельзя. Изменение селектора может непреднамеренно привести к тому, что Pod останутся без владельца, а такое поведение может сбить пользователей с толку.

Объект `.spec.selector` состоит из двух полей:

- `matchLabels` — работает так же, как `.spec.selector` у объекта ReplicationController.
    
- `matchExpressions` — позволяет создавать более сложные селекторы, задавая ключ, список значений и оператор, определяющий отношение между ключом и значениями.
    

Если указаны оба поля, их условия объединяются оператором AND.

Поле `.spec.selector` должно соответствовать `.spec.template.metadata.labels`. API отклонит конфигурацию, если эти значения не совпадают.

### Запуск Pod на определённых узлах

Если указать `.spec.template.spec.nodeSelector`, контроллер DaemonSet будет создавать Pod на узлах, соответствующих этому селектору узлов. Аналогично, если указать `.spec.template.spec.affinity`, контроллер создаст Pod на узлах, соответствующих заданным правилам привязки к узлам (node affinity). Если не указать ни одно из этих полей, контроллер DaemonSet будет создавать Pod на всех узлах.

## Как планируется запуск Pod, управляемых DaemonSet

DaemonSet позволяет гарантировать, что на каждом подходящем узле запущена копия Pod. Контроллер DaemonSet создаёт Pod для каждого подходящего узла и добавляет в поле `spec.affinity.nodeAffinity` этого Pod правило, указывающее целевой узел. После создания Pod обычно управление переходит к планировщику по умолчанию, который назначает Pod целевому узлу, устанавливая поле `.spec.nodeName`. Если новый Pod не помещается на узле, планировщик может вытеснить некоторые уже работающие Pod с учётом приоритета нового Pod.

#### Примечание

Если важно, чтобы Pod из DaemonSet запускался на каждом узле, рекомендуется задать в `.spec.template.spec.priorityClassName` класс `PriorityClass` с более высоким приоритетом. Это поможет обеспечить вытеснение других Pod при необходимости.

Пользователь может указать другой планировщик для Pod из DaemonSet, задав поле `.spec.template.spec.schedulerName`.

Контроллер DaemonSet учитывает исходные правила привязки к узлам, заданные в `.spec.template.spec.affinity.nodeAffinity` (если они указаны), при определении подходящих узлов. Однако в созданном Pod эти правила заменяются правилом, которое указывает имя соответствующего узла.

```
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
    - matchFields:
      - key: metadata.name
        operator: In
        values:
        - target-host-name
```

### Загрязнения и допустимые отклонения

Контроллер DaemonSet автоматически добавляет к Pod набор tolerations:

|Ключ toleration|Эффект|Описание|
|---|---|---|
|`node.kubernetes.io/not-ready`|`NoExecute`|Pod из DaemonSet можно планировать на узлах, которые находятся в неисправном состоянии или ещё не готовы принимать Pod. Уже работающие на таких узлах Pod из DaemonSet не будут вытеснены.|
|`node.kubernetes.io/unreachable`|`NoExecute`|Pod из DaemonSet можно планировать на узлах, недоступных для контроллера узлов. Уже работающие на таких узлах Pod из DaemonSet не будут вытеснены.|
|`node.kubernetes.io/disk-pressure`|`NoSchedule`|Pod из DaemonSet можно планировать на узлах с нехваткой дискового пространства.|
|`node.kubernetes.io/memory-pressure`|`NoSchedule`|Pod из DaemonSet можно планировать на узлах с нехваткой памяти.|
|`node.kubernetes.io/pid-pressure`|`NoSchedule`|Pod из DaemonSet можно планировать на узлах с нехваткой ресурсов для создания процессов.|
|`node.kubernetes.io/unschedulable`|`NoSchedule`|Pod из DaemonSet можно планировать на узлах, помеченных как недоступные для планирования.|
|`node.kubernetes.io/network-unavailable`|`NoSchedule`|Добавляется только к Pod из DaemonSet, которым требуется сеть узла, то есть к Pod с `spec.hostNetwork: true`. Такие Pod можно планировать на узлах с недоступной сетью.|

Также можно добавлять собственные tolerations к Pod из DaemonSet, задавая их в шаблоне Pod.

Поскольку контроллер DaemonSet автоматически добавляет toleration `node.kubernetes.io/unschedulable:NoSchedule`, Kubernetes может запускать Pod из DaemonSet на узлах, помеченных как unschedulable .

Если DaemonSet обеспечивает важную функцию на уровне узла, например сетевое взаимодействие внутри кластера, полезно, чтобы Kubernetes размещал его Pod на узлах ещё до того, как они станут готовы к работе. Без специального toleration может возникнуть взаимная блокировка: узел не получает статус Ready, потому что на нём не работает сетевой плагин, а плагин не запускается, поскольку узел ещё не готов.

## Взаимодействие с Pod из DaemonSet

Возможны следующие способы взаимодействия с Pod, управляемыми DaemonSet:

- Push : Pod из DaemonSet настроены на отправку обновлений в другую службу, например в базу данных статистики. Клиенты для взаимодействия с ними не используются.
    
- NodeIP и известный порт : Pod из DaemonSet могут использовать `hostPort`, чтобы к ним можно было обращаться по IP-адресам узлов. Клиенты каким-либо образом получают список IP-адресов узлов, а номер порта известен заранее по соглашению.
    
- DNS : создайте headless Service с тем же селектором Pod, а затем обнаруживайте DaemonSet через ресурс `endpoints` или получайте несколько записей A из DNS.
    
- Service : создайте Service с тем же селектором Pod и используйте его для обращения к службе на случайном узле. Используйте политику внутреннего трафика Service (Service Internal Traffic Policy), чтобы ограничить трафик Pod, работающими на том же узле.
    

## Обновление DaemonSet

При изменении меток узлов DaemonSet оперативно добавляет Pod на узлы, которые теперь соответствуют селектору, и удаляет Pod с узлов, которые перестали ему соответствовать.

Можно изменять Pod, создаваемые DaemonSet. Однако не все поля Pod допускают изменение. Кроме того, при последующем создании узла, даже с тем же именем, контроллер DaemonSet будет использовать исходный шаблон.

DaemonSet можно удалить. Если при использовании `kubectl` указать `--cascade=orphan`, Pod останутся на узлах. Если затем создать новый DaemonSet с тем же селектором, он примет существующие Pod под своё управление. Если какие-либо Pod потребуется заменить, новый DaemonSet сделает это в соответствии со своей стратегией обновления `updateStrategy`.

Для DaemonSet можно выполнить обновление поэтапно (rolling update).

## Альтернативы DaemonSet

### Скрипты инициализации

Службы можно запускать непосредственно на узле, например с помощью `init`, `upstartd` или `systemd`. Это вполне допустимый подход, однако запуск таких процессов через DaemonSet даёт несколько преимуществ:

- Возможность отслеживать и управлять журналами служб так же, как журналами приложений.
    
- Единый язык конфигурации и инструменты (например, шаблоны Pod и `kubectl`) для служб и приложений.
    
- Запуск служб в контейнерах с ограничениями ресурсов повышает изоляцию между службами и контейнерами приложений. Впрочем, аналогичного результата можно добиться, запуская службы в контейнерах, но не в Pod.
    

### Отдельные Pod

Можно создавать Pod напрямую, указывая конкретный узел, на котором они должны запускаться. Однако DaemonSet заменяет Pod, удалённые или завершённые по любой причине, например из-за отказа узла или планового обслуживания, нарушающего работу, такого как обновление ядра. Поэтому вместо создания отдельных Pod следует использовать DaemonSet.

### Статические Pod

Pod можно создавать, помещая файл в определённый каталог, за которым следит Kubelet. Такие Pod называются статическими. В отличие от DaemonSet, статическими Pod нельзя управлять с помощью `kubectl` или других клиентов Kubernetes API. Статические Pod не зависят от apiserver, поэтому они полезны при начальной настройке кластера. Кроме того, в будущем поддержка статических Pod может быть прекращена.

### Развертывания

DaemonSet похожи на Deployment: оба ресурса создают Pod, в которых запускаются процессы, обычно работающие непрерывно, например веб-серверы или серверы хранения данных.

Используйте Deployment для служб без сохранения состояния, например фронтендов, где важнее масштабировать количество реплик и выполнять поэтапные обновления, чем контролировать, на каком именно узле запускается Pod. Используйте DaemonSet, если важно, чтобы копия Pod постоянно работала на всех или определённых узлах, например когда он обеспечивает функциональность на уровне узла, необходимую для корректной работы других Pod.

Например, сетевые плагины часто включают компонент, работающий как DaemonSet. Этот компонент обеспечивает работоспособность сети кластера на узле, где он запущен.
