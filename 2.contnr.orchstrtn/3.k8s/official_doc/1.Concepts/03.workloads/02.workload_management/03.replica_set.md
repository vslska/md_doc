# ReplicaSet

>**ReplicaSet** поддерживает заданное количество работающих Pod-реплик. Обычно для этого создают ресурс Deployment, который автоматически управляет ReplicaSet.

>**ReplicaSet** помогает обеспечить доступность определённого количества одинаковых Pod.

## Как работает ReplicaSet

В конфигурации ReplicaSet задаются несколько параметров:

- Селектор (`selector`) — определяет, какие Pod ресурс может взять под своё управление.
- Количество реплик (`replicas`) — сколько Pod должно работать.
- Шаблон Pod (`template`) — описывает конфигурацию новых Pod, которые нужно создать для достижения заданного количества реплик.

ReplicaSet создаёт и удаляет Pod по мере необходимости, чтобы поддерживать нужное количество. Новые Pod создаются на основе указанного шаблона.

Связь между ReplicaSet и управляемыми Pod устанавливается через поле `metadata.ownerReferences`. В нём указывается, какому ресурсу принадлежит объект. У каждого Pod, которым управляет ReplicaSet, в этом поле содержится информация о соответствующем ReplicaSet. Благодаря этой связи ресурс отслеживает состояние своих Pod и принимает решения о необходимых действиях.

Чтобы найти новые Pod, ReplicaSet использует селектор. Если Pod соответствует селектору ReplicaSet и при этом у него отсутствует `OwnerReference` либо владелец не является контроллером (`Controller`), ReplicaSet немедленно берёт его под своё управление.

## Когда использовать ReplicaSet

ReplicaSet обеспечивает работу заданного количества Pod-реплик в любой момент времени. Однако Deployment — это ресурс более высокого уровня, который управляет ReplicaSet и позволяет декларативно обновлять Pod, а также предоставляет множество других полезных возможностей.

Поэтому рекомендуется использовать Deployment вместо непосредственного управления ReplicaSet. Исключение — случаи, когда требуется собственный механизм оркестрации обновлений или обновления вообще не нужны.

На практике это означает, что напрямую работать с объектами ReplicaSet, скорее всего, не придётся: достаточно использовать Deployment и описать приложение в секции `spec`.

## Пример

Файл `controllers/frontend.yaml`:

```
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: frontend
  labels:
    app: guestbook
    tier: frontend
spec:
  # modify replicas according to your case
  replicas: 3
  selector:
    matchLabels:
      tier: frontend
  template:
    metadata:
      labels:
        tier: frontend
    spec:
      containers:
      - name: php-redis
        image: us-docker.pkg.dev/google-samples/containers/gke/gb-frontend:v5
```

Сохраните манифест в файл `frontend.yaml` и примените его к кластеру Kubernetes. Будет создан ReplicaSet и управляемые им Pod.

```
kubectl apply -f https://kubernetes.io/examples/controllers/frontend.yaml
```

Посмотреть созданные ReplicaSet можно командой:

```
kubectl get rs
```

В выводе должен появиться созданный ресурс `frontend`:

```
NAME       DESIRED   CURRENT   READY   AGE
frontend   3         3         3       6s
```

Проверить состояние ReplicaSet можно командой:

```
kubectl describe rs/frontend
```

Пример вывода:

```
Name:         frontend
Namespace:    default
Selector:     tier=frontend
Labels:       app=guestbook
              tier=frontend
Annotations:  <none>
Replicas:     3 current / 3 desired

  Labels:  tier=frontend

  Volumes:        <none>
Events:
  Type    Reason            Age   From                   Message

  Normal  SuccessfulCreate  13s   replicaset-controller  Created pod: frontend-gbgfx
  Normal  SuccessfulCreate  13s   replicaset-controller  Created pod: frontend-rwz57
  Normal  SuccessfulCreate  13s   replicaset-controller  Created pod: frontend-wkl7w
```

Наконец, посмотреть созданные Pod можно командой:

```bash
kubectl get pods
```

Пример вывода:

```

frontend-gbgfx   1/1     Running   0          10m
frontend-rwz57   1/1     Running   0          10m
frontend-wkl7w   1/1     Running   0          10m
```

Также можно проверить, что в `ownerReferences` каждого Pod указан ReplicaSet `frontend`. Для этого получите YAML одного из работающих Pod:

```yaml
kubectl get pods frontend-gbgfx -o yaml
```

В выводе будет примерно следующее. Информация о ReplicaSet указана в поле `metadata.ownerReferences`:

```yaml

  creationTimestamp: "2024-02-28T22:30:44Z"
  generateName: frontend-

...
```

## Принятие под управление Pod, созданных не по шаблону

Вы можете создавать отдельные Pod без ReplicaSet, но настоятельно рекомендуется не назначать им метки, соответствующие селекторам существующих ReplicaSet. Дело в том, что ReplicaSet может управлять не только Pod, созданными по собственному шаблону, но и другими подходящими Pod, как описано выше.

Рассмотрим предыдущий пример с ReplicaSet `frontend` и следующие манифесты Pod.

Файл `pods/pod-rs.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod1
  labels:
    tier: frontend
spec:
  containers:
  - name: hello1
    image: gcr.io/google-samples/hello-app:2.0

---

apiVersion: v1
kind: Pod
metadata:
  name: pod2
  labels:
    tier: frontend
spec:
  containers:
  - name: hello2
    image: gcr.io/google-samples/hello-app:1.0
```

У этих Pod нет контроллера (или другого объекта) в качестве владельца, а их метки соответствуют селектору ReplicaSet `frontend`. Поэтому ReplicaSet сразу возьмёт их под своё управление.

Предположим, что вы создаёте эти Pod после развёртывания ReplicaSet, который уже запустил необходимое количество реплик:

```bash
kubectl apply -f https://kubernetes.io/examples/pods/pod-rs.yaml
```

ReplicaSet примет новые Pod под управление, после чего сразу завершит их, поскольку общее количество Pod превысит заданное значение.

Проверим состояние Pod:

```bash
kubectl get pods
```

Новые Pod уже завершены или находятся в процессе завершения:

```bash
NAME             READY   STATUS        RESTARTS   AGE
frontend-b2zdv   1/1     Running       0          10m
frontend-vcmts   1/1     Running       0          10m
frontend-wtsmm   1/1     Running       0          10m
pod1             0/1     Terminating   0          1s
pod2             0/1     Terminating   0          1s
```

Теперь рассмотрим обратный порядок: сначала создадим Pod.

```bash
kubectl apply -f https://kubernetes.io/examples/pods/pod-rs.yaml
```

Затем создадим ReplicaSet:

```bash
kubectl apply -f https://kubernetes.io/examples/controllers/frontend.yaml
```

ReplicaSet примет существующие Pod под управление и создаст только столько новых, сколько необходимо для достижения заданного количества реплик.

Проверим результат:

```bash
kubectl get pods
```

Вывод покажет, что ReplicaSet использует уже существующие Pod и создал только одну дополнительную реплику:

```bash
NAME             READY   STATUS    RESTARTS   AGE
frontend-hmmj2   1/1     Running   0          9s
pod1             1/1     Running   0          36s
pod2             1/1     Running   0          36s
```

Таким образом, ReplicaSet может управлять набором Pod с разными конфигурациями.

## Создание манифеста ReplicaSet

Как и любой другой объект Kubernetes API, ReplicaSet должен содержать поля `apiVersion`, `kind` и `metadata`. Для этого ресурса значение `kind` всегда равно `ReplicaSet`.

Когда плоскость управления создаёт Pod для ReplicaSet, имя ресурса (`.metadata.name`) используется как часть основы для формирования имён этих Pod. Имя ReplicaSet должно соответствовать формату DNS-поддомена. Однако это может привести к неожиданным результатам при формировании имён узлов Pod (`hostname`). Для лучшей совместимости рекомендуется придерживаться более строгих правил именования DNS-меток.

ReplicaSet также должен содержать секцию `.spec`.

### Шаблон Pod

Поле `.spec.template` содержит шаблон Pod, в котором обязательно должны быть указаны метки. В нашем примере `frontend.yaml` используется одна метка: `tier: frontend`.

Следите за тем, чтобы метки не пересекались с селекторами других контроллеров. Иначе они могут попытаться принять этот Pod под своё управление.

Для поля политики перезапуска `.spec.template.spec.restartPolicy` разрешено только значение `Always`. Оно используется по умолчанию.

### Селектор Pod

Поле `.spec.selector` задаёт селектор меток, по которым ReplicaSet определяет Pod, подходящие для управления. В нашем примере `frontend.yaml` он выглядит так:

```yaml
matchLabels:
  tier: frontend
```

В ReplicaSet значение `.spec.template.metadata.labels` должно соответствовать `spec.selector`. В противном случае API-сервер отклонит манифест.

> [!TIP] Примечание
  Если два ReplicaSet используют одинаковый `.spec.selector`, но разные значения `.spec.template.metadata.labels` и `.spec.template.spec`, каждый из них будет игнорировать Pod, созданные другим ReplicaSet.

### Количество реплик

Количество одновременно работающих Pod задаётся полем `.spec.replicas`. ReplicaSet создаёт или удаляет Pod, чтобы поддерживать указанное значение.

Если `.spec.replicas` не задано, по умолчанию используется значение `1`.

## Работа с ReplicaSet

### Удаление ReplicaSet вместе с его Pod

Чтобы удалить ReplicaSet и все принадлежащие ему Pod, используйте команду `kubectl delete`. По умолчанию сборщик мусора автоматически удаляет все зависимые Pod.

При использовании REST API или библиотеки `client-go` необходимо указать `propagationPolicy` со значением `Background` или `Foreground` в параметре `-d`. Например:

```bash
kubectl proxy --port=8080
curl -X DELETE  'localhost:8080/apis/apps/v1/namespaces/default/replicasets/frontend' \
  -d '{"kind":"DeleteOptions","apiVersion":"v1","propagationPolicy":"Foreground"}' \
  -H "Content-Type: application/json"
```

### Удаление только ReplicaSet

Можно удалить ReplicaSet, не затрагивая принадлежащие ему Pod. Для этого при использовании `kubectl delete` укажите параметр `--cascade=orphan`.

При использовании REST API или библиотеки `client-go` необходимо задать `propagationPolicy: Orphan`. Например:

```bash
kubectl proxy --port=8080
curl -X DELETE  'localhost:8080/apis/apps/v1/namespaces/default/replicasets/frontend' \
  -d '{"kind":"DeleteOptions","apiVersion":"v1","propagationPolicy":"Orphan"}' \
  -H "Content-Type: application/json"
```

После удаления исходного ReplicaSet можно создать новый взамен него. Если у старого и нового ресурсов совпадает `.spec.selector`, новый ReplicaSet примет существующие Pod под своё управление.

При этом он не будет пытаться привести существующие Pod в соответствие с новым шаблоном. Для контролируемого обновления Pod используйте Deployment, поскольку ReplicaSet не поддерживает непосредственное последовательное обновление (rolling update).

### Завершение Pod

Состояние функции: Beta начиная с Kubernetes v1.35; включена по умолчанию.

Чтобы включить эту функцию, задайте переключатель `DeploymentReplicaSetTerminatingReplicas` (`feature gate`) на API-сервере и в `kube-controller-manager`.

Завершение Pod после удаления или уменьшения количества реплик может занимать значительное время. В этот период Pod могут продолжать потреблять ресурсы, поэтому общее количество Pod временно может превышать значение `.spec.replicas`.

Отслеживать завершающиеся Pod можно с помощью поля `.status.terminatingReplicas` объекта ReplicaSet.

### Исключение Pod из ReplicaSet

Чтобы исключить Pod из ReplicaSet, измените его метки. Это может пригодиться, например, для отладки или восстановления данных.

Исключённый Pod будет автоматически заменён новым, если количество реплик не было изменено.

### Масштабирование ReplicaSet

Увеличить или уменьшить количество реплик можно, изменив поле `.spec.replicas`. Контроллер ReplicaSet следит за тем, чтобы нужное количество Pod с соответствующими метками было доступно и работало.

При уменьшении количества реплик контроллер выбирает Pod для удаления, сортируя их по следующим правилам:

1. Сначала удаляются Pod в состоянии `Pending`, которые не удаётся запланировать на узел.
2. Если задана аннотация `controller.kubernetes.io/pod-deletion-cost`, приоритет отдаётся Pod с меньшим значением.
3. Сначала удаляются Pod с узлов, на которых работает больше реплик.
4. Если время создания Pod различается, сначала удаляется более новый Pod. Время создания группируется по целочисленной логарифмической шкале.

Если ни одно из правил не позволяет определить приоритет, Pod выбирается случайным образом.

### Стоимость удаления Pod

Состояние функции: Beta начиная с Kubernetes v1.22.

С помощью аннотации `controller.kubernetes.io/pod-deletion-cost` можно указать, какие Pod предпочтительнее удалять при уменьшении количества реплик ReplicaSet.

Аннотацию задают непосредственно для Pod. Допустимый диапазон значений: `[-2147483648, 2147483647]`. Значение определяет стоимость удаления Pod относительно других Pod того же ReplicaSet. Pod с меньшей стоимостью удаляются в первую очередь.

Если аннотация не задана, её значение считается равным `0`. Допускаются отрицательные значения. Некорректные значения отклоняются API-сервером.

Функция имеет статус Beta и включена по умолчанию. Её можно отключить с помощью `feature gate` `PodDeletionCost` в `kube-apiserver` и `kube-controller-manager`.

 >[!TIP] **Примечание**
>- Аннотация учитывается по принципу наилучшего возможного результата (best effort) и не гарантирует определённый порядок удаления Pod.
>- Не рекомендуется часто обновлять аннотацию, например при каждом изменении значения метрики. Это может привести к большому количеству обновлений Pod на API-сервере.

#### Пример использования

У разных Pod одного приложения может быть разная нагрузка. При уменьшении количества реплик приложение может предпочесть удалить Pod с меньшим использованием ресурсов.

Чтобы не обновлять аннотации слишком часто, приложению следует установить `controller.kubernetes.io/pod-deletion-cost` один раз перед уменьшением количества реплик. Значение можно выбрать пропорционально уровню использования ресурсов Pod.

Этот подход подходит для случаев, когда само приложение управляет уменьшением количества реплик, например для управляющего Pod в развёртывании Spark.

### Использование ReplicaSet в качестве цели Horizontal Pod Autoscaler

ReplicaSet может выступать целью для Horizontal Pod Autoscaler (HPA), который автоматически изменяет количество его реплик.

Ниже приведён пример HPA для ReplicaSet, созданного ранее.

Файл `controllers/hpa-rs.yaml`:

```yaml
apiVersion: autoscaling/v1
kind: HorizontalPodAutoscaler
metadata:
  name: frontend-scaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: ReplicaSet
    name: frontend
  minReplicas: 3
  maxReplicas: 10
  targetCPUUtilizationPercentage: 50
```

Сохраните манифест в `hpa-rs.yaml` и примените его к кластеру Kubernetes. Будет создан HPA, который автоматически масштабирует целевой ReplicaSet в зависимости от использования CPU его Pod.

```bash
kubectl apply -f https://k8s.io/examples/controllers/hpa-rs.yaml
```

Того же результата можно добиться с помощью команды `kubectl autoscale` — это проще:

```bash
kubectl autoscale rs frontend --max=10 --min=3 --cpu=50%
```

## Альтернативы ReplicaSet

### Deployment (рекомендуется)

`Deployment` — это ресурс, который может владеть ReplicaSet и управлять обновлением этих ресурсов и их Pod с помощью декларативных обновлений на стороне сервера, включая последовательные обновления (rolling updates).

Хотя ReplicaSet можно использовать самостоятельно, сейчас он преимущественно применяется внутри Deployment для управления созданием, удалением и обновлением Pod.

При использовании Deployment не нужно вручную управлять создаваемыми ReplicaSet: Deployment владеет ими и управляет ими автоматически. Поэтому, если вам нужен ReplicaSet, рекомендуется использовать Deployment.

### Отдельные Pod

В отличие от Pod, созданных напрямую пользователем, ReplicaSet автоматически заменяет Pod, которые были удалены или завершились по любой причине. Например, это может произойти из-за сбоя узла или планового обслуживания, при котором требуется перезагрузка ядра.

Поэтому рекомендуется использовать ReplicaSet, даже если приложению нужен всего один Pod. Его можно сравнить с супервизором процессов, который управляет не отдельными процессами на одном узле, а несколькими Pod на разных узлах.

Перезапуск контейнеров на конкретном узле ReplicaSet делегирует соответствующему агенту, например Kubelet.

### Job

Для Pod, которые должны самостоятельно завершить работу, например для пакетных заданий, используйте `Job` вместо ReplicaSet.

### DaemonSet

Для Pod, выполняющих функции на уровне узла, например мониторинг или сбор журналов, используйте `DaemonSet` вместо ReplicaSet.

Срок жизни таких Pod связан со сроком жизни узла: Pod должен работать на узле до запуска других Pod и может быть безопасно завершён, когда узел готов к перезагрузке или выключению.

### ReplicationController

ReplicaSet пришёл на смену `ReplicationController`. Оба ресурса выполняют одну и ту же задачу и работают похожим образом.

Основное различие заключается в том, что `ReplicationController` не поддерживает селекторы на основе наборов значений (set-based selector requirements), описанные в руководстве по меткам.

Поэтому предпочтительнее использовать ReplicaSet.
