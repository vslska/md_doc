## Организация конфигураций ресурсов

Многие приложения требуют создания нескольких ресурсов, например Deployment вместе с Service. Управление можно упростить, сгруппировав их в одном файле (разделитель `---` в YAML). Ресурсы создаются в порядке их появления в манифесте, поэтому **лучше указывать Service первым** — это гарантирует, что планировщик сможет распределить Pod'ы, связанные с Service, по мере их создания контроллером (например, Deployment) .

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-nginx-svc
  labels:
    app: nginx
spec:
  type: LoadBalancer
  ports:
  - port: 80
  selector:
    app: nginx
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-nginx
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80
```

`kubectl apply` принимает несколько аргументов `-f` и URL в качестве источника конфигурации. Рекомендуется помещать ресурсы одной микрослужбы или уровня приложения в один файл, а все файлы приложения — в один каталог .

## Массовые операции в kubectl

`kubectl` умеет не только создавать ресурсы массово, но и извлекать их имена из конфигурационных файлов для других операций:

```bash
kubectl delete -f https://k8s.io/examples/application/nginx-app.yaml
# deployment.apps "my-nginx" deleted
# service "my-nginx-svc" deleted
```

Для двух ресурсов можно указать оба в командной строке через синтаксис `resource/name`:

```bash
kubectl delete deployments/my-nginx services/my-nginx-svc
```

Для большего числа ресурсов удобнее использовать селектор меток через `-l` или `--selector`:

```bash
kubectl delete deployment,services -l app=nginx
```

### Цепочки и фильтрация

Поскольку `kubectl` выводит имена ресурсов в том же синтаксисе, который принимает, можно строить цепочки через `$()` или `xargs`:

```bash
kubectl get $(kubectl create -f docs/concepts/cluster-administration/nginx/ -o name | grep service/)
kubectl create -f docs/concepts/cluster-administration/nginx/ -o name | grep service/ | xargs -i kubectl get '{}'
```

### Рекурсивные операции с локальными файлами

Если ресурсы организованы по подкаталогам внутри каталога, операции можно выполнять рекурсивно с помощью `--recursive` или `-R` вместе с `-f`. Без этого флага `kubectl apply -f project/k8s/development` остановится на первом уровне и вернёт ошибку, так как в самом каталоге нет файлов манифестов. Флаг работает с любой операцией, принимающей `-f`: `create`, `get`, `delete`, `describe`, `rollout`, а также с несколькими аргументами `-f` одновременно .

## Обновление приложения без простоя

`kubectl` поддерживает несколько операций обновления. Можно запускать несколько копий приложения и использовать rollout для постепенного переключения трафика на новые здоровые Pod'ы .

### Пример обновления через Deployment

```bash
kubectl create deployment my-nginx --image=nginx:1.14.2
kubectl scale --replicas 1 deployments/my-nginx --subresource='scale' --type='merge' -p '{"spec":{"replicas": 1}}'
kubectl patch --type='merge' -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge": "100%" }}}}'
kubectl edit deployment/my-nginx
# изменить .spec.template.spec.containers[0].image на nginx:1.16.1, сохранить
```

Deployment декларативно обновит приложение постепенно: только определённое количество старых реплик может быть недоступно во время обновления, и только определённое количество новых реплик может быть создано сверх желаемого числа Pod'ов. Rollout можно использовать с DaemonSet, Deployment или StatefulSet .

### Управление rollout

```bash
kubectl apply -f my-deployment.yaml
kubectl rollout status deployment/my-deployment --timeout 10m

kubectl apply -f backing-stateful-component.yaml
kubectl rollout status statefulsets/backing-stateful-component --watch=false
```

Rollout можно приостановить, возобновить или отменить .

## Канареечные развёртывания (Canary deployments)

Для различения разных релизов или конфигураций одного компонента используются метки. Распространённая практика — развернуть канареечную версию нового релиза (через тег образа в шаблоне Pod'а) рядом с предыдущим, чтобы новый релиз получил живой production-трафик до полного выката .

Стабильный релиз получает метку `track: stable`, канареечный — `track: canary`. Service выбирает общее подмножество меток (без `track`), чтобы трафик шёл на оба набора. Соотношение реплик (например, 3:1) определяет долю трафика каждого релиза .

```yaml
# stable
labels:
  app: guestbook
  tier: frontend
  track: stable
image: gb-frontend:v3

# canary
labels:
  app: guestbook
  tier: frontend
  track: canary
image: gb-frontend:v4

# service selector (без track)
selector:
  app: guestbook
  tier: frontend
```

## Обновление аннотаций

Аннотации — произвольные неидентифицирующие метаданные для извлечения API-клиентами. Добавляются через `kubectl annotate`:

```bash
kubectl annotate pods my-nginx-v4-9gw19 description='my frontend running nginx'
```

## Масштабирование приложения

```bash
kubectl scale deployment/my-nginx --replicas=1
kubectl autoscale deployment/my-nginx --min=1 --max=3
```

Автоматическое масштабирование требует существующего источника метрик контейнеров и Pod'ов (Metrics Server) .

## Обновление ресурсов на месте (In-place updates)

### kubectl apply

Рекомендуется хранить конфигурационные файлы в системе контроля версий и применять изменения через `kubectl apply`. Команда сравнивает отправляемую версию с предыдущей и применяет изменения, не перезаписывая автоматические изменения свойств, которые не указаны в конфигурации. Механизм описан в разделе Server-Side Apply .

**Важное замечание о смешивании методов**: смешивание `kubectl apply` с императивными `create` и `replace` не поддерживается, поскольку `create` и `replace` не сохраняют аннотацию `kubectl.kubernetes.io/last-applied-configuration`, которую `apply` использует для вычисления обновлений .

### kubectl edit

Обновление ресурса в редакторе. Эквивалентно последовательности `get` → редактирование → `apply`. Редактор задаётся через переменные окружения `EDITOR` или `KUBE_EDITOR` .

### kubectl patch

Обновление API-объектов на месте. Поддерживает JSON patch, JSON merge patch и strategic merge patch .

### Деструктивные обновления

Некоторые поля нельзя обновить после инициализации, или требуется немедленное рекурсивное изменение (например, исправление сломанных Pod'ов, созданных Deployment). Для таких случаев используется `replace --force`, который удаляет и пересоздаёт ресурс :

```bash
kubectl replace -f https://k8s.io/examples/application/nginx/nginx-deployment.yaml --force
# deployment.apps/my-nginx deleted
# deployment.apps/my-nginx replaced
```

## Внешние инструменты

- **Helm** — управление пакетами предварительно сконфигурированных ресурсов Kubernetes (Helm charts). Сторонний проект, не является частью Kubernetes.
- **Kustomize** — обходит манифест Kubernetes для добавления, удаления или обновления параметров конфигурации. Доступен как отдельный бинарник и как нативная функция `kubectl` (флаг `-k`).
