## Общие принципы

С помощью автомасштабирования можно автоматически обновлять рабочие нагрузки, чтобы кластер более эластично и эффективно реагировал на изменения спроса на ресурсы. Масштабирование может увеличивать или уменьшать количество реплик, управляемых рабочей нагрузкой (**горизонтальное масштабирование**), либо изменять ресурсы, доступные репликам, на месте (**вертикальное масштабирование**) .

Масштабирование может быть ручным и автоматическим.

### Ручное масштабирование

Горизонтальное масштабирование выполняется через `kubectl scale`. Вертикальное — через изменение определения ресурсов рабочей нагрузки (патч манифеста) .

## Горизонтальное автомасштабирование: HorizontalPodAutoscaler (HPA)

HPA реализован как API-ресурс Kubernetes и контроллер. Он периодически корректирует количество реплик в рабочей нагрузке, чтобы соответствовать наблюдаемому использованию ресурсов, например CPU или памяти .

**Важно о версии API**: текущая стабильная версия — `autoscaling/v2`, поддерживающая масштабирование по памяти и кастомным метрикам. Поля, добавленные в `autoscaling/v2`, при использовании `autoscaling/v1` сохраняются в аннотациях .

### Требования для работы HPA

| Компонент | Назначение |
|---|---|
| **Metrics Server** | Предоставляет Metrics API с базовыми метриками CPU и памяти; без него HPA не получает данные  |
| **Resource requests** | У Pod'ов должны быть заданы `resources.requests.cpu` и/или `memory` для расчёта утилизации  |
| **Readiness** | HPA учитывает только готовые Pod'ы; неготовые или только что запущенные Pod'ы могут игнорироваться при расчёте  |

### Пример HPA по CPU и памяти

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

### Алгоритм и допуск (tolerance)

Базовый расчёт желаемого числа реплик:

```
desiredReplicas = ceil(currentReplicas × (currentMetric / desiredMetric))
```

Если отношение текущей метрики к целевой достаточно близко к 1.0 (в пределах глобально настраиваемого допуска, по умолчанию **0.1**), контроллер пропускает операцию масштабирования. Это предотвращает «дрожание» (thrashing/flapping) при небольших колебаниях метрик .

**Новое в v1.33 (alpha)**: появилась возможность настраивать допуск отдельно для scale-up и scale-down через `spec.behavior.scaleUp.tolerance` и `spec.behavior.scaleDown.tolerance` (feature gate `HPAConfigurableTolerance`). Это полезно для больших деплойментов, где 10% допуска означают десятки Pod'ов .

### Масштабирование до нуля (Beta в v1.37)

Начиная с Kubernetes v1.37, HPA может масштабировать рабочую нагрузку **до нуля реплик** и обратно, используя object или external метрики. Раньше для этого требовался внешний компонент или alpha feature gate .

**Ключевое ограничение**: CPU и memory метрики не работают для масштабирования с нуля, так как при нуле реплик нет Pod'ов для измерения. Нужны метрики, существующие независимо от потребителей, например длина очереди (external metric) .

HPA различает два состояния нуля через condition `ScaledToZero`:
- `ScaledToZero=True` — HPA сам отмасштабировал до нуля и продолжит следить за метрикой.
- Ноль без этого condition — рабочая нагрузка была вручную приостановлена оператором; HPA не будет её «будить» .

**Важно для HTTP-нагрузок**: Service не буферизует запросы, пока нет готовых Pod'ов. Для request-driven нагрузок нужен отдельный буферный слой .

## Вертикальное автомасштабирование: VerticalPodAutoscaler (VPA)

VPA — **не встроенный** в Kubernetes компонент, а add-on, который необходимо развернуть отдельно. После установки позволяет создавать CRD для рабочих нагрузок, определяющие, как и когда масштабировать ресурсы управляемых реплик .

**Требование**: для работы VPA необходим Metrics Server .

### Режимы VPA

| Режим | Поведение |
|---|---|
| **Auto** | В настоящее время действует как `Recreate` |
| **Recreate** | Назначает requests при создании Pod'а и удаляет существующие Pod'ы, если запрошенные ресурсы значительно отличаются от новых рекомендаций |
| **Initial** | Назначает requests только при создании Pod'а, не изменяет позже |
| **Off** | Не изменяет ресурсы автоматически; рекомендации рассчитываются и доступны для просмотра в объекте VPA  |

### Ограничение: VPA и in-place resize

**По состоянию на Kubernetes 1.37 VPA не поддерживает изменение размеров Pod'ов на месте (in-place)**, хотя работа над этой интеграцией ведётся. Для ручного изменения размеров на месте используется отдельный механизм Resize Container Resources In-Place .

### In-Place Pod Vertical Scaling (стабильно с v1.35)

Функция in-place изменения CPU и memory для работающих Pod'ов стала стабильной в Kubernetes v1.35. Она позволяет изменять `spec.containers[*].resources` для CPU и memory без перезапуска контейнера (в зависимости от `resizePolicy` контейнера) .

**Важно**: это отдельный механизм, не интегрированный в VPA на момент v1.37.

## Автомасштабирование на основе размера кластера

Для рабочих нагрузок, которые нужно масштабировать в зависимости от размера кластера (например, cluster-dns или другие системные компоненты), используется **Cluster Proportional Autoscaler**. Как и VPA, это не часть ядра Kubernetes, а отдельный проект на GitHub. Он отслеживает количество планируемых узлов и ядер и масштабирует количество реплик целевой рабочей нагрузки соответственно .

**Cluster Proportional Vertical Autoscaler** (beta) корректирует resource requests рабочей нагрузки на основе количества узлов и/или ядер в кластере, сохраняя количество реплик неизменным .

## Автомасштабирование на основе событий: KEDA

**Kubernetes Event Driven Autoscaler (KEDA)** — CNCF-graduated проект, позволяющий масштабировать рабочие нагрузки на основе количества событий, подлежащих обработке, например количества сообщений в очереди. Существует широкий набор адаптеров для разных источников событий .

KEDA может масштабировать до нуля, что делает его популярным для обработчиков очередей и batch-процессоров.

## Автомасштабирование по расписанию

Стратегия масштабирования по расписанию (например, для снижения потребления ресурсов в непиковые часы) может быть реализована с помощью KEDA в связке с **Cron scaler**, который позволяет задавать расписания (и часовые пояса) для масштабирования рабочих нагрузок .

## Масштабирование инфраструктуры кластера

Если масштабирования рабочих нагрузок недостаточно, можно масштабировать саму инфраструктуру кластера — обычно это означает добавление или удаление узлов (Node autoscaling) .
