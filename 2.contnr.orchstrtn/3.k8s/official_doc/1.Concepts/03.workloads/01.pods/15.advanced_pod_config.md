## PriorityClass

PriorityClass позволяют задать **важность Pod'ов относительно других Pod'ов**. Если вы назначаете Pod'у priority class, Kubernetes устанавливает поле `.spec.priority` для этого Pod'а на основе указанной вами PriorityClass (напрямую задать `.spec.priority` нельзя). Если Pod не может быть запланирован из-за нехватки ресурсов, kube-scheduler пытается **вытеснить** Pod'ы с более низким приоритетом, чтобы сделать планирование Pod'а с более высоким приоритетом возможным.

PriorityClass — это **cluster-scoped** API-объект, который сопоставляет имя priority class целочисленному значению приоритета. **Большие числа означают более высокий приоритет.**

### Определение PriorityClass

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 10000
globalDefault: false
description: "Priority class for high-priority workloads"
```

### Указание приоритета Pod'а через PriorityClass

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx
  priorityClassName: high-priority
```

### Встроенные PriorityClass

Kubernetes предоставляет две встроенные PriorityClass:

- **`system-cluster-critical`** — для системных компонентов, критичных для кластера.
- **`system-node-critical`** — для системных компонентов, критичных для отдельных узлов. Это **наивысший приоритет**, который могут иметь Pod'ы в Kubernetes.

Подробнее см. «Pod Priority and Preemption».

## RuntimeClass

RuntimeClass позволяет указать **низкоуровневый container runtime** для Pod'а. Это полезно, когда нужно задать разные container runtime для разных типов Pod'ов — например, когда нужны разные уровни изоляции или функции runtime.

### Пример Pod'а

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  runtimeClassName: myclass
  containers:
  - name: mycontainer
    image: nginx
```

RuntimeClass — **cluster-scoped** объект, представляющий container runtime, доступный на некоторых или всех узлах.

Администратор кластера устанавливает и настраивает конкретные runtime, лежащие в основе RuntimeClass. Он может настроить специальную конфигурацию container runtime на всех узлах или только на некоторых.

Подробнее см. документацию RuntimeClass.

## Конфигурация security context на уровне Pod'а и контейнера

Поле **Security context** в спецификации Pod'а даёт гранулярный контроль над настройками безопасности для Pod'ов и контейнеров.

### securityContext на уровне всего Pod'а

Некоторые аспекты безопасности применяются ко всему Pod'у; для других аспектов может понадобиться задать значение по умолчанию без переопределений на уровне контейнера.

Пример использования `securityContext` на уровне Pod'а:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo
spec:
  securityContext:  # This applies to the entire Pod
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: sec-ctx-demo
    image: registry.k8s.io/e2e-test-images/agnhost:2.45
    command: ["sh", "-c", "sleep 1h"]
```

### Security context на уровне контейнера

Можно задать security context только для конкретного контейнера. Пример:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo-2
spec:
  containers:
  - name: sec-ctx-demo-2
    image: gcr.io/google-samples/node-hello:1.0
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
      runAsUser: 1000
      capabilities:
        drop:
        - ALL
      seccompProfile:
        type: RuntimeDefault
```

### Опции security context

- **User and Group IDs** — контроль того, от какого пользователя/группы работает контейнер.
- **Capabilities** — добавление или сброс Linux capabilities.
- **Seccomp Profiles** — установка профилей security computing.
- **SELinux Options** — настройка контекста SELinux.
- **AppArmor** — настройка профилей AppArmor для дополнительного контроля доступа.
- **Windows Options** — настройка специфичных для Windows параметров безопасности.

> **⚠️ Внимание:** можно также использовать Pod-level `securityContext`, чтобы разрешить **privileged mode** в Linux-контейнерах. Privileged mode **переопределяет** многие другие настройки безопасности в `securityContext`. Избегайте этой настройки, если только не можете предоставить эквивалентные разрешения через другие поля `securityContext`. Windows-контейнеры можно запускать в аналогичном privileged-режиме, установив флаг `windowsOptions.hostProcess` в security context уровня Pod'а. Подробности и инструкции см. «Create a Windows HostProcess Pod».

Подробнее см. «Configure a Security Context for a Pod or Container».

## Влияние на решения планирования Pod'ов

Kubernetes предоставляет несколько механизмов для контроля того, на каких узлах планируются Pod'ы.

### Node selectors

Простейшая форма ограничения выбора узла:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx
  nodeSelector:
    disktype: ssd
```

### Node affinity

Node affinity позволяет задавать правила, ограничивающие узлы, на которых может быть запланирован Pod. Пример Pod'а, который предпочитает узлы, помеченные как находящиеся на определённом континенте, с выбором по значению метки `topology.kubernetes.io/zone`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: with-node-affinity
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - antarctica-east1
            - antarctica-west1
  containers:
  - name: with-node-affinity
    image: registry.k8s.io/pause:3.8
```

### Pod affinity и anti-affinity

Помимо node affinity, можно ограничивать узлы, на которых может быть запланирован Pod, на основе **меток других Pod'ов**, уже работающих на узлах. Pod affinity позволяет задавать правила о том, где Pod должен быть размещён **относительно других Pod'ов**.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: with-pod-affinity
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - database
        topologyKey: topology.kubernetes.io/zone
  containers:
  - name: with-pod-affinity
    image: registry.k8s.io/pause:3.8
```

### Tolerations (допуски)

Tolerations позволяют Pod'ам планироваться на узлах с **соответствующими taint'ами**:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
  - name: myapp
    image: nginx
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"
```

Подробнее см. «Assign Pods to Nodes».

## Overhead Pod'а

Pod overhead позволяет учитывать ресурсы, потребляемые **инфраструктурой Pod'а**, поверх запросов и лимитов контейнеров.

```yaml
---
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kvisor-runtime
handler: kvisor-runtime
overhead:
  podFixed:
    memory: "2Gi"
    cpu: "500m"
---
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  runtimeClassName: kvisor-runtime
  containers:
  - name: myapp
    image: nginx
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"
```
