Есть два способа предоставить поля Pod'а и контейнера работающему контейнеру: **переменные окружения** и **файлы**, заполняемые специальным типом тома. Вместе эти два способа называются **downward API**.

Иногда контейнеру полезно иметь информацию о себе, не будучи слишком сильно связанным с Kubernetes. Downward API позволяет контейнерам потреблять информацию о себе или о кластере **без использования клиента Kubernetes или API-сервера**.

Пример — существующее приложение, которое предполагает, что конкретная общеизвестная переменная окружения содержит уникальный идентификатор. Один из вариантов — обернуть приложение, но это утомительно, подвержено ошибкам и нарушает цель слабой связанности. Лучший вариант — использовать **имя Pod'а** как идентификатор и внедрить имя Pod'а в общеизвестную переменную окружения.

В Kubernetes есть два способа предоставить поля Pod'а и контейнера работающему контейнеру:

- как **переменные окружения**;
- как **файлы в томе `downwardAPI`**.

Вместе эти два способа называются **downward API**.

## Доступные поля

Через downward API доступны только **некоторые** поля API Kubernetes. В этом разделе перечислено, какие поля можно сделать доступными.

Информацию из доступных полей **уровня Pod'а** можно передавать через `fieldRef`. На уровне API спецификация Pod'а всегда определяет как минимум один Container. Информацию из доступных полей **уровня Container'а** можно передавать через `resourceFieldRef`.

### Информация, доступная через `fieldRef`

Для некоторых полей уровня Pod'а их можно предоставить контейнеру либо как **переменную окружения**, либо через **том `downwardAPI`**. Поля, доступные через любой из этих механизмов:

| Поле | Описание |
|---|---|
| `metadata.name` | имя Pod'а |
| `metadata.namespace` | пространство имён Pod'а |
| `metadata.uid` | уникальный ID Pod'а |
| `metadata.annotations['<KEY>']` | значение аннотации Pod'а с именем `<KEY>` (например, `metadata.annotations['myannotation']`) |
| `metadata.labels['<KEY>']` | текстовое значение метки Pod'а с именем `<KEY>` (например, `metadata.labels['mylabel']`) |

Следующая информация доступна через **переменные окружения**, но **не** как поле `fieldRef` тома `downwardAPI`:

| Поле | Описание |
|---|---|
| `spec.serviceAccountName` | имя service account Pod'а |
| `spec.nodeName` | имя узла, на котором выполняется Pod |
| `status.hostIP` | основной IP-адрес узла, к которому назначен Pod |
| `status.hostIPs` | dual-stack версия `status.hostIP`; первый всегда совпадает с `status.hostIP` |
| `status.podIP` | основной IP-адрес Pod'а (обычно его IPv4-адрес) |
| `status.podIPs` | dual-stack версия `status.podIP`; первый всегда совпадает с `status.podIP` |

Следующая информация доступна через **поле `fieldRef` тома `downwardAPI`**, но **не** как переменные окружения:

| Поле | Описание |
|---|---|
| `metadata.labels` | все метки Pod'а в формате `label-key="escaped-label-value"`, по одной метке на строку |
| `metadata.annotations` | все аннотации Pod'а в формате `annotation-key="escaped-annotation-value"`, по одной аннотации на строку |

Внутри тома предоставленные данные находятся как **read-only файлы** в plain-text формате.

### Информация, доступная через `resourceFieldRef`

Эти поля **уровня Container'а** позволяют предоставить информацию о запросах и лимитах для таких ресурсов, как CPU и память.

> **Примечание:** **Состояние функции:** стабильно с Kubernetes v1.35.
>
> Ресурсы CPU и памяти контейнера можно **изменять (resize)** во время работы контейнера. Если это происходит, том `downwardAPI` будет **обновлён**, а переменные окружения — **нет**, если контейнер не перезапустится. Подробнее см. «Resize CPU and Memory Resources assigned to Containers».

| Поле | Описание |
|---|---|
| `resource: limits.cpu` | CPU-лимит контейнера |
| `resource: requests.cpu` | CPU-запрос контейнера |
| `resource: limits.memory` | memory-лимит контейнера |
| `resource: requests.memory` | memory-запрос контейнера |
| `resource: limits.hugepages-*` | hugepages-лимит контейнера |
| `resource: requests.hugepages-*` | hugepages-запрос контейнера |
| `resource: limits.ephemeral-storage` | ephemeral-storage-лимит контейнера |
| `resource: requests.ephemeral-storage` | ephemeral-storage-запрос контейнера |

### Резервная информация для лимитов ресурсов

Если CPU- и memory-лимиты для контейнера **не заданы**, а вы пытаетесь предоставить эту информацию через downward API, kubelet по умолчанию предоставляет **максимальное allocatable-значение** для CPU и памяти на основе расчёта node allocatable.
