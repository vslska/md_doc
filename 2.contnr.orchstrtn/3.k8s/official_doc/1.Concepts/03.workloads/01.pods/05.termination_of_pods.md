Поскольку Pod'ы представляют процессы, выполняющиеся на узлах кластера, важно дать этим процессам корректно завершиться, когда они больше не нужны, — а не обрывать их сигналом KILL без возможности что-либо почистить.

**Цель дизайна:** вы можете запросить удаление и знать, когда процессы завершатся, но при этом удаление в итоге обязательно завершится. Когда вы запрашиваете удаление Pod'а, кластер фиксирует и отслеживает **grace period** (льготный период) до принудительного убийства Pod'а. С этим отслеживанием kubelet пытается выполнить корректное завершение.

Обычно kubelet просит container runtime остановить контейнеры Pod'а, сначала отправляя сигнал `TERM` (он же `SIGTERM`) основному процессу в каждом контейнере с таймаутом grace period. Запросы на остановку контейнеров обрабатываются runtime **асинхронно**, порядок обработки не гарантирован. Многие container runtime уважают значение `STOPSIGNAL`, заданное в образе контейнера, и, если оно отличается, отправляют именно его вместо `TERM`. Когда grace period истекает, оставшимся процессам отправляется `KILL`, после чего Pod удаляется из API-сервера. Если kubelet или управляющий сервис container runtime перезапускается во время ожидания завершения процессов, кластер повторяет попытку с самого начала, включая полный исходный grace period.

## Сигналы остановки

Сигнал остановки, используемый для убийства контейнера, можно задать в образе контейнера инструкцией `STOPSIGNAL`. Если в образе сигнал не задан, используется сигнал по умолчанию container runtime (`SIGTERM` для containerd и CRI-O).

### Пользовательские сигналы остановки

> **Состояние функции:** Alpha с Kubernetes v1.33; отключено по умолчанию.

Если включён feature gate `ContainerStopSignals`, можно задать пользовательский сигнал остановки для контейнеров через `Lifecycle`. Для этого требуется поле `spec.os.name` в Pod'е. Список допустимых сигналов зависит от ОС, на которую запланирован Pod. Для Pod'ов на Windows-узлах поддерживаются только `SIGTERM` и `SIGKILL`.

Пример Pod'а с пользовательским сигналом остановки:

```yaml
spec:
  os:
    name: linux
  containers:
    - name: my-container
      image: container-image:latest
      lifecycle:
        stopSignal: SIGUSR1
```

Если сигнал задан в `lifecycle`, он **переопределяет** сигнал из образа контейнера. Если сигнал не задан в спецификации контейнера, используется поведение по умолчанию.

## Поток завершения Pod'а

Пример потока завершения:

1. Вы вручную удаляете Pod через `kubectl` с grace period по умолчанию (30 секунд).

2. В API-сервере Pod обновляется: добавляется время, после которого Pod считается «мёртвым», вместе с grace period. В `kubectl describe` Pod отображается как `Terminating`. На узле, где работает Pod, kubelet, увидев, что Pod помечен как terminating (задана длительность корректного завершения), начинает локальный процесс остановки.

   - Если у одного из контейнеров Pod'а задан `preStop`-хук и `terminationGracePeriodSeconds` в спецификации Pod'а **не** равен 0, kubelet выполняет этот хук внутри контейнера. Значение по умолчанию `terminationGracePeriodSeconds` — 30 секунд.
   - Если `preStop`-хук всё ещё выполняется после истечения grace period, kubelet запрашивает небольшое разовое продление grace period на 2 секунды.

   > **Примечание:** если `preStop`-хуку нужно больше времени, чем позволяет grace period по умолчанию, измените `terminationGracePeriodSeconds`.

3. Kubelet запускает container runtime, который отправляет сигнал `TERM` процессу 1 в каждом контейнере.

4. Если в Pod'е есть sidecar-контейнеры, действует специальный порядок. Иначе контейнеры Pod'а получают `TERM` в разное время и в произвольном порядке. Если порядок остановки важен, используйте `preStop`-хук для синхронизации (или перейдите на sidecar-контейнеры).

5. Одновременно с началом корректного завершения плоскость управления решает, удалять ли завершающийся Pod из объектов EndpointSlice, где эти объекты представляют Service с настроенным селектором. ReplicaSet и другие workload-ресурсы больше не считают завершающийся Pod валидной, работающей репликой.

   Pod'ы, которые завершаются медленно, не должны продолжать обслуживать обычный трафик и должны начать завершение и дообработку открытых соединений. Некоторым приложениям нужно больше, чем просто закрыть открытые соединения: например, слив сессий (session draining) и завершение.

   Endpoint'ы, представляющие завершающиеся Pod'ы, **не удаляются из EndpointSlice немедленно**, а статус terminating раскрывается через API EndpointSlice. У завершающихся endpoint'ов статус ready всегда `false` (для обратной совместимости с версиями до 1.26), поэтому балансировщики не используют их для обычного трафика.

   Если нужен слив трафика с завершающегося Pod'а, фактическую готовность можно проверить по condition `serving`. Подробнее о реализации слива соединений см. туториал «Pods And Endpoints Termination Flow».

6. Kubelet обеспечивает остановку и завершение Pod'а.

   - Когда grace period истекает и в Pod'е ещё есть работающие контейнеры, kubelet запускает принудительную остановку. Container runtime отправляет `SIGKILL` всем процессам, всё ещё работающим в любом контейнере Pod'а. Kubelet также чистит скрытый pause-контейнер, если container runtime его использует.
   - Kubelet переводит Pod в терминальную фазу (`Failed` или `Succeeded` в зависимости от конечного состояния контейнеров).
   - Kubelet запускает принудительное удаление объекта Pod из API-сервера, устанавливая grace period в 0 (немедленное удаление).
   - API-сервер удаляет API-объект Pod'а, после чего он больше не виден ни одному клиенту.

## Принудительное завершение Pod'а

> **⚠️ Внимание:** принудительное удаление может быть разрушительным для некоторых workload'ов и их Pod'ов.

По умолчанию все удаления корректны в пределах 30 секунд. Команда `kubectl delete` поддерживает опцию `--grace-period=<секунды>`, позволяющую переопределить значение по умолчанию.

Установка grace period в 0 **принудительно и немедленно** удаляет Pod из API-сервера. Если Pod всё ещё работал на узле, это принудительное удаление запускает немедленную очистку на kubelet.

Через `kubectl` для принудительного удаления нужно указать **дополнительный** флаг `--force` вместе с `--grace-period=0`.

При принудительном удалении API-сервер **не ждёт** подтверждения от kubelet, что Pod завершён на узле. Он немедленно удаляет Pod из API, чтобы можно было создать новый Pod с тем же именем. На узле Pod'ам, которым установлено немедленное завершение, всё равно даётся небольшой grace period перед принудительным убийством.

> **⚠️ Внимание:** немедленное удаление не ждёт подтверждения, что работающий ресурс завершён. Ресурс может продолжать работать в кластере неограниченно долго.

Если нужно принудительно удалить Pod'ы, входящие в StatefulSet, см. документацию по удалению Pod'ов из StatefulSet.

## Остановка Pod'а и sidecar-контейнеры

Если Pod содержит один или несколько sidecar-контейнеров (init-контейнеров с `restartPolicy: Always`), kubelet **откладывает** отправку `TERM` этим sidecar-контейнерам, пока последний основной контейнер полностью не завершится. Sidecar-контейнеры завершаются **в обратном порядке** их определения в спецификации Pod'а. Это гарантирует, что sidecar-контейнеры продолжают обслуживать остальные контейнеры Pod'а, пока они ещё нужны.

Это означает, что медленное завершение основного контейнера задерживает и завершение sidecar-контейнеров. Если grace period истекает до завершения процесса, Pod может перейти в принудительное завершение. В этом случае все оставшиеся контейнеры Pod'а завершаются **одновременно** с коротким grace period.

Аналогично, если у Pod'а есть `preStop`-хук, превышающий grace period завершения, может произойти экстренное завершение. В целом, если вы использовали `preStop`-хуки для управления порядком завершения **без** sidecar-контейнеров, теперь их можно убрать и позволить kubelet управлять завершением sidecar автоматически.

## Сборка мусора Pod'ов (Garbage collection)

Для **failed** Pod'ов API-объекты остаются в API кластера, пока человек или контроллер явно их не удалит.

**Pod garbage collector (PodGC)** — контроллер в плоскости управления — очищает завершённые Pod'ы (с фазой `Succeeded` или `Failed`), когда число Pod'ов превышает настроенный порог (определяется `terminated-pod-gc-threshold` в kube-controller-manager). Это предотвращает утечку ресурсов по мере создания и завершения Pod'ов.

Кроме того, PodGC очищает Pod'ы, удовлетворяющие любому из условий:

- **orphan Pod'ы** — привязаны к узлу, которого больше не существует;
- **незапланированные завершающиеся Pod'ы**;
- **завершающиеся Pod'ы**, привязанные к неготовому узлу с taint `node.kubernetes.io/out-of-service`.

Вместе с очисткой PodGC помечает их как failed, если они в нетерминальной фазе. Также PodGC добавляет condition «disruption» при очистке orphan Pod'а. Подробнее см. «Pod disruption conditions».
