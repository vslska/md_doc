>**Состояние функции:** стабильно с Kubernetes v1.36. Впервые появилась в v1.28. Отключить или отказаться от этого поведения больше нельзя (функция заблокирована); если явно задать значение для связанного feature gate `UserNamespacesSupport`, Kubernetes его проигнорирует без ошибки.

Эта страница объясняет, как user namespaces используются в Pod'ах Kubernetes. User namespace **изолирует пользователя, работающего внутри контейнера, от пользователя на хосте**.

Процесс, работающий как root в контейнере, может работать как **другой (не-root) пользователь на хосте**; иными словами, процесс имеет полные привилегии для операций **внутри** user namespace, но **непривилегирован** для операций **вне** namespace.

Эту функцию можно использовать, чтобы **уменьшить ущерб**, который скомпрометированный контейнер может нанести хосту или другим Pod'ам на том же узле. Есть несколько уязвимостей безопасности уровня HIGH или CRITICAL, которые **не эксплуатировались** при активном user namespace. Ожидается, что user namespace смягчит и некоторые будущие уязвимости.

## Перед началом

Это функция **только для Linux**, и требуется поддержка **idmap mounts** на используемых файловых системах. Это означает:

- На узле файловая система, используемая для `/var/lib/kubelet/pods/` (или настроенного вами каталога), должна поддерживать idmap mounts.
- Все файловые системы, используемые в томах Pod'а, должны поддерживать idmap mounts.

На практике это означает, что нужно **как минимум Linux 6.3**, так как `tmpfs` начал поддерживать idmap mounts в этой версии. Обычно это нужно, поскольку несколько функций Kubernetes используют `tmpfs` (токен service account, монтируемый по умолчанию, использует `tmpfs`; Secret'ы используют `tmpfs` и т.д.).

Некоторые популярные файловые системы, поддерживающие idmap mounts в Linux 6.3: `btrfs`, `ext4`, `xfs`, `fat`, `tmpfs`, `overlayfs`.

Кроме того, container runtime и его нижележащий OCI runtime должны поддерживать user namespaces. Поддержку предлагают следующие OCI runtime:

- **crun** версии 1.9 или выше (рекомендуется 1.13+).
- **runc** версии 1.2 или выше.

Чтобы использовать user namespaces с Kubernetes, также нужен CRI container runtime:

- **containerd**: версия 2.0 (и новее) поддерживает user namespaces для контейнеров.
- **CRI-O**: версия 1.25 (и новее) поддерживает user namespaces для контейнеров.

Статус поддержки user namespaces в `cri-dockerd` отслеживается в issue на GitHub.

## Введение

User namespaces — это функция Linux, позволяющая **отображать пользователей в контейнере на разных пользователей на хосте**. Более того, capabilities, выданные Pod'у в user namespace, **действительны только в namespace** и **недействительны вне него**.

Pod может **включить** использование user namespaces, установив поле `pod.spec.hostUsers` в `false`.

Kubelet выбирает host UID/GID, на которые отображается Pod, так, чтобы **гарантировать, что никакие два Pod'а на одном узле не используют одно и то же отображение**.

Поля `runAsUser`, `runAsGroup`, `fsGroup` и т.д. в `pod.spec` **всегда относятся к пользователю внутри контейнера**. Эти пользователи используются для монтирования томов (указанных в `pod.spec.volumes`), и поэтому **host UID/GID не влияет** на запись/чтение из томов, которые Pod может монтировать. Иными словами, inode'ы, создаваемые/читаемые в томах, смонтированных Pod'ом, будут такими же, как если бы Pod не использовал user namespaces.

Так Pod может легко включать и отключать user namespaces (не затрагивая владение файлами в томах) и **делить тома** с Pod'ами без user namespaces, просто задав соответствующих пользователей внутри контейнера (`RunAsUser`, `RunAsGroup`, `fsGroup` и т.д.). Это относится к любому тому, который Pod может монтировать, включая `hostPath` (если Pod'у разрешено монтировать `hostPath`-тома).

По умолчанию допустимые UID/GID при включении этой функции — диапазон **0–65535**. Это относится к файлам и процессам (`runAsUser`, `runAsGroup` и т.д.).

Файлы с UID/GID вне этого диапазона будут видны как принадлежащие **overflow ID**, обычно `65534` (настраивается в `/proc/sys/kernel/overflowuid` и `/proc/sys/kernel/overflowgid`). Однако **изменить** эти файлы невозможно, даже запустившись как пользователь/группа `65534`.

Если диапазон 0–65535 расширен конфигурационным параметром, вышеуказанные ограничения применяются к расширенному диапазону.

Большинство приложений, которым нужно работать как root, но которые не обращаются к другим host namespace'ам или ресурсам, должны продолжать работать без изменений при активированном user namespace.

## Понимание user namespaces для Pod'ов

Несколько container runtime с конфигурацией по умолчанию (например, Docker Engine, containerd, CRI-O) используют Linux namespaces для изоляции. Существуют и другие технологии, которые можно использовать с этими runtime (например, Kata Containers использует VM вместо Linux namespaces). Эта страница применима к container runtime, использующим Linux namespaces для изоляции.

При создании Pod'а по умолчанию используется несколько новых namespace'ов для изоляции: network namespace для изоляции сети контейнера, PID namespace для изоляции представления процессов и т.д. Если используется **user namespace**, он изолирует **пользователей в контейнере от пользователей на узле**.

Это означает, что контейнеры могут работать как root и **отображаться на не-root пользователя на хосте**. Внутри контейнера процесс будет думать, что работает как root (и поэтому такие инструменты, как `apt`, `dnf` и т.д., работают нормально), тогда как в реальности процесс **не имеет привилегий на хосте**. Это можно проверить, например, посмотрев, от какого пользователя работает процесс контейнера, выполнив `ps aux` на хосте. Пользователь, которого показывает `ps`, **не совпадает** с пользователем, которого вы видите, выполнив внутри контейнера команду `id`.

Эта абстракция **ограничивает** то, что может произойти, например, если контейнеру удастся **вырваться** на хост. Учитывая, что контейнер работает как непривилегированный пользователь на хосте, его возможности на хосте ограничены.

Более того, поскольку пользователи каждого Pod'а отображаются на **разных непересекающихся** пользователей на хосте, ограничено и то, что они могут сделать с **другими Pod'ами**.

Capabilities, выданные Pod'у, также **ограничены** user namespace Pod'а и в основном недействительны вне него, некоторые даже полностью **недействительны**. Два примера:

- `CAP_SYS_MODULE` **не имеет эффекта**, если выдан Pod'у с user namespaces: Pod не может загружать модули ядра.
- `CAP_SYS_ADMIN` **ограничен** user namespace Pod'а и **недействителен** вне него.

Без user namespace контейнер, работающий как root, в случае **container breakout** имеет root-привилегии на узле. И если контейнеру была выдана какая-то capability, эта capability **действительна и на хосте**. Ничего из этого не верно при использовании user namespaces.

Подробнее о том, что меняется при использовании user namespaces, см. `man 7 user_namespaces`.

## Настройка узла для поддержки user namespaces

По умолчанию kubelet назначает Pod'ам UID/GID **выше диапазона 0–65535**, исходя из предположения, что файлы и процессы хоста используют UID/GID в этом диапазоне, что стандартно для большинства дистрибутивов Linux. Этот подход **предотвращает любое пересечение** между UID/GID хоста и UID/GID Pod'ов.

Избегать пересечения важно, чтобы смягчить влияние уязвимостей вроде **CVE-2021-25741**, где Pod потенциально может прочитать произвольные файлы на хосте. Если UID/GID Pod'а и хоста не пересекаются, возможности Pod'а ограничены: UID/GID Pod'а не совпадёт с владельцем/группой файла хоста.

Kubelet может использовать **пользовательский диапазон** user ID и group ID для Pod'ов. Чтобы настроить пользовательский диапазон, на узле должны быть:

- Пользователь `kubelet` в системе (нельзя использовать другое имя пользователя).
- Бинарник `getsubids` (часть `shadow-utils`) и в `PATH` для бинарника kubelet.
- Конфигурация subordinate UID/GID для пользователя `kubelet` (см. `man 5 subuid` и `man 5 subgid`).

Эта настройка только **собирает** конфигурацию диапазона UID/GID и **не меняет** пользователя, выполняющего kubelet.

Нужно соблюдать некоторые ограничения для subordinate ID range, назначаемого пользователю `kubelet`:

- Subordinate user ID, с которого начинается диапазон UID для Pod'ов, должен быть **кратен 65536** и **больше или равен 65536**. Иными словами, нельзя использовать никакой ID из диапазона 0–65535 для Pod'ов; kubelet накладывает это ограничение, чтобы затруднить случайное создание небезопасной конфигурации.
- Количество subordinate ID должно быть **кратно 65536**.
- Количество subordinate ID должно быть **не меньше 65536 × `<maxPods>`**, где `<maxPods>` — максимальное число Pod'ов, которые могут работать на узле.
- Нужно назначить **один и тот же диапазон** и для user ID, и для group ID. Неважно, если у других пользователей есть диапазоны user ID, не совпадающие с диапазонами group ID.
- Ни один из назначенных диапазонов **не должен пересекаться** с любым другим назначением.
- Subordinate-конфигурация должна быть **одной строкой**. Иными словами, нельзя иметь несколько диапазонов.

Например, можно определить `/etc/subuid` и `/etc/subgid` с такими записями для пользователя `kubelet`:

```
# Формат:
#   name:firstID:count of IDs
# где
# - firstID — 65536 (минимально возможное значение)
# - count of IDs — 110 * 65536
#   (110 — лимит по умолчанию для числа Pod'ов на узле)

kubelet:65536:7208960
```

### Примечание о перенастройке узла

Если у вас есть существующий узел, на котором работают Pod'ы с user namespaces, и вы хотите применить вышеописанные настройки:

Конфигурацию следует менять, **когда на узле не работают Pod'ы с user namespaces**. При изменении на узле, где работают такие Pod'ы, нужно сначала **drain** узел перед применением конфигурации и перезапуском kubelet. При drain учитывайте, что DaemonSet-Pod'ы и другие Pod'ы, терпящие taint `unschedulable`, **не будут вытеснены**.

Причина, по которой не должно быть работающих Pod'ов с user namespaces, — они могут использовать **любой диапазон**, потенциально вне нового настроенного диапазона. Kubelet **не запустится**, если не сможет соблюсти новую конфигурацию для существующих Pod'ов на узле.

## Количество ID для каждого Pod'а

Начиная с Kubernetes v1.33, количество ID для каждого Pod'а можно задать в `KubeletConfiguration`:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
userNamespaces:
  idsPerPod: 1048576
```

Значение `idsPerPod` (uint32) должно быть **кратно 65536**. Значение по умолчанию — **65536**. Это значение применяется только к контейнерам, созданным **после** запуска kubelet с этой `KubeletConfiguration`. Работающие контейнеры на эту конфигурацию не реагируют.

В Kubernetes до v1.33 количество ID для каждого Pod'а было **жёстко закодировано** в 65536.

## Интеграция с проверками Pod security admission

Для Linux-Pod'ов, включающих user namespaces, Kubernetes **ослабляет** применение Pod Security Standards контролируемым образом.

Если вы создаёте Pod, использующий user namespaces, следующие поля **не будут ограничиваться** даже в контекстах, применяющих Baseline или Restricted pod security standard. Это поведение **не создаёт проблемы безопасности**, поскольку root внутри Pod'а с user namespaces фактически относится к пользователю внутри контейнера, который **никогда не отображается** на привилегированного пользователя на хосте. Список полей, не проверяемых для Pod'ов в этих обстоятельствах:

- `spec.securityContext.runAsNonRoot`
- `spec.containers[*].securityContext.runAsNonRoot`
- `spec.initContainers[*].securityContext.runAsNonRoot`
- `spec.ephemeralContainers[*].securityContext.runAsNonRoot`
- `spec.securityContext.runAsUser`
- `spec.containers[*].securityContext.runAsUser`
- `spec.initContainers[*].securityContext.runAsUser`
- `spec.ephemeralContainers[*].securityContext.runAsUser`

Кроме того, если Pod находится в контексте с **Baseline** pod security standard, проверка следующих полей также **ослабляется**:

- `spec.containers[*].securityContext.procMount`
- `spec.initContainers[*].securityContext.procMount`
- `spec.ephemeralContainers[*].securityContext.procMount`

При **Restricted** pod security standard Pod по-прежнему должен использовать только `ProcMount` по умолчанию или пустой.

## Ограничения

При использовании user namespace для Pod'а **запрещено** использовать другие host namespaces. В частности, если задан `hostUsers: false`, **нельзя** задавать:

- `hostNetwork: true`
- `hostIPC: true`
- `hostPID: true`

Ни один контейнер не может использовать `volumeDevices` (raw block volumes, например `/dev/sda`). Это включает все массивы контейнеров в спецификации Pod'а:

- `containers`
- `initContainers`
- `ephemeralContainers`

## Поддержка файловых систем

Pod'ы, использующие user namespace, требуют, чтобы файловая система поддерживала **idmap mounts**. Некоторые файловые системы не поддерживают idmap mounts и поэтому **не могут** использоваться с user namespaces. В таких случаях генерируются следующие события. Обратите внимание: детали предупреждения зависят от используемого container runtime.

```
Warning  Failed 1s kubelet Error: failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: failed to fulfil mount request: failed to set MOUNT_ATTR_IDMAP on ${your mount path} invalid argument (maybe the filesystem used doesn't support idmap mounts on this kernel?): unknown
```

**NFS-тома нельзя монтировать** в Pod с user namespace, поскольку Linux NFS-клиент пока не поддерживает idmap mounts. Актуальный список поддерживаемых файловых систем см. в `man`-странице ядра Linux `mount_setattr(2)`.

## Метрики и наблюдаемость

Kubelet экспортирует две prometheus-метрики, специфичные для user namespaces:

- `started_user_namespaced_pods_total` — счётчик, отслеживающий число Pod'ов с user namespaces, которые пытались создать.
- `started_user_namespaced_pods_errors_total` — счётчик, отслеживающий число ошибок при создании Pod'ов с user namespaces.
