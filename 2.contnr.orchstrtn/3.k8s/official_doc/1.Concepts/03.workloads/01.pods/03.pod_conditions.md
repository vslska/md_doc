
# Условия Pod

## Спецификация механизма

Фазовая модель Pod [[02.pod_lifecycle#Фаза Pod (Pod Phase)|(`Pod Phase`)]] предоставляет лишь укрупненную (высокоуровневую) оценку этапа жизненного цикла объекта и является недостаточной для прецизионного мониторинга. Условия (`Pod Conditions`) функционируют как независимые, детализированные индикаторы состояния, которые параллельно отслеживают специфические аспекты готовности Pod (аллокация на узел, готовность рантайма контейнеров, динамическое изменение ресурсов и влияние политик Taint).

---
## Структура условия Pod

Статус Pod содержит массив `PodConditions`, элементы которого показывают, пройдены ли определённые этапы жизненного цикла.

Каждый элемент массива `PodConditions` содержит следующие поля:

| Имя поля             | Описание                                                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `type`               | Название условия Pod.                                                                                                       |
| `status`             | Указывает, выполняется ли условие. Возможные значения: `"True"`, `"False"` или `"Unknown"`.                                 |
| `lastProbeTime`      | Время последней проверки условия Pod.                                                                                       |
| `lastTransitionTime` | Время последнего перехода Pod из одного состояния в другое.                                                                 |
| `reason`             | Машиночитаемое описание причины последнего изменения состояния в формате UpperCamelCase.                                    |
| `message`            | Текстовое описание причины последнего изменения состояния.                                                                  |
| `observedGeneration` | Значение `.metadata.generation` Pod на момент регистрации условия. См. раздел о [[01.pods#Pod generation\|поколениях Pod]]. |

## Встроенные условия Pod

K8s управляет следующими условиями Pod:

- **Условия жизненного цикла** устанавливаются по мере прохождения этапов жизненного цикла Pod, примерно в таком порядке: `PodScheduled`, `PodReadyToStartContainers`, `Initialized`, `ContainersReady`, `Ready`.

- **Другие условия** устанавливаются в ответ на определённые операции или события: `DisruptionTarget`, `PodResizePending`, `PodResizeInProgress`.

Помимо встроенных условий, можно определять собственные с помощью контрольных условий готовности Pod **[[#Расширенная проверка готовности Pod|(Pod readiness gates)]]**.

## Условия жизненного цикла Pod

По мере прохождения Pod этапов жизненного цикла kubelet устанавливает следующие условия примерно в указанном порядке:

1. `PodScheduled`: Pod назначен узлу.
2. `PodReadyToStartContainers`: среда Pod (sandbox) успешно создана, а сеть настроена. За настройку среды и сети отвечают среда выполнения контейнеров и плагин CNI.
3. `Initialized`: все init-контейнеры успешно завершились. Если init-контейнеров нет, это условие получает значение `True` ещё до создания среды Pod.
4. `ContainersReady`: все контейнеры в Pod готовы. Готовность контейнера определяется его пробой готовности, если она настроена.
5. `Ready`: Pod может обрабатывать запросы и должен быть включён в пулы балансировки нагрузки всех соответствующих Services. Pods, не имеющие статуса `Ready`, исключаются из конечных точек Service.

> [!TIP] Примечание
  Условие `Ready` зависит не только от `ContainersReady`. Если в Pod указано поле `readinessGates`, все заданные в нём пользовательские условия также должны иметь значение `True`, чтобы Pod считался готовым. Подробнее см. раздел о готовности Pod.

Просмотреть условия Pod можно с помощью kubectl:

```bash
kubectl get pod <pod-name> -o yaml
```

Ниже показан пример поля `status.conditions` для работающего Pod:

```yaml
status:
  conditions:
    - type: PodScheduled
      status: "True"
      lastProbeTime: null
      lastTransitionTime: "2026-03-29T08:52:21Z"
      observedGeneration: 1
    - type: PodReadyToStartContainers
      status: "True"
      lastProbeTime: null
      lastTransitionTime: "2026-04-11T06:02:16Z"
      observedGeneration: 1
    - type: Initialized
      status: "True"
      lastProbeTime: null
      lastTransitionTime: "2026-03-29T08:52:21Z"
      observedGeneration: 1
    - type: ContainersReady
      status: "True"
      lastProbeTime: null
      lastTransitionTime: "2026-04-11T06:02:45Z"
      observedGeneration: 1
    - type: Ready
      status: "True"
      lastProbeTime: null
      lastTransitionTime: "2026-04-11T06:02:45Z"
      observedGeneration: 1
```

### PodReadyToStartContainers

> **Состояние функции**: *стабильно начиная с Kubernetes v1.37*.


> [!TIP] Примечание
> На ранних этапах разработки это условие называлось `PodHasNetwork`.

После назначения Pod узлу kubelet должен допустить его к выполнению и смонтировать необходимые тома хранилища. Когда эти этапы завершены, kubelet взаимодействует со средой выполнения контейнеров через Container Runtime Interface (CRI), чтобы создать среду выполнения (sandbox) и настроить сеть Pod. После этого в поле `status.conditions` Pod добавляется условие `PodReadyToStartContainers`.

Kubelet устанавливает для этого условия значение `False`, если обнаруживает, что среда выполнения Pod с настроенной сетью отсутствует. Это происходит в следующих случаях:

- В начале жизненного цикла Pod, когда kubelet ещё не приступил к созданию среды с помощью среды выполнения контейнеров.
- На более поздних этапах жизненного цикла, если среда Pod была уничтожена по одной из следующих причин:
    
    - узел перезагрузился, но Pod не был выселен;
    - в средах выполнения контейнеров, использующих виртуальные машины для изоляции, перезагрузилась виртуальная машина среды Pod. В этом случае необходимо создать новую среду и заново настроить сеть контейнеров.

**Kubelet** устанавливает для условия `PodReadyToStartContainers` значение `True` после успешного создания среды Pod и настройки сети плагином среды выполнения. После этого **kubelet** может *начать загружать образы контейнеров и создавать контейнеры*.

Если в Pod есть init-контейнеры, kubelet устанавливает условие `Initialized` в `True` после их успешного завершения, которое происходит уже после создания среды Pod и настройки сети плагином среды выполнения. Если init-контейнеров нет, kubelet устанавливает `Initialized` в `True` до начала создания среды и настройки сети.

## Другие условия Pod

Следующие условия не относятся к обычной последовательности этапов жизненного цикла Pod. Они устанавливаются в ответ на определённые операции или события.

### DisruptionTarget

Условие Pod `DisruptionTarget` добавляется, чтобы указать, что Pod вскоре будет удалён в результате *нарушения доступности [(disruption)](obsidian://open?vault=obsidian&file=vslska%2F2.doc%2F2.contnr.orchstrtn%2F3.k8s%2Fdoc%2F1.Concepts%2F03.workloads%2F01.pods%2F08.disruptions)*. Поле `reason` указывает конкретную причину завершения Pod:

#### `PreemptionByScheduler`

Планировщик собирается вытеснить Pod, чтобы освободить ресурсы для нового Pod с более высоким приоритетом. Подробнее см. раздел о [вытеснении по приоритету Pod](obsidian://open?vault=obsidian&file=vslska%2F2.doc%2F2.contnr.orchstrtn%2F3.k8s%2Fdoc%2F1.Concepts%2F09.scheduling_preemption_eviction%2F05.pod_priority_preemption).

#### `DeletionByTaintManager`

Pod будет удалён менеджером Taint Manager, входящим в контроллер жизненного цикла узлов `kube-controller-manager`, из-за taint `NoExecute`, которому Pod не соответствует. Подробнее см. раздел о выселении на основе [taint](obsidian://open?vault=obsidian&file=vslska%2F2.doc%2F2.contnr.orchstrtn%2F3.k8s%2Fdoc%2F1.Concepts%2F09.scheduling_preemption_eviction%2F03.taints_tolerations).

#### `EvictionByEvictionAPI`

Pod помечен для выселения с помощью Kubernetes API.

#### `DeletionByPodGC`

Pod, привязанный к уже несуществующему узлу, будет удалён в процессе сборки мусора для Pods.

#### `TerminationByKubelet`

Kubelet завершил Pod из-за выселения при нехватке ресурсов узла, корректного завершения работы узла или вытеснения критически важных системных Pods.

В остальных сценариях нарушения доступности, например при выселении из-за превышения ограничений ресурсов контейнера Pod, условие `DisruptionTarget` не устанавливается. В таких случаях нарушение, вероятно, вызвано самим Pod и может повториться при следующей попытке.

> [!TIP] Примечание
  Процесс нарушения доступности Pod может быть прерван. Control plane может повторно попытаться продолжить удаление того же Pod, но это не гарантируется. Поэтому условие `DisruptionTarget` может быть добавлено, даже если Pod в итоге не будет удалён. В таком случае через некоторое время условие нарушения доступности будет сброшено.

Помимо очистки Pods, сборщик мусора Pod (PodGC) помечает их как завершившиеся с ошибкой, если они находятся в нетерминальной фазе. См. также раздел о сборке мусора для Pods.

При использовании Job или CronJob можно включить условия нарушения доступности Pod в политику обработки ошибок Pod для соответствующего задания.

Подробнее см. раздел о нарушениях доступности.

### PodResizePending и PodResizeInProgress

Kubelet обновляет условия статуса Pod, чтобы указать состояние запроса на изменение ресурсов:

- `type: PodResizePending`: kubelet не может сразу выполнить запрос. Причина указывается в поле `message`.
    
    - `reason: Infeasible`: выполнить запрошенное изменение на текущем узле невозможно, например если запрошено больше ресурсов, чем имеется у узла.
    - `reason: Deferred`: сейчас выполнить изменение невозможно, но позднее это может стать возможным, например после удаления другого Pod. Kubelet повторит попытку.
    
- `type: PodResizeInProgress`: kubelet принял запрос на изменение ресурсов и выделил ресурсы, но изменения ещё применяются. Обычно это занимает немного времени, однако в зависимости от типа ресурса и поведения среды выполнения процесс может длиться дольше. Ошибки при применении изменений указываются в поле `message` вместе с `reason: Error`.

Если изменение ресурсов отложено (`Deferred`), kubelet будет периодически повторять попытку, например после удаления другого Pod или уменьшения числа его реплик.

Подробнее см. раздел об изменении ресурсов CPU и памяти, выделенных контейнерам.

## Расширенная проверка готовности Pod

Приложение может передавать дополнительные сигналы или сведения о состоянии в `.status` Pod. Этот механизм называется расширенной проверкой готовности Pod (enhanced Pod readiness).

Чтобы использовать его, укажите в `spec` Pod поле `readinessGates` со списком дополнительных условий, которые kubelet должен учитывать при определении готовности Pod. Затем реализуйте или установите контроллер, управляющий этими пользовательскими условиями. Kubelet будет учитывать их при принятии решения о готовности Pod.

Контрольные условия готовности определяются текущими значениями полей `status.condition` Pod. Если Kubernetes не находит соответствующее условие в поле `status.conditions`, для него по умолчанию устанавливается значение `"False"`.

```
kind: Pod
...
spec:
  readinessGates:
    - conditionType: "www.example.com/feature-1"
status:
  conditions:
    - type: Ready                              # a built-in PodCondition
      status: "False"
      lastProbeTime: null
      lastTransitionTime: 2018-01-01T00:00:00Z
    - type: "www.example.com/feature-1"        # an extra PodCondition
      status: "False"
      lastProbeTime: null
      lastTransitionTime: 2018-01-01T00:00:00Z
  containerStatuses:
    - containerID: docker://abcd...
      ready: true
...
```

Названия добавляемых условий Pod должны соответствовать формату ключей меток Kubernetes.

### Статус готовности Pod

Чтобы задавать значения `status.conditions` Pod, приложения и операторы должны использовать операцию `PATCH` для подресурса `status` Pod. Для этого можно использовать `kubectl patch` с параметром `--subresource=status` или клиентскую библиотеку Kubernetes, написав код для установки пользовательских условий готовности Pod.

Pod с пользовательскими условиями считается готовым только при одновременном выполнении двух требований:

- Все контейнеры Pod готовы.
    
- Все условия, указанные в `readinessGates`, имеют значение `True`.
    

Если контейнеры Pod готовы, но хотя бы одно пользовательское условие отсутствует или имеет значение `False`, kubelet устанавливает для условия `Ready` значение `status: "False"` и причину `reason: ReadinessGatesNotReady`.
