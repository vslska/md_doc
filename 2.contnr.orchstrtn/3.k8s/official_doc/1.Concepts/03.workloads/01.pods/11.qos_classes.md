Эта страница знакомит с классами качества обслуживания (QoS) в Kubernetes и объясняет, как Kubernetes присваивает каждому Pod'у QoS-класс на основе ограничений ресурсов, которые вы задаёте для контейнеров этого Pod'а. Kubernetes использует эту классификацию, чтобы решать, какие Pod'ы вытеснять (evict), когда на узле не хватает доступных ресурсов.

## Классы качества обслуживания

Kubernetes классифицирует запускаемые Pod'ы и относит каждый Pod к определённому классу качества обслуживания (QoS). Kubernetes использует эту классификацию, чтобы влиять на то, как обрабатываются разные Pod'ы. Классификация основана на **запросах ресурсов** (resource requests) контейнеров в Pod'е и на том, как эти запросы соотносятся с **лимитами** (resource limits). Это называется **классом качества обслуживания (QoS)**.

Kubernetes присваивает каждому Pod'у QoS-класс на основе запросов и лимитов ресурсов его контейнеров. QoS-классы используются Kubernetes, чтобы решить, какие Pod'ы вытеснять с узла, испытывающего **node pressure** (нехватку ресурсов). Возможные QoS-классы: **Guaranteed**, **Burstable** и **BestEffort**.

Когда на узле заканчиваются ресурсы, Kubernetes сначала вытеснит **BestEffort**-Pod'ы на этом узле, затем **Burstable** и, наконец, **Guaranteed**. Когда вытеснение вызвано нехваткой ресурсов, кандидатами на вытеснение являются только Pod'ы, **превышающие свои запросы ресурсов**.

### Guaranteed

Pod'ы класса Guaranteed имеют **самые строгие** ограничения ресурсов и **наименее вероятно** будут вытеснены. Им гарантировано, что их не убьют, пока они не превысят свои лимиты или пока на узле не останется Pod'ов с более низким приоритетом, которые можно вытеснить. Они не могут получить ресурсы сверх указанных лимитов. Такие Pod'ы также могут использовать **эксклюзивные CPU** через политику статического управления CPU (static CPU management policy).

**Критерии.** Чтобы Pod получил QoS-класс Guaranteed:

- Каждый контейнер в Pod'е должен иметь **memory limit и memory request**, оба больше нуля.
- Для каждого контейнера в Pod'е **memory limit должен равняться memory request**.
- Каждый контейнер в Pod'е должен иметь **CPU limit и CPU request**, оба больше нуля.
- Для каждого контейнера в Pod'е **CPU limit должен равняться CPU request**.

Если Pod использует **Pod-level resources** (**Beta с Kubernetes v1.34; включено по умолчанию**):

- Pod должен иметь Pod-level memory limit и memory request, и их значения должны быть равны.
- Pod должен иметь Pod-level CPU limit и CPU request, и их значения должны быть равны.

### Burstable

Pod'ы класса Burstable имеют **некоторые нижние гарантии** ресурсов на основе запроса, но **не требуют конкретного лимита**. Если лимит не задан, он по умолчанию эквивалентен ёмкости узла, что позволяет Pod'ам гибко увеличивать ресурсы, если они доступны. При вытеснении Pod'ов из-за нехватки ресурсов на узле эти Pod'ы вытесняются **только после** вытеснения всех BestEffort-Pod'ов. Поскольку Burstable-Pod может включать контейнер без лимитов или запросов ресурсов, такой Pod может попытаться использовать любое количество ресурсов узла.

**Критерии.** Pod получает QoS-класс Burstable, если:

- Pod **не удовлетворяет** критериям QoS-класса Guaranteed.
- Хотя бы один контейнер в Pod'е имеет memory или CPU request или limit, **или** Pod имеет Pod-level memory или CPU request или limit.

### BestEffort

Pod'ы класса BestEffort могут использовать ресурсы узла, которые **не назначены специально** Pod'ам других QoS-классов. Например, если у узла 16 CPU-ядер, доступных kubelet, и вы назначили 4 CPU-ядра Guaranteed-Pod'у, то Pod класса BestEffort может попытаться использовать любое количество оставшихся 12 CPU-ядер.

Kubelet **предпочитает вытеснять** BestEffort-Pod'ы, если узел испытывает нехватку ресурсов.

**Критерии.** Pod имеет QoS-класс BestEffort, если он **не удовлетворяет** критериям ни Guaranteed, ни Burstable. Иными словами, Pod является BestEffort, только если **ни один** контейнер в Pod'е не имеет memory limit или memory request, и **ни один** контейнер не имеет CPU limit или CPU request, и у Pod'а нет Pod-level memory или CPU limit или request. Контейнеры в Pod'е могут запрашивать **другие** ресурсы (не CPU или память) и при этом оставаться в классе BestEffort.

## Memory QoS с cgroup v2

**Beta с Kubernetes v1.37; включено по умолчанию.**

Memory QoS использует memory-контроллер cgroup v2 для управления **memory throttling** и **memory protection** в Kubernetes. Он использует QoS-класс Pod'а, чтобы решить, какие настройки cgroup применить, но **не меняет** классификацию Pod'ов.

Конфигурация kubelet по умолчанию **не включает** ни memory throttling, ни memory protection. Чтобы включить любое из поведений, настройте `memoryThrottlingFactor` или `memoryReservationPolicy` соответственно.

### Memory throttling

Memory throttling управляется полем конфигурации kubelet `memoryThrottlingFactor`. Значение по умолчанию — `nil`, что означает: kubelet **не устанавливает** `memory.high`. Чтобы включить memory throttling, задайте `memoryThrottlingFactor` больше 0 и меньше или равно 1.

Для **Burstable**-Pod'ов kubelet использует `memory.high`, чтобы **притормозить** выделение памяти до того, как workload достигнет жёсткого лимита (`memory.max`). Порог throttling для контейнера вычисляется как:

```
memory.high = requests + memoryThrottlingFactor * (limits - requests)
```

Например, при `memoryThrottlingFactor: 0.9` контейнер с request 256 MiB и limit 1 GiB получит `memory.high` примерно 947 MiB. Если у Burstable-контейнера нет memory limit, kubelet использует **allocatable memory узла** вместо лимита.

Для **BestEffort**-контейнеров, у которых нет memory request или limit, kubelet вычисляет `memory.high`, используя request = 0 и allocatable memory узла вместо лимита. **Guaranteed**-контейнеры **не получают** `memory.high`, поскольку их requests равны limits.

### Настройка memory reservation

Memory reservation управляется полем конфигурации kubelet `memoryReservationPolicy`:

| Значение | Поведение |
|---|---|
| **None** (по умолчанию) | Kubelet не устанавливает `memory.min` или `memory.low` для контейнеров и Pod'ов. Память ядром не блокируется жёстко |
| **TieredReservation** | Kubelet устанавливает **трёхуровневую** memory protection на основе QoS-класса Pod'а:<br>• **Guaranteed**: `memory.min` = memory requests. Ядро **никогда** не вернёт эту память<br>• **Burstable**: `memory.low` = memory requests. Ядро **предпочтительно** сохраняет эту память, но может вернуть её при экстремальном давлении<br>• **BestEffort**: защита памяти не устанавливается |

Пример конфигурации kubelet, включающей memory throttling с фактором 0.9 и трёхуровневую memory protection:

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
memoryThrottlingFactor: 0.9
memoryReservationPolicy: TieredReservation
```

Поля можно настраивать **независимо**. Опустите `memoryThrottlingFactor`, чтобы kubelet не устанавливал `memory.high`, или задайте `memoryReservationPolicy: None`, чтобы отключить memory protection.

Поскольку memory protection cgroup v2 **иерархическая**, kubelet также настраивает **родительские cgroup**. Он устанавливает `memory.min` на корневой cgroup `kubepods` в сумму memory requests для Guaranteed и Burstable Pod'ов. Он устанавливает `memory.low` на корневой cgroup `kubepods` и cgroup Burstable QoS в сумму memory requests для Burstable Pod'ов. Без этого покрытия родительских cgroup защита на уровне Pod'ов и контейнеров была бы неэффективной.

> **⚠️ Внимание:** для Guaranteed-Pod'а memory requests равны memory limits. При `memoryReservationPolicy: TieredReservation` `memory.min` поэтому равен `memory.max`. Для workload'а, использующего большой page cache, ядро может не успеть вернуть достаточно page cache до того, как cgroup достигнет `memory.max`, что может привести к **OOM kill**. Задавайте memory limit с достаточным запасом под page cache.

### Отключение или откат Memory QoS

Чтобы отключить Memory QoS, установите feature gate `MemoryQoS` в `false`, убедитесь, что `memoryReservationPolicy` не задан или равен `None`, и перезапустите kubelet. При старте kubelet сбрасывает `memory.min` и `memory.low` на корневой cgroup `kubepods` и `memory.low` на cgroup Burstable QoS в ноль. Значения `memory.min` и `memory.low` на уровне Pod'ов и контейнеров могут остаться, но они **неэффективны**, поскольку соответствующая родительская защита равна нулю.

Когда Memory QoS отключён, kubelet устанавливает `memory.high` в `max` всякий раз, когда container runtime применяет конфигурацию ресурсов к новому, перезапущенному или изменённому на месте (in-place resized) контейнеру. Уже работающий контейнер, который не перезапускается и не изменяется, может сохранять предыдущее значение `memory.high` до следующего перезапуска или in-place resize.

### Системные требования

Memory QoS требует Linux с cgroup v2. Рекомендуется ядро **5.9 или выше**, поскольку throttling `memory.high` на более старых ядрах может вызвать известный баг **livelock**. Если feature gate `MemoryQoS` включён на старом ядре, kubelet пишет предупреждение при старте.

## Некоторое поведение не зависит от QoS-класса

Определённое поведение **не зависит** от QoS-класса, присвоенного Kubernetes. Например:

- Любой контейнер, **превышающий лимит** ресурсов, будет убит и перезапущен kubelet, не затрагивая другие контейнеры в этом Pod'е.
- Если контейнер превышает свой **resource request** и узел, на котором он работает, испытывает нехватку ресурсов, Pod, в котором он находится, становится **кандидатом на вытеснение**. В этом случае все контейнеры Pod'а завершаются. Kubernetes может создать замещающий Pod, обычно на другом узле.
- **Resource request** Pod'а равен сумме resource requests его контейнеров, а **resource limit** Pod'а равен сумме resource limits его контейнеров.
- **kube-scheduler не учитывает QoS-класс** при выборе Pod'ов для вытеснения (preempt). Preemption может произойти, когда в кластере не хватает ресурсов для запуска всех определённых вами Pod'ов.
- **QoS-класс определяется при создании Pod'а и остаётся неизменным в течение жизни Pod'а**. Если позже вы попытаетесь выполнить in-place resize, который привёл бы к другому QoS-классу, resize будет **отклонён admission**.
