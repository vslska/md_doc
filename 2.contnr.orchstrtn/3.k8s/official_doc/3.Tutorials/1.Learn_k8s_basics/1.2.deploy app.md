## Теория: Deployment и ReplicaSet

### Иерархия объектов

```
┌─────────────────────────────────────────────────────────┐
│                    Deployment                           │
│  "Хочу 3 копии приложения my-app с образом my-app:v1"   │
│  Отвечает за: обновления, rollback, стратегии           │
└────────────────────┬────────────────────────────────────┘
                     │ создаёт и управляет
                     ▼
┌─────────────────────────────────────────────────────────┐
│                  ReplicaSet                             │
│  "Поддерживаю 3 реплики Pod'ов"                         │
│  Отвечает за: создание/удаление Pod'ов, самовосстановление│
└────────────────────┬────────────────────────────────────┘
                     │ создаёт и управляет
                     ▼
┌─────────────────────────────────────────────────────────┐
│                     Pods                                │
│  ┌─────┐  ┌─────┐  ┌─────┐                              │
│  │Pod 1│  │Pod 2│  │Pod 3│                              │
│  └─────┘  └─────┘  └─────┘                              │
│  Отвечают за: запуск контейнеров                        │
└─────────────────────────────────────────────────────────┘
```

### Функциональные роли компонентов

#### Deployment

**Роль: менеджер объектов ReplicaSet.**

Функции:

- Создание ReplicaSet.
- Управление процедурами поэтапного обновления (rolling updates) путем создания нового ReplicaSet и плавного перенаправления трафика.
- Управление процессом отката (rollback) к предыдущим версиям.
- Поддержка стратегий обновления (`RollingUpdate`, `Recreate`).

Ограничения:

- Не создает Pod'ы напрямую.
- Не отслеживает напрямую точное количество активных Pod'ов.

#### ReplicaSet

**Роль: менеджер объектов Pod.**

Функции:

- Создание и удаление Pod'ов.
- Поддержание целевого количества реплик (desired replicas) — при сбое Pod'а создается новый экземпляр.
- Обеспечение самовосстановления при выходе из строя узла.

Ограничения:

- Не управляет стратегиями обновлений приложений.

#### Pod

**Роль: минимальная неделимая единица развертывания.**

Функции:

- Запуск контейнеров приложения.
- Предоставление общего сетевого стека и томов хранения.

### Аналогия с организационной структурой

- **Deployment** — руководитель проекта, определяющий целевые параметры команды, нанимающий менеджеров смен и управляющий сменой версий продукта.
- **ReplicaSet** — менеджер смены, контролирующий поддержание заданного количества исполнителей на линии и оперативно заменяющий выбывших сотрудников.
- **Pod** — непосредственный исполнитель (рабочая единица).

### Сценарии жизненного цикла

#### Сценарий 1: Создание Deployment

1. Отправка команды создания объекта с помощью `kubectl create deployment`.
2. Регистрация объекта Deployment в хранилище `etcd` через API Server.
3. Deployment Controller формирует соответствующий ReplicaSet.
4. ReplicaSet Controller инициирует создание требуемого числа Pod'ов.
5. Планировщик (Scheduler) назначает Pod'ы на доступные узлы кластера.
6. Демон `kubelet` запускает контейнеры через среду выполнения.

#### Сценарий 2: Отказ Pod'а

1. Аварийное завершение работы контейнера внутри Pod'а.
2. `kubelet` фиксирует статус завершения и передает информацию API Server.
3. ReplicaSet Controller обнаруживает отклонение текущего числа готовых реплик от целевого.
4. Запускается создание нового Pod'а с аналогичной спецификацией.

#### Сценарий 3: Поэтапное обновление (Rolling Update)

1. Изменение версии контейнерного образа в спецификации Deployment.
2. Создание нового ReplicaSet под новую версию приложения.
3. Поочередное уменьшение реплик в старом ReplicaSet и увеличение в новом.

#### Сценарий 4: Откат версии (Rollback)

1. Инициализация команды возврата к предыдущей ревизии.
2. Уменьшение числа реплик текущего ReplicaSet и масштабирование предыдущего.

### Контроллеры в составе Controller Manager

|**Контроллер**|**Контролируемый объект**|**Основная задача**|
|---|---|---|
|**Deployment Controller**|Deployment|Управление жизненным циклом ReplicaSet'ов|
|**ReplicaSet Controller**|ReplicaSet|Контроль количества и состояния Pod'ов|
|**Node Controller**|Nodes|Мониторинг состояния вычислительных узлов|
|**Job Controller**|Job|Управление задачами пакетной обработки|
|**EndpointSlice Controller**|Services|Синхронизация сетевых эндпоинтов|

## Основы kubectl

### Синтаксис команд

```bash
kubectl <action> <resource> [flags]
```

|**Компонент**|**Назначение**|**Пример**|
|---|---|---|
|`kubectl`|Клиентская утилита управления Kubernetes|`kubectl`|
|`<action>`|Выполняемое действие|`get`, `create`, `delete`, `describe`|
|`<resource>`|Целевой объект управления|`pods`, `deployments`, `replicasets`|
|`[flags]`|Дополнительные модификаторы|`-o yaml`, `-n kube-system`|

### Базовые команды

- `kubectl get <resource>` — вывод списка ресурсов.
- `kubectl describe <resource> <name>` — детальная диагностическая информация.
- `kubectl create <resource>` — императивное создание объекта.
- `kubectl apply -f <file>` — декларативное создание или обновление объектов.
- `kubectl delete <resource> <name>` — удаление ресурса.
- `kubectl logs <pod-name>` — просмотр потока вывода логов контейнера.
- `kubectl exec -it <pod-name> -- /bin/sh` — интерактивный доступ внутрь контейнера.

## Практика: Развертывание приложения

### Шаг 1: Проверка клиента и подключения

Проверка клиентской версии и доступности управляющего API-сервера:

```bash
kubectl version --client
kubectl version
```

### Шаг 2: Верификация узлов кластера

```bash
kubectl get nodes
```

Ожидаемый результат:

```bash
NAME       STATUS   ROLES           AGE   VERSION
minikube   Ready    control-plane   10m   v1.29.0
```

### Шаг 3: Создание Deployment

Развертывание тестового приложения `kubernetes-bootcamp`, поднимающего веб-сервер на порту `8080`:

```bash
kubectl create deployment kubernetes-bootcamp \
  --image=gcr.io/google-samples/kubernetes-bootcamp:v1
```

### Шаг 4: Проверка статуса Deployment

```Bash
kubectl get deployments
```

Ожидаемый результат:

```Bash
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
kubernetes-bootcamp   1/1     1            1           30s
```

### Шаг 5: Проверка ReplicaSet

```Bash
kubectl get replicasets
kubectl describe deployment kubernetes-bootcamp
```

Ожидаемый результат:

```Bash
NAME                             DESIRED   CURRENT   READY   AGE
kubernetes-bootcamp-7d4f8b7b9c   1         1         1       1m
```

### Шаг 6: Проверка Pod'ов

```bash
kubectl get pods
kubectl get pods -o wide
```

Ожидаемый результат:

```bash
NAME                                   READY   STATUS    RESTARTS   AGE
kubernetes-bootcamp-7d4f8b7b9c-x2y4z   1/1     Running   0          1m
```

### Шаг 7: Проверка системных событий

```bash
kubectl get events
```

## Доступ к приложению через API Proxy

Поскольку Pod'ы функционируют в изолированной виртуальной сети кластера с внутренними IP-адресами, для отладочного доступа используется локальный прокси-сервер `kubectl proxy`.

### Шаг 8: Запуск прокси-соединения

В отдельном терминале выполняется команда:

```bash
kubectl proxy
```

Ожидаемый результат:

```bash
Starting to serve on 127.0.0.1:8001
```

### Шаг 9: Проверка доступности API

```bash
curl http://localhost:8001/version
```

### Шаг 10: Получение имени запущенного Pod'а

```bash
export POD_NAME=$(kubectl get pods -o jsonpath='{.items[0].metadata.name}')
echo "Name of the Pod: $POD_NAME"
```

### Шаг 11: Обращение к приложению через прокси

```bash
curl http://localhost:8001/api/v1/namespaces/default/pods/$POD_NAME:8080/proxy/
```

Ожидаемый результат:

```bash
Hello Kubernetes bootcamp! | Running on: kubernetes-bootcamp-7d4f8b7b9c-x2y4z | v=1
```

## Практические задания

- Просмотр диагностических логов Pod'а:

```bash
kubectl logs $POD_NAME
```

- Интерактивный вход в контейнер:

```bash
kubectl exec -it $POD_NAME -- /bin/bash
```

- Детальный анализ ReplicaSet:

```bash
kubectl describe replicaset kubernetes-bootcamp-7d4f8b7b9c
```
  
- Тестирование механизма самовосстановления (удаление Pod'а и наблюдение за автоматическим созданием нового экземпляра ReplicaSet Controller'ом):

```bash
kubectl delete pod $POD_NAME
kubectl get pods
```
  
- Масштабирование количества реплик развертывания:
  
```bash
kubectl scale deployment kubernetes-bootcamp --replicas=3
kubectl get pods
```

## Устранение неполадок (Troubleshooting)

- При возникновении статуса `ImagePullBackOff` проверяется корректность имени образа и доступность реестра.
- В случае статуса `CrashLoopBackOff` анализируются логи контейнера с помощью `kubectl logs $POD_NAME --previous`.
