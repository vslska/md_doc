
# Диагностика CrashLoopBackOff в Kubernetes

**CrashLoopBackOff** означает, что контейнер падает, Kubernetes пытается его перезапустить, он снова падает, и K8s переходит в режим экспоненциальной задержки (BackOff), чтобы не нагружать ноду.

Главное правило диагностики: **Сначала смотрим `describe`, потом `logs --previous`.**

---

## 1. `Init:CrashLoopBackOff`

**Суть:** Падает **init-контейнер** (контейнер инициализации). 
**Главное следствие:** Основные контейнеры приложения **даже не стартуют**, пока init-контейнер не завершится с кодом `0`.

### Типичные причины:
1. **Ошибки в скриптах:** Опечатки в bash/sh, отсутствие утилит в минимальном образе (нет `curl`, `jq`, `wget`).
2. **Ожидание зависимостей:** Скрипт ждет БД, но при первой ошибке `connection refused` падает, вместо того чтобы делать `sleep` и ретраи.
3. **Проблемы с ConfigMaps/Secrets:** Скрипт ищет файл/переменную, а их нет (опечатка в имени ключа, неверный путь монтирования).
4. **Права доступа (Permissions):** Попытка записать данные в `readOnly` том или конфликт UID/GID (init-контейнер от root создал файл, а основное приложение от `nobody` не может его прочитать).
5. **Сетевые ошибки:** Init-контейнер пытается скачать конфиг/сертификат из интернета (Vault, S3), но у Pod нет доступа (NetworkPolicy) или ошибка TLS.

### 🛠 Как чинить:
```bash
# 1. Смотрим, какой именно init-контейнер падает
kubectl describe pod <pod-name> -n <namespace>

# 2. Читаем логи упавшего init-контейнера (замените <init-name> на имя из describe)
kubectl logs <pod-name> -c <init-name> -n <namespace>

# 3. ⚠️ САМОЕ ВАЖНОЕ: Логи ПРЕДЫДУЩЕЙ неудачной попытки
kubectl logs <pod-name> -c <init-name> --previous -n <namespace>
```

## 2. `CrashLoopBackOff` (без префикса Init)

**Суть:** Init-контейнеры отработали успешно, упал **основной контейнер** приложения.

### Типичные причины:
1. **Ошибки кода:** Непойманные исключения (Java `NullPointerException`, Go `panic`, Python `ImportError`).
2. **Неверная конфигурация:** Отсутствие обязательных ENV-переменных, битый JSON/YAML в ConfigMap.
3. **Недоступность зависимостей:** Приложение использует паттерн "fail-fast" и падает при старте, если не может подключиться к БД/Redis.
4. **Ошибки образа:** Неверный `command`/`args` в манифесте, у бинарника нет прав на исполнение (`chmod +x`).
5. **Нехватка ресурсов (OOM):** Приложение съело больше памяти, чем указано в `resources.limits.memory`.

### 🚨 Скрытая причина: Liveness / Startup Probes
**Приложение НЕ падает само по себе!** Оно работает нормально, но Kubernetes убивает его, потому что зонды (probes) не проходят.
* **Слишком агрессивный `livenessProbe`:** Приложение на время "задумалось" (например, сборка мусора в Java), зонд не получил ответ, K8s убил Pod.
* **Нет `startupProbe`:** Тяжелое приложение стартует 2 минуты, а `livenessProbe` начинает проверять его через 30 секунд и убивает на старте.

### 📊 Шпаргалка по Exit Code (смотреть в `kubectl describe`)

| Exit Code | Расшифровка | Что делать |
| :--- | :--- | :--- |
| **1** | Ошибка приложения / конфига | Читать `logs --previous`. Искать трейсбек, ошибку парсинга, отсутствие ENV. |
| **137** | **OOMKilled** (SIGKILL) или убит Liveness | Проверить `resources.limits.memory`. Если памяти хватает — смотреть `Events` на предмет `Liveness probe failed`. |
| **139** | Segmentation Fault | Ошибка в C/C++ коде или нативных библиотеках. Смотреть core dump / логи. |
| **143** | SIGTERM (Graceful shutdown) | Обычно означает, что его корректно остановил `livenessProbe`. Проверять таймауты зондов. |
| **126** | Permission denied | Нет прав на запуск бинарника/скрипта (нет `chmod +x` в Dockerfile). |
| **127** | Command not found | Ошибка в `command` / `args` в манифесте Deployment. |

### 🛠 Как чинить:
```bash
# 1. Смотрим Exit Code и события (ищем Liveness/Startup probe failed)
kubectl describe pod <pod-name> -n <namespace>

# 2. Читаем логи предыдущего запуска
kubectl logs <pod-name> -c <container-name> --previous -n <namespace>
```

## 💡 Быстрый алгоритм

1. **Есть префикс `Init:`?** → Проблема в скриптах подготовки. Ищи имя init-контейнера в `describe` и читай его логи.
2. **Exit Code `1`?** → Проблема в коде, конфиге или сети. Читай `logs --previous`.
3. **Exit Code `137` или `143`?** → Проблема в ресурсах или зондах. Проверяй `limits.memory`, `livenessProbe`, `startupProbe`.
4. **В логах пусто, но Pod падает?** → Скорее всего, его убивает `livenessProbe` (смотри `Events` в `describe`) или это OOM, который не успел написать в stdout.
5. **Всегда используй флаг `--previous`** (или `-p`), иначе будешь читать логи текущего, еще не упавшего (или уже очищенного) запуска.
