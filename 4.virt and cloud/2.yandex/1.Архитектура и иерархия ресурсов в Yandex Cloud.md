## Архитектурный разбор ресурсной модели Resource Manager

### Фундаментальные принципы изоляции

Организация структуры ресурсов в Yandex Cloud опирается на модель управления **Resource Manager**, которой следует подавляющее большинство сервисов платформы. Архитектура спроектирована таким образом, чтобы обеспечить жесткую логическую, финансовую и административную изоляцию между различными проектами и командами.

Все вычислительные и инфраструктурные объекты (включая виртуальные машины, диски, сети и базы данных) размещаются строго внутри **каталогов**. Создание любого ресурса требует обязательного указания целевого каталога.

```
               [ Организация (Yandex Identity Hub) ]
                                │
                                ▼
                       [ Облако (Cloud) ]
                                │
         ┌──────────────────────┼──────────────────────┐
         ▼                      ▼                      ▼
  [ Каталог (Folder) ]   [ Каталог (Folder) ]   [ Каталог (Folder) ]
  (Среда: Development)   (Среда: Staging)     (Среда: Production)
         │                      │                      │
         ▼                      ▼                      ▼
     [ Ресурсы: ]           [ Ресурсы: ]           [ Ресурсы: ]
    - ВМ, Сети, Диски      - ВМ, Сети, Диски      - ВМ, Сети, Диски
```

## Уровни иерархии ресурсов

### 1. Организации

- **Назначение:** Корневой элемент иерархии, объединяющий все облака компании под единым управлением. Организация связывается с платежным аккаунтом и управляется через специализированный сервис **Yandex Identity Hub**.
- **Особенности изоляции:** Организации полностью изолированы друг от друга. Средства Yandex Cloud не поддерживают прямое взаимодействие между ресурсами разных организаций. На уровне организации настраиваются федерации удостоверений (SSO), группы пользователей и общие политики безопасности.

### 2. Облака (Clouds)

- **Назначение:** Изолированные пространства первого уровня, в которых создаются каталоги. Облако выступает в роли финансово-юридической сущности, к которой привязан платежный аккаунт.
- **Особенности изоляции:** Облака по умолчанию полностью изолированы друг от друга. Переносить созданные ресурсы (например, диски или виртуальные машины) между разными облаками **невозможно** (кроме случаев организации специфического сетевого взаимодействия через VPN или публичные IP-адреса на уровне самих сервисов).

### 3. Каталоги (Folders)

- **Назначение:** Логические пространства (контейнеры), в которых непосредственно создаются и группируются все ресурсы Yandex Cloud.
- **Архитектурная роль:** Каталоги выполняют функцию папок для разделения инфраструктуры по проектам, командам, департаментам или типам сред (например, `dev-folder`, `stage-folder`, `prod-folder`).
- **Ограничения структуры:** Каталог всегда принадлежит одному конкретному облаку (не существует каталогов вне облака). Создание вложенных каталогов (каталог внутри каталога) архитектурно не поддерживается.

## Управление владельцами и ролями в облаке

### Владелец облака (`resource-manager.clouds.owner`)

- Пользователь, которому назначена системная роль владельца на конкретное облако. Создатель облака автоматически получает этот статус.
- Обладает абсолютными привилегиями: может выполнять любые операции с облаком и ресурсами внутри него, а также назначать и отзывать любые роли у других пользователей (включая передачу или отзыв роли владельца).
- **Правила безопасности:** У каждого облака в обязательном порядке должен быть как минимум один владелец. Единственный владелец облака технически не может лишить этой роли самого себя.

### Участник облака (`resource-manager.clouds.member`)

- Специализированная служебная роль, которая **не предоставляет** прав на создание, изменение или удаление каких-либо вычислительных ресурсов.
- Применяется в тех случаях, когда пользователю необходимо предоставить базовый доступ к консоли управления Yandex Cloud без расширенных привилегий. Обеспечивает минимальный видимый контекст облака при строгом соблюдении принципа наименьших привилегий.

## Механизм наследования прав доступа

Проверка прав доступа при выполнении любой операции в платформе осуществляется службой Identity and Access Management (IAM) на основе иерархического наследования сверху вниз:

1. **Уровень организации:** Права, выданные на организацию, автоматически распространяются на все вложенные федерации, группы пользователей и облака.
2. **Уровень облака:** Права, назначенные на облако, наследуются всеми каталогами, находящимися внутри этого облака.
3. **Уровень каталога:** Права на каталог распространяются на все ресурсы, созданные в его пределах.

> **Практический пример наследования:**
> 
> Назначение роли `resource-manager.viewer` на уровень организации позволяет пользователю просматривать общую структуру и список всех облаков и каталогов в консоли управления без возможности модификации. Назначение роли `editor` на конкретное облако предоставляет полный контроль над ресурсами во всех каталогах этого облака. В то же время назначение роли `admin` локально на отдельный каталог ограничивает зону административных полномочий пользователя исключительно рамками этого каталога.

_(Примечание: Помимо ролей, выполнение операций может жестко блокироваться специальными **политиками авторизации**, имеющими приоритет над назначенными ролями)._

## Жизненный цикл удаления ресурсов и ограничения

Удаление облаков и каталогов — это двухэтапный защищенный процесс, предотвращающий случайную потерю данных:

1. **Статус ожидания (`PENDING_DELETION`):** При запросе на удаление ресурс переводится в режим ожидания (по умолчанию — **7 дней**). В течение этого периода все запущенные внутри него вычислительные ресурсы принудительно останавливаются. Администратор может отменить удаление в любой момент до истечения срока.
2. **Статус удаления (`DELETING`):** По завершении периода ожидания запускается необратимый процесс физического уничтожения ресурса и всех вложенных компонентов, занимающий до 72 часов.

### Причины блокировки и отмена удаления

- **Политики авторизации:** Удаление может быть заблокировано специальными запрещающими политиками `resourceManager.denyFolderRemoval` или `resourceManager.denyCloudRemoval` на уровне каталога, облака или организации. Перед удалением такие политики необходимо предварительно отозвать.
- **Автоматический откат системы (`ACTIVE`):** Процесс удаления может быть принудительно прерван платформой, если сетевые ресурсы (например, IP-адреса Yandex Virtual Private Cloud) из удаляемого каталога продолжают использоваться виртуальными машинами из других каталогов, либо если в каталоге присутствуют защищенные кластеры баз данных. В этом случае каталог возвращается в статус `ACTIVE`, однако часть задействованных компонентов может оказаться необратимо удаленной, а оставшиеся продолжат тарифицироваться.

## Справочник команд CLI для управления иерархией

| **Задача**                | **Команда CLI**                                   | **Описание**                                        |
| ------------------------- | ------------------------------------------------- | --------------------------------------------------- |
| **Проверка конфигурации** | `yc config list`                                  | Вывод текущего активного профиля, облака и каталога |
| **Список облаков**        | `yc resource-manager cloud list`                  | Аудит доступных облаков организации                 |
| **Список каталогов**      | `yc resource-manager folder list`                 | Просмотр каталогов в текущем облаке                 |
| **Создание каталога**     | `yc resource-manager folder create --name <name>` | Регистрация нового проектного каталога              |
| **Список аккаунтов**      | `yc iam service-account list`                     | Вывод сервисных учетных записей                     |

## Заключение

Ресурсная модель Yandex Cloud на базе Resource Manager предоставляет строгий архитектурный фундамент для построения отказоустойчивых и безопасных сред. Понимание принципов иерархии, итерационного наследования прав и ограничений жизненного цикла позволяет проектировать инфраструктуру в полном соответствии с лучшими практиками информационной безопасности и индустриальными стандартами управления облачными ресурсами.
